# Standard library — modules guide

Loaded when working under `modules/`. Repo-wide rules live in the root `CLAUDE.md` — including the MANDATORY module documentation, description and release rules. The loader side of controller delivery lives in the kernel (`kernel/nodejs/CLAUDE.md`); kind semantics and annotations in `analyzer/nodejs/CLAUDE.md`.

## Tests

**A module has no integration tests in Node.** A test that needs something running (a database, a network service, a container) is a Telo manifest under `modules/<name>/tests/integration/*.yaml`, run by `pnpm run test:integration` in the CI job that provides that infrastructure. `nodejs/` may carry vitest unit tests that need nothing running, and never a `test:integration` script: `pnpm -r test:integration` is the kernel's Docker job, which has no database, so a module script there fails CI.

## Standard library notes

`modules/` — standard library: `http-server`, `http-client`, `sql`, `javascript`, `config`, `run`, `assert`, `test`, `console`, etc.

Outbound authentication is one seam: `Http.Credential` (an abstract on `http-client`) takes the request about to be sent and returns headers / query to merge into it, so bearer tokens, API keys and request-signing schemes share one contract; the request controller owns the 401 `forceRefresh`-and-retry-once so no implementation re-expresses it. `oauth-client` implements it for OAuth 2.0 and owns the flows (consent, exchange, refresh, device, client credentials) plus grant storage over `KvStore.Store`.

**An application can be a resource of another application**: `app`'s `App.Instance` starts the manifest at `source:` when it runs, supplies the child's declared `variables` / `secrets` / `ports` **by the child's own names** (lowered to its env bindings by the kernel, so a parent can never set a key the child did not declare), holds the kernel while the child runs, and reports `status.exitCode`. It is how several applications are supervised from one manifest and — since an application cannot be imported — the only way a test reaches the file a user copies, declared in a `Run.Sequence`'s `with:` so the child is torn down with the scope. There is deliberately **no `replicas:` count and no pool**: replicas are addressable peers, and a count cannot give a member the name a `!ref`, a nested `with:` or a status path needs; the shared configuration goes in a kind (`extends: App.Instance` + `base:`) and the members are declared. **The child's input contract is enforced at BOOT ONLY** — a supplied name the child does not declare is refused when it starts (`ERR_MANIFEST_VALIDATION_FAILED`, naming the declared set), and `telo check` says nothing, because checking it needs the child's manifest in hand while analysing the parent and the loader follows no such edge yet. Closing it means the loader resolving a `source:` the way it resolves an import, carrying the child's docs into the analysis, and one pass over them; until then this is a known check/run gap rather than an oversight, and the kind's `source:` field says so. `Assert.Manifest` stays for manifests that are SUPPOSED to fail — it runs one under a hard bound and pins a static verdict to the runtime one, which is why its `source:` resolves nothing statically.

**Talking to a running program is `channel`**, not whoever started it: `Channel.Text` (abstract) is anything reachable as duplex text — a child application today, a shell session or a remote host tomorrow — and `Channel.SendLine` / `Channel.ReadUntil` / `Channel.End` are invocables that name one through a ref slot. `App.Instance` merely `extends: Channel.Text`. Owning the vocabulary in `app` would force `shell` to import `app` to drive a session, or to re-invent reading with its own timeout, match and error codes. A read is bounded and consumes through its literal marker (`ERR_CHANNEL_READ_TIMEOUT` carries what arrived instead); retention is armed by the READER, so a channel nothing reads buffers nothing and a supervised server child stays flat; one reader per channel, since two would take each other's text. Conditional dialogue is the step grammar, deliberately not a script kind.

**Long polling is `watch`**: `Watch.Wait` holds a call until a topic's version passes the caller's cursor (timeout is data, capped by a creation-time `maxTimeout`), and `Watch.Publish` raises the version monotonically, waking every waiter below it. The `Watch.Store` is ONLY a wake-up signal — it remembers the latest version per topic so a publish landing between the caller's read and its wait still wakes it, and may forget idle topics — while the caller's database stays the source of truth, read before and after every wait. It is non-durable by declaration (`x-telo-violates-zone: replayed`); a one-value-to-one-waiter hand-off is a different primitive.

Two key/value abstracts coexist and differ by GUARANTEE, not operations: `Cache.Store` (freshness, evictable) and `KvStore.Store` (durable, non-evicting, atomic `putIfAbsent`/`compareAndSet`). `KvStore.Store` is storage only — the claim/settle/release protocol lives once in `KeyedClaim` (`@telorun/kv-store`), which `Lease.Critical` and `Idempotency.Once` both use, so no backend reimplements it.

**Binary objects are `blob`** (storage-neutral: the `Blob.Store` abstract, the `Blob.Key` shape and four invocables — `Put`, `Get`, `Head`, `Delete` — each naming a store through a ref slot) plus a backend, `blob-fs` today: one file per blob at a path derived from the SHA-256 of its key, a JSON header line and then the content, committed by a single rename out of `<root>/.tmp/`. **A store stores, and the operations do everything else, once for every backend**: `Blob.Put` hands the store a wrapped source that counts, hashes, checks each chunk is bytes and fails on the chunk that crosses `maxBytes`, so a refusal reaches a store as an ordinary source failure; `Blob.Get` compares the size a store reports with its bound and releases the unread content itself; `Blob.Get` and `Blob.Head` reduce whatever media type a store's medium recorded to the module's one vocabulary. The operation kinds own every code (`ERR_BLOB_NOT_FOUND`, `ERR_BLOB_TOO_LARGE`); a backend implements four methods (`@telorun/blob`, normative in `modules/blob/docs/store-contract.md`) — `put` and `delete` resolving with nothing, `get` and `head` with `found` or `absent`, each taking the invocation context last so a remote call can be cancelled — and **is recognised by those methods alone**, never by its class or by having imported the module's code, because a backend may live in another repository. The contract asks for nothing a remote object store cannot give (a streamed put that stores nothing unless the whole source arrived, atomic replace, idempotent delete, every valid key held), grows only additively, and deliberately has no list, copy, range read or time-limited link — a link arrives as a second abstract level, since no backend here can sign one. Nothing under `modules/blob` names a backend. **Each sink owns its byte bound** (`Blob.Put.maxBytes`, `Fs.FileWrite.maxBytes`) and there is no stream-level limiting kind: only the contract that persists can refuse before reading, name what was being written and cover the non-stream forms of the same input; a sink rethrows a source failure intact, removes its own staging and releases a source it did not finish, pulled or not; a store never releases. **A store's `get` leaves nothing open**: the content opens the read at its first pull and fails that pull when the blob no longer has the reported size and media type or is gone, and a read that has begun delivers that blob whole or fails. **A stream branch in a contract's `anyOf` admits any value at run time**, since a live value is never validated, so a kind taking "bytes or a stream" refuses anything else in its controller under `ERR_INPUT_INVALID` — the contract's own code, which a chunk of such a stream that is not bytes shares.

**What bytes are is `media-type`**: `MediaType.Detector` reads at most 4,096 leading bytes, returns the media type they support, whether the declared one was contradicted, and a stream of every input byte. It never refuses and declares no codes — the caller refuses, on `mislabelled` and then on its own accept list. The recognised set is one closed data file at the module root (`media-types.json`), a type either proven by its own signature or vouched for by its container's, and its output pattern is the one `blob` uses, pinned by a unit test that reads both manifests; neither module imports the other. **`Image.Fit` judges an image from its header before decoding** (`maxBytes`, then `maxPixels`), rewrites the orientation tag as upright in the copy it decodes and applies the orientation of any format carrying EXIF itself, so the result is upright once whatever the decoder does. `pdf`'s staged canvas addon (`sources.canvas.version`) and the `@napi-rs/canvas` wrapper the lockfile holds are one version, because `pdf` sets the addon path process-wide and every wrapper loaded afterwards — `image`'s included — opens that file.

**Declarative schema** is `sql`'s `Table` / `Schema` abstracts plus a backend (`postgres`, `sqlite`) that owns its whole type vocabulary, DDL rendering, introspection and locking; the shared half — the diff, the ledger, the tombstones and the phase ordering — ships through `@telorun/sql` as a module library. The split is the point: a neutral column-type vocabulary is a lowest-common-denominator one, so what crosses the boundary is a JSON Schema PROJECTION of the row, declared as data by each backend. **A table has two column maps**: `columns` is the row contract, and `internalColumns` holds columns in the same engine vocabulary that are outside it. `columns` is always written and may be `{}` only beside a non-empty `internalColumns` — a table with no row contract, whose projection is a closed object with no properties; it cannot be omitted, because the projection reads an absent entry collection as a failure rather than as empty. Normalization merges the two into one column list — so the diff, the ledger snapshot, tombstones and reclamation cannot tell them apart, and moving a column between the maps is no change — and keeps only the internal NAMES beside it (`DeclaredTable.internalColumns`), which is what a consumer reading the declaration filters on; the projection reads `columns` alone, so no contract and no seed row sees an internal column. An engine `Table` kind declares the second map as a `$ref` to its own column entry schema, so the vocabulary is stated once. One name in both maps is `SQL_COLUMN_DECLARED_TWICE`, a rule on `Sql.Table` twinned in normalization. A rule iterates one collection and a code names one rule per kind, so the two rename rules exist a second time for the internal map — `SQL_INTERNAL_COLUMN_RENAME_FROM_SELF` and `SQL_INTERNAL_COLUMN_RENAME_SOURCE_STILL_DECLARED` — while every rule about the table's columns as a whole reads both maps, each guarded for an absent one.

**Durable execution** is `durable` (the backend-neutral `Durable.Run` marker + `Durable.Idempotent`), a BACKEND (`durable-local` today: `Workflow` + the `Journal` abstract + `Resumer`) and a journal — `durable-journal-file` (a directory, one machine) or `durable-journal-postgres` (two tables, several machines: claiming is one conditional `UPDATE`, waking is `LISTEN`/`NOTIFY`). The split is deliberate — what is shared is a narrow replay seam, never a portable engine vocabulary, because flattening lifecycle models costs fidelity in both directions and nobody switches durable engines twice. **Exactly-once is a property of the JOURNAL's location, not of durable execution**: a journal writing into the same transaction as the work it records attests `writesInside` (over `SqlConnection.bindsZone`, which asks about the NAMED zone rather than whatever is ambient) and the step engine journals that region per step instead of collapsing it; every region reports which way it resolved as `durable.zone.mode` (`collapsed` / `perStep`), because the answer turns on a runtime coincidence the manifest cannot show. `LISTEN`/`NOTIFY` rides `Postgres.Connection.listen`, a Postgres-only convention method on the instance rather than a member of the neutral `Sql.Connection` contract, with its own connection — a listener holds one for as long as it is subscribed.

**A typeface is a resource, not a field**: `font` declares `Font.Family` (its name plus optional face bytes) and `Font.Measure` (advance widths for a BATCH of strings — one layout is one dispatch, and the contract is `inputType`/`outputType` rather than a method on a held instance, so a non-Node controller can measure text). `svg-chart` and `pdfmake` both reference one, which is what stops the family a layout was COMPUTED against from differing from the family that RENDERS — two hand-written strings whose disagreement has no visible cause. A family with no faces is a valid declaration (a websafe or already-served typeface, measured by estimate, which the result reports as `exact: false`); the consumer that genuinely needs bytes refuses it, where it can say what they were for.

**OCR** is `ocr` (the engine-neutral `Ocr.Recognizer` abstract, whose `throws:` list is the ceiling every engine's codes fall within) plus `tesseract` (Tesseract compiled to WebAssembly, staged as assets, no host install). Its models are resources, not strings: `tesseract-model` is a tiny LEAF holding only the model kinds, the engine re-exports them, and each language is a generated module under `modules/tesseract-lang/<code>/` (own release entry, published as `oci://ghcr.io/telorun/tesseract-lang/<code>`) exporting one instance. **A data module imports the stable leaf of kinds, never the engine that consumes it**: an in-repo import edge bumps its dependent on every release, so importing the engine would republish every language on every engine change, and each import would open its own engine scope. **A controller that runs work in `worker_threads` re-enters its own bundle** (`new Worker(new URL(import.meta.url), { workerData })`, guarded on the marker), which requires the bundle to import only TYPES from `@telorun/sdk` at the top level and load runtime values lazily on the main thread: a worker has no Telo kernel, so the realm shim throws when the SDK is evaluated there.

**Web search** is `web-search` (the `WebSearch.Engine` abstract with its query and result shapes, plus the engine-neutral rules — cursors, hint resolution, recency windows, slicing, reading reported dates — as seven exported `Telo.Function`s) plus one templated module per engine (`searxng`, `brave`, `kagi`, `tavily`, `exa`) over an `Http.Request`, with no controller: pure engine-neutral value logic ships as exported functions, and a module library only for logic that needs code.

**Knowledge graphs** are `graph` (backend-neutral: the `Store` / `Node` / `Relationship` abstracts, the twelve operations, the `throws:` codes, and the `@telorun/graph` store interface every backend implements — one method per operation returning a value or an outcome, never a code, each atomic: joining the caller's transaction when one is open and otherwise committing on its own) plus a backend: `graph-sql`, ONE module for the whole SQL family, written against `Sql.Connection` / `Sql.Table` / `Sql.Schema` and never branching on the engine. **The tables are plain**: every node and relationship type is an ordinary engine `Table` the author declares and lists in the engine `Schema`, which creates and migrates it; `graph-sql` issues no DDL and only maps the graph onto the tables. **In `graph-sql`, deletes cascade in the database**: a relationship table's endpoint columns must be foreign keys with `onDelete: cascade` (a rule, twinned at creation), so there is no store-side cascade to drift from it (a layered graph is the reverse — below). **The engine `Schema` instance owns table addressing**: every statement names a table as the store's `schema:` instance renders it (`SqlSchema.qualifiedTableName` in `@telorun/sql` — `Postgres.Schema` qualifies with its namespace, `SQLite.Schema` names the bare table), never a bare name that would resolve through `search_path`; a schema instance without the member is refused at store creation, never addressed unqualified. Operation contracts are derived through `x-telo-schema-projection-from` (`pick` / `omit` across the node and relationship references), and each backend kind carries the row projection they derive from. `sql` / `postgres` / `sqlite` know nothing about graphs. **Listings page by opaque cursor, with a bounded default, and the cursor has two owners**: `FindNodes` / `FindRelationships` / `Traverse` take `limit` (1–1000, default 100) and `cursor` and return `next` only when more exist; there is no offset, since an offset makes page *n* cost *n* pages. `graph` owns the ENVELOPE — a version plus a digest binding the cursor to the operation kind, the store's declared name, the type's declared name (a traversal's declared path and start key), the endpoint filters and the canonical `where`; names only, read from the stamped identity, because the identity's module component is a machine path and a binding must hold on every replica, so two same-named stores in different modules listing same-named types share one — and raises `GRAPH_CURSOR_INVALID` itself; a backend owns only the TAIL inside it (`page.after` in, `next` out, text it alone reads) and answers a tail it does not accept with the outcome `cursorInvalid`. So no backend re-implements binding, and a tail can change format without the public cursor changing shape. **A cursor is a position, never a credential**: the digest is unkeyed and does not cover the tail, so the guarantee is the tail rule in `modules/graph/docs/store-contract.md` — a tail is untrusted on every call, each field is a value bound into an ordering comparison or a selector re-checked against what the same call could read with no cursor, it never becomes statement text or widens the read, and one the backend cannot read as its own is `cursorInvalid` before any statement is issued, while a readable one gets what a `key` input gets (the engine may refuse a value of another type, as it would in `key`). **The key tail has one home, `@telorun/graph`** (`encodeKeyTail` / `decodeKeyTail`, beside `filterOperands`, which reads the `where` grammar into comparisons for any backend): "resume after the last key" is the contract's own ordering rule, so every key-ordered backend shares it, SQL or not. A tail carries each key in the value domain's one-to-one encoding — the SDK typed frame behind its generation — so a listing resumes after ANY key an operation can return (text, int64, a fraction, a boolean, bytes, a list, a map), text that is not such a frame or is of a generation this runtime does not read is `cursorInvalid`, and a key outside the domain is refused by the frame's own `ERR_TYPED_FRAME_UNENCODABLE`; there is deliberately no "pageable key type" rule, since a table's projection cannot tell the failing types apart and a rule would have to list one engine's type names in a generic module. **The stated limit is the engine's, not paging's**: `Postgres.Connection` returns `date` / `timestamp` / `timestamptz` / `interval` as host objects where `Postgres.Table` projects text, and `bigint` / `numeric` as text where it projects a number, so such a column cannot be a node key or endpoint (the first operation returning the key is `ERR_OUTPUT_INVALID`; a page boundary past a host date is the frame's refusal) until the connection returns what the projection declares — pinned by `postgres-key-type-limit.yaml` in `graph-sql` and the current strategy. **The statement builder is `@telorun/sql`'s** (`SqlFragments`, `sqlComparison`, `sqlWhere` — the argument shape of the connection's own `executeTemplate`, no graph concept in it), so a SQL backend keeps only the lookup from a property name to its own compiled column. `graph-sql`'s tail is the last key (or source and target): a find seeks to it through the key's index and costs its `limit`, while a traversal page costs at most one walk of its reach — never more than the first page, whatever else the graph holds — which indexes that rests on is `modules/graph-sql/docs/sql-graph.md`, and is the author's to declare, since the tables are plain. **A node or relationship value may carry `origin`** (`{ key, properties, origin? }`), the layer it was resolved from; `graph-sql` never sets it. `graph` requires telo `>=0.108.0`: the key tail imports the typed-frame generation exports of `@telorun/sdk`, first published in that release, and an older runtime fails at controller load. `graph-sql` leaves that floor to its import edge — its own file and bundle need nothing newer than its `>=0.105.0`.

**Layered knowledge graphs** are several typed graphs kept as named layers in one database, a layer built on one or many others. **A versioning strategy is a MODULE per engine** that ships the kinds a graph's storage is declared with, and the contract has three levels, each extending the one beneath: *current* (each layer holds only its current statements, a write is immediate), *drafted* (a layer is edited in a draft and published atomically — next paragraph), then *revisioned* (every published revision is kept, and the layers beneath are PINNED rather than declared — the paragraph after). `graph-layers` owns the contract and names no engine and no strategy: `GraphLayers.Store` (an abstract extending `Graph.Store`, adding `layer`), the `RetractNode` / `RetractRelationship` operations (withdraw a layer's own statement so the one beneath shows; `GRAPH_NODE_NOT_STATED` / `GRAPH_RELATIONSHIP_NOT_STATED`), and the `@telorun/graph-layers` store interface, which extends `@telorun/graph`'s with what the lifecycle kinds call — outcomes, never codes. `graph-layers-sql` is the SQL family's shared half — the `Node` / `Relationship` / `CurrentStore` abstracts, every structural rule of a layered TYPE declared once and inherited (a concrete node, relationship or store kind that declared a rule of its own would replace them), and the engine-neutral implementation as the code library `@telorun/graph-layers-sql`, which **exports exactly the five controller namespaces a strategy re-exports** (`Node`, `Relationship`, `CurrentStore`, `DraftedStore`, `RevisionedStore`) — its statement builders, column constants, row ids and tail selectors are internal, because publishing them would make every storage change a cross-module change, and a third-party strategy either re-exports these controllers under another engine's kinds or implements the `@telorun/graph-layers` store interface; it imports `graph`, `graph-layers` and `sql`, never an engine, and never branches on one. Each strategy module (`graph-layers-current-sqlite`, `graph-layers-current-postgres`) imports `graph-layers-sql` and its engine and holds only concrete kinds that extend the abstracts, narrow each slot to its own kinds and re-export the shared controllers from the specifier in its own bundle — the `sql` ↔ `sqlite` / `postgres` split repeated. Dependency direction: strategy → `graph-layers-sql` → `graph-layers` → `graph`; strategy → engine → `sql`; nothing points back. **Layered storage is DECLARED**: every table is a resource the author declares with the strategy's own table kind and lists in the engine `Schema`; nothing is registered at init and no module issues DDL. A strategy table kind `extends` the engine `Table` with `base:` — the author writes `table`, the key (or endpoint columns), `columns` and optionally `indexes` / `checks` / `renamedFrom`, and `base:` forwards them (`columns` as a bare `self.columns`, so a column typed by a `!ref` to an enum crosses as the reference) and adds the system columns under `internalColumns` (`graph_layer`, the layer's NAME, and `graph_effect`, `stated` | `removed`) plus its indexes (unique `(graph_layer, key)`; unique `(graph_layer, source, target)` and `(graph_layer, target, source)`), named `graph_<table>_…`. There is no bookkeeping table. **A table kind declares its own row projection**, because a projection is read from the kind's own document and is not inherited along `extends`, and the engine's column vocabulary is restated in it because the projection finds its `x-telo-schema-map` only through document-local references. **A strategy table kind is held to its engine table's rules, restated on its own fields, and reserves the `graph_` prefix in its schema**: a `base:`-form kind's author schema is its own, so it inherits NO rule — each table kind restates, under the engine's own `SQL_…` codes, every `Sql.Table` resource and referrer rule its author surface can still violate (the rules over `foreignKeys`, `seeds` and `internalColumns` are excluded, since the kinds do not offer those fields), refuses a column or index name beginning `graph_` in the property names of `columns` and `indexes` (`SCHEMA_VIOLATION`, at check and at creation, before `base:` maps anything), and declares no `GRAPH_…` rule; what a layered type requires of its table stays on the `GraphLayersSql` abstracts. Each strategy module's unit test (`nodejs/tests/engine-vocabulary.test.ts`) reads its own manifest and the engine's and fails when a restated column, index or check entry, the projection, or the rule list falls out of step. The node kind's `table` slot names the module's own table kind, so a plain engine table there is `REFERENCE_KIND_MISMATCH` — the static guarantee that the system storage exists. **A store's stack is its own layer, then each base in order followed by that base's stack; a layer reached more than once — two bases built on the same layer — has one place, the lowest of them, so every layer outranks the layers it is built on** (a diamond is legal; `GRAPH_BASE_LAYER_DUPLICATE` refuses one layer twice among a store's direct bases, a direct base naming the store's own layer, and — at creation only, since a rule reads one level — the store's own layer anywhere deeper). On the current and drafts strategies it is declared (`bases:`) and read against whatever the layers hold now; the first statement for a key wins, a `removed` winner makes the key absent, `origin` is the winning layer, and a `where` judges the winner only. A write states only in the store's own layer: a value from beneath is changed by copying its row with the change, and hidden by a `removed` row. **This reverses "deletes cascade in the database", and nothing is cascaded in its place**: a layered table has no foreign key (an endpoint is a logical key any layer beneath may state, checked by the store when a relationship is created or merged), and a relationship is in a view only while both endpoints resolve; a node delete withdraws the layer's own relationships touching it and states nothing about those beneath. The rule is decided at READ, on every strategy — a base cannot see the relationships stated above it, so no write-time cascade could keep a stack with live bases whole: a listing passes over a relationship whose endpoint does not resolve, a traversal neither ends on nor passes through such a node, update and delete answer as for an absent one, and the relationship is back when the node resolves again. Retract withdraws exactly one statement. Every operation is atomic — the store runs it in the caller's transaction when one is open and in one of its own otherwise (a private zone entry bound on `SqlConnection.runInTransaction`). **Concurrent writes to one key through one layer each take effect in some order, and a store retries nothing**: no write fails for having raced another, and none reports an outcome the layer does not then hold. On the current strategy — which has no bookkeeping row to hold — **every write that depends on the layer's own row for a key is a conditional statement against that row** — one, except a merge of a key the view does not show, which is two — the layer's unique `(graph_layer, key)` index being where writers meet: a merge first inserts the stated winner of the store's whole view with the given columns (it proposes nothing when the view shows nothing; a conflict sets the given columns on an own `stated` row only) and, only when that returned no row, states the key as new — an insert naming only the given columns, whose conflict arm always leaves the row `stated` with them, the other columns staying on an own `stated` row and taking the proposed row's values, which are their declared defaults, on an own `removed` one; update-from-beneath and the removal a delete writes are inserts of the winner beneath with a conflict arm, create replaces only an own `removed` row, and a statement returning no row is an outcome (`exists`, `absent`, or for a merge "not shown"), never an error and never a success: a delete answers `found` only from a returned row, and a second statement belongs to the outcome the first returned, so whatever lands between a merge's two statements equals a serial order. **"New" is one thing on every strategy**: the given columns only, so the ENGINE applies every other column's default — a statement's column list is fixed, and no engine-neutral expression yields a column's default inside an insert-from-select. It covers a key never stated, a key under the layer's own removal (nothing is taken from the statement the removal hid) and a key whose copy source vanished; a `nullable: false` property with no default must be given, or the engine's constraint error surfaces. The drafts and revisions strategies meet at the layer's own row instead, which every published write, `Publish` and `OpenDraft` take first. **A read never writes, and neither does a refusal**: a layer's bookkeeping row is created by the first call that CHANGES the layer — a node or relationship write, an opened draft, or on a revisioned store a pin move that changes its base list — inside that call's atomic operation, never by a read, a refused call or a call that changes nothing (`LabelRevision` never registers and answers `GRAPH_REVISION_NOT_FOUND` for a layer with no row; a `PinBase` / `UnpinBase` outside a session on a layer with no row is first judged against a layer holding nothing — no bases, revision 0 — and only a move that is a change registers the layer, takes its row and is judged again under it, so a racing first write is seen; a pin naming the store's own layer is `GRAPH_BASE_CYCLE` by name, registered or not); a read that finds a layer of its stack unregistered reads it as holding nothing (its own layer empty at revision 0, a base contributing nothing) and caches nothing from that partial resolution, so a read-only role or replica can read — and a revisioned layer can be pinned only once something has written it. The two-process proof is one fixture, `modules/graph-layers/tests/__fixtures__/write-race`, run by all three PostgreSQL strategies; `session-race` beside it — one process writing inside a draft session while another deletes the same keys outside it — is run by the drafts and revisions ones. **Overlay is an index probe per higher layer, never a resolution of the stack**: a find has each layer read its own first `limit` visible winners through `(graph_layer, key)` with one probe per layer above — always a SCALAR subquery, `(SELECT … LIMIT 1) IS NULL`, in listings, endpoint resolution and a traversal's shadowing alike, never `NOT EXISTS`, which a planner may answer by hashing the whole layer it probes (it did at 20,000 rows) — the seek repeated inside each probe, or a probe reads its layer from the start and a page costs its distance into the listing — so a node page costs `limit` × depth, and a relationship page that times twice the depth again, each endpoint being resolved by one probe of the node table's `(graph_layer, key)` index per layer; a traversal is one statement over the resolved node and relationship sets, with only base scans under a hop's `UNION ALL` so the join reaches each through its index. A current store pins nothing: a listing returns no key twice and every key visible throughout exactly once, and is never a single-moment view. The behaviour suite every strategy of every level runs is ONE fixture library, `modules/graph-layers/tests/__fixtures__/layered-suite`, taking seven stores as `resources:` inputs — four in a chain-and-side stack, three more forming a diamond — and one more input, `refreshStacks`, a `Run.Sequence` it invokes after every step that writes a base another store then reads: a strategy that reads its bases live supplies one that does nothing, a strategy that pins them one that pins every store of the fixture stack to the head of each of its bases. What only a live stack shows (a base's write visible above with no step between) is `live-stack-suite`, run by the current and drafts strategies; what only a pinned stack shows is `stacking-suite`, run by the revisions strategies. Rules and what a page rests on: `modules/graph-layers-sql/docs/layered-sql.md`.

**Drafting is the second level, and its kinds are declared ONCE in `graph-layers`**: `GraphLayers.DraftedStore` (an abstract extending `Store`), the `Actor` shape, and `OpenDraft` / `DraftSession` / `Publish` / `DiscardDraft` / `RebaseDraft` / `ListDrafts` / `NodeConflicts` / `RelationshipConflicts` / `ResolveNodeConflict` / `ResolveRelationshipConflict`, each `store` slot naming the LOWEST level at which the kind fully works — so a drafting kind over a current store is the analyzer's `REFERENCE_KIND_MISMATCH` and nothing branches on which store it holds; behaviour comes through the `@telorun/graph-layers` store interface (`DraftedGraphStore` extends `LayeredGraphStore`; outcomes, never codes). The twelve `Graph.*` operations stay the only read/write vocabulary and gain no code. **A session is a ZONE, and the store finds it**: `DraftSession` carries a step body (the shared step grammar) whose slot provides the zone correlated on `/store`; the conflict kinds require it on their `store` field (`ZONE_REQUIREMENT_UNSATISFIED`, runtime twin `ERR_ZONE_REQUIRED`), and a store recognises a call made inside a session by `ctx.zonesFor(store, invokeCtx)` against a map of its own keyed on the minted zone entry — nothing store-private rides the entry. Inside a session every graph or lifecycle operation on that store reads the draft's rows over the layer's published ones (then the bases' published ones; a base's draft is never visible above it) and writes draft rows; outside one it reads the published state and writes it in place. **A draft closed under a running session ends the session through cancellation, not through an error code**: `DraftSession` runs its body under a cancellation source of the session's own, linked to the caller's, and hands it to the store (`openSession`); every session operation makes its draft-open check and its write one conditional write the database enforces — no claim, lease or heartbeat — and an operation that finds the draft closed cancels that source and stops as `ERR_INVOKE_CANCELLED`, which no `try:` in the body catches (the step engine never absorbs a cancellation of the invocation it runs) and after which the dispatch gate refuses every later step; only `DraftSession`, seeing that the store cancelled and the caller did not, raises `GRAPH_DRAFT_CLOSED` (`data: { draft, closedAs, revision? }`). **A drafted layer has a revision counter, and a revision is a CHANGE to what the layer states**: every publish and every write outside a session that changes the layer's statement advances it by an atomic increment in the same atomic operation as the write (no retry loop) — a merge or update whose given values all equal the layer's OWN current statement writes nothing and returns that value (no revision, no changeset row, no change-feed entry, inside a session no draft row), so an open draft stays publishable across a redelivered merge; the first write of a key the layer does not itself state is a change even when the values equal a base's (the layer becomes its `origin`), its repeat is not, and inside a session a write to a key with an undecided conflict always settles it. The equality is ONE function (`same-value.ts`, also what the merges call "convergent"), by the value's own type and never the column's: both absent or null, the same text, the same boolean, the same number (an integer being one value whether held as a number or an int64), the same bytes, the same instant, lists the same element by element, plain maps the same key by key in any order — and everything else different, so text never equals a number or a boolean and on an open column `"7"` and `7` are two values. It errs toward writing: a PostgreSQL `bigint` / `numeric` property comes back as text, so an equal re-merge of one costs a revision until the connection returns what the table projects. **A drafted-store copy whose source a concurrent delete removed answers as after that delete** — the layer's published row, which a session does not hold, or a base's row: an update answers `absent` and writes nothing, a merge states the key new (stamped as over nothing when the vanished row was the layer's own published one), and a copy that would replace a draft row is one statement over that row, so the row stands. The uncoded errors left in the three stores are invariant errors ("…returned no row while the layer's row is held"), none worded as a race. **The actor of what a store does on nobody's behalf is `storeActor(name)`** from `@telorun/graph-layers` — `{ type: "store", id: <the store's declared name> }`, documented on the `Actor` shape — never the kind as an import alias spells it, which would audit one kind under a different `type` per application. `OpenDraft` is decided under the layer's row, so it never falls between a draft closing and the next opening. `Publish` succeeds only while the layer is at the draft's parent (`GRAPH_DRAFT_STALE` otherwise), applies all of the draft at once, is idempotent, creates no revision for a draft with no change, and is refused (`GRAPH_DRAFT_CONFLICTED`) while a conflict is undecided or a relationship the layer states has an endpoint that does not resolve in the view being published. `RebaseDraft` merges what both sides did alike and leaves the rest as conflicts in five classes — `changed-both`, `changed-removed`, `removed-changed`, `added-both`, `endpoint-missing`; a decision takes a side (`mine` / `theirs`), optionally with `set` on top, as one conditional write (`GRAPH_CONFLICT_NOT_FOUND` for the loser, `GRAPH_RESOLUTION_INVALID` where it cannot apply), and an ordinary write to the key inside the session settles it too. **Deciding is ordinary steps** — list, `switch` on `class`, a constant side for the mechanical cases, any invocable for the rest, then resolve; the graph modules import no AI, queue or rules module and the store retries nothing. **The drafts strategy** (`graph-layers-drafts-sqlite` / `-postgres`, over the `GraphLayersSql.DraftedStore` abstract, which restates the store rules over two more tables and requires a base to share them) keeps, per layer and key, at most one published row and one draft row, compared two-way through `graph_over` — so it retains no ancestor, a conflict has no `base`, and two sides changing different properties of one key is one `changed-both` (a revisioned store merges those). Its typed tables add `graph_layer` (the layer's INTERNAL id, not its name), `graph_state`, `graph_effect` (`retracted` on a draft row = the draft withdraws the layer's own statement), `graph_revision`, `graph_over`, `graph_written_at` and the three `graph_resolution…` columns. **State leads the key in its indexes** — unique (`graph_layer`, `graph_state`, key), and for a relationship (`graph_layer`, `graph_state`, source, target) and (`graph_layer`, `graph_state`, target, source) — so a layer is two contiguous ranges and every statement names the state it reads: with the key first a layer's draft rows lie scattered through its published ones, a published page walks every key the draft alone holds (and bulk loads are directed into drafts), and publish, rebase, discard and the conflict listings walk the layer; two bookkeeping kinds, `LayersTable` and `DraftsTable`, take ONE author field (`table`), write `columns: {}` with every column internal, and declare no row projection, so a repository over one is refused at check. A layer has one open draft, enforced by a partial unique index on the drafts table over rows neither published nor discarded — "open" is derived from the two timestamps, so the only correct guarantee is an index whose predicate reads them. It is two columns wide (`layer_id` and `open_slot`) for now: **`open_slot` is temporary**, a constant the store never names, there because both engines' schema passes read a ONE-column unique index back as a column `unique` flag and refuse the table on its second boot; once they tell an index from a flag, the index narrows to `layer_id` and the column leaves `internalColumns` — a manifest-only change the schema pass applies, with no store change. A draft has no state column: open, published and discarded are read from its timestamps. **Instants are the database's, written without naming an engine**: the engine `Schema` instance renders the current-instant expression (`SqlInstantSchema.currentInstant` — `clock_timestamp()` on PostgreSQL, fixed-width UTC text on SQLite, so plain comparison is chronological), a schema instance without the member is refused at store creation, and `@telorun/sql` exports the two readers a consumer needs for what a driver hands back (`readInt64Column` — PostgreSQL returns `bigint` as text — and `readTimestampColumn`). **In a session the top layer contributes TWO branches to a page** — its draft range, and its published range minus the keys the draft holds — and "what the top layer says" is the draft probe, then the published one; a node page reads depth + 1 ranges and stays independent of both the layer's and the draft's size. **As on every layered table, every probe of a layer above is a SCALAR subquery, never `NOT EXISTS` and never a join**: a planner answers an anti-join or a join by hashing the range it probes whenever that looks cheaper — the whole draft, or on a 20,000-row table the whole layer — and the counter tests caught each of these. **Whatever concerns a draft as a whole is driven from the draft's range** (publish, the convergent merge, the moved count, discard, both conflict listings), reaching a published row only by probing for a key the draft holds; `endpoint-missing` is two driven sets — the draft's own stated relationships, and the layer's published relationships at each node the draft removes or retracts, through the source-led and target-led indexes. A conflict page is therefore bounded by the draft plus those relationships, **not by `limit`**, because conflicts are not stored. `GRAPH_DRAFT_STALE` means only "the layer's revision is not the draft's parent": a base's write is never staleness, and an endpoint a base removes from under a stated relationship is `GRAPH_DRAFT_CONFLICTED`. A conflict's token is built from what its row stands on — `graph_over` for a draft row, its own `graph_revision` for a published relationship the draft never touched — and a decision is recorded on the row only where it leaves one (`mine`, `merged`, `theirs` on `endpoint-missing`). **The cursor envelope has one implementation**: `ListDrafts` and the conflict listings page through `GraphListing`, which `@telorun/graph` exports beside `boundName` / `declaredName` / `quoteKey` / `assertNodeListed` / `assertRelationshipListed` for any module adding operations over a `Graph.Store`; the envelope's encode, decode, version and digest are not exported, a lifecycle listing names its operation qualified by module in the subject (`GraphLayers.ListDrafts`), and a backend still owns only its tail. `graph-layers` requires telo `>=0.108.0` (it returns instants as native timestamps), and since every strategy imports it that is the floor of a layered graph of any strategy. The drafting behaviour suite is `modules/graph-layers/tests/__fixtures__/drafting-suite`, taking two drafted stores and written against the contract — every conflict in it is built from both sides writing the SAME property, so a strategy that merges more passes it unchanged. Details: `modules/graph-layers/docs/drafting.md`, `modules/graph-layers-sql/docs/drafted-sql.md`.

**Revisions are the third level, and on it a stack is DATA**: `GraphLayers.RevisionedStore` (an abstract extending `DraftedStore`) plus `ListRevisions`, `PinBase`, `UnpinBase`, `ListBases` and `LabelRevision`, each `store` slot naming the revisioned level, so over a current or a drafts store each is `REFERENCE_KIND_MISMATCH`; the interface is `RevisionedGraphStore` (guard `isRevisionedGraphStore`). `ListRevisions` (`order`, `after`, `layer`, `limit` / `cursor` → `revisions[] { number, label?, message?, publishedAt, publishedBy, bases[] }`, paged through `GraphListing` with the layer, the order and the lower bound in the subject) is a layer's change feed — a consumer asks for what came after the last number it holds and sees a gap by number, never by time — and lists any layer registered in the same tables, which is how a revision or label is chosen before it is pinned. **A revisioned store has no `bases:`** (`SCHEMA_VIOLATION`): `PinBase` takes `bases: [{ layer, revision?, position? }]` — an integer is a number, a string a label, omitted the base's head at the call, only the number stored, revision 0 legal — and applies the list as ONE move, which is what lets a diamond be upgraded (one side re-pinned alone would hold the shared layer at two revisions). The stack is the layer, then each direct pin in position order followed by that pin's own base list at the pinned revision; one layer at two revisions is `GRAPH_BASE_REVISION_CONFLICT`, the store's own layer beneath itself `GRAPH_BASE_CYCLE`, a thirty-third layer `GRAPH_BASE_LIMIT` (`BASE_STACK_LIMIT`) — each judged at the pinned revisions, never at heads. A base publishing again changes nothing above; a base's draft is never visible above it; `origin` is the winning layer's NAME, never a revision. `PinBase` / `UnpinBase` / `ListBases` follow the session (inside one they act on the draft; outside, a change is one published revision by the store itself, and one that would leave a conflict is `GRAPH_DRAFT_CONFLICTED` with nothing changed); `LabelRevision` and `ListRevisions` do not. **A move that changes nothing makes no revision** — which is what lets the shared suite's `refreshStacks` re-pin to the head after every base write. **Labels are permanent, one per revision** (`GRAPH_REVISION_LABEL_EXISTS` / `GRAPH_REVISION_LABELLED`; the same label on the same revision succeeds), and never all digits, so a label is never read as a number. **The revisions strategy** (`graph-layers-revisions-sqlite` / `-postgres`, over the `GraphLayersSql.RevisionedStore` abstract, which restates the three store rules over the `layers`, `changesets` and `changesetBases` tables) passes the drafting suite and the layered suite unchanged. **Storage is one mechanism: every row of a typed table is one VERSION of one layer's statement about one key, written by exactly one changeset**, which is a draft while open and a numbered, immutable revision once published; history is the rows themselves. The internal columns are `graph_row` (primary key, UUIDv7, never leaves the store), `graph_layer`, `graph_changeset`, `graph_from_revision` (null while the changeset is a draft), `graph_to_revision` (null while current), `graph_effect` (`stated`; `removed` — the layer hides a key from beneath, a full row carrying the values it hides; `retracted` draft-only), `graph_over` (on a draft row, the `graph_row` of the layer's own row it was written over or last rebased onto — the own-layer ancestor), `graph_beneath` (the `graph_row` of the statement winning among the bases that the row was written over or last reconciled with, set by every write and carried by a copy — the beneath ancestor) and the three `graph_resolution…` columns. `LayersTable`, `ChangesetsTable` and `ChangesetBasesTable` are the three bookkeeping kinds: a changeset row holds its `public_id` (`gdr_…`), `parent_revision`, `revision`, who opened, published or discarded it, its label columns, and `bases_changeset` — the changeset whose rows in the bases table are its base list. **A base list is stored once per CHANGE, not once per changeset**: a write, a publish and a new draft inherit the pointer, and the first pin change in a changeset writes the list under its own id — otherwise every write outside a session would write N bookkeeping rows for ever. A write outside a draft is a changeset opened and published at once by the store itself (`storeActor`). **Three ranges, three indexes, and every statement names the one it reads**: unique (`graph_changeset`, key) — a draft's rows as one range; a PARTIAL (`graph_layer`, key, `graph_from_revision`) over published rows only — every read as of a revision, and it holds no draft row, since a draft row carries its layer and would otherwise sit in every reader's range; and a partial unique (`graph_layer`, key) over rows published and not ended — at most one current statement per layer and key, kept by the database; a relationship table repeats the changeset and published ranges leading on the target. The changesets table adds a partial unique (`layer_id`, `label`); `graph_beneath` is in no index. No one-column unique index exists (both engines read one back as a column flag and refuse the table on its second boot), and a `where:` is never changed under an unchanged index name and column list (the schema pass compares neither). **A strategy table kind with a primary key of its own tightens the engine's composite-key rule**: no author column may be `primaryKey` (`SQL_COMPOSITE_PRIMARY_KEY`), or check passes and boot refuses. **A versioned table has no state column, so the overlay reads it through `rowsOf` — one BARE scan per layer of the view plus one for the draft, each tagging its rows with its state and its PLACE in the stack — and narrows every alias with `inView`** (`graph_changeset = ?` under the draft tag, `graph_layer = ? AND from <= ? AND (to IS NULL OR to > ?)` under each layer's own, at the revision that layer is pinned at): a planner joins through a `UNION ALL` only when its arms carry no predicate (the first form put the predicate in the arms, and a traversal's join then read both arms whole), while beside the alias each arm's tag folds the narrowing to that arm's own index condition; the place tag is the precedence, replacing a rank computed from the layer id. **On a versioned table the probes of one row are ONE expression evaluated in order** (`inOrder`: nested `CASE WHEN … THEN … ELSE FALSE END`), never conditions joined by `AND`: a planner prices each `AND`-ed probe separately and multiplies, so a few layers in it expects a page to keep almost none of its rows and reads the whole range to sort it (a session page read 10,000 rows at 20,000), and it reorders the probes by price, where the written order is the one that stops early. Everything else in `layer-overlay.ts` — the scalar probe shape, the page branches, the traversal — is shared with the other strategies. **A read outside a session is as of one revision** — the head, or the revision a listing's first page was read at, which its tail carries — over the bases THAT revision pinned, so a listing paged across publishes stays put, a pin reads what it pinned at the cost of reading a head, and no publish ever invalidates a cursor; **a session reads its draft over the layer at the draft's PARENT revision over the draft's base list**, unchanged by what siblings publish until `RebaseDraft`. A tail carries the last key plus a revision, or a draft's public id, its parent and a digest of its direct base list (names and numbers, no id), each a selector re-checked in code (a revision past the head, another draft, the session boundary crossed either way, a rebase since, a pin of that draft moved since → `cursorInvalid`). **A write outside a session that changes the layer's statement is one retained revision** (one that changes nothing writes no row and no changeset): it takes the layer's row, ends the current row at head + 1, writes the successor as a row of its own changeset and advances the head by an increment on that row — published writes to one layer apply one at a time, concurrent writers get consecutive numbers with no retry, a bulk load belongs in a draft, and a publish holds the layer for a time proportional to the draft. **`OpenDraft` always opens another draft**; `Publish` needs the head to equal the draft's parent, and a draft that only moved a pin publishes a revision. **The merge is three-way, per property, in one place** (`revision-merge.ts`), and serves both ancestors: for a rebase the draft's row, the layer's current row and the row `graph_over` names; for a moved pin the layer's statement, the row now beneath and the row `graph_beneath` names — compared in code (never in SQL, so listing, rebasing and resolving cannot disagree); what one side alone changed merges, equal changes merge, a `changed-both` names only the properties both changed to different values and carries `base`, and a decision takes a side for what clashed, a one-sided change keeping its side's value either way. **An upgrade is a pin move, and a pin is immutable, so "what lies beneath a statement" changes only when a base list changes**: the pin-move pass reads each statement the layer makes — the changeset's rows, and the layer's published rows the changeset does not cover — once, in key order, in batches, asks the new stack what lies beneath by one probe per layer, and sends every mismatch with `graph_beneath` to the merge. Published-only statements are the main case (a draft opened to upgrade a base has no rows of its own): one that clashes is copied into the changeset still carrying the old pointer, so both conflict listings stay driven from the changeset's range and publish counts conflicts from the changeset's rows alone; one that merges becomes a draft row with the merged values and the new pointer; one with nothing left to say becomes a withdrawal. A published relationship whose endpoint no longer resolves is copied the same way (`endpoint-missing`), which blocks the pin outside a session — a revisioned layer never publishes a dangling relationship of its own. `RebaseDraft` re-applies the draft's own pin changes onto the head's base list (the draft's entry stands where both moved one; a result that is no legal stack refuses the rebase with nothing changed — `GRAPH_BASE_REVISION_CONFLICT` / `GRAPH_BASE_LIMIT`) and runs the same pass. **A pin move costs the statements of the layer being re-pinned**, one probe per layer of the new stack each — independent of every base's size and of retained history, but not reduced by how little changed beneath — and outside a session the layer is held for the walk, so a large layer moves a pin inside a draft. A conflict's token is a DIGEST of the ids of every row its class was decided from (the draft row, both ancestors, the layer's row, the row now beneath, and for a missing endpoint the rows the endpoint nodes resolve to), so no row id leaves the store. Publish ends the replaced rows through the changeset's keys and the current-rows index rather than through `graph_over`, and touches only the typed tables the changeset wrote: a planner sizing a join reads the ends of the joined index, and how many such reads it makes varies run to run, which made a counter test flap. **A counter proof needs every probed layer to hold a real share of the measured table**: a planner reads a layer holding a handful of rows whole or by key as it pleases, so a fixture with a tiny layer in the stack measures the planner, not the statement. **Stated limits**: every layer of a stack lives in the application's own database and gets there by that application writing it; retained history is unbounded (no compaction); a stack holds at most 32 layers; each type is one table; published reads come from the authoring store; a reader of one layer can list any layer's revisions in the same tables. Details: `modules/graph-layers/docs/revisions.md`, `modules/graph-layers-sql/docs/revisioned-sql.md`.

**Charts** are `svg-chart`: one kind per chart type over two abstracts (`Chart` — canvas, palette, legend, labels, font; `Cartesian` — axes, series, gridlines), each mapping a row to a mark through CEL accessors typed by `x-telo-context-element-from` against a declared row shape. Server-rendered static SVG only — an interactive browser chart is a separate vocabulary, since no CEL engine ships to a client.

**Declarative UI** is `ui` (the vocabulary: the `Ui.Node` / `Ui.SpecNode` shapes, the `Ui.Composite` abstract — a provider of `{ node?, assets }` — and the server-side controllers for `View`, `Table`, `Form`, `Action`, `Filters`, `Collection`, `Component`, `ComponentExport`, `Theme`, the six surface kinds, the four filter placements and the two state stores; no browser code; its code specifier `@telorun/ui` gives a renderer's controller `entryAssets`, which turns a built browser entry into addressed files) plus a renderer, `ui-react`, whose `UiReact.App` mount serves a shell, per-request application and page documents (digest as ETag), content-addressed files and an event stream, and ships the React renderer, the four React entries and the host module `@telorun/ui-react` as browser entries. What crosses the wire is data — a spec the prebuilt renderer interprets — never generated code, and a row-bound value is an accessor binding resolved by path in the browser. A backend module imports `ui` alone to describe its interface. **What a list accepts is declared, never inferred from a row's types**: `Ui.Collection` holds `query: { filters: [{ property, operator }], sort: [{ property }] }`, every `Ui.Table` and `Ui.Filters` names one (`collection:`), a column sorts and a bar offers a control only where it lists the pair, and a kind that serves a collection extends it so one resource is both what the API enforces and what the screen offers. **A form's surface is declared by its opener, as a kind under `Ui.Surface`**: a table's `create` / `edit` are `{ form, surface?, afterSubmit?, unsaved? }`, and `surface` names a `Ui.Dialog`, `Ui.Drawer`, `Ui.Popover` (the three under the narrower `Ui.Overlay`), `Ui.InlineSurface`, `Ui.Panel` or `Ui.PageSurface` — nothing is declared on `Ui.Form`, so one form opens differently from two openers. **Variants are kinds and `kind:` is the only discriminator an author writes**: each kind's closed schema lists exactly the keys that mean something for it, so an inapplicable key is a `SCHEMA_VIOLATION` with no rule, and a new way of appearing is a new kind rather than another value of an enum whose every sibling key must then be cross-checked. The wire keeps a `type` tag one-to-one with the kind (`Ui.SurfaceSpec` / `Ui.OverlaySpec`). **The `ui` side owns every default**: a surface kind's controller fills its own members, the table fills an omitted `surface` (the dialog kind's defaults, byte-equal to `surface: { kind: Ui.Dialog }`), `afterSubmit` and `unsaved`, the spec shapes mark every member required with no `default:`, and a schema `default:` is documentation one test holds the controllers to — so a renderer reads no default of its own and two renderers cannot disagree. A controller reads an opener's members by name and treats one holding nothing as omitted, since a template forwards an absent value into a nested key as a present key holding nothing. **A filter bar's behaviour is one record plus per-field facts**: `Ui.Filters.policy` is the `Ui.FilterPolicy` shape embedded on the bar — `show` (`all` | `chosen`), `controls` (`direct` | `chips`), `apply` (`commit` | `typing` | `button`), `summary` (`none` | `chips`), `placement` and `state` — whose scalar axes are plain enums because none selects a key set, so every combination is valid and no cross-axis rule exists; what belongs to one bar's own filters (`fields[].pinned` / `control` / `default`, `presets`) stays on the bar. The policy is a record rather than a shared resource because its `state.key` is one bar's identity and the pinned warning must reach the placement in one hop. **Placement and store are kinds**: `policy.placement` names a `Ui.AbovePlacement`, `Ui.AsidePlacement`, `Ui.CollapsiblePlacement` or `Ui.OverlayPlacement` under the `Ui.FilterPlacement` abstract (omitted is byte-equal to `{ kind: Ui.AbovePlacement }`; `compact` on the first two takes only the two that fold, which have no `compact`, so nesting is unrepresentable; an overlay placement's `surface` is a full `Ui.Overlay`, address and compact included), and `policy.state.store` a `Ui.LocalStore` or `Ui.SessionStore` under `Ui.StateStore` — an abstract so that a server-backed store is one more kind and one more `Ui.StateStoreSpec` branch with no change to the bar. **Where a bar's state lives**: `state` is `{ key, address, store }` with at least one of `address: true` and `store` written (structural, a `SCHEMA_VIOLATION`); omitted, the state is in memory and the wire carries `store: { type: memory }`, which no kind provides. The address is a boolean beside the store, not a store kind: a bar may use both, and then every change is written to both, the address winning at start. A persistence key collision is not an error: one key is one state. The renderer owns the spelling (`_telo.f.<key>.<property>[.<operator>]` in the query, written by replace; `telo.ui:<mount path>:f:<key>` in browser storage, versioned) and holds whatever it reads back to the fields and schemas the node carries. The six judgements a default, a control and a preset are held to are `UI_FILTER_*` resource rules twinned in the bar's controller; `UI_FILTER_PINNED_UNUSED` is a warning declared three times — a referrer rule on each of the two placements that do not fold, a resource rule on the bar for an omitted placement — because a rule can read the resource it is declared on and its referrer, never a default nobody wrote. **An operation is run from a page by `Ui.Action`, reached by URL only**: `inputModel`, optional `outputModel`, `source.path`, `label`, `fields`, `lists` — always one `POST` with a JSON body under a documented action contract (2xx; the 400 validation envelope; 401 / 403; anything else), with no `!ref` to an invocable and no `method` key, because the browser can reach only what a route serves and a second way to name the operation would let the page and the route disagree about its shape; the route and the action are declared over the same two shapes instead. A bare button is an input model with no properties. **What an action draws is its own ordered `lists`** (`{ heading?, rows, columns: [{ header?, value }] }`), not a node tree and not a standalone list kind: `result` is typed from `outputModel` (closed and empty when there is none) and `row` as the element of the list that entry's own `rows` accessor names, through the generic `x-telo-context-element-from-item` — so a list needs no second declared row model that could drift from the answer's. **One definition of what a form can enter** (`isEnterable` in `ui`: a scalar, or a list of scalars) gives `Ui.Form` and `Ui.Action` their default fields; the renderer derives the control from the model alone — a list whose `items` declare `enum` is a multi-choice, any other a set of typed tags, an empty list left out of the record — and there is no per-field `control` key, since a second source for the control is a second thing to keep agreeing with the model. A string whose model property declares `format: uri` / `uri-reference` is drawn as a link wherever a value is presented, held in the browser to the one address rule a `link` node's `href` obeys (a failing value is plain text), because the value is data the manifest never saw. **The host takes a click as a move within the application only for a declared page** — exact equality with a `pages[].path`, the test that already chooses between a page and not-found — so an app-relative link to a file served under the mount is an ordinary browser load rather than a not-found page; a cell link to anything but a declared page also carries `target="_blank"`, since it comes from data and must not unload a page holding entered values, while a `link` node renders unchanged. **A table's `rowActions: [{ action, inputs, confirm? }]` run an action from a row**: `inputs` is judged as a call-site argument map against that action's own `inputModel` (the slot's `inputs:` pointer and a kind-level `inputType` derived from `inputModel`), so the codes are the analyzer's own (`CONTRACT_INPUTS_MISMATCH`, `CEL_UNKNOWN_FIELD`, `CEL_TYPE_ERROR`, `ACCESSOR_NOT_PLAIN_CHAIN`) with the controller twin `ERR_UI_ROW_ACTION_INPUTS_INVALID`, and two entries over different models do not mix; every required input is bound there, since nothing opens to complete one, and an action that declares `lists` is refused in a row (rule `UI_ROW_ACTION_DRAWS_LISTS`, twin `ERR_UI_ROW_ACTION_DRAWS_LISTS`), which has nowhere to draw them; a listed form field no control can enter is `UI_FORM_FIELD_UNSUPPORTED` / `ERR_UI_FORM_FIELD_UNSUPPORTED`. A resource or referrer rule reads an accessor field as its binding (`{ root, path }` / `{ value }`), which is what lets these rules judge a resource whose fields hold chains. A row's press sends the bound record, any 2xx reloads every table over the same `source.basePath` without reading the body, and a refusal is shown in the confirmation surface a delete uses. A named shape references a sibling shape only as `$ref: "telo:Ui/<Name>"`; `telo://Self/<Name>` is for the one hop from a kind's schema. The component ABI (`ui_react-1`), the part list and the host's field list are data files under `modules/ui-react/nodejs/src/contract/`, which the docs and the tests both read.

**CRUD's record shapes are one resource, shared.** `Crud.Model` names four `Telo.JsonSchema` shapes — `schemas.read` / `list` / `create` / `update`, all required — and both `Crud.Resource` and `Crud.Ui` reference it, so the API and its screen cannot be given different ones. **`Crud.Ui` forwards presentation and owns none of it**: its optional `filters` is the `Ui.FilterPolicy` shape by reference (`telo://UiKit/FilterPolicy`), handed to the generated bar whole as `policy`, and its `create` / `edit` are each a closed `{ surface, afterSubmit, unsaved }` forwarded piecewise beside the generated form — piecewise because the opener's `form` is the template's own. It declares no `default:` and no value set for any of them, only the references into `ui`, so an omitted key reaches the table or the bar as absent and the one owner of every default is still the `ui` side; `create: {}` and no `create` are the same page. What belongs to one property (`fields`, `presets`, columns) is not exposed and stays an eject. Nothing is derived (no `readOnly` / `writeOnly` projection, no default from another shape): a shape that exists only after evaluation cannot be named at another kind's `Telo.Type` slot, typed by `telo check`, or handed to a body entry — so shapes share properties through `extends:` and each template entry is forwarded the one it needs (`self.model.schemas.<operation>`). `read` is the top: the other three fall within it by property and type, `id` is declared (required in `read` / `list`, absent from the write shapes), and the six `CRUD_MODEL_*` shape rules are twinned by the model's controller (`shapeProblems`). Each operation is governed by its own shape — a write names only its shape's columns and answers with the stored row in the `read` shape, and a list selects `list`'s columns. **The list's query is declared too**: `Crud.Model` extends `Ui.Collection` (keeping its own controller), so its required `query` block is both what the reader accepts and what `Crud.Ui`'s bar and table offer. The lister is forwarded `self.model.query` and refuses any other `(property, operator)` filter or sort property with `ERR_CRUD_QUERY_INVALID`; `id` is not implicit, while the by-id reader is given the key filter as a literal so `GET /{id}` never depends on the model. Five more `CRUD_MODEL_*` rules, twinned the same way, hold `query` within `read` (a known property, an operator its type carries, a scalar sort, no filter named as a parameter the route owns — `limit` / `cursor` / `sort` / `_telo…`). The operator and sort rules judge a property exactly as the reader does (its plain types with `null` aside, or those of its `enum` values; the twin calls the reader's own predicates), so a declared pair is never refused at request time for its operator. The list route's request schema stays open — CEL has no list-to-map function to build one parameter per declared filter — so the generated OpenAPI document types only `limit` / `cursor` / `sort` and the reader is the guard.

- "what shape is this table / when may a removed column actually be dropped?" → `modules/sql/nodejs/src/schema/` (the shared half: `schema-driver.ts` the backend seam, `schema-reconciler.ts` the diff, `schema-ledger.ts` + `declaration-snapshot.ts` the record of what is owned, `reclaim-policy.ts` the grace window, `normalize-table.ts` the declaration-level refusals, `schema-run.ts` the boot pass), `modules/{postgres,sqlite}/nodejs/src/schema/` (each engine's own), `modules/sql/docs/declarative-schema.md`. **Two schema resources over one namespace are kept apart by LEDGER NAME** (`ledger:` → `telo_schema_<name>_{migrations,versions,tombstones}`, `telo_schema_*` by default) — the separation `flyway.table` / `databaseChangeLogTableName` / Alembic's `version_table` provide. The ledger records the DECLARATION, not just applied keys, so a shared one makes each resource read the other's tables as removed and eventually drop them — which is why sharing one on a single connection is refused, and why two APPLICATIONS sharing a namespace must each declare their own (invisible from inside either, exactly as for every tool that separates history this way). An identity COLUMN was rejected for this: it makes the identity implicit in the resource's name, so renaming the resource re-runs every migration under a fresh identity — silently corrupting data with any non-idempotent migration. A written-down name is durable identity in the same sense a migration key is, so a rename costs nothing. `telo_schema` is fixed: moving it would mean a rename on every deployed database.

## Controller delivery — bundle, don't publish to npm

A `Telo.Definition` names its controller with a PURL, and there are two delivery modes:

- `pkg:telo/local/js?path=./nodejs/<module>.mjs&local_path=./nodejs/src/index.ts#<Export>` — **bundled**: the controller ships inside the module's own artifact. **This is how the standard library delivers.** Nothing is fetched from npm at load. **A module is ONE bundle**, and every kind of it names that same entry and differs only in its `#fragment` (see Mechanics 1 below).
- `pkg:npm/@telorun/<pkg>@<ver>?local_path=./nodejs#<export>` — a published npm package. Still supported for third-party modules; in this repo it is what the **deferred** modules use — `image`, `starlark` — each of which either loads a native/wasm payload or inlines a dependency that resolves an asset relative to its own module URL. Don't add new ones.
- `pkg:cargo/<crate>?local_path=./rust#<entry>` — a **Rust controller crate**, built on load from a source checkout. `starlark` and `console` carry one. Both kernels consume the identical candidate; what differs is the loader (Node's `napi-loader.ts` produces a `.node`, the Rust kernel's `cargo_loader.rs` a `cdylib` opened over `telorun-abi`) and the SDK backend each selects at build time — `--features telorun-sdk/napi` vs `--features telorun-sdk/native`. **`telorun-sdk` declares no default backend**: the controller crate has no `[features]` block, so `--no-default-features` on that build would target the wrong crate, and a dependency feature is the only selector that works. `?local_path=` resolves only in a checkout, and a kernel never builds one from a published module's directory, so a distributable Rust controller ships prebuilt, ahead of its `pkg:cargo` candidate: one `pkg:telo/local/napi` candidate per tuple for the Node kernel (no `abi` — N-API is ABI-stable) and one `pkg:telo/local/dylib` candidate per tuple with `abi=telo-<controller ABI version>` for the Rust kernel, each in its own controller layer. Their files come from a `sources:` block whose `build: { cargo: ./rust }` records the digest of the crate's build inputs, so `telo release check` fails when the crate or a crate it reaches moves without a re-pin (`docs/extend/native-files.md`).

**PURL anatomy** (`kernel/nodejs/src/controller-loaders/bundle-loader.ts`) — every segment carries meaning: type `telo` = Telo-delivered rather than fetched from an ecosystem registry; namespace `local` = bundled in the artifact (reserving `pkg:telo/registry/…` for a controller fetched as its own artifact later); **name = the artifact format** (the Node kernel hosts `js` bundles and `napi` addons, the latter opened with `require` and the fragment read off its exports object; `dylib`, which only the Rust kernel opens, and `wasm` raise `ControllerEnvMissingError` so a candidate list like `[pkg:telo/local/dylib …, pkg:telo/local/js …]` falls through to one this — or another runtime's — kernel can load); `?path=` is the built file relative to `telo.yaml`; `?local_path=` is the TypeScript source it was built from; the `#fragment` is the named export selecting one kind's controller out of the module's single bundle (omit it and the whole bundle is the controller, which only fits a one-kind module); (A library's entry point is named by `exports.code:` instead — data rather than a PURL, since it never fetches; see Mechanics 4.) Format is explicit because bundling is the one delivery mode not tied to an ecosystem's runtime (npm ⇒ JS, cargo ⇒ Rust; a bundle is just files).

**Mechanics of bundling:**

1. **Sources** live in `modules/<name>/nodejs/src/*.ts`, and **`src/index.ts` is the module's single entry point** — it re-exports one namespace per kind (`export * as SqlQueryController from "./sql-query-controller.js"`), which is what the PURL fragments select. One bundle per module is not a packaging preference: a bundle is a module graph, so a shared source file compiled into two bundles is **two module scopes**, and any state the module keeps beside its instances (a registry, a `WeakMap`, a counter) silently becomes two of them. That was the live `sql` bug — six controller bundles, six copies of the connection registry. One bundle makes it unrepresentable rather than merely avoidable; the cost is that laziness is per module rather than per kind. `modules/<name>/nodejs/package.json` is `"private": true`, named `@telorun/<name>-build`, and is **never published**. It exists for two reasons only: to declare the dependencies esbuild inlines, and to **type-check** the sources (esbuild does not). **Four packages keep publishing**, because each is the TS contract a third-party implementation compiles against, not module code: `codec`, `http-dispatch`, `kv-store` and `type` declare no controller at all. `ai`, `cache`, `embedding`, `sql` and `vector-store` are module code and no longer publish: a dependent reaches them through the `exports.code:` seam at run time (Mechanics 4), not through npm. One rule: a package publishes iff someone outside this repo needs it to *build* — nothing ever loads any of them at run time, since no PURL names them.
2. **The kernel builds the bundle; a module's own `build` script only type-checks** (`tsc -p tsconfig.lib.json`). `CONTROLLER_BUNDLE_OPTIONS` (`controller-loaders/source-bundle-builder.ts`) is the single option set, used on the run path AND on the publish/release path through `buildControllerBundle` — so the bundle a contributor runs IS the bundle that ships, rather than two esbuild invocations kept agreeing by convention. The emitted `nodejs/<x>.mjs` is a build artifact, gitignored via `modules/*/nodejs/*.mjs` — never commit it, and never re-add an esbuild step to a module's `build`. The `--banner:js` `createRequire` shim is not optional: it defines `require` in module scope so esbuild's `__require` shim (emitted for a bundled CJS dependency) resolves instead of throwing "Dynamic require of X is not supported" under Node. `--conditions=source` is not optional either: an inlined workspace TS library must be taken from its `src/`, not its `dist/`, or building a controller would depend on having built every library it inlines — the exact build step this design removes, and a hard "Could not resolve" on a fresh clone. Every inlined package declares `source` ahead of `import` in its `exports`. esbuild is pinned to one version through a pnpm `catalog:` entry.
3. **`@telorun/sdk` stays external, never inlined.** The bundle has no `node_modules`, so `BundleControllerLoader` symlinks every name in `REALM_COLLAPSE_NAMES` (`controller-loaders/realm.ts` — `@telorun/sdk` today) into a `node_modules/` beside the bundle, pointing at the kernel's own copy. Standard resolution then finds it on both Node and Bun (ESM resolve hooks aren't honoured by Bun; Bun's plugins don't intercept runtime imports — a symlink is the one portable mechanism). That collapses *identity* as well as resolution, so `Stream` / `InvokeError` `instanceof` checks hold across the kernel/controller boundary. Authors write a plain `import { … } from "@telorun/sdk"`.
4. **A module-owned library stays external too, and is resolved through the import graph.** A library declares, once, on its own `Telo.Library` doc, which bare specifier its code is imported by — under `exports:`, beside the kinds and instances it already exports, because that is what it is: `exports.code: [{ specifier: "@telorun/sql", format: js, path: ./nodejs/sql.mjs, source: ./nodejs/src/index.ts }]`. **Data, not a package URL**: `controllers:` needs a PURL to be able to name an ecosystem fetch (`pkg:npm`, `pkg:cargo`), while this always names a file the module already ships, so `pkg:telo/local/` is constant noise before the first real datum — and a query string is one opaque box to the visual editor. `format` plus the optional `os`/`arch`/`libc`/`abi` build the same `ArtifactSelector` a controller candidate does, so layer matching and platform fallthrough are unchanged. The kernel joins that to the consumer's `imports:` (`Sql: ../sql`) during `kernel.load()` — the only point where the import edges, the target's manifest and the target's artifact are all in hand (`kernel.buildSiblingLibraries` → `controller-loaders/sibling-libraries.ts`) — and the loader resolves the specifier to **that module's own entry point** instead of letting esbuild copy its source in. Since that entry is usually the same file the module's controllers come out of, `@telorun/sql` is one module scope across sql's own six kinds and every dependent. The specifier is declared by the **library** rather than per consumer, because it is a property of the library (its name in a host ecosystem), not of the relationship — and sitting beside the format keeps runtime **derived, never declared**: the entry says `format: js`, and a future Rust entry carries `specifier: telorun-sql` with no runtime-keyed map anywhere. **One specifier, one entry point** — subpaths are deliberately unrepresentable, since reproducing npm's `exports` map inside the artifact would import a package manager's resolution semantics; importing one is a hard build error. Resolution is a **synthesized package** (`package.json` + a re-export shim) written beside the bundle, not a symlink: a published artifact ships files, not a `package.json`, so there is nothing standard resolution would accept — and generating it keeps the whole mechanism inside the loader and off the artifact contract. Every consumer's shim re-exports the same file, and Node keys its registry by resolved URL, so one library is one scope however many shims point at it. **Only workspace modules are de-inlined**: `kysely` / `pg` have no module artifact to resolve against, and inventing one would be building a package manager. Two guards keep the property from decaying silently, both in the builder because the analyzer is browser-safe and has no sources to read: a **subpath import** of a declared specifier is a build error, and a metafile input reaching into a sibling library's **entry-source directory** by any other route (a relative path, a transitive hop) is a build error naming the files. The directory is the entry source's, never the module's — a module directory holds its tests, and a fixture module nested in one is a different module whose bundle is its own. **Dedup is per (module, resolved version), and skew is a warning**: the import pin is the honest granularity, so two dependents pinning different versions legitimately run two scopes — that is different code — and the kernel says so rather than pretending otherwise. **An npm-delivered controller is outside the seam entirely**: it resolves a library from its own tarball, so that copy is a second scope and nothing reports it — the kernel cannot see inside another delivery mode's package. No in-repo module depends on a library that way any more, but a shared-state seam still must not assume one scope (which is why `sql` keeps its executor `WeakMap` on the connection instance).
5. **There is no build step in development.** When the declaring module has **no artifact handle** and `local_path` resolves on disk, the loader builds the controller from source with esbuild (`source-bundle-builder.ts`) and imports that — so a fresh clone runs `pnpm run telo ./manifest.yaml` after `pnpm install`, and editing `src/*.ts` and re-running picks the edit up. The guard is the *absence of an artifact*, not the shape of the base URI: a published module served from the on-disk manifest cache also has a local base, and its payload is still its layer. The cache under `<entry-dir>/.telo/controller-src/` is keyed on a digest of **every input esbuild reported** plus the build options — a bundle's inputs are a graph, so an entry-only staleness check would serve a stale controller after an edit to a sibling or to a shared library. A changed input is a different key: nothing to invalidate, and a cross-process race (the test suite spawns a kernel per manifest) writes identical bytes to identical paths, through a temp file and an atomic rename. **The publish path takes the same builder** (`buildControllerBundle`, which returns the bytes AND the metafile inputs the release edge graph is built from), so there is no `build:bundles` prestep and no staged artifact to go stale — but there the optional-esbuild fallthrough to the prebuilt `path=` file is a HARD failure, since digesting a stale bundle is exactly what the release design exists to prevent.
6. **`files:`** on the `Telo.Library` doc is the gitignore-style allowlist for what the manifest cannot otherwise name — assets, static files, sidecars. A controller's `path=` entry point joins the payload **because `controllers:` names it**, so it is never restated in `files:`, and a module whose only payload is its controller declares no `files:` at all — likewise a file or directory a tag names (`!include-*`, `!module-path`). Confinement is checked over the whole partition (`assertWithinModule`), not just the pattern match; a symbolic link ships as a link, and its target must be a file of the same layer inside the module directory. Publish then **partitions** the payload into layers — see Layered module artifacts in `kernel/nodejs/CLAUDE.md`.
7. **Loading materializes one layer.** `BundleControllerLoader` picks the candidate this host can run and asks the module's `ModuleArtifact` for that selector's directory; it never fetches, and never treats a module ref as a path. Missing file, unparseable PURL, non-`local` namespace, unhostable format, and a platform the host does not match are all env-missing (fall through to the next candidate); a bundle that imports but is malformed is a hard `ERR_CONTROLLER_INVALID`, and a source that fails to build is `ERR_CONTROLLER_BUILD_FAILED` — a real user-code failure is never masked as env-missing.
8. **Releases:** a bundled module publishes nothing to npm, so it takes **no changeset** — its version is its module's, moved by `telo release apply` (see Versioning & releases in the root `CLAUDE.md`). What decides that it moved is the **payload digest**, not a path rule: a bundle inlines its dependencies, so a shared-library fix changes its bytes while touching no file under its directory.
9. **A dependency that resolves a file beside itself cannot be inlined.** A package that reads an asset relative to its own module URL (`__dirname`, `import.meta.url`) looks for it beside the *bundle* instead, where it is not — the failure is a runtime "file not found", not a build error. The way out is to ship the asset as the module's own and stop the dependency looking for it: `sources:` stages it from the upstream archive, an `assets:` pattern claims it into the `assets` layer, and the controller reads it through `ctx.resolveControllerFile` and hands it over. `http-server` is the reference — `Http.Reference` registers its routes over `@scalar/core` rather than through `@scalar/fastify-api-reference`, whose plugin reads `dist/js/standalone.js` beside itself with no way to redirect it. **`pdf` is the other half of the pattern**: pdf.js locates its standard fonts, CMaps, wasm decoders AND its worker beside its own package, so the module stages all four from the upstream tarball, claims them with an `assets:` pattern, and names them through `standardFontDataUrl` / `cMapUrl` / `wasmUrl` / `GlobalWorkerOptions.workerSrc` — every one a supported relocation. A dependency with no such option is the case that stays deferred.
10. **A platform addon ships as a native file and is handed to its dependency by path.** `sqlite` is the reference: its `native:` block names better-sqlite3's addon per tuple, `sources:` stages each from the upstream release archive, and the connection controller passes `ctx.resolveNativeFile("better-sqlite3")` as better-sqlite3's `nativeBinding` — the package's own search walks up from its `__filename`, which a bundle does not have. A runtime-only built-in (`bun:sqlite`) is imported through a computed specifier, so esbuild leaves it to the runtime instead of failing to resolve it; a package self-reference (`@telorun/<name>/subpath`) is not an alternative, since subpath imports are a build error. A kernel reading a source checkout stages the one addon its host needs on first use, the way it builds a controller from source, so no manifest run is preceded by `telo release stage`; only publish, which ships every tuple, stages them all. **`pdf` is the same move through an environment variable**: `@napi-rs/canvas` takes `NAPI_RS_NATIVE_LIBRARY_PATH` rather than a constructor option, so the path is written once, before the wrapper's first import, and left — the variable is the wrapper's only override, and restoring it would point a concurrent load somewhere else. Its addon is `format: napi` with no `abi`, since N-API is ABI-stable; `format: node` is for an addon built against one Node ABI and must state which.
11. **Code for a browser is a browser entry, not a controller sidecar.** A module declares the ES modules it ships for a page under `exports.browser:` on its `Telo.Library` doc (`specifier`, `path`, `source`, optional `abi` / `external` / `exports`); the kernel builds them — on first use in a checkout, through the same builder at publish — into a `browser` layer no kernel imports, and a controller reaches one with `ctx.resolveControllerBrowserEntry(specifier)` (its own module's) or `ctx.resolveBrowserEntry(specifier)` (the module that declared the resource). Entries declaring the identical `external` list are one build and share their common code. Nothing is added to `files:`, and no built file is committed. Guide: `docs/extend/browser-entries.md`.
