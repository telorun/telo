# SDK (Node) — package guide

Loaded when working under `sdk/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. The kernel half of what the SDK declares (effect frames, zones, suspension handling, contract binding) is in `kernel/nodejs/CLAUDE.md`; kind semantics and annotations in `analyzer/nodejs/CLAUDE.md`.

## What the SDK is

The SDK uses no Node built-ins (the browser-side analyzer reads it), never imports the kernel, and has **one runtime dependency: `@telorun/cel`** — the CEL value domain.

**Identity is a string type key under `Symbol.for("telo.cel.value")`, never a constructor**, and that one fact removed a whole mechanism. The engine this replaced typed and dispatched by class, so a `Duration` or `UnsignedInt` built by one copy of it was rejected by another: the SDK existed as the single scope every package and controller obtained those classes from, templating refused to load when its engine's values were not the SDK's, and the kernel's bundle builder refused a controller bundle that inlined the engine. A symbol from the global registry is the same symbol in both copies, so **all three of those guards are gone** — nothing has to be deduplicated and there is nothing left to assert.

So `cel-value-identity.ts` is a re-export and nothing else: `celUint` / `isCelUint`, `celDurationFromNanos` / `isCelDuration` / `durationNanos` / `formatDuration` / `parseDuration` / `durationNanosFromText`, `celTimestamp` / `isCelTimestamp`, and `isCelRecord`. A controller BUILDS with the factories and ASKS with the predicates; `new` and `instanceof` are gone, the fields are the ones they were (`.value`, `.seconds`, `.nanos`), and a duration no longer renders itself — `String(d)` is `[object Object]` and `formatDuration` is what writes one.

**`isCelRecord` is the companion every structural walk needs.** A branded value is a PLAIN object, so a walk that decided "is this a container to descend into?" by testing the prototype now descends into a duration and rebuilds it without its brand, where a class instance was returned untouched by the same test. That is the one regression the brand change can cause and it is silent, so the question is asked of the value domain instead.

**A map has TWO representations and one seam between them.** A `CelMap` holds its entries by each key's own typed value, so one container carries CEL's four key types and no key can ever be a property name; a plain object with string keys is equally a map and is the only one of the two the rest of the runtime can read. So `hostValueOf` (`cel-host-value.ts`) is **the one seam a CEL value crosses on its way OUT to a host reader** — an all-string-key map becomes a plain object, recursively, by identity where nothing moved — and every such boundary goes through it rather than converting again: the result of a compiled value, a module function's arguments, a host-backed catalog function's arguments. A map with an int, uint or bool key is left exactly as it is, because a plain object cannot hold one and converting would collapse the four key types to text; whatever meets it next answers on its own terms (the typed frame names it, the plain-JSON writer keys each entry by its key's text). It converts the map representation and **nothing else** — a `uint`, an instant, a duration and bytes cross unchanged, because a host reader of a typed slot must receive the value its contract declares. Writing a value as text for a reader that is not a Telo runtime is `plain-json.ts`'s, and for one that is, `typed-frame.ts`'s.

**And both of those read a map through the domain, never through `instanceof Map`.** That was the whole cost of the representation change and it fell outside the engine entirely: a host `Map` is no longer a CEL value, so the typed frame refuses one by name — the gate that finds a controller still building one — while a `CelMap` is written as its contents rather than as its carrier. `celMapFromEntries` is therefore the only way a controller can build a map with a non-string key, and `isCelMap` the only way a reader recognises one; what identifies an entry stays the engine's business, and a reader walks `entries.values()` for the `{ key, value }` pairs.

**The two duration ranges nest, deliberately.** protobuf's `google.protobuf.Duration` reaches ±10,000 years, which **cannot be held in an int64 of nanoseconds at all** — and CEL's duration is exactly that int64. So the typed frame and the `cel-duration` plain encoding carry the wider range and cannot read through the engine's `parseDuration`; `durationNanosFromText` is CEL's grammar with no range applied, and the bound is the caller's. One grammar, two ranges, no second reader of the text. The value-type binding rows (`timestamp` and `duration` → branded values, `bytes` and `stream` → host classes) assert through a **predicate** (`ValueTypeBinding.holds`) rather than a constructor, since a brand has no constructor to test and a host class still answers with `instanceof`.

## What the SDK owns

`sdk/nodejs/src/` — public API for module authors (re-exports kernel contexts + capability interfaces). It owns the **step grammar's execution** (`step-engine.ts`, beside the `executeInvokeStep` leaf it delegates to): the SDK is the single name in `REALM_COLLAPSE_NAMES`, symlinked onto the kernel's own copy rather than inlined, so it is one version per process whatever anyone pins and is reachable from a controller bundle and the kernel's boot runner alike — a module library (`exports.code:`) is no longer copied per consumer but is still one scope per pinned version, outside the seam entirely for an npm-delivered controller, and unreachable from the kernel. Its context is STRUCTURAL (`StepEngineContext`, `InvokeStepContext` plus `ensureKindRef`), so nothing there imports the kernel or `run`.

It also owns the **durable replay seam** (`durable-run.ts`): `DurableRunHandle` — `step(path, target, inputs, execute)`, `decide(path, kind, compute)`, `park`, and the `writesInside(zone)` QUESTION — plus `stepPath` and the collapse rule. `step` MEDIATES execution rather than merely recording it, because lookup-plus-record is a leaky decomposition (two halves of one operation split so the CALLER performs the effect in between), which would silently fix the step engine and the resource graph in one process; *where* an effect executes is a real architectural axis, so `step` takes a declaration-site target identity even where the local backend resolves it in process. `decide` is the load-bearing half: a run's state is NOT just its `steps` map — inputs, predicates, loop conditions and collections are read from a scope carrying `resources.<name>.status`, a live reading republished on every dispatch by design — so recording only outcomes leaves a resume free to re-derive a decision and hand a recorded result to work it never described.

It also owns **`ctx.runtime`** (`runtime-seam.ts`), the host's own manifest machinery: `run(source, { env })` starts a child manifest isolated from the caller's and returns `{ stdout, stderr, exitCode, cancel }` — the streams are `Stream<string>`, `exitCode` settles at completion, `cancel()` stops the child and resolves once it has torn down; `check(source, { desugarImports })` runs the static-analysis pass and returns plain-data diagnostics plus a `loadError`. `test` runs child manifests through it and `assert`'s `Manifest` kind analyzes through it, so a published module binds to a versioned contract instead of importing `@telorun/kernel` / `@telorun/analyzer` — which would make kernel internals an unversioned ABI between an artifact and whatever kernel loads it. Output is streamed rather than captured because forwarding it live and retaining it on failure are both the caller's choice, and a string forecloses one. **A stream is not itself a memory bound** — withholding a `Writable`'s callback only fills its own unbounded internal buffer, and no controller awaits `drain` — so `cancel()` is what bounds an unread child, and is on the contract from the start because a supervisor needs termination before anything else. Isolation mode is the kernel's to pick (in-process child kernel today, subprocess later), which is what keeps process-global host-env state an implementation detail. Kernel half: `kernel/nodejs/src/runtime-seam.ts`.

**Contract errors are an ambient union** (`ERR_INPUT_INVALID` / `ERR_OUTPUT_INVALID` / `ERR_FUNCTION_FAILED` / `ERR_PREDICATE_NOT_BOOLEAN`, `sdk/nodejs/src/contract-errors.ts`; the last is raised by `predicateResult`, `step-predicate.ts`, the one reading of every step and boot-target predicate): raised as structured `InvokeError`s so they survive into a `catch`, nameable and typo-checked in `catches:`, never counted toward a kind's declared `throws:`, and never re-attempted by a retry policy. A kind must not declare any of them itself.

**A native function's surface is `function-controller.ts`**: `create(resource, ctx: FunctionContext)` with `resolveControllerFile`, `resolveNativeFile`, `log` and `effect` only, returning an instance whose `call(args)` is typed non-thenable, so an async `call` fails the build. **`plain-json.ts` is the one writer for readers outside Telo** (HTTP bodies, logs, CLI JSON): a `$telo` typed frame (`typed-frame.ts`) is written only at internal boundaries.

## Where to look

- "what does a host reader see of this CEL value?" → `sdk/nodejs/src/cel-host-value.ts` (`hostValueOf`, the one seam out; `tests/cel-host-value.test.ts`), `plain-json.ts` (text for a reader that is not a Telo runtime), `typed-frame.ts` (for one that is), `cel-value-identity.ts` (`isCelMap` to ask, `celMapFromEntries` to build). Its callers are pinned where they live: `templating/tests/module-call.test.ts` (a module function's arguments), `kernel/tests/cel-json-handler.test.ts` (`json`)
- "how is a step target named somewhere the instance does not exist?" → `sdk/nodejs/src/durable-target-encoding.ts` (the wire form: canonical key order, a version, refusal at the SENDER — including a `with:`-scoped target, whose `scoped` flag is separate from its `scope` tuple because a step engine knows a name resolved in a scope before it can identify WHICH RUN, and a target recording only the missing tuple would ship as its module-level namesake), `kernel/specs/durable-execution.md` §5.3, `sdk/nodejs/src/resource-instance.ts` (`RefIdentity.origin`, stamped at `create()` — the one point where an instance and its DECLARING context are both in hand), `tests/__fixtures__/durable-remote/` (the fixture backend that ships a step to a child kernel)
- "does this survive a crash?" → `sdk/nodejs/src/durable-run.ts` (the replay seam), `kernel/specs/durable-execution.md` (normative: the determinism contract, the key scheme, the conformance rules), `modules/durable-local/nodejs/src/run-handle.ts` (one backend's implementation), `analyzer/nodejs/src/validate-durable-regions.ts` (the checks), `analyzer/nodejs/src/resolve-zone-containment.ts` (the walk they all consume)
- "who journals a decision?" → `decideValue` (`durable-run.ts`), the ONE seam every decision point goes through: the step engine's `if` / `while` / `switch` / `value`, and a composer that DRIVES its own body (`Run.Iteration`'s collection, `Run.Loop`'s per-turn condition), which the engine never sees because the composer evaluates them before handing a step list over. A composer spelling the handle lookup itself is a decision point nothing can find.
- "can this value be recorded?" → `assertJournalable` (`durable-run.ts`), which is the TYPED FRAME's refusal re-raised at a step path: encodable means the value is in the CEL value domain and reads back one-to-one, so a class instance with a `toJSON` — which `JSON.stringify` accepts and which returns as a plain object — is refused where it used to pass. It returns the frame text it produced, so the backend records that rather than encoding the value twice; the refusal stays a property of the seam rather than of whichever store is wired in. A live value is still checked first, for its own message. **How a recorded value is written down is the SDK's** (`recorded-value.ts`: the codec version, absent-member stripping, the legacy / unknown-version / corrupt-frame rules), because the spec makes them normative for every backend; where the version sits on an entry is the backend's (`modules/durable-local/nodejs/src/journal-codec.ts`), never the store's: a journal keeps `v` and `value` together and looks inside neither.
- "a composer runs its body N times — how is each turn journaled?" → `turnStepPath` (`sdk/nodejs/src/step-engine.ts`), and `executeWhileStep`'s `stepPath(path, "do", turn)`, which is the same rule the engine applies to its own loop. A composer that DRIVES its own body (`Run.Iteration`, `Run.Loop`, `Run.Projection`) is handed one prefix for the whole dispatch, and journaling every turn under it is not merely imprecise: the journal takes the FIRST writer at a key, so turns 2..N replay turn 1's outcome instead of executing — work silently skipped, run still reporting success. Measured as one resource kind indexed per module version instead of all of them, with no error anywhere. Regression: `modules/durable-local/tests/iterates-every-item.yaml`, asserted on the kernel's own dispatch record.
- "can this WAIT, and what must not swallow the wait?" → `sdk/nodejs/src/durable-suspension.ts` (the signal, the latch, `parkRun` / `assertNotSwallowed` / `assertMaySuspend`, and `SUSPENDING_BACKOFF_MS`), `modules/durable/nodejs/src/{sleep,await-delivery,value}.ts`, `modules/durable-local/nodejs/src/deliver.ts`, `modules/run/nodejs/src/concurrency.ts` (branch-level parking), `analyzer/nodejs/src/validate-zone-violations.ts` (`ZONE_ATTRIBUTE_VIOLATED`), `modules/durable/docs/waiting.md`
- "what does this region guarantee about its contents?" → `sdk/zone-attributes/*.json` (the vocabulary, as data), `sdk/nodejs/src/zone-attribute.ts` (the reader + the composed schema), `analyzer/nodejs/src/zone-slot.ts` (the annotation's single reader), `kernel/nodejs/src/zone-context.ts` (`ctx.zoneAttributes`)
