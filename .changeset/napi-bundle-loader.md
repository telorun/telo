The Node kernel hosts `pkg:telo/local/napi` controller candidates: a prebuilt N-API addon at `path=` is loaded through `require`, from a source checkout or from the controller layer of a published artifact, and the PURL fragment selects a property of its exports object. A missing addon or a non-matching platform falls through to the next candidate, and a `pkg:telo/local/dylib` candidate always falls through on Node. In a source checkout an addon a `sources:` entry stages is checked against its pin first, once per file per loader, and a mismatch, a missing pin or an unreadable `sources:` block fails with `ERR_STAGED_FILE_INVALID`, naming `telo release stage`; an absent staged addon falls through with a message naming `telo release stage`. The kernel exports `NODE_HOSTED_FORMATS` and `ModuleArtifact.warmPlan(target)` — the layers a warm fetches and those it skips for want of an axis value — and `telo install` warms and reports only code layers of those formats plus `native` layers, so a Node image never warms a Rust kernel's `dylib` layer. `telo module manifest --json` reports a `napi` candidate as reaching `nodejs` and a `dylib` candidate as reaching `rust`, with no language for either, and a module declaring `native:` entries now carries `runtime.native` — the `os`/`arch`/`libc` platforms and the ABIs those entries cover.
