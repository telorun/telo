# Kernel (Node) — package guide

Loaded when working under `kernel/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. Also relevant here:

- kind semantics, capabilities, the invocation contract, CEL scope and every `x-telo-*` annotation → `analyzer/nodejs/CLAUDE.md` (the analyzer is the single reader the kernel re-imports);
- embedded files (`!include-*`) → `templating/nodejs/CLAUDE.md`;
- controller delivery (PURLs, bundles, `exports.code:`, the loader contract) → `modules/CLAUDE.md`;
- the SDK surfaces the kernel implements (step engine, durable seam, `ctx.runtime`) → `sdk/nodejs/CLAUDE.md`.

## Internals (`kernel/nodejs/src/`)

- `kernel.ts` — main orchestrator, boot sequence, multi-pass init loop, event bus. It registers `Self` on the ROOT context (pointing at the Application's own `metadata.name`), the half the import controller has always registered for a library: without it a root Application declaring its own `Telo.Definition` and instantiating it as `kind: Self.<Kind>` passed `telo check` — which registers `Self` for a root module — and failed at boot with "no module imported with alias 'Self'".
- YAML loading + CEL-YAML compilation lives in the **analyzer** (`analyzer/nodejs/src/manifest-loader.ts`, `parse-loaded-file.ts`), not here; `kernel.ts` imports it
- `evaluation-context.ts` — `EvaluationContext`, `ModuleContext` — variable/secret/resource scoping
- `resource-context.ts` — bridge: `getModuleContext()`, `registerModuleImport()`
- `module-context-registry.ts` — per-module store for variables, secrets, resources, imports
- `controller-registry.ts` — maps resource kinds to controller implementations
- `builtin-controllers.ts` — the controllers the kernel implements itself, one table (entry → lazy import) its boot registers from; its keys are exported as `BUILTIN_CONTROLLER_ENTRIES`, which is how the CLI reports a kernel candidate `{ runtime: kernel, entry }` (a need type's) as Node-hosted. The kernel-declared need types (`Telo.PublicUrl`, …) are registered per definition beside it, not entries of it
- `controllers/module/module-controller.ts` — handles `kind: Telo.Application` / `kind: Telo.Library` (includes, module scope)
- `controllers/module/import-controller.ts` — handles module imports (external modules, export CEL eval)
- `controllers/module/library-scope.ts` — the scope a `Telo.Import` normalizes and orders its library in, per resolved module URL: **the kernel's one analysis registry, read through the library's `AnalysisRegistry.forModule` view** (the same definitions and alias tables, with the library's own table as the top-level scope), plus the load-time flattened set as cross-module targets. The load already registered every module's scope, and Phase-5 injection and contract binding read it from there — normalizing against a second, per-library registry modelled one library's scope twice and cost a whole analysis pass per library. A library the load did not reach is analyzed once through the same view (validated as the pass's own module, errors raised as `ERR_MANIFEST_VALIDATION_FAILED`) and so joins the one registry. **The one exception is a library named like the application**: tables are keyed by module name, so a table under the entry's name would replace the application's own scope for every application resource (no definition found, no reference injected). Such a library is analyzed into a registry of its own, and `forModule` refuses the entry's name (`tests/library-named-like-application.yaml`). Scoped like `sharedLibraries` — a `WeakMap` on the kernel's root context — beside the target the import loads (`loadLibraryTarget`), so a second import of one URL fetches and parses nothing. `analyzer.normalize()` still runs once per import site, because Phase-5 injection mutates a registered resource's ref fields in place and two import sites must never share manifest object identity.
- `controllers/resource-definition/` — handles `kind: Telo.Definition` and parameterized templates
- `import-load-failure.ts` — what a load whose graph recorded import failures is refused with (`importLoadFailure`): one error carrying every import's diagnostic as `telo check` reports it (located at `imports.<alias>`), under the loader error's own code when it raised a coded `RuntimeError`, else `ERR_<static code>` — `ERR_INVALID_IMPORT_SOURCE`, `ERR_IMPORT_UNRESOLVED`, `ERR_INVALID_IMPORT_TARGET`, `ERR_KIND_PREFIX_RESERVED`. The load records the graph before raising it, so `telo run` locates the import line as `telo check` does; a failed `reconcile()` puts the previous graph back (with the rest of the static half) before rethrowing, so the next reconcile diffs against what is running. `importFailure` is the same refusal over failures no graph recorded: the import controller resolves, loads and identifies every target through the loader's own per-import step (`loadImportTarget`, the one the graph walk runs) and raises any failure through it, so a `Telo.Import` the graph walk never reaches (one declared in a `with:` scope) is refused exactly as one it reached — an unresolvable source `ERR_IMPORT_UNRESOLVED`, a malformed one `ERR_INVALID_IMPORT_SOURCE`, an unusable target `ERR_INVALID_IMPORT_TARGET` / `ERR_KIND_PREFIX_RESERVED` — located by its declaring file alone, since it has no `imports:` entry.
- `reserved-kind-prefix.ts` — `ERR_KIND_PREFIX_RESERVED`, over the analyzer's rule: an import aliased `Telo` / `Self` or reaching a library of either name is a loader refusal raised like every other import failure, and the root application's name and an import's alias are guarded where each is registered (`refuseReservedKindPrefix`). An imported library's name is judged with the import's target identity (`importFailure`, above), as is a `Telo.Builtins` archive reached as an import.
- `capabilities/` — base interfaces: runnable, invokable, listener, provider, template, mount
- `manifest-schemas.ts` — re-exports the shared manifest fragments. A `Telo.Definition` / `Telo.Abstract` document is validated where every resource is created, against the built-in entry's schema the registry holds — the one `telo check` applies — after `controllers/resource-definition/kind-document-guard.ts` refuses a `capability:` outside the roster (`ERR_CAPABILITY_UNKNOWN` / `ERR_CAPABILITY_NOT_DECLARABLE`), so a mistaken capability is one error and an undeclared key is `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED`
- `logging/` — structured logging, implementing `kernel/specs/logging.md`: `logging-pipeline.ts` (threshold → redaction → sampling → fan-out), the `json`/`pretty`/`otlp` encoders, `console-sink.ts` / `file-sink.ts` / `debug-wire-sink.ts`, `normalize-attributes.ts` (§6.3 limits, iterative and bounded), `span-id.ts` (salted counter, hex only at the encoding boundary), `kernel-logging.ts` (bootstrap writer → declared-config handover, replay, seal). The record model, severity scale, `Logger`, the `Telo.Sink` contract and `RecordBuffer` (the bounded §10.3 sink buffer) live in `@telorun/sdk` — a third-party sink is an ordinary module, so everything it composes must be on the module-author surface; the kernel's own sinks reach them through the `logging/log-sink.ts` re-export shim. The redaction **path parser** lives in the analyzer so `telo check` and the runtime share one grammar. Reached by controllers as `ctx.log`; a sink controller reads its level and counts drops through `ctx.logging` and attaches nothing.
- `tracing.ts` (`KernelTracer`: the counter, the attached trace sinks, the `enabled` gate — on while a debug consumer holds it or a sink is attached), `span-export.ts` (a finished span as the `SpanRecord` a sink receives — identity, timing, outcome, attributes; never inputs, outputs or scope), `instance-span-attributes.ts` (the `x-telo-span-attribute` paths recorded per instance at bind, read at the dispatch site), `controllers/tracing/log-trace-sink-controller.ts` (`Telo.LogTraceSink`, spans as log records carrying their own ids via `logging/span-record-identity.ts`), implementing `kernel/specs/tracing.md`. Every span end site — `runInvoke`, `runInstance`, `runTargets`' app span, `openSpan`'s `settle` — builds the record only when a sink is attached. `openSpan`'s `inbound` is the W3C carrier (`{ traceparent, tracestate? }`), parsed by `logging/trace-parent.ts` — an invalid or all-zero one roots a new trace — and an upstream parent id stays its hex string end to end, exported verbatim rather than salted like a local counter. **The kernel attaches exactly the sinks `logging.sinks` / `tracing.sinks` name** (`listed-sinks.ts`: the two entry forms, `{ sink, when }` evaluated at load, and `ERR_SINK_CONTRACT_MISSING` for a listed instance that is not itself the sink): a root resource right after `_createInstance` binds its effect owner, as one effect of its create frame whose inverse flushes, detaches and closes it; an import's exported instance once the graph is up, detached first at teardown. No controller can attach — `ctx.tracing` and `ctx.logging.attach` do not exist — so a sink declared outside the lists is inert (its inverse only closes it). When no listed log sink is attached, `sealBootstrap` adds the zero-config console sink.
- `workspace-marker.ts` + `resolveCacheRoot` — **the `.telo` cache is anchored at `telo-workspace.yaml`, so one repo has one cache.** Precedence: `TELO_CACHE_DIR` > the directory holding the marker > `<entry-dir>/.telo`; no marker anywhere above means the old per-entry behaviour, so the file enables the shared cache rather than gating one. Subdirs are `manifests/`, `analysis/`, `validators/`, `yaml-parses/`, `cel/`, `controller-src/`, `npm/`, `cargo/<sdk-backend>/`, `debug-ui/`. Both kernels resolve the root the same way, and a child kernel inherits its parent's rather than deriving one.
- `host-env.ts` — `boot()` replaces global `process.env` with a **guardrail** Proxy that denies a **manifest-derived** set: the env-var names the root Application binds via `variables`/`secrets`/`ports` (`collectDeclaredEnvKeys` in `application-env.ts`) and every need's env name. A need's name is hidden from `ctx.env` as well, through the same Proxy over the kernel's env snapshot; a declared variable's is not. A declared key reads back `undefined` (hidden from `in`/enumeration) with a once-per-key warning, so **controllers can't bypass a declared binding** — they use `ctx.env` or the declared `variables`/`secrets`. Every other key passes through — **no vendor-env allowlist** (a bundled SDK's `NODE_ENV`/`AWS_*`/`BUN_*` reads are undeclared, so untouched). The denied set is process-global and additive across in-process kernels. Kernel `TELO_*`/cache reads and subprocess spawns use `hostEnv()` (real env captured pre-lock); `analyzeOnly` never boots. A guardrail, not isolation; `process.env` is left non-writable. Tested in `tests/host-env.test.ts`.

## Lifecycle, scopes & value flow

**Capability governs *wiring*, not dispatch.** The kernel calls `init()` and `snapshot()` on any instance that has them, with no capability check, so a `Telo.Runnable` may implement `init()`. What the declared capability *does* govern is which `x-telo-ref` slots accept the kind, statically: a `Run.Sequence` step's `invoke:` takes `Telo.Executable` (the parent capability `Telo.Invocable` and `Telo.Runnable` extend), its `targets:` takes `Telo.Runnable | Telo.Service`. A resource that must be both started and invoked therefore has to be **two kinds** — no single declared capability satisfies both slots.

**`init()` and `run()` RETURN what undoes them; there is no `teardown()`** (normative: `kernel/specs/revertible-effects.md`; SDK half `sdk/nodejs/src/effect.ts`, kernel half `kernel/nodejs/src/effect-scope.ts`). An effect is a forward action paired with its **inverse**; `ctx.effect(reason, body)` returns a **lazy chain**, `.effect(...)` extends it threading each step's result into the next, and a lifecycle method hands the chain back for the kernel to execute. **The signature is the forcing function, and that is the whole design**: an opt-in `ctx.effect` beside a retained `teardown()` was implemented first and nothing pointed an author at it — the reference controller grew and behaved identically, and a mechanism that exists to stop something being forgotten cannot itself be forgettable. **Lazy** so sequencing and recovery are the kernel's and the chain stays a *description* a second runtime can execute; **not a thenable**, because an `async` function unwraps one on return and the kernel would receive the last step's result instead of the chain. A chain is a value, so branches and loops build it. **Frames**: one opened with the context (covering `create()`), one per `init()`, one per `run()`, unwound **LIFO** — a failed `init()` must not revert what `create()` built, and a subclass extending its parent's chain (`super.init(ctx).effect(…)`) unwinds in reverse construction order by construction. **No invocation frame** — a scope ending when a call returns is `try`/`finally` — but a chain may be executed in place with **`.perform()`**, the one spelling for an allocation whose lifetime is an *operation* (`Durable.Workflow`'s per-run hold, taken inside `invoke()` and released when the run settles *or parks*); it joins the resource's frame and must be **disposed** by that operation. `dispose()` is idempotent and **unordered**, takes the effect off its frame in constant time (a frame's entries are a set, so a resource performing one effect per connection holds only the live ones), and never cascades: `run()` takes its hold before it opens the socket, so releasing the hold must not close the socket — a frame is a recovery order, **not a dependency graph**. **`inverse` is OPTIONAL** — a step that allocated nothing returns its result alone, because a chain also SEQUENCES lifecycle work and a required no-op closure would make "nothing to undo" read the same as "the author forgot". **An inverse pairs with a forward action that HAPPENED**: a lazily-created listener or subscription registers its own effect at creation (`.perform()`), never a slot reserved in `init()`. Bodies come in two forms, the single `{result, inverse?}` and the async generator yielding one inverse **per completed step** (so a body failing between allocations recovers exactly what it did, and one interrupted by a shutdown stops at the next step boundary). `result` is pass-through — the kernel hands it to the next step and the caller, and keeps only the reason and the inverse. **A failed `init()` recovers and the INSTANCE IS DISCARDED**, so the retry constructs a fresh one: inverses restore state outside the instance, and a controller's own half-built fields are beyond their reach (which is why `Http.Server`'s per-mount resumability bookkeeping is gone). **A DEFERRAL is not a failure** — `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING` unwind the frame but KEEP the instance, since re-creating would re-register an import's alias or a template's children. An inverse refusing **during recovery withholds** the resource; one refusing **at teardown aggregates** into `ERR_EFFECT_RECOVERY_FAILED` and the cascade continues. **`acquireHold` returns the raw inverse and registers NOTHING** — which frame owns a hold is the caller's fact (`run()`'s belongs to the run frame; a per-operation hold taken inside `invoke()` is disposed when that operation ends), so it is placed in a chain rather than self-registered, which would also double-register wherever a caller states it. **The detached drain is NOT**: it waits under a bound and abandons, where an inverse succeeds or refuses, so it is no longer folded into `instance.teardown` and runs after the frames unwind. No per-effect events — one per effect would swamp the wire and the logging path. Every stdlib module whose controllers return chains declares `requires: telo: ">=0.82.0"`: an older kernel calls `init()`, discards the returned chain, and silently allocates nothing. A module with nothing to undo declares no chain and needs no floor — the three in-memory stores clear a `Map` they own, which is not an observable effect, so they stayed universally loadable.

**A frame orders one resource's own effects; the TEARDOWN CASCADE orders resources against each other, and a consumer unwinds before everything it holds.** Within a context the order is `teardownPriority` as a hard tier, and inside a tier a reverse-topological order over the create-time reference edges (`collectResourceRefs`, projected onto local names, so a cross-module `!ref Alias.name` orders against the local `Telo.Import`) with reverse insertion as the tiebreak. Priority stays a TIER rather than another edge because it states an edge nothing captured: a log sink is reached through `ctx.log` rather than a ref slot, so no walk of the manifest can find what will log on the way down, and letting a discovered edge reorder across tiers would override a declaration made precisely because the edges are not all discoverable. A cycle emits in tiebreak order rather than raising — teardown must always run to completion. **Own resources go first and the child-context sweep is a BACKSTOP**, which is the half that was wrong: a child context belonging to a resource is torn down by that resource's own inverse (an import's `init()` returns `child.teardownResources()`, and so does a template's), so it already unwinds at its owner's edge-determined position, and running a child cascade ahead of the own-resource loop tore every imported library down before any resource of the importing context — an app resource holding `!ref Alias.name` unwound against a provider already gone, and the owner's inverse then found nothing left to do. The sweep still runs, after, because `teardownResources` is idempotent and two shapes reach it with no owner to claim them: a `lifecycle: shared` library, which deliberately gives no importer a claim, and an import whose `init()` never ran to register one. **Both directions fall out of the one order** — a library borrowing a parent instance through `resources:` unwinds before that instance, because its import initialized after it — which is why neither "children first" nor "own first" is the rule and the position of the owning resource is.

**A dispatch that misses BECAUSE THE RUNTIME WITHDREW THE TARGET is a cancellation, not a manifest defect.** An unwind removes each instance as it goes, so work still in flight — a detached task the kernel waited for and then abandoned above all, since its ambient scope is the uncancellable root — finds an emptying map. Reported as `ERR_RESOURCE_NOT_FOUND` that is a durable claim about the author's code made about a condition that lasts as long as the shutdown: a durable run recorded it as `failed`, which is terminal, so one ordinary Ctrl-C left a run id nothing would ever pick up again. It raises `ERR_INVOKE_CANCELLED` with the usual `InvokeCancelled` event instead, and needs no cooperation from anyone — a durable body leaves its run `running` for the resumer, and a step's retry budget is not spent re-issuing a call nobody intends to answer. **Keyed on the recorded WITHDRAWAL, never on the context's state**: `unwindResources` (reconciliation's half) withdraws an instance and deliberately leaves the state alone, so a state check converts a shutdown and misses the watch-session save, which is the frequent one. The mark is set at `unwindEach`, the single removal site, and cleared when the name is registered again — a stale one would report a genuine missing resource as a cancellation forever after. Only the MISS is converted: a resource still in the map is dispatched as before, because a teardown-time flush is legitimate work.

**Configured state is pulled; observed state is pushed.** `snapshot()` returns what the author configured, and the kernel pulls it after `init()`, after `run()` is dispatched, after each `invoke()`, and on every `setStatus()` — it is a function of the manifest, so re-deriving it is always correct. What a resource *learns* goes the other way: `ctx.setStatus(...)` reports it at the moment it is known, because nothing but the controller knows when that is. Both meet in `EvaluationContext.publishSnapshot`, the single publication path. Splitting them is what keeps each shape described once — a controller never rebuilds observed state inside `snapshot()` from a field it stashed only for that purpose. A publication is a **reading, not a live window**: the published value is detached from what the controller handed over (`detachSnapshotValue` rebuilds plain objects / arrays; class instances and functions pass through, since copying one would break it), so mutating a reported structure cannot rewrite an already-published value.

**Observed state (`status:`)** is what a resource learns while running, as opposed to what its author configured. A kind declares it as a JSON Schema block on its `Telo.Definition` / `Telo.Abstract`; a controller reports it with **`ctx.setStatus(...)`**; the kernel holds the last value and publishes it at `resources.<name>.status.<field>`, leaving the flat half (`resources.<name>.<field>`) untyped and unchanged. Reporting **replaces** rather than merges (this is the resource's observed state now), is AJV-checked against `status:` at the call that made it (`ERR_OBSERVED_STATE_INVALID`, or `ERR_OBSERVED_STATE_UNDECLARED` when the kind declares no block), is an error **before the resource has started** (`ERR_OBSERVED_STATE_BEFORE_START` — `init()` performs no I/O, so nothing is observed there) **except for a `Telo.Provider`**, which has no `run()` and reports from `init()` onward: a report made inside `init()` is held and published when `init()` returns (`setResourceStatus` skips publication while the resource is still in `createdInstances`), and is dropped when the attempt fails or defers, and is **sticky**: the last reading stays published until teardown, so a dispatch that reports nothing leaves it in place. A kind that declares `status:` may not also return a flat `status` field (`ERR_OBSERVED_STATE_KEY_COLLISION`); one that declares none may use the name freely. `required:` inside `status:` is rejected — every declared field is mandatory once the resource has run, and a sometimes-absent one is declared nullable. The chain is folded in the scope that **declared** each definition (an `extends` alias belongs to the file it was written in) — the kernel stamps the folded block at registration beside `effectiveAuthorSchema`; the analyzer re-scopes per declaring module. A kind declaring `status:` publishes even without a `snapshot()`. A compile-eval read of a Provider's status is legal unless the provider is declared in a `with:` scope: `create()` defers the reader with `ERR_LOCAL_REF_PENDING` while a producer (or the import an `<Alias>.<name>` read crosses) is declared in the reader's context and not yet initialized (`deferPendingStartupReads`, over the analyzer's `startupObservedStateReads`), the backstop for the init-order edge `prepare()` already draws. Statically: `OBSERVED_STATE_IN_STARTUP_FIELD` (a path through `.status` in a compile-eval field whose producer is not a Provider, is a Provider declared in a `with:` scope, or resolves to nothing), `OBSERVED_STATE_NEVER_RUN` (nothing can start the producer — in no `targets:` and named by no step's `invoke:` — and it is not a Provider), `OBSERVED_STATE_REQUIRED_FORBIDDEN`, and `CEL_UNKNOWN_FIELD` under `.status` (cross-module too: an import's exported instances are typed under `resources.<Alias>.<name>`). At runtime there are three `ERR_OBSERVED_STATE_UNAVAILABLE` messages — not started / started but `run()` still pending / `run()` returned (or a Provider's `init()` returned) with a declared field missing — because each needs a different action and only the kernel can tell them apart. See `kernel/docs/observed-state.md`.

**`Run.Sequence` scopes (`with:` / `targets:`).** `with:` is an array of full resource declarations (`kind` + `metadata.name`) whose lifetime is the sequence — created on entry, torn down on exit — annotated `x-telo-scope: ["/steps", "/targets"]` so `!ref`s in either resolve against them. `targets:` lists with-resources to `run()` before the steps. Standing a server up around a test is exactly this shape (`modules/crud/tests/crud-over-http.yaml`). A scoped resource **publishes like any other**: each `ScopeHandle.run()` gets its own map of the scope's resources, layered **at read time** over the enclosing module's (not copied at scope entry — `setResource` replaces `_resources` wholesale, so a copy would go stale) with scope-local names winning (matching `ScopeContext.getInstance`'s order, so CEL and `!ref` agree), and `ScopeContext.run(name)` dispatches a scope target through the kernel chokepoint so it is traced, records that it started, and publishes. Fresh per run, so two concurrent runs never observe each other. A scoped name resolves only inside the `x-telo-scope` regions. **The handle is built on the context that OWNS the resource, never the root** (Phase 5 passes it as `PreInitHook`'s `owner`): a `with:` block's inline declarations name their kinds through the import aliases of the module that DECLARED them, so a library's scoped `kind: OAuth.RedirectListener` resolves against that library's `imports:` — the root Application has never heard of the alias. A scope nested inside a scoped resource forwards its opening scope's context rather than replacing it, so this holds at any depth.

**A template child is stamped with its DEFINING module**, because Phase-5 injection resolves a resource's reference sites through `metadata.module`: a child registered without one resolved its kind against the ROOT application's aliases, found a field map only when the consumer happened to import the same alias, and otherwise skipped injection silently — leaving every ref slot a raw `{kind, name}`. So a library's template body worked or failed depending on what its CONSUMER imported, and `http-client` explained the residue as a rule about scopes ("declare the client at module level"), sending the author to a remedy for a problem they did not have. That fallback is gone: `resolveClient` goes through `ctx.resolveRef` like every other slot, and a reference that genuinely does not resolve says so.

**A template body's bare `self.<path>` continues past a reference** (`memberOf`, `controllers/resource-definition/resource-template-controller.ts`): each step reads the member off the value in hand, and where a live instance has none, off the manifest that instance was declared with (`instance-declaration.ts`) — whose own reference slots hold live instances by then, so a reference a referenced resource holds is handed on as the instance. The instance is asked FIRST, which is what keeps `self.model.schema` reading a `Telo.JsonSchema`'s folded shape rather than the one written; the cost is that a member of the instance — a method included — shadows a declared field of the same name. The analyzer half is `fromSelf` in `template-forward.ts`.

**Controllers resolve a `!ref` slot with `ctx.resolveRef(value, guard, describe, expects)`**, not the standalone `resolveRefInstance` — only the context form rescues a `!ref` that reaches the controller as a raw sentinel (**Phase-5 injection substitutes at the reach's concrete sites, and the reach stops at an `x-telo-scope` array**, so a ref slot on a scoped resource is not an injection site; Phase 2.5 *does* rewrite such a sentinel when it can name a target, so both shapes arrive) and resolves a bare name **scope-local first, enclosing module as the fallback** — the order `ScopeContext.getInstance` and the CEL `resources` layering already use, so `!ref` and CEL agree about what a name means inside a scope. That is what lets a `with:`-scoped resource reference a scoped sibling (`OAuthClient.RedirectAwait`'s `listener:`). The standalone form stays for callers holding only a `{ moduleContext }` slice; it takes the precedence via the optional `resolveLocalInstance` hook on `RefResolveContext`. Sentinel knowledge lives in the kernel, never the SDK, whose only runtime dependency is the CEL engine's value identity.

**A need is bound at load to one FULFILMENT, and is never an instance a controller holds.** A fulfilment is a `NeedFulfilment` (`need-fulfilment.ts`) — the type, its fields, and the values of its sensitive fields — published as exactly its fields. Three things produce one: a resource of a need-type kind, created by the controller `controllers/need/need-type-controller.ts` registers for every `Telo.NeedType` (the analyzer's synthesized definition, registered as is); an import's field-by-field supply, which the import controller evaluates in the IMPORTER's scope and builds itself, owned by the importer; and nothing else — a whole supply hands down the importer's own fulfilment. The import controller resolves the supplies before loading (a fulfilment registered but not created, or a resource a supply's CEL reads, defers with `ERR_LOCAL_REF_PENDING`) and binds each need under its name in the child with `ModuleContext.bindNeed` BEFORE the library's resources register — borrowed, published directly rather than mirrored (a fulfilment's fields never change), an optional need nothing supplies bound to `null`. **A sensitive value joins the redaction set of the owning context and of every context it is bound to** (`addRedactedValues`); the set is one object for a context's lifetime, refilled in place, because a logging scope holds it by reference from the moment it is configured. `ctx.resolveRef` refuses a fulfilment in either shape it arrives in (`ERR_REF_UNRESOLVED`), and **Phase-5 injection never places one in a slot** (`dependency-injection.ts`): the slot keeps its reference, and a kind consuming the need whole opens it with **`ctx.resolveNeed(pointer)`** (`Need.Resolve`) — answered only for a reference site of the resource's own kind (the registry's reach over the manifest `create()` bound, the pointer from the site's keys) holding a fulfilment, with its fields, the names of its sensitive fields, and the constraints and parameters of the OUTERMOST need of the whole-forward chain, read off the load's need table (`Kernel.needTable`, `outermostNeedEntry`; a module context's own needs are the names `bindNeed` bound, `isNeed`, at `[...needPath, name]`). **`ctx.verifyNeed(pointer, observation)`** (`Need.Verify`) checks the report against the slot's `observes` (`ERR_NEED_OBSERVATION_INVALID` for a member it does not observe, one left out, a version that is not semver, or a slot observing nothing) and compares it with the outermost need (`need-resolution.ts`, `compareObservation` — the only place a range is compared): a mismatch is `ERR_NEED_UNMET` with `data { need, type, source, required, actual }`, the message naming the environment variable or the supplying declaration. **Every observing pointer is owed by a deadline** (`need-observation.ts`): `create()` records, per instance, the concrete pointers at observing slots holding a reference and the deadline its effective capability has (`OBSERVATION_DEADLINES`, the analyzer's one table), and the init loop, `runInvoke` and `runInstance` settle it when the entry point the deadline names first returns — a pointer still unreported is `ERR_NEED_OBSERVATION_INVALID`, failing that entry point. A kind whose slot `observes` with no deadline or no controller is refused at definition registration (`ERR_X_TELO_REF_INVALID_OBSERVES`, `controllers/resource-definition/observes-guard.ts`, both meta-controllers). A load the analysis refused for a need-table diagnostic (`isNeedTableDiagnostic`) raises the table's `ERR_` twins rather than the aggregate `ERR_MANIFEST_VALIDATION_FAILED` — one error carrying every other analysis error beside them, so fixing one refusal never uncovers another the analysis already knew. **Every static need refusal is raised at load, before any resource initializes**, by running the analyzer's need table over the whole loaded graph (`Kernel.refuseNeedTable`) — every module the application runs, those the import edges reach from the root, never a version reconciliation lost or what only it imports: a dependency's defect included, which the entry-scoped analysis never reports, each as its `ERR_` twin. **A need reaching the root unsupplied is read from the environment** — the table's `environment` list, one name per field — inside `resolveApplicationEnv` (run only, never `analyzeOnly`): each set value decoded against its field's schema as a root variable's is, a failure joining that call's `ERR_MANIFEST_VALIDATION_FAILED` (a sensitive field read as a secret, its value never printed); some set and a required one not is `ERR_NEED_PARTIALLY_SUPPLIED`; none set for a required need `ERR_NEED_UNMET`, naming every name to set; none for an optional one `null`. The root's own needs are bound in the root context right there (their injected declarations are not registered); a library's are bound by the import controller from the values the kernel left on the root context (`controllers/module/environment-needs.ts`), keyed by need path — `ModuleContext.needPath` is the module instance's place in the tree (`[...importer, alias]`, `[<LibraryName>]` for a shared library), the same rule the table's paths follow — and built IN THE LIBRARY's context, so its sensitive values join that context's redaction set. **Every need env name is hidden by exact name** from `process.env` (joined to the guardrail's denied set) and from `ctx.env` (the kernel hands controllers a `createLockedEnv` view, `controllerEnv`), each read warning once: a need is delivered to the module that declared it, through its fields, and to nothing else. The import controller's own checks are the backstops for a load that never ran the table. A `shared` library binds the needs of the import that instantiated it; every other import must supply the same (a whole supply by identity, a field supply by value) or `ERR_SHARED_LIBRARY_CONFLICT`.

**Public addresses are read with the root's needs, and refused before anything initializes** (`public-urls.ts`, over the analyzer's `public-address.ts`). Inside `resolveApplicationEnv` every root `Telo.PublicUrl` whose env name is unset is answered from the host values (`withDerivedPublicUrls`): a need's base is `TELO_HOST_PUBLIC_URL_TEMPLATE` with `{port}` filled from the resolved port; among the needs sharing a base the primary — or the only one — gets it, every other `TELO_HOST_PUBLIC_URL_SECONDARY_TEMPLATE` with `{label}` and `{port}` filled, and a need neither answers stays for the read to refuse (`ERR_NEED_UNMET`). The templates are read only when the root declares a `Telo.PublicUrl`. A template that is not an http/https origin, a main template holding `{label}`, a secondary without it, or a derived first label that is no DNS label is `ERR_NEED_HOST_VALUE_INVALID`, naming the variable and never its value. After the read, `resolveAddresses` refuses a URL with no host and two addresses no host could route apart (`ERR_NEED_PUBLIC_URL_COLLISION`: one port, same host or same pattern suffix and form; two ports, same host on the same effective port), and each port's `Telo.PublicUrl` hosts ride `getResolvedPorts()` as `publicUrls` into `Kernel.PortsResolved`. The two host values join the need env names in the guardrail's denied set (hidden from `process.env` and `ctx.env`, with their own warning), and the runtime seam strips them from a started child's inherited env (`withoutHostValues`, `host-values.ts`, over `KERNEL_HOST_VALUES` — exactly the host values, never the whole `TELO_HOST_*` prefix, since the container-engine values must reach a child) — a child is a root of its own. `ctx.resolveNeed` answers an address need with `port`, the number its `port` parameter resolved to (`Need.Resolve`'s optional `port`), which is what `Http.Server`'s port check reads. A pattern fulfilment the kernel cannot read as a host pattern is refused, never skipped.

**Durable directories are answered, scanned and checked with the root's needs, before anything initializes** (`durable-directories.ts`, over the analyzer's `durable-directory.ts`). Inside the environment read every `Telo.DurableDirectory` whose `path` env name is unset is answered from `TELO_HOST_STATE_DIR` (`withStateDirectories` / `stateDirectoryAnswers`): `<state dir>/needs/<need path>`, the path `.`-joined into ONE directory name, so the scan reads one level. After the read the kernel scans `needs/` (`scanStateDirectory`): an entry no durable-directory need path of the table names (a name starting with `.` is never one) is an orphan — `ERR_NEED_ORPHANED` naming both paths when an answered directory does not exist yet, else a `NEED_ORPHANED` warning on the kernel logger; nothing is moved or deleted. Then every directory read from the environment, root and library needs alike, is checked (`refuseUnusableDirectories`): created when absent, refused with `ERR_NEED_DIRECTORY_UNUSABLE` when it is not a directory, cannot be written or cannot be created, naming the need and the env name or host value it came from — one error for every refused need. The other two supply routes are checked where their fulfilment is built: an import's field-by-field supply in the import controller, a fulfilment the manifest writes in `needFulfilmentController`. `size` and `access` are never enforced. `TELO_HOST_STATE_DIR` joins the hidden names with the other host values.

**Phase-5 injection leaves a NON-reference value at a reference site untouched, by design — but an EXPRESSION there is refused before it is ever evaluated.** The injection walk substitutes at the reach's concrete sites and says nothing about a value that is not a reference; `ctx.resolveRef` / `resolveRefInstance` is what eventually refuses one, at DEREFERENCE time, as `ERR_REF_UNRESOLVED`. That backstop is unchanged and stays the backstop, because it is lazy and conditional — it fires at request time in one manifest and never in another, which is exactly what let a computed reference ship. So the two sites the kernel owns refuse an expression at or ABOVE a reference slot up front (`refuse-computed-ref-slots.ts`, `ERR_REF_SLOT_COMPUTED`): a template body's `self`-expansion, and every `create()` — for a compile-eval field, where a `Telo.Provider`'s implicitly compile-eval root makes such a field a legal eval site, so nothing static had looked at what was beneath it, for a field the kind marks `x-telo-eval: runtime`, which the controller's own per-call expansion would turn into data just the same, and for a field a CEL region covers with no `x-telo-eval` (`x-telo-context`, `x-telo-error-context`, a step context — how a route's per-request fields are declared): `create()` hands the kind's region scopes to the reader beside its compile and runtime paths and runs the refusal for a kind that has any of the three, a structural `Telo.Template` kind's regions excepted. "Is this evaluated" is the analyzer's one eval-mode question (`evaluatedField` over `celEvalModeAt`), never a list of annotations; `ERR_RUNTIME_EVAL_WITHOUT_INVOKE` still reads the runtime paths alone. Both read the ANALYZER's reader (`computedRefSlots` over `AnalysisRegistry.referencePositionsOf`), which is what makes the refused positions exactly the positions `telo check` reports as `REF_SLOT_COMPUTED`; the one exemption is a bare `self.<path>`, which `expandSelf` navigates rather than evaluates. Keyed on PROVENANCE, never on shape — a reference slot legitimately holds a reference, a live instance, an inline declaration, a value-branch scalar and raw JSON Schema. Pinned by `kernel/nodejs/tests/ref-slot-computed-placement.test.ts` (analyzer position set == kernel refusal set, per placement) and by both halves of `tests/check-run-agreement.yaml`, each guard independently.

**A controller's `ctx` is scoped to the context that OWNS its resource** — the module context for a top-level resource, the per-run scope child for a `with:`-scoped one. Registering a manifest, resolving a sibling by name, expanding CEL, spawning a child context, dispatching and publishing all go there. `ctx.moduleContext` is reserved for what belongs to the MODULE rather than the resource: imports (`registerImport` / `resolveImported*`), the controller policy, and the logging scope — all inherited by a scope child, not owned by it. The distinction is load-bearing: a scoped resource that registers an inline definition into the module lands it in a pending queue the module's init loop drained at boot, so it is never created and the dispatch fails with `ERR_RESOURCE_NOT_FOUND`.

**A kind is registered once per kernel; where its body runs is decided per instance.** The registry is keyed by canonical kind, so a library imported from many isolated sites brings the same definitions each time — an import skips a `Telo.Definition` / `Telo.Abstract` already registered from the same file under the same controller policy (`controllers/resource-definition/registered-definitions.ts`, scoped like the shared-library registry). The record lives as long as the definition instance that made it — its `init()` inverse forgets it — so a library rebuilt in place registers its edited kinds rather than being skipped. What DOES differ per import is the context: a template body and an inherited `base:` mapping run in `ModuleContext.resolveKindScope(kind)` — the context that declares the kind as THIS instance spelled it, answered by the same walk as `resolveKind` (one lookup returns both the canonical kind and its declaring context, so the two cannot drift); a kind no context declares is `ERR_KIND_SCOPE_UNRESOLVED` (`declaring-context.ts`). They used to capture the context of whichever import registered the kind, so with two isolated imports `A.Greet` read `B`'s variables (`tests/isolated-import-kind-scope.yaml`).

**Resources are created in dependency order, each initialized as soon as it is created.** The order is the analyzer's (`prepare()` → `setInitOrder`): reference edges plus SOFT edges to the declarations a kind is spelled through — the `Telo.Import` behind `Http.Api`, the `Telo.Definition` behind `Self.Page`, a definition's `extends:` target. Imports and definitions are not dependency-graph nodes, so they used to sort last and every resource spelled through one failed its first creation; a reference written through an import alias (`!ref Lib.sweep`, a step's `invoke:` included) orders its holder after that import the same way, because a call's plain-encoded literals are read against the target's declaration when the holder is created (`resource-literal-decoding.ts`) and an import that takes a resource input is created after that resource — a holder whose target had not resolved is read again at its next creation rather than marked read; soft because an import handed an instance of a kind it exports itself needs the instance first, and a hard edge would be a false `DEPENDENCY_CYCLE`. Interleaving create and init is what lets a `create()` that needs a dependency LIVE (a template forwarding `self.<ref>`) succeed on the first pass; creating everything before initializing anything cost one pass per such hop. The pass loop stays as the backstop for a dependency only visible at runtime, so a retry now means an edge the order lacked.

**An init failure is reported by ROOT CAUSE, not by count.** When the multi-pass loop gives up, everything downstream of the real failure is unfinished too, so the kernel classifies the set before raising `ERR_RESOURCE_INITIALIZATION_FAILED` (`init-failure-diagnostics.ts`). What makes an entry **derived** is its error CODE — `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING`, a deferral meaning it never ran — **never a reference edge**: an edge proves an edge exists, not causation, so a resource that refs a failed dependency *and* fails its own validation stays a root cause rather than having that error swallowed. Edges are **attribution only**; `RuntimeDiagnostic.blockedBy` is the **root** of the chain (the walk stops at the first non-derived entry), and a deferral with no visible edge is derived but unattributed. Edges are captured at `create()` time, before Phase-5 injection replaces refs with instances, so the walk never descends into a controller's object graph. A nested context's failures (an import initializing its library) attach as `children` rather than flattening into the parent's message — reported even when the wrapping entry is itself collapsed, since a child's roots are not shadows of the parent's failure — and both headlines come from `summarizeInitFailures`, never from re-parsing rendered text. Nothing is hidden wholesale: if every entry is a deferral, the set reports unclassified. Renderers consume the classification (`derived`/`blockedBy`/`children`), never re-derive it. See `kernel/docs/resource-lifecycle.md` §2.2.1.

**Execution zones ride the ambient invocation context.** A resource can require being invoked inside another's body (a statement inside its transaction); the **zone stack is the `zones` member of `InvokeContext`** — deliberately NOT a second ambient store beside the cancellation scope, because a parallel store means enumerating every site that must clear it and one missed site is a false guarantee under a hard error. On the existing context, the two clearings the runtime already performs do the work with no zone-specific code: `ctx.runDetached` replaces the ambient with the uncancellable root, and a `Telo.Service`'s `run()` establishes none (so every shipped inbound trigger, all registered by Services, is zone-free by construction). The residue is exactly one shape — a `trigger.inbound` registered from *inside* an invocation by a non-Service — spec'd as a conformance obligation on the registrant: dispatch through **`ctx.rootContext()`**, never `undefined`. That obligation is what the analyzer's hard error on `trigger.inbound` edges rests on. **Nothing hangs off `openSpan`** — tracing is off by default and `openSpan` is a no-op then, so a safety guarantee hung there would be absent by default. **Every context rebuild goes through `deriveContext(base, overrides)`** (SDK): a fresh object literal at `runInvoke`'s tracing branch / `runInstance` / `runTargets`' `targetCtx` / `openSpan` would drop `zones` under tracing-off and keep it under `--debug`, a safety property that changes with a debug flag. **A zone entry is three identities and nothing else** — providing kind, provider handle, correlation handle — so it stays ABI-serializable and no controller can read another module's open transaction off the stack. Instance identity is a **`ResourceHandle`** (`{ id, ref }`, `id` minted at `create()` — the single instance-production site, so an instance is never observable unbound; `ref` is the declaration site, diagnostics only). The instance→handle `WeakMap` has **no reverse direction**, which is what stops a handle becoming someone else's instance. A `with:`-scoped resource gets one id per scope run, which is also what the static correlation rule says. Controller surface: `ctx.self`, `ctx.withZone(slot, fn)` (a **scope function**, not push/pop — push/pop cannot be honest across async boundaries; hands back the derived context AND the minted entry), `ctx.requireZone(field, ctx?)` / `findZone` / `zonesFor(instance)`. **A controller names its own annotation SITE, never a kind** — it has no alias scope (`ctx.moduleContext` is the consumer's, and `resolveKind` is not on the surface), so every field of the entry is derived by the kernel from the annotation. **The payload rule: provider-private state hangs off an INJECTED INSTANCE, never a module import** — a module's controllers ship as separate bundles each inlining its copy of a shared source file, so module scope is one copy per bundle (that was the live `sql` bug: `transaction:` threw on every path). `sql` keeps its executor `WeakMap<ZoneEntry, Kysely>` as an instance field on the connection, and the explicit-zone path **throws** (`ERR_SQL_ZONE_FOREIGN`) rather than falling back, since `?? this.db` would convert a delivery split into silently non-transactional writes.

**A SUSPENSION is a signal, not an error, and the kernel must not wrap it.** A durable run that waits raises `ERR_DURABLE_SUSPENDED` (`sdk/nodejs/src/durable-suspension.ts`), which unwinds to the workflow that owns the run — so `runInvoke` passes it through and reports `InvokeParked` (a `SpanOutcome` of its own: a parked invocation neither succeeded nor failed), exactly as it already passes a cancellation through. That one site matters more than the rest: EVERY hop between a parking kind and its workflow goes through the chokepoint, so wrapping it once would convert a park into an `ERR_EXECUTION_FAILED` everywhere. The three composer sites — a `try:` step, a `catches:` list, a retry policy — also rethrow. **Everything beyond those is caught by a LATCH rather than by enumeration**: `parkRun` records the signal against the run handle (an SDK-owned `WeakMap`, safe because the SDK is one scope per process, so a backend cannot forget to set it) and the workflow calls `assertNotSwallowed` BEFORE settling the run, raising `ERR_DURABLE_SUSPENSION_SWALLOWED`. Enumerating the swallowers is unbounded and stale on the next module; detection is O(1) and needs no cooperation from the swallower.

**Module calls are bound per module scope at `create()`** (`module-functions.ts`), before compile-eval expansion, into one dispatch table per module context under `@telo:module-functions`, shared by reference with template and scope children — a template body binds in its defining library. Refusals (`ERR_FUNCTION_UNRESOLVED` / `_NOT_EXPORTED` / `_NOT_CALLABLE`) happen there, so a call in a branch that never runs still fails at boot; a pending callee defers the caller. Call edges join resource dependencies, withdrawal replaces a callee's entries with a cancellation thrower, and an impacted kind definition escalates reconcile to `restartRequired`. Anything a callable throws becomes `ERR_FUNCTION_FAILED` (suspension and cancellation pass through), and a coded error raised inside CEL keeps its code. Arguments bind through the analyzer's `callArgumentBinding`, shared with `telo check`. Every callable instance's `call`, CEL-bodied or native, is bound to its signature at creation (`function-binding.ts`), and only a kind declaring its own `controllers:` gets the narrowed `FunctionContext` — a child inheriting its controller keeps the full context and is not bound twice; a napi Rust function is created as an effect and destroyed at teardown. **A native function's data site is delivered as data** (`callable-data-views.ts`, over the analyzer's `callable-data-slot.ts`): before its `create()`, each reference at a site whose every use is `dependency` is resolved through the lookup Phase-5 injection uses — moved onto the context (`EvaluationContext.injectionInstance` / `injectionPending`, a scope child extending it), so an uninitialized referent defers with `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING` — and replaced, on the copy the controller receives, by the referent's VIEW: the configuration its own controller received (recorded for every creation, `recordReceivedConfiguration`), without `kind` and `metadata`, each reference inside replaced by its view, deep-cloned, frozen, one per declaration. The copy is recorded with the site paths beside the text paths (`recordControllerCopy`), so Phase-5 injection leaves them; the declaration keeps the reference, so creation order, deferral, reconcile and rebinding follow it. A view is checked positively — every leaf a CEL value, every container plain — and anything else (a compiled expression, a scope, a need's fulfilment, an instance at no reference site, a reference left unresolved, a cycle) is `ERR_CALLABLE_REFERENCE_NOT_DATA`, worded by the analyzer's `callableReferenceNotDataMessage`. In a template body that lookup is the child context's — siblings and the defining module's imports — so a bare name it leaves unresolved that the defining module declares (`EvaluationContext.declaredBeyondReach`, set by `spawnChildContext` over `declaresName` — a module context's needs included, an optional one bound to nothing too — and extended by a scope child) is refused with its own reason, naming the repair; Phase-5 injection is unchanged. **Polyglot debt:** `kernel/rust` hosts no `Telo.Callable`, so it delivers no views and raises no `ERR_CALLABLE_REFERENCE_NOT_DATA`; a kernel hosting native functions owes both. Application `logging:` and `Telo.JsonSchema` rule conditions bind nothing — the analyzer refuses module calls there (`x-telo-unbound-calls`).

**A compile-eval result is held to its slot's schema** (`compiled-results.ts`, over the analyzer's `compiledResultSlots`): validation sees an expression only as its stand-in — a create-time failure with any stand-in recorded is judged again on every error (`SchemaValidator.findingsFor`, two instances created on the first such failure) and refused only if a finding survives the analyzer's stand-in judge (`withoutStandInFindings`, which decides each union by validating its branches on their own), so a stand-in's own value-constraint failure neither refuses the resource nor hides a literal's after it, and a stand-in satisfying a union never excuses a finding raised beside that union. **A branch is judged with no default applied and nothing written; defaults come only from the whole-schema pass**: an all-errors pass first fills every default the first validation would have, into the kernel's stripped copy (never the resource; merged back from the normalized view where the value holds a 64-bit integer), and one verbose all-errors instance that fills none then raises every finding, the whole schema's and each branch's — a validator applies a `default:` inside a union to a branch compiled alone, which refused a correct resource on a key its author never wrote, and two instances would name two copies of one schema node and reproduce nothing. The same expression written twice in a `uniqueItems` list is a written duplicate and is refused here, before expansion and in either eval mode, where the text is repeatable (the stand-in identity `readStandIn` records, never the compiled value's resolved calls). Since that validation saw only stand-ins, once a resource's compile-eval fields are expanded each result is validated against the slot it fills — after the host-path and format refusals, which keep their codes — and refused as `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED` naming the path. A written value HOLDING results is held too, to the keywords that relate its parts (`uniqueItems`, `const`, `enum`): before expansion those are decided on the written parts alone, so two different expressions producing one item of a `uniqueItems` list are refused here, naming the list. A union the written value does not decide is validated whole, and the check runs on a detached copy, so it fills no default into what the controller receives or into an object the expression shared; the root Application's `logging:` / `tracing:` blocks are held the same way at load (`ERR_MANIFEST_VALIDATION_FAILED`, before any sink is created). **A predicate is a boolean**: every step predicate and every boot target's `when` goes through the SDK's `predicateResult`, and anything else is `ERR_PREDICATE_NOT_BOOLEAN` — never read by truthiness.

**Every text a resource holds is judged in its writer's language at creation, and a controller receives each `Text` as its record** (`text-records.ts`, over the analyzer's `text-slot.ts` / `text-judgement.ts` / `text-schemas.ts`). Before expansion `prepareResourceTexts` refuses the two text annotations in any schema the resource holds (`x-telo-text-context`'s shape as `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED`, a values pairing as `ERR_TEXT_VALUES_FOR_INVALID`) and every `TextCatalog` (`ERR_MESSAGE_ENTRY_COMPUTED`, `_PLACEHOLDER_UNKNOWN`, `_PLURAL_CATEGORY_INVALID`, `_ENTRY_DUPLICATE`) — a still-compiled expression ABOVE a catalog slot, in any eval mode, being `ERR_MESSAGE_ENTRY_COMPUTED` through the analyzer's `catalogsComputedAbove` — and settles WHO WROTE each value: a PROVENANCE, per field path, of the writing module's `lang:` and whether an expression produced it. A resource's own values are its declaring module's (`Kernel.moduleLang`, by the module file's source) — the library defining a template for its body's entries, the module declaring a `base:` child for the parent instance it builds — except where a value was FORWARDED: the template controller records, for each entry it registers, that a bare `self.<path>` carries what `self` held there (crossing a reference into the referenced declaration's own provenance, as `memberOf` crosses into its manifest) and that any other `self` expression computed its value; the inherited controller records the same for the parent resource its `base:` mapping builds (`mappingProvenance`), or the child's provenance whole without one. Provenance is internal, keyed by object identity, and never written into a manifest. After expansion `settleResourceTexts` refuses a catalog whose provenance says an expression produced it or a value in it — what a template's `init()` or a `base:` mapping computed before handing it on (`ERR_MESSAGE_ENTRY_COMPUTED`, `TextProvenance.computedWithin`) — and judges each text (`ERR_MESSAGE_SYNTAX_INVALID`, `_SOURCE_LANGUAGE_MISSING`, `_PLURAL_CATEGORY_INVALID`) and each values pairing, and — unless the kind forwards its configuration (a template, an inherited `base:` child), whose controller receives the text as written — replaces each `Text` with `{ text, context, lang, computed }` on a COPY the controller receives: the declaration keeps what its author wrote, and Phase-5 injection, which mutates the declaration, is carried into the copy (`syncInjectedReferences`) since the two share every container not on the way to a record. A values pairing at an accessor field is read as its bindings: a literal's `{ value }` is judged as that value, a chain's `{ root, path }` is a key present with a value its consumer resolves. **A text the controller's own evaluation produces is settled when it evaluates it** (`LateTexts`): creation fixes which expressions still compiled bear text — one AT or BELOW a `Text` / `Message` slot, one ABOVE one (walked by the schema it fills), one half of a values pairing — keyed by the identity of the nodes the controller's manifest holds, with each writer's language from the provenance; `ctx.expandValue` then settles every such node its input holds, a value the controller built around them included: each text judged as at creation and handed over as its record with `computed: true` (a record already built passes through as it is), each pairing judged when the same evaluation produces its computed half — a refusal is a `RuntimeError`, so at the dispatch chokepoint it is `ERR_EXECUTION_FAILED` carrying it as its cause. A resource holding no such expression pays nothing. **A kind typing an accessor field's value as text is refused when it registers** (`registerResourceDefinition`, `ERR_TEXT_SLOT_ACCESSOR`, over the analyzer's `textSlotAccessorProblems`, named shapes read from the shared validator and the registry). So is a misplaced `x-telo-text-values` (`ERR_TEXT_VALUES_INVALID`, over `textValuesProblems`); a text at a node declaring it is judged against those values wherever it is settled — at creation, and by `LateTexts` for one an expression produces. **At a call**, `bindModuleFunctions` refuses each call site's argument at a `Text` parameter that is not literals alone (`ERR_TEXT_ARGUMENT_COMPUTED`, off `CompiledValue.callArguments`), judges the literal in the calling module's language and the values it writes; at dispatch the function binding judges the values a call computes before the function runs (`ERR_MESSAGE_PLACEHOLDER_UNBOUND` / `_VALUE_UNSUPPORTED`) and hands a NATIVE function each `Text` argument as its record, attributed to the module whose table bound the call (`computed: false`, since a computed text is refused) — a call a controller makes through a slot it holds has no writer, so its text is `computed: true` in `und`; a function whose body is CEL reads the text as written, as its parameters are typed. The argument record a call is validated against is the analyzer's `argumentRecordSchema`, which lifts each parameter schema's reserved fragment definitions to its root. **A kind marking a catalog set** (`x-telo-text-catalog-set`) is refused when it registers if the mark is misplaced (`ERR_TEXT_CATALOG_SET_INVALID`, or `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED` for a value other than `true`), and before a resource of it is created its set is gathered (`text-catalog-sets.ts`, over the analyzer's `text-catalog-set.ts`): its own catalogs from the copy its controller is about to receive, each reference resolved through the lookup Phase-5 injection uses (deferring as injection defers) and each referent read as the configuration its controller received (`receivedConfigurationOf`) with its references off its declaration as registered (`authoredDeclarationOf`; the holder's own likewise), where a template body's bare `self.<path>` already holds the instance it forwards — compile-eval expansion copies a plain-object instance, and a copy names no declaration — a duplicate translation is `ERR_MESSAGE_ENTRY_DUPLICATE`, worded as `telo check` words it. **Polyglot debt:** `kernel/rust` builds no text records and refuses a resource whose kind's schema or parameters reach the `Text` fragment, or whose kind marks a catalog set, which it does not gather (`ERR_UNSUPPORTED_MANIFEST_FEATURE`); `sdk/rust/core`'s `TextRecord` is the type a controller would receive. That refusal is also why it owes nothing yet for a text settled at evaluation or under an accessor field: it raises no `ERR_TEXT_SLOT_ACCESSOR`, and a `Value.Expand` it would serve settles no text.

**A host path is held to what its slot says it names at creation** (`host-paths.ts`): after `!module-path` and compile-eval resolution, `refuseMisplacedHostEntries` stats every absolute host path at a slot declaring `entry` and refuses one that exists as the other kind (`ERR_HOST_PATH_ENTRY_MISMATCH`, naming the resource, field, path, found and declared) or that the filesystem will not answer for (`ERR_HOST_PATH_UNREADABLE`, with the OS's reason) — skipped, by a per-schema memo, for a kind whose schema declares no `entry`; each token maps to a filesystem query (`HOST_ENTRY_QUERIES`, an unmapped one a startup error). An Application variable or secret declaring `entry` is checked the same way at load, inside `ERR_MANIFEST_VALIDATION_FAILED`. An absent path is never refused.

**A value of a type declaring `members` (`Telo.Url`) is built at creation and redacted where it lands** (`members-values.ts`, over the analyzer's `members-value-slot.ts`; no type named). A literal — its text, or an object of literal members — is read before validation by the shared decoding walk, and validation refuses one that does not build, or whose bound member a slot argument refuses, under the type's own code (`ERR_URL_INVALID`, the reason in the message, never the value). An expression is only a stand-in then, so after compile-eval expansion `buildMembersValues` builds what it produced — text decoded, an object of members built — and holds every value of the type the resource holds to its slot's arguments through the shared validator, before the result checks that follow. Every such value's whole text and sensitive members (`redactedTextsOf`) join the redaction set of the context owning the resource; a need fulfilment's join every context it is bound to (`needFulfilment` marks a field sensitive as delivered when it is marked, or when its value holds a sensitive member), a secret of the type is redacted whole, and a root variable or secret holding one, at any depth (`redactedTextsWithin`), has its text and password added to the root's set. The same refusal is an entry of the application's `ERR_MANIFEST_VALIDATION_FAILED` for an environment value or a `default:` (`membersEnvRefusal`, naming the variable and the schemes, never the value), and an import's field-by-field supply is built and held the same way when the import initializes. **An import's `variables:` / `secrets:`, and the library `default:` standing in, are one decode site for every value type** (`controllers/module/import-inputs.ts`, `settleImportInputs`): decoded through each instance type's plain encoding, every members type built, then each entry validated against the library's declaration on a copy (no default filled) — `ERR_URL_INVALID` for one that does not build, `ERR_HOST_PATH_RELATIVE` / `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED` for any other mismatch (the issue's keyword, never the validator's message, which quotes the value), each naming the import and the variable; a built value's texts, nested ones included, join both the library's and the importer's sets, and two imports of a `shared` library agree when their values are equal by plain encoding. A bound contract builds the same way at dispatch, on a copy, in BOTH directions — a call's arguments before they are validated, a result before it is validated — when it reaches such a slot (`BoundContract.buildMembers`, read off `reachesMembersSlot`), so text or an object of members computed at a call site or by a template's `result:` arrives as the value. **A value built at dispatch joins no redaction set** — one per call would grow without bound — and is protected by the VALUE RULE instead: every observability writer asks the SDK's `holdsSensitiveMember` (read from the type's entry) and writes such a value as `[redacted]` — log attributes (`normalize-attributes.ts`), a thrown value written into a record's error (`to-error-value.ts`), span attributes (`span-export.ts`), trace payloads (`tracePayload`, built only when something may listen — `emitSpan`, over the bus's listener query — and censored through `sensitive-member-censor.ts` lazily, so a payload nobody reads costs no walk, with inputs and outputs first shown as the contract builds them — `BoundContract.payloadView`, recorded per instance beside the sensitive paths — so text at a `Telo.Url` slot carrying a password is censored too), the resource-Created properties and a validator's refusal message (`describeValue`, which quotes the value it refuses); a value holding none is written as its text. Text derived from a dispatch-built value is not covered. One that does not build is the direction's ambient `ERR_INPUT_INVALID` / `ERR_OUTPUT_INVALID` (`membersContractViolation`) — never the type's own code, which would widen what every dispatch can throw — its `data.issues` holding one entry per value (`pointer`, `code: ERR_URL_INVALID`, `reason`, plus a dotted `path` and `message`), the text the same, never the value. `ctx.readPlainEncoded` builds a transport's inbound value the same way, refusing with the same entries and adding to no set. `buildMembersValues` reports, it never throws: each caller decides which refusal carries the entry (`MembersRefusalEntry`, `membersEntryText` — the one line the env load prints too).

**An accessor field is delivered as a binding, never evaluated** (`accessor-bindings.ts`, over the analyzer's `accessor-binding.ts`). `create()` reads the kind's `x-telo-eval: accessor` sites beside its compile and runtime paths and its regions — every one through the analysis registry's named-shape lookup (`AnalysisRegistry.shapeLookup`, the lookup `telo check` reads them with, so a site inside a recursive named shape is one here too; the template controller reads a body entry's kind through the same lookup off its context) — refuses a value the field cannot hold as `ERR_ACCESSOR_NOT_PLAIN_CHAIN` before anything is expanded, leaves each accessor field out of the compile expansion BY ITSELF (`EvaluationContext.expandPaths`' holes: everything beside it under the same compile path is evaluated, while a runtime path keeps its whole-property overlap rule), and — after the checks that read each evaluated result against its slot — replaces each field with `{ root, path }` for a chain or `{ value }` for a literal, copying every container on the way so the manifest a resource is re-created from keeps what its author wrote. A template body leaves an accessor node compiled for the entry's own creation unless it reads only `self`. Accessor fields do not make a kind need `invoke()`: `ERR_RUNTIME_EVAL_WITHOUT_INVOKE` reads the runtime paths alone.

**A value naming a browser export is checked at `create()`** against the `exports.browser` entries of the module that declared the resource (`browserExportSites` / `browserExportProblems`, the analyzer's reader): `ERR_BROWSER_ENTRY_UNKNOWN`, `ERR_BROWSER_EXPORT_UNKNOWN`.

**Kernel holds decide when an app exits.** `waitForIdle()` resolves at zero holds, so **every inbound source takes one while it is armed** — a listening `Http.Server`, an `Mcp` endpoint, a `Schedule.Interval` / `Schedule.Cron`. An armed timer is NOT itself a reason to stay up (that is what made a schedule-only app exit before its first tick), and the hold is what makes "an app whose only work is scheduled" expressible without a server bolted on beside it. Taken in `run()` and released by the run frame, so a schedule that is never started holds nothing; a schedule that ENDS (a bounded cron with no further occurrences) releases early, since it is no longer a reason for anything. Anything that must let a one-shot app finish has to release its hold.

## Integers at the JSON boundary

**A CEL integer is int64 and needs no cast, anywhere** (normative: `kernel/specs/invocation-contract.md` §4.3–4.4). `int` evaluates to a JS BigInt, so `size(...)` / integer arithmetic produce one — and a BigInt used to be unable to leave a manifest: `JSON.stringify` throws on it, and AJV's type check is `typeof data == "number"`, so declaring `type: integer` rejected it *before* serialization. The only way out was `double(...)`, which says "float" about an integer and truncates past 2^53; it had spread into the stdlib's examples and docs. Both doors are open now, in the kernel, so **no module and no manifest handles this**: `boot()` installs `BigInt.prototype.toJSON` over `JSON.rawJSON` (`enableBigIntJson`, `kernel/nodejs/src/bigint-json.ts` — a composition-root action, so the installer is kernel-side; it **throws** rather than degrading on a runtime without `JSON.rawJSON`, since every site that used to carry its own handling now relies on it). A BigInt then serializes as its **exact decimal digits** — not a new policy, but what `fast-json-stringify` already emitted for a schema-typed `integer`, so the runtime's two JSON serializers now agree at every magnitude rather than only below 2^53. Process-global, in the same spirit as the `process.env` guardrail, so it covers every JSON boundary in the process including a third-party module's. The validator half is `withBigIntsAsNumbers` (`kernel/nodejs/src/bigint-schema-view.ts`), owned by `SchemaValidator.compile()`'s validator and `ctx.validateSchema` — **one layer, not two**: the contract binding validates the raw value and lets the validator normalize, merging the `useDefaults` fills back (**index-wise through arrays**, since AJV writes defaults under `items` too) so the dispatched value keeps its 64-bit range. `double(...)` retains only its real meaning — moving into the double domain for arithmetic, where CEL has no `int OP double` overload. Because `toJSON` runs **before** a replacer, a serializer that deliberately encodes a BigInt differently reaches the original through `bigIntAt(this, key)` (`@telorun/sdk`, the module-author half): `encodeJsonValue` tags it (a persisted value must replay as the same type), the `json` log encoding quotes it past the safe range (as OTLP does), and the `pretty` console encoding renders it as text. A `typeof v === "bigint"` replacer anywhere else is now dead code that changes an encoding silently. Regression coverage: `tests/integer-json-boundary.yaml`, `kernel/nodejs/tests/bigint-json.test.ts`.

## Layered module artifacts

A published module is **one artifact of several layers**, not one tarball — normative spec at `kernel/specs/module-artifact.md`, model/parser/matching in `analyzer/nodejs/src/artifact-{selector,layer-index}.ts` (browser-safe, shared by `telo check` and the runtime, same precedent as the redaction path parser). The publish half (the payload builder writing the `layers:` index, the pin gate) is in `cli/nodejs/CLAUDE.md` § Publishing.

- **Layers by role:** `manifest` (`telo.yaml` alone), one `controller` layer **per selector**, one `library` layer **per selector** (the `exports.code:` entry point a *dependent module* resolves this module's declared specifier to), one `native` layer **per selector** (the files of the module doc's `native:` entries on that tuple, materialized only by `ctx.resolveNativeFile` or a warm), one `browser` layer **per selector** (the built `exports.browser:` entries, `format: esm` plus the entry's `abi`; materialized only by a browser-entry resolution, and by every warm whatever its target), `assets` (what the author's optional `assets:` list claims, fetched lazily on first module-relative access), and `common` (everything unclaimed).
- **`library` is its own role because it is materialized by a different event**: a controller layer is reached when one of THIS module's kinds is instantiated, a library layer when a DEPENDENT's code imports it — which happens with no kind of this module in play, and happens for a module that has no kinds at all. Per selector rather than a singleton, for the same reason a controller layer is. A file named by BOTH an `exports.code:` entry and a `controllers:` candidate — the normal shape, since a module is one bundle whose controllers are fragment-selected — lands in the **library** layer: that is the weaker precondition, since a consumer must reach it without loading this module's controllers while the reverse never holds. So `materializeController` pulls **both code roles plus `common`** for its selector, and a consumer's resolution pulls the library role alone.
- **A selector** is `format` + optional `os`/`arch`/`libc`/`abi` PURL qualifiers on the same candidate (`pkg:telo/local/napi?path=./rust/x.node&os=linux&arch=amd64&libc=gnu`), in the OCI/GOOS vocabulary. **The axis names are data** — `analyzer/artifact-axes/axes.json`, generated into the untracked `analyzer/nodejs/src/artifact-axes.ts` by `scripts/generate-artifact-axes.mjs` from both `prepare` scripts, so `PLATFORM_AXES` stays a literal union and no TypeScript restates the list; an axis is appended, never reordered, because release ledger keys render axes in that order. An axis entry may declare a value form: `abi` must be `<family>-<version>`, enforced by the one selector normalizer for candidates, `exports.code:` and published layer indexes alike. The host reports `abi=node-<process.versions.modules>` on Node and leaves it undetermined under Bun, which reports Node's number and loads none of its addons. Matching is one rule per axis: an axis the selector omits accepts anything, an axis it states must be equal; an undetermined *host* axis matches nothing that constrains it. So a Node kernel never downloads the `dylib` layer, and a `linux/amd64` host never downloads the `darwin/arm64` binary. Selection reuses the existing `ControllerEnvMissingError` fallthrough — `ControllerPolicy` is untouched — and the platform check runs **before** materialization, or a candidate list would fetch every platform on the way to the right one.
- **The sink runs toward correctness.** An unclaimed file joins `common`, which is materialized alongside *any* code layer **and** on any module-relative file read, so both an undeclared sidecar (a `.wasm` beside its glue) and an unclaimed static file are on disk when needed — a module shipping only static files has no controller to ride along with. `assets:` and the `siblings=` qualifier are optional refinements: omitting either costs bytes, never a load failure. Publish prints the partition so an author sees where each file landed.
- **The `layers:` index** in the published `telo.yaml` replaces the old scalar `filesIntegrity`. Per layer: `role`, `selector`, `blob` (OCI blob digest — addresses the layer and verifies the transfer) and `integrity` (framing-independent content digest — verifies what is extracted, re-derivable from disk). It lives in `telo.yaml` because the import pin hashes `telo.yaml` and nothing else; the OCI manifest is fetched by a mutable tag and is outside the chain, and pinning *it* is circular since `telo.yaml` is one of its layers. The manifest layer has no entry for the same reason. Chain: `import pin → telo.yaml → blob digest → layer contents`.
- **Addressing never reads the OCI layer list** — the pinned index is self-addressing, so a republish that reorders layers is invisible rather than fatal. Only the *manifest* layer is located through the OCI manifest (by media type), and its bytes are then pin-verified. Flat layer list, never an image index: the manifest and asset layers are platform-neutral, so an index would duplicate them per platform.
- **`ModuleArtifact`** (`kernel/nodejs/src/bundle/module-artifact.ts`) is built during `kernel.load()`, the only point where the **pinned** ref (`requestedUrl`) and the already-verified manifest are both in hand — a controller loader sees only the canonical base URI, which carries no `#sha256-`, so a self-fetching loader would degrade to trusting the cached `telo.yaml`. It memoizes per layer and serializes through `withDirectoryLock` (`kernel/nodejs/src/directory-lock.ts`, shared with `NpmControllerLoader`).
- **Native files are reached by name through `ctx.resolveNativeFile(name)`** (SDK), resolved against the module declaring the resource's KIND (`definition.metadata.source`, the precedent the controller loader already follows) rather than `ctx.moduleContext.source` — the file ships with the controller asking for it, and an inherited controller runs in a context created for its ancestor's kind, so the ancestor's module answers with no special case. First matching entry in declaration order wins; from an artifact only that `native` layer is materialized; from a source checkout a staged file is brought to its `sources:` pin on first use (`ensureStagedEntry` in `bundle/source-staging.ts`: `checkStagedEntry`, the one rule `telo release stage`, publish and the Rust kernel's `dylib` loader share, then a fetch under a per-archive-URL lock in the module's `.telo/staging/`, written only once it matches — the one sequence `telo release stage` also runs, mirrored by the Rust kernel's `bundle/source_staging.rs`; per archive URL rather than per module because a fetch may take as long as a lock waiter waits, so a module-wide lock timed out a peer staging an unrelated file; a file on disk is never fetched again once it matches, an unpinned entry is refused rather than fetched, and a fetch prints one line, since a first run can block for minutes), no native file is read while the module's `sources:` block does not read (the unreadable block may be the one staging it), and a checked-in link is read only when it leads to a file inside the module. A staged `napi` addon gets the same treatment before it is opened, once per file per loader; one whose archive cannot be fetched falls through as env-missing and a stale copy on disk is never opened, a missing pin or an archive not holding the pinned file is `ERR_STAGED_FILE_INVALID`, and any other staging failure (a lock, a write) is `ERR_STAGING_FAILED` — three error classes (`ArchiveFetchError`, `ArchiveContentError`, anything else), so a lock timeout is never reported as a bad pin. Every failure of `resolveNativeFile` is `ERR_NATIVE_FILE_UNAVAILABLE` — not `ControllerEnvMissingError`, since there is no candidate to fall through to. Lookup is keyed by every file of a module (owner and `include:` partials), because a definition's `metadata.source` names the file that declared it.
- **Module files are reached through `ctx.resolveModuleFile(relative)`** (SDK), which returns a **URI** and materializes the `assets` layer on first use. Never derive a directory from `ctx.moduleContext.source`: for a published module the manifest URL is not where the payload lives, and a `dirname` of it silently resolves against the process cwd. `mcp-client`, `assert`'s manifest loader and `Test.Suite` all use it — every one resolves a path the resource's AUTHOR wrote, which is why it resolves against the module that declared the resource. A slot whose value is a location on the host needs no controller resolution at all: it declares `x-telo-type: Telo.HostPath`, the author writes `!module-path` for a module file, and the kernel hands the controller an absolute path (`Http.Static.root`; the anchoring and the refusal of a relative computed path are `host-paths.ts`). **A controller's own module file is `ctx.resolveControllerFile(relative)`**, resolved against the module declaring the kind by the same lookup `resolveNativeFile` uses (`Http.Reference` reads Scalar's browser bundle this way). Both, `!include-*` and `!module-path`, share one resolution, which in a source checkout brings every MODULE FILE a `sources:` entry stages AT OR BENEATH the reference to its pin (staging a missing or stale one, through one archive reader per resolution) before handing it over — a reference may be a directory a library reads files out of, so checking only an exact match would leave the files a directory reference reaches unverified — and resolves nothing while the module's `sources:` block does not read. A module file is an entry an `assets:` pattern selects or a notice (the analyzer's `stageableFiles` classification); a native file or platform-qualified controller beneath the reference is left to its own resolution, filtered to the host, since covering it made `resolveModuleFile("./")` fetch every platform's archive. Failures are `ERR_MODULE_FILES_UNAVAILABLE`.
- **Browser entries are reached by specifier** through `ctx.resolveBrowserEntry` (the module that declared the resource, `ctx.moduleContext.source`) and `ctx.resolveControllerBrowserEntry` (the module declaring the kind, the `resolveNativeFile` lookup) — one resolution, `browser-entry-resolution.ts`. From an artifact the entry's `browser` layer alone is materialized (`ModuleArtifact.materializeBrowser`, by exact selector, no `common`); from a source checkout the entry is built from its `source` by `controller-loaders/browser-bundle-builder.ts` into `<cache-root>/browser-src/`, together with every entry of the module declaring the identical `external` set — ONE esbuild run with code splitting, so what they share is a chunk both import; a module carried built (no source on disk, the built file and its sidecar at `path`) is served as it lies. `BROWSER_BUNDLE_OPTIONS` sits beside the controller options and differs where a page differs from a kernel: browser platform, ES2022, automatic JSX, the `source` condition, production `NODE_ENV`, no `require` banner and no realm external. The cache is keyed like `controller-src` — every input esbuild reported plus the options and the group's own declarations — and each build is written to a private directory and renamed into place. Beside each entry the build writes `<path>.siblings.json`, the files the entry loads (its chunks, its stylesheet) as `{ "files": [ { "path": "<module-relative POSIX path>" } ] }`, sorted by `path` and serialized one way (`serializeBrowserSiblings`) because it is inside the layer's integrity; that sidecar ships in the layer and is what a resolution reads in every mode, so the answer needs no metafile. `readBrowserSiblings` is its one reader: it ignores members it does not know, and refuses — the resolution's `ERR_BROWSER_ENTRY_UNAVAILABLE`, never an empty list — a sidecar that is missing or malformed, and one naming a path that is absolute, leaves the directory (`..`, or a link leading out of it) or is not a regular file there, which is therefore never read or served. The name is reserved; the publish and package builders refuse an author's file at it. A declared `exports` name the built entry lacks, and any other build failure, is `ERR_BROWSER_BUILD_FAILED`; an unknown specifier is `ERR_BROWSER_ENTRY_UNKNOWN`. **Polyglot debt:** `kernel/rust` reads the `browser` role off a layer index and materializes none, and `sdk/rust` has no counterpart of either method.
- **A `Telo.Builtins` root owns a published built-in vocabulary archive** the way a module doc owns a module (`bundle/module-manifest.ts`'s owner kinds): its identity is what a transport tags and annotates with, and its `layers:` index — one `common` layer holding the `LICENSE` — is appended by publish. No loader reads one as a module (`kernel/specs/builtin-vocabulary.md`).
- **Layers are OCI-only.** A plain HTTP origin serves a manifest and nothing else; a bundled payload is always an OCI artifact.
- **Pre-layers artifacts still resolve.** A single-blob artifact (`application/vnd.telo.module.v1+tar`) contains `telo.yaml`, which is all the read path wants, so every module published before layers keeps loading — that is what leaves npm-backed modules untouched. It carries no index, so a *payload* published that way fails at the controller with an actionable republish error. Only the six modules shipping `files:` need republishing.
- **`telo install --platform os/arch[/libc] --abi <family>-<version>`** pre-materializes every layer that target could need (cross-architecture image baking); `telo run` materializes lazily. `abi` comes from `--abi` alone, never from the host — the process running the install is not the runtime that will run the app — so a NAMED platform warms no abi-constrained layer without it — and **install then REFUSES** rather than reporting it: the tree an install produces for a platform someone named is the only cache its consumer (a baked image, a packaged application) has, so a skipped layer is a boot failure on another machine, delivered at build time as a line nobody read. **Without `--platform` the target is this machine and its abi is the host's**, since discarding a value already in hand made a bare `telo install` unable to warm the layer the very runtime about to open it reports; a gap there is a warning, because `telo run` on this machine still fetches lazily. The refusal names the module and the layer, and the caller supplies the remedy — the flags differ, and `telo package` accepts no `--abi` at all. Only code layers of `NODE_HOSTED_FORMATS` (`js`, `napi`) are warmed or reported, so a Node image never carries a Rust kernel's `dylib` layer. For `telo run` cache warming remains an optimization, never a correctness requirement — which is the bug the lazy path replaced, where a cold run failed because payloads landed on disk only after the load that needed them. For a consumer that will never fetch again, an incomplete warm is the same failure moved back to the machine that can still fix it.

## The realm, and what a controller resolves against

**A controller bundle's `@telorun/sdk` resolves to the instance the running kernel has already loaded** (`controller-loaders/realm.ts`). The kernel publishes its own instances into the process and writes a **generated package** — a `package.json` plus a module re-exporting them — into a `node_modules/` beside the bundle, under the slot rule the sibling-library shims use (`shim-package.ts`, shared by both). It replaced a symlink at the kernel's own package directory, and the reason is that a symlink needs that directory to exist: inside a single-file executable the SDK is *in the binary*, so there is nothing on disk to point at and every bundled controller failed with `ERR_MODULE_NOT_FOUND`. It is also the only mechanism that works on every runtime — Node's module hooks are not honoured by Bun, which this repo's own `pnpm run test` runs under. Identity holds because the shim reads the instance out of the process rather than resolving a package. Content-checked on every write, so a cache directory shared between kernel versions converges on the running kernel's surface; **a symlink found in a writable slot is removed first** (`clearLinkedSlot`), because writing through one lands in the SDK's own source tree. **A directory is remembered as prepared only when nothing was left undone**: a failed write is reported and retried on the next load, while a slot an installer owns is reported once and settled. What this mechanism fails into — two SDK instances in one process, or a bare `ERR_MODULE_NOT_FOUND` on a read-only mount — says nothing about itself, so it never fails silently.

**The npm install root keeps its `file:` dependency and is deliberately NOT unified with this.** That tree is reconciled by a package manager, which prunes what it did not install and (pnpm, by default) installs a missing peer from the registry — so a generated package there would be removed or shadowed by a registry copy, which is two SDK instances in one process. An install root only exists where a package manager does, so there is no binary case to unify with.

**A compiled validator is served from the same table, in-process** (`realmRequire`): the kernel evaluates cached validators with a `require` of its own, so ajv's runtime helpers are handed over directly and nothing is written to disk. Those helpers are imported statically by `realm.ts` precisely so a bundled kernel carries them.

## A CEL value leaving the kernel for a host reader

**`json(dyn): string` writes through the SDK's plain-JSON writer**, which is the one writer for a reader that is NOT a Telo runtime — not `JSON.stringify`, which wrote whatever each representation happens to look like: a map as its carrier (`json({'a': 1})` answered `{"entries":{}}`), a `uint` as `{"value":"7"}`, bytes as an index-keyed object and an instant as its seconds-and-nanos pair. The writer writes each as the one plain form its type declares, keys a map with non-string keys by each key's text (the protobuf JSON rule), and refuses a key two of them would share rather than dropping an entry. `nodeCelHandlers` is the only place in the kernel that answers a catalog function, and the gate is `tests/cel-json-handler.test.ts`.

**A log attribute and the debug wire read a map through the value domain** (`isCelMap`), never through `instanceof Map`: a `CelMap` is a plain object carrying a type key, so a prototype-shaped reading saw its own `entries` field and put `{entries: {}}` on the wire for every map a watch session showed. Anything else a controller hands over that is a map outside the domain is not one, and the typed frame is where that is refused by name.

## Caches are never keyed on an unknown

**A warm load parses no YAML.** Parsing is most of a warm `load()` (the `yaml` library composes at ~1 MB/s, and a module's `telo.yaml` is large), so the analyzer's `Loader` takes a `YamlParseCache` and the kernel hands it `<cache-root>/yaml-parses/`: a hit restores each document's JSON projection and position table, and the `yaml` documents are parsed only if something reads them — an editor or `telo migrate`, never the run path. One entry per source file and runtime family, holding the key it is valid for (text hash, exact runtime, analyzer / templating / `yaml` versions), so an edit or an upgrade overwrites the file's own entry and the directory stays bounded by the number of files. That is why the kernel reads a module's owner fields off `manifests` rather than `documents`. A parse that reported errors is never recorded.

**A packaged application names its own analysis key, and the key changes only how files are IDENTIFIED.** The stamp is filed under a hash of the entry URL and signed over each reachable file's source URL, both absolute paths on the machine that ran the load — neither survives a payload being unpacked at a digest-keyed path somewhere else, so every start of a packaged app re-ran the whole validation walk and said nothing, a miss being the designed quiet recovery. `Kernel.load({ analysisKey })` files the stamp under the payload's digest and identifies each file relocatably — a remote module by the pinned ref it was requested as, a local one by its path relative to the entry's own directory, which is a property of the manifests rather than of the machine. **Every signature still hashes the CONTENT of every reachable file**, and that is the half that cannot be dropped: a verdict keyed on the payload alone is a verdict about the PAYLOAD while the load is from an unpacked TREE, so a tree truncated by a full disk or half-restored from a backup would hit the stamp and boot a manifest nothing had validated. The CLI half is `cli/nodejs/CLAUDE.md` § `telo package`.

`runtime-versions.ts` reads the versions the analysis stamp and the validator cache are keyed by, and returns **`undefined` rather than a placeholder** when it cannot. A cache whose key is undefined neither reads nor writes, and says so once. The previous fallback — the string `unknown` — was a key every version agreed on, so one version's entry was served to another; a single-file executable made that permanent (no `package.json` to read), which is how it was found. A build that can know the answers bakes them (`__TELO_BAKED_VERSIONS__`); everywhere else the disk read stays the normal path.

Every report goes through the caller's logger, never `process.stderr`: a kernel diagnostic a `LoggingHost` cannot see is one nothing can route.

**A validator cache MISS and a validator cache FAILURE are different outcomes.** An absent file, or one whose integrity header does not match, is the designed recovery and stays silent. A file that is present and intact and still cannot be loaded means the cache is unusable in this environment — every entry will fail the same way — and is reported once with the path and the reason. It used to be a per-entry warning, which is how a cache that never hit went unnoticed.

**Load-time CEL runs as emitted JavaScript cached under `<cache-root>/cel/`** (`cel-emitted-modules.ts`). The loader compiles every expression of a file against that file's one environment and records each as a program site; after each module load (the entry and every import) the kernel emits one module per file and environment through the engine's store seam, writes it as `<key>.mjs` (the module body digested with Node's native SHA-256 through the seam's `digest`), imports it, and switches each site onto its emitted program before anything evaluates it. A later load imports the stored module, whose header and body the engine verifies first, re-emitting one that does not match. Only a module on disk is imported: with no cache root, or a read-only cache that does not hold it, the sites keep their closure programs and nothing is emitted, and an unwritable cache is reported once like the other caches. A stored module that cannot be imported fails the load, naming the file. A file two loads adopt at once is switched once, and both wait for it. Expressions compiled after load (a template body's per-dispatch expansion, a controller's own compile) stay on the closure backend. The emitted module is a derived cache and never part of a published artifact.

## External tools a controller needs

`controller-loaders/controller-tool-requirements.ts` is the single table saying which candidate needs which program (`pkg:npm` → the package manager, `pkg:cargo` → cargo), what the message says, and which failure shapes mean "not found": **spawn-level signals only** — POSIX `ENOENT`, a shell's 127, cmd's 9009. It lives in the kernel because that is the only ground the two readers share: the analyzer must stay browser-runnable and can spawn nothing, and the kernel cannot import the CLI.

**The failure's TEXT is deliberately not matched.** That text belongs to the tool, not to the spawn: npm says `404 Not Found` about a package that does not exist and cargo says ``linker `cc` not found`` about a broken toolchain. Matching it told an author to install Node.js for a misspelled dependency, and — worse — converted a real `ERR_CONTROLLER_BUILD_FAILED` into an env-missing fallthrough that DISCARDS the compiler's diagnosis and ends the run with a generic "no controller found".

**No loader probes.** A pre-flight check spends a process launch on every boot to answer a question that only matters on the path about to ask it anyway, so the message is built by recognising the spawn's own failure — which costs nothing where the tool exists. The `rustc --version` probe that used to precede every cargo build is gone; the first cargo spawn reports the same env-missing fallthrough. `telo check` is the half that may probe, and does (`cli/nodejs/src/controller-tool-probe.ts`), warning rather than failing, and only for kinds whose candidates ALL need a tool — a kind offering a bundled controller beside a Rust one needs nothing.

## esbuild

One seam (`controller-loaders/esbuild-runtime.ts`) loads esbuild for both bundle builders, and a host that carries the executable rather than installing it registers a provider (`setEsbuildExecutableProvider`) consulted lazily on first use. **Only the asynchronous API is ever used**: the synchronous entry points start a worker from the running program's own path, which in a single-file executable re-enters the program and never returns.

## What the runtime says it is

**`Kernel.Starting` carries `{ telo }`** — this kernel's own identity, `X` for a release and `X+unreleased` for a build made while `X` is pending — so a runner can pass on which version it actually started and an editor can compare it with the one it asked for. The value is the kernel's own generated constant (`src/telo-runtime-version.ts`, written by `scripts/generate-telo-version.mjs` from the version line, exported as `TELO_RUNTIME_VERSION`), not one borrowed from another package that happens to share the line. Reported, never enforced: nothing in the kernel refuses to start on account of it.

**Polyglot debt:** `kernel/rust` emits no `Kernel.Starting` at all — it has no debug stream — so a run on it reports no version and an editor shows the requested one as not confirmed. It owes the event, and with it this field, written from the same version line.
