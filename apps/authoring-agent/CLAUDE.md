# Authoring agent — package guide

Loaded when working under `apps/authoring-agent/`. Repo-wide rules live in the root `CLAUDE.md` — including the MANDATORY rule that every architectural change updates this agent's system prompt (`chat/primer.md`, which the chat library's `system:` reads with `!include-text`) in the same change. The primer's SHA-256 is the agent's prompt identity (`GET /capabilities` → `prompt.id`), so an edit to it is visible to every client.

## Asking the user

- "how does the agent ask the user a question?" → the analysis phase in the authoring agent's system prompt (`apps/authoring-agent/chat/primer.md`) and its e2e pair (`chat/tests/{authors-manifest,asks-before-building}.yaml`), `apps/studio/src/agent/questions.ts` (the block's single reader), `components/agent/QuestionCard.tsx`. **A question is a fenced `telo-questions` JSON block in the reply TEXT, never a tool call** — a tool result feeds the model loop straight into another step, so a tool cannot end a turn, and ending the turn is what asking is for. The editor renders it as clickable options and sends the picks back as an ordinary message, so the agent is never told whether a client parsed the block; a client that does not, and the user's own opt-out, both degrade to the same questions as text. **A question with NO options is an open one** — a fact only the user has (a sheet's columns, a tracker's field names, a join key), which the agent must never invent: the hub answers what a MODULE's fields are, nothing answers what the USER's are, and a made-up column name is not a syntax error but a manifest that checks clean, runs, and is wrong. The phase is CONDITIONAL on the request leaving something material unsaid — which is why the two e2e cases only assert anything as a pair, since either alone is satisfied by an agent that always asks or never does. **A placeholder is never an implementation** — a fetched-then-ignored source, a join returning a constant, a `value:` step of example rows where a computation belongs. Such a manifest checks clean and renders invented numbers, which is worse than not building: it reads as real and nothing downstream flags it. A computation the agent cannot work out is reported at the top of its reply; a gap in the CENTRAL capability is asked about before building around it, never footnoted after (the rule that permitted this said "build everything that does not depend on it", which is right for a peripheral unknown and licenses a hollow app for the load-bearing one). **A `default:` for a fact only the user has is an invented answer** wearing a nicer word, so such a variable is declared required. **A PROBE beats a question**: where a system is addressable and the agent has its identifier and a credential, it writes a throwaway read-only manifest under `.probes/`, runs it through `run_manifest`, reads what it printed off stdout and deletes it — so a spreadsheet's tabs and headers are discovered rather than transcribed by the user, leaving only the identifier and the credential's env var to ask about. The read-only rule is prompt-level and therefore NOT enforcement (the agent authors the probe); the enforceable control is the credential's own scope. **Having no credential is not a refusal** — the agent obtains one through `oauth-client`'s DEVICE flow (print the verification URL + user code, the user approves, poll), never the redirect flow, whose callback needs a listener the user's browser can reach and the container is not. It spans two runs, since a poll cannot outlast `runTimeoutMs` while a human signs in, and the second run does the READING too — an in-memory grant dies with the process that obtained it, so keeping the grant and the work together is what removes the need to persist one. Gated by `ALLOW_MANIFEST_RUNS`, off by default — the switch grants running ANY manifest, so it reaches the user's live systems with whatever the container holds, which is why it is named for what it does rather than for tests. **Questions come in ROUNDS that narrow** (shape first, then only what the previous answers made relevant, three-round ceiling): asking everything at once is what produced compound questions cramming four asks into one, and a tab's column headers cannot be asked for before the tab is known. **An application has screens unless the user says otherwise** — the primer's "Screens" section, which points the agent at `ui` (the vocabulary), `ui-react` (`UiReact.App`, the renderer mounted beside the API) and `crud` (one table's API and screen), so the agent never asks "UI or not?", only what the screens show; pinned as a pair, `chat/tests/assumes-ui.yaml` (a request silent on a UI writes a `UiReact.App`) against `asks-before-building.yaml` (answers ruling one out write none). **What the workspace CONTAINS is injected into every turn** as a `WORKSPACE STATE:` message rather than left to `list_dir` — the agent asked whether to create a new app or extend an existing one against an empty workspace, and a tool the model must remember to call is one it sometimes will not.

## Discovery

- "how does the agent find a module and a kind, and what does that cost?" → the chat library's `hub` resource input, `libraryIndex` / `readLibraryIndex`, `findKinds`, `discoverer`, `discoveryTools`, `callUsages`, the prompt `chat/discovery.md`, and the primer's "Discover modules" section. **Whatever a tool returns is re-sent on every later step of the turn**, so discovery is shaped by what enters the author's context, not by how many calls are made. Three things reach it: a `LIBRARY INDEX:` message leading every turn (the hub's `list_libraries` for `hubPublisher`, through a `Cache.View` — fresh an hour, served a day past that while the hub is down, and absent with a logged warning when there was never one; it leads the messages because a text identical across turns extends the provider's cached prefix), `get_kinds` (the hub's own tool, and beside the guide tools the only hub tool the author mounts) and `find_kinds`. **`find_kinds` is a second agent that only CHOOSES**: `discoverer` runs on the low-effort model with its own short prompt and the hub's search tools, and replies with a JSON object naming a module ref and kinds per need; `findKinds` reads the first JSON object in that reply and fetches the definitions itself with `get_kinds`. The discoverer never writes a schema — a model copying one can change a field, and would pay output prices for it. A reply that cannot be read, or definitions the hub did not return, come back as text leading with `ERR_DISCOVERY_UNREADABLE` / `ERR_DEFINITIONS_UNAVAILABLE` rather than as a thrown error, because **the tool's result is how its usage reaches the journal**: `callUsages` is the one definition of what a turn spent — the agent's steps, the naming and summary calls, and the `usage` in a `find_kinds` result's output — and a thrown tool records no output. **The hub is a library input, not a URL in the library**: the application declares the `Mcp.HttpClient` (`https://telo.sh/mcp`) and a test supplies a local stand-in, since the client's `url` is not a computed field. **The hub's authoring guides are hub tools**: `author` mounts `hubTools` with `include: [get_kinds, guide_build_ui, guide_write_integration_tests, guide_design_library]`, each guide taking no arguments, so a guide the hub adds is offered once its name joins that list, and a listed name the hub does not serve is left out rather than refused. They are tools, not the hub's MCP prompts, because a prompt is user-controlled — an MCP client offers it to its user, never to its model. No model call happens inside one, so `callUsages` is unchanged; a guide is at most the default `maxToolResultBytes`, so it arrives whole. The primer names no individual guide, only the `guide_` prefix: what each covers lives in its description on the hub. **`Mcp` and `Run` (application), `Mcp`, `AiMcp`, `Ai`, `OpenAI`, `Run`, `Stream` and `HttpClient` (chat library), and the same names in every chat test that imports the chat library, move together** — all pinned to one version, or all from the checkout while a change to one of them is built. The import sync never re-pins a test manifest, so the tests' copies are re-pinned by hand with the rest. `Run`, `Stream` and `HttpClient` are there because the checkout's `ai` and `openai` reach them by relative path: one module name loaded from two origins is two identities for one kind, and two `Ai` modules is a `DUPLICATE_IMPORT_ALIAS` reported at a line that declares its alias once. Tests: `chat/tests/find-kinds.yaml` (offline: `__fixtures__/hub-stub` serves the three hub tools and one stub guide tool, `guide_build_ui`, and the provider stub tells a discovery call by its instructions), `chat/tests/guide-tools.yaml` (offline: the stub guide offered, its text returned whole, no usage added), `chat/tests/authors-manifest.yaml` and `chat/tests/reads-ui-guide.yaml` (live).

## Conversations

- "who owns a conversation, and what counts as a change to it?" → the chat library (`chat/telo.yaml`): `conversations` holds only what nothing else determines (title, archived, timestamps, `revision`, the `removed_at` tombstone, the internal `assembling` mark); `model`, `messageCount` and `totalTokens` are DERIVED at read time from live turns through the `conversation_view` view over `turn_projections`, whose `tokens` / `model` / `context_tokens` / `summary` / `summary_through` are folded from the journal like `messages`, so the projection stays disposable. **`revision` + `updated_at` move in the transaction of every change** — admission, continue, a turn's ending (`endTurn`, in a `finally` so a failed projection still counts), a generated title applied, PATCH, truncation marking, the tombstone — and retention idleness is `updated_at`. **Admission order is the invariant everything else leans on: claim the journal key, THEN write the `turns` row** conditionally on a live, unarchived conversation, bumping `revision` in the same transaction (`admitTurn`'s `recordTurn`). A turn row is therefore never visible before its key, and **a continue likewise takes its turn's key over before its revision-bumping transaction** (`continueTurn`'s `takeOver`, then `touch`, which also refuses a turn marked removed); a refusal after the takeover gives the key back failed with the error it held just before the takeover, the error the takeover itself reports (`releaseAttempt`: a sink adopts the claim and re-raises the error) and refunds the reservation, so a removed key is never started; a takeover reporting no error created the key (removed and its marker forgotten since the continue's state-only snapshot), so it is given back failed `ERR_JOURNAL_KEY_REMOVED` and refused 410; the note's records are read after the takeover; `tombstoneConversation` is a compare-and-set on the `revision` it read beside its running check (DELETE retries on a mismatch, the sweep reports `busy` and moves on), and truncation compares its `revision` inside its marking transaction. **Deletion, truncation and the sweep share one removal**: mark (`turns.removed_at`, projection rows dropped, in the tombstone/marking transaction), then `cascadeTurns` removes each marked turn's key before its rows, so a crash leaves marked turns the next sweep finishes; a branch writes its conversation row FIRST, hidden (`assembling = 1`: excluded by `conversation_view`, so every route answers 404, and refused by every liveness-checked write), copies turns under it only while it is still hidden and live, and clears the mark last — so no turn row ever lacks its conversation row; a refusal mid-copy runs `discardBranch` (tombstone + cascade) and re-raises, and a branch a crash cut short is an idle conversation the sweep removes like any other (`tombstoneConversation`'s `includeHidden`). **Title and compaction are sources of the turn's own stream** (`nameConversation`, `compactHistory`, between the lead record and `agentTurn` in `turnRunner`), so their records are journaled before the agent reads the projection, and their usage is in the turn's settled amount (`turnEnd`) and `tokens`. **A call that returned is always journaled with its usage**: an unusable summary (a reply not ending `stop` → `ERR_SUMMARY_INCOMPLETE`, checked first; empty → `ERR_SUMMARY_EMPTY`) is a `context-summary` with `error` and no `summary`, yielded before `compactHistory` raises `ERR_CONTEXT_COMPACTION_FAILED` from a later `Stream.Concat` source, and only a record carrying `summary` is a summary (projection, provider-state reset, branch remap keep the two apart); a title the conditional update did not apply is `conversation-title { model, usage }`, so a `title` in a record is always one the conversation took. A `try:` step catches a cancellation, so both rethrow `ERR_INVOKE_CANCELLED` themselves. The naming and summary calls run on `bufferedModel` (`Ai.Buffered` over `lowEffortModel`: the agent's `model` and request at `reasoning.effort: low` with no reasoning summary, because `max_output_tokens` bounds reasoning and reply together), capped at 1024 and `maxContextTokens / 8` output tokens (`maxContextTokens` is at least 8, so the summary cap is at least 1); the stub tells them apart by their instructions. A branch's title stays within PATCH's 200 code points (`branchTitle`). Title handling counts code points: `titleOf` strips and cuts with regexes and the naming prompt is the first message's first 4000 code points, never `substring` (UTF-16 units). Tests: `chat/tests/{conversations,conversation-title,context-compaction,context-floor,conversation-removal,conversation-truncation,conversation-branch,conversation-migration,turn-spend,tool-result-bound}.yaml`.

## Checkpoints

- "what did a turn change, and how is it undone?" → the chat library's `acquireWorkspace` (the workspace lease and, inline, the one body it runs: the write, edit and removal arms `write_file` / `edit_file` / `delete_file` reach, a pushed change set, one batch of a revert's paths), `pathStates`, `currentDigests`, `settleEntries`, `netChanges`, `turnChanges`, `revertTurn`, and `projectTurn`'s summary half. **The writing tool records its own change, in SQL, BEFORE the effect** — never a watcher diffing the workspace, which is shared with the user's editor and other conversations, so a diff would charge their edits to the turn and a revert would discard them. Per call: the touched files (the path; every regular file under a recursive delete, enumerated by a paged, metadata-only listing that stops at the first bound crossed), the bounds (`maxCheckpointBytes` / `maxCheckpointFiles`, `ERR_CHECKPOINT_TOO_LARGE` before anything changes; each capture read bounded by what is left), the "before" copy stored, one `checkpoint_entries` row per path inserted only for a live turn (before digest, intended after digest; null is absent), the write, then `confirmed = 1`. **An entry is settled, never assumed** (`settleEntries`): an entry of a live turn whose write is not known to have happened is confirmed when the file it names holds its "after" and removed otherwise (entries of a turn marked removed are the cascade's) — by the failing call itself; a cancelled call leaves its entries to its turn's ending, since it cannot dispatch after cancellation (the failing call settles in the same hold, then re-raises; a recursive delete failing part-way keeps the entries of the files already gone), at the turn's ending before the summary is projected (`endTurn`; no lease, since nothing of that turn writes any more — which is why it is NOT done inside `projectTurn`, where a continue could have reopened the key between the state read and the settlement), and at boot for every unconfirmed entry of a live turn, before the catch-up projection and before any route is served (`catchUpProjections`). Summary, changes and revert read confirmed entries only. **What is at a path is learned from metadata, never by reading it** (`pathStates`): kind and size are the path's entry in its parent's listing — a link is never followed; where the parent cannot be listed, its ancestors are listed from the workspace root downward: a segment the listing above does not hold, or holds as a regular file, makes every path beneath `absent`, while a parent that is there raises that first listing's error as itself (as does any listing failing on the way down), so no content is ever probed, a path that could not be listed is never given a state, and settlement leaves such an entry unconfirmed for the next settlement that can list it (the tool call errors, the turn's ending fails as a failed projection does, boot stops naming the directory) — so a directory at a write or edit path is refused without being walked, the byte bound is judged on the listed size, a recursive delete of a symbolic link or of a tree holding a non-file entry is refused whole (`ERR_PATH_NOT_A_FILE`), and a revert and `changedSince` read a workspace file only when its size is that of one of the turn's copies of the path (`sizedDigest`, which `currentDigests` runs per path over one `pathStates` pass); the bounded capture read is the only other content read. **Blobs are files, `<stateDir>/checkpoints/<turnId>/<sha256>`, one directory per turn, never shared and never collected** — the shared removal (`cascadeTurns`: key, then directory, then rows) is what deletes them, for a deletion, a truncation, the sweep and a discarded branch alike, and a branch copies entries, blobs and recorded revert under the copy's id (`copyTurn`); the copies of a failed write stay with the turn, and a call whose entry insert is refused because the turn is gone removes that turn's directory before it raises (`recordEntries`), so blobs exist only under directories of live turns. `turns.checkpointed` is 1 for a turn admitted since the migration and 0 before it: an older turn's `summary.files` is null and its revert is 409. **The tools learn their turn from the agent's caller, not from the model**: `workspaceTools` declares `contextType { turnId }`, `agentTurn` invokes `author` with `context: { turnId }`, and the three tools map `turnId: context.turnId` — the model-visible parameters are unchanged. **One workspace lease** (the `Lease.Critical` inside `acquireWorkspace`, over the store `turnLock` uses, keyed per workspace, whose single inline body runs whichever of write / edit / remove / sync / revert the caller names) is held by the three tools (capture and write are one hold), by `POST /workspace` (the whole change set) and by a revert (one hold per batch of up to 25 paths, in path order: the batch's kinds and sizes from ONE listing per distinct parent, then each path compared, replaced and recorded in turn, its bounded read only when the listed size is that of one of the turn's copies and immediately before its own replacement; a path that fails stops its batch and is returned as data BESIDE whether an outcome was written before it, so `revertTurn` stamps what was recorded and then raises). The body returns a failure as data instead of raising, because the caller's step `retry:` — the one layer that retries a busy lease, in `leasedWorkspace` — retries every domain failure and must re-attempt only `ERR_WORKSPACE_BUSY`, never the work; `leasedWorkspace` re-raises the failure afterwards. **Every acquisition waits**: `attempts: 200`, `initialDelay: 5`, `maxDelay: 50`, `jitter: full` — about 5 s in expectation, never more than about 10 — then `ERR_WORKSPACE_BUSY` / 503; and a revert pauses 100 ms (`Timer.Delay`) between holds, so a waiter — whose waits never exceed 50 ms — gets in behind a long revert. The budget bounds how long a caller waits; it is not a promise of entry — a refused caller resends. The numbers are literals: a step's `retry:` is read as written, never evaluated, so a variable cannot lower the budget, and the lease tests hold the lease on purpose instead: a push whose `write` list names a named pipe stops inside its hold until the test reads the pipe (`Fs.TreeSync` writes its entries in list order and never looks at what is at a path), so no test depends on how long a hold takes. `acquireWorkspace` itself stays a named sequence: a code thrown by an inline sequence is not counted in the enclosing sequence's throws, and the routes' `catches:` name `ERR_WORKSPACE_BUSY`. It guarantees a revert never overwrites a change written through the agent; a process writing the disk directly can land within one hold — between a batch's listing, or a path's comparison, and that path's replacement — and is overwritten. **The summary is a projection, not a record** (a finished key is never re-opened): `projectTurn` writes `turn_changes` (net changes diffed with `TextDiff.lineDiff` over the blobs, each with its last check's exit code) — the diff of one turn reads at most `maxTurnDiffBytes` of copies (a library variable with no env binding, 4194304; `netChanges`, shared with the changes route): in path order a file is read when the listed sizes of its two copies fit what is left, and one that does not fit is listed with null counts, hunks and first line; the changes route has a second allowance of the same size per request for the WORKSPACE files it reads to answer `changedSince` (`turnChanges`: listed sizes, path order, only files whose size is that of the "after" copy count), and a file past it answers `changedSince: null` — not compared, never `true` or `false` — and the usage / runs columns of `turn_projections` at every ending — its end handler passes `ending: true`, since the key is still open while it runs — and `catchUpProjections` re-projects at boot every turn whose projection is not `ended`, which is how a turn a crash cut off gets its summary; the records route reads the projection and answers `summary: null` while the key is open. The reverted fact is likewise SQL state (`turns.reverted_at`, `turn_reverts`): a path's outcome is written the first time it is evaluated and afterwards only moves to `restored` (the file replaced now, or found already holding the "before"), and `reverted_at` / `revision` move exactly when an outcome was written or changed — stamped in a `finally`, so a revert that then stops at 503 or at a path it cannot write has recorded what it restored — or when the turn's first revert runs to its end (`files: []` for a turn with nothing to restore); a revert refused or failed before any outcome was written leaves `revert: null` and `revision` unmoved, so `revert` non-null means at least one path was evaluated or a revert with nothing to restore completed. A turn from before checkpoints — also one continued since, which is bounded, leased and recorded like any other and stays `checkpointed = 0` — answers `files: null` on its summary and on the changes route (`revert: null` there too) and 409 on revert. **A spent step budget concludes** (`author`: `onMaxSteps: conclude`, `maxSteps` a library variable so a test can lower it): an ordinary completed turn whose `finish` carries `limit: max-steps`; Studio's Continue is a new turn saying `Continue.`, and `POST /chat/{turnId}/continue` stays for interrupted keys. Tests: `chat/tests/{turn-checkpoints,turn-revert,turn-summary,workspace-lease,checkpoint-removal,conversation-migration}.yaml`.

## The boundary

- "who may call the agent, and what may a tool touch?" → the `api` mount's `guard` in `telo.yaml` (origin allowlist, then an HMAC-compared bearer token when `AGENT_TOKEN` is set; `probes` — `/health`, `/ready` — is a separate unguarded router), `Chat.outsideWorkspace` (the one lexical path rule every path-taking tool sequence and both `/workspace` routes apply first; it also refuses a path inside the agent's state directory), `Chat.unremovable` (a removal — `delete_file`, recursive or not, and each `delete` entry of `POST /workspace` — naming the workspace root, or a directory the state directory lies beneath, is refused whole with `ERR_PATH_OUTSIDE_WORKSPACE` before anything is listed, captured or removed; the root in every configuration, also with the state directory outside the workspace), and the write/edit sequences' `credentialFindings` scan (`ERR_SECRET_IN_MANIFEST`, before anything is written, no override). **A tool error reaches the model as its message alone** — the `ai` tool-result record carries no code — so a refusal the primer tells the agent to recognise leads its message with its code. **Tool results are text** (`result:` renderings; the check part is `Chat.renderCheck`, a command's output `Chat.renderRun`), while the structured value rides the record's `output` for Studio. **A file is found by search and read in ranges** (`searchWorkspace` → `search_files`, `readWorkspaceLines` → `read_file`'s `offset` / `limit`): a whole read past `maxToolResultBytes` is cut and then re-sent on every later step, which is what spent millions of tokens on one pasted error. `search_files` is confined like every path tool, skips `list_dir`'s exclude set, names a file past `maxSearchFileBytes` instead of reading it and stops at `maxSearchMatches` lines, saying so; `GET /workspace/file` keeps reading through `readWorkspaceFile`, whole. Tests: `chat/tests/{boundary-auth,workspace-tools,turn-tracing}.yaml`, offline against the provider stub, whose `STUB_CALLS:<base64 JSON>` directive scripts tool calls.

## Attachments

- "how does a file reach the model, and when is it removed?" → the chat library's `storeAttachment` / `storeParts` (the upload), `readAttachment`, `chatStart`'s `attached` step, `turnMessages`, `modelContent` and `agentTurn`'s `uploads` step, `cascadeConversation` and `branchConversation`'s `copyUploads`. **Bytes are blobs, facts are a row**: a `BlobFs.Store` rooted at `<stateDir>/attachments`, keyed `<conversationId>/<id>`, and an `attachments` row (name, media type, size, digest) per upload. **An upload belongs to its conversation and is removed with it, never before** — not with a turn — because a turn only NAMES it: Retry and Edit & resend truncate and then send the same ids again, so removing uploads with their turn would make both lose their files. That is also why there is no route deleting one upload, and why a conversation is capped (`maxConversationAttachments`, counted before the upload is read). `cascadeConversation` removes uploads only for a conversation that is no longer live (the same sequence serves a truncation), blob before row, so a crash leaves rows the next cascade finishes. **A branch copies every upload under the same ids**, into its own keys, so neither conversation's removal touches the other's messages and no reference counting exists. **The journal and the projection never hold bytes**: the `user-message` record carries descriptors, `turnMessages` projects them as `{ type: attachment, id, … }` parts — a shape of this library's own, not an `Ai.ContentPart` — and `agentTurn` resolves them per attempt, reading each named blob once. So `contentText`, search, the title and the summary read a message's text and pass over the references. **What a file is comes from its bytes** (`MediaType.Detector`): `mislabelled` refuses first, then the accept list (`attachmentTypes`, the one definition the capability document also serves). **Text is inlined, bounded by `maxToolResultBytes` characters**; an unbounded text file would exceed the model's window on every later turn, since history replays it. An image or PDF is not bounded that way — a turn that fails on one is removed with Delete from here. **Every code a route names is thrown by a NAMED resource**: `storeParts` is a named `Run.Iteration` because a code thrown inside an inline one is not counted in the enclosing sequence's throws. The upload route's `maxBodyBytes` is the file bound plus 64 KiB of multipart framing; `Blob.Put.maxBytes` is what bounds the file itself. Test: `chat/tests/attachments.yaml`.
