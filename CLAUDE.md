# Claude

Use `pnpm run telo ./manifest.yaml` for testing.
**Never run a whole test suite** — `pnpm run test` with no filter, `pnpm -r test`, `cargo test --workspace`, `pnpm run test:integration`. Run only the tests the change reaches: `pnpm run test --include 'modules/<name>/tests/*.yaml'` (repeatable, or a positional filter) for the touched modules' manifest tests, and each changed package's own unit tests. CI runs everything else.
Tests should live in the module they test: `modules/<name>/tests/*.yaml`.
Test fixtures go in `__fixtures__/` subdirectories (excluded from test discovery).
Prefer `Assert.Equals` (deep-equals `actual` against an `expected` literal) for asserting outputs in manifest tests — not `Assert.Schema`. It reads as a plain expected value, compares the whole result at once, and serializes BigInt safely.
Implementation plans always live in the root `plans/` directory, eg. `plans/2026-10-17-some-plan.md` — never in a package's own `plans/`.
A plan's filename is prefixed with the ISO date it was written (`YYYY-MM-DD-<name>.md`), so the newest plans sort last.
Plans MUST NOT have any open decisions, all open decisions must be resolved before plan is written.
Every plan opens with YAML frontmatter: `status` (`draft` | `approved` | `in-progress` | `blocked` | `done`), `priority` (`high` | `medium` | `low`), `depends-on` (filenames of plans that must ship first; `[]` when none — a name with no file has shipped), `packages` (areas touched; `[]` when none), `refinement` (the `plan-refine` skill's state: `not-started` | `in-progress` | `ready` | `not-ready`; a new plan starts `not-started`) and, once `in-progress`, `tracking` (the branch or PR). `tracking` is the only optional key. `blocked` means waiting on something that is not a plan (an upstream release, an answer); a plan waiting on a plan it depends on is blocked by that edge alone. When a plan's work is implemented, set its `status` to `done` in the same change — the agent does this, not the user. `done` means shipped and awaiting deletion — the user deletes done plans, never the agent.
Every plan has a **Surface** section right after Problem: each observable name the plan adds, changes or removes, under **Added**, **Changed** and **Removed** — one line each, the name exactly as a user sees it (kind, key, annotation, tag, diagnostic code, CLI flag, env var, file path, wire field, ABI member) and a phrase on what it is or what changes. Existing surface the plan only reuses is not listed. A plan that changes only internals writes `None — internal only.`
**Never cite a plan path from this file.** A plan is deleted the moment its work ships, so a path here becomes a dangling reference nothing catches — and a plan is a record of how a decision was reached, which is exactly what this file must not depend on. State the decision itself instead.

Follow this strictly:

- **Do not create, edit, or delete any file until the user's latest message clearly authorizes the specific change you are about to make.** Authorization is a direct instruction to act now — to write, change, or remove something concrete. It is NOT: a question ("would X work?", "is this better?"), a critique or correction of a proposal, a request to compare or weigh options, or general discussion — none of these grant permission, no matter how positive. Agreeing that an idea is good is not the same as asking for it to be done. When the intent for you to act *now* is anything less than unambiguous, stay in proposal mode and ask: "Apply this?" This gate overrides Auto Mode and any "execute immediately" directive.
- Do not run `git commit`, `git commit --amend`, `git push`, or any other command that creates, rewrites, or publishes a commit unless the user's latest message explicitly asks for it (directly, or by asking to run a skill that commits, such as `pr`) — never on your own initiative, not even to make a check pass or "fix" state. The `rust-parity` and `backlog` skills are standing exceptions, each in its own worktree (`.claude/worktrees/<skill>`) on its own `<skill>/*` branches: they commit, push (`--force-with-lease` after a rebase) and open pull requests, exactly as each skill lists. No session ever merges a pull request.
- a commit message's conventional scope lists at most 3 components; a change touching more than 3 gets no scope at all (`fix: …`, not `fix(a,b,c,d): …`)
- never run more than one builder agent (`builder`, `builder-high`, `builder-lite`) at once — a second is spawned only after the first has finished or been stopped
- prefer not to schedule wakeups (`ScheduleWakeup`, self-paced loops) unless the user asks or a skill requires it — an agent's completion notice already wakes you
- never wait with a foreground `sleep` (the harness blocks it): a `run_in_background` command wakes you when it exits, and a condition is waited on with `Monitor` and an until-loop
- never `pkill -f` a pattern your own command line contains — it matches the shell running it and kills it (exit 144); stop a background task with `TaskStop`, or kill the PID an earlier `pgrep` printed
- when the session has no `Grep` / `Glob` tool (the main session usually has none), search with `grep` / `find` through Bash instead of calling them
- never add underscores to unused function arguments
- never look at commit history
- never use git stash
- work in the current tree: create a separate git worktree only when the user asks for one or a skill requires it — "create a branch" or "do it here" means a branch in this tree
- never fix linting problems, and never mention it
- keep code comments very concise and add them only when necessary; prefer self-documenting code and module documentation
- if you cannot implement a feature in a way it was established or planned to be implemented, send the approaches to `decider` and follow its answer; stop for approval only when that answer overrules something the user explicitly asked for
- never implement logic that swallows errors
- telo manifests MUST be type safe
- in telo manifests, CEL is ALWAYS written behind a tag: a computed value of any type with `!cel "..."`, text with values embedded in it with `!interpolate "http://localhost:${{ ports.http }}"`. A plain string holding `${{` is never a value — it is the deprecated untagged spelling, which `telo migrate` rewrites and which is refused wherever it survives.
- in telo manifests, declare a resource INLINE at its use site when it is used exactly once — `invoke: { kind: Some.Kind, ...config }`, with no `metadata.name`. Give a resource its own top-level document only when something needs to name it: it is referenced more than once, listed in `targets:`, or exported. A named single-use resource makes the reader jump documents to follow one call. The exception is a router (`Http.Api`) mounted on a server — keep it named, because that is what makes it independently testable.
- in telo manifests, write short leaves in YAML flow style instead of block style — lists of scalars (`enum: [as, break, const]`), small maps (`not: { enum: [...] }`), and single-key chains. Use block style only where a value holds a `!cel` / `!interpolate` / `!include-*` tag worth reading alone. Quote scalars that YAML would otherwise read as another type (`"true"`, `"null"`, `"false"`). Whenever you edit a manifest for any reason, run `telo format` on it without asking; reading one is not a trigger.
- never use `cat` nor `sed` to read files — read them directly
- to learn which modules, kinds or ready-made instances exist — or what can do a job — ask the Telo hub first (the `telo_hub` MCP server: `search_resources`, `find_implementations`, `find_instances`, `get_module_manifest`), not the `modules/` directory. `modules/` holds only the standard library kept in this repo, so a module missing there is not evidence that it does not exist. Read `modules/<name>/` when the task is that module's own source, or when the checkout is ahead of what is published — the hub knows only released versions.
- never do major upgrades of modules nor packages
- never modify files in `dist` directories
- never use Bun-only APIs (e.g. `Bun.Glob`, `Bun.file`); all code must run on Node.js
- never make architectural decisions alone (package boundaries, dependency direction, where code lives): send the options to `decider` before presenting them, and bring the user its answer, not a menu. Do what it decides — inside a skill without stopping, outside one under the file-edit gate above; stop for the user only when it overrules something they explicitly asked for
- UI primitives must use Radix (`radix-ui` package, same pattern as `apps/studio/src/components/ui/*`); if a needed component isn't wrapped yet, install it via shadcn before rolling your own
- Icons must come from `lucide-react` (already a dep). No inline `<svg>` paths.
- When working on a plan, when a decision is made then remove the decision section entirely, not just mark it as decided. The plan should reflect the current state of the world, not a history of how we got here.
- `JS.Script` is **deprecated** — declaring it reports `DEPRECATED_KIND`. Do not write a new one, and do not propose one. A body of JavaScript is opaque to every guarantee the runtime rests on: it cannot be type-checked, and it cannot be rendered in a visual editor. There is no single successor and the kind declares no `replacedBy`, because what replaces a script depends on what it does — value shaping / branching / iteration is the `run` module's step grammar with CEL, and reaching an API nothing else exposes is what a new resource kind is for. Existing uses keep working and are migrated as they are touched, not in bulk.
- every example that serves an HTTP server with a UI, or an API with docs, opens its page with a `Telo.OpenUrl` boot target after the server starts — the UI's address, or the API docs' address — and its `requires: telo` is at least the release that introduced the kind (`>=0.133.0`)
- every example that serves an HTTP API showcases it with a UI, API reference docs, or both: a UI where the example is about what a person does in a page, an `Http.Reference` mount at `/docs` on a server that declares `openapi:` (a mount on a server guarding its mounts declares `authentication: { anonymous: allow }`)
- **every example under `examples/` is self-contained**: `telo run ./examples/<name>` works with nothing set up beforehand — no fictional or placeholder service address (`id.example.com`), no required input without a `default:`, no second process or container to start by hand. The only thing it may ask of the user is a credential for the real remote system it showcases (an AI provider's key, an OAuth client id of the API it calls). A service the example needs for its own flow (an identity provider, a token issuer, an object store) ships beside it as a stand-in the example starts itself (`App.Instance`), and an external one is an override the user may supply, never the default.
- never add Docusaurus or any other rendering-tool annotations (`sidebar_label`, `sidebar_position`, `description`, etc.) to `README.md` files. Docusaurus-specific labels and ordering belong in `pages/sidebars.ts`; other markdown files under `docs/` may keep frontmatter where it's actually consumed.
- keep your communication very concise and to the point; avoid unnecessary preambles, or apologies. Focus on the task at hand and the specific changes being made. If you need to explain a complex decision, do so.
- Avoid putting code into generic `utils.ts`, `types.ts`, `helpers.ts` files. Drive the filename from the specific domain or feature it serves.

## Communicating — plans, reviews, and every answer

Everything written for the user — a plan, a review, a chat reply, a changelog fragment, a commit body — is read by someone deciding whether the work is RIGHT, not by someone looking up where to type. Every rule below follows from that one sentence.

- **No code, unless the code IS the answer.** Not a snippet, not a signature, not a diff, to illustrate a change. A change that cannot be stated as behaviour is not understood well enough to describe. (Answering "what does this function do" or showing a one-line API a user must type is the exception; illustrating a design is never one.)
- **No source paths, no function names, no line links** in a plan or a design discussion. Where code lives and what a function is called are not decisions — they are lookups, they cost a line each, and they are wrong the moment a file moves. `resolveCacheRoot in manifest-sources/local-manifest-cache-source.ts` says nothing that `the cache root` does not. A bug report is the exception: there, the location is the finding.
- **But name every OBSERVABLE artifact exactly.** On-disk paths and filenames (`.telo/manifests/.validated.json` → `.telo/analysis/<hash>.json`), env vars, CLI flags, manifest keys, diagnostic codes, wire fields. These ARE the behaviour: they are what a user sees, what an upgrade breaks, and what a reviewer checks the implementation against. Cutting them is what makes a description unreviewable — cutting source paths is what makes it readable, and the two are opposite moves that look similar.
- **Before / After / Verify.** What happens today, what should happen instead, and how you would know it worked. A claim with no verify is a wish, and the verify is what catches work that only *sounds* complete — "the manifest is read from the old location" passes a review and still fetches every controller, because nobody wrote down what to check.
- **State a constraint once.** One sentence for why the losing option loses, only where a reader would otherwise re-propose it. Never restate the same rationale in the summary, the body and the conclusion. A "not in scope" section is usually a list of things that are not tasks — cut it unless its absence reads as an oversight.
- **Lead with the finding.** The answer, the verdict, the number — then the reasoning, once. Never narrate what you are about to do, never re-explain a decision the user has already made, and never open with a summary of the question. A yes-or-no question gets yes or no as its first word.
- **Check before you answer, then separate what you verified from what you believe.** Anything a tool call can settle — a file, a log, a CI run, whether an agent is still running — is looked up before you reply; never answer that you did not check something you could have. Say which claims you verified. "236/236, and the earlier failures were a stale `fastify`" is a report; "should be fine now" is not. Only what cannot be checked from here is stated as belief, in the same breath as the claim rather than in a caveat at the end.
- **Report a failure as a failure**, with the output and the reason, in the same message that reports the rest. A result that is partly bad and described as good costs more than the bad result did.
- **Answer a review point by point, and concede plainly.** Say which points are valid, fix those, and give the measurement for any you decline. "You're right" is a whole sentence; do not pad it, and do not defend a decision the evidence has just overturned.
- **Weigh a suggestion; do not adopt it because the user made it.** A proposal from the user is one option: set it beside the alternatives and recommend the one that holds up.
- Always prefer answering over editing.

## Architecture

Telo is a declarative runtime: YAML manifests describe desired state, the kernel resolves resource dependencies via a multi-pass init loop, and controllers implement each resource kind. CEL expressions (`!cel`, `!interpolate` holes) are compiled before execution.

**Scope: everything is on the table.** Telo is intended to support every transport, every protocol, every backend domain — HTTP, MCP, gRPC, WebSocket, message queues, databases, file I/O, AI providers, workflow engines, and whatever else lands. Design abstractions for breadth, not for the current consumer. When choosing between a generic primitive and a use-case-specific shortcut, **default to the generic primitive**. "We'll only need it for X" is the wrong question — assume any transport-neutral concept (encoders, codecs, streams, schedulers, retry policies, etc.) will eventually be reused across multiple modules, and shape the API and package layout accordingly. Do not YAGNI on cross-cutting primitives.

**Cross-cutting concerns Telo intends to cover** (non-exhaustive): data shape (codecs, serialization, validation, compression), streaming & I/O, reliability (retry, circuit breakers, timeouts, idempotency), performance (caching, pooling, batching, rate limiting), coordination & data integrity (locks, leases, queues, sagas; execution zones — `kernel/specs/execution-zones.md`, guide `docs/extend/execution-zones.md`), observability (structured logging — `kernel/specs/logging.md`, guide `docs/guides/logging.md`; tracing — `kernel/specs/tracing.md`, guide `docs/guides/tracing.md`; metrics, health checks), security (authn/authz, secrets, signing), time & scheduling, configuration, lifecycle (migrations, rollouts), i18n, inputs & boundaries (pagination, uploads, webhooks), and errors (structured contracts, retryable vs terminal). When designing a new module or capability, ask which of these the resource genuinely needs to declare or compose with; if the answer touches more than one consumer, the concern belongs in a shared primitive (kernel built-in capability or transport-neutral package), not buried inside the current module.

**Topology-driven constraint:** The analyzer and telo studio must never hardcode knowledge about specific resource kinds. All resource-specific behaviour must be expressed via `x-telo-*` schema annotations in `Telo.Definition` schemas and resolved generically.

**Browser compatibility:** The `analyzer` package must be runnable in the browser without Node.js polyfills. Do not import Node.js built-ins (`fs`, `path`, `url`, `child_process`, etc.) from analyzer code. Node.js-specific adapters belong in the consuming package (kernel, IDE extension, CLI).

## Core goals

- **Polyglot architecture** — Telo must support controllers and runtimes in any language, not just Node.js
- **Visual editing** — Telo manifests must remain visually editable in a GUI editor; solutions must not break declarative structure or introduce constructs that can't be represented visually
- **Performance** — the init loop, CEL evaluation, and resource resolution must stay fast; solutions must not introduce unnecessary overhead
- **Static analysis** — YAML manifests must remain statically analyzable; solutions must preserve the ability to validate references, type-check CEL expressions, and detect errors without running the kernel
- **Developer friendly** — Errors must not be swallowed; they should be surfaced clearly to developers. Error messages must be actionable and informative, guiding developers to concrete place in YAML manifest that needs fixing.

## Monorepo Structure

- `kernel/nodejs/src/` — core runtime: orchestration, multi-pass init loop, controllers, event bus. Manifest loading is the analyzer's; the kernel consumes it.
- `cli/nodejs/` — CLI wrapper (`bin/telo.mjs`). **Every CLI-owned write goes through the `Output` seam** (`src/output.ts`), never `console.*` and never a bare `process.stdout.write`: stdout is the machine surface, stderr the human one in both formats.
- `sdk/nodejs/src/` — public API for module authors (re-exports kernel contexts + capability interfaces); owns step-grammar execution, the durable replay seam, `ctx.runtime`, the controller protocol's frame codec (`encodeFrame` / `decodeFrame` / `FrameReader`) and the issue vocabulary `sdk/issue-keywords/` (Node-only). It never imports the kernel and has two runtime dependencies — `@telorun/cel`, the CEL value domain, and `@telorun/message-format`, the message core it re-exports so controllers format through one copy. A value says what it is under a string type key, never by its class, so a controller BUILDS with `celUint` / `celDurationFromNanos` and ASKS with `isCelUint` / `isCelDuration`; `isCelRecord` is the companion a structural walk needs, since a branded value is a plain object and a walk testing the prototype would rebuild one without its brand. A map has two representations — a `CelMap`, keyed by each key's own typed value so one container holds CEL's four key types, and the plain object a host hands one over as — and **`hostValueOf` is the one seam a value crosses on its way out to a host reader**, applied at every such boundary (a compiled value's result, a module function's arguments, a host-backed catalog function's arguments) rather than converted again at each; a map with a non-string key is left as it is, because a plain object cannot hold one. `celMapFromEntries` is the only way a controller builds such a map and `isCelMap` the only way a reader recognises one.
- `modules/` — standard library: `http-server`, `http-client`, `sql`, `javascript`, `config`, `run`, `assert`, `test`, `console`, etc. Not the full set of modules that exist — discovery goes through the hub.
- `analyzer/nodejs/` — static manifest validator (schema checks, reference validation, CEL type-checking); also owns manifest loading and manifest migrations.
- `release/nodejs/` — `@telorun/release` (MIT, off the telo line, bin `telo-release`): the release planner — units and anchors, fragments, the ledger, the edge graph, groups, version planning, candidates, changelogs — the `npm` / `cargo` / `docker` / `helm` ecosystems and the command tree `@telorun/cli` mounts as `telo release` (which adds the `telo` ecosystem, `floor`, `stage`, `imports` and the `requires:` checks). Its main entry is browser-safe; it imports nothing of the analyzer, kernel, CLI, templating or CEL, so a plain Node project can install it alone. Twin `release/rust`.
- `templating/nodejs/` — the TAG engines (`!cel`, `!interpolate`, `!sql`, `!include-*`, `!module-path`) over `@telorun/cel`: the two environments, the hole grammar, the nine host handlers and the call list the analyzer judges. It declares no CEL function and classifies no verdict — the engine owns the catalog and decides every code itself.
- `cel/nodejs/` — `@telorun/cel`, on the telo version line: the CEL language as a library — lexer, parser, the canonical ranged tree with its `qcall` node, error recovery, the serializer's round-trip, the input limits, the tree queries, the replaceable standard library as data, deep JSON Schema type checking with every verdict ranged, and **evaluation**: the value domain (identity is a string type key under `Symbol.for("telo.cel.value")`; a map's entries are keyed by each key's own typed value, so CEL's four key types separate themselves), the one member-read seam, the semantics written once — reached through implementations that take their call context first and their arguments positionally, up to `CALL_SITE_DIRECT_ARITY`, with a wider signature refused where it is registered — and **two backends** over them: an eval-free closure backend, and a **JS-source emitter** whose module takes the runtime as its factory's argument (it imports nothing), is keyed by a format generation + the engine version + an order-independent environment digest + the expression list, carries an integrity header of five fields — those three plus the module's own key and a digest of its body — verified before it runs, and is stored through one host-supplied seam — the engine touches no filesystem and exports no loader. The two backends answer identically, case for case, because everything beneath the tree walk is one shared function both call. It also carries **Telo's function catalog** as signature data plus implementations — the dialect, 67 functions registered through the public `registerFunction` with no privileged path, the nine host-backed ones supplied through one handler seam, each refusal worded by the catalog and a refusal over a literal argument decided by the checker (`CEL_INVALID_ARGUMENT`). It depends on **nothing** in this repo, reaches no Node built-in, and holds **no host vocabulary at all** (no kind, no annotation, no value brand, no manifest word): a catalog signature names only CEL's own types, and a host registers its types onto the engine. It is what the whole repo runs on: the SDK's value domain, templating's two environments and tag engines, the analyzer's verdicts and the kernel's evaluation all resolve here, and `@marcbachmann/cel-js` is gone.
- `message-format/nodejs/` — `@telorun/message-format`, on the telo version line, MIT with no dependency: Telo's closed profile of Unicode MessageFormat 2 — the pattern parser (`{$name}` placeholders, `\{ \} \\` escapes), the message model (plain JSON, so a parsed Message crosses a wire), nested plural selections (`=N` before categories, `other` required), the canonical identity (the all-`other` pattern plus context), RFC 4647 lookup, and CLDR plural selection and decimal formatting from a number's value alone (int64 / uint64 exact). Its CLDR 48.2 data is generated from exact-pinned `cldr-core` / `cldr-numbers-full` into the tracked `message-format/cldr/*.json`, carrying the Unicode License V3 notice; it calls no `Intl`, so Node, Rust and every browser answer alike. `message-format/rust` (`telorun-message-format`) is its twin, and both run one vector set (`message-format/conformance/`).

## Resource Kinds

Every module file must start with exactly one `Telo.Application` OR `Telo.Library` doc. Applications are runnable entry points, Libraries are importable units of kinds/definitions. Full semantics, with the rationale behind each rule: `analyzer/nodejs/CLAUDE.md`.

`Telo` and `Self` are reserved kind prefixes: no module may be named either and no import aliased either, and a library named either cannot be imported (`KIND_PREFIX_RESERVED` / `ERR_KIND_PREFIX_RESERVED`).

**The built-in vocabulary of a release is the `Telo.Builtins` archive** (normative: `kernel/specs/builtin-vocabulary.md`): a YAML stream rendered at build from `sdk/builtins/` (plus `sdk/value-types/`, `sdk/zone-attributes/`, `sdk/formats/`, `sdk/error-codes/`, `sdk/translations/`), shipped in `@telorun/analyzer` as `src/builtin-vocabulary/builtins.yaml` and exported as `BUILTIN_VOCABULARY_ARCHIVE`, embedded by `cli/rust`, printed by `telo builtins [<name>...]` in both CLIs and published per release as `oci://ghcr.io/telorun/telo@<version>`. It is read, never declared, run or imported: as an entry it is one `UNDEFINED_KIND`, as an import target `INVALID_IMPORT_TARGET`, each saying what it is.

**`Telo.OpenUrl`** is the built-in `Telo.Invocable` that hands a URL to the host to open in a browser (input `url`, a `Telo.Url` of scheme `http` or `https`; output `null`). Every call logs `telo.url.open_requested` with `url.full` and forwards the URL, fire-and-forget, to the optional open-url hook the host gave the kernel (`KernelOptions.openUrl`); with no hook only the log record remains. No outcome of opening a page is an error, and the Rust kernel refuses the kind (`ERR_UNSUPPORTED_MANIFEST_FEATURE`).

### `kind: Telo.Application`

A runnable entry point, loaded via `Kernel.loadFromConfig`. **Never** imported.

- `metadata.name` — PascalCase (`OAuthClient`, `HttpServer`, `SQL`); becomes the canonical kind prefix. A name, not a locator; it must contain no dot. Directory and npm package names stay kebab-case.
- `lifecycle` — `"shared"` (default) | `"isolated"`
- `include` — partial files/globs loaded into the same module scope; partials must not contain `Telo.Application`, `Telo.Library`, `Telo.Import` or `Telo.Definition`.
- `imports` — alias-keyed map; each value is a source string (`Console: oci://ghcr.io/telorun/console@0.9.0`) or `{ source, variables?, secrets?, needs?, runtime? }`. An alias shares ONE namespace with every resource, definition and the module's own `metadata.name` (`DUPLICATE_RESOURCE_NAME`).
- `targets` — optional boot sequence run after init: a `!ref` to a `Telo.Runnable` / `Telo.Service`, `{ ref, when? }`, or an inline invoke step `{ name?, invoke: !ref …, inputs?, when? }` (results as `steps.<name>.result`). Control flow and `with:` scopes stay in `Telo.Sequence`. No targets is valid, but the kernel runs only what `targets:` names — no Service starts on init.
- `variables` / `secrets` — each entry binds `env:` and/or (variables only) `arg:`, plus `type:`, optional `default:` (`default: null` declares the input may be absent; never on a `ports:` entry) and further JSON Schema keywords; resolved at `kernel.load()` into `variables.X` / `secrets.X`.
- **The command line is the root Application's**: `telo run [options] <path> [arguments]`, every token after the path read against the `arg:` bindings of its `variables:` / `ports:` entries (a flag, `{ flag, short }` or `{ position }`), the first source with a value winning — supplied by name, then argv, then env, then `default:`, then — only for an entry those leave empty, and only when every load failure is a missing value — an answer the host gives when asked (`telo run` at a terminal asks, decoding it like env text and never writing it to the environment; `--no-input` and every runner refuse instead, naming the missing inputs). Undeclared tokens are refused before boot and `--help` prints the usage; no controller reads argv. Runners and the studio supply inputs through env only, so a port always binds `env:` and a variable bound by `arg:` alone needs a `default:`. Spec: `kernel/specs/application-arguments.md`.
- `logging` / `tracing` — **Application-only** `{ sinks, … }`. A `sinks:` entry is a sink (`!ref` or inline) or `{ sink, when }` (`when` a boolean resolved once at load); **only listed sinks attach** — a sink declared anywhere else does nothing (`SINK_UNATTACHED`). One attached `Telo.TraceSink` turns tracing on and every finished span is exported. `tracing:` on a Library is refused.
- `translations` — **Application-only** `{ catalogs }`, each entry a `!ref` or inline `Telo.Translations` (`Telo.TextTranslations`, or a library's keyed `<Module>.Translations`), resolved at load; on a Library it is refused as `tracing:` is, and each `App.Instance` child has its own. Per language the catalogs layer in order and a later one wins per text and context; the served languages are the Application's `lang:` (the fallback, `und` without one) plus every catalog's `lang`, and an imported library's texts are translated through the application's set. The transport negotiates the request language (RFC 4647 lookup, landing on the fallback) and exposes it as `lang` on its inbound context — HTTP `request.lang`, with `Http.Server.preferredLanguages` for a cookie, path or query choice; controllers reach the set as `ctx.translations`. The Rust kernel refuses `translations:`, `Telo.TextTranslations` and `Telo.KeyedTranslations` (`ERR_UNSUPPORTED_MANIFEST_FEATURE`).
- `needs` — as a Library's, plus `env: { <field>: <NAME> }` choosing the variable a field is read from; every Application need is read from the environment at load, and is forwarded to a library whole at its import.
- `lang` — the language the module's own texts are written in (an RFC 5646 tag); without it a module writes in `und`, and a plural source text is `MESSAGE_SOURCE_LANGUAGE_MISSING`.
- `ports` — **Application-only** map of inbound ports (`env:`, optionally `arg:` beside it, `protocol: tcp|udp`, `default:`), read as `ports.X`; a runner knows them before boot.
- `exports` is **forbidden** — if you want to export kinds, the file is a Library.

### `kind: Telo.Library`

Loaded **only** as an imported dependency; `loadFromConfig` on one is a hard error.

- `metadata.name`, `include`, `imports` — as Application (an import's object form also carries `resources:`).
- `variables` / `secrets` — JSON Schema property map; the public contract for importers, who supply each at the import's object form — decoded and validated against the entry statically and when the import initializes (`SCHEMA_VIOLATION` / `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED`). No `env` or `arg` access.
- `resources` — instances the library requires from its importer, constrained by kind only (`connection: { kind: Sql.Connection }`); the importer supplies `resources: { connection: !ref db }`. An entry may be `optional: true`: inside the library `resources.<name>` is nullable and its presence (`resources.<name> != null`) is a dimension of the library's own check — a literal fact at each importer — the library's own declaration-position `!if` on it declares the default, and a `!ref <name>` outside a branch proving it present is `RESOURCE_INPUT_OPTIONAL_REFERENCED` / `ERR_RESOURCE_INPUT_OPTIONAL_REFERENCED`. Borrowed, never owned. Guide: `docs/extend/library-resource-inputs.md`.
- `needs` — typed requests for what the library depends on (`databaseAccess: { kind: Fx.DatabaseAccess, version?, features?, parameters?, optional? }`), each naming a need type. A need is a kind-only declaration in the module's namespace, read as `resources.<need>.<field>` (typed and closed from the type's fields; nullable when optional), never handed to a controller as an instance (`ctx.resolveRef` refuses it): a kind consuming it whole takes it at a reference slot of the need type, whose controller opens it with `ctx.resolveNeed(pointer)` and reports the real version / features with `ctx.verifyNeed(pointer, observation)` — the kernel compares with the outermost need of the whole-forward chain (`ERR_NEED_UNMET` naming the source; a missing or malformed report by the end of startup is `ERR_NEED_OBSERVATION_INVALID`). A stated `version` (`>=15.0.0`, the `requires:` grammar, on a `version: semver` type) or `features` must reach a slot that `observes` it (`NEED_CONSTRAINT_UNVERIFIED`), a need forwarded whole must state at least what it supplies (`NEED_FORWARD_INCOMPATIBLE`), and a `!ref` to an optional need at a reference slot is `NEED_OPTIONAL_REFERENCED`. Guide: `docs/extend/consuming-needs.md`. The importer supplies it at the import, whole (`needs: { databaseAccess: !ref <need or fulfilment> }`) or field by field (a map of literals / CEL over the importer's scope); an unsupplied one bubbles to the root, where it is read from the environment at load — one variable per field, `TELO_NEED_<PATH SEGMENTS>__<FIELD>` (`Orders.databaseAccess` field `url` → `TELO_NEED_ORDERS__DATABASE_ACCESS__URL`), or the name a root need's `env:` binds — a required one the running configuration reaches with none set being `ERR_NEED_UNMET` naming every variable, some set `ERR_NEED_PARTIALLY_SUPPLIED`; those names are hidden from `process.env` and `ctx.env`, and `telo needs report` lists them with nothing booted (guide `docs/guides/providing-needs.md`). One fulfilment per module instance (a `shared` library's needs sit at `<LibraryName>.<need>`, a scoped import's beneath its holders: `seq.Inner.<need>`). Every static refusal is computed by ONE reader, the need table (`need-table.ts`), over every module built whole: `telo check` reports the entry's own where written and an imported library's at the `imports:` entry reaching it, and the kernel raises each as `ERR_<code>` at load. A `resources:` entry of a need type is `RESOURCE_INPUT_NEED_TYPE`. Guide: `docs/guides/declaring-a-need.md`.
- `lifecycle` — `"isolated"` (default: one child scope per import) | `"shared"` (one instance for the whole application; every import must agree on its configuration).
- `exports.kinds` — kinds importers may reference: a bare local name, or `<Alias>.<Kind>` to re-export. No block means ungated.
- `exports.resources` — plain name strings (`<name>` or `<Alias>.<name>`) exporting ready-made instances; importers use `!ref <Alias>.<name>` and `resources.<Alias>.<name>`. A library declares its own instance as `kind: Self.<Kind>`, so it can export an instance of a kind it does not export (singleton enforcement).
- `exports.browser` — the ES modules the library ships for a browser: `{ specifier, path, source, abi?, external?, exports? }` per entry, built by the kernel and reached through `ctx.resolveBrowserEntry` / `ctx.resolveControllerBrowserEntry`; a malformed entry is `BROWSER_ENTRY_INVALID`. Guide: `docs/extend/browser-entries.md`.
- `targets` is **forbidden**.

**Naming:** case encodes what a name denotes — `PascalCase` for types (module names, kinds, import aliases, `Telo.Type` resources), `camelCase` for values (resource instances, steps, `variables`/`secrets`/`ports` keys, CEL bindings). A name must match `^[A-Za-z_][A-Za-z0-9_]*$` and not be a CEL keyword (`INVALID_NAME`); a lowercase type name is `INVALID_TYPE_NAME`; an uppercase value name warns (`NAME_CASE_CONVENTION`).

### `imports`

- `source` — relative path / `oci://` ref / URL; resolved to `telo.yaml`. The CLI `install` / `upgrade` / `publish` commands read and rewrite this map. At publish a relative import of a library outside the module's directory becomes a separate pinned artifact; one inside it ships nested in the module's own artifact (Layered module artifacts).
- Each import creates an isolated child context; child resources are not visible to the root scope.
- Importing a `Telo.Application` is a hard error. Only the root Application binds host env vars, and forwards them into imports.
- An import that cannot be identified registers no alias: `INVALID_IMPORT_SOURCE` / `IMPORT_UNRESOLVED` / `INVALID_IMPORT_TARGET`.
- A `Telo.Import` declared as a scope member (`with:`) is loaded and checked as an `imports:` entry is, its refusals reported at the member and refused at load; its library is one instance per scope run beneath its holders, giving the scope its exported instances (`!ref <Member>.<name>`, `resources.<Member>.<name>`) and never a module name (`kind: <Member>.<Kind>` is `UNDEFINED_KIND`).

### `kind: Telo.NeedType`

Registers a kind `<module-name>.<Name>` a module can ask for: `fields` (a JSON Schema property map of what a fulfilment hands over; a field may be `x-telo-sensitive: true` and must then be a string), `required`, `parameters` (the schema of a need's `parameters:`), `version: semver` and `features` (what a need may constrain), `supply: root` (fulfilled only through a root need forwarded whole — a self-supplied fulfilment, a field-by-field supply and a library need reaching the root unforwarded are `NEED_ROOT_SUPPLY_REQUIRED` / `ERR_NEED_ROOT_SUPPLY_REQUIRED`), `unique: true` (a module declares at most one need of the type; a second is `NEED_DUPLICATE` / `ERR_NEED_DUPLICATE`, naming both); no `extends`. A need's `parameters:` are literals, except a `!module-path` at a `Telo.HostPath` parameter — a module file claim like one on a resource (carried by `telo publish` / `telo package`, `MODULE_PATH_NOT_FOUND`, `HOST_PATH_ENTRY_MISMATCH`), resolved at load against the declaring module to the absolute path `ctx.resolveNeed` hands over, printed module-relative by `telo needs report`; any other tag is `NEED_PARAMETERS_INVALID`. The kind is a `Telo.Provider` served by the kernel's one need-type controller, so a resource of it — a FULFILMENT, written with `fields:` — publishes exactly its fields. A sensitive field's value joins the redaction set of every module context the fulfilment reaches. The Rust kernel refuses `needs:`, an import's `needs:` and a `Telo.NeedType` (`ERR_UNSUPPORTED_MANIFEST_FEATURE`). Guide: `docs/extend/need-types.md`.

**Public addresses are two kernel-declared need types**, `supply: root`: `Telo.PublicUrl` (field `url`, a `Telo.Url` constrained to an http/https origin; parameters `port` — a `tcp` key of the root's `ports:`, required at the root — `primary`, `customDomains`) and `Telo.PublicHostPattern` (field `pattern`, `<scheme>://*.<rest>` or `*<text>.<rest>`; parameter `port`); a library declares them with no parameters (`NEED_PARAMETERS_INVALID`). An `Http.Server` mount names them in `hostnames`, so a domain name is never written in a manifest. A host supplies each through its env name (report mode) or sets the host values `TELO_HOST_PUBLIC_URL_TEMPLATE` / `TELO_HOST_PUBLIC_URL_SECONDARY_TEMPLATE`, from which the kernel derives every unset `Telo.PublicUrl` (template mode: the primary, or a base's only need, gets the main template with `{port}` filled, every other the secondary with `{label}` — the need name lowercased, `_` as `-`; a bad template or label is `ERR_NEED_HOST_VALUE_INVALID`) and announces each port's hosts as `publicUrls` on `Kernel.PortsResolved`. Two addresses no host could route apart are `ERR_NEED_PUBLIC_URL_COLLISION` at load. Both host values are hidden from controllers and stripped from a started child's environment. Guides: `docs/guides/providing-needs.md`, `modules/http-server/docs/host-routing.md`.

**The desktop shell is the kernel-declared need type `Telo.DesktopHost`**, `supply: root` and `unique: true`: fields `endpoint` (a `Telo.Url`, scheme `unix` or `npipe`, no credentials) and `token` (`x-telo-sensitive`) — the shell's control channel; parameters `identifier` (reverse-DNS), `productName`, `icon` (a `Telo.HostPath`, `entry: file`, `mediaType: image/png`, written `!module-path`), `port` (a `tcp` key of the root's `ports:`), `showInDock` (default `true`) and `callbackPaths` (literal app-relative paths, no query or fragment). Supplied like every root need through `TELO_NEED_<NEED>__ENDPOINT` / `__TOKEN` (one without the other is `ERR_NEED_PARTIALLY_SUPPLIED`, neither `ERR_NEED_UNMET`); a library declares it with no parameters, and a bad `port`, `callbackPaths` entry or library parameters are `NEED_PARAMETERS_INVALID`. **`telo run` is the desktop host** when neither field is set (an environment supplying both carries the control channel only): before the kernel is built it checks the machine, takes a single-instance lock per `identifier` (a second start shows the first's windows and exits 0), binds `127.0.0.1` on a remembered origin port — the root's port `default:` first — and hands the kernel that socket, the port number and the channel (`KernelOptions.listeners` / `inputs`, `redactedValues`) while the helper `telo-desktop-host` owns the windows; only the application's own windows are admitted (a one-time code exchanged on a host origin of its own — a second loopback port serving every page the host shows a window — then a cookie), a navigation to another origin opens the system browser, and a return to a declared `callbackPaths` entry is replayed into the window that left. `TELO_HOST_DESKTOP_HELPER` names a helper binary (hidden like every host value); `ERR_DESKTOP_HOST_UNAVAILABLE` refuses a machine or helper that cannot host (`--watch` included), `ERR_DESKTOP_ICON_INVALID` an icon `telo package` cannot use. `telo package` of such a root writes a `.app`, a GUI `.exe` or an ELF with `desktopHost: { identifier }` in its index and, started, works in the per-user directory of the `identifier` with `TELO_HOST_STATE_DIR` beneath it. The Rust kernel refuses the need with every `needs:`. Spec: `kernel/specs/desktop-host.md` §5; guide `docs/guides/providing-needs.md#desktop-hosts`.

**Persistent storage is the kernel-declared need type `Telo.DurableDirectory`**: field `path`, a `Telo.HostPath`; parameters `size` (`<n>Mi|Gi|Ti`, default `1Gi`) and `access` (`single-writer`, default, | `shared`), neither measured nor enforced — `telo needs report` lists every need's parameters with its type's defaults filled in, for whoever provides the storage. A host supplies one per need through its env name, or sets `TELO_HOST_STATE_DIR` once and the kernel answers every unset one as `<state dir>/needs/<need path>` (path `.`-joined), created at load. However supplied, the directory must be one the process can write to (`ERR_NEED_DIRECTORY_UNUSABLE`, checked before any resource initializes for an environment read, at the import or fulfilment otherwise); an entry under `needs/` no declared path names is an orphan — `ERR_NEED_ORPHANED` when the load would also create a fresh directory, a `NEED_ORPHANED` warning otherwise, nothing moved or deleted. Forwarded whole, a `shared` one into a `single-writer` need or a smaller `size` into a larger one is `NEED_FORWARD_INCOMPATIBLE`, and one directory forwarded to two needs `NEED_DIRECTORY_FORWARDED_TWICE`. A child application a resource runs (`App.Instance`) is answered `<state dir>/apps/<path>` (the resource's module path and name, `.`-joined: `apps/web`, `apps/Admin.web`; beneath its holders for a scope member: `apps/seq.web`), created at load, as its own `TELO_HOST_STATE_DIR`, so its directories nest beneath it, and the orphan rule covers `apps/` as it covers `needs/`; a child never asks for a missing input (only the root does) and is refused at its start naming the instance and the fix. `TELO_HOST_STATE_DIR` is hidden from controllers and stripped from a started child's environment with the other host values, the child receiving its own derived value instead. Guide: `docs/guides/providing-needs.md#durable-directories`.

### `kind: Telo.Definition`

Registers a new resource kind (`<module-name>.<Name>`).

- `capability` — one of the capabilities below, and nothing else; inherited and immutable under `extends` (`EXTENDS_CAPABILITY_MISMATCH`). A kind a definition specializes goes in `extends:` — the legacy `capability: <Alias>.<Kind>` is rewritten to it by the `capability-as-extends` migration (`CAPABILITY_SHADOWS_EXTENDS`).
- The `Telo.Definition` / `Telo.Abstract` documents are validated against ONE built-in schema by `telo check` and the kernel alike, so an undeclared key (`controllrs:`) is refused by both.
- `extends` — alias-qualified kind this definition specializes: an abstract (implements its contract) or a concrete kind (single inheritance, Liskov-substitutable). `Self.<Kind>` names the declaring library's own kind (ungated); the module's own name works too. Guide: `docs/extend/kind-inheritance.md`.
- `base` — "super(...)": CEL over `self` mapping the child's schema onto the inherited controller's config. With `base:` the author schema is the child's own; without it, `merge(parent, own)`, and the parent's `required` still applies. `base:` beside a template body is refused (`BASE_WITH_TEMPLATE_BODY`).
- `controllers` — PURL candidates (see Controller delivery); omit on a concrete-`extends` child to inherit.
- `schema` — JSON Schema with `x-telo-*` annotations.
- `status` — optional JSON Schema for observed state (`resources.<name>.status.<field>`); `required:` is rejected.
- `inputType` / `outputType` — the invocation contract.
- `resources` / `invoke` / `run` / `provide` — template bodies: entries are named by literals, dispatch slots take a `!ref` to a sibling or a module resource, and `inputs:` / `result:` are top-level siblings. The `{ kind, name }` object form and CEL-computed entry names are deprecated.
- `targets` — on a templated Service / Runnable, instead of `run:`: `!ref` entries the instance starts in order when it runs (a server and the poller beside it). Guide: `docs/extend/templated-definitions.md`.
- **Blueprints** (`blueprints/`) are libraries exporting one templated kind that is a whole application; a starter imports one. Guide: `blueprints/README.md`.

**Resource-doc validation injects only `kind` and `metadata`** into a definition's `additionalProperties: false` schema. Every other top-level field an author may write — including `outputType` — must be declared as a property in the kind's own `schema`, or validation rejects it.

## Capabilities

**The roster is closed**: a capability names a lifecycle a kernel implements, so no module adds one. It is the built-in `Telo.Abstract` entries carrying `declarable` in `sdk/builtins/` (the built-in vocabulary as data — every `Telo.*` kind and the `telo://manifest#/$defs` fragments, one JSON file each, read by both analyzers, both kernels and the editor support). A value outside it is `CAPABILITY_UNKNOWN`, a roster entry no author may declare (`Telo.Executable`, `Telo.Template`) `CAPABILITY_NOT_DECLARABLE` — refused by both kernels before schema validation — the Node kernel's registration guard as `ERR_<code>`, a load's analysis as one `ERR_MANIFEST_VALIDATION_FAILED` carrying it — and reported for a dependency's definition at the import reaching it.

- `Telo.Service` — `init()` + `run()`; long-lived servers, pools
- `Telo.Runnable` — `run()`; one-shot tasks, pipelines
- `Telo.Invocable` — `invoke(inputs)`; request handlers
- `Telo.Provider` — `init()` + optional `provide()`; config/secret/value-flow sources; all fields implicitly `x-telo-eval: compile`
- `Telo.Mount` — mounted into a Service (HTTP APIs, middleware)
- `Telo.Sink` — `write(record)` + `flush()` / `flushSync()` / `close()`; a record stream the runtime writes to directly, never through `ctx.invoke`
- `Telo.Type` — pure schema definition, no runtime instance
- `Telo.Callable` — synchronous `call(args)`; a function reached from CEL through a module name (`Self.fn(x)`, `<Alias>.fn(x)` for an exported one), declaring `params` / `returns`; outside `Telo.Executable`. `Telo.Function` is the built-in CEL-bodied callable, whose determinism is derived and never declared. A native callable's `use: dependency` slot names any kind but a need type and hands its controller the referent's configuration as frozen data at `create()` (`CALLABLE_REFERENCE_NOT_DATA` / `ERR_CALLABLE_REFERENCE_NOT_DATA` when it is not data). Guide: `docs/extend/cel-functions.md`.

`Telo.Executable` is a slot constraint — the parent of `Telo.Invocable` and `Telo.Runnable` — not a capability; `capability: Telo.Executable` is rejected, and `Telo.Service` is deliberately outside it. `Telo.Template` is the role of the built-in document kinds, read and never authored. A `Telo.Abstract` is a non-instantiable base kind: a contract with no default implementation. To reuse an existing controller under a friendlier schema, `extends` the concrete kind with `base:` instead.

## Lifecycle & value flow

- **Capability governs wiring, not dispatch**: it decides which `x-telo-ref` slots accept a kind; the kernel calls `init()` / `snapshot()` on anything that has them. A resource that must be both started and invoked is two kinds.
- **Observable side effects belong in `run()`, never `init()`.** `init()` builds the instance — it may ALLOCATE (that is what its effect frame is for: registered listeners, half-built pools), but it performs no I/O the outside world can see, which is also why `ctx.setStatus()` is an error before the resource has started. `run()` is where the effect becomes observable. `Http.Server` is the reference: `init()` registers plugins and routes as one effect, `run()` takes a kernel hold and calls `listen()` as two more. **The one exception is `Telo.Provider`**, which has no `run()`: it may acquire external resources in `init()` (a connection, a container) when each acquisition is an effect whose inverse releases it completely, and may report observed state from `init()` — published when `init()` returns, discarded with a failed or deferred attempt.
- **`init()` and `run()` RETURN what undoes them** (a `ctx.effect(reason, body)` chain); there is no `teardown()`. Spec: `kernel/specs/revertible-effects.md`. A module whose controllers return chains needs telo `>=0.82.0`, stated as a `restrictions:` entry wherever its measured floor does not already imply it.
- **Configured state is pulled, observed state is pushed**: `snapshot()` returns configuration; `ctx.setStatus(...)` reports what the resource learns, against its declared `status:` block (it replaces, is sticky, and is illegal before start and in startup fields — except a Provider's, which is reported from `init()` and readable at startup unless the provider is declared in a `with:` scope, the read being an init-order edge). See `kernel/docs/observed-state.md`.
- A controller's `ctx` is scoped to the context that OWNS its resource; `ctx.moduleContext` is only for imports, the controller policy and the logging scope.
- Controllers resolve a `!ref` slot with `ctx.resolveRef(value, guard, describe, expects)`, not the standalone `resolveRefInstance`.
- Controllers read configuration through `ctx.env` or the declared `variables` / `secrets`; a key the Application binds reads `undefined` from `process.env`.
- In-process state every resource of one application must share is keyed by `ctx.kernelInstanceId` (opaque, unique in the process, kept across a reconcile, never reused), never held module-global: one process may run several kernels, and a child manifest (`ctx.runtime.run`, `App.Instance`) is a kernel of its own.
- Module files are reached with `ctx.resolveModuleFile(relative)` (a path the resource's author wrote, resolved against the author's module) or `ctx.resolveControllerFile(relative)` (the controller's own module file, resolved against the module declaring the kind), never by deriving a directory from `ctx.moduleContext.source`. A browser entry is reached by specifier the same two ways: `ctx.resolveBrowserEntry` (the resource's module) and `ctx.resolveControllerBrowserEntry` (the kind's module).
- **Every inbound source takes a kernel hold while armed** (a listening server, an MCP endpoint, a schedule), taken in `run()`; the app exits at zero holds.
- `Telo.Sequence` is the built-in ordered list of steps behind a contract (a `Telo.Runnable`, invokable with inputs, no import; `Run.Sequence` is its deprecated twin). Its `with:` declares resources whose lifetime is one run of the sequence, which ends once the run has produced its result and every stream leaving it has settled — a stream is owned by the call that received it and cancelled when that call ends unread, at once under a context nobody opened (spec: `kernel/specs/invocation-contract.md` §4.9); its `targets:` runs them before the steps.
- `Telo.Value` is the built-in `Telo.Invocable` that returns a CEL-shaped value (`inputType`, `outputType`, `bindings`, required `value`; no import; `Run.Value` is its deprecated twin). Its controller evaluates through the SDK's binding and value expansion, as `Run.Value`'s does, and the Rust kernel refuses it (`ERR_UNSUPPORTED_MANIFEST_FEATURE`).
- **`inputs`/`outputs` are always VALUES; `inputType`/`outputType` are always SCHEMAS.** A contract resolves instance → nearest along `extends` and replaces rather than merges; the kernel binds it at `create()` and fails with `ERR_INPUT_INVALID` / `ERR_OUTPUT_INVALID`. `Telo.JsonSchema` is a kernel built-in (`modules/type` is deprecated). `throws:` is the contract's third part: an abstract may declare a literal `codes` list, and the nearest ancestor's list is a ceiling every descendant's codes must fall within (`THROWS_NOT_SUBSTITUTABLE` / `ERR_THROWS_NOT_SUBSTITUTABLE`); a dispatch through a kind-only library input resolves to that list, unbounded when none is declared. A literal `codes` list is legal on every capability, but only a dispatchable (`throwsAllowed`) kind's feeds unions and ceilings. **A failure carries two messages**: `message` is the developer's (logs, traces), `displayMessage` the text a person is shown, a `TextRecord` in its source language. `throws.codes.<CODE>.displayMessage` is a `Text` whose placeholders name required `data` properties; where an error leaves a dispatch of the declaring kind the kernel attaches it as `InvokeError.displayMessage` unless one is already attached, first holding `data` to the code's `data` schema (`ERR_OUTPUT_INVALID` naming the original code); a `throw` step is `{ code, message?, displayMessage?, data? }` — `message` a string, computed allowed, `displayMessage` a literal `Text` over `data` or `!cel "error.displayMessage"`, the developer message defaulting to the display message formatted with `data`, else the code — and inside a `catch:` it records the caught failure as its `cause`; `rethrow: {}` re-raises the caught failure unchanged, legal only under a non-nullable `error` (`RETHROW_WITHOUT_CAUGHT_ERROR` / `ERR_RETHROW_WITHOUT_CAUGHT_ERROR`); the ambient codes carry built-in English display messages (`sdk/error-codes/`, the archive's `errorCodes`); every catch context reads `error.displayMessage` beside `error.message`; a refusal outside a dispatch asks `ctx.declaredDisplayMessage(code, data)`. Spec: `kernel/specs/invocation-contract.md`.
- `ERR_DURABLE_SUSPENDED` is a signal, not an error: anything that catches (a `try:` step, `catches:`, a retry policy) rethrows it, as it does a cancellation.
- **One import instead of two.** An app that configures a backend itself imports both the abstract and the implementation (`sql` + `sqlite`) — that is normal and ~25 manifests do it. When a consumer should need only one import, the sanctioned collapse is a library that owns the wiring and exports **instances** via `exports.resources` (`tests/__fixtures__/re-export/`), not a module re-exporting another module's kinds.

## x-telo-* Schema Annotations

Inside `Telo.Definition` schema blocks. Each annotation has ONE reader in the analyzer and no other surface pattern-matches its shape; full semantics in `analyzer/nodejs/CLAUDE.md`.

- `x-telo-eval: "compile" | "runtime" | "accessor"` — when CEL in the field is evaluated. **Every CEL-bearing field must be annotated** (or sit in an `x-telo-context` / step-body / error-context region, or a provider's implicit root eval); otherwise `CEL_IN_NON_EVAL_FIELD`. `accessor` is typed and never evaluated: the field holds a plain `!cel` chain rooted at one of its `x-telo-context` bindings, or a literal, and the controller receives a binding map (`{ root, path }` / `{ value }`); anything else is `ACCESSOR_NOT_PLAIN_CHAIN` / `ERR_ACCESSOR_NOT_PLAIN_CHAIN`. Only the accessor field itself is skipped at compile time — an expression beside it is evaluated. The chain's fit to the field is format-aware: a string with no `format` fed to a field whose schema requires `date` or `date-time` is `CEL_TYPE_ERROR`. An accessor field declaring a `format` (or a union whose every branch does) takes only a chain whose declared source is a string of one of those formats — any other declared string is `CEL_TYPE_ERROR`. Eval paths, accessor sites and regions are reached through named shapes, JSON Pointers into them and recursion at any depth, by one walk and one shape lookup the kernel shares. A relative pointer inside a named shape (`x-telo-context-element-from-item`, `x-telo-context-nullable-when`, `x-telo-text-values-from`) resolves within the shape and is refused at the shape where it climbs above the shape's root. That walk reads a union's branches at one path with no value, so a property two `oneOf` / `anyOf` branches declare must carry the same eval sites in each, same paths and modes (`EVAL_MODE_BRANCH_CONFLICT` / `ERR_EVAL_MODE_BRANCH_CONFLICT` at registration); a type difference is fine and `allOf` is not judged. Guide: `docs/extend/accessor-fields.md`.
- `x-telo-ref` — a reference slot plus what the declaring resource does with it. Structured form `{ kind, use, inputs? }` (`kind` may be a list; the bare string is legacy). `use`: `schema` | `dependency` | `call` | `detached` | `trigger.inbound` | `trigger.consumer` — when control reaches the target's bound entry points; a set when several hold, a case map `{ by, cases }` when a statically resolvable sibling chooses. Kinds are alias-qualified (`Self.<Kind>`, `Telo.<Kind>`). `throwsThrough: true` carries throws through a `dependency`. `outputTo: { slot, member }` hands the target's output, null removed, to the input member `member` of the sibling slot's target, which it must fit (`CONTRACT_INPUTS_MISMATCH` at the source; `X_TELO_REF_INVALID_OUTPUT_TO` misdirected; guide `docs/extend/reference-slot-outputs.md`). `completedWhen: /<boolean sibling>` beside `inputs:`: where the sibling is literally `true` the target obtains what the map leaves unbound, so a missing required input is not refused there (`X_TELO_REF_INVALID_COMPLETED_WHEN` / `ERR_X_TELO_REF_INVALID_COMPLETED_WHEN` misdirected). `callsCoReferrers: { kind, slot }`: dispatching the declaring resource calls every module-scope declaration of `kind` (or one extending it) whose slot at `slot` names the same target in the same module instance, in load order — one definition (`co-referrers.ts`) gives the call graph its edges and the kernel its set (`X_TELO_REF_INVALID_CALLS_CO_REFERRERS` malformed, `CO_REFERRER_SCOPED` for such a declaration in a scope). `observes: [version, features]` on a slot holding a need's fulfilment: the kind reports what it found (`ctx.verifyNeed`) and the kernel compares it with the outermost need — legal only on a `Telo.Provider` / `Service` / `Runnable` / `Invocable` kind with a controller of its own or inherited (or an abstract), the kinds the kernel can hold to an observation deadline (`X_TELO_REF_INVALID_OBSERVES` / `ERR_X_TELO_REF_INVALID_OBSERVES`). Reader: `ref-slot.ts`. References are written only as `!ref <name>` / `!ref <Alias>.<name>`, and a member of a template body's `!for-each` family as `!ref <family>[<binding>.key]` (`[<binding>.index]` over a list), one index per family depth, each binding a loop around the reference iterating the family's own source (`REF_MEMBER_INVALID` otherwise). A slot declared inside a named shape (`Telo.JsonSchema`) the kind's schema reaches by `$ref` to the shape or a JSON Pointer into it (`telo://Self/Bound#/properties/action`) is a slot of the kind, with its siblings read from the object holding the `$ref`; every annotation reached that way, and through a local pointer (`#/$defs/X/properties/y`), is read as if written inline. A computed value (`!cel`, `!interpolate`) at or above a slot in a field the kind evaluates — one marked `x-telo-eval` (`compile` or `runtime`) or covered by a CEL region (`x-telo-context`, `x-telo-error-context`, a step context) — is `REF_SLOT_COMPUTED` / `ERR_REF_SLOT_COMPUTED`.
- `x-telo-scope: "/json/pointer"` — an execution scope, on a named top-level property only; resources inside initialize on demand and the controller receives a `ScopeHandle`, opening each run with `run(inputs, fn)`. The object form `{ regions: [...], openedBy: dispatch }` says a call of the holder opens it: `inputs` is then that call's inputs (`null` for the other forms, `ERR_SCOPE_OPENING_INVALID` on disagreement), read by the members' creation-time fields; `openedBy: dispatch` on a kind with no `invoke` / `run` is `SCOPE_OPENED_BY_INVALID` / `ERR_SCOPE_OPENED_BY_INVALID`. Every member is a declaration of the holder's module: `telo check` checks it as a top-level resource, reports at its place inside the holder, and resolves its names scope first, innermost out, then the module.
- `x-telo-schema-from: "refProp/$defs/Name"` — field schema derived from a sibling ref's definition (polymorphic config).
- `x-telo-value-schema-from: "<location>"` — the value here must satisfy every type declared at `<location>`: a field of the resource, or a JSON Pointer that may cross its references and range over a list with `*`; a list of locations holds it to every type each reaches; a pointer ending at a referenced resource's `inputType` / `outputType` reads the contract that resource resolves to along `extends`. On a configuration slot every annotated slot is checked, not only the one that wins at runtime; inside `inputType` / `outputType` it types that contract node (`VALUE_SCHEMA_FROM_INVALID` / `ERR_VALUE_SCHEMA_FROM_INVALID` for a location the kind's schema cannot hold). `{ from: <location>, member: "0#" }` holds the value to the property of each reached type its own map key names (a Relative JSON Pointer: `N#` a key, `N/<pointer>` a string; one naming no key or no string is `VALUE_SCHEMA_FROM_INVALID`) — typed on the map, so a key naming no property is refused and a key the kind's schema fixes keeps its own reading — and on a configuration slot every expression, accessors included, joins the CEL slot-fit check (`CEL_TYPE_ERROR`).
- `x-telo-context: <JSON Schema>` — the CEL context inside a handler field; properties may carry `x-telo-context-from`, `-from-root`, `-from-ref-kind` and `x-telo-context-ref-from` (its first hop resolving `!ref <Alias>.<name>` through the holder's imports, a named shape read with `extends` folded). A nested region adds to every one enclosing it (an inner name shadows). `x-telo-context-eval: <mode> | [<mode>…]` (`compile`, `runtime`, `accessor`; absent = every mode) on a binding names the eval modes it exists at: elsewhere it is out of scope — an evaluated read of an `accessor`-only binding is `CEL_UNKNOWN_IDENTIFIER`, and an accessor chain rooted at a binding without `accessor` is `CEL_UNKNOWN_IDENTIFIER` at check and `ERR_ACCESSOR_NOT_PLAIN_CHAIN` at creation (`SCHEMA_VIOLATION` for a malformed value, warning `CONTEXT_EVAL_MISPLACED` off a binding). `x-telo-context-from-referrer: "<binding>[/<member>…]"` on a binding or a member beneath one types that node from what the path names in scope at each slot referencing the resource, read at the site's own eval mode, replacing its own keywords (kept with no referrer) — judged once per distinct type, a finding only some referrers' types make naming them (`CONTEXT_FROM_REFERRER_INVALID` misplaced). `x-telo-context-from-path-template: "<relative pointer>"` (`0/path`) on the same nodes types the node as the variables of the path template the resource holds there — closed, one required string per `{name}` — and an open map of strings where it holds none (`CONTEXT_FROM_PATH_TEMPLATE_INVALID` misplaced). `x-telo-context-nullable-when: { at, equals, absent }` on the same nodes adds null to the node's type where the resource's value at `at` (a relative pointer from the context holder, schema defaults filling a present object, a computed value matching) is one of `equals` or — `absent: true` — missing (`CONTEXT_NULLABLE_WHEN_INVALID` misdirected). `x-telo-context-withheld: "<reason>"` on the same nodes names a binding or member that holds no value at the site: any read of it, guarded or not, is `CEL_UNKNOWN_IDENTIFIER` / `CEL_UNKNOWN_FIELD` naming the referrer withholding it and the reason, the mark travelling through `x-telo-context-from-referrer` (`CONTEXT_WITHHELD_INVALID` misplaced or beside a typing keyword). Guide: `docs/extend/referrer-typed-bindings.md`. `x-telo-context-item-fills: [<pointer>…]` on a binding of a region declared on a list names the member each item fills (`""` the item, `/property` its field); items reading each other's members in a cycle are `CONTEXT_FILL_CYCLE` (`CONTEXT_ITEM_FILLS_INVALID` misplaced).
- `x-telo-match-for: "<pointer>"` — on a JSON-Schema-valued field, names the sibling accessor field the schema is matched against; a schema that can never hold for the accessor's static type is `MATCH_UNSATISFIABLE` (refused at load through the kernel's analysis), a misdirected annotation `MATCH_FOR_INVALID`. Guide: `docs/extend/accessor-fields.md`.
- **Step bodies** — `items: { $ref: "telo://manifest#/$defs/Step" }` gives any kind the shared step grammar (`invoke` / `value` / `if` / `while` / `switch` / `try` / `throw` / `rethrow`); `x-telo-step-context` is the legacy spelling. Guide: `docs/extend/step-bodies.md`.
- `x-telo-context-element-from` / `x-telo-context-collection-from` — type a binding from a sibling collection's element / the collection itself. `x-telo-context-element-from-item: "<relative pointer>"` types one as the element of the collection the chain at another field names — a Relative JSON Pointer from the object holding the field the region is declared on (`0/rows` a sibling, `2/rows` two levels up), the chain typed as at its own site — and leaves it untyped, silently, when the data does not resolve; a pointer naming no CEL-typed field is `ELEMENT_FROM_ITEM_INVALID`, and the bare field name ui 0.3/0.4 shipped is rewritten to `0/<field>` at load (`DEPRECATED_ELEMENT_FROM_ITEM_FIELD`).
- `x-telo-bindings-from: "<field>"` — named CEL bindings readable by bare name.
- `x-telo-error-context` — the `error` variable's schema inside a `catch:` / `finally:` branch.
- `x-telo-caught-member: code | data` — on a member of a catch list's (`x-telo-outcome-list: catches`) context binding: the member carrying the caught code, which a proving `when:` compares (`problem.code == 'X'` as well as `error.code`), or its data, typed inside each entry from the codes it matches. Catch-list analysis reads no binding by name; misplaced is `CAUGHT_MEMBER_MISPLACED`, a list marking no code `CAUGHT_MEMBER_MISSING`; the `caught-member-marks` migration marks a published `error` binding. `x-telo-catches-for: { slot, raises: [<CODE>…] }` names the codes a kind raises into a catch list itself, each declared in its own `throws.codes`: nameable and typed on that list and every list above it on the scope ladder, owed by no site (`CATCHES_FOR_INVALID` misplaced or undeclared). `x-telo-raises: [<CODE>…]` on a field says the kind raises those codes wherever the field holds a value: they reach the lists of the object holding it, every list it reaches through a `throwsThrough` slot and every scope list above, each list receiving what its own `raises` names, and type a catch-all there; an exported declaration receives every code its lists declare (`RAISES_INVALID` for a code it does not declare).
- **Shared fragments** `telo://manifest#/$defs/<Name>` — `InvokeStep`, `EmittedStep`, `RetryPolicy`, `RetryAttempts`, `Step`, `JsonSchema7`, `KindSchema`, `Message`, `Text`, `TextCatalog`, `TextRecord`; owned by the analyzer. A recursive one is hoisted into the root of the author-written schema holding the reference — a top-level schema key, or a position a built-in declares as a schema fragment (a parameter's `schema`, a need type's `fields`).
- **Text shown to a person** is typed `Text` (a MessageFormat 2 pattern with `{$name}` placeholders, or a plural selection `{ plural, cases }`, optionally `{ text, context }`), written in the module's `lang:` (`Telo.Application` / `Telo.Library`, a `language-tag`); `x-telo-text-context` gives a data schema node's title, description and enum labels a context, `x-telo-text-values-for: /<pointer>` names the `Text` an object holds the values of, `x-telo-text-values: { <name>: <schema> }` on a text's node declares the values whoever shows it formats it with (a placeholder outside them is `MESSAGE_PLACEHOLDER_UNBOUND`; misuse `TEXT_VALUES_INVALID`), `x-telo-text-values-from: "<relative pointer>"` (`0/data`) limits them to the required string / number properties of the schema it names (`MESSAGE_PLACEHOLDER_UNBOUND` / `MESSAGE_PLACEHOLDER_VALUE_UNSUPPORTED`), and `x-telo-text-keys: [<Alias>.<Kind>]` on a kind's schema root names the keyed translation sets its resources show (`TEXT_KEYS_INVALID` / `ERR_TEXT_KEYS_INVALID`), read by the controller as `ctx.translations.keyed()`. In a union of a `Text` and a `TextRecord` branch an expression is admitted only as a record (`TEXT_ARGUMENT_COMPUTED` / `ERR_TEXT_ARGUMENT_COMPUTED`). A text site is recorded only where the fragment admits the value, so a union of a text with another shape judges each value by its own branch; `TextRecord` types a record a kind hands on, which is never judged again. A `Text` parameter takes a literal argument (`TEXT_ARGUMENT_COMPUTED`), and a controller receives each `Text` as the record `{ text, context, lang, computed }` attributed to the module that wrote it — a text its own per-call evaluation produces included, settled when it evaluates it. A text typed at or beneath an `x-telo-eval: accessor` field is refused at the kind (`TEXT_SLOT_ACCESSOR`). A translation is a built-in `Telo.TextTranslations` (a `Telo.Translations` with `lang` and `texts`) listed in the Application's `translations:`; a library's own texts are declared by key in a built-in `Telo.KeyedTranslations` (`keys:` of a message or `{ message, values?, description? }`, in the library's `lang:`), which registers `<Module>.Translations` (`lang` + a closed `messages:` map) layered per key over the source wording, and the Rust kernel refuses it; per language the catalogs layer in order, a text and context translated twice within one catalog is `MESSAGE_ENTRY_DUPLICATE` (by the message core's identity) and across catalogs a later one overrides. The built-in error codes' display messages arrive translated into fourteen languages as the lowest layer of every application's set, from the archive's `translations` section (`sdk/translations/`), beneath every listed catalog and never widening the served languages. `telo check` warns `MESSAGE_TRANSLATION_MISSING` — at the Application's `translations` key, else its `lang:` — once per served language and keyed set, plus once per language for by-text texts, listing every key or non-computed `Text` written in another language that the language lacks; at run time nothing is refused and a missing translation shows the source. A library proves its translations complete with a fixture application listing them all (`modules/ui/tests/translations.yaml`). Codes `MESSAGE_*`; guide `docs/extend/text-records.md`.
- `x-telo-schema-map` / `x-telo-schema-projection` / `x-telo-schema-projection-from` — a collection of typed entries projected to a JSON Schema consumers type against.
- `x-telo-resource-rules` — CEL rules relating the fields of one resource (`RESOURCE_RULE_VIOLATED`); `reachable: { kind, use, through }` (instead of `in:`) iterates as `this` every declaration a reference of `kind` at a `use` slot names, walked through slots and step `invoke:` targets whose use is in `through`, a dependency's reported at the entry slot the walk entered it through; a bound declaration is equal only to itself under `==` / `!=` / `in`; a rule's `resolve:` reads the declarations its own reference slots name, a pointer continuing past a slot into what it names (`/fields/*/options/model`) and repeating a group over the resource's own fields as `in:` does (`/navigation/items(/*/items)*/*/page`); `coReferrers: /<slot>` binds the other resources the rule judges whose slot there names the same declaration (two session sets claiming one `name` on one store), skipped where the slot names nothing comparable. Guide: `docs/extend/resource-rules.md`.
- `x-telo-referrer-rules` — CEL rules on whoever references the resource (`REFERRER_RULE_VIOLATED`); `resolve:` reads the declarations the referrer's own reference slots name, `resolveSelf:` those of the kind's own; `coReferrers: /<slot>` binds the OTHER declarations of the `referrer:` kind reaching the same resource through that slot of theirs (two queues claiming one `name` in one table); a code is unique per `referrer:` filter. Guide: `docs/extend/referrer-rules.md`.
- `x-telo-sensitive: true` — on a contract property: the value is redacted in trace payloads; on a need type's string field: the value is redacted in every log line of a module context the fulfilment reaches.
- `x-telo-serializable: true` — on a slot holding a shape whose values the kind stores or serializes (a queue's `messageType`): the shape may hold no live value type (`Telo.Stream`) at any depth (`SCHEMA_NOT_SERIALIZABLE` / `ERR_SCHEMA_NOT_SERIALIZABLE`; a misplaced mark `SERIALIZABLE_ANNOTATION_INVALID`). Reader: `serializable-slot.ts`.
- `x-telo-retry-for: { slot: /<field>, codes? }` — on a field holding a `RetryPolicy` that the kind runs itself around a slot it dispatches (a worker's `retry:` around its handler): `nonRetryable` and `retryAfter` are judged against that slot target's throws plus the listed `codes` the kind raises into the loop, as for a step's own `retry:` (a `nonRetryable` code nothing can throw warns `NON_RETRYABLE_CODE_NOT_THROWN`; misuse `RETRY_FOR_INVALID`). Reader: `retry-for-slot.ts`.
- `x-telo-span-attribute: "<name>"` — on a scalar contract property (reached through `properties`, following `$ref`): its value is exported on the resource's dispatch span under that name. Misplaced is `SPAN_ATTRIBUTE_MISPLACED`, a malformed name `SPAN_ATTRIBUTE_INVALID`, the kernel twin `ERR_SPAN_ATTRIBUTE_INVALID`.
- `x-telo-browser-export: { entry: "/json/pointer", abi?: [<family>-<version>…], external?: [<specifier>…] }` — on a string field: the value names an export of a browser entry, and the pointer names the sibling string holding that entry's `specifier`, one the module declaring the resource lists under `exports.browser`; `abi` lists the generations the kind accepts and `external` the specifiers it supplies, each held against the entry's own (`BROWSER_ENTRY_UNKNOWN` / `BROWSER_ENTRY_ABI_UNSUPPORTED` / `BROWSER_ENTRY_IMPORT_UNSUPPLIED` / `BROWSER_EXPORT_UNKNOWN`, `ERR_`-prefixed at creation; an imported library's resources are judged against its own entries and reported at the `imports:` entry first reaching it). A malformed annotation is `BROWSER_EXPORT_ANNOTATION_INVALID` at the kind (import-anchored for a dependency's), `ERR_BROWSER_EXPORT_ANNOTATION_INVALID` at registration. Reader: `browser-export-slot.ts`.
- `x-telo-path-params-for: { template: "/json/pointer", through?: <field> }` — on a map of path variables (a named property declared `type: object`): `template` points, from the enclosing object, at the field holding the path template (an app-relative path or an `http`/`https`/`mailto:` address whose `{name}` variables are whole segments, after the authority), `through` names the field holding it on the declaration a `!ref` there names (written exactly when the field may hold one); an expression at the template field is never expanded, so every entry is unused. Codes `PATH_TEMPLATE_INVALID` / `PATH_PARAMETER_UNBOUND` / `PATH_PARAMETER_UNUSED` at the resource (`ERR_`-prefixed at creation), `PATH_PARAMS_FOR_INVALID` at the kind (`ERR_` at registration). Reader: `path-params-slot.ts`; guide `docs/extend/path-templates.md`.
- `x-telo-application-source: { variables?, secrets?, ports?, needs? }` — on a named top-level string property: the value is the source of a child application the resource runs, each key a JSON Pointer to the map feeding that block of the child; the loader follows it like an import's source, and `telo check` refuses a key the child does not declare (`APPLICATION_INPUT_UNDECLARED`), a literal its declaration refuses (`SCHEMA_VIOLATION`), a need of the wrong type or stating less (`REFERENCE_KIND_MISMATCH` / `NEED_FORWARD_INCOMPATIBLE`), and an unresolvable or non-application source with the import codes; a malformed annotation is `APPLICATION_SOURCE_ANNOTATION_INVALID`. Reader: `application-source-slot.ts`.
- `x-telo-widget: "code"` — studio renders a code editor (language from `contentMediaType`).
- `x-telo-provides-zone` / `x-telo-requires-zone` / `x-telo-violates-zone` — execution zones, with the closed zone attributes `atomic`, `idempotent`, `noSuspend`, `replayed` (each value is the author's reason). A requirement at the schema root (the whole resource must run inside the zone, not one field) is read by the controller with the field-less `ctx.requireZone()` / `ctx.findZone()`. Spec: `kernel/specs/execution-zones.md`.
- `x-telo-context-parameters-from` / `x-telo-returns-from` / `x-telo-unbound-calls` — a function body's CEL context is its parameters alone (it replaces the kernel globals), its result is checked against `returns`, and a site nothing binds refuses module calls (`FUNCTION_CALL_UNBOUND`).
- `x-telo-type` — what a value IS: `Telo.TcpPort`, `Telo.UdpPort`, `Telo.Uint64`, `Telo.Bytes`, `Telo.Timestamp`, `Telo.Duration`, `Telo.Stream` (`{ name: Telo.Stream, of: … }`), `Telo.HostPath`, `Telo.Url` (`{ name: Telo.Url, scheme: { enum: [postgres] } }`); an instance type is written in YAML in its plain encoding (RFC 3339, `"5400s"`, base64url), and `Telo.Duration` also as an integer number of milliseconds; an ordered instance type takes bounds as arguments in that same form (`{ name: Telo.Duration, minimum: 0s }`, also `maximum`, `exclusiveMinimum`, `exclusiveMaximum`); a named shape is a `!ref` to a `Telo.JsonSchema`. A union with an instance branch must use `anyOf`, never `oneOf`; a union of instance types is decoded by the one whose encoding reads the value. A type whose entry declares `members` (`Telo.Url`: `scheme`, `host`, `port`, `user`, `password`, `path`, `query`) is read in CEL by those members as fields, written as its text or as an object of members it escapes, accepts a CEL `string` (`acceptsText`), and is written as `[redacted]` by every log, trace payload and span attribute when it holds a `password` (`holdsSensitiveMember`, from the entry); a literal it refuses is `URL_INVALID`, a computed one `ERR_URL_INVALID`.

## Host paths and module files

**A path is anchored by what DECLARES it, never by the controller reading it.** `Telo.HostPath` is an absolute path on the machine running the app — in CEL a nominal type of its own, not a `string`: extended with `.joinPath('sub/dir')` (the host's separator at runtime, a `Telo.HostPath` statically), read as text with `string(path)`, and a plain string at a host-path slot is a static error, however it was built: a relative one is refused wherever it is held (`HOST_PATH_RELATIVE` at check, with a `!module-path` repair; `ERR_HOST_PATH_RELATIVE` for a computed one at creation), except in an Application `variables:` / `secrets:` entry typed `Telo.HostPath`, whose env value or `default:` the kernel resolves against the working directory at load — the directory `.env*` is read from, and a double-clicked packaged app's own. Nothing else anchors: a Library's variable is its importer's value (supplied absolute), and a relative `default:` at a host-path node in a kind's schema or a Library variable is `HOST_PATH_RELATIVE` at the declaring doc — a blueprint's host-path field is required, and the consuming app supplies it from its own host-path variable. A string expression at a host-path slot is `HOST_PATH_UNTYPED_SOURCE` (or `HOST_PATH_RELATIVE` when its text starts with a relative literal), at a resource field and where an import supplies `variables:`; a relative literal an import passes is `HOST_PATH_RELATIVE`; a value of undeclared type (`dyn`) is left to the runtime's refusal at creation. A stdlib slot holding a path on the host declares `x-telo-type: Telo.HostPath` — `Http.Static.root`, every Fs kind's `cwd`, `SQLite.Connection.file` (`anyOf: [{const: ":memory:"}, HostPath]`), `DurableJournalFile.Journal.directory`, `BlobFs.Store.root`.

**A host path may say what it names**: `x-telo-type: { name: Telo.HostPath, entry: directory | file }` — a token argument found by the parameter's `hostEntry` flag in the value-type data, never by its name; omitted means either, an absent path is never refused (what uses it may create it). A `!module-path` naming the other kind (the loader asks each source's `ManifestSource.entryAt` and stamps what it found on the tag), a variable declared with the other `entry` read into the field, and an import passing one to a library input declaring the other are `HOST_PATH_ENTRY_MISMATCH` (at a call's `inputs:` the generic `CEL_TYPE_ARGUMENT_MISMATCH`); a token outside the vocabulary is `X_TELO_TYPE_ARGUMENT_INVALID`. The kernel refuses an existing path of the other kind when it creates the resource (`ERR_HOST_PATH_ENTRY_MISMATCH`; one the filesystem will not answer for is `ERR_HOST_PATH_UNREADABLE`) and an Application variable declaring `entry` at load. Declared by `Http.Static.root`, the Fs `cwd`s, `DurableJournalFile.Journal.directory`, `BlobFs.Store.root` and `Telo.DurableDirectory.path` (`directory`), and `SQLite.Connection.file` and `TesseractModel`'s `data` (`file`). Both kernels refuse at creation by one set of vectors (`analyzer/host-path-conformance/`), the Rust kernel also refusing a relative literal there, since its analysis has no host-path pass.

**A host path may say what media type its file holds**: `x-telo-type: { name: Telo.HostPath, entry: file, mediaType: image/png }` — a token found by the parameter's `hostMediaType` flag, a key of that parameter's `signatures` in the value-type data (hex patterns of the file's leading bytes, `??` any byte; `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `application/pdf`), one with none `X_TELO_TYPE_ARGUMENT_INVALID`; only the head is read, never the size; a directory holds none; omitted means any, an absent path is never refused. A `!module-path` whose head carries another type (the loader reads it through `ManifestSource.readHead` beside `entryAt` and stamps it on the tag; a source without it leaves the file to the runtime), at a resource field or a need parameter, a variable declared with another `mediaType`, and an import passing one to a library input declaring another are `HOST_PATH_CONTENT_MISMATCH`, naming the path, the type found (or that none known matched) and the one declared; the kernel refuses the same at creation, after the entry check, and an Application variable at load (`ERR_HOST_PATH_CONTENT_MISMATCH`), by the same conformance vectors in both kernels.

`!include-text` (→ string) and `!include-bytes` (→ `Uint8Array`) embed a file that ships with the module; `!module-path` (→ `Telo.HostPath`) names a file or DIRECTORY that ships with it by location, resolved to its absolute path on disk. Paths are module-root-relative literals confined to the module, never relative to the declaring file; resolution happens at resource creation. `telo publish` / `telo package` carry what a tag claims with no `files:` entry — a `!module-path` directory is everything beneath it — and refuse a claim naming nothing (`MODULE_PATH_NOT_FOUND`) or an empty directory (`MODULE_PATH_EMPTY`); a claim naming nothing — an `!include-*` file (`INCLUDE_FILE_NOT_FOUND`) as much as a `!module-path` — is also reported by every host that loads from a filesystem and refuses `telo run` / `telo install` at load: the loader asks each module's `ManifestSource.entryAt` (`file`, `directory` or nothing) and stamps what a single-claim tag names on it, for the entry and every module it reaches through a filesystem-path import, counting a path its own `sources:` block stages as a module file as present, as release planning from pins also does — while emptiness stays a publish/package refusal only. Details: `templating/nodejs/CLAUDE.md`.

## CEL values (`!cel`, `!interpolate`)

A computed value is written `!cel` and yields a typed value (`!cel "variables.port"`). Text with values embedded in it is written `!interpolate` — literal text with `${{ expr }}` holes, always a string, meaning exactly the CEL join of the text with `string(<hole>)` for each hole (`!interpolate "Hello ${{ variables.name }}!"`); a hole CEL cannot convert is `INTERPOLATION_HOLE_NOT_CONVERTIBLE` (`ERR_INTERPOLATION_HOLE_NOT_CONVERTIBLE` for a `dyn` hole null at runtime). Concatenation inside `!cel` stays valid. `!sql` shares the hole grammar, which reads every quoted literal as the language does, so a hole may hold `}`; `${{ '${{' }}` is a literal `${{`. A plain string holding `${{` is the deprecated untagged spelling: the `untagged-interpolation` migration rewrites it at load (`DEPRECATED_UNTAGGED_INTERPOLATION`) and anything left is `UNTAGGED_INTERPOLATION` / `ERR_UNTAGGED_INTERPOLATION`; text that is literally `${{` is `!literal`.

In scope (in `!cel` and in every hole):

- `variables`, `secrets` — module inputs
- `ports.<name>` — root Application only
- `module.<field>` — the declaring module doc's own `metadata` (`!cel "module.version"`)
- `resources.<name>` — a resource's published reading (after `snapshot()`; republished after `run()`, each `invoke()` and each `setStatus()`); `resources.<name>.status.<field>` is declared observed state, illegal in any startup (compile-eval) field unless `<name>` is a `Telo.Provider` not declared in a `with:` scope Inside a template body it also holds the body's own `resources:` entries, a family as a map by element key, shadowing a module resource of the same name.
- `self.<ref>.<field>` — member access on a referenced instance reads its published state
- `steps.<step>.result` — inside step bodies, typed from the invoked resource's `outputType`, then its kind's, then open
- `inputs` — inside a step body, the call's inputs; in a creation-time field of a `with:` member (a scope its kind declares `x-telo-scope: { regions, openedBy: dispatch }`), the inputs of the call that opened this run, typed by the holder's `inputType`, a sensitive one redacted in what the run's resources and dispatches write. A run is its contract applied to `{}`
- `request` — inside handler CEL (HTTP: query, body, params, headers, path, method)
- `<Alias>.fn(…)`, `Self.fn(…)`, `<ModuleName>.fn(…)` — a module function (`Telo.Callable`), resolved on the parsed tree at compile and bound per module scope at `create()`; a bare name is always the core catalog

A CEL integer is int64 and **needs no cast anywhere** — never `double(...)` to get an integer out of a manifest. A module `variables` / `secrets` entry declared `integer` (holding a value int64 can hold) or `number` is bound in that representation at the root Application and in every import, so `variables.x * 2` runs as checked. A controller reading another resource's declared-integer output, or a config slot fed `!cel "variables.x"`, must accept both representations (`integerInput` from `@telorun/sdk`). Dereferencing a nullable value without a guard (`error != null && error.code`) is `CEL_NULLABLE_ACCESS`.

## Declared runtime requirements (`requires:`)

A top-level `requires:` block on a module doc declares the runtime range the module is verified against: `telo:` (the manifest surface generation, one scale every kernel reports) and `host: { node: … }`. **`requires.telo` is a floor only**, `">=<version>"` or `">=unreleased"` (the telo release carrying the pending telo-line fragments, met only by a `+unreleased` build); an upper bound on it in a module's own source is `REQUIRES_INVALID`, while a published manifest's is still honoured as a restriction of that version. **In a release workspace it is never hand-written**: `telo release floor` measures it by running published CLIs, and `telo release check` fails `REQUIRES_FLOOR_TOO_LOW` / `REQUIRES_FLOOR_TOO_HIGH` when it drifts; a module the oldest CLI that reads `requires:` accepts carries none. Everything measurement cannot see — a ceiling found after publish, a floor the static check cannot see (a controller needing a runtime feature), a Node bound — is a top-level **`restrictions:`** entry `{ versions?, requires, reason }` (`RESTRICTIONS_INVALID`): it narrows the range of the declaring version and, with `versions`, of earlier ones, and a later version speaks for earlier ones at selection. Bounds use explicit comparators — `^`/`~`, a bare version, `||`, hyphen ranges and wildcards are rejected, and an upper bound must name a release that exists. An older runtime reports `MODULE_REQUIRES_NEWER_RUNTIME` and a newer one than a ceiling allows `MODULE_REQUIRES_OLDER_RUNTIME`, each suppressing every other diagnostic from that module; a malformed block is `REQUIRES_INVALID`. A module whose controllers return effect chains needs telo `>=0.82.0`: that is a `restrictions:` entry wherever the measured floor does not already imply it. The Rust kernel reads no `requires:`, and `cli/rust` owes `telo release floor` as it owes `telo publish`. Guide: `docs/extend/declaring-runtime-requirements.md`.

### Changing the grammar — MANDATORY

**A surface change is only half done until the modules that adopt it carry a measured floor.** Widening what a manifest may say — a new annotation, a new SHAPE an existing annotation accepts, a new key on a built-in doc, a new field on a shared fragment — makes every module that uses it unreadable to every already-released telo, which blames the module's author for a version skew. `requires:` converts that into one `MODULE_REQUIRES_NEWER_RUNTIME` naming the cause.

So, on the same change that widens the surface, **run `telo release floor`**. It finds which modules' own files an older analyzer rejects by executing the published CLIs, writes `>=unreleased` where no published telo reads the syntax yet (`telo release apply` turns it into the surface of the line version it plans), and writes all or nothing. Do not hand-write or forward-declare a bound, and do not verify by reading: the execution is what the command does, and `telo release check` re-verifies it.

**Do NOT add a requirement because a module's kinds merely EXPOSE the new syntax to consumers.** A field added to a kind's schema is delivered in that module's own artifact, so the module is readable by an older analyzer and measures none; the *app* that writes the new syntax is what needs the floor. `Assert.Events` gaining a `times:` property is this case, while `Sql.Transaction` adopting the zone-attribute object form is the other. A requirement measurement cannot see (a runtime feature, a Node bound) is a `restrictions:` entry with its reason.

**A dependent takes its siblings' floors, by rule rather than by the walk**: no published CLI gates a relatively imported sibling's `requires:`, so measurement cannot see it. `telo release floor` writes a module's floor as the highest of its measurement and the floors of every sibling it imports by relative path, transitively (`>=unreleased` the highest, no floor the lowest), and `telo release check` holds each floor to the same value.

A PR or push to `main` runs the Linux jobs plus `macOS: core unit tests` and `Windows: core unit tests` (analyzer, kernel and CLI unit tests only); the full macOS and Windows unit and manifest jobs, Bun and the Docker-image manifests run only on a PR or push to a `release/*` branch, and on `main` they are skipped — except for a PR labelled `full-ci` or whose head commit message holds `[full ci]`, which runs everything as a release would. 2. Documentation matches the current code. If code changed, docs must be updated.

## Manifest descriptions — MANDATORY

`metadata.description` on a `Telo.Library` and on every kind doc (`Telo.Definition` / `Telo.Abstract`) is **hub search text**: the hub embeds it for semantic search, so it is read by someone who does not yet know the module exists. Write it for that reader, not for a maintainer.

- **Say what it does, in terms of the problem it solves.** Lead with the capability and the vocabulary a searcher would type (locks, leases, retries, pagination, idempotency, …).
- **Keep it to one paragraph** — roughly 40–60 words. It is embedded as a single vector; a long multi-paragraph text dilutes it. Rationale, design history and trade-offs belong in `docs/` and in YAML comments above the doc, never in `description`.
- **No kind names, no capability names, no "the X abstract".** The kind and capability are already structured metadata on the doc. `The KvStore.Store abstract — a durable store…` → `Durable key/value storage…`.
- **No implementations, no backend names.** A generic module must not name the modules that extend it (`backed by Redis SET NX` / `kv-store-sql`); that coupling is backwards and pollutes search hits for the generic kind. Backends describe themselves.
- **No contrast with sibling modules.** `Cache.Store is also a key/value store, but…` reads as noise to a searcher and drags the sibling's terms into this vector. State this module's own guarantee positively.
- **No wording that only makes sense against history.** `NON-EVICTING`, `unlike before`, shouting caps for emphasis. Say `records live their full TTL and are never dropped early`.
- **Kind descriptions state the operation and its contract** — inputs, outputs, and what a failure/edge return means — in two or three sentences. See `modules/collection/telo.yaml` and `modules/kv-store/telo.yaml` for the target shape.
- **A field's `description` is one or two sentences:** what it is, plus any constraint or edge behaviour the schema can't state (what an empty value means, when it is ignored). Rationale, examples and design history go in the module's `docs/`. A YAML comment holds only a non-obvious why, in at most three lines; anything longer goes in `docs/`.
- **Whenever you edit a manifest for any reason, trim its descriptions and comments to this rule across the whole file**, moving what you cut that is worth keeping to `docs/`; never drop a constraint to make a description shorter. Reading one is not a trigger.

## Benefits ledger — MANDATORY

`docs/guides/what-you-get.md` lists the features a Telo author gets without writing them, compared with a **typed framework** — TypeScript, Go or Java with its usual libraries, not bare Node. The list grows with the code. **A change that gives authors a new feature for free adds its entry in the same change**, never as a follow-up.

- **An entry is a feature an app author would ask for by name** — request cancellation, graceful shutdown, safe retries, schema migrations — never a runtime mechanism (undo frames, init discarding, an internal error code). A mechanism that serves a feature extends that feature's entry instead of getting one.
- **It qualifies only if a typed framework leaves it to the author.** A check that fixes a problem only YAML or CEL creates (a name CEL would misparse, an expression in a field nothing evaluates, editor support inside `!cel`), or that a type checker already gives (typed reads, null checks, rename), gets no entry. Neither does manifest-surface churn (`telo migrate`).
- **Where it goes:** under **Telo itself** when every application gets it whatever it imports; under its domain in **Standard library** when a module provides it; under **For module authors** when only someone publishing modules needs it.
- **Format:** a list item — a bold feature name, then one or two sentences on what you get, naming what an author types (manifest keys, env vars, CLI commands, kind names). **No diagnostic codes**, `ERR_` ones included: say when a mistake is caught ("refused before the app runs", "refused at start") instead of what the check is called. Add the contrast ("no cancellation token passed through every function") only where it is not obvious, and never as one language's API (`parseInt`, nodemon, `__dirname`). Never source paths or function names.
- One entry per feature. If one already covers it, extend that entry rather than adding a near-duplicate.
- No absolute claim ("never", "every", "cannot") beyond what a test pins; scope it to what is checked ("refuses the unsafe changes it detects").
- Place a new entry by how often authors ask for it within its group, never simply at the end. No scores.
- Internal refactors, bug fixes and stdlib additions that bring no new feature add nothing.
- The site's "For developers" page (`/for-developers`) shows a curated subset of the ledger: every card there corresponds to a ledger entry and says nothing the entry does not, and a card no entry backs is not allowed. Positioning (Git-native, no boilerplate) belongs in the page's intro, not in a card.

## Module metadata

The `metadata:` block on a module doc carries `name` (the only field anything resolves against) plus descriptive `version`, `description`, `repository`, `homepage`, `documentation`, `license`, `categories`, `deprecated`; a near-miss of a known key is reported (`licence:` → `license`). There is deliberately no `authors` / `maintainers` field. **`metadata.deprecated: { reason, replacedBy? }`** is legal on a module doc and on any kind doc: on a kind, `replacedBy` is an alias-qualified kind resolved through the file's own `imports:`; on a module, a module ref. Declaring a resource of a deprecated kind is a `DEPRECATED_KIND` warning at the use site. Which kernels can host a kind is derived from its `controllers:` PURLs, never declared.

## Controller delivery

A `Telo.Definition` names its controller with PURL candidates:

- `pkg:telo/local/js?path=./nodejs/<module>.mjs&local_path=./nodejs/src/index.ts#<Export>` — **bundled**: the controller ships inside the module's own artifact. **This is how the standard library delivers.** A module is ONE bundle: `nodejs/src/index.ts` re-exports one namespace per kind, and each kind selects its export by `#fragment`.
- `pkg:npm/@telorun/<pkg>@<ver>?local_path=./nodejs#<export>` — a published npm package; no module in this repo uses it. Don't add new ones.
- `pkg:cargo/<crate>?local_path=./rust#<entry>` — a Rust controller crate, built on load from a source checkout.
- `pkg:telo/local/napi?path=…&os=…&arch=…[&libc=…]` / `pkg:telo/local/dylib?path=…&os=…&arch=…&abi=telo-<n>` — a prebuilt native controller in a per-platform controller layer: the Node kernel opens `napi`, the Rust kernel `dylib`. In a checkout its file is staged by `sources:` (below), fetched on first use when missing or stale, and verified against its pin before it is opened.

- **The kernel builds the bundle** — from source on load in development (no build step), and through the same builder on publish. A module's own `build` script only type-checks (`tsc -p tsconfig.lib.json`). Never commit `nodejs/*.mjs`, and never re-add an esbuild step.
- `modules/<name>/nodejs/package.json` is private (`@telorun/<name>-build`) and never published.
- `@telorun/sdk` stays external; a sibling module's code is reached through its `exports.code:` specifier, never inlined.
- `files:` lists what the manifest cannot otherwise name; the controller entry is never restated there.
- A dependency that resolves an asset beside its own module URL cannot be inlined.

Full mechanics: `modules/CLAUDE.md`.

## Layered module artifacts

A published module is one OCI artifact of several layers — `manifest`, per-selector `controller`, `library`, `native` and `browser`, `assets`, `common` — addressed by the `layers:` index in the published `telo.yaml`, which the import pin covers. A `browser` layer holds the built `exports.browser:` entries of one selector (`format: esm` plus the entry's `abi`); no kernel imports it, and a cache warm always includes it. A host materializes only the layers its selector (`format` + `os`/`arch`/`libc`/`abi`) needs. **A library whose manifest lies inside the published module's directory ships inside its artifact**: its import stays relative and pinned (`./chat#sha256-…`), its `telo.yaml` rides in the parent's manifest layer, its own `layers:` index names blobs pushed into the parent's repository, and the runtime reads it as `oci://<host>/<repo>@sha256:<parent digest>/<path>`, materialized inside the parent's directory; a library inside another module's directory imported from outside it is refused at publish (`import_nested`). Digest-addressed cache entries are spelled `sha256-<hex>`. Spec: `kernel/specs/module-artifact.md`; details: `kernel/nodejs/CLAUDE.md`.

- **`native:`** on a module doc names each platform-specific file a controller opens by name (`{ name, format, os, arch, libc?, abi?, path }`), shipped in the `native` layer of its selector and reached through `ctx.resolveNativeFile(name)`.
- **`sources:`** says where every staged file comes from — `{ version, url, archive: tar.gz, notices, entries, build? }`, each entry a file (`upstream`, `member`, pinned `sha256` + `executable`) or a link (`target`), and for files built in this repo `build: { cargo: <crate dir>, inputs: <digest> }`. An entry stages a `native:` path, a platform-qualified controller `path=`, a file an `assets:` pattern selects, or a notice. `telo release stage [--pin]` fetches every entry and pins it; a kernel reading a source checkout fetches a missing or stale file on first use (verified against its pin, never read unpinned), and reads no native or module file of a module whose block does not read. It is removed from the published `telo.yaml`.
- Guide: `docs/extend/native-files.md`; `telo check` codes `NATIVE_*` / `SOURCE_*`.

## Versioning & releases — MANDATORY

**The whole repo is intentionally pre-1.0, and staying pre-1.0 is the goal.** Breaking changes are released as **minor** bumps on purpose — npm packages, crates, images, charts and Telo modules alike. A documented breaking change shipped as a minor (an `Added` fragment describing the break) is the convention working as designed, **never** a versioning defect. Do not flag "breaking change shipped as minor" in reviews. `release.maxBump: minor` in `telo-workspace.yaml` enforces it (`MAX_BUMP_EXCEEDED`) — anything that would bump to 1.0.0 is the error, not the minor.

**One release system for every artifact: `telo release`** (`@telorun/release`, `release/nodejs/`, MIT; guide `docs/extend/releasing-modules.md`, marker `docs/guides/workspaces.md`).

- **A unit is one component with one version, one changelog and one fragment target** — listed in `release.units` of `telo-workspace.yaml`, keyed by its workspace-relative path. Each package it ships is an anchor of an ecosystem (`npm`, `cargo`, `docker`, `helm`, `telo`): `kernel` is one unit with an npm package at `nodejs` and crates under `rust`, `apps/k8s-runner` one unit with an npm package, an image and a chart, so a change confined to a crate, a Dockerfile or a chart releases the unit with one changelog entry. Whether a unit bumps is decided by the digest of what it ships, never by the paths a change touched; edges (including code inlined into a bundle, through a unit's `metafile:`) are never declared by hand.
- **Every change to a released unit ships a fragment**: `telo release add --unit <path> --kind <Kind> --body "…"` (`.changes/pending/*.yaml` — one file, several units, one body, the kinds `Added | Changed | Deprecated | Removed | Fixed | Security`), addressing a polyglot component by its parent directory (`--unit kernel`). Studio and the Docker runner need one too. **Never write or edit a fragment file by hand** — to change one, delete it and run `telo release add` again: the command serializes the body safely, while a hand-written plain YAML scalar holding `: ` or quotes stops parsing as a string and fails `telo release check`. **A fragment's body lands verbatim in the changelog of EVERY unit it names**, so a fragment names several units only when the one body is true of each as written. A missing fragment is the `CHANGELOG_ENTRY_REQUESTED` warning, and the unit still releases as an unattributed patch. `Changed` and `Removed` induce a major bump and are refused under `maxBump: minor`: a breaking change is written as `Added`, with the break described in the body. Never hand-edit a unit's version.
- **The telo version line** is `release.groups.telo`: the units `kernel`, `sdk`, `cel`, `templating`, `analyzer`, `message-format`, `cli`, `packages/language-server` and `packages/ide-support` share ONE version, the manifest surface generation `requires: telo:` is written against. **Membership test: a unit belongs iff its content is bound to exactly one telo generation.** A contract spoken ACROSS generations (`@telorun/editor-protocol`, a host package) and `@telorun/release` stay off the line. Rust twins are anchors of their unit, not a separate rule: a change confined to a crate, `sdk/rust/abi` or `telo-desktop-host` releases the line, and every anchor carries its unit's version (`UNIT_VERSION_MISMATCH` otherwise), except `telorun-abi`, a declared payload of `sdk` that is never versioned (the ABI generation is). Images and charts are `docker` / `helm` anchors; `ide/vscode` a declared unit.
- **A build never plans.** Every build reports its recorded version — `nodejs/package.json` of the analyzer unit — as `V+unreleased` (the engine handshake, `Kernel.Starting`, the built-in vocabulary archive, the CEL module key); only a package's `prepack` embeds exactly `V`, and its `postpack` restores the tree byte-identical, so a published package reports its own version — `@telorun/language-server` included, whose `prepack` refuses a tarball whose engine does not report exactly its package version, so editors never mistake a `+unreleased` engine for a published one; the editor's version catalog never selects a candidate. The surface (`TELO_SURFACE_VERSION`) is the triple of the recorded version. `requires: telo: ">=unreleased"` is rewritten by `telo release apply` to the surface of the `telo` group's planned version, and a `>=unreleased` floor in a plan that moves no telo version fails `telo release check`.
- **Releases are cut, never published from main.** Main publishes nothing. A release is ONE release PR on its branch, `chore(release): version` from `release-version/release/<x.y>`, pushed with `TELO_BOT_TOKEN` so checks start, plus the record PR on main. `Start release candidates` (manual, on main) creates `release/<major>.<minor>` at the commit it was dispatched on and changes nothing on main; `Publish final release` (dispatched at the branch) builds the final release PR itself and replaces an open rc release PR; dispatched at main it skips candidates, refusing what `Start release candidates` refuses. **Candidacy is derived, never stored**: a branch is in candidates while `v<x.y>.0` is absent and its open release PR's head carries no final versions, and Telo's scripts pass `telo release apply --candidate`. A candidate versions each planned unit `<final>-rc.<k>` and publishes npm packages, modules (so an rc tag can be installed and run as its final will be), kernel images and the rest of its channel, with a publication commit like a final; no pointer moves. Tags: `v<line version>` (`-rc.<k>`) only when the telo line moved, else `packages-<x.y>-[rc.]<n>` / `modules-<x.y>-[rc.]<n>`; each moved unit is also tagged `<unit key>@<version>` on the release commit (`telo release tag`), which the links in a published package name (`blob/<unit key>@<version>/…`). **Branch history never merges into main**: after every final, patch, packages-only and module release — never a candidate (`-rc.`) — Publish dispatches `Record release` on main, which rebuilds one PR per line (`release-record/release/<x.y>`, landed by squash) from the live branch's newest non-rc tag, copying each unit's version, changelog and ledger entry and deleting the fragments that tag released, and `Start release candidates` refuses until main records that tag. Every fix lands on main first and reaches the branch as a `git cherry-pick -x` PR. Only the newest `release/*` branch publishes. Every tag of a final, patch, module or packages release sits on its **publication commit** — a branchless child of the merge whose only change is `telo release imports --as=published` over the consumer roots — so pins live only in tags, while every branch imports workspace modules relatively. Shared pointers (npm `latest`, Docker `latest`, Studio pages, Marketplace, GitHub latest, the docs site) move only forward. On main, `telo release check --carried-by <live branch>` drops every fragment the live release branch carries, and coverage of the bot-opened release PR and record PR (`release-version/*`, `release-record/*` heads) is exempt. A workflow on `release/*` runs that branch's own files, so a pipeline fix the branch needs is a PR into the branch; `cut-release.yml` and `finish-release.yml` live on main. Procedure, refusals and recovery: `RELEASING.md`.
- **Publish walks `telo release order`** — one row per unit and anchor in edge order, each dispatched on its `ecosystem` and published from its `path`: npm through `scripts/publish-packages.mjs`, modules through `scripts/publish-modules.mjs`, images and charts from their docker / helm rows (`scripts/image-tags.mjs`, `scripts/publish-charts.mjs`; an image's tag and a chart's `version` and `appVersion` are its unit's version). The unit tags are placed on the release commit and pushed before npm publishes, so a linked file is identical to the publication commit's. A package whose build inlines workspace code declares its bundler `metafile:` on its unit; the inlined units' edges come from it.
- **Prereleases are inert to consumers**: `telo upgrade` and the editor read a prerelease's `restrictions:` only with `--include-prerelease`, the hub indexes final versions only, and during candidates `telo publish` measures a floor equal to the line's surface with the newest published candidate CLI of that surface.
- **A bundled module takes no hand-written version**: it moves when its payload digest does. Coming from changesets, `telo release adopt changesets` converts a setup once.

## Licensing — MANDATORY

Two licenses, split by directory, under one rule: **no MIT package depends on a Sustainable Use package.** MIT covers what an author links against and writes, and the first-party apps built purely from those; everything that loads, checks, edits or runs a manifest stays under the root Sustainable Use `LICENSE`.

- **MIT directories**, each with its own `LICENSE`: `cel/`, `message-format/`, `sdk/`, `templating/`, `release/`, `packages/glob/`, `packages/editor-protocol/`, `modules/`, `blueprints/`, `starters/`, `examples/`, `docs/`, `benchmarks/`, `apps/hub`, `apps/hub-web`. Everything else is Sustainable Use — the analyzer, kernel, CLI, editor packages, runners, studio, authoring agent and `pages`. The telo version line is therefore mixed-license; membership is decided by binding to one generation, never by license.
- **A new dependency from an MIT package on a restricted one is refused**, dev and peer dependencies included, as is a Cargo path dependency. Move the shared code down into an MIT package, or keep the consumer restricted — never relicense a package to make an import legal without asking.
- **Every module root carries `license: MIT` and its own `LICENSE`** beside `telo.yaml` (a new module needs both; the Tesseract generator emits them). The directory-level file is outside the module, and `telo publish` / `telo package` carry only the one at the module root, in the `common` layer. The field states the license of the module's own files; a third-party file staged through `sources:` keeps its upstream license through that entry's `notices`. Test, fixture, starter and example manifests declare no license — a starter becomes its author's own application.
- `pnpm run check:licenses` (CI) enforces all of it; the MIT directory list lives in that script and in the root `README.md`.
