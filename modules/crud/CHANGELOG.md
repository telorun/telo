# Changelog

## 0.24.0 - 2026-10-08
### Added
* Crud.Model: a record's shape for each operation, as four named shapes - schemas.read, schemas.list, schemas.create and schemas.update - shared by Crud.Resource and Crud.Ui. A create body is validated against create and an update body against update; read-one and both writes answer in the read shape, and each list row holds the list shape, while a list is filtered and sorted by what the model's query declares, typed by read. POST and PUT answer with the stored record, taken from the write itself: the id the table assigned and every value it filled in. PUT replaces the columns the update shape declares and leaves every other column as it was. The create route is rendered through the connection's dialect and names only the columns its shape declares. The generated OpenAPI document states each operation's shape, and the id path parameter takes the type read declares. Six rules relate the shapes, each reported by telo check as RESOURCE_RULE_VIOLATED and refused when the model is created as the same name prefixed ERR_: CRUD_MODEL_KEY_UNDECLARED, CRUD_MODEL_KEY_WRITABLE, CRUD_MODEL_WRITE_SHAPE_OPEN, CRUD_MODEL_PROPERTY_NOT_READABLE, CRUD_MODEL_PROPERTY_TYPE_DIFFERS and CRUD_MODEL_UPDATE_REQUIRES_OPTIONAL. A seventh, CRUD_MODEL_FILTER_RESERVED_NAME, refuses a declared filter by a property named limit, cursor or sort, or beginning _telo: a filter is sent under its property's name, and those are the list route's own parameters. Crud.Ui draws the table from list and the filter bar from read, the create form from create and a separate edit form from update. BREAKING: model on Crud.Resource and Crud.Ui takes a Crud.Model, no longer a Telo.JsonSchema - declare the four shapes and name the model. BREAKING: id is declared, required in the read and list shapes and absent from the write shapes; it was implicit. BREAKING: POST and PUT answer with the stored record instead of echoing the request body. BREAKING: a write needs INSERT / UPDATE ... RETURNING (SQLite 3.35 or later, PostgreSQL). BREAKING: a response is validated against its shape, so a stored row the shape refuses is a 500 naming the property; a column holding NULL whose property declares listed values without null is read as a typed property is - left out where optional, the empty value of its listed type where required - instead of null.
* Crud.Model declares the filters and sorts its list accepts, in a required query block: query.filters, each a property with one operator, and query.sort. Breaking: every Crud.Model must add query (empty lists accept none), and the list route refuses whatever it does not declare with a 400 naming the parameter. A filter whose property and operator are not a declared pair answers 'is not a filter this collection accepts', replacing the unknown-property, unknown-operator and operator-does-not-apply messages; a sort by an unlisted property answers 'is not a property this collection sorts by'. id is no longer filterable or sortable unless declared; reading one record by its key is unaffected. Four rules hold query within the read shape: CRUD_MODEL_FILTER_UNKNOWN_PROPERTY, CRUD_MODEL_FILTER_OPERATOR_UNSUPPORTED, CRUD_MODEL_SORT_UNKNOWN_PROPERTY and CRUD_MODEL_SORT_UNSUPPORTED. Crud.Model is a Ui.Collection, and Crud.Ui shows exactly the declared filters and sortable columns instead of one filter per scalar property.
* Crud.Ui takes three optional keys that say how the generated screen behaves: `filters` is the filter bar's whole policy (what is on show, placement, controls, when a change applies, the summary, where state is kept), and `create` / `edit` each hold the `surface` their form opens in, `afterSubmit` and `unsaved`. Each is passed on as written to the generated bar and table, so a key left out takes their default and Crud.Ui declares none of its own; a wrong key, value or kind is reported at the Crud.Ui that wrote it.
* Crud.Ui writes its table create and edit in the object form the ui module now requires ({ form: ... }); the generated screen is unchanged. BREAKING for an ejected screen: a hand-written Ui.Table copied from the expansion listing must change create: !ref <form> and edit: !ref <form> to create: { form: !ref <form> } and edit: { form: !ref <form> }.
* The list route is a collection: limit (1-100, default 25), an opaque stateless cursor, a one-property sort with nulls last and id as tiebreaker, and filters by equality, contains, gt / gte / lt / lte and in, each read by the property's model type; limit, cursor and sort are typed in the request schema, and a bad query is the 400 request-validation envelope naming the parameter. Crud.Ui adds a filter bar, table and create / edit form over a model and a base path, and expands into hand-writable Ui.Filters, Ui.Table and Ui.Form. Every route returns values in the model's declared JSON types, so a boolean is true / false on SQLite; both read routes and the update route run through the connection's dialect. Requires telo 0.112.0 or newer (requires: telo: ">=0.112.0"). BREAKING: GET on the collection answers { rows, total, next } instead of a bare array, and returns at most 100 rows per request. BREAKING: PUT replaces the row instead of updating the columns present - its body is a whole record validated against the full model, as a POST body is, and a property it leaves out is set to NULL; a body missing a required property is a 400 naming it. A write body holds the properties that have a value: a null at a typed property, like a value of another JSON type, is a 400 naming the property, so a property is cleared by leaving it out. BREAKING: a read returns a record valid against the model, on read-one and in every list row, so the record read (less id) is accepted when sent back. A column holding NULL is no longer always null: it is null where the property admits null (its type lists "null", or it declares no type), left out of the record where the property is optional, and the type's empty value where it is required ("" for string, 0 for integer / number, false for boolean, [] for array, {} for object). The empty value is the type's alone and may not satisfy a further constraint on the property (minLength, enum, minimum). A client that tested a cleared property against null must test for its absence.

## 0.16.0 - 2026-09-10
### Added
* A template body now has ONE reference spelling: every `resources:` entry is named by a literal and every dispatch slot is a `!ref` to one. The `{ kind, name }` object form and the CEL-computed entry name it existed to reach are removed — each template instance owns its children in a child context of its own, so a per-instance suffix bought nothing, while a `!ref` is looked up verbatim and so could never name such an entry. `crud` and `sql-repository` are rewritten to it. `http-client` drops the raw-manifest fallback in `Http.Request`: a client is resolved through `ctx.resolveRef` like every other slot, so a reference that does not resolve says so instead of being explained as a rule about scopes. `assert` gains `Assert.Manifest.expect.runFails`, which runs the manifest as well and asserts it fails — pinning a static verdict to the runtime one in a single test.

## 0.9.0 - 2026-08-09
### Added
* metadata.name is now CRUD, so the module contributes its kinds under the `CRUD.<Kind>` canonical prefix instead of `crud.<Kind>` — a name rather than a slug, in the PascalCase form the manifest grammar asks for. Importers are unaffected: a kind is always written through the import alias the consumer picks (`<Alias>.<Kind>`), and the `exports.kinds` list is unchanged. Only a manifest that names the canonical `<module>.<Kind>` form directly — a legacy bare-string `x-telo-ref`, or a diagnostic matched by its text — sees the new prefix.## 0.8.0 - 2026-08-08
### Added
* Every `x-telo-ref` slot now declares what this module does with the target: `use: dependency` (held and read), `call` (control transfers during the invocation and returns), `detached`, `trigger.inbound`, `trigger.consumer`, or `schema` for a slot that only names a shape. Slots that accepted `Telo.Invocable | Telo.Runnable` through an `anyOf` now say `Telo.Executable`, the new built-in parent of both. Wiring manifests are unchanged — this is schema metadata, and it is what lets `telo check` answer whether control reaches a referenced resource, and when.## 0.7.0 - 2026-07-31
### Added
* Data shapes are declared with the kernel built-in `Telo.JsonSchema` instead of `Type.JsonSchema`, so the module no longer imports `std/type` to describe its own contracts. Identical behaviour; `Type.JsonSchema` still resolves for anyone who prefers it, though the `type` module is now deprecated.## 0.6.0 - 2026-07-27
### Added
* Reference slots name their target as an alias-qualified kind (`<Alias>.<Kind>`, `Self.<Kind>`, `Telo.<Kind>`) instead of the `<namespace>/<module>#<Kind>` identity string, so a constraint resolves through this module's own `imports:` map and stays pinned to the version it imports. `metadata.namespace` is dropped — a module's location is the ref it is published under, never anything it declares about itself.## 0.5.1 - 2026-07-27

Kinds that carried no description at all now have one. The README is corrected alongside: reference and CEL syntax the analyzer no longer accepts, unpinned version tags, and examples that named fields or kinds that do not exist.

### Added
