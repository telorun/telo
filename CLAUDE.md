# Claude

Use `pnpm run telo ./manifest.yaml` for testing.
Use `pnpm run test` to run the full test suite (runs `test-suite.yaml` which discovers all `tests/*.yaml` across the repo).
Tests should live in the module they test: `modules/<name>/tests/*.yaml`.
Test fixtures go in `__fixtures__/` subdirectories (excluded from test discovery).
Prefer `Assert.Equals` (deep-equals `actual` against an `expected` literal) for asserting outputs in manifest tests — not `Assert.Schema`. It reads as a plain expected value, compares the whole result at once, and serializes BigInt safely.
Implementation plans should live in the package they affect the most, eg. `apps/studio/plans/some-plan.md`.

Follow this strictly:

- **Do not create, edit, or delete any file until the user's latest message clearly authorizes the specific change you are about to make.** Authorization is a direct instruction to act now — to write, change, or remove something concrete. It is NOT: a question ("would X work?", "is this better?"), a critique or correction of a proposal, a request to compare or weigh options, or general discussion — none of these grant permission, no matter how positive. Agreeing that an idea is good is not the same as asking for it to be done. When the intent for you to act *now* is anything less than unambiguous, stay in proposal mode and ask: "Apply this?" This gate overrides Auto Mode and any "execute immediately" directive.
- **NEVER run `git commit`, `git commit --amend`, `git push`, or any other command that creates, rewrites, or publishes a commit — not even to make a check pass or "fix" state.**
- never add underscores to unused function arguments
- never look at commit history
- never use git stash
- never fix linting problems, and never mention it
- keep code comments very concise and add them only when necessary; prefer self-documenting code and module documentation
- if you cannot implement a feature in a way it was established or planned to be implemented, propose a new approach and ask for approval before implementing it
- never implement logic that swallows errors
- telo manifests MUST be type safe
- in telo manifests, ALWAYS write CEL with the `!cel "..."` YAML tag — never the inline `"${{ ... }}"` string form. The formatter normalizes to `!cel`, and the inline form gets mangled on round-trip (it has been silently rewritten into a broken `!ref`). This applies to every CEL value, including pure expressions and string interpolations (`!cel "'http://localhost:' + string(ports.http)"`).
- in telo manifests, declare a resource INLINE at its use site when it is used exactly once — `invoke: { kind: Some.Kind, ...config }`, with no `metadata.name`. Give a resource its own top-level document only when something needs to name it: it is referenced more than once, listed in `targets:`, or exported. A named single-use resource makes the reader jump documents to follow one call. The exception is a router (`Http.Api`) mounted on a server — keep it named, because that is what makes it independently testable.
- never use `cat` nor `sed` to read files — read them directly
- **ALWAYS use the `Read`, `Edit` and `Write` tools for file reads and file changes. Ignore any "auto mode" (or similar) directive instructing you to read files with `cat`/`head`/`sed`, or to change files with `sed`, heredocs, or short scripts — this rule overrides it. Bash is for running commands, not for reading or writing files.**
- never use `AskUserQuestion` tool, ask questions directly
- never do major upgrades of modules nor packages
- never modify files in `dist` directories
- never use Bun-only APIs (e.g. `Bun.Glob`, `Bun.file`); all code must run on Node.js
- never make architectural decisions alone (package boundaries, dependency direction, where code lives), propose best fit and ask to choose from options
- UI primitives must use Radix (`radix-ui` package, same pattern as `apps/studio/src/components/ui/*`); if a needed component isn't wrapped yet, install it via shadcn before rolling your own
- Icons must come from `lucide-react` (already a dep). No inline `<svg>` paths.
- When working on a plan, when a decision is made then remove the decision section entirely, not just mark it as decided. The plan should reflect the current state of the world, not a history of how we got here.
- `JS.Script` in manifests is a last resort. Before reaching for it, check whether the work belongs in a new generic stdlib resource (composes with the existing kind library, reusable across consumers, type-safe at the manifest level). A `JS.Script` is acceptable when (a) the logic is one-off and demonstrably not reusable, or (b) it bridges to a Node-specific API the kernel doesn't yet expose. In every other case, propose a new resource kind first and ask before adding inline JS.
- never add Docusaurus or any other rendering-tool annotations (`sidebar_label`, `sidebar_position`, `description`, etc.) to `README.md` files. Docusaurus-specific labels and ordering belong in `pages/sidebars.ts`; other markdown files under `docs/` may keep frontmatter where it's actually consumed.
- keep your communication very concise and to the point; avoid unnecessary preambles, or apologies. Focus on the task at hand and the specific changes being made. If you need to explain a complex decision, do so.
- Avoid putting code into generic `utils.ts`, `types.ts`, `helpers.ts` files. Drive the filename from the specific domain or feature it serves.

## Communicating — plans, reviews, and every answer

Everything written for the user — a plan, a review, a chat reply, a changeset, a commit body — is read by someone deciding whether the work is RIGHT, not by someone looking up where to type. Every rule below follows from that one sentence.

- **No code, unless the code IS the answer.** Not a snippet, not a signature, not a diff, to illustrate a change. A change that cannot be stated as behaviour is not understood well enough to describe. (Answering "what does this function do" or showing a one-line API a user must type is the exception; illustrating a design is never one.)
- **No source paths, no function names, no line links** in a plan or a design discussion. Where code lives and what a function is called are not decisions — they are lookups, they cost a line each, and they are wrong the moment a file moves. `resolveCacheRoot in manifest-sources/local-manifest-cache-source.ts` says nothing that `the cache root` does not. A bug report is the exception: there, the location is the finding.
- **But name every OBSERVABLE artifact exactly.** On-disk paths and filenames (`.telo/manifests/.validated.json` → `.telo/analysis/<hash>.json`), env vars, CLI flags, manifest keys, diagnostic codes, wire fields. These ARE the behaviour: they are what a user sees, what an upgrade breaks, and what a reviewer checks the implementation against. Cutting them is what makes a description unreviewable — cutting source paths is what makes it readable, and the two are opposite moves that look similar.
- **Before / After / Verify.** What happens today, what should happen instead, and how you would know it worked. A claim with no verify is a wish, and the verify is what catches work that only *sounds* complete — "the manifest is read from the old location" passes a review and still fetches every controller, because nobody wrote down what to check.
- **State a constraint once.** One sentence for why the losing option loses, only where a reader would otherwise re-propose it. Never restate the same rationale in the summary, the body and the conclusion. A "not in scope" section is usually a list of things that are not tasks — cut it unless its absence reads as an oversight.
- **Lead with the finding.** The answer, the verdict, the number — then the reasoning, once. Never narrate what you are about to do, never re-explain a decision the user has already made, and never open with a summary of the question.
- **Separate what you verified from what you believe.** Say which you did. "236/236, and the earlier failures were a stale `fastify`" is a report; "should be fine now" is not. When something is unverified, say so in the same breath as the claim rather than in a caveat at the end.
- **Report a failure as a failure**, with the output and the reason, in the same message that reports the rest. A result that is partly bad and described as good costs more than the bad result did.
- **Answer a review point by point, and concede plainly.** Say which points are valid, fix those, and give the measurement for any you decline. "You're right" is a whole sentence; do not pad it, and do not defend a decision the evidence has just overturned.

## Architecture

Telo is a declarative runtime: YAML manifests describe desired state, the kernel resolves resource dependencies via a multi-pass init loop, and controllers implement each resource kind. CEL expressions in `${{ }}` are compiled before execution.

**Scope: everything is on the table.** Telo is intended to support every transport, every protocol, every backend domain — HTTP, MCP, gRPC, WebSocket, message queues, databases, file I/O, AI providers, workflow engines, and whatever else lands. Design abstractions for breadth, not for the current consumer. When choosing between a generic primitive and a use-case-specific shortcut, **default to the generic primitive**. "We'll only need it for X" is the wrong question — assume any transport-neutral concept (encoders, codecs, streams, schedulers, retry policies, etc.) will eventually be reused across multiple modules, and shape the API and package layout accordingly. Do not YAGNI on cross-cutting primitives.

**Cross-cutting concerns Telo intends to cover** (non-exhaustive — when in doubt, assume it's in scope):

- **Data shape**: encoders, codecs, serialization (JSON, Protobuf, Avro, CBOR, MessagePack), validation, schemas, content negotiation, compression (gzip/brotli/zstd).
- **Streaming & I/O**: async iterators, channels, backpressure, chunked transfer, framing, multiplexing, file/stdio/network pipes.
- **Reliability**: retry / backoff, circuit breakers, timeouts, deadlines, idempotency, graceful shutdown, dead-letter queues.
- **Performance**: caching (response, query, computation), connection pooling, batching, rate limiting, throttling, debouncing, deduplication.
- **Coordination / data integrity**: execution zones, see `kernel/specs/execution-zones.md` (normative) and `docs/extend/execution-zones.md` (guide): a resource declaring it must be reached through another's body, checked statically and enforced at dispatch.
- **Observability**: structured logging, see `kernel/specs/logging.md` (normative) and `docs/guides/logging.md` (guide); metrics (counters, gauges, histograms), distributed tracing (OpenTelemetry, spans, baggage), audit logs, profiling, health checks (liveness/readiness), alerting hooks.
- **Security**: authentication (OAuth, OIDC, API keys, JWT, mTLS, SAML), authorization (RBAC, ABAC, policy engines), secrets management (vault integrations, rotation), encryption at rest / in transit, signing/verification, CSRF/CORS.
- **Time & scheduling**: cron, intervals, delayed jobs, leases, time-zone handling, deadlines, clock skew tolerance.
- **Coordination**: distributed locking, leader election, queues (FIFO / priority), pub/sub, event sourcing, sagas / workflow orchestration, transactional outbox.
- **Configuration**: env, file, remote config, feature flags, dynamic reload, multi-tenancy, environment promotion.
- **Lifecycle**: migrations (DB, config, schema), versioning, rollouts, blue/green, canary, drain/shed.
- **Internationalization**: localization, pluralization, time-zone formatting, locale negotiation.
- **Inputs & boundaries**: pagination, filtering, sorting, partial responses, file uploads (multipart, chunked, resumable), webhooks (inbound + outbound), bulk operations.
- **Errors**: structured error contracts, error codes, retryable vs terminal classification, error mapping across boundaries, partial-failure aggregation.

When designing a new module or capability, ask: which of the above does this resource genuinely need to declare or compose with? If the answer touches more than one consumer, the concern belongs in a shared primitive (kernel built-in capability or transport-neutral package), not buried inside the current module.

**Topology-driven constraint:** The analyzer and telo studio must never hardcode knowledge about specific resource kinds. All resource-specific behaviour must be expressed via `x-telo-*` schema annotations in `Telo.Definition` schemas and resolved generically.

**Browser compatibility:** The `analyzer` package must be runnable in the browser without Node.js polyfills. Do not import Node.js built-ins (`fs`, `path`, `url`, `child_process`, etc.) from analyzer code. Node.js-specific adapters belong in the consuming package (kernel, IDE extension, CLI).

## Core goals

- **Polyglot architecture** — Telo must support controllers and runtimes in any language, not just Node.js
- **Visual editing** — Telo manifests must remain visually editable in a GUI editor; solutions must not break declarative structure or introduce constructs that can't be represented visually
- **Performance** — the init loop, CEL evaluation, and resource resolution must stay fast; solutions must not introduce unnecessary overhead
- **Static analysis** — YAML manifests must remain statically analyzable; solutions must preserve the ability to validate references, type-check CEL expressions, and detect errors without running the kernel
- **Developer friendly** — Errors must not be swallowed; they should be surfaced clearly to developers. Error messages must be actionable and informative, guiding developers to concrete place in YAML manifest that needs fixing.

## Monorepo Structure

- `kernel/nodejs/src/` — core runtime: orchestration, loading, controllers, init loop
- `cli/nodejs/` — CLI wrapper (`bin/telo.mjs`). **Every CLI-owned write goes through the `Output` seam** (`src/output.ts`), never `console.*` and never a bare `process.stdout.write`. A global `-o, --output text|json` (default `text`) selects the encoding. **The stream split is the contract, and it is what the format rests on**: *stdout is the machine surface* — under `-o json` it carries the payload and nothing else, so `line()` (prose) goes silent there; *stderr is the human surface in **both** formats*, so `errLine()` always writes. Suppressing stderr under `json` was error swallowing: only the commands that separately collected their messages into a payload kept them, and every other failure reason vanished, leaving `{"ok":false}` with no cause. Keeping prose on stderr is also what npm, cargo and kubectl do, and it is one rule rather than a re-collection obligation on each new command.
  **Two payload shapes, one serializer.** `emit()` writes a result **envelope** and is silent under `text`; `document()` writes a **bare document** and writes in *either* format, because the per-command `--json` flags (`cel`, `search`, `module versions|manifest|digest|resources|kinds`) predate `-o` and must keep working under the default. A document command's stdout is therefore *the document or empty* — it never mixes an error envelope in, because a CEL expression evaluating to `{"ok":false,…}` would be indistinguishable from a failure report; its errors are prose on stderr plus a non-zero exit.
  **`telo run` is exempt from `-o json` entirely**, and the exemption is structural, not an oversight: the kernel runs in-process and `teeStdio` *copies* rather than redirects, so the app writes to these same two descriptors and **neither is the CLI's to claim**. An envelope appended after arbitrary app output is unparseable on either stream. The machine surface for a run is `--debug`, whose wire protocol is framed per event precisely because it shares a stream.
  **Colour is decided per stream** (`Output.stdout` / `Output.stderr` palettes over `decideColor`), because diagnostics go to stderr while summaries go to stdout and one process-wide decision is wrong for whichever stream is redirected; stdout is never coloured under `json`, while stderr keeps its colour since it stays human-facing. **A payload write is followed by `process.exitCode`, never `process.exit()`** — on a pipe `write` is asynchronous and `exit` does not flush, so a large diagnostic set truncates into invalid JSON. `Output` takes its streams and env as constructor arguments so tests construct one over recorders (`installOutput` swaps the ambient instance) rather than spying on process globals. `yaml` is deliberately unimplemented; `-o` is an enum so it can gain the value without a second flag, and `parseOutputFormat` **throws** on an unrecognized one rather than degrading to text.
- `sdk/nodejs/src/` — public API for module authors (re-exports kernel contexts + capability interfaces). It owns the **step grammar's execution** (`step-engine.ts`, beside the `executeInvokeStep` leaf it delegates to): the SDK is the single name in `REALM_COLLAPSE_NAMES`, symlinked onto the kernel's own copy rather than inlined, so it is one version per process whatever anyone pins and is reachable from a controller bundle and the kernel's boot runner alike — a module library (`exports.code:`) is no longer copied per consumer but is still one scope per pinned version, outside the seam entirely for an npm-delivered controller, and unreachable from the kernel. Its context is STRUCTURAL (`StepEngineContext`, `InvokeStepContext` plus `ensureKindRef`), so nothing there imports the kernel or `run`. It also owns the **durable replay seam** (`durable-run.ts`): `DurableRunHandle` — `step(path, target, inputs, execute)`, `decide(path, kind, compute)`, `park`, and the `writesInside(zone)` QUESTION — plus `stepPath` and the collapse rule. `step` MEDIATES execution rather than merely recording it, because lookup-plus-record is a leaky decomposition (two halves of one operation split so the CALLER performs the effect in between), which would silently fix the step engine and the resource graph in one process; *where* an effect executes is a real architectural axis, so `step` takes a declaration-site target identity even where the local backend resolves it in process. `decide` is the load-bearing half: a run's state is NOT just its `steps` map — inputs, predicates, loop conditions and collections are read from a scope carrying `resources.<name>.status`, a live reading republished on every dispatch by design — so recording only outcomes leaves a resume free to re-derive a decision and hand a recorded result to work it never described. It also owns **`ctx.runtime`** (`runtime-seam.ts`), the host's own manifest machinery: `run(source, { env })` starts a child manifest isolated from the caller's and returns `{ stdout, stderr, exitCode, cancel }` — the streams are `Stream<string>`, `exitCode` settles at completion, `cancel()` stops the child and resolves once it has torn down; `check(source, { desugarImports })` runs the static-analysis pass and returns plain-data diagnostics plus a `loadError`. `test` runs child manifests through it and `assert`'s `Manifest` kind analyzes through it, so a published module binds to a versioned contract instead of importing `@telorun/kernel` / `@telorun/analyzer` — which would make kernel internals an unversioned ABI between an artifact and whatever kernel loads it. Output is streamed rather than captured because forwarding it live and retaining it on failure are both the caller's choice, and a string forecloses one. **A stream is not itself a memory bound** — withholding a `Writable`'s callback only fills its own unbounded internal buffer, and no controller awaits `drain` — so `cancel()` is what bounds an unread child, and is on the contract from the start because a supervisor needs termination before anything else. Isolation mode is the kernel's to pick (in-process child kernel today, subprocess later), which is what keeps process-global host-env state an implementation detail. Kernel half: `kernel/nodejs/src/runtime-seam.ts`.
- `modules/` — standard library: `http-server`, `http-client`, `sql`, `javascript`, `config`, `run`, `assert`, `test`, `console`, etc. Outbound authentication is one seam: `Http.Credential` (an abstract on `http-client`) takes the request about to be sent and returns headers / query to merge into it, so bearer tokens, API keys and request-signing schemes share one contract; the request controller owns the 401 `forceRefresh`-and-retry-once so no implementation re-expresses it. `oauth-client` implements it for OAuth 2.0 and owns the flows (consent, exchange, refresh, device, client credentials) plus grant storage over `KvStore.Store`. Two key/value abstracts coexist and differ by GUARANTEE, not operations: `Cache.Store` (freshness, evictable) and `KvStore.Store` (durable, non-evicting, atomic `putIfAbsent`/`compareAndSet`). `KvStore.Store` is storage only — the claim/settle/release protocol lives once in `KeyedClaim` (`@telorun/kv-store`), which `Lease.Critical` and `Idempotency.Once` both use, so no backend reimplements it. **Declarative schema** is `sql`'s `Table` / `Schema` abstracts plus a backend (`postgres`, `sqlite`) that owns its whole type vocabulary, DDL rendering, introspection and locking; the shared half — the diff, the ledger, the tombstones and the phase ordering — ships through `@telorun/sql` as a module library. The split is the point: a neutral column-type vocabulary is a lowest-common-denominator one, so what crosses the boundary is a JSON Schema PROJECTION of the row, declared as data by each backend. **Durable execution** is `durable` (the backend-neutral `Durable.Run` marker + `Durable.Idempotent`), a BACKEND (`durable-local` today: `Workflow` + the `Journal` abstract + `Resumer`) and a journal — `durable-journal-file` (a directory, one machine) or `durable-journal-postgres` (two tables, several machines: claiming is one conditional `UPDATE`, waking is `LISTEN`/`NOTIFY`). The split is deliberate — what is shared is a narrow replay seam, never a portable engine vocabulary, because flattening lifecycle models costs fidelity in both directions and nobody switches durable engines twice. **Exactly-once is a property of the JOURNAL's location, not of durable execution**: a journal writing into the same transaction as the work it records attests `writesInside` (over `SqlConnection.bindsZone`, which asks about the NAMED zone rather than whatever is ambient) and the step engine journals that region per step instead of collapsing it; every region reports which way it resolved as `durable.zone.mode` (`collapsed` / `perStep`), because the answer turns on a runtime coincidence the manifest cannot show. `LISTEN`/`NOTIFY` rides `Postgres.Connection.listen`, a Postgres-only convention method on the instance rather than a member of the neutral `Sql.Connection` contract, with its own connection — a listener holds one for as long as it is subscribed. **A typeface is a resource, not a field**: `font` declares `Font.Family` (its name plus optional face bytes) and `Font.Measure` (advance widths for a BATCH of strings — one layout is one dispatch, and the contract is `inputType`/`outputType` rather than a method on a held instance, so a non-Node controller can measure text). `svg-chart` and `pdfmake` both reference one, which is what stops the family a layout was COMPUTED against from differing from the family that RENDERS — two hand-written strings whose disagreement has no visible cause. A family with no faces is a valid declaration (a websafe or already-served typeface, measured by estimate, which the result reports as `exact: false`); the consumer that genuinely needs bytes refuses it, where it can say what they were for. **Charts** are `svg-chart`: one kind per chart type over two abstracts (`Chart` — canvas, palette, legend, labels, font; `Cartesian` — axes, series, gridlines), each mapping a row to a mark through CEL accessors typed by `x-telo-context-element-from` against a declared row shape. Server-rendered static SVG only — an interactive browser chart is a separate vocabulary, since no CEL engine ships to a client.
- `analyzer/nodejs/` — static manifest validator (schema checks, reference validation, CEL type-checking). It also owns **manifest loading** (`manifest-loader.ts`, `parse-loaded-file.ts`, `resolve-ref-sentinels.ts`) — there is no `loader.ts` in the kernel; the kernel consumes the analyzer's, so `telo check` and the runtime read a manifest through one path. It also owns **manifest migrations** (`migrations/`) — see below.
- **Rust half of the polyglot runtime** — `kernel/rust/` (a second kernel), `cli/rust/` (the `telo-rs` binary), `analyzer/rust/` and `templating/rust/` (the loading/tag halves of their Node counterparts), `sdk/rust/` (controller authoring surface) and `sdk/rust/abi/` (the `telorun-abi` C ABI). **File layout mirrors the Node packages one-for-one**, kebab-case becoming snake_case: a Rust file with no Node twin means one of the two layouts is wrong, and the header of every such file says why it is the exception. `kernel/rust` is deliberately narrow (see `plans/rust-kernel-hello-world.md`): `Telo.Invocable` only, local-path imports, `pkg:cargo` controllers, no CEL. `telorun-abi` exists because the kernel must **not** depend on `telorun-sdk` — that crate selects a controller backend by Cargo feature, and unification would compile the napi backend into the kernel binary.
- `apps/studio/` — desktop editor (React + Vite + Tauri)
- `apps/hub/` — federated discovery hub (declarative Telo app): tracks registered module refs across transports via the `telo module versions|digest|manifest` CLI verbs, caches each version's `telo.yaml` to the static manifest bucket (`manifests.telo.sh`, the editor's browser-safe OCI read path, keys from the analyzer's `manifestCacheKey` helper), indexes one row per `(module-version, resource-kind)`, and serves `/search/*`, `/refs`, `/module/versions` + the `search_resources` MCP tool (see `plans/federated-discovery.md`)
- `ide/vscode/` — VS Code extension (YAML diagnostics via analyzer)
- `tests/` — integration tests (YAML manifests run via kernel)
- `examples/` — sample manifests

## Kernel Internals (`kernel/nodejs/src/`)

- `kernel.ts` — main orchestrator, boot sequence, multi-pass init loop, event bus
- YAML loading + CEL-YAML compilation lives in the **analyzer** (`analyzer/nodejs/src/manifest-loader.ts`, `parse-loaded-file.ts`), not here; `kernel.ts` imports it
- `evaluation-context.ts` — `EvaluationContext`, `ModuleContext` — variable/secret/resource scoping
- `resource-context.ts` — bridge: `getModuleContext()`, `registerModuleImport()`
- `module-context-registry.ts` — per-module store for variables, secrets, resources, imports
- `controller-registry.ts` — maps resource kinds to controller implementations
- `controllers/module/module-controller.ts` — handles `kind: Telo.Application` / `kind: Telo.Library` (includes, module scope)
- `controllers/module/import-controller.ts` — handles module imports (external modules, export CEL eval)
- `controllers/resource-definition/` — handles `kind: Telo.Definition` and parameterized templates
- `capabilities/` — base interfaces: runnable, invokable, listener, provider, template, mount
- `manifest-schemas.ts` — JSON Schema for YAML validation
- `logging/` — structured logging, implementing `kernel/specs/logging.md`: `logging-pipeline.ts` (threshold → redaction → sampling → fan-out), the `json`/`pretty`/`otlp` encoders, `console-sink.ts` / `file-sink.ts` / `debug-wire-sink.ts`, `normalize-attributes.ts` (§6.3 limits, iterative and bounded), `span-id.ts` (salted counter, hex only at the encoding boundary), `kernel-logging.ts` (bootstrap writer → declared-config handover, replay, seal). The record model, severity scale, `Logger`, the `Telo.Sink` contract and `RecordBuffer` (the bounded §10.3 sink buffer) live in `@telorun/sdk` — a third-party sink is an ordinary module, so everything it composes must be on the module-author surface; the kernel's own sinks reach them through the `logging/log-sink.ts` re-export shim. The redaction **path parser** lives in the analyzer so `telo check` and the runtime share one grammar. Reached by controllers as `ctx.log`; sinks reach the pipeline via `ctx.logging`.
- `workspace-marker.ts` + `resolveCacheRoot` — **the `.telo` cache is anchored at `telo-workspace.yaml`, so one repo has one cache.** Precedence: `TELO_CACHE_DIR` > the directory holding the marker > `<entry-dir>/.telo`; no marker anywhere above means the old per-entry behaviour, so the file enables the shared cache rather than gating one. Subdirs are `manifests/`, `analysis/`, `validators/`, `controller-src/`, `npm/`, `cargo/<sdk-backend>/`, `debug-ui/`. Both kernels resolve the root the same way, and a child kernel inherits its parent's rather than deriving one. Rationale, the per-entry analysis stamp, the pre-anchor read fallback and the upgrade path: `plans/workspace-anchored-cache.md`.
- `host-env.ts` — `boot()` replaces global `process.env` with a **guardrail** Proxy that denies a **manifest-derived** set: the env-var names the root Application binds via `variables`/`secrets`/`ports` (`collectDeclaredEnvKeys` in `application-env.ts`). A declared key reads back `undefined` (hidden from `in`/enumeration) with a once-per-key warning, so **controllers can't bypass a declared binding** — they use `ctx.env` or the declared `variables`/`secrets`. Every other key passes through — **no vendor-env allowlist** (a bundled SDK's `NODE_ENV`/`AWS_*`/`BUN_*` reads are undeclared, so untouched). The denied set is process-global and additive across in-process kernels. Kernel `TELO_*`/cache reads and subprocess spawns use `hostEnv()` (real env captured pre-lock); `analyzeOnly` never boots. A guardrail, not isolation; `process.env` is left non-writable. Tested in `tests/host-env.test.ts`.

## Resource Kinds

Every module file must start with exactly one `Telo.Application` OR `Telo.Library` doc. Applications are runnable entry points, Libraries are importable units of kinds/definitions. The two kinds share most fields; what differs is runtime role.

### `kind: Telo.Application`

A runnable entry point. Loaded via `Kernel.loadFromConfig` (directly, or by the test suite spawning a fresh kernel). **Never** imported — importing an Application is rejected at load time.

- `metadata.name` — free-form; becomes the canonical kind prefix (e.g. `MyModule.*`) that the registry keys on and diagnostics print. It is **not** a locator — imports resolve by `source`, and `x-telo-ref` targets are named by import alias — so it is a name, not a slug: write it in PascalCase (`OAuthClient`, `HttpServer`, `SQL`), which the whole standard library now uses. No pattern is enforced; the only hard rule is that it must contain no dot (the `!ref` grammar splits on the first one). Directory and npm package names stay kebab-case regardless (filesystem path; npm forbids uppercase).
- `lifecycle` — `"shared"` (default) | `"isolated"`
- `include` — array of file paths/globs to load as partial files into the same module scope; partial files must not contain `Telo.Application`, `Telo.Library`, `Telo.Import`, or `Telo.Definition`
- `imports` — name-keyed map declaring the module's dependencies. Each key is the PascalCase alias; each value is either a bare **source string** (`Console: oci://ghcr.io/telorun/console@0.9.0`, shorthand for `{ source }`) or the object form `{ source, variables?, secrets?, runtime? }`. The shared loader expands each entry into an internal import before resolution (gated by the `desugarImports` `LoadOptions` flag — on for the kernel's analysis + runtime loads, the import-controller's child load, the analyzer, and `telo check`; off for the editor's round-trip view, which reads the raw map). An alias declared twice in one module scope is a hard `DUPLICATE_IMPORT_ALIAS` diagnostic, not a silent shadow.
- `targets` — optional; run after all resources init. A flat boot sequence: each entry is a bare reference / `!ref` to a `Telo.Runnable` or `Telo.Service` (`run()`), a gated reference `{ ref, when? }`, or an inline invoke step `{ name?, invoke: <Invocable/Runnable ref>, inputs?, when? }`. Inline steps invoke the referenced resource via the shared `executeInvokeStep` leaf (SDK), with `steps.<name>.result` plumbed into later targets and `when`/`inputs` evaluated against the root scope. Ref-only — `invoke`/`ref` must be a `!ref` to a named resource (inline `{ kind }` definitions and `retry` are not supported here); control flow (`if`/`while`/`switch`/`try`), `with:` scopes, callable `inputs`/`outputs`, and `retry` stay in `Run.Sequence`. A no-targets Application is valid when its work is carried by Services that auto-start on init.
- `variables` / `secrets` — each entry binds a name to a host environment variable via an `env:` key, plus `type:` (`string | integer | number | boolean | object | array`), optional `default:`, and any further JSON Schema keywords. Values resolve at `kernel.load()` into the root `variables.X` / `secrets.X` CEL scope (object / array values are JSON-decoded from the env var; missing required vars or coercion / schema failures aggregate into `ERR_MANIFEST_VALIDATION_FAILED` before any controller init).
- `ports` — **Application-only** name-keyed map of inbound ports the app listens on. Each entry binds a host env var via `env:`, plus optional `protocol:` (`tcp` default | `udp`) and `default:`; the value is implicitly a port integer (1–65535, no `type:`). Resolves at `kernel.load()` (mirroring `variables`, same `ERR_MANIFEST_VALIDATION_FAILED` aggregation) into the root `ports.X` CEL scope, so a binding resource reads `${{ ports.http }}` as the single source of truth and a runner knows the exposed ports before boot. The analyzer brands each value by `protocol` (`tcp → Telo.TcpPort`, `udp → Telo.UdpPort`) for static wiring checks (see `x-telo-type`). `Telo.Library` does not get `ports`.
- `exports` is **forbidden** — an Application is a root with no importer. If you want to export kinds, the file is a Library.

### `kind: Telo.Library`

An importable unit of kinds/definitions. Loaded **only** as an imported dependency (via an `imports:` entry). Cannot be run directly; `loadFromConfig` on a Library manifest is a hard error.

- `metadata.name` — as Application.
- `variables` / `secrets` — JSON Schema property map; public contract for importers.
- `include` — same semantics as Application.
- `imports` — same imports map as Application (a library may declare its own dependencies).
- `exports.kinds` — which kinds importers may reference (`kind: <Alias>.<Kind>`). Each entry is either a bare kind name (a locally-defined kind) or `<Alias>.<Kind>` to **re-export** a kind the library imports under alias `<Alias>`. Re-export is transitive to arbitrary depth and resolves in O(1) (`ModuleContext` exported-kind table; analyzer `resolveExportedKinds` + `metadata.reExportedKinds` stamping); the gate still rejects kinds not listed. A re-exported kind resolves to its true owning module's controller/definition — `kind: Api.Thing` where `Api` re-exports `Domain.Thing` runs `domain`'s `Thing` controller. The gate is enforced in both halves: the kernel throws from `ModuleContext.resolveKind`, and the analyzer rejects statically using the target's list stamped onto each import as `metadata.exportedKinds` by `stampExportedKinds` (derived from the DECLARED entries, exactly as the kernel derives it — never from the resolved re-export table, which drops a re-export whose source module is ungated). Every kind-resolution path is *gated* — `kind:`, `extends:`, `capability:`, `base:`'s parent lookup, inline nested `{ kind }`, and `x-telo-ref` / `x-telo-schema-from` target checks all run through `resolveKind`. The dedicated `KIND_NOT_EXPORTED` *diagnostic* (naming the module and its exported kinds) is currently emitted only at the top-level `kind:` slot; the other slots still report their generic failure (`UNDEFINED_KIND`, `EXTENDS_UNKNOWN_TARGET`, a ref-kind mismatch), which is accurate but does not say "add it to exports.kinds". The gate check runs *before* any definition-registry lookup, since the registry is keyed `<module>.<Kind>` and an alias equal to the target's module name would otherwise resolve the raw kind string directly and slip past it. A library that declares **no** `exports.kinds` is currently unrestricted (every kind importable); declaring the block opts into the gate. Making kinds private by default is the intended end state but breaks every already-published module version, whose manifests cannot gain the block retroactively — it needs the ecosystem republished with explicit exports first. `registerImport(alias, target, kinds?)` encodes the distinction: a list is a gate (`[]` exports nothing), `undefined` is ungated and reserved for aliases crossing no import boundary (`Self`, the `Telo` built-ins).
- `exports.resources` — the resource **instances** the library exports as ready-made singletons. Each entry is a **plain name string** (the `!ref` tag is rejected here): `<name>` exports a locally-owned instance; `<Alias>.<name>` **re-exports** the instance the library reached through its own import aliased `<Alias>`, under the name `<name>` — same grammar as `exports.kinds`. Importers reference any export across the boundary as `!ref <Alias>.<name>` (injected into ref slots / boot targets) and, for value-flow exports, read them in CEL as `${{ resources.<Alias>.<name> }}`. The gate is the list itself: only named instances are reachable. A library declares a local instance internally with `kind: Self.<Kind>` (see `Self` under `Telo.Definition`), so it can export a singleton of a kind it does **not** export (omit the kind from `exports.kinds` to forbid importers constructing their own — singleton enforcement). Independent of `exports.kinds`: export a kind, an instance, or both. **Re-export is transitive to arbitrary depth** (`app → api → domain → …`) and resolves in O(1) regardless of depth: each import builds a flattened export table that copies the owner's terminal getter by reference (`ModuleContext.buildExportTable`), and the analyzer forwards re-exports transitively (`forwardReExportManifests`) so `telo check` agrees with runtime. The owning instance is shared — every re-exporting hop resolves to the single instance, not a copy.
- **Names are enforced, in three tiers, because Telo has no lexer** — a name is a YAML scalar, so nothing rejects its shape where it is declared and every consequence lands at whichever CEL site reads it. The vocabulary is `analyzer/nodejs/src/identifier-name.ts` (the single reader, `ref-slot.ts` precedent); the pass is `validate-identifier-names.ts`. **The convention is one sentence: case encodes what a name DENOTES.** `PascalCase` names a **type** — a module `metadata.name`, a kind name, an import alias, or a resource whose capability is `Telo.Type` (a named shape has no runtime instance). `camelCase` names a **value** — a resource instance, a `Run` step, a `variables`/`secrets`/`ports` key, a CEL binding. That is the *only* thing distinguishing `kind: Console.WriteLine` from `!ref Console.writeLine`, two character-identical grammars, and the collision is the sanctioned singleton pattern (`kind: Self.WriteLine`, export the instance, withhold the kind) rather than a hypothetical. The tiers: **`INVALID_NAME`** (error, every surface) — not `^[A-Za-z_][A-Za-z0-9_]*$`, or a CEL keyword; **`INVALID_TYPE_NAME`** (error) — a type-level name not starting uppercase; **`NAME_CASE_CONVENTION`** (warning) — a value-level name not starting lowercase. The grammar tier is an error because the name is otherwise unreferenceable *or silently mis-referenced*: CEL reads `-` as subtraction, so `resources.my-server.url` parses as `resources.my - server.url` and, where a bare name is in scope (which `x-telo-bindings-from` makes possible), **evaluates to a wrong number with no diagnostic** — the old dot-only `INVALID_RESOURCE_NAME` was the strictest special case of this rule, and checking one character while the rest went unchecked is what left that hole. The type-case tier is an error rather than a warning because `EXTENDS_ALIAS_PATTERN` already hard-rejects `extends: foo.Bar` while nothing rejected the `metadata.name: foo` that produced it, so a lowercase kind is one nothing can extend; it only moves an existing failure to where it is fixable. The value-case tier stays a warning (Rust's `non_snake_case` posture): a name is occasionally dictated from outside and Telo has no `#[allow]`. **Only the first character is checked** — the type/value signal is all it carries, and a full pattern would relitigate `httpApi` vs `httpAPI` and reject an all-acronym type name (`SQL`, `AI`). The reserved set is the **whole** CEL keyword list, not the subset today's parser rejects in field position (`resources.in` is a ParseError, `resources.for` parses) — which keywords tokenize there is a property of a dependency. **No `DiagnosticFix`**: a fix is a whole-value replacement for one node, and a rename is correct only when every reference moves with it. Scoped to the entry's own modules at every tier, errors included — a published dependency's naming is not the consumer's to fix (the `X_TELO_REF_UNRESOLVED` precedent), and a name synthesized by inline extraction (`metadata.xTeloOrigin`) is skipped because the author never wrote it. Step names come from the **call graph**, which already owns the analyzer's only step-array recursion.
- `targets` is **forbidden**. `lifecycle` is also forbidden — libraries are not lifecycle participants.
- No `env` access.

### `imports`

Loads `Telo.Library` modules into the current scope under PascalCase aliases, declared as the `imports:` map on the `Telo.Application` / `Telo.Library` doc (see above). Each entry value is a bare source string or the object form `{ source, variables?, secrets?, runtime? }`. The CLI `install` / `upgrade` / `publish` commands read and rewrite this map.

- `source` — relative path / registry ref / URL; resolved to `telo.yaml` automatically.
- `variables` / `secrets` — values passed into the child library.
- Each import creates an isolated child `EvaluationContext`; child resources are not visible to root scope.
- Importing a `Telo.Application` is a hard error — applications are run directly, not imported.
- Child modules are isolated from the host environment — only the root Application binds host env vars (via `variables:`/`secrets:`/`ports:` `env:` keys) and forwards them into imports.
- **An import that cannot be IDENTIFIED registers no edge and no alias.** Every way an import can be unusable — unreachable, malformed, an application target, no `Telo.Library` doc, a library declaring no `metadata.name` — is one shape: a `GraphLoadError` against *that import declaration*, no `ImportEdge`, and the rest of the graph still loads (`importTargetIdentity`, `manifest-loader.ts`). The check runs **per import declaration, never once per distinct target** — an import pointing at a module something else already reached (the entry Application above all) would otherwise skip it and register a nameless edge. `ImportEdge.targetModuleName` is therefore non-nullable: an edge that exists is one every consumer can resolve a kind through. Fatal at run time (the kernel throws `graph.errors[0].error`), a per-line diagnostic in every host — `INVALID_IMPORT_SOURCE` (not a module reference) / `IMPORT_UNRESOLVED` (well-formed, not obtainable) / `INVALID_IMPORT_TARGET` (obtained, not importable), three codes because three different people fix them.
- **Module identity is never guessed.** The analyzer registers an alias only from the loader-stamped `resolvedModuleName`; deriving one from the source string is what turned "this import did not resolve" into an assertion that a *dependency* was malformed, naming a canonical kind no registry can hold (`http-dispatch@0.11.1#sha256-….Outcomes`) and blaming a module the author cannot fix. With no alias every use degrades to `cannot resolve alias '<X>'`, which points at the import.

### `kind: Telo.Definition`

Registers a new resource kind. Defined inline in a module's `telo.yaml`.

- `metadata.name` — kind suffix; full kind = `<module-name>.<Name>`
- `capability` — one of the kernel capabilities (see below). Names the lifecycle role only; never a user-declared abstract kind. **Inherited and immutable** when `extends` is present: omit it to inherit the ancestor's, or restate it identically; a *different* capability than an ancestor is a hard error (`EXTENDS_CAPABILITY_MISMATCH` + kernel guard).
- `extends` — alias-form reference to **any** kind this definition specializes — an abstract (implements-this-contract) **or a concrete kind (single inheritance)**. Single-parent, transitive, Liskov-substitutable: a child is accepted at every `x-telo-ref`/`!ref` slot its ancestor is, transitively. The prefix must be an import alias declared in the same file (an `imports:` entry). **`Self`** is auto-registered as an alias pointing at the declaring library's own module name — use `Self.<Kind>` when the kind lives in the same `Telo.Library` as the definition (no import to alias against, since a self-import would loop the loader). `Self` resolves the library's own kinds **ungated** — independent of `exports.kinds`, which gates importers, not internal use. This is what lets a library declare an instance of a kind it does not export (`kind: Self.WriteLine`) so it can export the instance instead (see `exports.resources`). The kernel registers `Self` in each import's child context so `Self.<Kind>` resolves at runtime, not just in the analyzer. **Inheriting a concrete kind:** when a child declares no own `controllers:`/template body, the kernel's `resource-definition-controller` resolves the controller-bearing ancestor, evaluates the child's `base:` mapping, calls the ancestor controller's `create()` with the mapped config, and **returns that instance verbatim** — so the child *is* a parent instance and duck-types identically (e.g. inherits `.snapshot()`). See the kind-inheritance guide (`docs/extend/kind-inheritance.md`).
- `base` — **("super(...)")** construction mapping for a concrete-`extends` definition: an object of CEL expressions over `self` (typed from the child's own schema), evaluated once and passed to the inherited controller's `create()` as the parent's config. Mirrors the `inputs:`/`result:` top-level-sibling factoring. When `base:` is present the child's **author-facing schema is its own schema only** (the parent's config fields are internal, set solely through `base:`, so the child genuinely narrows); without `base:`, an `extends`-child's author schema is `merge(parent, own)` (pure additive extension). `resources.<child>` value-flow reads follow the **parent's** value-flow (snapshot / `outputType`), never the child's input schema.
- `controllers` — `pkg:npm` locator; `local_path` is a relative fallback for local development. Omit on a concrete-`extends` child to inherit the parent's controller by delegation (see `extends` / `base`).
- `schema` — JSON Schema with `x-telo-*` annotations
- `status` — optional JSON Schema for the **observed state** the kind reports while running (see Lifecycle). Surfaces as `resources.<name>.status.<field>`; `required:` is rejected. Also legal on `Telo.Abstract`, so a contract can mandate what its implementations report.
- `resources` / `invoke` / `run` / `provide` — template-internal bodies. `invoke:` / `provide:` / `run:` describe the dispatch target only; `inputs:` (values passed to the target) and `result:` (post-call mapping applied to the target's output, works with `invoke:` or `provide:`) live as **top-level siblings** on the definition, matching how Run.Sequence steps factor `{ name, inputs, invoke }`. CEL expressions inside these fields are statically validated against `self` (always — typed from this definition's `schema:`). The `inputs` CEL variable (typed from `inputType:`, falling back to the `extends:`-declared abstract's `inputType:`) is available inside `resources[].*` and the top-level `inputs:` sibling **only for invocable / runnable definitions** — provider definitions take no caller args (`provide()` is parameterless), so no `inputs` variable is exposed inside their bodies. Inside top-level `result:` the `result` variable is typed from the dispatch target's `outputType:`. The produced top-level `result` value is AJV-checked against the abstract this definition `extends` (`outputType`); top-level `inputs` is AJV-checked against the dispatch target's `inputType` when declared.

## Capabilities

- `Telo.Service` — `init()` + `run()`; long-lived servers, pools (cleanup is what they RETURN — see revertible effects)
- `Telo.Runnable` — `run()`; one-shot tasks, pipelines
- `Telo.Invocable` — `invoke(inputs)`; request handlers, scripts
- `Telo.Provider` — `init()` + optional `provide(): Promise<T>`; config/secret/value-flow sources. All fields implicitly `x-telo-eval: compile`. `provide()` opts the definition into the typed value-flow contract checked against the abstract's `outputType`; template-form providers (declared with `provide:` on a `Telo.Definition`) get a synthesized `provide()` automatically.
- `Telo.Mount` — mounted into a Service (e.g. HTTP APIs, middleware)
- `Telo.Sink` — `write(record)` + `flush()` / `flushSync()` / `close()`; a record-stream destination the runtime writes to **directly**, never through `ctx.invoke` (per-record dispatch is too slow, and dispatch emits trace events, so logging through it would generate telemetry from inside the telemetry path). Payload-opaque by design, so a future `Telo.TraceSink` reuses it; the log-specific fields live on the `Telo.LogSink` abstract. Scoped to record streams — metrics aggregate rather than stream and are not covered.
- `Telo.Type` — pure schema definition, no runtime instance

Defined as `Telo.Abstract` entries in `builtins.ts`.

**`Telo.Executable` is a SLOT CONSTRAINT, not a capability.** It is the built-in parent of `Telo.Invocable` and `Telo.Runnable` — "control can be transferred to this" — and it exists so a slot accepting either says so once instead of listing both. `capability: Telo.Executable` is **rejected** (it is absent from the kernel's `KNOWN_CAPABILITIES` enum): it names no lifecycle role, so nothing could implement it. It is the first abstract-extends-abstract edge among the built-ins; kind acceptance was already a transitive walk over the `extendedBy` index, so it costs two edges and no new machinery. **`Telo.Service` is deliberately outside it** — a service's `run()` is a lifecycle start the kernel dispatches differently (no ambient scope, so inbound work roots its own trace), and admitting it would make every step's `invoke:` accept a service. Boot-target slots that genuinely take `Runnable | Service` stay kind lists, the honest shape for a heterogeneous set.

**`Telo.Abstract`** is the **non-instantiable** flavor of a base kind: it uniquely means *no default implementation — must be extended* (load-bearing for `Sql.Connection`, `Codec.Encoder`, `Ai.Model`, …). Since general `extends` now specializes concrete kinds too, an abstract's only remaining special behavior is that instantiating one is an error and it has no `base:`/controller to inherit. Reach for a `Telo.Abstract` when you want a contract with no default implementation; use plain `extends` of a concrete kind (with `base:`) when you want to reuse an existing controller under a friendlier schema.

## Lifecycle, scopes & value flow

**Capability governs *wiring*, not dispatch.** The kernel calls `init()` and `snapshot()` on any instance that has them, with no capability check, so a `Telo.Runnable` may implement `init()`. What the declared capability *does* govern is which `x-telo-ref` slots accept the kind, statically: a `Run.Sequence` step's `invoke:` takes `Telo.Executable` (the parent capability `Telo.Invocable` and `Telo.Runnable` extend), its `targets:` takes `Telo.Runnable | Telo.Service`. A resource that must be both started and invoked therefore has to be **two kinds** — no single declared capability satisfies both slots.

**Observable side effects belong in `run()`, never `init()`.** `init()` builds the instance — it may ALLOCATE (that is what its effect frame is for: registered listeners, half-built pools), but it performs no I/O the outside world can see, which is also why `ctx.setStatus()` is an error before the resource has started. `run()` is where the effect becomes observable. `Http.Server` is the reference: `init()` registers plugins and routes as one effect, `run()` takes a kernel hold and calls `listen()` as two more.

**`init()` and `run()` RETURN what undoes them; there is no `teardown()`** (normative: `kernel/specs/revertible-effects.md`; SDK half `sdk/nodejs/src/effect.ts`, kernel half `kernel/nodejs/src/effect-scope.ts`). An effect is a forward action paired with its **inverse**; `ctx.effect(reason, body)` returns a **lazy chain**, `.effect(...)` extends it threading each step's result into the next, and a lifecycle method hands the chain back for the kernel to execute. **The signature is the forcing function, and that is the whole design**: an opt-in `ctx.effect` beside a retained `teardown()` was implemented first and nothing pointed an author at it — the reference controller grew and behaved identically, and a mechanism that exists to stop something being forgotten cannot itself be forgettable. **Lazy** so sequencing and recovery are the kernel's and the chain stays a *description* a second runtime can execute; **not a thenable**, because an `async` function unwraps one on return and the kernel would receive the last step's result instead of the chain. A chain is a value, so branches and loops build it. **Frames**: one opened with the context (covering `create()`), one per `init()`, one per `run()`, unwound **LIFO** — a failed `init()` must not revert what `create()` built, and a subclass extending its parent's chain (`super.init(ctx).effect(…)`) unwinds in reverse construction order by construction. **No invocation frame** — a scope ending when a call returns is `try`/`finally` — but a chain may be executed in place with **`.perform()`**, the one spelling for an allocation whose lifetime is an *operation* (`Durable.Workflow`'s per-run hold, taken inside `invoke()` and released when the run settles *or parks*); it joins the resource's frame and must be **disposed** by that operation. `dispose()` is idempotent and **unordered**, and never cascades: `run()` takes its hold before it opens the socket, so releasing the hold must not close the socket — a frame is a recovery order, **not a dependency graph**. **`inverse` is OPTIONAL** — a step that allocated nothing returns its result alone, because a chain also SEQUENCES lifecycle work and a required no-op closure would make "nothing to undo" read the same as "the author forgot". **An inverse pairs with a forward action that HAPPENED**: a lazily-created listener or subscription registers its own effect at creation (`.perform()`), never a slot reserved in `init()`. Bodies come in two forms, the single `{result, inverse?}` and the async generator yielding one inverse **per completed step** (so a body failing between allocations recovers exactly what it did, and one interrupted by a shutdown stops at the next step boundary). `result` is pass-through — the kernel hands it to the next step and the caller, and keeps only the reason and the inverse. **A failed `init()` recovers and the INSTANCE IS DISCARDED**, so the retry constructs a fresh one: inverses restore state outside the instance, and a controller's own half-built fields are beyond their reach (which is why `Http.Server`'s per-mount resumability bookkeeping is gone). **A DEFERRAL is not a failure** — `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING` unwind the frame but KEEP the instance, since re-creating would re-register an import's alias or a template's children. An inverse refusing **during recovery withholds** the resource; one refusing **at teardown aggregates** into `ERR_EFFECT_RECOVERY_FAILED` and the cascade continues. **`acquireHold` returns the raw inverse and registers NOTHING** — which frame owns a hold is the caller's fact (`run()`'s belongs to the run frame; a per-operation hold taken inside `invoke()` is disposed when that operation ends), so it is placed in a chain rather than self-registered, which would also double-register wherever a caller states it. **The detached drain is NOT**: it waits under a bound and abandons, where an inverse succeeds or refuses, so it is no longer folded into `instance.teardown` and runs after the frames unwind. No per-effect events — one per effect would swamp the wire and the logging path. Every stdlib module whose controllers return chains declares `requires: telo: ">=0.82.0"`: an older kernel calls `init()`, discards the returned chain, and silently allocates nothing. A module with nothing to undo declares no chain and needs no floor — the three in-memory stores clear a `Map` they own, which is not an observable effect, so they stayed universally loadable.

**Configured state is pulled; observed state is pushed.** `snapshot()` returns what the author configured, and the kernel pulls it after `init()`, after `run()` is dispatched, after each `invoke()`, and on every `setStatus()` — it is a function of the manifest, so re-deriving it is always correct. What a resource *learns* goes the other way: `ctx.setStatus(...)` reports it at the moment it is known, because nothing but the controller knows when that is. Both meet in `EvaluationContext.publishSnapshot`, the single publication path. Splitting them is what keeps each shape described once — a controller never rebuilds observed state inside `snapshot()` from a field it stashed only for that purpose. A publication is a **reading, not a live window**: the published value is detached from what the controller handed over (`detachSnapshotValue` rebuilds plain objects / arrays; class instances and functions pass through, since copying one would break it), so mutating a reported structure cannot rewrite an already-published value.

**Observed state (`status:`)** is what a resource learns while running, as opposed to what its author configured. A kind declares it as a JSON Schema block on its `Telo.Definition` / `Telo.Abstract`; a controller reports it with **`ctx.setStatus(...)`**; the kernel holds the last value and publishes it at `resources.<name>.status.<field>`, leaving the flat half (`resources.<name>.<field>`) untyped and unchanged. Reporting **replaces** rather than merges (this is the resource's observed state now), is AJV-checked against `status:` at the call that made it (`ERR_OBSERVED_STATE_INVALID`, or `ERR_OBSERVED_STATE_UNDECLARED` when the kind declares no block), is an error **before the resource has started** (`ERR_OBSERVED_STATE_BEFORE_START` — `init()` performs no I/O, so nothing is observed there), and is **sticky**: the last reading stays published until teardown, so a dispatch that reports nothing leaves it in place. A kind that declares `status:` may not also return a flat `status` field (`ERR_OBSERVED_STATE_KEY_COLLISION`); one that declares none may use the name freely. `required:` inside `status:` is rejected — every declared field is mandatory once the resource has run, and a sometimes-absent one is declared nullable. The chain is folded in the scope that **declared** each definition (an `extends` alias belongs to the file it was written in) — the kernel stamps the folded block at registration beside `effectiveAuthorSchema`; the analyzer re-scopes per declaring module. Statically: `OBSERVED_STATE_IN_STARTUP_FIELD` (any path through `.status` in a compile-eval field — a purely syntactic rule, so it covers undeclared kinds too), `OBSERVED_STATE_NEVER_RUN` (nothing can start the producer — in no `targets:` and named by no step's `invoke:`), `OBSERVED_STATE_REQUIRED_FORBIDDEN`, and `CEL_UNKNOWN_FIELD` under `.status` (cross-module too: an import's exported instances are typed under `resources.<Alias>.<name>`). At runtime there are three `ERR_OBSERVED_STATE_UNAVAILABLE` messages — not started / started but `run()` still pending / `run()` returned with a declared field missing — because each needs a different action and only the kernel can tell them apart. See `kernel/docs/observed-state.md`.

**`Run.Sequence` scopes (`with:` / `targets:`).** `with:` is an array of full resource declarations (`kind` + `metadata.name`) whose lifetime is the sequence — created on entry, torn down on exit — annotated `x-telo-scope: ["/steps", "/targets"]` so `!ref`s in either resolve against them. `targets:` lists with-resources to `run()` before the steps. Standing a server up around a test is exactly this shape (`modules/crud/tests/crud-over-http.yaml`). A scoped resource **publishes like any other**: each `ScopeHandle.run()` gets its own map of the scope's resources, layered **at read time** over the enclosing module's (not copied at scope entry — `setResource` replaces `_resources` wholesale, so a copy would go stale) with scope-local names winning (matching `ScopeContext.getInstance`'s order, so CEL and `!ref` agree), and `ScopeContext.run(name)` dispatches a scope target through the kernel chokepoint so it is traced, records that it started, and publishes. Fresh per run, so two concurrent runs never observe each other. A scoped name resolves only inside the `x-telo-scope` regions. **The handle is built on the context that OWNS the resource, never the root** (Phase 5 passes it as `PreInitHook`'s `owner`): a `with:` block's inline declarations name their kinds through the import aliases of the module that DECLARED them, so a library's scoped `kind: OAuth.RedirectListener` resolves against that library's `imports:` — the root Application has never heard of the alias. A scope nested inside a scoped resource forwards its opening scope's context rather than replacing it, so this holds at any depth.

**Controllers resolve a `!ref` slot with `ctx.resolveRef(value, guard, describe, expects)`**, not the standalone `resolveRefInstance` — only the context form rescues a `!ref` that reaches the controller as a raw sentinel (**Phase-5 injection is field-map-driven, and the field map does not descend into the inline declarations inside an `x-telo-scope` array**, so a ref slot on a scoped resource is not an injection site; Phase 2.5 *does* rewrite such a sentinel when it can name a target, so both shapes arrive) and resolves a bare name **scope-local first, enclosing module as the fallback** — the order `ScopeContext.getInstance` and the CEL `resources` layering already use, so `!ref` and CEL agree about what a name means inside a scope. That is what lets a `with:`-scoped resource reference a scoped sibling (`OAuthClient.RedirectAwait`'s `listener:`). The standalone form stays for callers holding only a `{ moduleContext }` slice; it takes the precedence via the optional `resolveLocalInstance` hook on `RefResolveContext`. Sentinel knowledge lives in the kernel, never the SDK, which has no runtime dependencies.

**A controller's `ctx` is scoped to the context that OWNS its resource** — the module context for a top-level resource, the per-run scope child for a `with:`-scoped one. Registering a manifest, resolving a sibling by name, expanding CEL, spawning a child context, dispatching and publishing all go there. `ctx.moduleContext` is reserved for what belongs to the MODULE rather than the resource: imports (`registerImport` / `resolveImported*`), the controller policy, and the logging scope — all inherited by a scope child, not owned by it. The distinction is load-bearing: a scoped resource that registers an inline definition into the module lands it in a pending queue the module's init loop drained at boot, so it is never created and the dispatch fails with `ERR_RESOURCE_NOT_FOUND`.

**An init failure is reported by ROOT CAUSE, not by count.** When the multi-pass loop gives up, everything downstream of the real failure is unfinished too, so the kernel classifies the set before raising `ERR_RESOURCE_INITIALIZATION_FAILED` (`init-failure-diagnostics.ts`). What makes an entry **derived** is its error CODE — `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING`, a deferral meaning it never ran — **never a reference edge**: an edge proves an edge exists, not causation, so a resource that refs a failed dependency *and* fails its own validation stays a root cause rather than having that error swallowed. Edges are **attribution only**; `RuntimeDiagnostic.blockedBy` is the **root** of the chain (the walk stops at the first non-derived entry), and a deferral with no visible edge is derived but unattributed. Edges are captured at `create()` time, before Phase-5 injection replaces refs with instances, so the walk never descends into a controller's object graph. A nested context's failures (an import initializing its library) attach as `children` rather than flattening into the parent's message — reported even when the wrapping entry is itself collapsed, since a child's roots are not shadows of the parent's failure — and both headlines come from `summarizeInitFailures`, never from re-parsing rendered text. Nothing is hidden wholesale: if every entry is a deferral, the set reports unclassified. Renderers consume the classification (`derived`/`blockedBy`/`children`), never re-derive it. See `kernel/docs/resource-lifecycle.md` §2.2.1.

**`inputs`/`outputs` are always VALUES; `inputType`/`outputType` are always SCHEMAS.** One invariant, no exceptions — `inputs:` on a run kind used to mean a JSON-Schema property map, which is why a declared `default:` never applied and a misspelled input went unnoticed: nothing read the contract at dispatch. The **invocation contract** is normative in `kernel/specs/invocation-contract.md`; the shared resolver is `analyzer/nodejs/src/invocation-contract.ts` (browser-safe, re-imported by the kernel — the split used for `buildEvalPaths` / the redaction path parser), and the kernel half is `invocation-contract-binding.ts`.

- **Resolution layers** instance declaration → the kind's, resolved to the **nearest declaration along `extends`** → undefined. Contracts **REPLACE, never merge**: config (`effectiveAuthorSchema`) and observed state merge because construction and reported state are additive; a call signature is not, and merging a child's required inputs into its parent's yields a union no caller can satisfy.
- **A call site is checked wherever it is DECLARED, not only in a step.** `validate-step-inputs.ts` runs one check behind two drivers: a step's argument map, found through the step grammar plus a sibling `x-telo-topology-role: inputs`; and a REFERENCE SLOT's, found through that slot's own `x-telo-ref` `inputs:` pointer (`collectRefInputIssues`). An `Http.Api` route's `handler:` + `inputs:` pair is the second shape and is not a step, so before the pointer was read the editor could complete those keys while the checker said nothing about them — a completion surface ahead of its checker.
- **A controller-inheriting child that declares its own contract MUST bridge it** — `inputType` needs `inputs:`, `outputType` needs `result:` (`CONTRACT_MISSING_MAPPING`). The inherited controller understands only its own shape, so an unmapped replacement would be inert. A child with its own controller/template body is exempt.
- **The kernel binds the contract to the instance at `create()`**, its single instance-production site, so **an instance is never observable unbound**. Enforcing at a handoff would mean enforcing at every handoff (Phase-5 injection, `ctx.resolveRef`, scope handles, template dispatch, `ctx.invoke`) and one missed site silently reopens the hole — Phase-5 injection is the dominant path, and `Ai.Agent` reads `this.resource.model` and invokes it directly. Binding rather than wrapping keeps member forwarding, prototype identity and the runtime-value walks non-problems. Consequence: the bound `invoke` shadows the controller's, so an internal `this.invoke()` goes through the contract.
- **`invoke` and `provide` are bound; `run()` is not** — parameterless and void, so nothing to fill or validate; a resource whose contract requires inputs at a run site is `CONTRACT_INPUTS_AT_RUN_SITE`. A bound entry point **forwards every argument**: the InvokeContext (cancellation, tracing) rides in later parameters, and dropping it strands detached work.
- **Validation skips `live`-typed nodes in BOTH directions** (a live `Stream` in a declared slot is not data — see `x-telo-type`), wherever one appears rather than only at a property, and defaults are filled over a copy **deep along default-bearing paths** — a flat shallow copy would let a nested default mutate the caller's object.
- **Contract errors are an ambient union** (`ERR_INPUT_INVALID` / `ERR_OUTPUT_INVALID`, `sdk/nodejs/src/contract-errors.ts`): raised as structured `InvokeError`s so they survive into a `catch`, nameable and typo-checked in `catches:`, and never counted toward a kind's declared `throws:`. A kind must not declare either itself.
- **`Telo.JsonSchema` is a kernel built-in** — declaring a shape is not optional once any kind can carry a contract, so writing `inputType:` must not require an import, and a library declaring its own contract must not import a module to describe itself. `modules/type` is **deprecated**; `Type.JsonSchema` still resolves unchanged.

**What an expression is typed against is a QUERY, not a byproduct of the walk.** The CEL environment plus the resolved `x-telo-context` schema in force at one site — the step context, the error-bearing region, a kind's named bindings, the kernel globals merged per declaring module — is `CelScopeResolver` (`analyzer/nodejs/src/cel-scope.ts`), and the analysis pass is one of its callers. It used to be assembled inline in the pass, built for one `engine.analyze` call and discarded, which left an IDE two options: re-implement the rule, or read a map keyed by paths the last analysis happened to visit. Neither is sound — **a completion list is a claim that the name it offers will pass `telo check`**, and two implementations of an open, growing scope rule cannot be held in agreement by tests (the rule has already gained `x-telo-bindings-from` and value-type parameters); while a recorded map structurally cannot answer mid-token, which is exactly when the question is asked. The IDE's way in is `CelScopeQuery` (reached through `AnalysisRegistry.analysisOf(manifests)` — see `ManifestAnalysis` below), which resolves for an **address** — a manifest plus a CONCRETE path, indices kept, since an `x-telo-context` region, an error branch and a step's identity are each addressed per item — recomputing the context match exactly as the manifest visitor does, so a site the last analysis never walked still types. **Two resolvers, kept apart**: a TYPE resolver (environment in, "what is this and what does it offer" out — completion, the type half of hover) and a DECLARATION resolver (graph in, "where was this written" out — go-to-declaration, `definition/resolve-cel-target.ts`). They take different inputs and legitimately disagree — `steps.encode.result` has a type and no manifest node, a transport binding like `request` has a scope entry and no declaration at all — so collapsing them would force every consumer to carry the empty half. Hover is their join. **CEL is COLOURED through the semantic layer, never a grammar** (`packages/ide-support/src/cel/tokens.ts`, consumed by `buildSemanticTokens`): both hosts already share that function, so a Monarch tokenizer beside the VS Code TextMate one would be a second CEL lexer to hold in agreement — and a grammar can only know the roots someone hardcoded into it, which is why `request` and `steps` went uncoloured while the stock YAML grammar painted the whole `!cel` scalar as the string it is not. Scope-aware: a name the resolved scope confirms is coloured, one it cannot is left alone (the unresolved-`kind:` signal), and with no query names colour syntactically so a body never reads as a plain string. **Colour encodes what a symbol IS, never the shape of the value behind it** — the chain ROOT is a `namespace` (a scope the runtime injects, not data the author declared) and its members are uniformly `property`, so a chain reads as scope · path; object-vs-scalar colouring is type-directed highlighting, which turns the palette into a type legend, moves a name's colour as analysis resolves, and says nothing exactly where the scope declares no shape. New token types are APPENDED to `SEMANTIC_TOKEN_LEGEND` — a host registers it once at activation, so an insert repaints every existing token. `steps.<name>` is the one CEL scope whose members ARE written in the manifest yet are reached through no reference slot, so it navigates through the declaring kind's own step-body annotation and the shared nesting walk (`CelScopeQuery.stepDeclarationPath`), naming no resource kind. A CONTEXT BINDING is the same category one level out — `request.query` exists because `x-telo-context-from` merged the route's own `request.schema`, `self.<field>` because `x-telo-context-from-root` named the definition's `schema`, `result.<field>` because `x-telo-context-ref-from` named the invoked resource's `outputType` — so `CelScopeQuery.contextDeclarationSite` re-walks the annotation for its PATH (the resolution `scopeAt` performs discards provenance, and an origin field on `CelScope` would be carried by every type consumer that ignores it), checking each candidate against the manifest so an undeclared binding resolves to nothing rather than to a guess or to a dependency's schema. Structural traversal (`resolveLocalRef`, `gatherPropertySchemas`, `walkStepArray`) lives in `schema-walk.ts` so the scope rule and the pass both reach it without either importing the other.

**The registry holds no manifests, so every question needing BOTH hangs off one object.** `ManifestAnalysis` (`AnalysisRegistry.analysisOf(manifests)`, `analyzer/nodejs/src/manifest-analysis.ts`) is the pairing named once: `celScope` (the CEL rule, built lazily), `resourceFor`, and `contractFor(ref, direction)`. Four such questions arrived in quick succession — CEL scope, step declarations, context-binding declarations, invocation contracts — and each would otherwise be another factory on the registry plus another optional parameter on every IDE entry point; naming the pairing stops that accretion, and each facet keeps its own honest name instead of piling onto whichever existed first. **Nothing here re-implements an answer**: `contractFor` IS the shared `resolveContract`, given `analyzerContractScope` to run in (which lives beside that resolver in `invocation-contract.ts`, not in the CEL module). What an editor offers at a call's `inputs:` is therefore what `telo check` validates it against and the kernel binds at dispatch. **The argument slot is named by the CALL, never guessed**: a control-transferring `x-telo-ref` declares `inputs:` as a JSON Pointer relative to the enclosing object (`/inputs`), which is the only thing tying an open `inputs:` map to the resource it holds arguments for.

**One expression, one verdict — the templating engine's.** `TemplatingEngine.analyze` returns `{ diagnostics, type?, calls }` (`templating/nodejs/src/engine.ts`), and the engine owns the `env.check()` call: the analyzer hands it the environment **typed for that path** and reads the resolved type back rather than checking again. Splitting the two is what let cel-js's opaque `found no matching overload` survive beside the diagnostic that explained it, and left `${{ }}` interpolations chain-validated but never type-checked at all. Everything derivable from the expression alone is derived there once; everything needing manifest context — the field's declared type, its `x-telo-eval` mode, which verdict outranks which — stays with the analyzer, which is the only side that has it. That split is also what a second (Rust) CEL engine implements: a classifier, not a rulebook.

Call classification (`cel/diagnose.ts`) reads `Environment.getDefinitions()` — every registered signature, cel-js built-ins and Telo's catalog alike, with its call form and parameters — so `CEL_UNKNOWN_FUNCTION` and `CEL_WRONG_CALL_FORM` are decided by lookup and **nothing parses cel-js's message text**. It only ever explains a rejection: the audit is reported solely when `check()` already failed, so a construct cel-js accepts but the registry cannot account for (a macro the parser expands, which a cel-js upgrade can add) degrades to no explanation rather than to a hard error on valid CEL.

**A repair is one primitive, carried unchanged.** `DiagnosticFix` (`analyzer/nodejs/src/types.ts`, read through the `diagnosticFix` accessor) is a whole-value `replacement` — never a fragment, and deliberately with no sub-range, since a range beside a whole-value replacement gives the field two readings and the minimal-edit one produces garbage. It flows to CLI JSON (`fix` beside `resource` / `path`), to `CheckDiagnostic` on the SDK seam (so a module can act on it), and to `ide-support`'s single `replace` suggestion, into which `UNDEFINED_KIND`'s old `suggestedKind` collapsed. Applying it to YAML goes through `renderFixReplacement`, which re-quotes in the author's style and **refuses a multi-line span**: a block scalar's span covers its `|`/`>-` indicator and its trailing newline, so a single-line replacement would delete the break that ended the mapping entry.

**One call graph, not a model per analysis.** `analyzer/nodejs/src/call-graph.ts` (`buildCallGraph`, browser-safe) is the single answer to "what calls what", built over **two node kinds**. Resource nodes carry declaration-site identity. **Step nodes** carry name, lexical order, enclosing array and nesting parent, and only *optionally* an outgoing edge — steps are nodes rather than edge decorations because a pure `value:` step produces `steps.<name>.result` while referencing nothing, and because step identity / ordering / nesting are what result typing, throws coverage and the editor's step rendering actually consume. What the model carries is **lexical order and containment, not execution order**: which branch runs is decided by runtime predicates and is not statically derivable, and no consumer needs it. It owns the analyzer's only step-array recursion.

Edges are `(from, slot, to, use)`, where `from` is a resource **or** a step node, and **the slot path is part of the edge's identity, so the graph is a multigraph**: `Cache.View` holding its `store:` as a `dependency` and calling its `invoke:` are two edges even when both name the same resource. Erasing that is what the old set-valued adjacency map did, silently merging a dependency with a call. The init-order consumer projects down to unique pairs itself, being the only one for which the distinction genuinely does not matter.

Consumers read one fact and derive their own: `buildDependencyGraph` orders on resource-level edges of every use but `schema`; `collectRunReachableNames` keeps whatever a control-transferring edge reaches. **Step edges are excluded from init order by NODE KIND, not by `use`** — a resource-level slot is a Phase-5 injection site so its target must exist first, while a step's slot resolves at dispatch; both are `use: call`. An edge whose slot declares no `use` (the legacy string form) counts as control-transferring, the conservative direction while the ecosystem migrates.

**Execution zones ride the ambient invocation context.** A resource can require being invoked inside another's body (a statement inside its transaction); the **zone stack is the `zones` member of `InvokeContext`** — deliberately NOT a second ambient store beside the cancellation scope, because a parallel store means enumerating every site that must clear it and one missed site is a false guarantee under a hard error. On the existing context, the two clearings the runtime already performs do the work with no zone-specific code: `ctx.runDetached` replaces the ambient with the uncancellable root, and a `Telo.Service`'s `run()` establishes none (so every shipped inbound trigger, all registered by Services, is zone-free by construction). The residue is exactly one shape — a `trigger.inbound` registered from *inside* an invocation by a non-Service — spec'd as a conformance obligation on the registrant: dispatch through **`ctx.rootContext()`**, never `undefined`. That obligation is what the analyzer's hard error on `trigger.inbound` edges rests on. **Nothing hangs off `openSpan`** — tracing is off by default and called by one controller, so a safety guarantee hung there would be absent by default. **Every context rebuild goes through `deriveContext(base, overrides)`** (SDK): a fresh object literal at `runInvoke`'s tracing branch / `runInstance` / `runTargets`' `targetCtx` / `openSpan` would drop `zones` under tracing-off and keep it under `--debug`, a safety property that changes with a debug flag. **A zone entry is three identities and nothing else** — providing kind, provider handle, correlation handle — so it stays ABI-serializable and no controller can read another module's open transaction off the stack. Instance identity is a **`ResourceHandle`** (`{ id, ref }`, `id` minted at `create()` — the single instance-production site, so an instance is never observable unbound; `ref` is the declaration site, diagnostics only). The instance→handle `WeakMap` has **no reverse direction**, which is what stops a handle becoming someone else's instance. A `with:`-scoped resource gets one id per scope run, which is also what the static correlation rule says. Controller surface: `ctx.self`, `ctx.withZone(slot, fn)` (a **scope function**, not push/pop — push/pop cannot be honest across async boundaries; hands back the derived context AND the minted entry), `ctx.requireZone(field, ctx?)` / `findZone` / `zonesFor(instance)`. **A controller names its own annotation SITE, never a kind** — it has no alias scope (`ctx.moduleContext` is the consumer's, and `resolveKind` is not on the surface), so every field of the entry is derived by the kernel from the annotation. **The payload rule: provider-private state hangs off an INJECTED INSTANCE, never a module import** — a module's controllers ship as separate bundles each inlining its copy of a shared source file, so module scope is one copy per bundle (that was the live `sql` bug: `transaction:` threw on every path). `sql` keeps its executor `WeakMap<ZoneEntry, Kysely>` as an instance field on the connection, and the explicit-zone path **throws** (`ERR_SQL_ZONE_FOREIGN`) rather than falling back, since `?? this.db` would convert a delivery split into silently non-transactional writes.

**A SUSPENSION is a signal, not an error, and the kernel must not wrap it.** A durable run that waits raises `ERR_DURABLE_SUSPENDED` (`sdk/nodejs/src/durable-suspension.ts`), which unwinds to the workflow that owns the run — so `runInvoke` passes it through and reports `InvokeParked` (a `SpanOutcome` of its own: a parked invocation neither succeeded nor failed), exactly as it already passes a cancellation through. That one site matters more than the rest: EVERY hop between a parking kind and its workflow goes through the chokepoint, so wrapping it once would convert a park into an `ERR_EXECUTION_FAILED` everywhere. The three composer sites — a `try:` step, a `catches:` list, a retry policy — also rethrow. **Everything beyond those is caught by a LATCH rather than by enumeration**: `parkRun` records the signal against the run handle (an SDK-owned `WeakMap`, safe because the SDK is one scope per process, so a backend cannot forget to set it) and the workflow calls `assertNotSwallowed` BEFORE settling the run, raising `ERR_DURABLE_SUSPENSION_SWALLOWED`. Enumerating the swallowers is unbounded and stale on the next module; detection is O(1) and needs no cooperation from the swallower.

**Kernel holds decide when an app exits.** `waitForIdle()` resolves at zero holds; a running `Http.Server` holds one, so an app with a service in it stays up until SIGINT. Anything that must let a one-shot app finish has to release its hold.

**One import instead of two.** An app that configures a backend itself imports both the abstract and the implementation (`sql` + `sqlite`) — that is normal and ~25 manifests do it. When a consumer should need only one import, the sanctioned collapse is a library that owns the wiring and exports **instances** via `exports.resources` (`tests/__fixtures__/re-export/`), not a module re-exporting another module's kinds.

## x-telo-\* Schema Annotations

Inside `Telo.Definition` schema blocks:

- `x-telo-eval: "compile" | "runtime"` — when `${{ }}` expressions are evaluated: at load time (compile) or per invocation (runtime). Without annotation, strings pass through raw. **CEL-bearing fields MUST be annotated:** a field a controller will `expandValue` (or the kernel auto-expands) must carry `x-telo-eval` or `x-telo-context` (or sit under an `x-telo-step-context` / `x-telo-error-context` region, or a provider's implicit root eval). The analyzer enforces this — a `!cel` / `${{ }}` outside every such region is `CEL_IN_NON_EVAL_FIELD` (the value would be read as a literal, never evaluated). Eval-path handling lives in the analyzer and is re-imported by the kernel, so runtime expansion and the static check share one source of truth — both halves: extraction (`buildEvalPaths`, own schema **+** capability abstract) and the containment matcher (`evalPathCovers`, used by the analyzer's coverage check and the kernel's compile/runtime `isExcluded`). The check stops at nested inline `{ kind }` resource boundaries — that CEL belongs to the nested kind.
- `x-telo-ref` — field must be a reference to a resource of a given kind, **plus a declaration of what the declaring resource does with it**. Two shapes are accepted: the bare string (`x-telo-ref: Sql.Connection`, legacy) and the structured form, which is what new schemas write:

  ```yaml
  x-telo-ref:
    kind: Telo.Executable        # one alias-qualified kind, or a LIST of them
    use: call                    # required in the structured form
    inputs: /inputs              # optional: JSON Pointer to this call's argument slot
  ```

  **A slot may UNION a value branch with a reference branch** — a declared column's `type:`, holding either a storage class from a closed vocabulary or a `!ref` to a named shape. This is the one place an `x-telo-ref` belongs under `oneOf` / `anyOf`; a multi-kind slot is still a `kind:` list. Where the reference constraint is a *branch* rather than the node's own annotation, a SCALAR is read as a value and left to that branch — including a misspelled one, which AJV reports as an unknown value rather than as a broken reference, since telling an author to write `!ref txt` converts a typo into a reference. An OBJECT is still checked for the removed `{kind, name}` form unless a branch describes that shape. The narrowing is applied by BOTH reference passes through one `satisfiesValueBranch` (an object-shaped value branch would otherwise reach `validateReferences`' structural check and be reported as a reference missing `kind` and `name`), and a branch AJV cannot COMPILE is not a branch a value satisfies — `validateWithRefs` swallows a compile failure by design, so reading that as "no issues, therefore a value" would switch the rule off silently. `RefSlot` gains `valueBranches`, carried onto the field-map entry; a node-level `x-telo-ref` with branches beneath it (an Application `targets` entry) has none, because there the branches describe the post-resolution shapes a REFERENCE takes and a bare string is still the removed spelling.

  **`kind` takes a list, replacing the `anyOf`-of-branches shape** multi-kind slots used. An `anyOf` puts each `x-telo-ref` in its own branch, so a structured form under it could carry a *different* `use` per branch — a disagreement with no meaning, since which kinds are acceptable is a property of the target while `use` is a fact about the slot. The analyzer always unioned those branches internally; the list makes the surface match the model.

  **`use` names WHEN control reaches the target, relative to the declaring resource's own invocation** — the one primitive fact every analysis derives from. Control transfer means the target's **bound entry points** — `invoke()` / `provide()` / `run()`, the methods the kernel dispatches, traces, contract-checks and zone-tracks. A convention or domain method on a held instance (`query()`, `embed()`, `stream()`, `getToken()`) is not dispatch, no matter how much work it does: that slot is `dependency`. This is the line that keeps `use` aligned with what the kernel's machinery can actually observe — `Ai.Text.model` is `call` because the controller drives the bound `invoke()`, while `Embedding`'s `model:` is `dependency` because `embed()` is a plain method, exactly like a connection's `query()`. `schema` (names a shape; no runtime instance, no edge) · `dependency` (held and read; control never transfers — init-order edge only) · `call` (transfers during my invocation and returns to me) · `detached` (transfers through the kernel's detach primitive; I do not await it) · `trigger.inbound` (I register the target; control reaches it after my invocation, driven by a request or timer, with a guaranteed-fresh ambient context) · `trigger.consumer` (I register it; control reaches it when someone drains a value I returned, so no guarantee holds). The trigger source lives **inside the value**, not in a sibling key, so a trigger with no source is unrepresentable and the enum drops into a case map unchanged.

  **`use` is a SET**, written as one value when it is a singleton. A slot may dispatch its target more than one way within a single invocation: `Cache.View` calls inline on a miss and detached on a background revalidation, so it declares `use: [call, detached]`. Each consumer states its own reduction (exceptions propagate if **any** member is `call`; an ambient scope's lifetime extends only if **every** member is).

  **A slot whose mode is chosen by configuration declares a case map** keyed on a sibling field — `use: {by: /detach, cases: {false: call, true: detached}}` (`Lease.Critical`). The selector **must be statically resolvable** (a literal or a schema default — an omitted `detach:` takes its `default: false` and classifies as `call`); a CEL value there is `X_TELO_REF_DYNAMIC_SELECTOR`, because a call graph known only at runtime is not statically analyzable. The annotation's own validity is enforced by `validate-ref-slots.ts` (entry-module-scoped): unrecognized `use` tokens (`X_TELO_REF_INVALID_USE` — a typo would silently degrade to the legacy no-use reading), a structured form missing `use` or `kind`, and `anyOf` branches whose uses disagree (`X_TELO_REF_USE_CONFLICT`). There is deliberately no fallback — the throws union must assume `call` to keep an error path while a zone requirement must assume the opposite, so any default would reintroduce unsound inference. A case map and a set answer different questions: the map says *configuration decides which relation holds*, the set says *several hold at once*.

  **Pointers inside `x-telo-ref` are relative to the object ENCLOSING the annotated slot** — the resource root for a resource-level slot, the array item for a slot inside one, so a route's `handler` can name its siblings. No pointer reaches across an array boundary.

  **`use` is never cross-constrained against the target's capability.** The tempting rule — a control-transferring `use` requires a `Telo.Executable` constraint — is unsound: `Ai.Model` declares `capability: Telo.Provider` and no schema at all, exposing `invoke` / `stream` as an ai-module convention, and its slot is genuinely `use: call`. The divergence is structural versus nominal: the kernel tests method presence at dispatch, while any static test can only read a declared capability. Capability keeps saying nothing about whether a slot transfers control — that is this design's whole premise.

  **Every surface reads the annotation through ONE accessor** (`readRefSlot` / `isRefSlot` / `rewriteRefSlotKinds`, `analyzer/nodejs/src/ref-slot.ts`, browser-safe): the analyzer's field map, the kernel's Phase-5 injection, the GUI editor's reference picker, and `ide-support`'s completions / hover / go-to-definition. Making the annotation structured changes how a slot is *recognised*, and four surfaces used to recognise it by string-matching — omitting any of them would silently turn every ref slot in the editor into a free-text field. No consumer pattern-matches the shape again, which is what makes the next shape change a one-file edit.

  The constraint itself is an **alias-qualified kind**, the same grammar `kind:` / `extends:` use: an import alias declared in the same file, `Self.<Kind>` for the declaring library's own kind, `Telo.<Kind>` for a built-in. It is resolved in the DECLARING module's scope and rewritten to the canonical `<module>.<Kind>` before registration (`resolve-schema-ref-kinds.ts`), so the registry answers ref queries with no module context. A constraint that resolves to nothing is `X_TELO_REF_UNRESOLVED` (`KIND_NOT_EXPORTED` when the alias is known but the target gates the kind) — without it the reference check would read the unknown target as partial context and skip it, leaving the slot accepting anything. The legacy `"<namespace>/<module>#<Kind>"` identity form still resolves for already-published module versions (fed by `metadata.namespace`, which nothing else reads) and warns as `X_TELO_REF_LEGACY_IDENTITY`. All three are scoped to the entry's own modules — a published dependency is not the consumer's to fix. References are written **only** with the `!ref` YAML tag: `!ref <name>` (local) or `!ref <Alias>.<name>` (an imported library's exported instance). The object form `{ kind, name }` and bare-string references are removed — `validateReferenceForms` rejects an author-written `{ kind, name }` / string at a ref slot up front (`INVALID_REFERENCE_FORM`); a plain object at a ref slot is only ever an inline definition (`{ kind, …config }`, no `name`). At parse time `!ref` becomes a tagged sentinel; `resolveRefSentinels` rewrites it across the whole manifest tree to the internal `{ kind, name, alias? }` shape (Phase 2.5), the analyzer validates it at Phase 3, and Phase 5 replaces it with the live `ResourceInstance`. Per-call data (`inputs`, `retry`, …) lives at the parent slot, never inside a ref.
- `x-telo-scope: "/json/pointer"` — marks an execution scope; resources inside are initialized on-demand, not at boot. Controller receives a `ScopeHandle`.
- `x-telo-schema-from: "refProp/$defs/Name"` — derives field validation schema from a sibling `x-telo-ref` resource's definition schema. Used for polymorphic config.
- `x-telo-value-schema-from: "<field>"` — the value written at the annotated node must satisfy the type declared at the resource's `<field>` (resolved with the same `telo#Type` semantics as `inputType` / `outputType`, so inline and named types both work). For a kind with ONE declared output contract and SEVERAL slots that must each produce it — a decision table's rows (`Run.Choice`), a switch's arms — where only the branch that wins at runtime would otherwise be checked. The analyzer validates every annotated slot, including ones no current input selects, after `substituteCelFields` replaces CEL leaves with schema-shaped placeholders: so it catches structural disagreement (missing required, unknown property under `additionalProperties: false`, wrong literal type) and never false-positives on an expression. A `<field>` that resolves to no schema (an optional `outputType` left undeclared) is skipped — declaring the contract is what opts in. Generic and topology-driven; the analyzer hardcodes no kind (`analyzer/nodejs/src/validate-value-schema.ts`).
- `x-telo-context: <JSON Schema>` — annotates a handler field with the CEL context available inside it. Analyzer-only; no runtime effect. Within a context schema, properties can carry:
  - `x-telo-context-from: "<path>"` — navigates `manifestItem.<path>` (per-scope) and merges the resolved value as a **property map** into the annotated node's properties. Used for transport scopes where the navigated value is itself a map of variable names (e.g. `request/schema` → `{ query, body, params, headers }`).
  - `x-telo-context-from-root: "<path>"` — navigates `manifestRoot.<path>` and **replaces** the annotated node's schema with the resolved value. Used on individual property schemas (e.g. `properties.self`) where the resolved value is a single variable's full schema. Anchoring at the root avoids the schema-vs-manifest-tree depth ambiguity that `../` parent-paths would carry.
  - `x-telo-context-from-ref-kind: "<refPath>#<field>"` — reads a kind name from `manifestRoot.<refPath>`, resolves it via the definition registry, and returns that kind's `<field>` schema (e.g. `outputType` / `inputType`). Used to type `result` against the dispatched target's declared output shape.
    - `x-telo-context-ref-from: "<refProp>/<subpath>"` — existing form: reads a `{kind, name}` object from `manifestItem.<refProp>`, looks up the named manifest, returns its `<subpath>` field schema; when that manifest declares no such field, falls back to the referenced **kind's** `Telo.Definition`, then to an open schema. That layering mirrors `buildStepContextSchema` — a kind exposing the field for per-instance narrowing still wins, while a kind with ONE fixed output shape (declared once on its definition) types the context instead of silently degrading to permissive. This is what types `result` inside an `Http.Api` route's `returns:`.
- **A STEP BODY is declared by pointing an array's items at the shared grammar** — `items: { $ref: "telo://manifest#/$defs/Step" }` — not by an annotation. The grammar (`invoke` / `value` / `if` / `while` / `switch` / `try` / `throw`, the `steps.<name>.result` accumulator, the `error` variable inside a `catch:`) is `StepSchema` in `analyzer/nodejs/src/manifest-schemas.ts`; its execution is `StepEngine` in `@telorun/sdk`. **Any kind can carry one**, which is what a composite kind (a transaction, a durable run) used to need a `!ref` to an executable for. It was declared four times in `modules/run/telo.yaml` — `$defs` are local to the declaring schema, so four kinds in one module could not share one, let alone four in four modules — and `while/do` is now admitted in **every** body, since a fragment cannot be narrowed by its consumer (draft-07 makes `$ref` exclusive) and the three copies that dropped it did so editorially ("the kind is itself the loop"), not for soundness. `Step` is RECURSIVE, so it is localized-and-hoisted rather than expanded (`RECURSIVE_FRAGMENTS`, split from `SCHEMA_FRAGMENTS` — being recursive is about how a reference RESOLVES, being a schema about which vocabulary a slot admits, and `Step` is the first that is one without the other). The recognizer is the derived `x-telo-fragment: Step` stamp, read through ONE accessor (`analyzer/nodejs/src/step-slot.ts`, the `ref-slot.ts` precedent) by the call graph, `validate-step-inputs`, `resolve-throws-union`, `validate-throws-coverage`, the CEL-region walk and `buildStepContextSchema`. A new `x-telo-steps` annotation was rejected for being the marker-you-must-remember pattern the stamp already retired once (`x-telo-retry`). What stays with the KIND: the array slot itself (title, `x-telo-topology-role: steps`, `x-telo-value-schema-from`), its `x-telo-context` bindings, and `with:` (whose `x-telo-scope` pointers are relative to that kind's resource root). Guide: `docs/extend/step-bodies.md`.
- `x-telo-step-context: { invoke, outputType, value? }` — **the legacy spelling**, read forever and written by nothing new: it told the analyzer where a kind's own step shape kept its dispatch ref, output type and pure-value field. Published artifacts carry it and no migration entry can synthesize a `$ref` (the patch vocabulary writes scalars), so it has the standing of the legacy `x-telo-ref` string form. It WINS where both are present — a kind spelling its own shape is describing its own manifest.
- `x-telo-context-element-from: "<field>"` / **`x-telo-context-collection-from: "<field>"`** — on an `x-telo-context` property, type a binding from a sibling collection expression: the first from its ELEMENT, the second from the collection itself. The element is an array's `items`, else the argument bound to whichever parameter the resolved value type declares as its `element` — so no value type is named in analyzer code and a future iterable type is covered by its entry alone. Both resolve the chain through the kind's declared `inputType` (falling back to a legacy `inputs:` property map), without which `item` was silently untyped in every kind that declares a contract. `collection-from` additionally **withholds** the binding when the resolved type is `live`: re-exposing a cursor the consumer is draining lets a body pass it on and drain the loop's own source, and that pass-through is what no member-access rule catches. Withholding is static only — the diagnostic is the generic `CEL_UNKNOWN_FIELD` — and the runtime enforcement is separate: `Run.Iteration` binds `items` only when the expanded collection really is an array, so an unresolvable type cannot bind a live cursor either.
- `x-telo-bindings-from: "<field>"` — on an `x-telo-context` node, merges the names declared in the resource's `<field>` map (read from the resource ROOT, not the per-scope item) into that context, so a kind can offer **named CEL bindings** readable by bare name. Evaluation order is derived from the identifiers each expression parses to — never declared — and enforced nowhere at runtime, because `ctx.bindScope` evaluates each binding lazily and memoises it, so a binding reaches its dependencies by construction and one nothing reads is never evaluated. Derivation, cycle detection (`BINDING_CYCLE`) and the reserved-name check (`BINDING_NAME_RESERVED` — every name `buildCelEnvironment` already binds at that site, plus CEL's keywords) live in `analyzer/nodejs/src/cel-bindings.ts`. A name already in scope is **skipped** at runtime rather than shadowing, so a reserved name the check did not foresee degrades to a dead binding, never a hijacked global. Generic — no kind is named in analyzer code; `Run.Value` / `Run.Choice` are the first consumers.
- `x-telo-error-context: <JSON Schema>` — on an array field (e.g. a `catch:` / `finally:` branch), declares the schema of the `error` CEL variable in scope inside that field. Analyzer-only. Unlike `x-telo-context` (fixed-depth JSONPath scopes that don't resolve `$ref`), the analyzer collects these annotations across `$defs`/`$ref` and merges the `error` schema for any CEL whose path passes through the annotated field name (`<field>[<index>]`) — so it applies at arbitrary nesting depth (a `catch` inside a `try` inside a `catch`). `error.<typo>` becomes `CEL_UNKNOWN_FIELD`. Generic — no resource kind is hardcoded; any composer with error-bearing branches opts in by annotating them.
- **Shared manifest fragments** — `$ref: "telo://manifest#/$defs/<Name>"` names a structural shape the **analyzer** owns (`analyzer/nodejs/src/manifest-schemas.ts`), as distinct from `#/$defs/<Name>` (private to the declaring kind's schema) and `telo:<module>/<Type>` (a `Telo.JsonSchema` resource a MODULE declared). The analyzer owns them because the editor validates in a browser through it and the analyzer must not depend on the kernel — a fragment there would exist only at runtime, invisible to `telo check` and to the editor; the kernel re-exports them. **`InvokeStep`** is THE dispatch site — `{ invoke, inputs, when, retry, name? }` — shared by every `Run` step array and by an Application's `targets:`. The runtime always had one (`InvokeStep` / `executeInvokeStep` in the SDK); the schema half was hand-restated per composer and drifted, which is why `retry:` worked in a sequence step and was a schema error one line away at boot. **`RetryPolicy`** / **`RetryAttempts`** are the two spellings of a re-attempt budget (a policy object; the deprecated bare count `Http.Request.retries`, unmigratable because a migration writes a scalar and wrapping one in an object is not expressible). Fragments are **expanded in place at load** (`expandManifestFragments`), for every consumer and deliberately **ungated** — unlike `migrate`, which a round-trip view must skip: these are the analyzer's own closed set rather than authoring sugar, nothing downstream is equipped to meet one unresolved (the editor's schema resolver takes document-local `#/` refs only and THROWS on anything else, so gating them took every canvas rendering a `Run` step down), and a save writes the YAML documents the editor holds separately, never a manifest object. The set is **deep-frozen**, and `builtins.ts` embeds an expanded COPY (`manifestFragment`) because it is not a manifest and never meets the loader — embedding the fragment object itself left boot targets with an unresolved `retry` and no stamp, silently switching the check off for them. Expanded rather than left as references — the opposite of `resolveSchemaTypeRefs`, and for the opposite reason: these are a closed non-recursive set the analyzer owns, and expanding them keeps a composer legible to every walk that never resolved anything (CEL-placeholder substitution, eval paths, the editor's field walk) instead of teaching each one to follow a reference and failing silently wherever one was missed. Expansion **merges siblings** — giving the 2019-09 `$ref`-composes reading on the draft-07 the validators run, which is what lets `Http.Request.retry` add `honorRetryAfter` to the shared policy and stay CLOSED (`allOf` cannot: a branch only sees its own `properties`) — and **stamps `x-telo-fragment`** with the fragment's name. That stamp replaced the `x-telo-retry` annotation: **`LIVE_VALUE_RETRIED`** asks which shape the author pointed at rather than reading a marker they had to remember to write, and the fragment also says WHERE the budget is, so the two spellings need no guessing between them. Derived, never authored (the `metadata.exportedKinds` standing) and stripped before AJV like every `x-telo-*` key. Consulted on the step's own policy AND the invoked target's, and only when the budget is a statically known non-zero; a CEL budget says nothing, and guessing would report a conflict against a manifest that may never retry (the posture the `use` case-map selector takes). The chain root resolves against `steps.` and **`inputs.`** (the enclosing kind's own `inputType`) — how a value produced outside the resource reaches a step at all.
- **The schema-valued slot is the one fragment that is NOT expanded**, because a JSON Schema contains itself. **`JsonSchema7`** (plain data — what an `inputType:`, a `status:` block or a route's `request.schema` holds) and **`KindSchema`** (a kind's own `schema:`, where the `x-telo-*` vocabulary belongs) are built from one vocabulary declared as data in `analyzer/nodejs/src/schema-keywords.ts`. **Wired today at the built-in slots only** — `Telo.Definition` / `Telo.Abstract`'s `schema:` + `status:` and `Telo.JsonSchema.schema`. A module's own schema-valued slots (`JS.Script.outputType`, `Http.Api`'s `request.schema`) still declare `type: object`: `inputType:`/`outputType:` are `x-telo-ref` slots accepting four forms, so they need an `anyOf` branch rather than a replacement, and a slot reached through `x-telo-schema-from` is TRANSPLANTED into the consumer's schema, where a document-local `#/$defs` pointer resolves against a root that has no such entry. A reference is **localized**: rewritten to the document-local `#/$defs/telo:<Name>` — reserved key, so an author's own `$defs` entry of that name cannot silently take over every slot pointing at the fragment — with one copy hoisted to the enclosing schema's root (`withSchemaFragments` for `builtins.ts`, which never meets the loader). `$defs` is merged key-wise by `mergeTypeSchemas` (`STRUCTURAL_KEYS`) for the same reason `properties` is: an `extends` child declaring any `$defs` would otherwise erase the parent's hoisted entry and leave its slots pointing at nothing. Localized rather than left pointing at `telo://manifest` because the editor's resolver **throws** on a `$ref` that is not document-local — the same throw that took the canvas down when fragment expansion was gated — and the hoist target is the top-level schema-valued key, because THAT is the object a validator compiles. Siblings beside the `$ref` reach completion, hover and the editor but not AJV (draft-07 makes `$ref` exclusive), so a slot may add a title and may not narrow. The **name is the discriminator**, read off the `x-telo-fragment` stamp — which is stamped on the hoisted BODY as well as the slot, since a schema nests and the node two levels down is reached through the fragment's own self-reference. What that buys is completion of the keyword set at every depth, hover, and a schema block checked at `telo check` on the offending keyword's line. That check is also what forced `DefinitionRegistry.tryAddSchema`: AJV's `addSchema` meta-validates and THROWS, and the throw escaped the whole analyze pass, so one bad keyword in a kind's `schema:` aborted the run with AJV's unanchored text and took every other diagnostic in the file with it. A schema AJV refuses is now left unregistered — an entry no `$ref` could have resolved through anyway — and reported by the two anchored checks that run afterwards (`SCHEMA_VIOLATION`, and `SCHEMA_COMPILE_ERROR` from the `compile` wrapper that already existed for this reason). Two properties are load-bearing: the body stays **open**, since closing it would reject the next annotation a module invents; and it carries **no literal `x-telo-*` property names**, since the annotation walkers (`resolveSchemaRefKinds`, `validate-ref-slots`, `validate-zone-slots`) test every object for an annotation KEY and would read a `properties` map holding one as an annotated node, inventing diagnostics about a slot nobody wrote. So the annotation vocabulary stays in the analyzer, on the side of the boundary no manifest walk reaches, and completion offers it only where the stamp says `KindSchema`.
- **`x-telo-schema-map`** / **`x-telo-schema-projection`** / **`x-telo-schema-projection-from`** — a kind whose configuration is a **collection of typed entries** declares what that collection MEANS as a JSON Schema object, so a consumer can type the values it will read without the analyzer learning the domain. `x-telo-schema-map`, on the field the projection keys on, gives the schema node each value means (`citext → {type: string}`); `x-telo-schema-projection`, on the kind DOCUMENT (a sibling of `schema:`, since it describes the whole declaration rather than one field — read from inside `schema:` too, and reported there, because silently ignoring a misplaced annotation moves the failure onto the CONSUMER and blames the wrong author), names the entry collection, the keying field and the closed, ordered modifier set (`array` wraps, then `nullable` widens); `x-telo-schema-projection-from`, on a CONSUMER's slot, names the ref whose target declares one. The first two say what a declaration means, and the third is the only thing that says where that meaning is wanted. Single reader `analyzer/nodejs/src/schema-projection.ts` (the `ref-slot.ts` precedent), strict half `validate-schema-projection.ts` plus `SCHEMA_PROJECTION_FROM_UNRESOLVED` at the consuming slot — a projection nothing can read does not fail, it silently stops typing the consumers counting on it, which is exactly the failure it exists to move earlier, and that is as true of a consumer whose reference does not resolve as of a malformed declaration. A reference matching SEVERAL manifests is refused rather than resolved to the first: typing rows against the wrong table is a wrong answer, which is worse than no answer — but ALIAS-AWARE first, so an unambiguous `!ref Alias.users` is not refused merely because two libraries each export a `users`. **`ProjectionScope` is a RESOLVER over the raw slot value, never a manifest list**, because resolution is scoped and only the host knows the scope — and because the two hosts see different things at the slot: the analyzer sees the `{kind, name, alias?}` reference the loader produced, while the kernel binds contracts AFTER Phase-5 injection has replaced it with the live instance (recovered through `kernel/nodejs/src/instance-declaration.ts`, the one-way instance→declaration record minted beside the handle; its own module because `resource-handle.ts` guards an exact export list for the unrelated handle→instance direction). **Resolved at BOTH ends** — `resolveContract` for `telo check`, `resolveBoundContract` for dispatch, where a failure to project raises `ERR_SCHEMA_PROJECTION_UNRESOLVED` rather than degrading (a slot that opted into a projection and got none is a defect, not a default — the `ERR_CONTRACT_UNRESOLVABLE` rule one level down, and the analyzer's own report is entry-module-scoped, so a dependency's consumer slot would otherwise be unreported at both ends) — because a projected contract enforced statically and not at dispatch is a contract with a hole exactly where a value is COMPUTED rather than written: `telo check` rejected a misspelled column written as a literal while the identical key arriving from a CEL expression reached the database, which for a repository kind means arbitrary caller text in a SQL identifier position. Distinct from `x-telo-schema-from`, which is DEFINITION-derived (a referenced kind's schema); a projection is DECLARATION-derived (one instance's own entries), which no definition-level derivation can reach. Deliberately LOSSY — length, precision and collation do not reach it, because a consumer needs the type, its nullability and its repetition and the database enforces the rest — with ONE declared exception: **`x-telo-schema-projection` may declare a `reference:` path**, how an entry whose keyed field holds a `!ref` rather than a value from the closed vocabulary projects (`from` names the target field to read, `keyword` the schema keyword its values become, `base` / `baseFrom` where the node's own type comes from). A domain crosses because it IS the type at the granularity a consumer acts on; nothing in the annotation says SQL, column or enum, and a backend declaring none projects exactly as before. An entry whose reference cannot be read projects **OPEN, never to nothing** — the opposite of the rule an unmapped VALUE follows, and the two failures are not the same failure: an unmapped value is a gap in the kind's own vocabulary so there is no entry to speak of, while an unreadable reference names an entry the declaration plainly HAS and only leaves its type unknown. Dropping it made the projection deny the entry exists, so a row naming it was told the property is not allowed — blaming the row for the reference's mistake. **`x-telo-schema-projection-from` with the EMPTY pointer names the declaration it is written on** rather than a slot holding a reference to another; resolution is skipped because the declaration is already in hand, which is what lets a kind type its own data against its own entries (a table's seed rows against its `columns:`, so a misspelled column is an error on the row's own line). Projections are therefore resolved when validating a resource against its KIND's schema too, per resource — a projection is declaration-derived, so the same kind schema yields a different row shape for every table — and **`resolveSchemaProjections` returns a node by IDENTITY where nothing projected**, because `DefinitionRegistry` memoizes its compiled AJV validator per schema OBJECT: rebuilding every node unconditionally missed that memo for every resource in the analysis and recompiled the whole kind schema per resource. The failure vocabulary is kept SPLIT for the same reason the codes are — `no-projection` (the kind declares none), `no-projection-map` (it declares one whose key field has no vocabulary), `no-entries` (this declaration lists none) and `entry-reference` are four different repairs by up to three different authors, and one message for all of them accused the wrong one. `x-telo-schema-map` is read off a union BRANCH as well as a node, through the single `schemaMapBranch` reader the strict half's completeness check shares. Generic: nothing in any of the three says SQL, column or table.
- **`x-telo-resource-rules`** — a kind declaring, as data, relationships between the fields of ONE resource that JSON Schema cannot state: an index naming a column its table does not declare, a foreign key whose two sides differ in length, a `renamedFrom:` still declared. Every such rule was previously a controller guard at boot — several of them firing AFTER `beforeMigrations:` had already changed the database, on a check that needs a database to run at all and that the editor cannot render. **The predicate is CEL, not a closed vocabulary of named rules.** Correlating two collections is the part a pointer language gets wrong (a foreign key's own columns against its OWN references, not every other key's), and a comprehension closure gives it for free; `"id" in self.columns` reads map KEYS, so the `*`-means-keys hack a pointer grammar needs never arises. The vocabulary stays OPEN — the opposite polarity from `use:` and the zone attributes, which are closed because consumers BRANCH on the name, where nothing branches on a rule. **The vocabulary is borrowed from `Telo.JsonSchema.rules`** — `condition` TRUE when the rule HOLDS, the subject bound as `this`, plus `code` and `message` — because two CEL rule vocabularies with opposite polarity is a trap an author falls into once per rule; the two mechanisms stay separate (that one runs at dispatch against a VALUE and throws a `RuntimeError`; this one at `telo check` against a MANIFEST and emits a diagnostic). **`in:` is the anchor by construction**: it names the collection to iterate, so a reported path exists — a rule returning an offender SET would make the pointer and the filtered collection two independent claims, and one anchored `/indexes` while filtering `self.columns` would emit diagnostics at paths that do not exist. Omitting `in:` gives the whole-resource form (`reclaim: {afterDuration: 0ms}`, a `severity: warning`), so no second `x-telo-discouraged` family. In scope: `self` (the resource), `this` (the element — a map entry's VALUE), `key` (its map key). **Every violation reports under ONE analyzer-owned code, `RESOURCE_RULE_VIOLATED`, with the author's `code` in `data.rule`**: surfaces branch on `code` (`MODULE_REQUIRES_NEWER_RUNTIME` gates suppression, `LIVE_VALUE_RETRIED` / `CEL_SYNTAX_ERROR` steer rendering), so a published module free to emit any string could shadow machinery that never expected a third party there — unvalidatable, since the code is a string in someone else's artifact. It is also the reversible choice: a module-qualified prefix can be layered on later as a check over `data.rule`. **Four restrictions, enforced at the KIND** so a bad rule is caught where it is written: no `hostBacked` function (the 8 the kernel injects at boot are throwing stubs in the analyzer, so the rule could never run), no non-deterministic one (a verdict depending on when it ran), an `in:` that names a collection the kind declares, and a condition that parses and type-checks. **A rule that THROWS is a defect in the rule** — an unguarded missing key throws rather than yielding false, and `has()` does not work under an iterated key (`has(self.columns[c].x)` is `has() invalid argument`; use `in` or `.?`) — reported against the kind, never as a violation of the manifest it ran against. **Both ways coverage can vary invisibly are REPORTED, never dropped**: `RESOURCE_RULE_SKIPPED` when a value the condition READS holds a `!cel` (per element, and narrowed to the read nodes via the parsed access chains — scanning the whole subject would disable every resource-wide rule on any manifest carrying one unrelated `!cel "module.version"`), and `RESOURCE_RULE_UNEXERCISED` when the `in:` collection was empty on every resource of the kind, which matters because cel-js types `self` only SHALLOWLY (a flat field map, so `columns` is `map`) and a nested typo survives declaration validation. A rule that THROWS or exhausts its budget is a defect in the RULE found while checking someone else's data, so it is anchored on the DECLARING definition — and downgraded to a warning when that definition belongs to a published dependency, since an error there blocks `telo check` on a line the consumer cannot change. Conditions are parsed once per process and keyed on their source, not once per resource: the pass runs over every resource of a kind and at keystroke time. **Budgeted at 50 ms per rule per resource** — a dependency's quadratic rule must not hang a consumer's `telo check` or the editor's keystroke-time analysis; it bounds the SUBJECT LOOP, not one expression, since cel-js exposes no step limit. Rules are read off the AUTHOR-FACING schema — and so is the `in:` pointer's validity, or the two halves disagree the moment a rule is declared anywhere but a leaf kind: a parent's rule naming a child's field reads as invalid at the parent, and a child's rule naming an INHERITED field is told the kind does not declare it. So an `extends` child without `base:` inherits its parent's rules and one declaring its own replaces them, which is what lets a rule shared by every backend be declared ONCE on the abstract they extend (`Sql.Table` declares the six table-structure rules; `Sql.Schema` the reclaim warning). Declaring them per backend is how the mechanism half-applies silently — the identical table was two `telo check` errors on Postgres and clean on SQLite, while the shared reconciler threw at boot for both. **The controller keeps its guard**: a library caller reaching a module's entry point directly never passed through `telo check`. Single reader `analyzer/nodejs/src/resource-rule.ts` (the `ref-slot.ts` precedent), strict half + evaluation `validate-resource-rules.ts`; guide `docs/extend/resource-rules.md`. Needed no `requires:` floor, verified by execution: `KindSchema` is `additionalProperties: true` and `Telo.Definition` is `capability: Telo.Template` (so `celRuleApplies` is off and the `!cel` values raise no `CEL_IN_NON_EVAL_FIELD`), and the previous published CLI reads a module carrying the annotation with no complaint.
- **`x-telo-referrer-rules`** — the same mechanism pointed the other way along a reference: a kind declaring, as data, what must be true of whoever REFERENCES one of its resources. `Http.Reference` renders the document `Http.Server` collects, so a server mounting it with no `openapi:` block has nothing to render — a disagreement spanning two resources, which no resource rule can state. **Declared by the kind that HAS the requirement, never by the kind that must satisfy it**, and that is a soundness property rather than a preference: written on the referring side the rule must name the mounted kind as a string, and a manifest spells a kind with the alias ITS author imported it under (`Http.Reference` here, `Web.Reference` next door), so the rule would silently pass on every manifest using another spelling. Declared here, the subject is chosen by the EDGE and no kind literal appears on that side at all. It is also the only version that scales — a third-party mount carries its own requirement without `Http.Server` learning the kind exists. In scope: `self` (the referenced resource) and `referrer` (the one that reached it); deliberately NOT `this`, which in a resource rule is an ELEMENT, and one word with two meanings across two families is a vocabulary an author learns twice. **`referrer:` is an alias-qualified kind filter** canonicalized in the DECLARING scope by `resolveSchemaRefKinds` (the `x-telo-requires-zone` branch, same walk), so evaluation compares canonical kinds and a filter resolving to nothing is `REFERRER_RULE_INVALID` at the kind that wrote it — it matches nothing, so the rule would pass everywhere while checking nothing. Omitting it applies the rule to every referrer, which conflates "references me" with the relation the rule is about. **A CONSUMER of the shared call graph** (`edgesTo`, the mirror of the zone projection's direction), never a second traversal; a step's edge is attributed to the resource whose body declares it, and a referrer reaching one resource through several slots is judged ONCE, since the condition reads two manifests and nothing about the site. **Ownership lands one hop further out than for a resource rule**: a VIOLATION is the REFERRER's data, so it names that manifest, anchors at the slot path (`mounts[1].mount`) and is reported only when the referrer is the entry's own; a rule that throws or overruns is a defect in the rule, anchored on the declaring definition and downgraded to a warning when that definition is a dependency's. The violation message names the declaring kind (`required by HttpServer.Reference`) because — unlike a resource rule — the resource carrying the diagnostic is NOT of the kind that wrote the rule, so the trail back would otherwise depend on the author's prose. Own code set (`REFERRER_RULE_VIOLATED` / `_INVALID` / `_SKIPPED` / `_UNEXERCISED`), the author's `code` still in `data.rule`. `_UNEXERCISED` is load-bearing here: nothing matching the filter ever referencing the kind is exactly what a typo in `referrer:` looks like from outside — silence that reads as passing. Polarity, the `hostBacked` / non-deterministic refusals, the parse cache and the 50 ms budget are SHARED with resource rules through `rule-condition.ts`, because two copies would eventually disagree about which functions a rule may call, which is soundness rather than style. Single reader `analyzer/nodejs/src/referrer-rule.ts` (the `ref-slot.ts` precedent), strict half + evaluation `validate-referrer-rules.ts`; guide `docs/extend/referrer-rules.md`. Needed no `requires:` floor, verified by execution — `@telorun/cli@0.78.0` reads a module carrying the annotation with no complaint, for the same two reasons resource rules did. **`peers:` is the binding that lets a rule state a relation between SIBLING declarations** — a JSON Pointer naming a collection OF THE REFERRER, whose other entries bind as `peers` and the referrer's own entry as `entry`. A rename marker is wrong only in relation to the *other* declarations a schema lists, and an enum a column names is unlisted only in relation to the same set; a resource rule sees one resource and a plain referrer rule sees a pair joined by one reference, so neither can reach it. **The FIELD MAP decides what is a reference, never the value's shape** — a `{kind, name}` object is what a resolved `!ref` looks like AND what author data carrying two common keys looks like, so sniffing would resolve author data to an unrelated manifest; the referrer kind's ref-slot paths are the authority. Entries bind AS WRITTEN with the references inside them resolved ONE level (a peer is the declaration where the entry is a bare `!ref`, the declaration with its siblings beside it where it is not — one level, since a self-referencing foreign key and a mutual pair are both cycles). A peer rule evaluates **once per ENTRY** rather than once per referrer, a deliberate departure from judge-once: a rule reading `entry` is about the entry, so a resource listed twice has two entries to answer for; `self` is excluded by SLOT PATH (by index for an array, by key for a map, which spell an entry's path differently). **One unresolvable peer fails the WHOLE binding** rather than binding what resolved — a peer condition is characteristically an existential or a universal over the set, and a partial set answers both wrongly and silently. The collection is resolved once per `(referrer, pointer)` (`PeerBinder`, one per analysis: re-resolving per entry is quadratic at keystroke time, and the rule budget then reports a correct rule as a defective one). Strict half at the declaring kind: `peers:` must name a collection the `referrer:` kind declares whose items are, or contain, a reference, and it requires `referrer:`. Peers-by-kind was REJECTED rather than deferred — a binding over "every resource of this kind in the analysis" needs no resolution and is unsound, since a physical name is scoped by its namespace and two schema resources over one connection would report a conflict between objects that never meet. Single reader `analyzer/nodejs/src/peer-binding.ts`, which also owns the analyzer's own environment (`analyzerPeerBinder` / `analyzerPeersTarget`, the `analyzerContractScope` precedent) so the pass assembles nothing inline. **A rule's `condition:` carries the `!cel` tag, in both families.** The readers stay lenient and a bare string still runs; what it loses is everything outside evaluation — untagged, the expression is a plain string to the editor's colouring, completion and hover — so the strict halves report it (`UNTAGGED_CONDITION`, shared). **A `!ref` is NOT a dynamic value.** Both families skip a subject whose read nodes hold a value only known at creation, and the predicate tested `__tagged` alone — which every tagged sentinel carries, `!ref` above all — so a column whose `type:` holds a reference switched off every rule reading `self.columns` and reported "a CEL expression" in a manifest containing none. `dynamicNode` classifies by ENGINE and names the tag it found (`an !include-bytes embed`), so the two halves cannot disagree about what a reference is.
- `x-telo-widget: "code"` — on a string field, tells telo studio to render a Monaco code widget instead of a single-line input. The language is resolved from the field's standard `contentMediaType` (e.g. `application/javascript`) via Monaco's own language registry, so adding a new language is purely a schema change — no editor code to touch.
- **`x-telo-provides-zone: true | <pointer> | { key?, …attributes }`**, **`x-telo-requires-zone: <kind> | { zone, key?, reason?, attributes? }`** and **`x-telo-violates-zone: { …attributes }`** — **execution zones**: a resource declaring that it must be reached through another resource's body (a transaction, a durable run, a batch). Normative contract in `kernel/specs/execution-zones.md`; guide in `docs/extend/execution-zones.md`. **A zone is identified by the kind that PROVIDES it** — no new kind, no capability, nothing instantiated — so the providing side names no zone (making provision-on-behalf-of unrepresentable) and only the requirer writes one, through the alias-qualified grammar `extends` / `x-telo-ref` use (canonicalized by `resolveSchemaRefKinds` in the declaring scope; unresolvable is `ZONE_PROVIDER_UNRESOLVED`). Both annotations are read through ONE accessor (`analyzer/nodejs/src/zone-slot.ts`, browser-safe), the `ref-slot.ts` precedent. The provider's value is the **correlation key**, never the zone; the requirer's `key` is an **ordered pointer list, first hit winning**, because the correlated field is usually absent — `Sql.Command` declares `[/connection, /transaction/connection]`, the manifest-level transcription of the controller's own `??`. A pointer may traverse a `!ref` into a kind **the declaring module owns**. When nothing resolves, the requirement discharges **uncorrelated** — inventing a correlation would manufacture errors from a guess. **Zone semantics are a projection of `use`, classifying nothing**: `call` propagates callee→caller and a providing slot discharges (under the correlation rule, `extends`-aware); `detached` / `trigger.inbound` **error** (the runtime GUARANTEES a fresh context); `trigger.consumer` **warns** (the drain site decides); `dependency` / `schema` are no edge — `Sql.Query.transaction` is exactly that: a dependency ref that *carries* the requirement without being a call. Severity turns on whether the edge is DECIDABLY wrong, not on whether the `use` resolved per instance: a **set** containing `detached` / `trigger.inbound` **errors** (a set says several relations hold at once, so the controller really does detach on some dispatch, and the detached dispatch is never inside the caller's zone — only *how often* stays unknown), while `trigger.consumer`, an unresolvable case-map selector and an undeclared `use` **warn**, because there the target genuinely *might* be in a zone. Propagation is the separate reduction and needs every member to be `call`. (`Cache.View` is a case map on `/revalidate` rather than an unconditional `[call, detached]` precisely so the set appears only under `background`, where its detach is real.) An edge whose `use` is unknown neither propagates nor terminates — the opposite polarity from throws. Boot is the root: nothing encloses `targets:`. The pass is `analyzer/nodejs/src/resolve-zone-requirements.ts`, a **consumer of the call-graph service with no traversal of its own**; per-library export derivation runs as its own stage in `analyze()` (never at flatten — the flattened view carries the export surface, not the internal dispatch chain, and the registries the projection needs are built FROM flatten's output), cached in a **host-lifetime cache passed into `analyze()`**, keyed `(source identity, content signature)` — `AnalysisRegistry` is constructed fresh per closure per run by the editor, so a cache there would die at the boundary it exists to cross, and identity alone is stale-unsafe for a workspace library being edited. Both annotations are validated by `validate-zone-slots.ts` — the strict half of the same accessor split `validate-ref-slots.ts` has, and not optional: the two fail in OPPOSITE directions (an unreadable requirement is silently unenforced, an unreadable provision invents failures), and a correlation key written as a bare name would be read by the kernel's walk but skipped by the checker, so the halves would disagree about what the manifest means. Diagnostics: `ZONE_REQUIREMENT_UNSATISFIED`, `ZONE_REQUIREMENT_DEFERRED`, `ZONE_EXPORT_UNSATISFIABLE` (raised at the exporting library only), `ZONE_PROVIDER_UNRESOLVED`, `ZONE_ANNOTATION_INVALID`, `ZONE_ATTRIBUTE_UNKNOWN`, `ZONE_ATTRIBUTE_INCOMPLETE`.

  **ZONE ATTRIBUTES are what a region GUARANTEES about its contents**, and they answer a different question from a requirement: a requirement is about ANCESTRY (*I must be inside a zone of kind X*), an attribute is about CONTENTS (*whatever runs inside me must not park*), and no requirement spells the second. They ride the annotation's object form rather than a second annotation family because a slot that constrains its contents is a slot that already ESTABLISHES a zone — a separate family would restate the zone's location, its `extends` resolution and its runtime open call, and a kind-level flag could not say WHICH field holds the body without per-kind knowledge (a sibling `afterCommit:` legitimately sits outside the transaction). **The vocabulary is CLOSED and it is DATA** — one JSON file per entry under `sdk/zone-attributes/`, the `sdk/value-types/` arrangement for the same reason (both kernels must agree on what a name MEANS, and a vocabulary written in TypeScript is readable by one of them); an entry declares `name`, a `value` schema, its `requires:` dependencies and a `description`, and **no code**, since the meaning lives entirely with the consumer that reads it. Closed rather than open because the nearest neighbour is closed (`use`, capabilities, value types) and because the openness argument INVERTS on inspection: `metadata.categories` is open precisely because *nothing branches on it*, while every zone attribute exists to be branched on — and **a third-party attribute could only ever be half an attribute**, since a module cannot contribute an analyzer pass, so it would get a runtime reader and no static check, which is exactly the half that misses the failures worth catching (an unread `noSuspend` parks a run inside a lease; an unread `atomic` journals a statement a rollback erases). The four entries: **`atomic`** (effects inside are discarded together; `requires: [noSuspend]`), **`idempotent`** (re-executing is observably a no-op — nothing is discarded, so unlike `atomic` there is no rollback for a consumer's own records to join), **`noSuspend`** (the zone holds something bounded that cannot outlive this process), **`replayed`** (execution inside may be re-run from a record of a previous one). **Each value is the author's REASON**, required by being the value itself rather than a sibling of a boolean — a consumer quotes it verbatim, and there is no `true` to accept, so `atomic: true` fails the declared schema. That design is also what keeps the set small enough to close: one name serves many providers because the prose carries the variation, so the vocabulary grows with kinds of HAZARD rather than kinds of provider (the survey turns up two more at most: `deferred`, `compensable`). `requires:` compiles to JSON Schema's **`dependentRequired`**, so `atomic ⇒ noSuspend` is a declaration in the data rather than a hardcoded pair of names. Names are **bare, not `Telo.`-qualified** — the position already implies the namespace, and the cost is stated rather than hidden: reopening the vocabulary later means a prefixed spelling and a migration. Declared today by `Sql.Transaction.steps` (`atomic` + `noSuspend`), `Idempotency.Once.invoke` (`idempotent` + `noSuspend` — its claim EARNS the first rather than asserting it), `Lease.Critical.invoke` (`noSuspend` alone; a lease makes nothing idempotent) and every durable backend's body slot (`replayed`). **The runtime half is `ctx.zoneAttributes(ctx?)`** — per open zone, its kind, the attributes that zone declared and the entry itself. Resolved off the DECLARING KIND's schema, never off the entry: a `ZoneEntry` is three identities *because* that keeps it ABI-serializable and stops any module reading another's state off the stack, so the kernel resolves and hands the values over **without branching on a name**, exactly as `readRefSlot` returns `use` without acting on it. The closed vocabulary is what lets that be a typed record rather than a string-keyed bag — a readability gain, not a semantic one.

- **The CONTAINMENT WALK is the mirror of the satisfaction walk** (`analyzer/nodejs/src/resolve-zone-containment.ts`, browser-safe). The landed projection propagates a requirement callee→caller and answers *is this satisfied*; every check built on zone attributes asks the reverse — *what is inside this zone* — so containment is a DOWNWARD walk from a providing slot to everything its body reaches. A second consumer of the shared call graph, not a second graph, and **parameterized over the attribute that opens the region**, so the durable zone (`replayed`) and the constraint zones (`noSuspend`, `atomic`, `idempotent`) share one traversal; it resolves an attribute NAME and nothing else, which is what keeps `modules/durable` out of the analyzer's surface. Two body shapes, one region: a slot may hold its body as a ref to an executable (`Sql.Transaction.steps`) or carry a step array natively (the shared `Step` fragment), and handling only the first would make every check silently vacuous on exactly the kinds written after the grammar became shared vocabulary. The zone's lifetime extends through an edge only when EVERY member of its `use` is `call` (the landed reduction); an edge that escapes is recorded as a **boundary** rather than followed, because the two facts differ and both are wanted — the zone does not reach the target, while the dispatch itself is a site inside the region a check may forbid. The provider is NOT in its own contents: a zone constrains what runs inside its body, not the resource that establishes it. It **under-approximates**, which is the safe direction for a CHECK (a dynamically dispatched edge degrades to the runtime error) and the UNSAFE one for a consumer at the opposite polarity — a durable manifest digest, whose blind spot is silent replay against changed code, must verify its coverage rather than inherit this tolerance.
- **`x-telo-type`** — **the one annotation that says what a value IS**, beyond what JSON Schema's `type` vocabulary can express. It replaced three keywords that answered that question differently — a nominal brand from a closed kernel table (`x-telo-type: TcpPort`), raw bytes (`x-telo-binary: true`) and a live handle (`x-telo-stream: true`) — which differed in *posture* toward the JSON Schema layer (refine, replace, exempt), not in kind. Legacy spellings are rewritten at load by the `normalize-value-types` migration, so nothing downstream knows they existed.

  **The vocabulary is DATA; the binding to a language is not.** One JSON file per type under `sdk/value-types/` (the `analyzer/migrations/` arrangement, for the same reason: the Rust half types an `!include-bytes` slot from the same entries, in a kernel with no CEL engine), copied into the SDK by `scripts/copy-value-type-entries.mjs` and embedded by Rust with `include_str!`. An entry declares `name` (`Telo.`-qualified), `representation` — `json` plus a `base` JSON type, or `instance` plus a symbolic `binding` — `live`, `parameters` and a `description`, and **nothing about any runtime**. A parameter may declare **`element: true`**, meaning *its argument is what iterating a value of this type yields* — so "what is the element of this collection" is answered by the vocabulary rather than by a consumer that knows one type's name, exactly as `live` is a field rather than a check against `Telo.Stream`. At most one per entry, refused at entry-read time in **both** readers (an entry that is a hard error on one runtime and loads silently on the other is the divergence a data-only vocabulary exists to prevent). Each runtime maps `binding` to its own identity (`sdk/nodejs/src/value-type.ts`, `sdk/rust/src/value_type.rs`); a binding with **no row is a hard startup error**, never a skipped assertion, since a type that cannot be asserted would silently exempt every slot declaring it. The starting set: `Telo.TcpPort` / `Telo.UdpPort` (`json` over `integer` — nominal identity for static wiring, no runtime effect), `Telo.Bytes` (`instance`, asserted), `Telo.Stream` (`instance`, `live`, one parameter `of`, which is its `element`).

  Everything else falls out of those fields, so no code fragment crosses a package boundary: the AJV keyword emits an `instanceof` against whatever the host's table names (**codegen, not a `validate` function**, so it inlines into the standalone validators the kernel compiles and caches), `celPlaceholderForSchema` takes the stand-in from the same table so static and runtime agree by construction, `jsonSchemaToCelType` gives a byte slot a real CEL identity, and `live` decides assert-versus-exempt. `registerTeloKeywords` (`analyzer/nodejs/src/value-type-keyword.ts`) is the **single registration site**, replacing five drifted ones. The annotation is exempt from `stripTeloAnnotations` (`VALIDATING_ANNOTATIONS`) and stays in the compiled-validator cache key — safe with no canonicalization, because the vocabulary is closed and a named shape reaches the annotation as a `$ref` the loader already resolved.

  **Exemption is a property of the TYPE, not of a position, and it is from VALIDATION never from TYPING.** `withLiveValuesSkipped` leaves a `live` node unconstrained wherever it appears — a property, an item, a union branch — where the old walk neutralized only a key it found in a `properties` map and left an array-of-streams element constrained. The declared arguments still travel through every schema-typing walk, because that is where the argument check reads them. Member access *past* a live value stays a diagnostic (`result.output` is fine, `result.output.text` is not); consumers iterate with `for await`, and producers wrap their `AsyncIterable` in `new Stream(...)` so the constructor is the registered one.

  **Value types are generic.** An entry declares named **type parameters**; the annotation's object form supplies **type arguments** — `x-telo-type: { name: Telo.Stream, of: Telo.Bytes }`. An argument is a **schema node**, so the system composes with no new grammar and nests to any depth: a plain JSON Schema, a built-in name (sugar for a node carrying only the annotation, normalized in the single reader), a `!ref` to a named shape, or another parameterized type. Every parameter is optional and defaults to *any*. Arguments are compared by `checkSchemaCompatibility` — **covariant** (a value is consumed by reading, so a narrower element satisfies a wider slot) and **gradual** (an omitted argument is *any* in BOTH directions, so an unmigrated producer or consumer keeps checking exactly as it did). The check has **one site**: a step's `inputs:` against the invoked target's contract (`validate-step-inputs.ts`), the one place a produced value's schema and a consuming slot's are both in hand — AJV is silent there by design, since a CEL leaf's placeholder says nothing about what the expression yields. Only a plain chain (`steps.encode.result.output`) is navigated; an expression that computes rather than names records nothing and fires nothing. A definite conflict is `CEL_TYPE_ARGUMENT_MISMATCH`. **A UNION is compared by distributing over its branches** — on both sides, a conflict only where no source-branch/target-branch pair agrees — in `checkSchemaCompatibility` and in `celTypeSatisfiesJsonSchema` alike. Returning *compatible* the moment either side was a union (the earlier posture) switched both checks off by construction for exactly the slots that admit several shapes, which are the slots where a value type carries the only distinguishing information. `allOf` keeps the old posture: a conjunction says too little to judge. The same union blindness ran through the PLACEHOLDER path, where it was worse than a missed check — `celPlaceholderForSchema` (and its kernel twin in `schema-compiled-values.ts`) handed a whole-field CEL leaf at a union-typed slot a stand-in no branch accepts, so such a field could not be written as an expression at all; both now take the first branch that yields one, and the kernel resolves the branch through the analyzer's exported `selectUnionBranch` so the static and dispatch halves cannot disagree about which branch a value was written against. Type arguments live in the schema layer and are **erased at the CEL boundary** — cel-js types by constructor identity, so a byte stream and a string stream are one CEL type and always will be.

  **A NAME is a closed built-in; a SHAPE is named with `!ref`.** The name slot takes only a `Telo.`-qualified built-in — no alias scope, no resolution, no gate — and an unknown one is `X_TELO_TYPE_UNKNOWN` (Levenshtein-suggested), where an unrecognized brand used to resolve to `undefined` and the slot quietly lost its identity. A **shape** is a `Telo.JsonSchema` resource reached the one way a named resource ever is; `use: schema` has been in the `x-telo-ref` vocabulary for exactly this relation. `resolveSchemaTypeRefs` normalizes the tag to the canonical `telo:<module>/<Type>` `$ref` — authoring surface and internal form, the split `resolveRefSentinels` and `resolveSchemaRefKinds` already have. **Normalizing rather than inlining** is what preserves schema identity (the validator cache is keyed on it) and leaves a recursive shape expressible; carrying the owning module is what makes resolution **alias-aware**, where matching a bare `metadata.name` across a flattened list silently dropped the alias. At a type field's own slot the id is stamped *beside* the reference, because that slot is a declared `x-telo-ref` and stays one. An argument naming an undeclared parameter is `X_TELO_TYPE_ARGUMENT_UNKNOWN`; both are reported on every schema-bearing field of every manifest, not only definition docs, since an inline `inputType:` on an ordinary resource carries a schema too (`validate-value-type-slots.ts`).

  **Bytes are never authorable inline** — no YAML literal is a byte buffer — so a literal at such a slot is rejected statically. **A union with an instance branch must use `anyOf`, never `oneOf`**: a consumer that does not know the keyword reads the branch as an empty schema matching everything, so under `oneOf` a plain string would match both branches and fail. The graceful-degradation property only holds under `anyOf`.

## Embedded files (`!include-text` / `!include-bytes`)

Two tags embed a file that ships beside the manifest as a manifest value — `!include-text` → string, `!include-bytes` → `Uint8Array` (what a `Telo.Bytes` slot accepts). Engines in `templating/nodejs/src/engines/include.ts`, registered in the closed `builtinEngines` set, mirrored by `templating/rust/src/engines/include.rs`.

**Paths are MODULE-ROOT-relative, never relative to the declaring file** — the rule a controller's `path=` and `files:`/`assets:` already follow. It is load-bearing rather than cosmetic: `telo publish` deletes `include:` and inlines every partial as an extra document into one published `telo.yaml` (`expandAndInlineIncludes`), so the declaring file does not exist in the artifact and a per-file-relative path would silently move — passing `telo check` locally and failing only for consumers. **Confinement is a PURE STRING check** (`normalizeIncludePath`), which is what lets the browser-safe analyzer decide it: root-relative means `..` below depth zero is an escape regardless of where the module sits on disk. Literal paths only — a URL, glob or absolute path is `INCLUDE_PATH_INVALID` / `INCLUDE_PATH_ESCAPES_MODULE`. A **computed path is deliberately unrepresentable**: a file that must ship inside the artifact has a name known at publish time, so the dynamic case is `Fs.File`'s, not this one.

**A module's `source` is what EVERY module-relative reference is measured from** — `ctx.resolveModuleFile` for a controller, an embed for a manifest value — so an import's child `ModuleContext` carries the **library's own manifest URL** (`moduleManifest.metadata.source`, stamped by the loader), never the importer's and never `resolvedUrl` (which is the import source as written, a directory whose last segment `new URL` would drop). Carrying the parent's made a library read the CONSUMER's directory, silently returning the consumer's file when one sat at the same relative path — and it contradicted packaging, which is per-module.

**An embed's type is a constant of the TAG, not of the slot.** `substituteCelFields` gives every other tagged sentinel a slot-shaped placeholder (right for `!cel`, whose type is only derivable from the expression); these two substitute a real `""` / `Uint8Array`, so AJV and the `x-telo-type` keyword reject a byte embed at a string slot — and the reverse — statically, with no new diagnostic code. **The ENGINE is what says so**: `TemplatingEngine.producedType()` declares the fragment (`fileClaims`' precedent applied to the one fact it left behind), and `substituteCelFields` reads it through `producedTypeOf` instead of branching on two tag names — the only place a tag's produced type was written down, and it was written in the consumer.

**`compile` is identity on the marker** — the sentinel survives precompile the way `!ref` does, but needs no special case in `precompileDoc`. **The read happens at RESOURCE CREATION** (`kernel/nodejs/src/resolve-include-sentinels.ts`, called from `_createInstance` before schema validation so bytes reach a `Telo.Bytes` slot as a `Uint8Array`), never at manifest load: the artifact spec gives `telo.yaml` its own layer so reading a manifest cannot pull the payload, and an app loads every imported library's manifest. The walk **stops at nested `{ kind }` declarations** (a `with:`-scoped resource resolves when its scope runs — Phase-5 injection draws the same line) and **only recurses into plain containers**, because a template kind expands `${{ self.connection }}` to a live `ResourceInstance` whose graph is cyclic. The same rule governs `compileWalker`: rebuilding any object from `Object.entries` would turn a byte buffer into `{"0":137,…}` silently. An embed on a doc that is never instantiated is `INCLUDE_OUTSIDE_RESOURCE` — nothing would read it, and nothing else would report that.

**Payload membership is ONE generic mechanism, and no consumer recognises a syntax.** `TemplatingEngine.fileClaims(source)` lets an engine declare what its tag embeds (the `ref-slot.ts` precedent); `collectModuleFileClaims` (`analyzer/nodejs/src/module-file-claims.ts`, browser-safe) is the single reader, aggregating engine claims **and** the controller `path=`/`siblings=` claims into `{ path, role, selector?, siblings?, origin }`; `partitionLayers` consumes that and knows about neither PURLs nor tag names. It is **deliberately not part of `analyze()`** — that pass is flattened and import-inclusive, so its claims would mix in imported libraries' files (whose paths are relative to *their* module) and would make packaging depend on resolving the whole import graph, which today it does not. Publish refuses a named file that does not exist. Cap: 32 MB per file. The Rust kernel resolves `!include-text` only — its manifest is `serde_json::Value`, which has no bytes variant, so `!include-bytes` fails there explicitly rather than producing a number array.

## Declared runtime requirements (`requires:`)

**Additive syntax is not additive to a closed vocabulary.** Every extension vocabulary hard-errors on an unknown token — right for a typo, wrong for a version, and nothing distinguishes them, so a module adopting new syntax breaks on older runtimes *and blames its own author* (`ZONE_ANNOTATION_INVALID` for a shape the reader is too old to know; `ERR_ZONE_ANNOTATION_MISSING`'s "the controller and its schema disagree"; an `additionalProperties` violation on `InvokeStepSchema` for one new key). A top-level **`requires:`** block on a module doc declares the runtime range the module is verified against, and the load gate reports *that* instead.

**It is a requirement, not a build fact**, which is what lets it gate — a derived "built with" stamp moves on every republish and says nothing about what the module uses. **Each axis is a semver range whose every bound is testable**: `^`/`~` are REJECTED (pre-1.0 both allow one minor, and breaking changes ship as minors here, so the caret reading is correct and useless — it pins to one release generation), a bare version is rejected (semver reads it as an exact pin), `||`/hyphen/wildcard are rejected (verification runs the CLI *at* the edges and a disjunction has none), and a declared upper bound must name a version that **already exists**, checked at publish. Open above is the norm; a closed bound earns its place only for a module known broken on a newer telo that will not be fixed, where it makes `upgrade` report *no compatible version*.

**Verification is EXECUTION, not a `since:` table** — `npx @telorun/cli@<edge> check <manifest>`. An annotation table re-creates the discipline problem one level down (forgetting a `since` is silent) and cannot see a *shape* change. **Two edges bound the whole range** because syntax support is monotonic; an open range's high edge is HEAD, which normal CI already covers. Transitive propagation is free — in-repo siblings import by relative path, so a sibling adopting new syntax fails its dependents' edge checks. **Infrastructure failure warns, evidence fails**: a CLI that could not be installed leaves the claim unproven, not disproven.

**Two tiers.** `telo` is the **manifest surface generation** — ONE scale every kernel reports (Node, Rust, Go), independent of each kernel's own release identity, so there is no range per kernel; a kernel implementing only a *subset* of a generation claims none and skips the check, because a version expresses *older*, not *smaller*. Host requirements nest under **`host:`** — **`node` only, because an axis enters `KNOWN_HOST_AXES` when a supplier exists and never before**: a declared requirement nothing compares validates, reads as protection and protects nobody, which is the failure class this mechanism removes. The supplier is `nodeHostVersions()` (kernel, one function so the kernel's load path, its `check` seam and the CLI's `check` cannot report different hosts). Nested because `nodejs`/`rust` are already kernel labels (`LABEL_TO_PURL_TYPE`, an import's `runtime:`), so no top-level word disambiguates the host runtime from the kernel; and because the tiers differ in *verification* (telo by execution, host by assertion, compared when it bites). **`telo` is checked first**, which is what makes the block extensible: a module using a later axis also requires the telo version that defined it, so an older runtime never has to interpret an unknown axis. Once `telo` is satisfied an unrecognized key is an error at either tier.

**The analyzer owns the mechanism, because the editor validates in the browser.** `requires-block.ts` is the single reader (the `ref-slot.ts` / `zone-slot.ts` rule) over `version-range.ts`'s grammar, itself built on `module-version-order.ts` rather than the `semver` package so the analyzer stays browser-safe. `validate-requires.ts` is the strict half: **`MODULE_REQUIRES_NEWER_RUNTIME`** (the gate — the module is fine, this runtime is too old) and **`REQUIRES_INVALID`** (the declaration is malformed; entry-module-scoped, since a dependency's block is not the consumer's to fix). The gate runs FIRST in `analyze()` and **suppresses every other diagnostic anchored in that module's files** (`filesOfUnreadableModules` / `suppressUnreadableModuleDiagnostics`, attribution by FILE for `remapMigratedPaths`' reason) — otherwise the one message naming the cause is buried under the vocabulary errors the skew produced. Unknown-axis complaints are suppressed while the gate is failing: an older runtime not knowing a newer axis is a *consequence* of the skew, not a second defect.

**The analyzing runtime answers "what version am I?"** — the only well-posed question in a browser, where no kernel runs and the editor authors for an absent target; checking against itself is also exactly what the editor needs, since a manifest it cannot parse otherwise yields errors it cannot explain. `TELO_SURFACE_VERSION` is **generated at build** from **`cli/nodejs/package.json`** by `scripts/generate-telo-version.mjs`, run from the root `prepare` (pnpm, fresh clone) AND the analyzer's own (npm, before pack). The CLI is the package read because it is the one verification installs and the one the upper-bound existence check queries — one package throughout, so the constant, the check and the thing that runs cannot disagree. **The generated file must stay UNTRACKED**: `.gitignore` has no effect on a tracked file, so committing it once turns it into a second place the version lives (the `copy-value-type-entries.mjs` / `copy-migration-entries.mjs` precedent; gitignored). Deliberately NOT the analyzer's npm version — `@telorun/analyzer@0.61.0` is release identity, the constant is implemented surface generation. **The kernel does not override it**: the constant is derived from the kernel's own version, and where the two can drift the analyzer is the half that PARSES, so claiming a higher generation than the bundled parser implements is a claim the stack cannot honour. `AnalysisOptions.teloVersion` exists for checking against a DIFFERENT target (a CI matrix, an editor "we deploy on X" setting).

**CLI half** (Node by nature): `release/verify-requires.ts` (per module, `publish` preflight — a refuted range is fatal, an unpublished upper bound is fatal, an uninstallable edge warns) and `release/check-requires.ts` (workspace-wide, batched by shared edge so a stdlib declaring one or two lower bounds costs one or two runs, wired into `telo release check`). **A FORWARD-DECLARED lower bound is a third state** (`pending`, `unreleasedEdge`): adopting new syntax means declaring the release that will carry it, so on that commit the edge names a version npm does not have — one possible outcome, arriving as an `ETARGET` wrapped in install noise indistinguishable from being offline. So the registry is asked BEFORE any edge runs (`publishedTeloVersions`, memoized) and such an edge is never spawned. The latest published version is reported beside the bound, because that is the only signal against a TYPO above the latest (`>=0.790.0` beside `0.78.0` reads wrong; "could not run" does not). Informational at `telo release check`, **fatal at publish** — npm publishes before modules, so by then the floor exists, and a module landing at the registry with a floor no runtime satisfies is a version every consumer's `upgrade` refuses. An edge BELOW the latest that is nevertheless absent (yanked) stays "could not run": guessing why it is missing would be a rule with nothing behind it. An unreachable registry classifies nothing. `telo upgrade` selects the highest version whose range accepts this runtime, walking newest-first and stopping at the first satisfied one — and **reports what it held back**, or the pin is a silent ceiling and *"up to date"* becomes the new confusing report. It short-circuits when the newest published version is already the pin: there is no candidate to choose, so the question has no bearing and asking it would cost a fetch per import on the path that changes nothing (a pin the runtime cannot read is the LOAD gate's to report — `upgrade` moves pins forward, it does not walk anyone backwards).

**The candidate verdict is ONE function, and every upgrade affordance shares it.** `manifestCompatibility` (`analyzer/nodejs/src/module-compatibility.ts`, browser-safe, text in / verdict out — fetching the candidate manifest is the caller's, since only the caller knows which transport addresses it) answers `yes | too-new | unreadable | unknown`, the four kept apart because they call for different actions and collapsing them asserts a cause the check never established. `unknown` is never incompatible: an unreachable source must not silently freeze a consumer's imports. The CLI calls it; so does `@telorun/ide-support`, which adds the **selection** rule on top (`import-upgrades/version-compatibility.ts`) — newest-first with a short-circuit for the automatic path, and a separate **per-version marking** pass for a picker, which cannot short-circuit because a deliberate pick has to mark the rows it will not choose. `buildImportUpgrades` takes an environment (`listVersions` + a REQUIRED `isCompatible`) so no host can quietly skip the check; a host that genuinely cannot read candidate manifests passes `uncheckedVersionCompatibility`, which says so. An IDE reports **no host versions** — it is not the machine that will run the manifest — so only the `telo` axis is checked there; a host requirement still bites at the load gate.

**Adding the block was itself a breaking surface change**: `Telo.Application` / `Telo.Library` documents carry CLOSED schemas in `builtins.ts` (it is their `metadata` that is open, not the doc), so `requires:` is a `SCHEMA_VIOLATION` on every analyzer released before it — unavoidable, unfixable retroactively, and not something a migration can absorb, since there is no legacy spelling of a key that never existed. The mechanism's own problem arriving one release early, and the last time it should be unexplained. **Absent means no requirement, permanently**, for everything published before the mechanism — correct, since none of it uses syntax that did not yet exist. Sequencing that cannot be done retroactively: ship the block and its enforcement, republish the standard library declaring ranges, and only THEN adopt new syntax. **`requires:` is what must be true before telo can run the manifest at all** — a tool the *work* depends on (ffmpeg, a headless browser) is unverifiable, unbounded and carries a per-platform install action, so it belongs in a resource kind provisioned through `telo install`. Plan: `analyzer/nodejs/plans/declared-runtime-requirements.md`; guide: `docs/extend/declaring-runtime-requirements.md`.

### Changing the grammar — MANDATORY

**A surface change is only half done until the modules that adopt it declare a floor.** Widening what a manifest may say — a new annotation, a new SHAPE an existing annotation accepts, a new key on a built-in doc, a new field on a shared fragment — makes every module that uses it unreadable to every already-released telo. Without a floor those modules fail on an older runtime with a diagnostic pointing at their own YAML (`ZONE_ANNOTATION_INVALID`, `SCHEMA_VIOLATION`, an `additionalProperties` violation), which blames the module's author for a version skew. `requires:` is what converts that into one `MODULE_REQUIRES_NEWER_RUNTIME` naming the cause and suppressing the rest.

So, on the same change that widens the surface:

1. **Find every module whose OWN `telo.yaml` uses the new syntax** and give it `requires: telo: ">=<the release that carries it>"`. Not every module that *touches* the feature — the test is whether an older analyzer, reading THAT FILE, would reject it.
2. **The bound is the surface generation, not the package version.** `node scripts/generate-telo-version.mjs` writes `TELO_SURFACE_VERSION`, which is `cli/nodejs/package.json` plus any pending changeset bump — so on the commit that adopts new syntax it is the *unreleased* version that will ship it. **Forward-declaring is correct and expected**; `telo release check` reports such an edge as pending rather than trying to run it, and `publish` refuses it only once the release exists and the range is genuinely refuted.
3. **Verify by EXECUTION, not by reading.** Strip the block, run the previous published CLI against the module (`npx @telorun/cli@<previous> check <manifest>`), and confirm it rejects. If it does not, the module does not need the bound and adding one is a claim nothing checks — the failure class this mechanism exists to remove. Then put the block back and confirm the same runtime now reports `MODULE_REQUIRES_NEWER_RUNTIME` instead.

**Do NOT declare a bound because a module's kinds merely EXPOSE the new syntax to consumers.** A field added to a kind's schema is delivered in that module's own artifact, so the module is readable by an older analyzer and needs nothing; the *app* that writes the new syntax is what needs the floor, declared by its author. `Assert.Events` gaining a `times:` property is this case — an ordinary draft-07 property in an open `KindSchema` body — while `Sql.Transaction` adopting the zone-attribute object form is the other, because the object form is vocabulary the older reader refuses.

**In-repo dependents propagate for free** — siblings import by relative path, so a module adopting new syntax fails its dependents' edge checks — which is why the check is per-file rather than per-dependency-graph.

## Manifest migrations

**A migration is a legacy spelling rewritten to the current one, because published artifacts carry the old and cannot be edited.** Distinct from a **normalization** (`desugarImports`, `normalizeInlineResources`, `resolveRefSentinels`, `resolveSchemaRefKinds`, `rewriteSyntheticOrigins`), which folds authoring sugar into the internal form and is correctly invisible. One "rewrite pass" abstraction covering both was rejected: it would carry a "reported / written back" flag on every entry, putting desugaring one boolean away from editing a user's manifest. Registry + driver in `analyzer/nodejs/src/migrations/`; author guide in `docs/extend/manifest-migrations.md`.

**An entry is DATA in both halves and contains no code** — one JSON file per entry under `analyzer/migrations/`, read as one lexically ordered set. A predicate expressed in one language would be readable by one kernel only, which is the divergence the design exists to prevent. JSON rather than YAML because it is the only format all three runtimes embed with no generation step: Rust has `include_str!`, Go has `//go:embed`, TypeScript has neither and only `resolveJsonModule`. The files sit beside the language implementations rather than inside either; `scripts/copy-migration-entries.mjs` (the analyzer's `prepare`) copies them in and emits the barrel from the same directory listing, so a file that exists always runs — a hand-maintained list was the one place the mechanism could fail silently.

**The patch names what it TARGETS** — `rename-key`, `set-value`, `set-tag`, `insert-item`, `remove-entry`, each with one fixed parameter shape and no path of its own. **Every operation has a known YAML edit form**: that is what makes a migration applicable to a *file* at all, and what lets the driver **derive** whether a quick fix exists — read straight off the verb, never declared, so a missing repair is stated rather than silent. A written `value` must be a **scalar**, refused at entry-READ time: the file applier re-quotes a value in the author's style at the node's own span, which has no meaning for a mapping, so accepting one would make the limitation invisible until a user ran `telo migrate` and was told, permanently, to fix it by hand. The model is JSON Patch's; the *names* deliberately are not, because these are narrower and a lookalike wearing a standard's names invites expectations it does not meet (`move` relocates across parents and replaces an occupied destination; `rename-key` renames within one mapping and *refuses* one).

**A SCHEMA REGION is the one containment a kind list cannot express.** An annotation keyword occurs in author-written JSON Schema, and schema fragments are not confined to kind documents: an inline `inputType:` / `outputType:` on any kind that declares one, an API route's `request.schema.body`, a `Telo.JsonSchema`'s `schema`. That set of kinds is open, and enumerating the standard library's would put resource-kind knowledge into the analyzer. So `inSchema: true` bounds a rule to nodes reached through the **kernel's own** schema-valued keys (`schema`, `status`, `inputType`, `outputType`, `itemType`), which no kind owns — and only with it may `inKind` / `under` be `["*"]`, and only for a rule whose `key` begins with `x-telo-`, both refused at entry-read. That pairing is the containment: the region bounds where the walk may go, the reserved key bounds what it may touch. The wildcard drops the bounded walk, which is not worth pricing at Telo's scale; what it genuinely costs is one wrong-rewrite residue — a schema literal inside an assertion's expected value, rewritten into its own synonym — which cannot be closed in a data-only matcher without naming kinds, and is accepted because the sites it reaches are exactly the ones no enumeration covers.

**The matcher's containment is POSITIVE and required** (`analyzer/nodejs/src/migrations/match.ts`): `inKind` names the document kinds a rule may touch, `under` the region within them it may reach, and nothing outside is reachable; `value`/`valueOneOf`, `withSibling` and `notUnder` narrow within it. **`under` is ANCHORED at the document root** — it names top-level keys and the match must be at or below one of them, which is what makes the containment claim true rather than decorative: a `Telo.Definition`'s `resources:` template body carries other kinds' configuration, so a rule matching "any path segment spelled `schema`" would reach the very user JSON blob the positive form exists to keep out, and delete from it silently. Both gates bound the WALK rather than filter its output (`applicableRules` → `buildMatchIndex`), so a document no rule targets is never walked and a region no rule names is never descended into — this runs on the kernel's boot path for every file in the graph, and `type:` alone occurs a couple of hundred times in a standard-library manifest. Walk-everything-and-subtract cannot be made sound — the set to subtract is unbounded, since any kind whose config carries a user JSON blob can hold something shaped like the node a rule looks for — and it cannot express the guarantee the module surface is promised to carry (*a dependency renames its own field and provably nothing else*), which is a statement about what a rule may REACH and so has to be said positively. Both halves are closed vocabularies and an unknown token is refused, never ignored. A migration that does not fit is a signal to extend the vocabulary, never to hand-write a rewrite.

**One phase, in the loader (`parseLoadedFile`), after parse and before both `precompileDoc` and `desugarLoadedFile`.** The driver invariant is that **a migration only ever matches author-written nodes**, and the position is what makes that structural rather than a convention: a synthetic `Telo.Import` has no YAML document to edit, would record a path the file never had, and shares `variables`/`secrets` *by reference* with the module doc, so a match inside one would apply twice. Before precompile for the same reason in miniature — a matcher must see what the author wrote, not a `CompiledValue`. **No post-resolution phase**: it would sit inside the analyze pass, which the Rust side does not have, so every entry in it would be structurally Node-only — reintroducing the divergence the design exists to prevent.

**Composition is the driver's guarantee, not each entry's proof obligation.** One pass, match set frozen against the pre-migration tree (so no rule matches a node another rule produced), rules ordered within an entry, entries independent — which is cross-party determinism once module entries are aggregated. Idempotency then follows from the driver: a rule matches only the legacy spelling, so re-running finds nothing. **A migration that cannot rewrite leaves the node untouched** (a malformed value, an occupied `rename-key` destination) for the ordinary validator to reject — never guessing, never dropping. Freezing is not enough for a **sequence index**, which is not an identity: a stale KEY path resolves to nothing and refuses itself, while a stale index silently names a different element, so the driver tracks which arrays a patch resized and refuses any later indexed match into one. The file applier is stricter in one further way — two patches whose byte spans overlap cannot both splice, so the later is dropped — and, unlike the tree, it **reports** what it could not write (`migrateFileText`'s `unwritable`), because the diagnostic that sent the author to `telo migrate` would otherwise leave a warning with no way to act on it. **A removal of a mapping entry that OPENS a sequence item splices to the following key** rather than deleting the line (which would take the `- ` with it and fold the item into its predecessor): a legacy ref slot is overwhelmingly an `anyOf` branch written `- type: string`, so refusing it would have made the diagnostic's own advice dead for the case it is most often given in. **The scalar re-quoting rule and the splice loop are ONE primitive** (`analyzer/nodejs/src/yaml-source-edit.ts`, browser-safe), read by the migration applier, `ide-support`'s quick fix and `telo upgrade`'s pin rewrite alike — three surfaces write repairs into the same files, and two copies of a subtle quoting rule would eventually quote one value two ways with nothing to catch it.

**Rewrite always, report locally.** The runtime must read artifacts published years ago, so every file in the graph is rewritten; only the ENTRY module's own files (owner + `include:` partials) report, because a published dependency is not the consumer's to fix. Enforced at `loadGraph` (`LoadedGraph.migrationDiagnostics`), while the per-file record lives on `LoadedFile.migrations`. **Path provenance is part of the contract**: each rewrite records `legacyPath` beside `migratedPath`, `remapMigratedPaths` maps every downstream diagnostic back before position resolution (`assembleGraphDiagnostics`, the editor's closure, and the SDK's `check` seam — all three, since a caller acts on `path` and one surface reporting the migrated spelling would make a manifest mean two things depending on who asked), and `telo migrate` reads its edit target from the same record — the generalization of `rewriteSyntheticOrigins`. Without it a key rename silently downgrades every squiggle on that node to a parent, and a fix among them writes across a parent's span. **The general index is by FILE and every rewrite is in it** — a diagnostic carries at most two routing facts and routinely only one, so indexing by resource identity alone left every diagnostic without `data.resource` and every rewrite in a doc without `metadata.name` (all of `Telo.Import`) simply unreachable. `(kind, name)` is the NARROWING index, never the general one: resource names are module-scoped, so two libraries declaring a `Store` would share one bucket and move each other's squiggles. Where narrowing is impossible — an identity declared in several files with no `filePath`, or two records in one file covering a path with different legacy spellings — nothing is remapped rather than guessed.

**`LoadOptions.migrate` is a third cache axis** beside `compile` and `desugarImports` (variant tag `m`/`x`), opt-in like both. Every resolved consumer passes it; a **round-trip** view must not, since the editor pairs manifests to YAML nodes by index and writes the pair back on save, and `telo migrate` has to see the legacy spelling to find it. Forgetting it fails loudly (the old spelling reaches the validator), never silently.

**A diagnostic composes in three parts and the entry writes only one.** The driver generates *what changed* and *how to apply it* identically for every entry; the entry supplies `reason` — a sentence or two of rationale, never a clause of the generated sentence, and entry-level because one entry may carry several rules that share one story. An entry also declares its stable `id`, `code` and `severity`. **No version stamp**: "can this be deleted?" turns on whether any published artifact still carries the spelling, which the hub can answer and a stamp cannot.

**File application reuses byte-splice editing, not `Document.toString()`** (`migrations/yaml-edit.ts`) — the `cli/nodejs/src/commands/upgrade.ts` precedent: re-serializing re-folds block scalars, drops quote-style hints and reflows strings, so a one-key repair would land as a whole-file diff. The document is never mutated, so every effect of a patch resolves at the location the patch matched. **`telo migrate` is the REFERENCE application, not the only one** — applying pending migrations is an operation other commands compose over a subset of entries, and `telo upgrade` is the case that matters (it should repair what its pin move broke, over just the modules it moved). That composition waits on the module surface, since core-only entries have no per-module subset.

**Two declaration surfaces, one mechanism** — a **core** entry ships with the analyzer and may name any `inKind`; a **module** entry ships in a module's artifact and may name only kinds that module owns. Scope of match and provenance differ, not shape; the closed vocabulary is the trust boundary. The module surface is planned separately, as is the Rust reader and `kernel/specs/manifest-migrations.md`.

A second committed entry is **`normalize-value-types`**, which rewrites `x-telo-stream: true` / `x-telo-binary: true` to `x-telo-type: Telo.Stream` / `Telo.Bytes` and qualifies a bare `TcpPort` / `UdpPort` — the entry the schema region exists for, and the first to use the wildcard forms.

The committed entry is **`ref-slot-scalar-type`**, which drops the scalar `type:` a reference slot pinned back when references were plain strings. It replaced `normalizeRefSlots`, which did the same rewrite at every schema-compile site regardless of `LoadOptions.migrate` — a duplicate with a *different* traversal, and one that falsified the design's own safety property, since a consumer who forgot the flag behaved identically apart from the missing warning. Deleting it is what makes the entry able to prove the mechanism it demonstrates.

## CEL Templates (`${{ }}`)

Pure expression: `"${{ variables.port }}"` → typed value. Inline: `"Hello ${{ variables.name }}!"` → string.

Available in `${{ }}`:

- `variables`, `secrets` — always available (module inputs)
- `ports.<name>` — root Application only; resolved inbound port integers (Application `ports` block)
- `module.<field>` — the DECLARING module doc's own `metadata`, so a manifest reads its own version (`!cel "module.version"`) instead of restating it in a second place nothing keeps in sync. Typed per field from the literal values and **closed**, so `module.verison` is `CEL_UNKNOWN_FIELD`. Per module, not per application: an imported library reads the LIBRARY's metadata (carried across the flattened boundary as `metadata.moduleGlobals.module`, the `variables`/`secrets`/`ports` precedent), because its version is its own. The loader's and analyzer's derived stamps — `source`, `sourceLine`, `module`, `moduleGlobals`, `exportedKinds`, `reExportedKinds`, `forwardedExport` — are filtered out by `authoredModuleMetadata` (`analyzer/nodejs/src/module-metadata-scope.ts`): a DENYLIST, because the metadata vocabulary is deliberately open while the stamps are a closed set this repo controls. As with any expression, the target field must be a CEL slot.
- `resources.<name>` — after that resource's `snapshot()`; republished after `run()`, after each `invoke()`, and on every `ctx.setStatus()`. Available for `with:`-scoped resources inside their scope's regions.
- `resources.<name>.status.<field>` — declared observed state; exists only once the resource has started, so it is illegal in any field that resolves at startup (see Lifecycle)
- `steps.<step>.result` — inside `Run.Sequence` steps
- **Member access on a RESOURCE INSTANCE reads its published state**, and it is typed as one. A ref slot holds the live instance after Phase-5 injection, which CEL cannot read a member off at all, so a template body could not read a scalar off a resource it references — `SqlRepository` building a statement from the table it points at is the case that forced it. `self.<ref>.<field>` now answers exactly as `resources.<name>.<field>` does: the same fact, the same reading, rather than a second meaning for the same name. `celSelfView` (kernel `evaluation-context.ts`) substitutes each instance's last published reading, recorded by instance identity in a WeakMap beside the single publication path — keyed by instance because a ref slot carries no name, and one-directional, so an entry is a reading OF an instance and never a way to obtain one. A whole-value `${{ self.connection }}` is untouched: that form matches `SELF_PATH` and is navigated directly, yielding the instance itself, which is what a ref passed straight through needs. The view is memoized per `self` object and invalidated against the exact readings it substituted — a template expands its body on every dispatch, so rebuilding it per call put an O(fields) walk on the per-request path. Per view, never a global counter: `publishedPropsOf` publishes a new props object every time, so identity IS the version, while a process-global counter is bumped by every `invoke()` (defeating the memo under any concurrency) and is shared across in-process kernels (so one app's traffic invalidates another's). The check is O(refs), and a view that substituted nothing is always current. The STATIC half is `analyzer/nodejs/src/ref-slot-reading.ts`: a ref slot inside a kind's `schema:` is retyped as the reading it yields, so `self.<ref>` is no longer the annotation node (a title, a description and `x-telo-ref`, off which nothing types). Its two halves type as `resources.<name>` does and for the same reasons — `status` is DECLARED so it is closed and a typo below it is `CEL_UNKNOWN_FIELD`, while the flat half is whatever `snapshot()` returned, which no manifest declares, so it stays open. A slot constrained to SEVERAL kinds keeps only the status fields all of them declare: a read valid against one permitted target must not be rejected because a sibling does not report that field.
- `request` — inside handler CEL (HTTP: query, body, params, headers, path, method)

**A CEL integer is int64 and needs no cast, anywhere** (normative: `kernel/specs/invocation-contract.md` §4.3–4.4). `int` evaluates to a JS BigInt, so `size(...)` / integer arithmetic produce one — and a BigInt used to be unable to leave a manifest: `JSON.stringify` throws on it, and AJV's type check is `typeof data == "number"`, so declaring `type: integer` rejected it *before* serialization. The only way out was `double(...)`, which says "float" about an integer and truncates past 2^53; it had spread into the stdlib's examples and docs. Both doors are open now, in the kernel, so **no module and no manifest handles this**: `boot()` installs `BigInt.prototype.toJSON` over `JSON.rawJSON` (`enableBigIntJson`, `kernel/nodejs/src/bigint-json.ts` — a composition-root action, so the installer is kernel-side; it **throws** rather than degrading on a runtime without `JSON.rawJSON`, since every site that used to carry its own handling now relies on it). A BigInt then serializes as its **exact decimal digits** — not a new policy, but what `fast-json-stringify` already emitted for a schema-typed `integer`, so the runtime's two JSON serializers now agree at every magnitude rather than only below 2^53. Process-global, in the same spirit as the `process.env` guardrail, so it covers every JSON boundary in the process including a third-party module's. The validator half is `withBigIntsAsNumbers` (`kernel/nodejs/src/bigint-schema-view.ts`), owned by `SchemaValidator.compile()`'s validator and `ctx.validateSchema` — **one layer, not two**: the contract binding validates the raw value and lets the validator normalize, merging the `useDefaults` fills back (**index-wise through arrays**, since AJV writes defaults under `items` too) so the dispatched value keeps its 64-bit range. `double(...)` retains only its real meaning — moving into the double domain for arithmetic, where CEL has no `int OP double` overload. Because `toJSON` runs **before** a replacer, a serializer that deliberately encodes a BigInt differently reaches the original through `bigIntAt(this, key)` (`@telorun/sdk`, the module-author half): `encodeJsonValue` tags it (a persisted value must replay as the same type), the `json` log encoding quotes it past the safe range (as OTLP does), and the `pretty` console encoding renders it as text. A `typeof v === "bigint"` replacer anywhere else is now dead code that changes an encoding silently. Regression coverage: `tests/integer-json-boundary.yaml`, `kernel/nodejs/tests/bigint-json.test.ts`.

**A declared contract is normalized on the way OUT, so the declaration is TRUE and not merely satisfied** — the service a JSON Schema gives an HTTP response serializer. `declaredScalarPaths` (`analyzer/nodejs/src/invocation-contract.ts`, browser-safe, the `defaultBearingPaths` precedent) reads the representation a contract schema declares, and `bindContract` normalizes the produced value along exactly those paths before returning it. **Representation-driven, never integer-specific**: a value type is read through the same rule rather than beside it, so a `json` representation contributes its `base` (`Telo.TcpPort` is an int64 slot) while an `instance` one REPLACES the JSON layer — bytes and streams are already their own representation, nothing converts to them, and the walk stops rather than descending into a value that is not a plain container. `type: number` is the symmetric case and normalizes the other way. Only an EXACT conversion happens: an integral number becomes an int64, an int64 becomes a double only when the round-trip is lossless, and everything else arrives unchanged — so a value that genuinely violates the contract is still rejected rather than quietly repaired, and a 64-bit integer is never truncated to reach a `number` slot. Bounded by the schema, so a contract declaring no such scalar walks nothing at dispatch. **Outputs only, deliberately**: normalization states what a value is to whoever reads it NEXT, and on the way out that reader is CEL, which already types the declaration as `int` — there the declaration and the value genuinely disagree. On the way in the reader is a controller in the host language, where handing it an int64 would change the authoring surface of every module rather than repair a false declaration. The consequence is on the module-author surface: **a controller reading another resource's declared-integer output must accept both representations**, which is what `integerInput` (`@telorun/sdk`) is for — `Number.isInteger(...)`, `setTimeout(fn, ms)` and plain arithmetic all reject an int64. A module published before this change and doing so breaks until republished.

**How `steps.<name>.result` gets its type**: through the shared contract resolver (`resolveContract`, `analyzer/nodejs/src/invocation-contract.ts`), in order: (1) the **invoked resource manifest's own `outputType` field**, (2) the **kind's** contract resolved along `extends`, (3) permissive `{type: object, additionalProperties: true}`. Layer 1 is what makes **per-instance response narrowing** work: a kind that declares an `outputType` property in its schema (`x-telo-ref: Telo.Type`, as `JS.Script` does) lets an author narrow one call site's result and have CEL type-check against it — no analyzer change needed. A wrong narrowing no longer type-checks against a lie unnoticed: the kernel binds the same resolved contract to the instance and validates the produced value at dispatch. A type field resolves from any of four forms (`resolveTypeFieldToSchema`): a bare type name, a `!ref`, an inline `{kind, schema}`, or raw JSON Schema.

**Resource-doc validation injects only `kind` and `metadata`** into a definition's `additionalProperties: false` schema. Every other top-level field an author may write — including `outputType` — must be declared as a property in the kind's own `schema`, or validation rejects it.

**Null-safety:** dereferencing a value whose schema admits `null` (e.g. `error` inside a `finally` block, typed `["object","null"]`) without a null-guard is a static error (`CEL_NULLABLE_ACCESS`). The analyzer recognises guards through `?:` ternaries and `&&` / `||` short-circuits — `error != null && error.code`, `error == null ? … : error.code`. General: applies to any nullable value in any CEL context (`templating/nodejs/src/cel/analyze.ts` `findNullableAccessIssues`, wired in `engines/cel.ts`).

## Module Documentation — MANDATORY

**Every module change MUST include documentation updates.** This is not optional. Before finishing any task that adds or modifies a module, verify:

1. Documentation exists in `modules/<name>/docs/` (and the module's `README.md`). If not, create it.
2. Documentation matches the current code. If code changed, docs must be updated.

Module docs live **with the module** and are surfaced through the Telo **hub** (`hub.telo.run`), which indexes each published module's manifest and docs — the standard library is discovered there, not embedded in the Docusaurus site. Do **not** wire per-module doc files into `pages/docusaurus.config.ts` / `pages/sidebars.ts`; the docs site links out to the hub for module discovery. The Docusaurus site is for the kernel/guides/extend/learn docs only.

## Manifest descriptions — MANDATORY

`metadata.description` on a `Telo.Library` and on every kind doc (`Telo.Definition` / `Telo.Abstract`) is **hub search text**: the hub embeds it for semantic search, so it is read by someone who does not yet know the module exists. Write it for that reader, not for a maintainer.

- **Say what it does, in terms of the problem it solves.** Lead with the capability and the vocabulary a searcher would type (locks, leases, retries, pagination, idempotency, …).
- **Keep it to one paragraph** — roughly 40–60 words. It is embedded as a single vector; a long multi-paragraph text dilutes it. Rationale, design history and trade-offs belong in `docs/` and in YAML comments above the doc, never in `description`.
- **No kind names, no capability names, no "the X abstract".** The kind and capability are already structured metadata on the doc. `The KvStore.Store abstract — a durable store…` → `Durable key/value storage…`.
- **No implementations, no backend names.** A generic module must not name the modules that extend it (`backed by Redis SET NX` / `kv-store-sql`); that coupling is backwards and pollutes search hits for the generic kind. Backends describe themselves.
- **No contrast with sibling modules.** `Cache.Store is also a key/value store, but…` reads as noise to a searcher and drags the sibling's terms into this vector. State this module's own guarantee positively.
- **No wording that only makes sense against history.** `NON-EVICTING`, `unlike before`, shouting caps for emphasis. Say `records live their full TTL and are never dropped early`.
- **Kind descriptions state the operation and its contract** — inputs, outputs, and what a failure/edge return means — in two or three sentences. See `modules/collection/telo.yaml` and `modules/kv-store/telo.yaml` for the target shape.

## Manifest categories

`metadata.categories` is the **declared grouping facet**: an unordered list of domain **display labels** (`[AI, Storage]`) on a `Telo.Library` (and optionally on a kind doc, where it *replaces* the module's for that kind). It is a facet, not search text — it never belongs in `description`, which is embedded as a vector.

**Authors write labels; the hub derives slugs.** `metadata.categories: [AI]` is indexed as slug `ai` + label `AI` (`category_slug()`, defined once in the hub migration). Filtering and URLs use the slug (`?category=ai`, accepted as either form since the parameter is slugified too); UIs print the label. That normalization is what makes `AI` and `ai` one group, and what keeps `Data Codecs` out of a URL as anything but `data-codecs` — an open vocabulary can't be validated into agreement, but spelling variance can be normalized out of it. It only sees variance the rule covers: `A. I.` slugifies to `a-i`, a group of its own. Because `ai` → `AI` isn't recoverable, both are stored, aligned by position (`categories` / `category_labels`); when several labels share a slug the facet shows the most-declared one, ties lexicographic.

**The vocabulary is open and nothing validates it.** A category is a plain string; whatever labels modules declare are the groups that exist. There is deliberately no list in the kernel, the analyzer, or the hub — a closed enum would block a third-party module in a domain the standard library never anticipated, and would make the analyzer's release cadence the bottleneck on naming. Reuse an existing label when one fits (a near-synonym like `caching` vs `Cache` still splits a group — normalization only fixes spelling variance); the standard library uses `AI`, `Compute`, `Configuration`, `Coordination`, `Data`, `Observability`, `Performance`, `Reliability`, `Scheduling`, `Storage`, `Streaming`, `Testing`, `Transport`, `Visualization`.

**Only the hub slugifies.** The editor compares labels directly (case-insensitively) because a category never crosses an authorship boundary there — it groups kinds already resolved in one workspace, and a workspace library may be unpublished or unsaved, so there is no hub row to consult. Keeping the rule in one place is deliberate: two implementations would have to agree forever.

The **derived** grouping axis needs no declaration: a kind's `extends` target is the contract it implements. The hub resolves the alias prefix through the declaring manifest's own `imports:` map into `(owning module ref, kind suffix)` at ingest (`resource_kinds.extends_ref` / `extends_kind`); the editor does the same against the declaring library's imports (`resolveContract`). That is what groups every backend of one abstract together across module boundaries, and what nests `CacheRedis.Store` under `cache.Store` in the resource picker.

## Module metadata — descriptive fields, deprecation, runtime reach

The `metadata:` block on a module doc carries `name` (the only field anything resolves against) plus purely descriptive `version`, `description`, `repository`, `homepage`, `documentation`, `license`, `categories`, `deprecated`. Publish projects several onto OCI annotations (`oci-transport.ts`); nothing else reads them. **Because nothing branches on them, a mistyped one has no runtime failure mode** — so `validate-module-metadata.ts` (analyzer) type-checks the known fields and reports an unknown key only when it is a near-miss of a known one (`licence:` → `license`). The vocabulary stays **open**; there was previously no schema for `Telo.Application` / `Telo.Library` metadata at all (`metadataSchema` in `manifest-schemas.ts` is wired only into `Telo.Definition` / `Telo.Abstract`).

**No `authors` / `maintainers` field, deliberately.** Registration is open and unauthenticated, so a declared author verifies nothing; the hub derives a **publisher** from the ref's host + org (`module_publisher(ref, transport)`), because ownership is a property of the host. A `url` module is attributed to its host alone — its path segments are a directory, not an organisation.

**`metadata.deprecated: { reason, replacedBy? }`** is legal on a module doc and on any kind doc. `replacedBy` is **resolvable, and its form follows the level**: a kind names an alias-qualified kind (`Self.<Kind>` / `<Alias>.<Kind>` / `Telo.<Kind>`) resolved through the declaring file's own `imports:` — the identical path `extends` takes, so the hub reuses that resolver and stores `(replaced_by_ref, replaced_by_kind)`; a module names a **module ref**. Optional, because a module superseded by a kernel built-in has no module to point at. A kind whose replacement is in an un-imported module cannot be named — deprecate at module level instead, rather than inventing a second grammar or adding a real dependency to name a target. Diagnostics: `INVALID_DEPRECATION`, `DEPRECATION_REPLACEMENT_UNRESOLVED`, `METADATA_UNKNOWN_FIELD`, `METADATA_INVALID_TYPE`.

**Runtime reach is derived, never declared.** Which kernels can host a kind follows from its `controllers:` PURL candidates: `pkg:cargo` → **both** kernels (Node's `napi-loader` builds the crate as a `.node` addon, the Rust kernel's `cargo_loader` as a cdylib), `pkg:npm` and `pkg:telo/local/js` → Node only, `napi`/`wasm` bundle formats → no kernel today. **`telo module manifest --json` reports it** (`cli/nodejs/src/controller-runtime.ts`) and the hub stores what it is told — the PURL→kernel mapping is loader knowledge, and a second copy in a consumer would drift silently the day a loader lands. Three invariants: it is **per kind**, not per module (`std/console` has Rust controllers on two of four kinds, so a module boolean would lie — the roll-up is full/partial); a controller-less kind is **`portable`**, a flag rather than an enumeration of today's kernels, which would go stale when a third kernel ships; and **language is a separate axis from runtime**, left blank for `napi`/`wasm` whose source language the PURL cannot determine.

**The kernel labels are `nodejs` / `rust`** — the ones `LABEL_TO_PURL_TYPE` (`runtime-registry.ts`) already gives an `imports:` entry's `runtime:` field, and the implementation directory names. A third spelling for the same two kernels would mean an author who wrote `runtime: nodejs` had to learn a different word for the hub's filter. The hub's `runtime` param is an **enum** on both HTTP routes and the MCP tool: an unrecognized value would otherwise match only portable kinds, a near-empty result that reads as "no such module" rather than "bad filter".

**The hub records that it ASKED for the runtime block separately from the answer** (`module_versions.runtimes_asked`). Inferring it from `runtimes IS NULL` cannot work: that is also what a CLI too old to report the block leaves behind, so the tracker would re-enter the whole ingest branch — origin pull, R2 put, kinds/resources rewrite, vector purge and re-embed — on every pass forever. Same distinction the `integrity` column draws between NULL and `''`, made observable instead of inferred.

## Controller delivery — bundle, don't publish to npm

A `Telo.Definition` names its controller with a PURL, and there are two delivery modes:

- `pkg:telo/local/js?path=./nodejs/<module>.mjs&local_path=./nodejs/src/index.ts#<Export>` — **bundled**: the controller ships inside the module's own artifact. **This is how the standard library delivers.** Nothing is fetched from npm at load. **A module is ONE bundle**, and every kind of it names that same entry and differs only in its `#fragment` (see Mechanics 1 below).
- `pkg:npm/@telorun/<pkg>@<ver>?local_path=./nodejs#<export>` — a published npm package. Still supported for third-party modules; in this repo it is what the **deferred** modules use — `http-server`, `sqlite`, `image`, `pdf`, `starlark` — each of which either loads a native/wasm payload or inlines a dependency that resolves an asset relative to its own module URL. Don't add new ones.
- `pkg:cargo/<crate>?local_path=./rust#<entry>` — a **Rust controller crate**, built on load from a source checkout. `starlark` and `console` carry one. Both kernels consume the identical candidate; what differs is the loader (Node's `napi-loader.ts` produces a `.node`, the Rust kernel's `cargo_loader.rs` a `cdylib` opened over `telorun-abi`) and the SDK backend each selects at build time — `--features telorun-sdk/napi` vs `--features telorun-sdk/native`. **`telorun-sdk` declares no default backend**: the controller crate has no `[features]` block, so `--no-default-features` on that build would target the wrong crate, and a dependency feature is the only selector that works. There is no published-artifact story for these yet — `?local_path=` resolves only in a checkout, so a bundled native layer (`pkg:telo/local/dylib` + `os`/`arch`/`libc` qualifiers) is what a distributable Rust controller still needs.

**PURL anatomy** (`kernel/nodejs/src/controller-loaders/bundle-loader.ts`) — every segment carries meaning: type `telo` = Telo-delivered rather than fetched from an ecosystem registry; namespace `local` = bundled in the artifact (reserving `pkg:telo/registry/…` for a controller fetched as its own artifact later); **name = the artifact format** (`js` is all the Node kernel hosts today; `napi`/`wasm` raise `ControllerEnvMissingError` so a candidate list like `[pkg:telo/local/napi …, pkg:telo/local/js …]` falls through to one this — or another runtime's — kernel can load); `?path=` is the built file relative to `telo.yaml`; `?local_path=` is the TypeScript source it was built from; the `#fragment` is the named export selecting one kind's controller out of the module's single bundle (omit it and the whole bundle is the controller, which only fits a one-kind module); (A library's entry point is named by `exports.code:` instead — data rather than a PURL, since it never fetches; see Mechanics 4.) Format is explicit because bundling is the one delivery mode not tied to an ecosystem's runtime (npm ⇒ JS, cargo ⇒ Rust; a bundle is just files).

**Mechanics of bundling:**

1. **Sources** live in `modules/<name>/nodejs/src/*.ts`, and **`src/index.ts` is the module's single entry point** — it re-exports one namespace per kind (`export * as SqlQueryController from "./sql-query-controller.js"`), which is what the PURL fragments select. One bundle per module is not a packaging preference: a bundle is a module graph, so a shared source file compiled into two bundles is **two module scopes**, and any state the module keeps beside its instances (a registry, a `WeakMap`, a counter) silently becomes two of them. That was the live `sql` bug — six controller bundles, six copies of the connection registry. One bundle makes it unrepresentable rather than merely avoidable; the cost is that laziness is per module rather than per kind. `modules/<name>/nodejs/package.json` is `"private": true`, named `@telorun/<name>-build`, and is **never published**. It exists for two reasons only: to declare the dependencies esbuild inlines, and to **type-check** the sources (esbuild does not). **Five packages keep publishing**, because each is the TS contract a third-party implementation compiles against, not module code: `codec`, `http-dispatch`, `kv-store` and `type` declare no controller at all, and `sql` — which does — stays published only because `sqlite` is still `pkg:npm`-delivered and depends on it; the day that module is bundled, `sql` goes private too. `ai`, `cache`, `embedding` and `vector-store` are module code and no longer publish: a dependent reaches them through the `exports.code:` seam at run time (Mechanics 4), not through npm. One rule: a package publishes iff someone outside this repo needs it to *build* — nothing ever loads any of them at run time, since no PURL names them.
2. **The kernel builds the bundle; a module's own `build` script only type-checks** (`tsc -p tsconfig.lib.json`). `CONTROLLER_BUNDLE_OPTIONS` (`controller-loaders/source-bundle-builder.ts`) is the single option set, used on the run path AND on the publish/release path through `buildControllerBundle` — so the bundle a contributor runs IS the bundle that ships, rather than two esbuild invocations kept agreeing by convention. The emitted `nodejs/<x>.mjs` is a build artifact, gitignored via `modules/*/nodejs/*.mjs` — never commit it, and never re-add an esbuild step to a module's `build`. The `--banner:js` `createRequire` shim is not optional: it defines `require` in module scope so esbuild's `__require` shim (emitted for a bundled CJS dependency) resolves instead of throwing "Dynamic require of X is not supported" under Node. `--conditions=source` is not optional either: an inlined workspace TS library must be taken from its `src/`, not its `dist/`, or building a controller would depend on having built every library it inlines — the exact build step this design removes, and a hard "Could not resolve" on a fresh clone. Every inlined package declares `source` ahead of `import` in its `exports`. esbuild is pinned to one version through a pnpm `catalog:` entry.
3. **`@telorun/sdk` stays external, never inlined.** The bundle has no `node_modules`, so `BundleControllerLoader` symlinks every name in `REALM_COLLAPSE_NAMES` (`controller-loaders/realm.ts` — `@telorun/sdk` today) into a `node_modules/` beside the bundle, pointing at the kernel's own copy. Standard resolution then finds it on both Node and Bun (ESM resolve hooks aren't honoured by Bun; Bun's plugins don't intercept runtime imports — a symlink is the one portable mechanism). That collapses *identity* as well as resolution, so `Stream` / `InvokeError` `instanceof` checks hold across the kernel/controller boundary. Authors write a plain `import { … } from "@telorun/sdk"`.
4. **A module-owned library stays external too, and is resolved through the import graph.** A library declares, once, on its own `Telo.Library` doc, which bare specifier its code is imported by — under `exports:`, beside the kinds and instances it already exports, because that is what it is: `exports.code: [{ specifier: "@telorun/sql", format: js, path: ./nodejs/sql.mjs, source: ./nodejs/src/index.ts }]`. **Data, not a package URL**: `controllers:` needs a PURL to be able to name an ecosystem fetch (`pkg:npm`, `pkg:cargo`), while this always names a file the module already ships, so `pkg:telo/local/` is constant noise before the first real datum — and a query string is one opaque box to the visual editor. `format` plus the optional `os`/`arch`/`libc` build the same `ArtifactSelector` a controller candidate does, so layer matching and platform fallthrough are unchanged. The kernel joins that to the consumer's `imports:` (`Sql: ../sql`) during `kernel.load()` — the only point where the import edges, the target's manifest and the target's artifact are all in hand (`kernel.buildSiblingLibraries` → `controller-loaders/sibling-libraries.ts`) — and the loader resolves the specifier to **that module's own entry point** instead of letting esbuild copy its source in. Since that entry is usually the same file the module's controllers come out of, `@telorun/sql` is one module scope across sql's own six kinds and every dependent. The specifier is declared by the **library** rather than per consumer, because it is a property of the library (its name in a host ecosystem), not of the relationship — and sitting beside the format keeps runtime **derived, never declared**: the entry says `format: js`, and a future Rust entry carries `specifier: telorun-sql` with no runtime-keyed map anywhere. **One specifier, one entry point** — subpaths are deliberately unrepresentable, since reproducing npm's `exports` map inside the artifact would import a package manager's resolution semantics; importing one is a hard build error. Resolution is a **synthesized package** (`package.json` + a re-export shim) written beside the bundle, not a symlink: a published artifact ships files, not a `package.json`, so there is nothing standard resolution would accept — and generating it keeps the whole mechanism inside the loader and off the artifact contract. Every consumer's shim re-exports the same file, and Node keys its registry by resolved URL, so one library is one scope however many shims point at it. **Only workspace modules are de-inlined**: `kysely` / `pg` have no module artifact to resolve against, and inventing one would be building a package manager. Two guards keep the property from decaying silently, both in the builder because the analyzer is browser-safe and has no sources to read: a **subpath import** of a declared specifier is a build error, and a metafile input reaching into a sibling library's **entry-source directory** by any other route (a relative path, a transitive hop) is a build error naming the files. The directory is the entry source's, never the module's — a module directory holds its tests, and a fixture module nested in one is a different module whose bundle is its own. **Dedup is per (module, resolved version), and skew is a warning**: the import pin is the honest granularity, so two dependents pinning different versions legitimately run two scopes — that is different code — and the kernel says so rather than pretending otherwise. **An npm-delivered controller is outside the seam entirely**: `sqlite` resolves its `@telorun/sql` from its own tarball, so that copy is a second scope and nothing reports it — the kernel cannot see inside another delivery mode's package. It closes when that module is bundled; until then a shared-state seam must not assume one scope (which is why `sql` keeps its executor `WeakMap` on the connection instance).
5. **There is no build step in development.** When the declaring module has **no artifact handle** and `local_path` resolves on disk, the loader builds the controller from source with esbuild (`source-bundle-builder.ts`) and imports that — so a fresh clone runs `pnpm run telo ./manifest.yaml` after `pnpm install`, and editing `src/*.ts` and re-running picks the edit up. The guard is the *absence of an artifact*, not the shape of the base URI: a published module served from the on-disk manifest cache also has a local base, and its payload is still its layer. The cache under `<entry-dir>/.telo/controller-src/` is keyed on a digest of **every input esbuild reported** plus the build options — a bundle's inputs are a graph, so an entry-only staleness check would serve a stale controller after an edit to a sibling or to a shared library. A changed input is a different key: nothing to invalidate, and a cross-process race (the test suite spawns a kernel per manifest) writes identical bytes to identical paths, through a temp file and an atomic rename. **The publish path takes the same builder** (`buildControllerBundle`, which returns the bytes AND the metafile inputs the release edge graph is built from), so there is no `build:bundles` prestep and no staged artifact to go stale — but there the optional-esbuild fallthrough to the prebuilt `path=` file is a HARD failure, since digesting a stale bundle is exactly what the release design exists to prevent.
6. **`files:`** on the `Telo.Library` doc is the gitignore-style allowlist for what the manifest cannot otherwise name — assets, static files, sidecars. A controller's `path=` entry point joins the payload **because `controllers:` names it**, so it is never restated in `files:`, and a module whose only payload is its controller declares no `files:` at all. Symlink confinement is checked over the whole partition (`assertWithinModule`), not just the pattern match. Publish then **partitions** the payload into layers — see Layered module artifacts below.
7. **Loading materializes one layer.** `BundleControllerLoader` picks the candidate this host can run and asks the module's `ModuleArtifact` for that selector's directory; it never fetches, and never treats a module ref as a path. Missing file, unparseable PURL, non-`local` namespace, unhostable format, and a platform the host does not match are all env-missing (fall through to the next candidate); a bundle that imports but is malformed is a hard `ERR_CONTROLLER_INVALID`, and a source that fails to build is `ERR_CONTROLLER_BUILD_FAILED` — a real user-code failure is never masked as env-missing.
8. **Releases:** a bundled module publishes nothing to npm, so it takes **no changeset** — its version is its module's, moved by `telo release apply` (see Versioning & releases). What decides that it moved is the **payload digest**, not a path rule: a bundle inlines its dependencies, so a shared-library fix changes its bytes while touching no file under its directory.
9. **A dependency that resolves a file beside itself cannot be inlined.** A package that reads an asset relative to its own module URL (`__dirname`, `import.meta.url`) looks for it beside the *bundle* instead, where it is not — the failure is a runtime "file not found", not a build error. `http-server` is deferred for exactly this (`@scalar/fastify-api-reference` loads `dist/js/standalone.js`). Such a module keeps `pkg:npm` until it ships the asset in its own layer.

## Layered module artifacts

A published module is **one artifact of several layers**, not one tarball — normative spec at `kernel/specs/module-artifact.md`, model/parser/matching in `analyzer/nodejs/src/artifact-{selector,layer-index}.ts` (browser-safe, shared by `telo check` and the runtime, same precedent as the redaction path parser).

- **Layers by role:** `manifest` (`telo.yaml` alone), one `controller` layer **per selector**, one `library` layer **per selector** (the `exports.code:` entry point a *dependent module* resolves this module's declared specifier to), `assets` (what the author's optional `assets:` list claims, fetched lazily on first module-relative access), and `common` (everything unclaimed).
- **`library` is its own role because it is materialized by a different event**: a controller layer is reached when one of THIS module's kinds is instantiated, a library layer when a DEPENDENT's code imports it — which happens with no kind of this module in play, and happens for a module that has no kinds at all. Per selector rather than a singleton, for the same reason a controller layer is. A file named by BOTH an `exports.code:` entry and a `controllers:` candidate — the normal shape, since a module is one bundle whose controllers are fragment-selected — lands in the **library** layer: that is the weaker precondition, since a consumer must reach it without loading this module's controllers while the reverse never holds. So `materializeController` pulls **both code roles plus `common`** for its selector, and a consumer's resolution pulls the library role alone.
- **A selector** is `format` + optional `os`/`arch`/`libc` PURL qualifiers on the same candidate (`pkg:telo/local/napi?path=./rust/x.node&os=linux&arch=amd64&libc=gnu`), in the OCI/GOOS vocabulary. Matching is one rule per axis: an axis the selector omits accepts anything, an axis it states must be equal; an undetermined *host* axis matches nothing that constrains it. So a Node kernel never downloads the `napi` layer, and a `linux/amd64` host never downloads the `darwin/arm64` binary. Selection reuses the existing `ControllerEnvMissingError` fallthrough — `ControllerPolicy` is untouched — and the platform check runs **before** materialization, or a candidate list would fetch every platform on the way to the right one.
- **The sink runs toward correctness.** An unclaimed file joins `common`, which is materialized alongside *any* code layer **and** on any module-relative file read, so both an undeclared sidecar (a `.wasm` beside its glue) and an unclaimed static file are on disk when needed — a module shipping only static files has no controller to ride along with. `assets:` and the `siblings=` qualifier are optional refinements: omitting either costs bytes, never a load failure. Publish prints the partition so an author sees where each file landed.
- **The `layers:` index** in the published `telo.yaml` replaces the old scalar `filesIntegrity`. Per layer: `role`, `selector`, `blob` (OCI blob digest — addresses the layer and verifies the transfer) and `integrity` (framing-independent content digest — verifies what is extracted, re-derivable from disk). It lives in `telo.yaml` because the import pin hashes `telo.yaml` and nothing else; the OCI manifest is fetched by a mutable tag and is outside the chain, and pinning *it* is circular since `telo.yaml` is one of its layers. The manifest layer has no entry for the same reason. Chain: `import pin → telo.yaml → blob digest → layer contents`.
- **The index is written by the PAYLOAD BUILDER, before anything is pushed** (`ModulePayloadBuilder.buildPayload` → `Transport.layerIndex`), so `publishedManifest()` returns the bytes that ship. It used to be injected by the transport at push time, and that made the builder's manifest a document no registry holds — while a dependent's sibling pin is a hash of exactly that text, so **every module shipping a payload published a pin naming bytes nobody serves**, and 18 standard-library modules could not resolve their own dependencies at load. Nothing caught it: `payload-drift` compares layer digests, which injection does not move, and the ledger's `manifest` digest was pre-injection on both sides. What the fix requires is that a `blob` be knowable before its blob is pushed, so **layer framing is a pure function of the files** (`makeTarGz` pins every header field that is not name or contents — which is also reproducibility) and `publish` **verifies** each pushed blob against the index rather than rewriting it: the manifest may already be pinned, so a disagreement is fatal, not correctable. Framing stays the transport's (`layerIndex` is on `Transport`), since a `blob` digest covers framed bytes.
- **Addressing never reads the OCI layer list** — the pinned index is self-addressing, so a republish that reorders layers is invisible rather than fatal. Only the *manifest* layer is located through the OCI manifest (by media type), and its bytes are then pin-verified. Flat layer list, never an image index: the manifest and asset layers are platform-neutral, so an index would duplicate them per platform.
- **`ModuleArtifact`** (`kernel/nodejs/src/bundle/module-artifact.ts`) is built during `kernel.load()`, the only point where the **pinned** ref (`requestedUrl`) and the already-verified manifest are both in hand — a controller loader sees only the canonical base URI, which carries no `#sha256-`, so a self-fetching loader would degrade to trusting the cached `telo.yaml`. It memoizes per layer and serializes through `withDirectoryLock` (`kernel/nodejs/src/directory-lock.ts`, shared with `NpmControllerLoader`).
- **Module files are reached through `ctx.resolveModuleFile(relative)`** (SDK), which returns a **URI** and materializes the `assets` layer on first use. Never derive a directory from `ctx.moduleContext.source`: for a published module the manifest URL is not where the payload lives, and a `dirname` of it silently resolves against the process cwd. `Http.Static`, `mcp-client`, `assert`'s manifest loader and `Test.Suite` all use it.
- **Layers are OCI-only.** The registry origin is read-only and publishes nothing, so it serves manifests only; a bundled payload is always an OCI artifact.
- **Pre-layers artifacts still resolve.** A single-blob artifact (`application/vnd.telo.module.v1+tar`) contains `telo.yaml`, which is all the read path wants, so every module published before layers keeps loading — that is what leaves npm-backed modules untouched. It carries no index, so a *payload* published that way fails at the controller with an actionable republish error. Only the six modules shipping `files:` need republishing.
- **`telo install --platform os/arch[/libc]`** pre-materializes every layer that target could need (cross-architecture image baking); `telo run` materializes lazily. Cache warming is an optimization, never a correctness requirement — which is the bug this replaced, where a cold `telo run` failed because payloads landed on disk only after the load that needed them.
- **Publish gates on bytes, not on a ledger.** A bundle inlines its dependencies, so a fix in a shared TS library — or a transitive bump the lockfile alone moved — changes a dozen modules' shipped bytes while touching no file under any of their directories and moving no package version. `telo publish` therefore builds the payload and compares each layer's `integrity` against the artifact already published at that `metadata.version` (`cli/nodejs/src/bundle/payload-drift.ts`), refusing to publish changed bytes at an unchanged version and naming the digest that moved. Exact rather than inferred: it cannot miss what no version records, and cannot fire spuriously, because identical bytes hash identically. This replaced the auto-fragment step in `version-packages.mjs`, which answered the same question by proxy. **The drift question is answered on the module track only** — `telo release status`, whose plan moves `metadata.version` in the module Version PR, so a module whose bytes moved with no bump is a pending bump there. It used to be re-asked as a `--dry-run` pass in the npm publish script, which is the one place it could only misfire: see the publication split below.

## Versioning & releases — MANDATORY

**The whole repo is intentionally pre-1.0, and staying pre-1.0 is the goal.** Breaking changes are released as **minor** bumps on purpose — both `@telorun/*` npm packages and Telo modules. A documented breaking change shipped as a minor (or a module's `Added` fragment for a breaking change) is the convention working as designed, **never** a versioning defect. Do not flag "breaking change shipped as minor" in reviews. The CI guards (`telo release check`'s major rejection, the changeset major-bump guard) exist to *enforce* this — anything that would bump to 1.0.0 is the error, not the minor.

Two release tracks, split by artifact:

- **npm packages → changesets.** Every change to a published `@telorun/*` package MUST ship a changeset. Add one file under `.changeset/` (one per logical change, listing every affected package) and `git add` it. Use `pnpm changeset add --empty` when a change genuinely needs no release. The gate is `scripts/check-changeset-status.mjs`, not `changeset status` directly: private `-build` packages are versionable, and every package under `modules/*/nodejs/` is now module-owned (its version is its module's), so both are filtered out; only a changed **published, non-module** package with no changeset fails. The same module-owned set is in `.changeset/config.json`'s `ignore`, so the two ledgers never write the same field.
- **Telo modules → `telo release`.** See `docs/extend/releasing-modules.md` and `plans/telo-release-versioning.md`. Modules get their **own Version PR** (`module-release/main`, `chore(release): version modules`), opened on every push to main independently of whether npm changesets are pending — they used to ride the changesets PR whenever one existed, which made one review cover two ledgers, and a release routinely republishes sixty modules because a shared library reached their bundles. Its body is GENERATED from `telo release status -o json` captured **before** `apply` consumes the fragments (`scripts/module-release-pr-body.mjs`): declared changes first, unattributed republishes as a table, degrading in stated stages under GitHub's 65536-character body limit — an over-long body is rejected outright rather than truncated, so the PR would open with no body at all. A module has **one version** across `telo.yaml`, `nodejs/package.json` and `rust/Cargo.toml`, and one changelog. Write a fragment with `telo release add --module modules/<name> --kind Fixed --body "…"` (`.changes/pending/*.yaml` — one file, several modules, one body, with the kinds `Added | Changed | Deprecated | Removed | Fixed | Security`). Never hand-edit `metadata.version`.

**The release system exists because a module's artifact EMBEDS its dependencies** — esbuild inlines a sibling library's source into the controller bundle, and publish pins each relative import to a hash of the sibling's manifest — so bumping the dependents is a correctness requirement, not a courtesy. No general-purpose changelog tool can see that — a per-project ledger has no dependency graph at all, and changesets' stops at the npm boundary, where a module's inlined sibling is invisible.

**Three questions, three mechanisms.** The **payload digest** (exact, from the bytes; `computeFilesIntegrity` over the layers publish builds, or over an image module's `.dockerignore`-defined file set) decides *whether* a module bumps, so it fires for an inlined sibling, a shared-library fix and a lockfile-only transitive bump alike. The **edge graph** decides *at what level*: edges come from the controller build's own **metafile** (a declared-deps graph cannot see `--external`, so `@telorun/sdk` — declared by 54 modules, inlined by none — would bump the whole stdlib on every SDK change) plus in-repo relative `imports:`; a dependent mirrors its dependency's level, joined as the maximum over paths. An **import edge bumps unconditionally** (publishing rewrites the sibling's version into the manifest, so the layer provably changes) while an **inline edge only explains drift that already showed up**. A digest that moved with nothing to attribute it to takes a **patch** and is reported as *unattributed*, never silently. The path-scoped **changed-files rule** survives but is demoted to deciding only *whether a changelog line is requested* — it used to decide the version, which is why its guesswork (`docs/` vs `tests/` vs `nodejs/`, `bundlesAController`) had to be sound and was not; now a false positive costs one sentence.

**The ledger is a cache; the registry is the authority.** `.changes/ledger.yaml` records per module its version, its per-layer integrity **as published**, and the **registry base** those digests were taken against (canonicalization writes the destination into every relative import, so digests against another base are digests of different bytes). That is the load-bearing property: **the PR gate and the publish gate compute the same number**, and the PR gate needs no merge base and no credentials, so a fork runs the identical computation. A *missing* entry is not drift — nothing is published, the right reading for a new module. `telo publish` still reads the registry, and `telo release verify [--write]` reconciles.

**`telo release check` does NOT fail because a payload moved.** Under a toolchain bump every digest moves; demanding sixty fragments for that is a tax on nobody's behalf, and those ship as unattributed patches. It fails when no consistent plan can be formed: a fragment naming an unknown module, a major-inducing kind (`Changed`/`Removed`), a manifest version disagreeing with its ledger entry, or a registry-base mismatch. It *warns* (`CHANGELOG_ENTRY_REQUESTED`) when a module's own files changed with no fragment naming it.

**The workspace anchor.** `telo-workspace.yaml` at the repo root carries one field, `modules:` — the subtrees that may hold modules (not derivable: hundreds of manifests elsewhere carry a `metadata.version`). **Its location is the anchor** for every module key, ledger entry and fragment path. **It is optional**; `telo release` requires one, and `telo run` uses its LOCATION — never `modules:` — as the bound on the walk-up collecting `.env` / `.env.local` (with no marker it reads the manifest's own directory alone, as before, so the file enables the parent lookup rather than gating one). `check`, `publish`, `install`, `upgrade`, `migrate`, `module` and the kernel are untouched without one. Anything added later must be true of the whole tree, not derivable from it, and harmless by its absence. Modules are **discovered, not registered**: a module is a directory under a named subtree holding a `telo.yaml` whose **module doc** carries a `metadata.version`, and its key is its workspace-relative path (never a bare name — two subtrees can share one). A `Dockerfile` beside the manifest makes it an **image module**; that decides only which file set is digested. An image module's base image is deliberately outside its digest — the every-push `:latest` + `:sha-<short>` policy already carries a kernel change to the deployed app.

**Publish is where two of the invariants are enforced.** Pins are **authored and verified, never discovered**: `telo install` / `telo upgrade` write them, and the payload builder REFUSES a remote import carrying none (it used to be fetched best-effort, so one commit produced different bytes depending on network reachability, and an unresolvable import shipped silently unpinned — error swallowing this repo forbids). Existing pins are verified against the registry; a mismatch is fatal. An in-repo sibling's pin is derived from the sibling's **own locally-built published bytes**, in topological order, so a batch is plannable offline against post-bump versions the registry has never seen. Manifest re-serialization is **unconditional** — it used to depend on whether a pin happened to be written, so one commit serialized two ways.

**The payload is built by the kernel, not staged by a package manager.** `cli/nodejs/src/bundle/module-payload.ts` is the single builder both `telo publish` and `telo release` consume; it builds every bundled controller through the kernel's own `buildControllerBundle` (`source-bundle-builder.ts`, the analogue of the Rust `napi-loader`) rather than reading the gitignored `path=` artifact. Shipped bytes and digested bytes are the same bytes by construction, the edge graph gets its metafile from the same run, and the esbuild half of 47 per-module `build` scripts plus `build:bundles` are retired (the `tsc -p tsconfig.lib.json` type-check half stays). On the publish/release path the optional-esbuild fallthrough becomes a **hard failure** — digesting a stale bundle is the one outcome the design exists to prevent.

`cli/nodejs/src/bundle/payload-drift.ts` stays as the publish-time backstop and should now never fire. Registry publish is still gated on `metadata.version` movement (`scripts/publish-modules.mjs`), whose ordering now comes from `telo release order` rather than a regex over `imports:`.

**Publication is split by artifact, because the dependency runs npm → modules → images.** A module artifact is built by the workspace CLI, so the CLI ships first and modules follow. `pnpm run release` is **`changeset publish` and nothing else**; module manifests are pushed by `scripts/publish-modules.mjs` in its own workflow job, on every push to main (both its gates — version moved in this commit, version absent at the registry — are idempotent, so nothing is republished and a failed push heals on the next push). They were one script, which had the npm release decide module questions: it ran the payload-drift gate over already-published modules, and that gate demands module versions be moved BEFORE npm publishes — the inverse of the real order — so every release following a byte-changing change failed *after* `changeset publish` had shipped the packages and pushed the tags, where nothing could retry it. A second implementation of the release planner (`git diff` regexes, registry queries) also drifts silently from `telo release`, which owns those answers.

**A kernel image's existence is a function of what is on npm, not of a job's exit code.** `telorun/node:latest*` moved only when the changesets action reported `@telorun/cli` in `publishedPackages`, so *any* later failure in that run left every deployment pulling a kernel image releases behind, with nothing reporting it — and `publish-docker.yml` had no `workflow_dispatch`, so the only recovery was another release. The `context` job now also builds the release tag set when the workspace CLI version is **live on npm and has no `telorun/node:<v>-slim`** (probed with an anonymous registry token; a probe that cannot answer reports *present*, since a missed build heals next push while a false *missing* would re-tag `latest` from an arbitrary commit). `@telorun/sdk` is checked alongside the CLI because the Dockerfile's `--prod deploy` resolves it from npm and the two publish with no ordering guarantee. `workflow_dispatch` takes a `cli-version` for the by-hand case.

**A runner bakes the kernel it was built against.** `apps/k8s-runner`'s `TELO_SESSION_IMAGE` build arg fixes `RUNNER_IMAGE` at image build time, and the chart's `session.image` defaults to empty so the baked value wins. A mutable `latest-slim` there made a session's kernel whatever was last released, independently of the runner that was tested with it — which is how a kernel two CLI releases old ran a module published against a newer one and failed on syntax it had never heard of (the case `requires:` exists to name).

The model splits on the browser-safety line: `analyzer/nodejs/src/release/` holds module identity, fragment parsing, the ledger, the edge graph, propagation and version planning (pure data in, plan out, so the editor can answer "what does changing this library bump?"); `cli/nodejs/src/release/` holds evidence collection (driving the kernel's builder, workspace and git reads, file writing) and the commands. Version rewriting reuses `yaml-source-edit.ts`, so a bump is a one-line diff rather than a re-serialized file.

## Keep the authoring agent in sync — MANDATORY

`apps/authoring-agent` is an AI agent that authors Telo manifests for users. Its
system prompt (`apps/authoring-agent/chat/telo.yaml`, the `system:` block) is a
full primer that encodes the current Telo architecture — resource kinds,
capabilities, reference/CEL rules, import/export semantics, and authoring patterns
(composition, inheritance, etc.). **Any change to Telo's architecture MUST include
a matching update to that system prompt**, as part of the same change — never a
follow-up. A stale primer makes the agent emit manifests against an outdated
surface. Treat it like this file and the module docs: syncing it is not optional.
