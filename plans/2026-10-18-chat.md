# Chat

A fully featured AI chat a manifest declares as one node, whose upload button and
other input surfaces appear only when the agent behind it offers them, beside a
conversation list the page composes from ordinary `ui` kinds.

## Shape of the solution

- **`conversation` owns the contract.** A neutral module that imports nothing
  (`metadata.name: Conversations`, imported as `Conversation`, since a library
  cannot declare a kind named like itself) holds what every server and client of a
  conversation speaks: the shapes `Conversation.Spec`, `Conversation.Event` and
  `Conversation.Entry`, the `Conversation.Conversation` abstract, and the
  conversation contract — the routes, their bodies and their problems.
- **`ui` owns the viewer's side.** `Ui.ConversationSource` pairs a conversation
  with the address it is served at, and a `Ui.Chat` composite (wire node `chat`)
  draws one. `ui` imports `conversation`, never `ai`.
- **The model owns what it accepts.** `Ai.Model` and `Ai.ModelStream` declare
  `accepts:`. The same declaration makes the provider refuse an unaccepted part and
  makes the upload button appear; nothing else restates it.
- **Storage is separate from presentation.** `ai-conversation` persists branching
  transcripts for any agent consumer; `ai-chat` serves the conversation contract
  over an `Ai.AgentStream`, storing through `ai-conversation`.
- **The journal owns a running turn.** A turn's `record-stream` journal key is its
  only claim and the only judge of whether it is alive; a cancel marks that key, so
  it reaches the writer from any replica.
- **Declared vs drawn.** Only what the user acts on before a reply is declared —
  attachments and conversation operations. Reasoning, tool calls, approvals,
  citations and usage are drawn from the events that arrive.

Dependency direction: `conversation` imports nothing; `ui` → `conversation`;
`ai-chat` → `conversation`, `ai`, `ai-conversation`, `record-stream`, `blob`,
`media-type`, `multipart`, `http-server`, `sse-codec`; `ai-conversation-sql` →
`ai-conversation` → `ai`, `sql`. `ui` and `ui-react` import no `ai`, and `ai-chat`
imports no `ui`. Every new module is MIT, with `license: MIT` and its own `LICENSE`.

No phase widens the manifest grammar (no new annotation, built-in key or fragment),
so no module takes a new `requires:` floor.

## Phase 1 — The conversation contract, `Ui.ConversationSource` and `Ui.Chat`

**Before.** `ui` has no streaming node. A chat is hand-built as a custom component
through the component ABI, reading `host.fetch` by hand — the ABI docs carry a
"streaming chat" recipe doing exactly that.

**After.**

In `conversation`, each shape a named `Telo.JsonSchema` exported as a resource:

- `Conversation.Spec` — what an endpoint offers before any event arrives:
  - `attachments` (absent when none): `{ accepts: [{ type, mediaTypes, maxBytes }], maxPerMessage }`,
    `type` one of `image`, `audio`, `video`, `file`.
  - `operations`: the subset of `branch`, `cancel` the endpoint supports. The
    conversation routes (list, read, rename, archive, delete) are not gated by it.
- `Conversation.Event` — a closed union on `type`: `text-delta`,
  `reasoning-delta`, `content` (a completed part: media by attachment URL, a
  citation, a refusal), `tool-call-delta`, `tool-call`, `tool-result`,
  `approval-request`, `approval-decision`, `step-usage`, `turn-end` (usage and a
  `reason`: `stop`, `length`, `content-filter`, `limit`, `approval`, `cancelled`,
  `failed`), `error` (`code`, `detail`, read like a problem). The contract grows
  only by adding event types; a client ignores a type it does not know.
- `Conversation.Entry` — one transcript entry as a viewer reads it: id, parent
  id, role, content parts (media by URL), tool calls and results, usage.
- `Conversation.Conversation` — a `Telo.Abstract` (Provider) providing a
  `Conversation.Spec`.

Kinds in `ui`:

- `Ui.ConversationSource` — a Provider shaped like `Ui.CollectionSource`:
  `conversation` (required, a ref to a `Conversation.Conversation`,
  `use: dependency`) and `basePath` (required, a `Ui.AppRelativeReference`). It is
  the one name every chat over an endpoint uses for what it talks to.
- `Ui.Chat` — extends `Ui.Composite`. Fields: `source` (a ref to
  `Self.ConversationSource`), `title`, `placeholder` and `starters` (prompts
  offered on an empty conversation), each a `Text` with no values,
  `show: { reasoning, toolDetail, usage }`, `conversation: { parameter }` (the
  page query parameter naming the conversation shown) and `refreshes` (request
  targets read again when a send is admitted and a turn ends). It draws no
  conversation list: the page composes one from a `Ui.SplitView` and a
  `Ui.Listing` over `Conversation.conversations`. Its controller reads the spec from
  `source.conversation`'s reading at creation and emits a `chat` node carrying the
  spec, the `basePath` and every presentation member, defaults filled by `ui`:
  every `show` switch on, an omitted `title` or `placeholder` `null` (not drawn),
  `starters` `[]`. A switch can only hide a surface; none can turn on what the spec
  does not offer.
- `chat` joins the closed `Ui.SpecNode` union and the list of nodes composites
  provide. Every text it carries sits where the spec translator finds it.
- What the chat draws on its own — the composer's accessible name `chatMessage`
  ("Message", drawn always and never taken from the placeholder), send, stop,
  attach, approve, reject, copy, regenerate, edit, new conversation, rename,
  archive, delete, search and the rest — becomes new keys of `ui`'s
  `Telo.KeyedTranslations` document `Translations` (kind `Ui.Translations`), each
  with its English wording, a `description`, and `values` for any placeholder (a
  file's name, a size). Each of the fourteen shipped `Ui.<language>Translations`
  translates every new key. The renderer draws them from the application
  document's `texts.own`, so an application writes nothing to show them and
  overrides one with a `Ui.Translations` of its own listed after the shipped one.
  `Ui.Chat` fills no keyed text itself, so it names no `x-telo-text-keys`.

The conversation contract (`modules/conversation/docs/conversation-contract.md`),
every path under the source's `basePath`:

| Route | Meaning |
| --- | --- |
| `GET /capabilities` | the same `Conversation.Spec` the node carries, for clients other than `ui`; the renderer never reads it |
| `POST /turns` | `{ conversation?, parent?, message, attachments, approvals? }` → `{ conversation, turn }`; `approvals` resumes a turn that ended with `reason: approval`; an `idempotency-key` header makes a retried send start one turn; a turn already running on the conversation is a 409 `ERR_CONVERSATION_TURN_RUNNING` |
| `GET /turns/<id>/events` | SSE of `Conversation.Event`, each frame's `event` its `type` and `id` its resume position; resumed with `Last-Event-ID` |
| `POST /turns/<id>/cancel` | stops a running turn (`cancel`), on whichever replica runs it |
| `GET /conversations` | a page `{ rows, total, next }` as the collection contract pages for `Conversation.conversations` (`limit`, `cursor`, `sort`, `title.contains`, `archived`); served whatever `operations` holds |
| `GET /conversations/<id>/entries` | a page of one branch's transcript, `?leaf=` choosing the branch |
| `PATCH /conversations/<id>` | `{ title?, archived? }` (rename, archive) |
| `DELETE /conversations/<id>` | delete; 204 |
| `POST /attachments` | a `multipart/form-data` upload of one file → `{ id, url, mediaType, size }` |
| `GET /attachments/<id>` | the stored bytes |

Every failure is an RFC 9457 problem (`application/problem+json`); a refused
request is `ERR_INPUT_INVALID` with `data.issues`. How `ui` shows one is the
client's behaviour, documented in `modules/ui/docs/chat.md`: `data.issues` worded
with `ui`'s validation texts, as a form's are; any other problem's `code` and
`detail` shown as the error; a problem without a `code` falling back to
`ERR_UI_UNAUTHORIZED` / `ERR_UI_FORBIDDEN` / `ERR_UI_REQUEST_FAILED`, and a 2xx
body the contract refuses being `ERR_UI_RESPONSE_INVALID`, as for actions and
records.

The `chat` node in `ui-react`:

- Transcript text through the `markdown` node and its lazy chunk — CommonMark +
  GFM tables and task lists, raw HTML shown as text, links held to the
  app-relative address rule. Whichever of this plan and the review-app-screens
  work lands first introduces that node; the chat adds highlighted code blocks
  with copy to it.
- Streaming text, a collapsible reasoning panel, tool-call cards with arguments and
  result, approval cards (approve / reject with reason) that resume the turn,
  citations, refusals, per-turn usage.
- Composer: multiline input named `chatMessage`, Enter to send / Shift+Enter for a
  newline, stop while a turn runs; attachments by button, drag-and-drop and paste,
  checked against `accepts` and `maxPerMessage` before upload, with per-file
  progress and removal.
- Edit-and-resend and regenerate as branches when `branch` is offered, with a
  branch switcher on the entry; copy message; export transcript as Markdown.
- Follows the page: `conversation: { parameter }` opens the conversation the
  address names, writes a created one back by replacing the history entry, and
  switches on a changed parameter without cancelling a running turn. The list of
  conversations is composed from `ui` kinds (see the composable chat screens
  plan); the chat only subscribes to `<basePath>/conversations/<id>`, so a
  rename or delete reaches it.
- Reconnects a dropped event stream with `Last-Event-ID`; an `error` event or a
  failed request is shown in place with its code.
- Keyboard-reachable throughout, with live-region announcements for streamed text.
- The chat's highlighting loads with the markdown chunk, so a page with neither
  does not fetch them.
- Every drawn element carries `data-telo-part`: each new part is added to the part
  list, drawn in a conformance scene, and styled by `UiReact.defaultTheme` and by
  ui-react-radix's theme, which `UiReactConformance.CheckTheme` holds to it. Only
  existing `Ui.DesignTokens` are read.

## Phase 2 — `accepts:` on models

**Before.** No model declares what content it carries. A provider refuses an
unsupported part at call time (`ERR_MODEL_CONTENT_UNSUPPORTED`, data
`{ partType, scheme?, mediaType? }`) on its own rules: Anthropic checks media
types, OpenAI checks none; every provider also refuses on URI scheme,
by-reference vs by-bytes and a file without a name; none enforces a size. What each
carries is written only in prose tables in its docs. `Ai.Agent` and
`Ai.AgentStream` publish an empty reading, and `Ai.Buffered` is a template that
publishes none.

**After.**

- `ai` declares the shape `Ai.AcceptedContent`: a list of
  `{ type: image|audio|video|file, mediaTypes, maxBytes? }`. `Ai.Model` and
  `Ai.ModelStream` both declare `accepts:` of that shape. Absent means text only.
  There are no defaults keyed on model ids.
- Every provider kind narrows `accepts` in its own schema to the types and media
  types its dialect can carry at all — the content of today's prose tables:
  `OpenAI.ChatModel` / `ChatModelStream`, `OpenAI.ResponsesModel` /
  `ResponsesModelStream`, `Anthropic.MessagesModel` / `MessagesModelStream`. The
  deprecated `OpenAI.Model` / `OpenAI.ModelStream` inherit their parent's.
- Every provider refuses a part outside the resource's own `accepts` — wrong type,
  media type outside `mediaTypes`, or bytes over `maxBytes` — with
  `ERR_MODEL_CONTENT_UNSUPPORTED`, before anything is sent, with the same payload as
  today. The check covers every part sent, tool-result media included. The
  scheme, by-reference and file-name refusals stay call-time rules of each
  provider, outside `accepts`.
- Every provider publishes its `accepts` in its reading. `Ai.Agent` and
  `Ai.AgentStream` publish their model's (`resources.<name>.accepts`).
  `Ai.Buffered` gains a controller of its own, which publishes its inner model's.
- Every fixture model declares `accepts`: `AiEcho.EchoModel` /
  `EchoModelStream` accept every type, agent-app's `EchoModel.Model` and the
  throws-ceiling `VendorModel` / `VendorModelStream` follow the contract.
- The prose capability tables are replaced by `accepts` examples in the provider
  docs; `ai-model.md` documents the field.
- This is breaking for an application that sends media without declaring
  `accepts`; each module's fragment is `Added` and says so. Every in-repo manifest
  that sends media declares it: `examples/draw-shapes-agent`, the authoring agent,
  and the media tests of `ai`, `ai-mcp`, `openai` and `anthropic`.

**Verify.**

- An `accepts` entry outside a provider's ceiling is `SCHEMA_VIOLATION` under
  `telo check`, at the line that wrote it.
- A model with no `accepts` refuses an image part with
  `ERR_MODEL_CONTENT_UNSUPPORTED` and makes no request; the same model declaring
  `image/png` sends it; a part over `maxBytes` is refused; an image in a tool
  result outside `accepts` is refused.
- `resources.<agent>.accepts` equals its model's `accepts` (`Assert.Equals`),
  through `Ai.Buffered` as well.

## Phase 3 — `ai-conversation` and `ai-conversation-sql`

**Before.** Each agent consumer stores history its own way: `agent-app` keeps user
and assistant text in one SQLite table, with no list and no branches; the
authoring agent keeps its own tables, and branches by copying turns into a new
conversation.

**After.**

- `ai-conversation` (depends on `ai`): the `AiConversation.Store` abstract and its
  operations, each an invocable over a store ref:
  `AiConversation.Create`, `AiConversation.List`, `AiConversation.Entries`,
  `AiConversation.Append`, `AiConversation.Update`, `AiConversation.Delete`.
- A conversation is a header (id, title, archived, `turn`, version, created /
  updated) and a branching transcript of `Ai.Message` entries, each naming its
  parent; editing or regenerating appends a sibling and keeps the old branch.
- `turn` is the latest admitted turn id (`trn_…`, null before the first) — a
  fencing token, not a claim. `Update` writes title, archived and `turn`,
  conditional on the version. `Append` names its turn and is refused when the
  header's `turn` is another one; it is not conditional on the version, so a
  rename during a turn does not break the turn. A stale version, or an append by a
  superseded turn, is `ERR_CONVERSATION_CONFLICT`; an unknown id
  `ERR_CONVERSATION_NOT_FOUND`. The store keeps no claim and no expiry: whether a
  turn is alive is judged by its journal key (Phase 4).
- `List` (filtered by title text and archived) and `Entries` page by opaque
  cursor: `{ rows, total, next }`.
- Public ids carry a prefix and 128 random bits in base 62: `cnv_…` for
  conversations, `ent_…` for entries.
- `ai-conversation-sql`: `AiConversationSql.Store` over a `Sql.Connection`, owning
  its tables: `tablePrefix` (default `ai_conversation_`) and `createTables`
  (default `true`). It records its schema version in `<prefix>schema`, upgrades an
  older one in place at start, and refuses a newer one.

**Verify.**

- Append on a branch, then regenerate: `Entries` with each leaf returns each branch
  intact (`Assert.Equals`).
- Two `Update`s of `turn` at one version: exactly one succeeds, the other is
  `ERR_CONVERSATION_CONFLICT`.
- An `Append` by a superseded turn is `ERR_CONVERSATION_CONFLICT`; a rename during
  a turn does not refuse that turn's appends.
- Paging a 1 000-entry transcript and a 1 000-conversation list returns every row
  once.
- A store started over tables of the previous schema version upgrades them; over a
  newer version it refuses to start.
- `modules/ai-conversation/docs/` and `modules/ai-conversation-sql/docs/` exist and
  match.

## Phase 4 — `JournalCancel` and `ai-chat`

**Before.** Nothing serves the conversation contract. A `RecordStream.Journal` key
can be failed or removed, but nothing lets another replica ask its writer to stop:
`Lease.Critical` cancels only a run on the replica that started it.
`MediaType.Detector` recognises png, jpeg, gif, webp, pdf, zip and Office files
only; any other upload takes the type the client declared.

**After.**

- `record-stream` gains `RecordStream.JournalCancel`, an invocable over a journal:
  input `{ key }`, output `outcome` — `requested`, `ended`, `unknown` or
  `removed`. It applies the stale-writer rule first (a stale key is failed as
  lost and answers `ended`, so a cancel never keeps a dead writer alive), then
  marks the open key's header with a cancel request by compare-and-set.
  `JournalSink` sees the request at its next refused append or heartbeat, and
  waits on its own key through the store's `wait` between writes, so a cancel
  lands within the store's wake-up latency. It then stops pulling, cancels its
  input, fails the key with `ERR_JOURNAL_CANCELLED` and raises that code.
  `ERR_JOURNAL_CANCELLED` joins `JournalSink`'s `throws:` and the codes
  `JournalSource`'s stream raises. The store contract gains the protocol rows; no
  store method is added.
- `AiChat.Conversation` (Provider, extends `Conversation.Conversation`): `agent`
  (an `Ai.AgentStream`), `store` (an `AiConversation.Store`), `journal` (a
  `RecordStream.Journal`, whose `writerTimeout` is the only liveness setting),
  `blobs` (a `Blob.Store`), `detector` (a `MediaType.Detector`) and
  `attachments: { maxBytes?, maxPerMessage? }`. It provides the spec:
  `attachments.accepts` is the agent's published `accepts`, each entry's
  `maxBytes` the tighter of the model's and its own; `attachments` is absent when
  the agent accepts nothing; `operations` is `[branch, cancel]`.
- The turn, history and attachment operations are invocables that know no
  transport; `AiChat.Api` is a templated `Telo.Mount` over them (an `Http.Api`
  with its handlers, as `Crud.Api` is built) that speaks the conversation
  contract, mounted where a `Ui.ConversationSource.basePath` over the same
  conversation points. It names the conversation, never the source.
- A turn (`trn_…`) is admitted in this order: read the conversation header;
  `RecordStream.JournalRead` the header's `turn` (which fails a stale writer as
  `ERR_JOURNAL_WRITER_LOST`); an open key answers 409
  `ERR_CONVERSATION_TURN_RUNNING`; otherwise `RecordStream.JournalClaim` the new
  key under a writer token, then `Update` `turn` at the version read — on a
  conflict the claimed key is removed with `JournalRemoval` and admission starts
  again. The turn then runs detached, draining into `JournalSink` under the same
  token; each record is journaled before its entry is appended to the store.
- Each translated `Conversation.Event` is written to the journal keyed by the
  turn. `GET /turns/<id>/events` replays and tails that key from `Last-Event-ID`
  on any replica, each entry flattened to `{ id, type, … }` before `SseCodec`
  writes it. Each `message` part is appended to the store as it commits;
  `message` and `provider-state` never cross the wire.
- `POST /turns/<id>/cancel` on any replica is `RecordStream.JournalCancel` of the
  turn's key. `Ai.AgentStream` aborts its in-flight provider request when its
  consumer stops; this phase makes it do so where it does not.
- Agent parts map to events: `tool-approval-request` / `tool-approval-decision` →
  `approval-request` / `approval-decision`; `step-finish` → `step-usage`; the
  terminal `finish` → `turn-end`, its `finishReason` `stop` / `length` /
  `content-filter`, `limit: max-steps` and `interrupt: approval` choosing the
  reason.
- An abnormal ending is derived from the key, never written by the writer: a key
  failed with `ERR_JOURNAL_CANCELLED` closes with `turn-end` `reason: cancelled`;
  any other recorded error — `ERR_JOURNAL_WRITER_LOST`, `ERR_INVOKE_CANCELLED`
  from a shutdown, a failed run — closes with `error` (its code and detail), then
  `turn-end` `reason: failed`. These closing frames take ids after the key's last
  record, so `Last-Event-ID` resumes them deterministically.
- An attachment (`att_…`) arrives as one multipart file part, its route's
  `maxBodyBytes` the attachment limit plus 64 KiB of framing. It is detected
  before it is stored and streamed into the blob store under `maxBytes`; its media
  type must fall within the spec's `accepts`, else a 400 problem naming it. Its
  bytes are loaded into a `data` part only when a turn calls the model.
- `media-type` recognises the common audio and video containers (MP3, WAV, OGG,
  FLAC, MP4 / M4A, WebM, QuickTime). A `text/*` upload, which has no signature,
  keeps the type the client declared.
- A unit test reads both manifests and fails when an `Ai.AgentStreamPart` type is
  neither mapped to an event nor listed as dropped.

**Verify.**

- `ai-chat`'s import graph holds no `ui`.
- `JournalCancel` on an open key answers `requested` and the sink fails the key
  with `ERR_JOURNAL_CANCELLED`; on a stale key `ended`, on an unknown key
  `unknown`, on a removed key `removed` (`record-stream` tests).
- The application in the example below, over the echo model fixture: a turn's
  events, its entries after the turn, and `GET /capabilities` match expected values
  (`Assert.Equals`).
- Over a text-only model, `/capabilities` has no `attachments` and the page's
  `chat` node draws no upload control; declaring `accepts: [{ type: image,
  mediaTypes: [image/png] }]` adds both.
- Two application instances sharing one SQLite file (store and journal through
  `record-stream-sql`):
  - two turns started on one conversation — exactly one is admitted, the other is
    409 `ERR_CONVERSATION_TURN_RUNNING`;
  - events opened on the other instance resume from a given id;
  - a cancel sent to the other instance ends the turn `cancelled`, and the stub
    model receives no request after it;
  - killing the writer's instance mid-turn: after `writerTimeout` a new turn is
    admitted, and the old turn's events close with `error`
    `ERR_JOURNAL_WRITER_LOST` and `turn-end` `failed`;
  - a graceful shutdown mid-turn reads `failed`, not `cancelled`.
- An upload over `maxBytes`, or of a type outside `accepts`, is a 400 problem and
  stores nothing; a large upload keeps memory bounded. An MP3 and a WebM file are
  detected by content.
- No wire frame holds base64 media.
- A new `Ai.AgentStreamPart` type fails the mapping test.

**After.** `AgentApp.App` serves the conversation contract through `AiChat.Api`

## Phase 6 — Studio and authoring-agent on the contract

**Before.** `apps/authoring-agent` serves its own protocol: `GET /capabilities`
with `features[]`, `POST /chat`, `GET /chat/<turnId>/events`, abort, continue,
changes and revert per turn; conversations with keyset paging, rename, archive,
delete, truncation, and branching by copy into a new conversation; per-conversation
attachments; workspace routes. A turn holds a per-conversation `Lease.Critical`
lock, and an abort is recorded as `aborted_at`. Its errors are `{ error, code }`.
Studio's panel gates every surface on `features`; on the contract it gates on
`Conversation.Spec.operations` (`branch`, `cancel`) alone.

**After.**

- authoring-agent serves its conversations through `ai-chat`; its `/chat`,
  conversation, attachment and capability routes are removed, and its failures
  are problems. Its turn lock and `aborted_at` are replaced by `ai-chat`'s
  admission and `ERR_JOURNAL_CANCELLED`.
- Its stored conversations are migrated into `ai-conversation-sql`'s tables; a
  branch it copied stays a conversation of its own.
- What maps onto the conversation contract: list (the collection contract, with
  `title.contains` for search), rename, archive, delete (always served), cancel,
  attachments, idempotent send. Truncation is replaced by branching: Retry
  and Edit & resend append a sibling. Continue becomes a new message after a
  `limit` turn.
- What stays authoring-agent's own contract, never an extension of
  `Conversation.Spec`: turn changes and revert, turn summary and conclusion,
  workspace routes, editor-selection context, manifest runs, and how a client
  authenticates.
- Studio's panel becomes a client of the conversation contract, keeping its own
  React components; its feature gating reads `Conversation.Spec` for
  conversation surfaces and authoring-agent's own capabilities for the rest.
- `plans/production-ready.md` is updated to the new protocol: the capability-doc
  gating in its problem statement, D0 (tool results and approvals — these use
  `approvals` on `POST /turns`), E5, E9 (approval cards are `ui-react`'s), E10,
  F9, G1, H2, H3, H6 and its housekeeping list.
- Parts the agent-text-edits work adds pass through Phase 4's mapping test like
  any other.

**Verify.** Studio's panel connects to a plain `ai-chat` endpoint (not

## Example — an application after Phase 4

A chat over Claude with image and PDF uploads, its conversations, turn journal and
uploads in one state directory. Imports are written as from `examples/chat/`.

```yaml
kind: Telo.Application
metadata: { name: ChatApp, version: 1.0.0 }
requires:
  telo: ">=0.121.0"
lang: en
imports:
  Http: ../../modules/http-server
  HttpClient: ../../modules/http-client
  Ai: ../../modules/ai
  Anthropic: ../../modules/anthropic
  AiConversationSql: ../../modules/ai-conversation-sql
  AiChat: ../../modules/ai-chat
  RecordStream: ../../modules/record-stream
  RecordStreamSql: ../../modules/record-stream-sql
  BlobFs: ../../modules/blob-fs
  MediaType: ../../modules/media-type
  SQLite: ../../modules/sqlite
  Ui: ../../modules/ui
  UiReact: ../../modules/ui-react
targets: [!ref server]
ports:
  http: { env: PORT, protocol: tcp, default: 8080 }
variables:
  stateDir:
    env: STATE_DIR
    type: string
    x-telo-type: { name: Telo.HostPath, entry: directory }
    default: .data/chat
  model: { env: MODEL, type: string, default: claude-sonnet-4-5 }
secrets:
  anthropicApiKey: { env: ANTHROPIC_API_KEY, type: string }
---
kind: SQLite.Connection
metadata: { name: db }
file: !cel "variables.stateDir.joinPath('chat.sqlite')"
---
# Read by the page for what it offers and served by the API under /api/chat.
kind: AiChat.Conversation
metadata: { name: conversation }
agent:
  kind: Ai.AgentStream
  system: You are a concise assistant. Answer from the files the user attaches when there are any.
  maxSteps: 8
  model:
    kind: Anthropic.MessagesModelStream
    model: !cel "variables.model"
    maxTokens: 4096
    request:
      kind: HttpClient.Request
      client:
        kind: Anthropic.Client
        credential:
          kind: HttpClient.ApiKeyHeader
          header: x-api-key
          key: !cel "secrets.anthropicApiKey"
    # The upload button and the provider's refusal both come from this list.
    accepts:
      - { type: image, mediaTypes: [image/png, image/jpeg, image/gif, image/webp], maxBytes: 5242880 }
      - { type: file, mediaTypes: [application/pdf], maxBytes: 33554432 }
store: { kind: AiConversationSql.Store, connection: !ref db }
journal:
  kind: RecordStream.Journal
  store: { kind: RecordStreamSql.JournalStore, connection: !ref db, table: chat_journal }
blobs:
  kind: BlobFs.Store
  root: !cel "variables.stateDir.joinPath('attachments')"
detector: { kind: MediaType.Detector }
attachments: { maxBytes: 10485760, maxPerMessage: 4 }
---
kind: UiReact.App
metadata: { name: ui }
title: Assistant
theme: !ref UiReact.defaultTheme
pages:
  - kind: Ui.Page
    path: /
    title: Assistant
    children:
      - type: composite
        ref:
          kind: Ui.Chat
          source: { kind: Ui.ConversationSource, conversation: !ref conversation, basePath: /api/chat }
          title: Assistant
          placeholder: Ask anything, or drop an image or a PDF
          starters: [Summarise the attached PDF, What is in this picture?]
          show: { usage: false }
---
kind: Http.Server
metadata: { name: server }
listen: { port: !cel "ports.http" }
mounts:
  - path: /api/chat
    mount: { kind: AiChat.Api, conversation: !ref conversation }
  - { path: /, mount: !ref ui }
```
