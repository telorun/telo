# Templating (Node) — package guide

Loaded when working under `templating/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. What an expression is typed AGAINST (the CEL scope rule) is the analyzer's — see `analyzer/nodejs/CLAUDE.md`.

## CEL analysis

**One expression, one verdict — the templating engine's.** `TemplatingEngine.analyze` returns `{ diagnostics, type?, calls }` (`templating/nodejs/src/engine.ts`), and the engine owns the `env.check()` call: the analyzer hands it the environment **typed for that path** and reads the resolved type back rather than checking again. Splitting the two is what let the replaced engine's opaque `found no matching overload` survive beside the diagnostic that explained it, and left interpolation holes chain-validated but never type-checked at all. Everything derivable from the expression alone is derived there once; everything needing manifest context — the field's declared type, its `x-telo-eval` mode, which verdict outranks which — stays with the analyzer, which is the only side that has it. That split is also what a second (Rust) CEL engine implements: a classifier, not a rulebook.

**The classifier is gone, and so is its reason for existing.** `cel/diagnose.ts` used to decide `CEL_UNKNOWN_FUNCTION`, `CEL_WRONG_CALL_FORM`, `CEL_UNKNOWN_FIELD` and `CEL_INVALID_ARGUMENT` itself, by looking every call up in the registry — because the engine it drove reported ONE sentence for three unrelated mistakes (`found no matching overload for 'f(...)'`), two of whose readings actively misled: the message named argument types, so the repair for `startsWith(key, 'x')` looked like a cast when the fix was `key.startsWith('x')`. `@telorun/cel` decides each of them where the cause is known, with a range and a whole-source fix, and `CheckResult.diagnostics` carries them coded. So nothing here classifies and nothing reads a message; `diagnose.ts` is now the call LIST, which the analyzer needs in order to judge whether a module call reaches a function at all — a verdict that is manifest context and never this engine's.

## Two environments, and the conformance vectors

**The language and the dialect are two environments, and the options exist once.** `buildCelLanguageEnvironment()` is the engine's standard library under Telo's options (unlisted variables `dyn`, optional types on, heterogeneous aggregate literals allowed) and nothing else; `buildCelEnvironment(handlers?)` is built from it by adding the catalog and `Stream`. A second engine reproduces the two separately, so they are named separately.

**The dialect is no longer declared in this package.** Telo's 67 functions and their 86 signatures ship inside `@telorun/cel` as data plus implementations, registered through the very `registerFunction` a host uses, so `cel/catalog.ts` — 1,455 lines of table — is deleted: `registerFunctionCatalog(environment, { handlers })` is what the dialect IS, and `functionCatalog()` is the one listing surface (`celFunctionCatalog()` re-exports it, and `telo cel functions` reads it). What is left here is the pair of environments and the nine host handlers, which is the only part that was ever this package's. `cel/json-prefix-scan.ts` went the same way — the engine words `parseJson`'s refusal from its own scan.

**Telo's CEL behaviour is frozen as data in `templating/cel-conformance/`** — language-neutral rows, whose README is the format and states per file whose answer a row holds and how much of it is compared. `language.json` is cel-spec's `simple` suite as the replaced engine answered it in the language environment, each difference from cel-spec recorded as a `deviation` rather than filtered out — and **a row is a RECORDING of the engine that has been replaced**, so where its `deviation.celSpec` says otherwise, cel-spec is the authority and the row is evidence of what used to run. The engine's own four drivers (`cel/nodejs/conformance/`) replay the same files with the correction and exclusion machinery that states, per row, which way it went and why; the drivers here cover the TAG layer those cannot see — the hole grammar, `!sql` and `!interpolate`, module-call dispatch, and the verdict vocabulary. `tests/cel-conformance-value.ts` is the conformance value — the typed frame as a JSON value plus the `$cel` type and optional forms. No generator is committed: the data is the artifact, so a changed answer is a changed row in review.

**The tag files (`holes.json`, `module-calls.json`, `verdicts.json`) are driven through the TAG ENGINE's own seams** (`tests/cel-conformance-dialect.ts`) — `catalog.json` and `types.json` are answered by the engine's replay and read here only for the coverage gates below — for the tag each row names — `cel`, `interpolate` or `sql`: `analyze` in the dialect environment plus the nominal brands and the row's declarations, then `compile` and evaluation without either — at runtime a branded value is its base. Their host handlers are the **conformance handler set**, each answering `<handler>(<typed-frame text of each argument>)`, so a row pins exactly what the engine hands the host and a second engine reproduces it with its own frame writer — the set is defined only over values the typed frame writes (not an optional, a type, a live `Stream`, an out-of-domain number or instant, or a string holding an unpaired surrogate), a row handing a handler anything else is malformed and fails the runner, and a writer's refusal is the typed frame's contract, not the vectors'; a volatile function is pinned only through a deterministic expression over its result. Coverage is mechanical: the runner fails when a registered catalog overload is dispatched by no evaluating `catalog.json` row (a mirror of the dialect environment reports each overload's dispatch, held to `buildCelEnvironment`'s own definitions), when a literal guard fires in no row, when a kind of `RE2_PATTERN_ERROR_KINDS` is the refusal of no row, when a brand of `valueBrandBases()` is declared by no `types.json` row, or when a code the engine source can emit is reported by no `verdicts.json` row.

**`holes.json`, `module-calls.json` and `verdicts.json` pin what the engine answers beyond the catalog.** `holes.json` is the hole grammar through both hole tags — where a hole opens and closes, `interpolate`'s conversions and its static and runtime refusals, what `sql` yields, and diagnostics, fixes and call offsets re-anchored onto the scalar. `module-calls.json` is resolution and dispatch: a row's `modules` key carries the name set and, per qualified function, what the host answers for it (`returns`, the flags, `resultSchema`) and what it does when dispatched; the driver binds those functions as the dispatch table under `MODULE_CALL_DISPATCH_KEY` and records every dispatch as `expect.dispatched`. `verdicts.json` is every diagnostic code and Telo error code the three tag engines emit, each in each circumstance it is reported, with every `fix`. **The engines' verdict codes are declared once** — `CEL_VERDICT_CODES` in `cel/verdict-codes.ts`, two lists: `diagnostics` and `errors`. Every diagnostic the `!cel`, `!interpolate` and `!sql` engines build is typed against the first (`CelDiagnostic`, through `CelAnalyzeResult` and `CelCallAudit`, the narrowed forms of `AnalyzeResult` and `CallAudit` those engines return), so the package's own build refuses a code the list does not hold; a coded error is thrown through `celVerdictError`, typed against the second. The vocabulary is not on the package's public entry — the conformance runner imports it from the source file, and fails until a `verdicts.json` row reports each code, a diagnostic code as a diagnostic's `code` and an error code as the row's `error.code`. A new verdict is added to the list first.

**Not yet pinned by the vectors — no row answers on any of these:**

1. the refusals of `range` (a count too large), `urlDecode`, `urlEncode`, `uuidv3`, `uuidv5`, `uuidVersion`, `hmac` (an unknown algorithm) and `joinPath` (an absolute argument) — today each is a dependency's or the host's wording;
2. three refusals the catalog words, which no row holds yet: `nowIso` and `today` of an unknown zone (`<function>: unknown IANA time zone "<zone>"`) — with whether `Z` is a zone, which the host's zone data decides, and with neither function having a literal guard; `addMonths` of a result out of range (`addMonths: the result is outside the range of a timestamp`; its unknown-zone refusal is pinned); and a non-finite number handed to `round`, `format`, `fixed` or `formatDuration` (`<function>: expected a finite number, got double`);
3. whether `parseJson` and `bytesFromBase64` refuse a literal argument statically — their refusals at evaluation are pinned, through a bound argument; today neither has a literal guard;
4. what a catalog function answers where its result would hold an unpaired surrogate — `parseJson` for a text whose string holds one, `slice` for a string range that starts or ends inside a surrogate pair, `split` for an empty separator and `replace` for an empty search over a string holding a pair; today each returns the unpaired surrogate.

Also not yet pinned: how `ERR_INTERPOLATION_HOLE_NOT_CONVERTIBLE` names a value that is not null, a list or a map (an optional, a type), and with it the static refusal of `${{ optional.of(1) }}` and `${{ int }}`; in the hole grammar, where a hole ends when a raw string holds a backslash directly before its own quote, and a string under a two-letter prefix — `holes/language/*` pins only what the language itself reads of those; and what the language's `substring` and receiver `split` answer where the result would hold an unpaired surrogate. The language row `timestamps/timestamp_selectors_tz/getHours` records the replaced engine's refusal in its JS host's wording; the engine answers the row's `deviation.celSpec` instead (a zone written `HH:MM` is a fixed offset, so `1`) and words an unknown zone itself (`"<zone>" is not a time zone`), which no row holds. No conformance file holds a string with an unpaired surrogate — the runner fails on one (`unpairedSurrogateAt`).

**Zone rows use settled history:** the vectors pin how an engine applies time-zone rules, never the rules, so a row whose answer depends on a zone names one present, and an instant on or before 2021-12-31 whose local time is the same, in every tzdata release from `2022a` on, and a row over a clock-reading function names only an `Etc/GMT±n` zone or asserts only the result's shape.

**A catalog function's refusal is Telo's words, and the vectors pin it verbatim.** The rule: a refusal reads `<fn>: <what is wrong>`, identically on every engine, and is never a dependency's or the JS engine's wording. `parseJson` words its refusal from its own prefix scan (`cel/json-prefix-scan.ts` — `invalid JSON at offset <n>`, never V8's message): the host parser's verdict stands and the scan runs only when it refuses, a text the host refused and the scan reads as JSON being a defect carrying the host's error as its `cause`; the scan's agreement with RFC 8259 is its unit tests', not a runtime check. The regex functions end an invalid-pattern refusal with one of the closed `RE2_PATTERN_ERROR_KINDS` (`cel/catalog.ts`), dropping re2js's prefix and quoted fragment — a parse failure outside that vocabulary is a defect carrying the library's error as its `cause`. The compile the runtime runs is also each regex function's `checkArgs`, so a literal invalid pattern or unknown flag is `CEL_INVALID_ARGUMENT` at check. A new refusal is written in that voice and gets its row in `catalog.json`.

**A literal guard reports only a refusal.** The refusals a guard can meet are thrown as `CatalogRefusal` (`cel/catalog.ts`, which prints as a plain `Error` everywhere), and `literalGuard` turns that type alone into a message; anything else thrown while a literal is judged propagates out of `analyze` with its cause, so an engine defect is never reported as the author's argument. A refusal a new guard runs is thrown as that type.

**`re2js` and `uuid` are the ENGINE's pinned dependencies now**, at the exact versions the vectors ran against: the regex answers, RE2's parse-error vocabulary and its limits, and the UUID answers are those libraries', so an upgrade is a deliberate change that re-runs the vectors. They moved with the catalog.

**Brand registration is this package's** (`cel/value-brands.ts`, `registerValueBrands`, exported): every nominal brand the SDK's value types define, its base conversion, its `string()` rendering and, for a host-derived brand, `.joinPath` typed back to the brand. `buildCelEnvironment` registers none of it — brands are static only, registered on the clone a caller types a site with (the analyzer's three typed environments, the dialect vectors' static half), because at runtime a branded value is its base.

## Module calls — the engine's second input

**An expression is compiled against a NAME SET as well as an environment.** `CompileEnv.moduleNames` / `AnalyzeEnv.moduleNames` carry the declaring module's own names — its `imports:` keys, `Self`, its `metadata.name` and `Telo` — and a call whose receiver is one of them (`Billing.format(x)`) is a call on a resource of the module that name reaches, not a method on a value. Everything else is the core catalog, so `format(…)` and `Billing.format(…)` never collide and one catalog environment still compiles both. The caller supplies the set because it is known from the module's own file before any import resolves; a partial is compiled with the names of the module including it, and the analyzer's parse cache is keyed on them. Absent means "no module names here", which is the reading every caller had before module functions existed.

**Resolution is the ENGINE's, and `qcall` is a node of its own.** This package used to rewrite the parsed tree itself, through internals the previous engine did not expose — `setMeta('macro', …)` redirecting check and evaluation, a comprehension macro's `alternate` winning over `macro` unless cleared, an rcall's asyncness derived from state the replaced checker filled in: three facts about a dependency's internals, each pinned by a test, and the reason it was pinned to an exact version. `@telorun/cel` produces `qcall` by a total tree-to-tree pass over the name set (never by the parser, because the set is the host's), and a `CelExpression` records the set it was resolved under, so an environment **refuses** a tree resolved for a different site rather than answering a different question about it. So reading a module call is reading a node kind (`moduleCallOf`), there is nothing to rewrite and nothing to pin, and `resolveModuleCalls` is gone from the surface. A receiver that is a field access (`a.b.c(x)`) is still not a module call.

**Every reader takes the resolved tree, never a re-parse.** `extractAccessChains`, the nullable walk and `auditCalls` all skip a resolved call's receiver — it names a module, so reading it as a root would invent a dependency, an undeclared identifier and a `resources` read the expression never states — and the type check goes through `celEnv.check(parsed)`, since `check(source)` re-reads the text and an environment refuses a tree resolved under another site's names. A `CompiledValue` carries its qualified calls in `calls`, beside `refs`, because re-deriving them needs the name set a consumer holding one expression does not have. `CEL_UNKNOWN_FUNCTION` / `CEL_WRONG_CALL_FORM` skip a module call, and no catalog flag is attached to one: what a module function's determinism and host-backedness are follows from the callable it resolves to, so a module call's `CallSite.deterministic` / `CallSite.hostBacked` carry what the host's `AnalyzeEnv.moduleCallFlags` (or `auditCalls`' `moduleCallFlags` argument) derives, and stay absent where it gives nothing — which every consumer reads as "no signal". A catalog call carries both from the catalog entry.

**A module function's arguments cross the one host seam** (`hostValueOf`, `@telorun/sdk`), as the result of a compiled value does. What is behind a qualified call is a `Telo.Callable` — a CEL body whose parameters are AJV-checked against its declared `params`, or a controller's own `call` — and neither reads the value domain's map container, so a map literal written at a call site arrived as `{"entries":{}}` and was refused for a property its author had written. Pinned in `tests/module-call.test.ts`; nothing here converts, the seam does.

**The dispatch is private.** `evaluate` reads a per-scope table from the activation under `MODULE_CALL_DISPATCH_KEY` (`@telo:module-functions`) — `@` and `:` are outside CEL's identifier grammar and the activation is reachable no other way, so no author can call past the export gate or the dependency edge. Binding the table is the kernel's, per owning scope; with none, evaluating throws `unbound function '<qualified>'`.

**Whether a call reaches a function is the ANALYZER's verdict, not this engine's** — it is manifest context, and the engine reports every module call in `AnalyzeResult.calls` for the caller to judge (`FUNCTION_UNRESOLVED` / `_NOT_EXPORTED` / `_NOT_CALLABLE` / `_ARITY_MISMATCH` / `_ARGUMENT_MISMATCH`), each with its arguments' CEL types and, for an argument that is a plain chain, the chain — the caller compares those against the signature. What the engine does take from the host is the callee's RESULT: `AnalyzeEnv.moduleCallType` types the call node (so an operator over it checks), and `moduleCallResult` supplies the schema a member read off it is checked against (`CEL_UNKNOWN_FIELD`, labelled `<qualified>(…)`); absent, a call types as `dyn`. The one place manifest vocabulary would otherwise leak in is the unknown-identifier hint: the engine knows which bare identifiers are unresolved call *receivers*, and asks the host through `AnalyzeEnv.couldNameModule` whether such a name could denote a module at all, so `dbb.query(1)` is not told to add an `imports:` alias. Naming rules are the host's; absent, the hint stays off.

**Null-safety:** dereferencing a value whose schema admits `null` (e.g. `error` inside a `finally` block, typed `["object","null"]`) without a null-guard is a static error (`CEL_NULLABLE_ACCESS`). The analyzer recognises guards through `?:` ternaries and `&&` / `||` short-circuits — `error != null && error.code`, `error == null ? … : error.code`. General: applies to any nullable value in any CEL context (`templating/nodejs/src/cel/analyze.ts` `findNullableAccessIssues`, wired in `engines/cel.ts`).

## Interpolation (`!interpolate`) and the hole grammar

**`!interpolate` is text with `${{ expr }}` holes, always a string, and its meaning is fixed as exactly the CEL expression joining the text with `string(<hole>)` for each hole** (`engines/interpolate.ts`). Conversion is the environment's own `string()` overloads — RFC 3339 for a timestamp, the `Telo.Duration` plain encoding for a duration (`5400s`, the catalog's `string(duration)`), UTF-8 for bytes — never the host's `String()`, which is what makes a Go or Rust engine render the same text. Statically each hole is analyzed by the shared `analyzeCelExpression` (diagnostics and fixes re-anchored onto the whole scalar, as `!sql` does), a clean hole is checked by type-checking `string((<hole>))` in the same environment — a type no overload accepts is `INTERPOLATION_HOLE_NOT_CONVERTIBLE` — and a hole that is a plain chain whose schema admits null is `CEL_NULLABLE_ACCESS`. A `dyn` hole passes; one that is null, a list or a map at runtime throws `ERR_INTERPOLATION_HOLE_NOT_CONVERTIBLE` naming the hole, its offset and the type found — null never renders as `""`, which would contradict the static verdict. `producedType()` declares `{type: string}`, so the slot check, the placeholder substitution and the studio picker handle it without naming it.

**One hole grammar, normative** (`cel/interpolation-holes.ts`, read by `!sql`, `!interpolate` and the `untagged-interpolation` migration's `match.scalar`): a hole opens at `${{` and closes at the first `}}` outside a CEL string literal and outside any `{` the expression itself opened. String literals are CEL's — `'`, `"`, their triple-quoted forms, the `r`/`b` prefixes, a single-quoted one ending at a newline; how a raw string with a backslash directly before its own quote, and a two-letter prefix, are read is not yet pinned (see above). Outside a hole only `${{` is special, and a literal one is written `${{ '${{' }}`. A hole that never closes is a reading failure at its `${{`, never a guess. The expression is the hole's body trimmed. A scalar's SHAPE is `none` / `lone-hole` (one hole, only whitespace around it) / `interpolated` / `malformed`. The `[^}]+?` regex it replaced could not read a map literal and left such a string as literal text.

**Where a tag's CEL sits is the ENGINE's to say** — `expressionRegions(source)`: the whole scalar for `!cel`, each hole's expression for a tag with holes, nothing for a tag holding no CEL. `celExpressionsOf(engine, source)` is the single reader, and every analyzer pass that asks "what CEL is written here" (non-eval fields, observed-state reads, durable regions, throws, scope reach, unused declarations, module calls, the module graph's data edges) goes through it, as the editor's segment builder does — so no consumer outside the registry branches on `interpolate`. A question about the value's OWN expression (is it a plain chain, a computed reference) stays `!cel`'s: a tag with holes produces something other than the value of one expression.

**Whether a tag's text is REPEATABLE is the engine's to say too** — `repeatable(source, celEnv)`, read through `repeatableSource`: written twice in one value, the text means one value both times. A verdict on the text alone, with no module name set and nothing evaluated: `!cel` is repeatable when it calls no catalog function marked non-deterministic and makes no call on a bare identifier (which may name a module, whose function's determinism is its callee's — `a.b.f()` is a method on a value and stays repeatable); a tag with holes when every hole is; text the engine cannot read is not; an engine giving no verdict reads as not repeatable. The analyzer's stand-in judge is the consumer: two character-identical repeatable scalars in a `uniqueItems` list are a duplicate as written. Taking no name set is what lets `telo check` (a tagged sentinel) and the kernel (a compiled value) reach one verdict from the same two facts, the tag and its text.

**A plain string is never an expression.** The untagged `"…${{ }}…"` spelling is rewritten at load by the core migration `untagged-interpolation` (a lone hole to `!cel "<expr>"`, anything else to `!interpolate` with the text unchanged), and `precompileDoc` refuses one that survives (`ERR_UNTAGGED_INTERPOLATION`) in whichever module holds it, so its static twin `UNTAGGED_INTERPOLATION` is reported for every module too — a dependency's at the consumer's import of it, read off the library's full documents (`moduleDocuments`). The load-time rewrite changes one thing a published artifact did: a hole null, a list or a map at runtime now fails where the untagged spelling printed empty text or a comma list, and the entry's `reason` says so. The Rust tag reader refuses `!cel` / `!interpolate` / `!sql` by name and a plain string holding `${{`, having no expression engine.

## Embedded files (`!include-text` / `!include-bytes`)

Two tags embed a file that ships beside the manifest as a manifest value — `!include-text` → string, `!include-bytes` → `Uint8Array` (what a `Telo.Bytes` slot accepts). Engines in `templating/nodejs/src/engines/include.ts`, registered in the closed `builtinEngines` set, mirrored by `templating/rust/src/engines/include.rs`.

**Paths are MODULE-ROOT-relative, never relative to the declaring file** — the rule a controller's `path=` and `files:`/`assets:` already follow. It is load-bearing rather than cosmetic: `telo publish` deletes `include:` and inlines every partial as an extra document into one published `telo.yaml` (`expandAndInlineIncludes`), so the declaring file does not exist in the artifact and a per-file-relative path would silently move — passing `telo check` locally and failing only for consumers. **Confinement is a PURE STRING check** (`normalizeIncludePath`), which is what lets the browser-safe analyzer decide it: root-relative means `..` below depth zero is an escape regardless of where the module sits on disk. Literal paths only — a URL, glob or absolute path is `INCLUDE_PATH_INVALID` / `INCLUDE_PATH_ESCAPES_MODULE`. A **computed path is deliberately unrepresentable**: a file that must ship inside the artifact has a name known at publish time, so the dynamic case is `Fs.File`'s, not this one.

**A module's `source` is what EVERY module-relative reference is measured from** — `ctx.resolveModuleFile` for a controller, an embed for a manifest value — so an import's child `ModuleContext` carries the **library's own manifest URL** (`moduleManifest.metadata.source`, stamped by the loader), never the importer's and never `resolvedUrl` (which is the import source as written, a directory whose last segment `new URL` would drop). Carrying the parent's made a library read the CONSUMER's directory, silently returning the consumer's file when one sat at the same relative path — and it contradicted packaging, which is per-module.

**An embed's type is a constant of the TAG, not of the slot.** `substituteCelFields` gives every other tagged sentinel a slot-shaped placeholder (right for `!cel`, whose type is only derivable from the expression); these two substitute a real `""` / `Uint8Array`, so AJV and the `x-telo-type` keyword reject a byte embed at a string slot — and the reverse — statically, with no new diagnostic code. **The ENGINE is what says so**: `TemplatingEngine.producedType()` declares the fragment (`fileClaims`' precedent applied to the one fact it left behind), and `substituteCelFields` reads it through `readStandIn` (`stand-in-findings.ts`), which asks `producedTypeOf`, instead of branching on two tag names — the only place a tag's produced type was written down, and it was written in the consumer.

**`compile` is identity on the marker** — the sentinel survives precompile the way `!ref` does, but needs no special case in `precompileDoc`. **The read happens at RESOURCE CREATION** (`kernel/nodejs/src/resolve-include-sentinels.ts`, called from `_createInstance` before schema validation so bytes reach a `Telo.Bytes` slot as a `Uint8Array`), never at manifest load: the artifact spec gives `telo.yaml` its own layer so reading a manifest cannot pull the payload, and an app loads every imported library's manifest. The walk **stops at nested `{ kind }` declarations** (a `with:`-scoped resource resolves when its scope runs — Phase-5 injection draws the same line) and **only recurses into plain containers**, because a template kind expands `${{ self.connection }}` to a live `ResourceInstance` whose graph is cyclic. The same rule governs `compileWalker` (rebuilding any object from `Object.entries` would turn a byte buffer into `{"0":137,…}` silently), `walkCelExpressions` and the kernel's dependency-edge walk (`collectResourceRefs`): every walk over a declaration meets that live instance on every creation attempt of a template child, and one that descends into it overflows the stack or traverses the whole kernel. An embed on a doc that is never instantiated is `INCLUDE_OUTSIDE_RESOURCE` — nothing would read it, and nothing else would report that.

**Payload membership is ONE generic mechanism, and no consumer recognises a syntax.** `TemplatingEngine.fileClaims(source)` lets an engine declare what its tag embeds (the `ref-slot.ts` precedent); `collectModuleFileClaims` (`analyzer/nodejs/src/module-file-claims.ts`, browser-safe) is the single reader, aggregating engine claims **and** the controller `path=`/`siblings=` claims into `{ path, role, selector?, siblings?, origin }`; `partitionLayers` consumes that and knows about neither PURLs nor tag names. It is **deliberately not part of `analyze()`** — that pass is flattened and import-inclusive, so its claims would mix in imported libraries' files (whose paths are relative to *their* module) and would make packaging depend on resolving the whole import graph, which today it does not. Publish refuses a named file that does not exist. Cap: 32 MB per file. The Rust kernel resolves `!include-text` only — its manifest is `serde_json::Value`, which has no bytes variant, so `!include-bytes` fails there explicitly rather than producing a number array.

## Module paths (`!module-path`)

`!module-path ./public` names a file or DIRECTORY that ships with the module by its LOCATION: at resource creation the kernel resolves it — beside the embeds, through the same `resolveModuleFileUri`, so a published module's assets layer is materialized first — to the absolute path on disk, and refuses one naming nothing (`ERR_MODULE_PATH_NOT_FOUND`). Engine in `templating/nodejs/src/engines/module-path.ts`, mirrored by `templating/rust/src/engines/module_path.rs`; its path grammar is the include grammar under its own codes (`normalizeModulePath`, `MODULE_PATH_INVALID` / `MODULE_PATH_ESCAPES_MODULE`, the module root itself refused). It produces a `Telo.HostPath`, which is how a slot on the host (`Http.Static.root`) holds a directory of the module without the controller anchoring a relative string itself — a relative literal there is `HOST_PATH_RELATIVE`, whose repair is this tag.

**Its claim may be a directory** (`EngineFileClaim.directory`), so the analyzer's claim stays a pure string and the Node side that holds the directory expands it (`cli/nodejs/src/bundle/module-path-claims.ts`) into one assets claim per file, for publish and `telo package` alike — refusing `MODULE_PATH_NOT_FOUND` / `MODULE_PATH_EMPTY`, since an empty directory is not something a layer can carry. **Existence is asked at LOAD, of the source, for every tag that claims a file** — `!include-text` / `!include-bytes` as well as `!module-path` — because the analyzer never touches a filesystem: the loader puts each engine's `fileClaims` to the owning module's `ManifestSource.exists(base, relative)` and records the code the claim itself names (`EngineFileClaim.notFoundCode`: `INCLUDE_FILE_NOT_FOUND`, `MODULE_PATH_NOT_FOUND`) in `LoadedGraph.moduleFileDiagnostics` (`analyzer/nodejs/src/module-file-existence.ts`), which the shared assembler and the runtime seam report — so `telo check`, VS Code, Studio and `Assert.Manifest` all see it — and which `kernel.load` refuses, so `telo run` and `telo install` stop before creating anything. **Scope is the entry plus every module reached through a filesystem-path import**, transitively: such a module is never published on its own, so nothing else checks its files before the resource embedding one is created (an embed a Docker ignore file left out used to pass every check and fail the container's boot). A registry import is skipped — its files were verified at publish and its assets layer is fetched lazily. A path at or above a module file the module's own `sources:` block stages (an entry an `assets:` pattern selects, or a notice) counts as present, since the kernel stages it on first use; the classification is the kernel's (`stagedModuleFiles` in `module-named-files.ts`, native entries first), nothing is exempted while the block does not read, and release planning from pins expands a directory claim over the same staged entries. A source that cannot answer (an in-browser store) reports nothing and the kernel's refusal remains. Emptiness is NOT asked there: it depends on the packaging ignore rules, so it stays a publish/package refusal alone rather than a second rule that could disagree with it. A tag on a doc that is never instantiated is `MODULE_PATH_OUTSIDE_RESOURCE`.

## Where to look

- Embedding or locating a file that ships with a module → `templating/nodejs/src/engines/include.ts` (the path grammar), `engines/module-path.ts`, `analyzer/nodejs/src/module-file-claims.ts` (who claims which file), `kernel/nodejs/src/resolve-include-sentinels.ts` (the read and the location)
- Holes and `!interpolate` → `templating/nodejs/src/cel/interpolation-holes.ts` (the grammar), `engines/interpolate.ts`, `engines/hole-analysis.ts` (shared with `!sql`), `celExpressionsOf` in `builtins.ts`
- CEL type checking → `templating/nodejs/src/engines/cel.ts` (`analyzeCelExpression`, which owns the verdict), `cel/diagnose.ts` (the call classifier); the analyzer supplies the typed environment (`cel-environment.ts`) and the context schema (`validate-cel-context.ts`)
- "is this call the catalog's or another module's?" → `templating/nodejs/src/cel/module-call.ts` (the rewrite, the reader and the private dispatch key), `analyzer/nodejs/src/module-call-names.ts` (where a module's names come from, at load and at analysis)
