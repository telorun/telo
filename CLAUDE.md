# Claude

Use `pnpm run telo ./manifest.yaml` for testing.
Use `pnpm run test` to run the full test suite (runs `test-suite.yaml` which discovers all `tests/*.yaml` across the repo).
Tests should live in the module they test: `modules/<name>/tests/*.yaml`.
Test fixtures go in `__fixtures__/` subdirectories (excluded from test discovery).
Prefer `Assert.Equals` (deep-equals `actual` against an `expected` literal) for asserting outputs in manifest tests — not `Assert.Schema`. It reads as a plain expected value, compares the whole result at once, and serializes BigInt safely.
Implementation plans should live in the package they affect the most, eg. `apps/telo-editor/plans/some-plan.md`.

Follow this strictly:

- **Do not create, edit, or delete any file until the user's latest message clearly authorizes the specific change you are about to make.** Authorization is a direct instruction to act now — to write, change, or remove something concrete. It is NOT: a question ("would X work?", "is this better?"), a critique or correction of a proposal, a request to compare or weigh options, or general discussion — none of these grant permission, no matter how positive. Agreeing that an idea is good is not the same as asking for it to be done. When the intent for you to act *now* is anything less than unambiguous, stay in proposal mode and ask: "Apply this?" This gate overrides Auto Mode and any "execute immediately" directive.
- **NEVER run `git commit`, `git commit --amend`, `git push`, or any other command that creates, rewrites, or publishes a commit — not even to make a check pass or "fix" state.**
- never add underscores to unused function arguments
- never look at commit history
- never use git stash
- never fix linting problems, and never mention it
- keep code comments very concise and add them only when necessary; prefer self-documenting code and module documentation
- if you cannot implement a feature in a way it was established or planned to be implemented, propose a new approach and ask for approval before implementing it
- never implement logic that swallows errors
- telo manifests MUST be type safe
- in telo manifests, ALWAYS write CEL with the `!cel "..."` YAML tag — never the inline `"${{ ... }}"` string form. The formatter normalizes to `!cel`, and the inline form gets mangled on round-trip (it has been silently rewritten into a broken `!ref`). This applies to every CEL value, including pure expressions and string interpolations (`!cel "'http://localhost:' + string(ports.http)"`).
- in telo manifests, declare a resource INLINE at its use site when it is used exactly once — `invoke: { kind: Some.Kind, ...config }`, with no `metadata.name`. Give a resource its own top-level document only when something needs to name it: it is referenced more than once, listed in `targets:`, or exported. A named single-use resource makes the reader jump documents to follow one call. The exception is a router (`Http.Api`) mounted on a server — keep it named, because that is what makes it independently testable.
- never use `cat` nor `sed` to read files — read them directly
- never use `AskUserQuestion` tool, ask questions directly
- never do major upgrades of modules nor packages
- never modify files in `dist` directories
- never use Bun-only APIs (e.g. `Bun.Glob`, `Bun.file`); all code must run on Node.js
- never make architectural decisions alone (package boundaries, dependency direction, where code lives), propose best fit and ask to choose from options
- UI primitives must use Radix (`radix-ui` package, same pattern as `apps/telo-editor/src/components/ui/*`); if a needed component isn't wrapped yet, install it via shadcn before rolling your own
- Icons must come from `lucide-react` (already a dep). No inline `<svg>` paths.
- When working on a plan, when a decision is made then remove the decision section entirely, not just mark it as decided. The plan should reflect the current state of the world, not a history of how we got here.
- `JS.Script` in manifests is a last resort. Before reaching for it, check whether the work belongs in a new generic stdlib resource (composes with the existing kind library, reusable across consumers, type-safe at the manifest level). A `JS.Script` is acceptable when (a) the logic is one-off and demonstrably not reusable, or (b) it bridges to a Node-specific API the kernel doesn't yet expose. In every other case, propose a new resource kind first and ask before adding inline JS.
- never add Docusaurus or any other rendering-tool annotations (`sidebar_label`, `sidebar_position`, `description`, etc.) to `README.md` files. Docusaurus-specific labels and ordering belong in `pages/sidebars.ts`; other markdown files under `docs/` may keep frontmatter where it's actually consumed.
- keep your communication very concise and to the point; avoid unnecessary preambles, or apologies. Focus on the task at hand and the specific changes being made. If you need to explain a complex decision, do so.
- Avoid putting code into generic `utils.ts`, `types.ts`, `helpers.ts` files. Drive the filename from the specific domain or feature it serves.

## Architecture

Telo is a declarative runtime: YAML manifests describe desired state, the kernel resolves resource dependencies via a multi-pass init loop, and controllers implement each resource kind. CEL expressions in `${{ }}` are compiled before execution.

**Scope: everything is on the table.** Telo is intended to support every transport, every protocol, every backend domain — HTTP, MCP, gRPC, WebSocket, message queues, databases, file I/O, AI providers, workflow engines, and whatever else lands. Design abstractions for breadth, not for the current consumer. When choosing between a generic primitive and a use-case-specific shortcut, **default to the generic primitive**. "We'll only need it for X" is the wrong question — assume any transport-neutral concept (encoders, codecs, streams, schedulers, retry policies, etc.) will eventually be reused across multiple modules, and shape the API and package layout accordingly. Do not YAGNI on cross-cutting primitives.

**Cross-cutting concerns Telo intends to cover** (non-exhaustive — when in doubt, assume it's in scope):

- **Data shape**: encoders, codecs, serialization (JSON, Protobuf, Avro, CBOR, MessagePack), validation, schemas, content negotiation, compression (gzip/brotli/zstd).
- **Streaming & I/O**: async iterators, channels, backpressure, chunked transfer, framing, multiplexing, file/stdio/network pipes.
- **Reliability**: retry / backoff, circuit breakers, timeouts, deadlines, idempotency, graceful shutdown, dead-letter queues.
- **Performance**: caching (response, query, computation), connection pooling, batching, rate limiting, throttling, debouncing, deduplication.
- **Coordination / data integrity**: execution zones, see `kernel/specs/execution-zones.md` (normative) and `docs/extend/execution-zones.md` (guide): a resource declaring it must be reached through another's body, checked statically and enforced at dispatch.
- **Observability**: structured logging, see `kernel/specs/logging.md` (normative) and `docs/guides/logging.md` (guide); metrics (counters, gauges, histograms), distributed tracing (OpenTelemetry, spans, baggage), audit logs, profiling, health checks (liveness/readiness), alerting hooks.
- **Security**: authentication (OAuth, OIDC, API keys, JWT, mTLS, SAML), authorization (RBAC, ABAC, policy engines), secrets management (vault integrations, rotation), encryption at rest / in transit, signing/verification, CSRF/CORS.
- **Time & scheduling**: cron, intervals, delayed jobs, leases, time-zone handling, deadlines, clock skew tolerance.
- **Coordination**: distributed locking, leader election, queues (FIFO / priority), pub/sub, event sourcing, sagas / workflow orchestration, transactional outbox.
- **Configuration**: env, file, remote config, feature flags, dynamic reload, multi-tenancy, environment promotion.
- **Lifecycle**: migrations (DB, config, schema), versioning, rollouts, blue/green, canary, drain/shed.
- **Internationalization**: localization, pluralization, time-zone formatting, locale negotiation.
- **Inputs & boundaries**: pagination, filtering, sorting, partial responses, file uploads (multipart, chunked, resumable), webhooks (inbound + outbound), bulk operations.
- **Errors**: structured error contracts, error codes, retryable vs terminal classification, error mapping across boundaries, partial-failure aggregation.

When designing a new module or capability, ask: which of the above does this resource genuinely need to declare or compose with? If the answer touches more than one consumer, the concern belongs in a shared primitive (kernel built-in capability or transport-neutral package), not buried inside the current module.

**Topology-driven constraint:** The analyzer and telo editor must never hardcode knowledge about specific resource kinds. All resource-specific behaviour must be expressed via `x-telo-*` schema annotations in `Telo.Definition` schemas and resolved generically.

**Browser compatibility:** The `analyzer` package must be runnable in the browser without Node.js polyfills. Do not import Node.js built-ins (`fs`, `path`, `url`, `child_process`, etc.) from analyzer code. Node.js-specific adapters belong in the consuming package (kernel, IDE extension, CLI).

## Core goals

- **Polyglot architecture** — Telo must support controllers and runtimes in any language, not just Node.js
- **Visual editing** — Telo manifests must remain visually editable in a GUI editor; solutions must not break declarative structure or introduce constructs that can't be represented visually
- **Performance** — the init loop, CEL evaluation, and resource resolution must stay fast; solutions must not introduce unnecessary overhead
- **Static analysis** — YAML manifests must remain statically analyzable; solutions must preserve the ability to validate references, type-check CEL expressions, and detect errors without running the kernel
- **Developer friendly** — Errors must not be swallowed; they should be surfaced clearly to developers. Error messages must be actionable and informative, guiding developers to concrete place in YAML manifest that needs fixing.

## Monorepo Structure

- `kernel/nodejs/src/` — core runtime: orchestration, loading, controllers, init loop
- `cli/nodejs/` — CLI wrapper (`bin/telo.mjs`). **Every CLI-owned write goes through the `Output` seam** (`src/output.ts`), never `console.*` and never a bare `process.stdout.write`. A global `-o, --output text|json` (default `text`) selects the encoding. **The stream split is the contract, and it is what the format rests on**: *stdout is the machine surface* — under `-o json` it carries the payload and nothing else, so `line()` (prose) goes silent there; *stderr is the human surface in **both** formats*, so `errLine()` always writes. Suppressing stderr under `json` was error swallowing: only the commands that separately collected their messages into a payload kept them, and every other failure reason vanished, leaving `{"ok":false}` with no cause. Keeping prose on stderr is also what npm, cargo and kubectl do, and it is one rule rather than a re-collection obligation on each new command.
  **Two payload shapes, one serializer.** `emit()` writes a result **envelope** and is silent under `text`; `document()` writes a **bare document** and writes in *either* format, because the per-command `--json` flags (`cel`, `search`, `module versions|manifest|digest|resources|kinds`) predate `-o` and must keep working under the default. A document command's stdout is therefore *the document or empty* — it never mixes an error envelope in, because a CEL expression evaluating to `{"ok":false,…}` would be indistinguishable from a failure report; its errors are prose on stderr plus a non-zero exit.
  **`telo run` is exempt from `-o json` entirely**, and the exemption is structural, not an oversight: the kernel runs in-process and `teeStdio` *copies* rather than redirects, so the app writes to these same two descriptors and **neither is the CLI's to claim**. An envelope appended after arbitrary app output is unparseable on either stream. The machine surface for a run is `--debug`, whose wire protocol is framed per event precisely because it shares a stream.
  **Colour is decided per stream** (`Output.stdout` / `Output.stderr` palettes over `decideColor`), because diagnostics go to stderr while summaries go to stdout and one process-wide decision is wrong for whichever stream is redirected; stdout is never coloured under `json`, while stderr keeps its colour since it stays human-facing. **A payload write is followed by `process.exitCode`, never `process.exit()`** — on a pipe `write` is asynchronous and `exit` does not flush, so a large diagnostic set truncates into invalid JSON. `Output` takes its streams and env as constructor arguments so tests construct one over recorders (`installOutput` swaps the ambient instance) rather than spying on process globals. `yaml` is deliberately unimplemented; `-o` is an enum so it can gain the value without a second flag, and `parseOutputFormat` **throws** on an unrecognized one rather than degrading to text.
- `sdk/nodejs/src/` — public API for module authors (re-exports kernel contexts + capability interfaces). It also owns **`ctx.runtime`** (`runtime-seam.ts`), the host's own manifest machinery: `run(source, { env })` starts a child manifest isolated from the caller's and returns `{ stdout, stderr, exitCode, cancel }` — the streams are `Stream<string>`, `exitCode` settles at completion, `cancel()` stops the child and resolves once it has torn down; `check(source, { desugarImports })` runs the static-analysis pass and returns plain-data diagnostics plus a `loadError`. `test` runs child manifests through it and `assert`'s `Manifest` kind analyzes through it, so a published module binds to a versioned contract instead of importing `@telorun/kernel` / `@telorun/analyzer` — which would make kernel internals an unversioned ABI between an artifact and whatever kernel loads it. Output is streamed rather than captured because forwarding it live and retaining it on failure are both the caller's choice, and a string forecloses one. **A stream is not itself a memory bound** — withholding a `Writable`'s callback only fills its own unbounded internal buffer, and no controller awaits `drain` — so `cancel()` is what bounds an unread child, and is on the contract from the start because a supervisor needs termination before anything else. Isolation mode is the kernel's to pick (in-process child kernel today, subprocess later), which is what keeps process-global host-env state an implementation detail. Kernel half: `kernel/nodejs/src/runtime-seam.ts`.
- `modules/` — standard library: `http-server`, `http-client`, `sql`, `javascript`, `config`, `run`, `assert`, `test`, `console`, etc. Outbound authentication is one seam: `Http.Credential` (an abstract on `http-client`) takes the request about to be sent and returns headers / query to merge into it, so bearer tokens, API keys and request-signing schemes share one contract; the request controller owns the 401 `forceRefresh`-and-retry-once so no implementation re-expresses it. `oauth-client` implements it for OAuth 2.0 and owns the flows (consent, exchange, refresh, device, client credentials) plus grant storage over `KvStore.Store`. Two key/value abstracts coexist and differ by GUARANTEE, not operations: `Cache.Store` (freshness, evictable) and `KvStore.Store` (durable, non-evicting, atomic `putIfAbsent`/`compareAndSet`). `KvStore.Store` is storage only — the claim/settle/release protocol lives once in `KeyedClaim` (`@telorun/kv-store`), which `Lease.Critical` and `Idempotency.Once` both use, so no backend reimplements it.
- `analyzer/nodejs/` — static manifest validator (schema checks, reference validation, CEL type-checking). It also owns **manifest loading** (`manifest-loader.ts`, `parse-loaded-file.ts`, `resolve-ref-sentinels.ts`) — there is no `loader.ts` in the kernel; the kernel consumes the analyzer's, so `telo check` and the runtime read a manifest through one path.
- **Rust half of the polyglot runtime** — `kernel/rust/` (a second kernel), `cli/rust/` (the `telo-rs` binary), `analyzer/rust/` and `templating/rust/` (the loading/tag halves of their Node counterparts), `sdk/rust/` (controller authoring surface) and `sdk/rust/abi/` (the `telorun-abi` C ABI). **File layout mirrors the Node packages one-for-one**, kebab-case becoming snake_case: a Rust file with no Node twin means one of the two layouts is wrong, and the header of every such file says why it is the exception. `kernel/rust` is deliberately narrow (see `plans/rust-kernel-hello-world.md`): `Telo.Invocable` only, local-path imports, `pkg:cargo` controllers, no CEL. `telorun-abi` exists because the kernel must **not** depend on `telorun-sdk` — that crate selects a controller backend by Cargo feature, and unification would compile the napi backend into the kernel binary.
- `apps/telo-editor/` — desktop editor (React + Vite + Tauri)
- `apps/hub/` — federated discovery hub (declarative Telo app): tracks registered module refs across transports via the `telo module versions|digest|manifest` CLI verbs, caches each version's `telo.yaml` to the static manifest bucket (`manifests.telo.sh`, the editor's browser-safe OCI read path, keys from the analyzer's `manifestCacheKey` helper), indexes one row per `(module-version, resource-kind)`, and serves `/search/*`, `/refs`, `/module/versions` + the `search_resources` MCP tool (see `plans/federated-discovery.md`)
- `ide/vscode/` — VS Code extension (YAML diagnostics via analyzer)
- `tests/` — integration tests (YAML manifests run via kernel)
- `examples/` — sample manifests

## Kernel Internals (`kernel/nodejs/src/`)

- `kernel.ts` — main orchestrator, boot sequence, multi-pass init loop, event bus
- YAML loading + CEL-YAML compilation lives in the **analyzer** (`analyzer/nodejs/src/manifest-loader.ts`, `parse-loaded-file.ts`), not here; `kernel.ts` imports it
- `evaluation-context.ts` — `EvaluationContext`, `ModuleContext` — variable/secret/resource scoping
- `resource-context.ts` — bridge: `getModuleContext()`, `registerModuleImport()`
- `module-context-registry.ts` — per-module store for variables, secrets, resources, imports
- `controller-registry.ts` — maps resource kinds to controller implementations
- `controllers/module/module-controller.ts` — handles `kind: Telo.Application` / `kind: Telo.Library` (includes, module scope)
- `controllers/module/import-controller.ts` — handles module imports (external modules, export CEL eval)
- `controllers/resource-definition/` — handles `kind: Telo.Definition` and parameterized templates
- `capabilities/` — base interfaces: runnable, invokable, listener, provider, template, mount
- `manifest-schemas.ts` — JSON Schema for YAML validation
- `logging/` — structured logging, implementing `kernel/specs/logging.md`: `logging-pipeline.ts` (threshold → redaction → sampling → fan-out), the `json`/`pretty`/`otlp` encoders, `console-sink.ts` / `file-sink.ts` / `debug-wire-sink.ts`, `normalize-attributes.ts` (§6.3 limits, iterative and bounded), `span-id.ts` (salted counter, hex only at the encoding boundary), `kernel-logging.ts` (bootstrap writer → declared-config handover, replay, seal). The record model, severity scale, `Logger`, the `Telo.Sink` contract and `RecordBuffer` (the bounded §10.3 sink buffer) live in `@telorun/sdk` — a third-party sink is an ordinary module, so everything it composes must be on the module-author surface; the kernel's own sinks reach them through the `logging/log-sink.ts` re-export shim. The redaction **path parser** lives in the analyzer so `telo check` and the runtime share one grammar. Reached by controllers as `ctx.log`; sinks reach the pipeline via `ctx.logging`.
- `host-env.ts` — `boot()` replaces global `process.env` with a **guardrail** Proxy that denies a **manifest-derived** set: the env-var names the root Application binds via `variables`/`secrets`/`ports` (`collectDeclaredEnvKeys` in `application-env.ts`). A declared key reads back `undefined` (hidden from `in`/enumeration) with a once-per-key warning, so **controllers can't bypass a declared binding** — they use `ctx.env` or the declared `variables`/`secrets`. Every other key passes through — **no vendor-env allowlist** (a bundled SDK's `NODE_ENV`/`AWS_*`/`BUN_*` reads are undeclared, so untouched). The denied set is process-global and additive across in-process kernels. Kernel `TELO_*`/cache reads and subprocess spawns use `hostEnv()` (real env captured pre-lock); `analyzeOnly` never boots. A guardrail, not isolation; `process.env` is left non-writable. Tested in `tests/host-env.test.ts`.

## Resource Kinds

Every module file must start with exactly one `Telo.Application` OR `Telo.Library` doc. Applications are runnable entry points, Libraries are importable units of kinds/definitions. The two kinds share most fields; what differs is runtime role.

### `kind: Telo.Application`

A runnable entry point. Loaded via `Kernel.loadFromConfig` (directly, or by the test suite spawning a fresh kernel). **Never** imported — importing an Application is rejected at load time.

- `metadata.name` — free-form; becomes the canonical kind prefix (e.g. `MyModule.*`) that the registry keys on and diagnostics print. It is **not** a locator — imports resolve by `source`, and `x-telo-ref` targets are named by import alias — so it is a name, not a slug: write it in PascalCase (`OAuthClient`, `HttpServer`, `SQL`), which the whole standard library now uses. No pattern is enforced; the only hard rule is that it must contain no dot (the `!ref` grammar splits on the first one). Directory and npm package names stay kebab-case regardless (filesystem path; npm forbids uppercase).
- `lifecycle` — `"shared"` (default) | `"isolated"`
- `include` — array of file paths/globs to load as partial files into the same module scope; partial files must not contain `Telo.Application`, `Telo.Library`, `Telo.Import`, or `Telo.Definition`
- `imports` — name-keyed map declaring the module's dependencies. Each key is the PascalCase alias; each value is either a bare **source string** (`Console: oci://ghcr.io/telorun/console@0.9.0`, shorthand for `{ source }`) or the object form `{ source, variables?, secrets?, runtime? }`. The shared loader expands each entry into an internal import before resolution (gated by the `desugarImports` `LoadOptions` flag — on for the kernel's analysis + runtime loads, the import-controller's child load, the analyzer, and `telo check`; off for the editor's round-trip view, which reads the raw map). An alias declared twice in one module scope is a hard `DUPLICATE_IMPORT_ALIAS` diagnostic, not a silent shadow.
- `targets` — optional; run after all resources init. A flat boot sequence: each entry is a bare reference / `!ref` to a `Telo.Runnable` or `Telo.Service` (`run()`), a gated reference `{ ref, when? }`, or an inline invoke step `{ name?, invoke: <Invocable/Runnable ref>, inputs?, when? }`. Inline steps invoke the referenced resource via the shared `executeInvokeStep` leaf (SDK), with `steps.<name>.result` plumbed into later targets and `when`/`inputs` evaluated against the root scope. Ref-only — `invoke`/`ref` must be a `!ref` to a named resource (inline `{ kind }` definitions and `retry` are not supported here); control flow (`if`/`while`/`switch`/`try`), `with:` scopes, callable `inputs`/`outputs`, and `retry` stay in `Run.Sequence`. A no-targets Application is valid when its work is carried by Services that auto-start on init.
- `variables` / `secrets` — each entry binds a name to a host environment variable via an `env:` key, plus `type:` (`string | integer | number | boolean | object | array`), optional `default:`, and any further JSON Schema keywords. Values resolve at `kernel.load()` into the root `variables.X` / `secrets.X` CEL scope (object / array values are JSON-decoded from the env var; missing required vars or coercion / schema failures aggregate into `ERR_MANIFEST_VALIDATION_FAILED` before any controller init).
- `ports` — **Application-only** name-keyed map of inbound ports the app listens on. Each entry binds a host env var via `env:`, plus optional `protocol:` (`tcp` default | `udp`) and `default:`; the value is implicitly a port integer (1–65535, no `type:`). Resolves at `kernel.load()` (mirroring `variables`, same `ERR_MANIFEST_VALIDATION_FAILED` aggregation) into the root `ports.X` CEL scope, so a binding resource reads `${{ ports.http }}` as the single source of truth and a runner knows the exposed ports before boot. The analyzer brands each value by `protocol` (`tcp → TcpPort`, `udp → UdpPort`) for static wiring checks (see `x-telo-type`). `Telo.Library` does not get `ports`.
- `exports` is **forbidden** — an Application is a root with no importer. If you want to export kinds, the file is a Library.

### `kind: Telo.Library`

An importable unit of kinds/definitions. Loaded **only** as an imported dependency (via an `imports:` entry). Cannot be run directly; `loadFromConfig` on a Library manifest is a hard error.

- `metadata.name` — as Application.
- `variables` / `secrets` — JSON Schema property map; public contract for importers.
- `include` — same semantics as Application.
- `imports` — same imports map as Application (a library may declare its own dependencies).
- `exports.kinds` — which kinds importers may reference (`kind: <Alias>.<Kind>`). Each entry is either a bare kind name (a locally-defined kind) or `<Alias>.<Kind>` to **re-export** a kind the library imports under alias `<Alias>`. Re-export is transitive to arbitrary depth and resolves in O(1) (`ModuleContext` exported-kind table; analyzer `resolveExportedKinds` + `metadata.reExportedKinds` stamping); the gate still rejects kinds not listed. A re-exported kind resolves to its true owning module's controller/definition — `kind: Api.Thing` where `Api` re-exports `Domain.Thing` runs `domain`'s `Thing` controller. The gate is enforced in both halves: the kernel throws from `ModuleContext.resolveKind`, and the analyzer rejects statically using the target's list stamped onto each import as `metadata.exportedKinds` by `stampExportedKinds` (derived from the DECLARED entries, exactly as the kernel derives it — never from the resolved re-export table, which drops a re-export whose source module is ungated). Every kind-resolution path is *gated* — `kind:`, `extends:`, `capability:`, `base:`'s parent lookup, inline nested `{ kind }`, and `x-telo-ref` / `x-telo-schema-from` target checks all run through `resolveKind`. The dedicated `KIND_NOT_EXPORTED` *diagnostic* (naming the module and its exported kinds) is currently emitted only at the top-level `kind:` slot; the other slots still report their generic failure (`UNDEFINED_KIND`, `EXTENDS_UNKNOWN_TARGET`, a ref-kind mismatch), which is accurate but does not say "add it to exports.kinds". The gate check runs *before* any definition-registry lookup, since the registry is keyed `<module>.<Kind>` and an alias equal to the target's module name would otherwise resolve the raw kind string directly and slip past it. A library that declares **no** `exports.kinds` is currently unrestricted (every kind importable); declaring the block opts into the gate. Making kinds private by default is the intended end state but breaks every already-published module version, whose manifests cannot gain the block retroactively — it needs the ecosystem republished with explicit exports first. `registerImport(alias, target, kinds?)` encodes the distinction: a list is a gate (`[]` exports nothing), `undefined` is ungated and reserved for aliases crossing no import boundary (`Self`, the `Telo` built-ins).
- `exports.resources` — the resource **instances** the library exports as ready-made singletons. Each entry is a **plain name string** (the `!ref` tag is rejected here): `<name>` exports a locally-owned instance; `<Alias>.<name>` **re-exports** the instance the library reached through its own import aliased `<Alias>`, under the name `<name>` — same grammar as `exports.kinds`. Importers reference any export across the boundary as `!ref <Alias>.<name>` (injected into ref slots / boot targets) and, for value-flow exports, read them in CEL as `${{ resources.<Alias>.<name> }}`. The gate is the list itself: only named instances are reachable. A library declares a local instance internally with `kind: Self.<Kind>` (see `Self` under `Telo.Definition`), so it can export a singleton of a kind it does **not** export (omit the kind from `exports.kinds` to forbid importers constructing their own — singleton enforcement). Independent of `exports.kinds`: export a kind, an instance, or both. **Re-export is transitive to arbitrary depth** (`app → api → domain → …`) and resolves in O(1) regardless of depth: each import builds a flattened export table that copies the owner's terminal getter by reference (`ModuleContext.buildExportTable`), and the analyzer forwards re-exports transitively (`forwardReExportManifests`) so `telo check` agrees with runtime. The owning instance is shared — every re-exporting hop resolves to the single instance, not a copy.
- **Resource names must contain no dot** (hard diagnostic `INVALID_RESOURCE_NAME`): a `!ref` value is split on its first dot to separate the import alias from the resource name (`Console.writeLine` → alias `Console`, name `writeLine`), so a dotted `metadata.name` would mis-resolve. This is the load-bearing invariant of the reference grammar — enforced, not just convention.
- `targets` is **forbidden**. `lifecycle` is also forbidden — libraries are not lifecycle participants.
- No `env` access.

### `imports`

Loads `Telo.Library` modules into the current scope under PascalCase aliases, declared as the `imports:` map on the `Telo.Application` / `Telo.Library` doc (see above). Each entry value is a bare source string or the object form `{ source, variables?, secrets?, runtime? }`. The CLI `install` / `upgrade` / `publish` commands read and rewrite this map.

- `source` — relative path / registry ref / URL; resolved to `telo.yaml` automatically.
- `variables` / `secrets` — values passed into the child library.
- Each import creates an isolated child `EvaluationContext`; child resources are not visible to root scope.
- Importing a `Telo.Application` is a hard error — applications are run directly, not imported.
- Child modules are isolated from the host environment — only the root Application binds host env vars (via `variables:`/`secrets:`/`ports:` `env:` keys) and forwards them into imports.

### `kind: Telo.Definition`

Registers a new resource kind. Defined inline in a module's `telo.yaml`.

- `metadata.name` — kind suffix; full kind = `<module-name>.<Name>`
- `capability` — one of the kernel capabilities (see below). Names the lifecycle role only; never a user-declared abstract kind. **Inherited and immutable** when `extends` is present: omit it to inherit the ancestor's, or restate it identically; a *different* capability than an ancestor is a hard error (`EXTENDS_CAPABILITY_MISMATCH` + kernel guard).
- `extends` — alias-form reference to **any** kind this definition specializes — an abstract (implements-this-contract) **or a concrete kind (single inheritance)**. Single-parent, transitive, Liskov-substitutable: a child is accepted at every `x-telo-ref`/`!ref` slot its ancestor is, transitively. The prefix must be an import alias declared in the same file (an `imports:` entry). **`Self`** is auto-registered as an alias pointing at the declaring library's own module name — use `Self.<Kind>` when the kind lives in the same `Telo.Library` as the definition (no import to alias against, since a self-import would loop the loader). `Self` resolves the library's own kinds **ungated** — independent of `exports.kinds`, which gates importers, not internal use. This is what lets a library declare an instance of a kind it does not export (`kind: Self.WriteLine`) so it can export the instance instead (see `exports.resources`). The kernel registers `Self` in each import's child context so `Self.<Kind>` resolves at runtime, not just in the analyzer. **Inheriting a concrete kind:** when a child declares no own `controllers:`/template body, the kernel's `resource-definition-controller` resolves the controller-bearing ancestor, evaluates the child's `base:` mapping, calls the ancestor controller's `create()` with the mapped config, and **returns that instance verbatim** — so the child *is* a parent instance and duck-types identically (e.g. inherits `.snapshot()`). See the kind-inheritance guide (`docs/extend/kind-inheritance.md`).
- `base` — **("super(...)")** construction mapping for a concrete-`extends` definition: an object of CEL expressions over `self` (typed from the child's own schema), evaluated once and passed to the inherited controller's `create()` as the parent's config. Mirrors the `inputs:`/`result:` top-level-sibling factoring. When `base:` is present the child's **author-facing schema is its own schema only** (the parent's config fields are internal, set solely through `base:`, so the child genuinely narrows); without `base:`, an `extends`-child's author schema is `merge(parent, own)` (pure additive extension). `resources.<child>` value-flow reads follow the **parent's** value-flow (snapshot / `outputType`), never the child's input schema.
- `controllers` — `pkg:npm` locator; `local_path` is a relative fallback for local development. Omit on a concrete-`extends` child to inherit the parent's controller by delegation (see `extends` / `base`).
- `schema` — JSON Schema with `x-telo-*` annotations
- `status` — optional JSON Schema for the **observed state** the kind reports while running (see Lifecycle). Surfaces as `resources.<name>.status.<field>`; `required:` is rejected. Also legal on `Telo.Abstract`, so a contract can mandate what its implementations report.
- `resources` / `invoke` / `run` / `provide` — template-internal bodies. `invoke:` / `provide:` / `run:` describe the dispatch target only; `inputs:` (values passed to the target) and `result:` (post-call mapping applied to the target's output, works with `invoke:` or `provide:`) live as **top-level siblings** on the definition, matching how Run.Sequence steps factor `{ name, inputs, invoke }`. CEL expressions inside these fields are statically validated against `self` (always — typed from this definition's `schema:`). The `inputs` CEL variable (typed from `inputType:`, falling back to the `extends:`-declared abstract's `inputType:`) is available inside `resources[].*` and the top-level `inputs:` sibling **only for invocable / runnable definitions** — provider definitions take no caller args (`provide()` is parameterless), so no `inputs` variable is exposed inside their bodies. Inside top-level `result:` the `result` variable is typed from the dispatch target's `outputType:`. The produced top-level `result` value is AJV-checked against the abstract this definition `extends` (`outputType`); top-level `inputs` is AJV-checked against the dispatch target's `inputType` when declared.

## Capabilities

- `Telo.Service` — `init()` + optional `teardown()`; long-lived servers, pools
- `Telo.Runnable` — `run()`; one-shot tasks, pipelines
- `Telo.Invocable` — `invoke(inputs)`; request handlers, scripts
- `Telo.Provider` — `init()` + optional `provide(): Promise<T>`; config/secret/value-flow sources. All fields implicitly `x-telo-eval: compile`. `provide()` opts the definition into the typed value-flow contract checked against the abstract's `outputType`; template-form providers (declared with `provide:` on a `Telo.Definition`) get a synthesized `provide()` automatically.
- `Telo.Mount` — mounted into a Service (e.g. HTTP APIs, middleware)
- `Telo.Sink` — `write(record)` + `flush()` / `flushSync()` / `close()`; a record-stream destination the runtime writes to **directly**, never through `ctx.invoke` (per-record dispatch is too slow, and dispatch emits trace events, so logging through it would generate telemetry from inside the telemetry path). Payload-opaque by design, so a future `Telo.TraceSink` reuses it; the log-specific fields live on the `Telo.LogSink` abstract. Scoped to record streams — metrics aggregate rather than stream and are not covered.
- `Telo.Type` — pure schema definition, no runtime instance

Defined as `Telo.Abstract` entries in `builtins.ts`.

**`Telo.Executable` is a SLOT CONSTRAINT, not a capability.** It is the built-in parent of `Telo.Invocable` and `Telo.Runnable` — "control can be transferred to this" — and it exists so a slot accepting either says so once instead of listing both. `capability: Telo.Executable` is **rejected** (it is absent from the kernel's `KNOWN_CAPABILITIES` enum): it names no lifecycle role, so nothing could implement it. It is the first abstract-extends-abstract edge among the built-ins; kind acceptance was already a transitive walk over the `extendedBy` index, so it costs two edges and no new machinery. **`Telo.Service` is deliberately outside it** — a service's `run()` is a lifecycle start the kernel dispatches differently (no ambient scope, so inbound work roots its own trace), and admitting it would make every step's `invoke:` accept a service. Boot-target slots that genuinely take `Runnable | Service` stay kind lists, the honest shape for a heterogeneous set.

**`Telo.Abstract`** is the **non-instantiable** flavor of a base kind: it uniquely means *no default implementation — must be extended* (load-bearing for `Sql.Connection`, `Codec.Encoder`, `Ai.Model`, …). Since general `extends` now specializes concrete kinds too, an abstract's only remaining special behavior is that instantiating one is an error and it has no `base:`/controller to inherit. Reach for a `Telo.Abstract` when you want a contract with no default implementation; use plain `extends` of a concrete kind (with `base:`) when you want to reuse an existing controller under a friendlier schema.

## Lifecycle, scopes & value flow

**Capability governs *wiring*, not dispatch.** The kernel calls `init()`, `snapshot()` and `teardown()` on any instance that has them, with no capability check (`if (instance.teardown) await instance.teardown()`), so a `Telo.Runnable` may implement `teardown()` — `Run.Sequence` does. What the declared capability *does* govern is which `x-telo-ref` slots accept the kind, statically: a `Run.Sequence` step's `invoke:` takes `Telo.Executable` (the parent capability `Telo.Invocable` and `Telo.Runnable` extend), its `targets:` takes `Telo.Runnable | Telo.Service`. A resource that must be both started and invoked therefore has to be **two kinds** — no single declared capability satisfies both slots.

**Side effects belong in `run()`, never `init()`.** `init()` builds the instance and nothing observable; `run()` performs the effect. `Http.Server` is the reference: `init()` registers plugins and routes, `run()` calls `listen()` and acquires a kernel hold, `teardown()` closes and releases it.

**Configured state is pulled; observed state is pushed.** `snapshot()` returns what the author configured, and the kernel pulls it after `init()`, after `run()` is dispatched, after each `invoke()`, and on every `setStatus()` — it is a function of the manifest, so re-deriving it is always correct. What a resource *learns* goes the other way: `ctx.setStatus(...)` reports it at the moment it is known, because nothing but the controller knows when that is. Both meet in `EvaluationContext.publishSnapshot`, the single publication path. Splitting them is what keeps each shape described once — a controller never rebuilds observed state inside `snapshot()` from a field it stashed only for that purpose. A publication is a **reading, not a live window**: the published value is detached from what the controller handed over (`detachSnapshotValue` rebuilds plain objects / arrays; class instances and functions pass through, since copying one would break it), so mutating a reported structure cannot rewrite an already-published value.

**Observed state (`status:`)** is what a resource learns while running, as opposed to what its author configured. A kind declares it as a JSON Schema block on its `Telo.Definition` / `Telo.Abstract`; a controller reports it with **`ctx.setStatus(...)`**; the kernel holds the last value and publishes it at `resources.<name>.status.<field>`, leaving the flat half (`resources.<name>.<field>`) untyped and unchanged. Reporting **replaces** rather than merges (this is the resource's observed state now), is AJV-checked against `status:` at the call that made it (`ERR_OBSERVED_STATE_INVALID`, or `ERR_OBSERVED_STATE_UNDECLARED` when the kind declares no block), is an error **before the resource has started** (`ERR_OBSERVED_STATE_BEFORE_START` — `init()` performs no I/O, so nothing is observed there), and is **sticky**: the last reading stays published until teardown, so a dispatch that reports nothing leaves it in place. A kind that declares `status:` may not also return a flat `status` field (`ERR_OBSERVED_STATE_KEY_COLLISION`); one that declares none may use the name freely. `required:` inside `status:` is rejected — every declared field is mandatory once the resource has run, and a sometimes-absent one is declared nullable. The chain is folded in the scope that **declared** each definition (an `extends` alias belongs to the file it was written in) — the kernel stamps the folded block at registration beside `effectiveAuthorSchema`; the analyzer re-scopes per declaring module. Statically: `OBSERVED_STATE_IN_STARTUP_FIELD` (any path through `.status` in a compile-eval field — a purely syntactic rule, so it covers undeclared kinds too), `OBSERVED_STATE_NEVER_RUN` (nothing can start the producer — in no `targets:` and named by no step's `invoke:`), `OBSERVED_STATE_REQUIRED_FORBIDDEN`, and `CEL_UNKNOWN_FIELD` under `.status` (cross-module too: an import's exported instances are typed under `resources.<Alias>.<name>`). At runtime there are three `ERR_OBSERVED_STATE_UNAVAILABLE` messages — not started / started but `run()` still pending / `run()` returned with a declared field missing — because each needs a different action and only the kernel can tell them apart. See `kernel/docs/observed-state.md`.

**`Run.Sequence` scopes (`with:` / `targets:`).** `with:` is an array of full resource declarations (`kind` + `metadata.name`) whose lifetime is the sequence — created on entry, torn down on exit — annotated `x-telo-scope: ["/steps", "/targets"]` so `!ref`s in either resolve against them. `targets:` lists with-resources to `run()` before the steps. Standing a server up around a test is exactly this shape (`modules/crud/tests/crud-over-http.yaml`). A scoped resource **publishes like any other**: each `ScopeHandle.run()` gets its own map of the scope's resources, layered **at read time** over the enclosing module's (not copied at scope entry — `setResource` replaces `_resources` wholesale, so a copy would go stale) with scope-local names winning (matching `ScopeContext.getInstance`'s order, so CEL and `!ref` agree), and `ScopeContext.run(name)` dispatches a scope target through the kernel chokepoint so it is traced, records that it started, and publishes. Fresh per run, so two concurrent runs never observe each other. A scoped name resolves only inside the `x-telo-scope` regions. **The handle is built on the context that OWNS the resource, never the root** (Phase 5 passes it as `PreInitHook`'s `owner`): a `with:` block's inline declarations name their kinds through the import aliases of the module that DECLARED them, so a library's scoped `kind: OAuth.RedirectListener` resolves against that library's `imports:` — the root Application has never heard of the alias. A scope nested inside a scoped resource forwards its opening scope's context rather than replacing it, so this holds at any depth.

**Controllers resolve a `!ref` slot with `ctx.resolveRef(value, guard, describe, expects)`**, not the standalone `resolveRefInstance` — only the context form rescues a `!ref` that reaches the controller as a raw sentinel (**Phase-5 injection is field-map-driven, and the field map does not descend into the inline declarations inside an `x-telo-scope` array**, so a ref slot on a scoped resource is not an injection site; Phase 2.5 *does* rewrite such a sentinel when it can name a target, so both shapes arrive) and resolves a bare name **scope-local first, enclosing module as the fallback** — the order `ScopeContext.getInstance` and the CEL `resources` layering already use, so `!ref` and CEL agree about what a name means inside a scope. That is what lets a `with:`-scoped resource reference a scoped sibling (`OAuthClient.RedirectAwait`'s `listener:`). The standalone form stays for callers holding only a `{ moduleContext }` slice; it takes the precedence via the optional `resolveLocalInstance` hook on `RefResolveContext`. Sentinel knowledge lives in the kernel, never the SDK, which has no runtime dependencies.

**A controller's `ctx` is scoped to the context that OWNS its resource** — the module context for a top-level resource, the per-run scope child for a `with:`-scoped one. Registering a manifest, resolving a sibling by name, expanding CEL, spawning a child context, dispatching and publishing all go there. `ctx.moduleContext` is reserved for what belongs to the MODULE rather than the resource: imports (`registerImport` / `resolveImported*`), the controller policy, and the logging scope — all inherited by a scope child, not owned by it. The distinction is load-bearing: a scoped resource that registers an inline definition into the module lands it in a pending queue the module's init loop drained at boot, so it is never created and the dispatch fails with `ERR_RESOURCE_NOT_FOUND`.

**An init failure is reported by ROOT CAUSE, not by count.** When the multi-pass loop gives up, everything downstream of the real failure is unfinished too, so the kernel classifies the set before raising `ERR_RESOURCE_INITIALIZATION_FAILED` (`init-failure-diagnostics.ts`). What makes an entry **derived** is its error CODE — `ERR_LOCAL_REF_PENDING` / `ERR_CROSS_MODULE_REF_PENDING`, a deferral meaning it never ran — **never a reference edge**: an edge proves an edge exists, not causation, so a resource that refs a failed dependency *and* fails its own validation stays a root cause rather than having that error swallowed. Edges are **attribution only**; `RuntimeDiagnostic.blockedBy` is the **root** of the chain (the walk stops at the first non-derived entry), and a deferral with no visible edge is derived but unattributed. Edges are captured at `create()` time, before Phase-5 injection replaces refs with instances, so the walk never descends into a controller's object graph. A nested context's failures (an import initializing its library) attach as `children` rather than flattening into the parent's message — reported even when the wrapping entry is itself collapsed, since a child's roots are not shadows of the parent's failure — and both headlines come from `summarizeInitFailures`, never from re-parsing rendered text. Nothing is hidden wholesale: if every entry is a deferral, the set reports unclassified. Renderers consume the classification (`derived`/`blockedBy`/`children`), never re-derive it. See `kernel/docs/resource-lifecycle.md` §2.2.1.

**`inputs`/`outputs` are always VALUES; `inputType`/`outputType` are always SCHEMAS.** One invariant, no exceptions — `inputs:` on a run kind used to mean a JSON-Schema property map, which is why a declared `default:` never applied and a misspelled input went unnoticed: nothing read the contract at dispatch. The **invocation contract** is normative in `kernel/specs/invocation-contract.md`; the shared resolver is `analyzer/nodejs/src/invocation-contract.ts` (browser-safe, re-imported by the kernel — the split used for `buildEvalPaths` / the redaction path parser), and the kernel half is `invocation-contract-binding.ts`.

- **Resolution layers** instance declaration → the kind's, resolved to the **nearest declaration along `extends`** → undefined. Contracts **REPLACE, never merge**: config (`effectiveAuthorSchema`) and observed state merge because construction and reported state are additive; a call signature is not, and merging a child's required inputs into its parent's yields a union no caller can satisfy.
- **A controller-inheriting child that declares its own contract MUST bridge it** — `inputType` needs `inputs:`, `outputType` needs `result:` (`CONTRACT_MISSING_MAPPING`). The inherited controller understands only its own shape, so an unmapped replacement would be inert. A child with its own controller/template body is exempt.
- **The kernel binds the contract to the instance at `create()`**, its single instance-production site, so **an instance is never observable unbound**. Enforcing at a handoff would mean enforcing at every handoff (Phase-5 injection, `ctx.resolveRef`, scope handles, template dispatch, `ctx.invoke`) and one missed site silently reopens the hole — Phase-5 injection is the dominant path, and `Ai.Agent` reads `this.resource.model` and invokes it directly. Binding rather than wrapping keeps member forwarding, prototype identity and the runtime-value walks non-problems. Consequence: the bound `invoke` shadows the controller's, so an internal `this.invoke()` goes through the contract.
- **`invoke` and `provide` are bound; `run()` is not** — parameterless and void, so nothing to fill or validate; a resource whose contract requires inputs at a run site is `CONTRACT_INPUTS_AT_RUN_SITE`. A bound entry point **forwards every argument**: the InvokeContext (cancellation, tracing) rides in later parameters, and dropping it strands detached work.
- **Validation skips `x-telo-stream` properties in BOTH directions** (a live `Stream` in a declared slot is not data), and defaults are filled over a copy **deep along default-bearing paths** — a flat shallow copy would let a nested default mutate the caller's object.
- **Contract errors are an ambient union** (`ERR_INPUT_INVALID` / `ERR_OUTPUT_INVALID`, `sdk/nodejs/src/contract-errors.ts`): raised as structured `InvokeError`s so they survive into a `catch`, nameable and typo-checked in `catches:`, and never counted toward a kind's declared `throws:`. A kind must not declare either itself.
- **`Telo.JsonSchema` is a kernel built-in** — declaring a shape is not optional once any kind can carry a contract, so writing `inputType:` must not require an import, and a library declaring its own contract must not import a module to describe itself. `modules/type` is **deprecated**; `Type.JsonSchema` still resolves unchanged.

**One call graph, not a model per analysis.** `analyzer/nodejs/src/call-graph.ts` (`buildCallGraph`, browser-safe) is the single answer to "what calls what", built over **two node kinds**. Resource nodes carry declaration-site identity. **Step nodes** carry name, lexical order, enclosing array and nesting parent, and only *optionally* an outgoing edge — steps are nodes rather than edge decorations because a pure `value:` step produces `steps.<name>.result` while referencing nothing, and because step identity / ordering / nesting are what result typing, throws coverage and the editor's step rendering actually consume. What the model carries is **lexical order and containment, not execution order**: which branch runs is decided by runtime predicates and is not statically derivable, and no consumer needs it. It owns the analyzer's only step-array recursion.

Edges are `(from, slot, to, use)`, where `from` is a resource **or** a step node, and **the slot path is part of the edge's identity, so the graph is a multigraph**: `Cache.View` holding its `store:` as a `dependency` and calling its `invoke:` are two edges even when both name the same resource. Erasing that is what the old set-valued adjacency map did, silently merging a dependency with a call. The init-order consumer projects down to unique pairs itself, being the only one for which the distinction genuinely does not matter.

Consumers read one fact and derive their own: `buildDependencyGraph` orders on resource-level edges of every use but `schema`; `collectRunReachableNames` keeps whatever a control-transferring edge reaches. **Step edges are excluded from init order by NODE KIND, not by `use`** — a resource-level slot is a Phase-5 injection site so its target must exist first, while a step's slot resolves at dispatch; both are `use: call`. An edge whose slot declares no `use` (the legacy string form) counts as control-transferring, the conservative direction while the ecosystem migrates.

**Execution zones ride the ambient invocation context.** A resource can require being invoked inside another's body (a statement inside its transaction); the **zone stack is the `zones` member of `InvokeContext`** — deliberately NOT a second ambient store beside the cancellation scope, because a parallel store means enumerating every site that must clear it and one missed site is a false guarantee under a hard error. On the existing context, the two clearings the runtime already performs do the work with no zone-specific code: `ctx.runDetached` replaces the ambient with the uncancellable root, and a `Telo.Service`'s `run()` establishes none (so every shipped inbound trigger, all registered by Services, is zone-free by construction). The residue is exactly one shape — a `trigger.inbound` registered from *inside* an invocation by a non-Service — spec'd as a conformance obligation on the registrant: dispatch through **`ctx.rootContext()`**, never `undefined`. That obligation is what the analyzer's hard error on `trigger.inbound` edges rests on. **Nothing hangs off `openSpan`** — tracing is off by default and called by one controller, so a safety guarantee hung there would be absent by default. **Every context rebuild goes through `deriveContext(base, overrides)`** (SDK): a fresh object literal at `runInvoke`'s tracing branch / `runInstance` / `runTargets`' `targetCtx` / `openSpan` would drop `zones` under tracing-off and keep it under `--debug`, a safety property that changes with a debug flag. **A zone entry is three identities and nothing else** — providing kind, provider handle, correlation handle — so it stays ABI-serializable and no controller can read another module's open transaction off the stack. Instance identity is a **`ResourceHandle`** (`{ id, ref }`, `id` minted at `create()` — the single instance-production site, so an instance is never observable unbound; `ref` is the declaration site, diagnostics only). The instance→handle `WeakMap` has **no reverse direction**, which is what stops a handle becoming someone else's instance. A `with:`-scoped resource gets one id per scope run, which is also what the static correlation rule says. Controller surface: `ctx.self`, `ctx.withZone(slot, fn)` (a **scope function**, not push/pop — push/pop cannot be honest across async boundaries; hands back the derived context AND the minted entry), `ctx.requireZone(field, ctx?)` / `findZone` / `zonesFor(instance)`. **A controller names its own annotation SITE, never a kind** — it has no alias scope (`ctx.moduleContext` is the consumer's, and `resolveKind` is not on the surface), so every field of the entry is derived by the kernel from the annotation. **The payload rule: provider-private state hangs off an INJECTED INSTANCE, never a module import** — a module's controllers ship as separate bundles each inlining its copy of a shared source file, so module scope is one copy per bundle (that was the live `sql` bug: `transaction:` threw on every path). `sql` keeps its executor `WeakMap<ZoneEntry, Kysely>` as an instance field on the connection, and the explicit-zone path **throws** (`ERR_SQL_ZONE_FOREIGN`) rather than falling back, since `?? this.db` would convert a delivery split into silently non-transactional writes.

**Kernel holds decide when an app exits.** `waitForIdle()` resolves at zero holds; a running `Http.Server` holds one, so an app with a service in it stays up until SIGINT. Anything that must let a one-shot app finish has to release its hold.

**One import instead of two.** An app that configures a backend itself imports both the abstract and the implementation (`sql` + `sql-sqlite`) — that is normal and ~25 manifests do it. When a consumer should need only one import, the sanctioned collapse is a library that owns the wiring and exports **instances** via `exports.resources` (`tests/__fixtures__/re-export/`), not a module re-exporting another module's kinds.

## x-telo-\* Schema Annotations

Inside `Telo.Definition` schema blocks:

- `x-telo-eval: "compile" | "runtime"` — when `${{ }}` expressions are evaluated: at load time (compile) or per invocation (runtime). Without annotation, strings pass through raw. **CEL-bearing fields MUST be annotated:** a field a controller will `expandValue` (or the kernel auto-expands) must carry `x-telo-eval` or `x-telo-context` (or sit under an `x-telo-step-context` / `x-telo-error-context` region, or a provider's implicit root eval). The analyzer enforces this — a `!cel` / `${{ }}` outside every such region is `CEL_IN_NON_EVAL_FIELD` (the value would be read as a literal, never evaluated). Eval-path handling lives in the analyzer and is re-imported by the kernel, so runtime expansion and the static check share one source of truth — both halves: extraction (`buildEvalPaths`, own schema **+** capability abstract) and the containment matcher (`evalPathCovers`, used by the analyzer's coverage check and the kernel's compile/runtime `isExcluded`). The check stops at nested inline `{ kind }` resource boundaries — that CEL belongs to the nested kind.
- `x-telo-ref` — field must be a reference to a resource of a given kind, **plus a declaration of what the declaring resource does with it**. Two shapes are accepted: the bare string (`x-telo-ref: Sql.Connection`, legacy) and the structured form, which is what new schemas write:

  ```yaml
  x-telo-ref:
    kind: Telo.Executable        # one alias-qualified kind, or a LIST of them
    use: call                    # required in the structured form
    inputs: /inputs              # optional: JSON Pointer to this call's argument slot
  ```

  **`kind` takes a list, replacing the `anyOf`-of-branches shape** multi-kind slots used. An `anyOf` puts each `x-telo-ref` in its own branch, so a structured form under it could carry a *different* `use` per branch — a disagreement with no meaning, since which kinds are acceptable is a property of the target while `use` is a fact about the slot. The analyzer always unioned those branches internally; the list makes the surface match the model.

  **`use` names WHEN control reaches the target, relative to the declaring resource's own invocation** — the one primitive fact every analysis derives from. Control transfer means the target's **bound entry points** — `invoke()` / `provide()` / `run()`, the methods the kernel dispatches, traces, contract-checks and zone-tracks. A convention or domain method on a held instance (`query()`, `embed()`, `stream()`, `getToken()`) is not dispatch, no matter how much work it does: that slot is `dependency`. This is the line that keeps `use` aligned with what the kernel's machinery can actually observe — `Ai.Text.model` is `call` because the controller drives the bound `invoke()`, while `Embedding`'s `model:` is `dependency` because `embed()` is a plain method, exactly like a connection's `query()`. `schema` (names a shape; no runtime instance, no edge) · `dependency` (held and read; control never transfers — init-order edge only) · `call` (transfers during my invocation and returns to me) · `detached` (transfers through the kernel's detach primitive; I do not await it) · `trigger.inbound` (I register the target; control reaches it after my invocation, driven by a request or timer, with a guaranteed-fresh ambient context) · `trigger.consumer` (I register it; control reaches it when someone drains a value I returned, so no guarantee holds). The trigger source lives **inside the value**, not in a sibling key, so a trigger with no source is unrepresentable and the enum drops into a case map unchanged.

  **`use` is a SET**, written as one value when it is a singleton. A slot may dispatch its target more than one way within a single invocation: `Cache.View` calls inline on a miss and detached on a background revalidation, so it declares `use: [call, detached]`. Each consumer states its own reduction (exceptions propagate if **any** member is `call`; an ambient scope's lifetime extends only if **every** member is).

  **A slot whose mode is chosen by configuration declares a case map** keyed on a sibling field — `use: {by: /detach, cases: {false: call, true: detached}}` (`Lease.Critical`). The selector **must be statically resolvable** (a literal or a schema default — an omitted `detach:` takes its `default: false` and classifies as `call`); a CEL value there is `X_TELO_REF_DYNAMIC_SELECTOR`, because a call graph known only at runtime is not statically analyzable. The annotation's own validity is enforced by `validate-ref-slots.ts` (entry-module-scoped): unrecognized `use` tokens (`X_TELO_REF_INVALID_USE` — a typo would silently degrade to the legacy no-use reading), a structured form missing `use` or `kind`, and `anyOf` branches whose uses disagree (`X_TELO_REF_USE_CONFLICT`). There is deliberately no fallback — the throws union must assume `call` to keep an error path while a zone requirement must assume the opposite, so any default would reintroduce unsound inference. A case map and a set answer different questions: the map says *configuration decides which relation holds*, the set says *several hold at once*.

  **Pointers inside `x-telo-ref` are relative to the object ENCLOSING the annotated slot** — the resource root for a resource-level slot, the array item for a slot inside one, so a route's `handler` can name its siblings. No pointer reaches across an array boundary.

  **`use` is never cross-constrained against the target's capability.** The tempting rule — a control-transferring `use` requires a `Telo.Executable` constraint — is unsound: `Ai.Model` declares `capability: Telo.Provider` and no schema at all, exposing `invoke` / `stream` as an ai-module convention, and its slot is genuinely `use: call`. The divergence is structural versus nominal: the kernel tests method presence at dispatch, while any static test can only read a declared capability. Capability keeps saying nothing about whether a slot transfers control — that is this design's whole premise.

  **Every surface reads the annotation through ONE accessor** (`readRefSlot` / `isRefSlot` / `rewriteRefSlotKinds`, `analyzer/nodejs/src/ref-slot.ts`, browser-safe): the analyzer's field map, the kernel's Phase-5 injection, the GUI editor's reference picker, and `ide-support`'s completions / hover / go-to-definition. Making the annotation structured changes how a slot is *recognised*, and four surfaces used to recognise it by string-matching — omitting any of them would silently turn every ref slot in the editor into a free-text field. No consumer pattern-matches the shape again, which is what makes the next shape change a one-file edit.

  The constraint itself is an **alias-qualified kind**, the same grammar `kind:` / `extends:` use: an import alias declared in the same file, `Self.<Kind>` for the declaring library's own kind, `Telo.<Kind>` for a built-in. It is resolved in the DECLARING module's scope and rewritten to the canonical `<module>.<Kind>` before registration (`resolve-schema-ref-kinds.ts`), so the registry answers ref queries with no module context. A constraint that resolves to nothing is `X_TELO_REF_UNRESOLVED` (`KIND_NOT_EXPORTED` when the alias is known but the target gates the kind) — without it the reference check would read the unknown target as partial context and skip it, leaving the slot accepting anything. The legacy `"<namespace>/<module>#<Kind>"` identity form still resolves for already-published module versions (fed by `metadata.namespace`, which nothing else reads) and warns as `X_TELO_REF_LEGACY_IDENTITY`. All three are scoped to the entry's own modules — a published dependency is not the consumer's to fix. References are written **only** with the `!ref` YAML tag: `!ref <name>` (local) or `!ref <Alias>.<name>` (an imported library's exported instance). The object form `{ kind, name }` and bare-string references are removed — `validateReferenceForms` rejects an author-written `{ kind, name }` / string at a ref slot up front (`INVALID_REFERENCE_FORM`); a plain object at a ref slot is only ever an inline definition (`{ kind, …config }`, no `name`). At parse time `!ref` becomes a tagged sentinel; `resolveRefSentinels` rewrites it across the whole manifest tree to the internal `{ kind, name, alias? }` shape (Phase 2.5), the analyzer validates it at Phase 3, and Phase 5 replaces it with the live `ResourceInstance`. Per-call data (`inputs`, `retry`, …) lives at the parent slot, never inside a ref.
- `x-telo-scope: "/json/pointer"` — marks an execution scope; resources inside are initialized on-demand, not at boot. Controller receives a `ScopeHandle`.
- `x-telo-schema-from: "refProp/$defs/Name"` — derives field validation schema from a sibling `x-telo-ref` resource's definition schema. Used for polymorphic config.
- `x-telo-value-schema-from: "<field>"` — the value written at the annotated node must satisfy the type declared at the resource's `<field>` (resolved with the same `telo#Type` semantics as `inputType` / `outputType`, so inline and named types both work). For a kind with ONE declared output contract and SEVERAL slots that must each produce it — a decision table's rows (`Run.Choice`), a switch's arms — where only the branch that wins at runtime would otherwise be checked. The analyzer validates every annotated slot, including ones no current input selects, after `substituteCelFields` replaces CEL leaves with schema-shaped placeholders: so it catches structural disagreement (missing required, unknown property under `additionalProperties: false`, wrong literal type) and never false-positives on an expression. A `<field>` that resolves to no schema (an optional `outputType` left undeclared) is skipped — declaring the contract is what opts in. Generic and topology-driven; the analyzer hardcodes no kind (`analyzer/nodejs/src/validate-value-schema.ts`).
- `x-telo-context: <JSON Schema>` — annotates a handler field with the CEL context available inside it. Analyzer-only; no runtime effect. Within a context schema, properties can carry:
  - `x-telo-context-from: "<path>"` — navigates `manifestItem.<path>` (per-scope) and merges the resolved value as a **property map** into the annotated node's properties. Used for transport scopes where the navigated value is itself a map of variable names (e.g. `request/schema` → `{ query, body, params, headers }`).
  - `x-telo-context-from-root: "<path>"` — navigates `manifestRoot.<path>` and **replaces** the annotated node's schema with the resolved value. Used on individual property schemas (e.g. `properties.self`) where the resolved value is a single variable's full schema. Anchoring at the root avoids the schema-vs-manifest-tree depth ambiguity that `../` parent-paths would carry.
  - `x-telo-context-from-ref-kind: "<refPath>#<field>"` — reads a kind name from `manifestRoot.<refPath>`, resolves it via the definition registry, and returns that kind's `<field>` schema (e.g. `outputType` / `inputType`). Used to type `result` against the dispatched target's declared output shape.
    - `x-telo-context-ref-from: "<refProp>/<subpath>"` — existing form: reads a `{kind, name}` object from `manifestItem.<refProp>`, looks up the named manifest, returns its `<subpath>` field schema; when that manifest declares no such field, falls back to the referenced **kind's** `Telo.Definition`, then to an open schema. That layering mirrors `buildStepContextSchema` — a kind exposing the field for per-instance narrowing still wins, while a kind with ONE fixed output shape (declared once on its definition) types the context instead of silently degrading to permissive. This is what types `result` inside an `Http.Api` route's `returns:`.
- `x-telo-step-context: { invoke, outputType, value? }` — on an array field, tells the analyzer to build typed `steps.<name>.result` context from each item's invoked resource's output type. The optional `value` key names the step field that produces a result **without dispatching** (a pure step); such a step registers `steps.<name>.result` typed from its expression when that expression is a plain chain into something already typed (an earlier step, the kind's `inputType`), and permissively otherwise.
- `x-telo-bindings-from: "<field>"` — on an `x-telo-context` node, merges the names declared in the resource's `<field>` map (read from the resource ROOT, not the per-scope item) into that context, so a kind can offer **named CEL bindings** readable by bare name. Evaluation order is derived from the identifiers each expression parses to — never declared — and enforced nowhere at runtime, because `ctx.bindScope` evaluates each binding lazily and memoises it, so a binding reaches its dependencies by construction and one nothing reads is never evaluated. Derivation, cycle detection (`BINDING_CYCLE`) and the reserved-name check (`BINDING_NAME_RESERVED` — every name `buildCelEnvironment` already binds at that site, plus CEL's keywords) live in `analyzer/nodejs/src/cel-bindings.ts`. A name already in scope is **skipped** at runtime rather than shadowing, so a reserved name the check did not foresee degrades to a dead binding, never a hijacked global. Generic — no kind is named in analyzer code; `Run.Value` / `Run.Choice` are the first consumers.
- `x-telo-error-context: <JSON Schema>` — on an array field (e.g. a `catch:` / `finally:` branch), declares the schema of the `error` CEL variable in scope inside that field. Analyzer-only. Unlike `x-telo-context` (fixed-depth JSONPath scopes that don't resolve `$ref`), the analyzer collects these annotations across `$defs`/`$ref` and merges the `error` schema for any CEL whose path passes through the annotated field name (`<field>[<index>]`) — so it applies at arbitrary nesting depth (a `catch` inside a `try` inside a `catch`). `error.<typo>` becomes `CEL_UNKNOWN_FIELD`. Generic — no resource kind is hardcoded; any composer with error-bearing branches opts in by annotating them.
- `x-telo-widget: "code"` — on a string field, tells the telo editor to render a Monaco code widget instead of a single-line input. The language is resolved from the field's standard `contentMediaType` (e.g. `application/javascript`) via Monaco's own language registry, so adding a new language is purely a schema change — no editor code to touch.
- **`x-telo-binary: true`** — the property carries **raw bytes** (a `Uint8Array`; `Buffer` extends it). The **only `x-telo-*` keyword that emits validation code**, which is why it exists at all: bytes have no JSON Schema type, `type: object` is satisfied by every object (so a mistyped literal reached the controller instead of failing check), and `type: binary` is not an option — AJV refuses to *compile* an unknown type, with no setting to allow it, and a published `telo.yaml` would stop being JSON Schema for the hub, the editor and every third-party reader. An `x-` key is ignored by unaware tooling **by specification**, so it degrades to "unconstrained" rather than to "cannot validate this kind at all". Single accessor + AJV keyword in `analyzer/nodejs/src/binary-slot.ts` (browser-safe, the `ref-slot.ts` precedent), registered by the analyzer's `createAjv()` and by every kernel AJV site. Three consequences are load-bearing: the keyword is **AJV codegen, not a `validate` function**, so it inlines into the standalone validators the kernel compiles and caches; `celPlaceholderForSchema` hands a CEL leaf at a byte slot a real `Uint8Array`, so static and runtime agree by construction rather than by two rules kept in step; and it is exempt from `stripTeloAnnotations` (`VALIDATING_ANNOTATIONS` in `schema-validator.ts`), whose whole premise was that no annotation affects the validator — stripping it would silently reduce the slot to an empty schema. What falls out is the check the annotation exists for: **bytes always arrive by reference, never authored inline**, so no YAML literal is a `Uint8Array` and a literal at such a slot is rejected statically. **A union with a byte branch must use `anyOf`, never `oneOf`**: a consumer that does not know the keyword reads the branch as an empty schema matching everything, so under `oneOf` a plain string would match both branches and fail — the graceful-degradation property only holds under `anyOf`.
- `x-telo-stream: true` — on a property in an `inputType` or `outputType` schema, marks it as carrying a `Stream<T>` (the class exported by `@telorun/sdk`). Producers wrap their `AsyncIterable` in `new Stream(...)` so the value's constructor is recognized — CEL's runtime type-checker rejects unrecognized object constructors, and the analyzer's `buildCelEnvironment` registers `Stream` so `${{ steps.X.result.output }}` evaluations pass through as opaque values. The analyzer's chain validator forbids member access _past_ a stream-marked property (`result.output` is fine; `result.output.text` / `result.output[0]` are diagnostics). Convention: streaming Invocables put their stream on the `input` property of `inputs` and the `output` property of the result. Consumers iterate with `for await`. Forward-compatible: today a boolean; later may evolve to `x-telo-stream: { items: <JsonSchema> }` for element-type validation under the typed-abstracts plan, with `true` aliasing to `{ items: any }`.
- **`x-telo-provides-zone: true | <pointer>`** and **`x-telo-requires-zone: <kind> | { zone, key?, reason? }`** — **execution zones**: a resource declaring that it must be reached through another resource's body (a transaction, a durable run, a batch). Normative contract in `kernel/specs/execution-zones.md`; guide in `docs/extend/execution-zones.md`. **A zone is identified by the kind that PROVIDES it** — no new kind, no capability, nothing instantiated — so the providing side names no zone (making provision-on-behalf-of unrepresentable) and only the requirer writes one, through the alias-qualified grammar `extends` / `x-telo-ref` use (canonicalized by `resolveSchemaRefKinds` in the declaring scope; unresolvable is `ZONE_PROVIDER_UNRESOLVED`). Both annotations are read through ONE accessor (`analyzer/nodejs/src/zone-slot.ts`, browser-safe), the `ref-slot.ts` precedent. The provider's value is the **correlation key**, never the zone; the requirer's `key` is an **ordered pointer list, first hit winning**, because the correlated field is usually absent — `Sql.Command` declares `[/connection, /transaction/connection]`, the manifest-level transcription of the controller's own `??`. A pointer may traverse a `!ref` into a kind **the declaring module owns**. When nothing resolves, the requirement discharges **uncorrelated** — inventing a correlation would manufacture errors from a guess. **Zone semantics are a projection of `use`, classifying nothing**: `call` propagates callee→caller and a providing slot discharges (under the correlation rule, `extends`-aware); `detached` / `trigger.inbound` **error** (the runtime GUARANTEES a fresh context); `trigger.consumer` **warns** (the drain site decides); `dependency` / `schema` are no edge — `Sql.Query.transaction` is exactly that: a dependency ref that *carries* the requirement without being a call. Severity turns on whether the edge is DECIDABLY wrong, not on whether the `use` resolved per instance: a **set** containing `detached` / `trigger.inbound` **errors** (a set says several relations hold at once, so the controller really does detach on some dispatch, and the detached dispatch is never inside the caller's zone — only *how often* stays unknown), while `trigger.consumer`, an unresolvable case-map selector and an undeclared `use` **warn**, because there the target genuinely *might* be in a zone. Propagation is the separate reduction and needs every member to be `call`. (`Cache.View` is a case map on `/revalidate` rather than an unconditional `[call, detached]` precisely so the set appears only under `background`, where its detach is real.) An edge whose `use` is unknown neither propagates nor terminates — the opposite polarity from throws. Boot is the root: nothing encloses `targets:`. The pass is `analyzer/nodejs/src/resolve-zone-requirements.ts`, a **consumer of the call-graph service with no traversal of its own**; per-library export derivation runs as its own stage in `analyze()` (never at flatten — the flattened view carries the export surface, not the internal dispatch chain, and the registries the projection needs are built FROM flatten's output), cached in a **host-lifetime cache passed into `analyze()`**, keyed `(source identity, content signature)` — `AnalysisRegistry` is constructed fresh per closure per run by the editor, so a cache there would die at the boundary it exists to cross, and identity alone is stale-unsafe for a workspace library being edited. Both annotations are validated by `validate-zone-slots.ts` — the strict half of the same accessor split `validate-ref-slots.ts` has, and not optional: the two fail in OPPOSITE directions (an unreadable requirement is silently unenforced, an unreadable provision invents failures), and a correlation key written as a bare name would be read by the kernel's walk but skipped by the checker, so the halves would disagree about what the manifest means. Diagnostics: `ZONE_REQUIREMENT_UNSATISFIED`, `ZONE_REQUIREMENT_DEFERRED`, `ZONE_EXPORT_UNSATISFIABLE` (raised at the exporting library only), `ZONE_PROVIDER_UNRESOLVED`, `ZONE_ANNOTATION_INVALID`.
- `x-telo-type: "<Brand>"` — analyzer-only nominal value brand (e.g. `TcpPort`, `UdpPort`). Marks a value as a distinct CEL type even when its base type is identical (a `TcpPort` and a `UdpPort` are both integers), so wiring a `UdpPort` into a `TcpPort`-branded field is a static error. Standard JSON Schema keywords (`type`, `minimum`/`maximum`) still do the real validation; the brand carries only nominal identity and has no runtime effect (the value flows as its base type). Brands register on the analyzer's cloned CEL registry only, never the kernel runtime env. A plain base value flows into a branded field (gradual typing); only a conflicting brand is rejected. General mechanism — not port-specific; `ports` entries get their brand from `protocol` automatically.

## CEL Templates (`${{ }}`)

Pure expression: `"${{ variables.port }}"` → typed value. Inline: `"Hello ${{ variables.name }}!"` → string.

Available in `${{ }}`:

- `variables`, `secrets` — always available (module inputs)
- `ports.<name>` — root Application only; resolved inbound port integers (Application `ports` block)
- `resources.<name>` — after that resource's `snapshot()`; republished after `run()`, after each `invoke()`, and on every `ctx.setStatus()`. Available for `with:`-scoped resources inside their scope's regions.
- `resources.<name>.status.<field>` — declared observed state; exists only once the resource has started, so it is illegal in any field that resolves at startup (see Lifecycle)
- `steps.<step>.result` — inside `Run.Sequence` steps
- `request` — inside handler CEL (HTTP: query, body, params, headers, path, method)

**A CEL integer is int64 and needs no cast, anywhere** (normative: `kernel/specs/invocation-contract.md` §4.3–4.4). `int` evaluates to a JS BigInt, so `size(...)` / integer arithmetic produce one — and a BigInt used to be unable to leave a manifest: `JSON.stringify` throws on it, and AJV's type check is `typeof data == "number"`, so declaring `type: integer` rejected it *before* serialization. The only way out was `double(...)`, which says "float" about an integer and truncates past 2^53; it had spread into the stdlib's examples and docs. Both doors are open now, in the kernel, so **no module and no manifest handles this**: `boot()` installs `BigInt.prototype.toJSON` over `JSON.rawJSON` (`enableBigIntJson`, `kernel/nodejs/src/bigint-json.ts` — a composition-root action, so the installer is kernel-side; it **throws** rather than degrading on a runtime without `JSON.rawJSON`, since every site that used to carry its own handling now relies on it). A BigInt then serializes as its **exact decimal digits** — not a new policy, but what `fast-json-stringify` already emitted for a schema-typed `integer`, so the runtime's two JSON serializers now agree at every magnitude rather than only below 2^53. Process-global, in the same spirit as the `process.env` guardrail, so it covers every JSON boundary in the process including a third-party module's. The validator half is `withBigIntsAsNumbers` (`kernel/nodejs/src/bigint-schema-view.ts`), owned by `SchemaValidator.compile()`'s validator and `ctx.validateSchema` — **one layer, not two**: the contract binding validates the raw value and lets the validator normalize, merging the `useDefaults` fills back (**index-wise through arrays**, since AJV writes defaults under `items` too) so the dispatched value keeps its 64-bit range. `double(...)` retains only its real meaning — moving into the double domain for arithmetic, where CEL has no `int OP double` overload. Because `toJSON` runs **before** a replacer, a serializer that deliberately encodes a BigInt differently reaches the original through `bigIntAt(this, key)` (`@telorun/sdk`, the module-author half): `encodeJsonValue` tags it (a persisted value must replay as the same type), the `json` log encoding quotes it past the safe range (as OTLP does), and the `pretty` console encoding renders it as text. A `typeof v === "bigint"` replacer anywhere else is now dead code that changes an encoding silently. Regression coverage: `tests/integer-json-boundary.yaml`, `kernel/nodejs/tests/bigint-json.test.ts`.

**How `steps.<name>.result` gets its type**: through the shared contract resolver (`resolveContract`, `analyzer/nodejs/src/invocation-contract.ts`), in order: (1) the **invoked resource manifest's own `outputType` field**, (2) the **kind's** contract resolved along `extends`, (3) permissive `{type: object, additionalProperties: true}`. Layer 1 is what makes **per-instance response narrowing** work: a kind that declares an `outputType` property in its schema (`x-telo-ref: Telo.Type`, as `JS.Script` does) lets an author narrow one call site's result and have CEL type-check against it — no analyzer change needed. A wrong narrowing no longer type-checks against a lie unnoticed: the kernel binds the same resolved contract to the instance and validates the produced value at dispatch. A type field resolves from any of four forms (`resolveTypeFieldToSchema`): a bare type name, a `!ref`, an inline `{kind, schema}`, or raw JSON Schema.

**Resource-doc validation injects only `kind` and `metadata`** into a definition's `additionalProperties: false` schema. Every other top-level field an author may write — including `outputType` — must be declared as a property in the kind's own `schema`, or validation rejects it.

**Null-safety:** dereferencing a value whose schema admits `null` (e.g. `error` inside a `finally` block, typed `["object","null"]`) without a null-guard is a static error (`CEL_NULLABLE_ACCESS`). The analyzer recognises guards through `?:` ternaries and `&&` / `||` short-circuits — `error != null && error.code`, `error == null ? … : error.code`. General: applies to any nullable value in any CEL context (`templating/nodejs/src/cel/analyze.ts` `findNullableAccessIssues`, wired in `engines/cel.ts`).

## Module Documentation — MANDATORY

**Every module change MUST include documentation updates.** This is not optional. Before finishing any task that adds or modifies a module, verify:

1. Documentation exists in `modules/<name>/docs/` (and the module's `README.md`). If not, create it.
2. Documentation matches the current code. If code changed, docs must be updated.

Module docs live **with the module** and are surfaced through the Telo **hub** (`hub.telo.run`), which indexes each published module's manifest and docs — the standard library is discovered there, not embedded in the Docusaurus site. Do **not** wire per-module doc files into `pages/docusaurus.config.ts` / `pages/sidebars.ts`; the docs site links out to the hub for module discovery. The Docusaurus site is for the kernel/guides/extend/learn docs only.

## Manifest descriptions — MANDATORY

`metadata.description` on a `Telo.Library` and on every kind doc (`Telo.Definition` / `Telo.Abstract`) is **hub search text**: the hub embeds it for semantic search, so it is read by someone who does not yet know the module exists. Write it for that reader, not for a maintainer.

- **Say what it does, in terms of the problem it solves.** Lead with the capability and the vocabulary a searcher would type (locks, leases, retries, pagination, idempotency, …).
- **Keep it to one paragraph** — roughly 40–60 words. It is embedded as a single vector; a long multi-paragraph text dilutes it. Rationale, design history and trade-offs belong in `docs/` and in YAML comments above the doc, never in `description`.
- **No kind names, no capability names, no "the X abstract".** The kind and capability are already structured metadata on the doc. `The KvStore.Store abstract — a durable store…` → `Durable key/value storage…`.
- **No implementations, no backend names.** A generic module must not name the modules that extend it (`backed by Redis SET NX` / `kv-store-sql`); that coupling is backwards and pollutes search hits for the generic kind. Backends describe themselves.
- **No contrast with sibling modules.** `Cache.Store is also a key/value store, but…` reads as noise to a searcher and drags the sibling's terms into this vector. State this module's own guarantee positively.
- **No wording that only makes sense against history.** `NON-EVICTING`, `unlike before`, shouting caps for emphasis. Say `records live their full TTL and are never dropped early`.
- **Kind descriptions state the operation and its contract** — inputs, outputs, and what a failure/edge return means — in two or three sentences. See `modules/collection/telo.yaml` and `modules/kv-store/telo.yaml` for the target shape.

## Manifest categories

`metadata.categories` is the **declared grouping facet**: an unordered list of domain **display labels** (`[AI, Storage]`) on a `Telo.Library` (and optionally on a kind doc, where it *replaces* the module's for that kind). It is a facet, not search text — it never belongs in `description`, which is embedded as a vector.

**Authors write labels; the hub derives slugs.** `metadata.categories: [AI]` is indexed as slug `ai` + label `AI` (`category_slug()`, defined once in the hub migration). Filtering and URLs use the slug (`?category=ai`, accepted as either form since the parameter is slugified too); UIs print the label. That normalization is what makes `AI` and `ai` one group, and what keeps `Data Codecs` out of a URL as anything but `data-codecs` — an open vocabulary can't be validated into agreement, but spelling variance can be normalized out of it. It only sees variance the rule covers: `A. I.` slugifies to `a-i`, a group of its own. Because `ai` → `AI` isn't recoverable, both are stored, aligned by position (`categories` / `category_labels`); when several labels share a slug the facet shows the most-declared one, ties lexicographic.

**The vocabulary is open and nothing validates it.** A category is a plain string; whatever labels modules declare are the groups that exist. There is deliberately no list in the kernel, the analyzer, or the hub — a closed enum would block a third-party module in a domain the standard library never anticipated, and would make the analyzer's release cadence the bottleneck on naming. Reuse an existing label when one fits (a near-synonym like `caching` vs `Cache` still splits a group — normalization only fixes spelling variance); the standard library uses `AI`, `Compute`, `Configuration`, `Coordination`, `Data`, `Observability`, `Performance`, `Reliability`, `Scheduling`, `Storage`, `Streaming`, `Testing`, `Transport`.

**Only the hub slugifies.** The editor compares labels directly (case-insensitively) because a category never crosses an authorship boundary there — it groups kinds already resolved in one workspace, and a workspace library may be unpublished or unsaved, so there is no hub row to consult. Keeping the rule in one place is deliberate: two implementations would have to agree forever.

The **derived** grouping axis needs no declaration: a kind's `extends` target is the contract it implements. The hub resolves the alias prefix through the declaring manifest's own `imports:` map into `(owning module ref, kind suffix)` at ingest (`resource_kinds.extends_ref` / `extends_kind`); the editor does the same against the declaring library's imports (`resolveContract`). That is what groups every backend of one abstract together across module boundaries, and what nests `CacheRedis.Store` under `cache.Store` in the resource picker.

## Module metadata — descriptive fields, deprecation, runtime reach

The `metadata:` block on a module doc carries `name` (the only field anything resolves against) plus purely descriptive `version`, `description`, `repository`, `homepage`, `documentation`, `license`, `categories`, `deprecated`. Publish projects several onto OCI annotations (`oci-transport.ts`); nothing else reads them. **Because nothing branches on them, a mistyped one has no runtime failure mode** — so `validate-module-metadata.ts` (analyzer) type-checks the known fields and reports an unknown key only when it is a near-miss of a known one (`licence:` → `license`). The vocabulary stays **open**; there was previously no schema for `Telo.Application` / `Telo.Library` metadata at all (`metadataSchema` in `manifest-schemas.ts` is wired only into `Telo.Definition` / `Telo.Abstract`).

**No `authors` / `maintainers` field, deliberately.** Registration is open and unauthenticated, so a declared author verifies nothing; the hub derives a **publisher** from the ref's host + org (`module_publisher(ref, transport)`), because ownership is a property of the host. A `url` module is attributed to its host alone — its path segments are a directory, not an organisation.

**`metadata.deprecated: { reason, replacedBy? }`** is legal on a module doc and on any kind doc. `replacedBy` is **resolvable, and its form follows the level**: a kind names an alias-qualified kind (`Self.<Kind>` / `<Alias>.<Kind>` / `Telo.<Kind>`) resolved through the declaring file's own `imports:` — the identical path `extends` takes, so the hub reuses that resolver and stores `(replaced_by_ref, replaced_by_kind)`; a module names a **module ref**. Optional, because a module superseded by a kernel built-in has no module to point at. A kind whose replacement is in an un-imported module cannot be named — deprecate at module level instead, rather than inventing a second grammar or adding a real dependency to name a target. Diagnostics: `INVALID_DEPRECATION`, `DEPRECATION_REPLACEMENT_UNRESOLVED`, `METADATA_UNKNOWN_FIELD`, `METADATA_INVALID_TYPE`.

**Runtime reach is derived, never declared.** Which kernels can host a kind follows from its `controllers:` PURL candidates: `pkg:cargo` → **both** kernels (Node's `napi-loader` builds the crate as a `.node` addon, the Rust kernel's `cargo_loader` as a cdylib), `pkg:npm` and `pkg:telo/local/js` → Node only, `napi`/`wasm` bundle formats → no kernel today. **`telo module manifest --json` reports it** (`cli/nodejs/src/controller-runtime.ts`) and the hub stores what it is told — the PURL→kernel mapping is loader knowledge, and a second copy in a consumer would drift silently the day a loader lands. Three invariants: it is **per kind**, not per module (`std/console` has Rust controllers on two of four kinds, so a module boolean would lie — the roll-up is full/partial); a controller-less kind is **`portable`**, a flag rather than an enumeration of today's kernels, which would go stale when a third kernel ships; and **language is a separate axis from runtime**, left blank for `napi`/`wasm` whose source language the PURL cannot determine.

**The kernel labels are `nodejs` / `rust`** — the ones `LABEL_TO_PURL_TYPE` (`runtime-registry.ts`) already gives an `imports:` entry's `runtime:` field, and the implementation directory names. A third spelling for the same two kernels would mean an author who wrote `runtime: nodejs` had to learn a different word for the hub's filter. The hub's `runtime` param is an **enum** on both HTTP routes and the MCP tool: an unrecognized value would otherwise match only portable kinds, a near-empty result that reads as "no such module" rather than "bad filter".

**The hub records that it ASKED for the runtime block separately from the answer** (`module_versions.runtimes_asked`). Inferring it from `runtimes IS NULL` cannot work: that is also what a CLI too old to report the block leaves behind, so the tracker would re-enter the whole ingest branch — origin pull, R2 put, kinds/resources rewrite, vector purge and re-embed — on every pass forever. Same distinction the `integrity` column draws between NULL and `''`, made observable instead of inferred.

## Controller delivery — bundle, don't publish to npm

A `Telo.Definition` names its controller with a PURL, and there are two delivery modes:

- `pkg:telo/local/js?path=./nodejs/<file>.mjs&local_path=./nodejs/src/<file>.ts` — **bundled**: the controller ships inside the module's own artifact. **This is how the standard library delivers.** Nothing is fetched from npm at load.
- `pkg:npm/@telorun/<pkg>@<ver>?local_path=./nodejs#<export>` — a published npm package. Still supported for third-party modules; in this repo it is what the **deferred** modules use — `http-server`, `sql-sqlite`, `image`, `pdf`, `starlark` — each of which either loads a native/wasm payload or inlines a dependency that resolves an asset relative to its own module URL. Don't add new ones.
- `pkg:cargo/<crate>?local_path=./rust#<entry>` — a **Rust controller crate**, built on load from a source checkout. `starlark` and `console` carry one. Both kernels consume the identical candidate; what differs is the loader (Node's `napi-loader.ts` produces a `.node`, the Rust kernel's `cargo_loader.rs` a `cdylib` opened over `telorun-abi`) and the SDK backend each selects at build time — `--features telorun-sdk/napi` vs `--features telorun-sdk/native`. **`telorun-sdk` declares no default backend**: the controller crate has no `[features]` block, so `--no-default-features` on that build would target the wrong crate, and a dependency feature is the only selector that works. There is no published-artifact story for these yet — `?local_path=` resolves only in a checkout, so a bundled native layer (`pkg:telo/local/dylib` + `os`/`arch`/`libc` qualifiers) is what a distributable Rust controller still needs.

**PURL anatomy** (`kernel/nodejs/src/controller-loaders/bundle-loader.ts`) — every segment carries meaning: type `telo` = Telo-delivered rather than fetched from an ecosystem registry; namespace `local` = bundled in the artifact (reserving `pkg:telo/registry/…` for a controller fetched as its own artifact later); **name = the artifact format** (`js` is all the Node kernel hosts today; `napi`/`wasm` raise `ControllerEnvMissingError` so a candidate list like `[pkg:telo/local/napi …, pkg:telo/local/js …]` falls through to one this — or another runtime's — kernel can load); `?path=` is the built file relative to `telo.yaml`; `?local_path=` is the TypeScript source it was built from; the `#fragment` is the named export (omit it and the whole bundle is the controller). Format is explicit because bundling is the one delivery mode not tied to an ecosystem's runtime (npm ⇒ JS, cargo ⇒ Rust; a bundle is just files).

**Mechanics of bundling:**

1. **Sources** live in `modules/<name>/nodejs/src/*.ts`. `modules/<name>/nodejs/package.json` is `"private": true`, named `@telorun/<name>-build`, and is **never published**. It exists for two reasons only: to declare the dependencies esbuild inlines, and to **type-check** the sources (esbuild does not). **Nine packages keep publishing**, because each is the TS contract a third-party implementation compiles against, not module code: `codec`, `http-dispatch`, `kv-store` and `type` declare no controller at all and are pure libraries inlined into each consumer's bundle; `ai`, `cache`, `sql`, `embedding` and `vector-store` *do* carry controllers, so those move into bundles and the package keeps publishing with its controller subpaths dropped and only the contract exports left. One rule, two shapes: a package publishes iff someone outside this repo needs it to *build* — nothing ever loads any of them at run time, since no PURL names them.
2. **Build** = `tsc -p tsconfig.lib.json && esbuild src/<x>.ts --bundle --format=esm --platform=node --target=node20 --external:@telorun/sdk --outdir=. --banner:js='<createRequire shim>' --out-extension:.js=.mjs`. The emitted `nodejs/<x>.mjs` is a build artifact, gitignored via `modules/*/nodejs/*.mjs` — never commit it. The banner is not optional: it defines `require` in module scope so esbuild's `__require` shim (emitted for a bundled CJS dependency) resolves instead of throwing "Dynamic require of X is not supported" under Node. `--conditions=source` is not optional either: an inlined workspace TS library must be taken from its `src/`, not its `dist/`, or building a controller would depend on having built every library it inlines — the exact build step this design removes, and a hard "Could not resolve" on a fresh clone. Every inlined package declares `source` ahead of `import` in its `exports`. The kernel's dev build uses the same option set (`CONTROLLER_BUNDLE_OPTIONS` in `controller-loaders/source-bundle-builder.ts`) and esbuild is pinned to one version through a pnpm `catalog:` entry — the flags AND the version must match, or the bundle a contributor runs is not the bundle that ships.
3. **`@telorun/sdk` stays external, never inlined.** The bundle has no `node_modules`, so `BundleControllerLoader` symlinks every name in `REALM_COLLAPSE_NAMES` (`controller-loaders/realm.ts` — `@telorun/sdk` today) into a `node_modules/` beside the bundle, pointing at the kernel's own copy. Standard resolution then finds it on both Node and Bun (ESM resolve hooks aren't honoured by Bun; Bun's plugins don't intercept runtime imports — a symlink is the one portable mechanism). That collapses *identity* as well as resolution, so `Stream` / `InvokeError` `instanceof` checks hold across the kernel/controller boundary. Authors write a plain `import { … } from "@telorun/sdk"`.
4. **There is no build step in development.** When the declaring module has **no artifact handle** and `local_path` resolves on disk, the loader builds the controller from source with esbuild (`source-bundle-builder.ts`) and imports that — so a fresh clone runs `pnpm run telo ./manifest.yaml` after `pnpm install`, and editing `src/*.ts` and re-running picks the edit up. The guard is the *absence of an artifact*, not the shape of the base URI: a published module served from the on-disk manifest cache also has a local base, and its payload is still its layer. The cache under `<entry-dir>/.telo/controller-src/` is keyed on a digest of **every input esbuild reported** plus the build options — a bundle's inputs are a graph, so an entry-only staleness check would serve a stale controller after an edit to a sibling or to a shared library. A changed input is a different key: nothing to invalidate, and a cross-process race (the test suite spawns a kernel per manifest) writes identical bytes to identical paths, through a temp file and an atomic rename. `pnpm run build:bundles` materializes what ships; it is on nobody's inner loop.
5. **`files:`** on the `Telo.Library` doc is the gitignore-style allowlist for what the manifest cannot otherwise name — assets, static files, sidecars. A controller's `path=` entry point joins the payload **because `controllers:` names it**, so it is never restated in `files:`, and a module whose only payload is its controller declares no `files:` at all. Symlink confinement is checked over the whole partition (`assertWithinModule`), not just the pattern match. Publish then **partitions** the payload into layers — see Layered module artifacts below.
6. **Loading materializes one layer.** `BundleControllerLoader` picks the candidate this host can run and asks the module's `ModuleArtifact` for that selector's directory; it never fetches, and never treats a module ref as a path. Missing file, unparseable PURL, non-`local` namespace, unhostable format, and a platform the host does not match are all env-missing (fall through to the next candidate); a bundle that imports but is malformed is a hard `ERR_CONTROLLER_INVALID`, and a source that fails to build is `ERR_CONTROLLER_BUILD_FAILED` — a real user-code failure is never masked as env-missing.
7. **Releases:** a bundled module publishes nothing to npm, so it takes **no changeset**. `metadata.version` under changie is its only version, and its fragment is written by hand. Two gates keep that honest, because nothing else can see the change: `scripts/check-changie-fragments.mjs` requires a pending fragment for any module whose files changed in the branch, and `telo publish` refuses changed bytes at an unchanged version (below).
8. **A dependency that resolves a file beside itself cannot be inlined.** A package that reads an asset relative to its own module URL (`__dirname`, `import.meta.url`) looks for it beside the *bundle* instead, where it is not — the failure is a runtime "file not found", not a build error. `http-server` is deferred for exactly this (`@scalar/fastify-api-reference` loads `dist/js/standalone.js`). Such a module keeps `pkg:npm` until it ships the asset in its own layer.

## Layered module artifacts

A published module is **one artifact of several layers**, not one tarball — normative spec at `kernel/specs/module-artifact.md`, model/parser/matching in `analyzer/nodejs/src/artifact-{selector,layer-index}.ts` (browser-safe, shared by `telo check` and the runtime, same precedent as the redaction path parser).

- **Layers by role:** `manifest` (`telo.yaml` alone), one `controller` layer **per selector**, `assets` (what the author's optional `assets:` list claims, fetched lazily on first module-relative access), and `common` (everything unclaimed).
- **A selector** is `format` + optional `os`/`arch`/`libc` PURL qualifiers on the same candidate (`pkg:telo/local/napi?path=./rust/x.node&os=linux&arch=amd64&libc=gnu`), in the OCI/GOOS vocabulary. Matching is one rule per axis: an axis the selector omits accepts anything, an axis it states must be equal; an undetermined *host* axis matches nothing that constrains it. So a Node kernel never downloads the `napi` layer, and a `linux/amd64` host never downloads the `darwin/arm64` binary. Selection reuses the existing `ControllerEnvMissingError` fallthrough — `ControllerPolicy` is untouched — and the platform check runs **before** materialization, or a candidate list would fetch every platform on the way to the right one.
- **The sink runs toward correctness.** An unclaimed file joins `common`, which is materialized alongside *any* controller layer **and** on any module-relative file read, so both an undeclared sidecar (a `.wasm` beside its glue) and an unclaimed static file are on disk when needed — a module shipping only static files has no controller to ride along with. `assets:` and the `siblings=` qualifier are optional refinements: omitting either costs bytes, never a load failure. Publish prints the partition so an author sees where each file landed.
- **The `layers:` index** in the published `telo.yaml` replaces the old scalar `filesIntegrity`. Per layer: `role`, `selector`, `blob` (OCI blob digest — addresses the layer and verifies the transfer) and `integrity` (framing-independent content digest — verifies what is extracted, re-derivable from disk). It lives in `telo.yaml` because the import pin hashes `telo.yaml` and nothing else; the OCI manifest is fetched by a mutable tag and is outside the chain, and pinning *it* is circular since `telo.yaml` is one of its layers. The manifest layer has no entry for the same reason. Chain: `import pin → telo.yaml → blob digest → layer contents`.
- **Addressing never reads the OCI layer list** — the pinned index is self-addressing, so a republish that reorders layers is invisible rather than fatal. Only the *manifest* layer is located through the OCI manifest (by media type), and its bytes are then pin-verified. Flat layer list, never an image index: the manifest and asset layers are platform-neutral, so an index would duplicate them per platform.
- **`ModuleArtifact`** (`kernel/nodejs/src/bundle/module-artifact.ts`) is built during `kernel.load()`, the only point where the **pinned** ref (`requestedUrl`) and the already-verified manifest are both in hand — a controller loader sees only the canonical base URI, which carries no `#sha256-`, so a self-fetching loader would degrade to trusting the cached `telo.yaml`. It memoizes per layer and serializes through `withDirectoryLock` (`kernel/nodejs/src/directory-lock.ts`, shared with `NpmControllerLoader`).
- **Module files are reached through `ctx.resolveModuleFile(relative)`** (SDK), which returns a **URI** and materializes the `assets` layer on first use. Never derive a directory from `ctx.moduleContext.source`: for a published module the manifest URL is not where the payload lives, and a `dirname` of it silently resolves against the process cwd. `Http.Static`, `mcp-client`, `assert`'s manifest loader and `Test.Suite` all use it.
- **Layers are OCI-only.** The registry origin is read-only and publishes nothing, so it serves manifests only; a bundled payload is always an OCI artifact.
- **Pre-layers artifacts still resolve.** A single-blob artifact (`application/vnd.telo.module.v1+tar`) contains `telo.yaml`, which is all the read path wants, so every module published before layers keeps loading — that is what leaves npm-backed modules untouched. It carries no index, so a *payload* published that way fails at the controller with an actionable republish error. Only the six modules shipping `files:` need republishing.
- **`telo install --platform os/arch[/libc]`** pre-materializes every layer that target could need (cross-architecture image baking); `telo run` materializes lazily. Cache warming is an optimization, never a correctness requirement — which is the bug this replaced, where a cold `telo run` failed because payloads landed on disk only after the load that needed them.
- **Publish gates on bytes, not on a ledger.** A bundle inlines its dependencies, so a fix in a shared TS library — or a transitive bump the lockfile alone moved — changes a dozen modules' shipped bytes while touching no file under any of their directories and moving no package version. `telo publish` therefore builds the payload and compares each layer's `integrity` against the artifact already published at that `metadata.version` (`cli/nodejs/src/bundle/payload-drift.ts`), refusing to publish changed bytes at an unchanged version and naming the digest that moved. Exact rather than inferred: it cannot miss what no version records, and cannot fire spuriously, because identical bytes hash identically. `scripts/publish-packages.mjs` runs it as a `--dry-run` pass over every module the version-moved and version-absent gates skipped, so the release fails loudly instead of shipping the fix to nobody. This replaced the auto-fragment step in `version-packages.mjs`, which answered the same question by proxy.

## Versioning & releases — MANDATORY

**The whole repo is intentionally pre-1.0, and staying pre-1.0 is the goal.** Breaking changes are released as **minor** bumps on purpose — both `@telorun/*` npm packages and Telo modules. A documented breaking change shipped as a minor (or a module's `Added` fragment for a breaking change) is the convention working as designed, **never** a versioning defect. Do not flag "breaking change shipped as minor" in reviews. The CI guards (`check-no-major-module-bump`, the changeset major-bump guard) exist to *enforce* this — anything that would bump to 1.0.0 is the error, not the minor.

Two release tracks, split by artifact:

- **npm packages → changesets.** Every change to a published `@telorun/*` package MUST ship a changeset — CI gates on `pnpm changeset status --since=origin/main`. Add one file under `.changeset/` (one per logical change, listing every affected package) and `git add` it. Use `pnpm changeset add --empty` when a change genuinely needs no release.
- **Telo module manifests → changie.** A module's published version is `metadata.version` in `modules/<name>/telo.yaml`, owned by **changie** — language-agnostic, so Node, Rust, and manifest-only modules version identically. Bump a module by adding a changie fragment: `changie new --project <module>` (writes `.changes/unreleased/<id>.yaml`). The `.changes/` ledger is the source of truth — never hand-edit `metadata.version`. Modules are pre-1.0 — use `Added` (minor) / `Fixed` (patch); `Changed`/`Removed` auto-bump to 1.0.0 and are rejected by CI (`scripts/check-no-major-module-bump.mjs`), mirroring the changeset major-bump guard. **Every module change that reaches the published artifact needs a hand-written fragment** — a bundled module has no npm package, so nothing auto-generates one; `scripts/check-changie-fragments.mjs` fails a PR that changed `modules/<name>/**` with no pending fragment for `<name>`. What "reaches the artifact" means is the whole rule, and it is not the same as "is under the module directory": `docs/`, `plans/`, `README.md` and `CHANGELOG.md` never ship, and for a module that delivers **no bundled controller** neither does `nodejs/` — there it is a pure npm package whose ledger is changesets, and the artifact is `telo.yaml` plus whatever `files:` selects. Requiring a fragment there would bump `metadata.version` and republish an artifact whose bytes did not move. A module that *does* bundle a controller has its sources as bundle inputs, so `nodejs/**` counts. Also skipped: a module whose version already moved on the branch (the fragment was written and batched) or that does not exist at the base ref (new, with no published predecessor). **`apps/<name>/**` is gated on the same rule**, because an app's artifact is a Docker image whose publish job keys on `metadata.version` moving — so a fragment is likewise the only thing that ships it. An app has no per-language delivery question (its Dockerfile copies the directory, so every non-doc file is in the image), which is the one branch that does not apply there. This gap is what let `apps/authoring-agent`'s system prompt be edited, merged, and shipped to nobody while the deployed image aged 22 days. The gate still depends on someone writing a fragment, so it is paired with a publish policy that does not: **every app image publishes `:latest` + `:sha-<short>` on each push** and reserves the immutable `:<version>` tag for the version move. `version-packages.mjs` keeps only its PURL-sync step, for the modules still on `pkg:npm`. `.changie.yaml` is generated by `scripts/gen-changie-config.mjs` (re-run after adding/removing a module; CI checks it's committed). Registry publish is gated on `metadata.version` movement plus the payload-drift check (`scripts/publish-packages.mjs`).

The PR gate for npm is `scripts/check-changeset-status.mjs`, not `changeset status` directly: private `-build` packages are versionable (deliberately — that is what propagates a shared-library bump into the modules that inline it), so a module-only PR would otherwise fail a check it should pass. The wrapper fails only for a changed **published** package with no changeset.

## Keep the authoring agent in sync — MANDATORY

`apps/authoring-agent` is an AI agent that authors Telo manifests for users. Its
system prompt (`apps/authoring-agent/chat/telo.yaml`, the `system:` block) is a
full primer that encodes the current Telo architecture — resource kinds,
capabilities, reference/CEL rules, import/export semantics, and authoring patterns
(composition, inheritance, etc.). **Any change to Telo's architecture MUST include
a matching update to that system prompt**, as part of the same change — never a
follow-up. A stale primer makes the agent emit manifests against an outdated
surface. Treat it like this file and the module docs: syncing it is not optional.
