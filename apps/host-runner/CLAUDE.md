# Host runner

`@telorun/host-runner` (bin `telo-host-runner`, Sustainable Use, off the telo line) serves runner-core's `/v1` session contract over a local-process backend. It was a CLI command until the CLI went MIT: a session server cannot live in an MIT binary, so the runner is its own package that depends on `@telorun/cli` and reaches it only through `main` and `@telorun/cli/release-binary`. The contract it serves is `packages/runner-core/CLAUDE.md`.

**One executable, both roles.** `src/entry.ts` hands a leading `telo` to the CLI's `main` before the server stack (fastify, pino, ws) is loaded, so a re-entry starts as fast as a plain `telo`; anything else is the runner. A session is a directory, and each Run is `telo-host-runner telo run --watch --inspect` of **the currently-running executable** in it, never a `telo` resolved from `PATH` — core builds the argv, and its program name stands for that executable (`src/runner/self-invocation.ts`: a single-file executable IS the command, an npm install re-enters through `process.argv[1]`). Every telo it starts is itself or a release binary, so no child gets `TELO_APP_CLI`.

**Identity.** What `telo-host-runner telo --version` prints is the bundled telo's identity (`X`, or `X+unreleased` for a build made while `X` is pending). This package's own version is `/v1/health`'s `version`; `/v1/capabilities` names the runner `Local (host runner)`. The bundled telo's identity reaches a client as the version a run reports.

**An application that names another telo version runs on that release's own binary** (`src/runner/telo-supply.ts`). The runner's own identity runs as this executable; any other version is the release asset for this platform, fetched, verified against the release's `checksums.txt` and cached by `@telorun/cli/release-binary`. What is known without the network is refused before a session exists (`400 telo_version_unavailable`: another build's unreleased identity, a platform no binary is published for); the download happens inside the session's start, reported as a progress event, and a failed fetch is that session's failed start. A cached binary is rehashed against the digest recorded when it was written, which catches corruption and nothing more. Every flag the runner passes sits before the manifest path, which every release reads the same way.

What differs from the container runners is **advertised rather than hidden**:

- **`io: ["streams"]` only.** No pty library rides inside the single-file executable; an explicit `io: "tty"` is `400 io_unsupported`, never downgraded, since `isatty()` is observable to the application.
- **No isolation.** The workload inherits this process's environment and privileges. Hence loopback by default (`--host` anything else is refused without `--allow-remote`) and **no browser origin by default**: every page the user visits reaches `127.0.0.1`, and a cross-origin `POST /v1/sessions` that `*` waves through runs arbitrary code as this user. `--allow-origin` names one; `RUNNER_CORS_ORIGINS` still wins, and core refuses an unnamed origin server-side.
- **The co-resident agent is a process.** `AGENT_MODULE_REF` (an `oci://` reference or an absolute path) names the agent's module; `AGENT_IMAGE` and `RUNNER_SESSION_USER` are refused at boot (exit 2). A session naming the agent gets one `telo run --no-input <ref>` as its own process group in the session's `agent/` directory (`src/runner/agent-process.ts`, `local-agent.ts`).
- **No session config**, enforced: a request carrying one is `400 invalid_config`. The telo version an application runs on is the contract's own field, advertised as `features.teloVersions`.
- **Ports are bound, not published.**

**A session is a directory kept by id, and nothing outlives the runner process.** The state root is ONE directory (`src/runner/state-root.ts`): `--state-dir`, then `RUNNER_STATE_DIR`, then the platform's per-user application-state directory — never the temp directory and never the telo cache. It holds `sessions.sqlite` and `sessions/<sessionId>/` with `workspace/`, `agent/` and `apps/<app name>/` (each application's `TELO_HOST_STATE_DIR`, the absolute path, created `0700` when it first runs), all `0700`, and `secret-seed` (the root of every application's generated secrets, from `@telorun/secret-seed` — core derives each application's own seed per Run; `RUNNER_SECRET_SEED` wins when set and is stripped from every process the runner spawns). Suspend keeps a session's directory; delete and retention remove it. The backend has no `adopt`, so at boot core marks every stored running session `suspended`, and **the boot sweep removes only what the store does not know**. A Run spawns core's argv as its own process group (`detached` on POSIX, `taskkill /T` on Windows); the SIGTERM handler detaches every workload before it closes the server, because a leaked `telo run --watch` holding a port after the editor quits is the failure that discipline exists to prevent.

**The runner owns its output.** Its stdout and stderr are genuinely its own (workload bytes travel the `/v1` byte channel): the address is the command's result (`-o json`, `{ url, host, port, stateDir }`), and stderr goes to runner-core as the server's `logStream`.

**Notices.** The runner redistributes MIT code, so `scripts/third-party-notices.mjs` writes `THIRD_PARTY_NOTICES` — each MIT package of the bundle's esbuild metafile, with its `LICENSE` text — into the tarball (`prepack`) and the single-file executable (`scripts/build-standalone.mjs`). `scripts/notice-supplements.json` supplies the copyright line of a package whose license text carries none.

**Build.** The single-file executable is the CLI's standalone build with this entry (`pnpm --filter @telorun/host-runner build:standalone`); the entry declares nothing about carriers, so it is never a carrier for `telo package`. Studio's desktop build ships it as its one sidecar.

Tests: `tests/` (`pnpm --filter @telorun/host-runner test`) — the contract against a fake telo (`tests/__fixtures__/runner-fake-telo`), the state root, the workspace, the re-entry and the notices.
