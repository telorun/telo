# Changelog

## 0.2.0 - 2026-11-15
### Added
* `@telorun/release` gains a Node-only `./node` entry and a `telo-release` bin: the whole `release` command tree (`add --unit`, `status`, `order`, `check`, `apply [--candidate[=<id>]]`, `verify [--write]`, `tag`, `adopt changesets`) over the `npm`, `cargo`, `docker` and `helm` ecosystems, each layer digested as a file set — the package manager's `pack` output (npm, pnpm, yarn classic and berry, bun; a packed `workspace:` / `catalog:` range is refused), `cargo package --list`, a Docker build context less its ignore file with the Dockerfile and ignore file always in it, and the chart `helm package` builds — plus a declared `payload:` (patterns or a `{ command }`), `metafile:` inline edges, and read-back from the npm registry, crates.io and an OCI chart registry. An ecosystem's settings are written at an anchor (`ecosystem: { docker: { ".": { context: ., name: web } } }`) or for every anchor under the new `release.ecosystems` block (`telo` and `helm` take `registry`, `docker` takes `registry`, `name` and `context`); a setting written flat on an entry, `release.registry` and `release.modules` are refused naming where each went, and an anchor that publishes with no registry is `NO_DESTINATION_KNOWN`. `order` emits one row per unit and package (`{ key, ecosystem, path, version, destination, group, imports }`), `status` / `check` / `apply` report their plan under `units`, `tag` tags `<unit>@<version>` for what the last committed apply moved, and `apply` writes each unit's `CHANGELOG.md` at its directory. `telo release` is that tree with the `telo` ecosystem registered, its `floor`, `stage` and `imports` subcommands and `requires:` checks kept, and `apply` rewriting `requires: telo: ">=unreleased"` to the surface the telo line is planned at; `telo release add --module` is now `--unit`.
* The release planner is its own MIT package, `@telorun/release`, with a browser-safe entry holding the whole release model: release units listed in `telo-workspace.yaml` under `release.units` (string-or-object entries, `!` excludes, last match wins), each shipping through the ecosystems it lists — a name, an order-free set, or a map of ecosystem to the anchor directories inside the unit holding that ecosystem's package — with `version`, `payload`, `metafile`, `versionFiles`, `ignore` and `maxBump` per entry, and `groups` and `maxBump` beside them. It ships the `npm`, `cargo`, `docker` and `helm` ecosystems' recognition and version files, resolves each unit's version from a declared `version:` or the one anchor that keeps one (`WORKSPACE_UNIT_VERSION_UNRESOLVED` otherwise), refuses an ecosystem no adapter serves (`WORKSPACE_ECOSYSTEM_UNAVAILABLE`), an anchor that is no literal directory in the unit or holds no package (`WORKSPACE_ANCHOR_INVALID`), one package claimed by two units (`WORKSPACE_ANCHOR_CLAIMED`), a unit left with no layer (`WORKSPACE_UNIT_PAYLOAD_EMPTY`) and a key none of an entry's ecosystems reads (`WORKSPACE_UNKNOWN_KEY`). The planner bumps a unit when its layers' digests move from the ledger, at the level its fragments, import edges, inline edges and the version locations of other units inside its payload give it; a group releases every member at one version, a level above `maxBump` is refused (`MAX_BUMP_EXCEEDED`, replacing the fixed rejection of `Changed` / `Removed`), locations that disagree are `UNIT_VERSION_MISMATCH`, and a candidate plan versions units `<final>-<id>.<k>` beside an untouched final entry. The ledger nests layers by ecosystem and anchor (`telo: { ".": … }`, `npm: { nodejs: … }`, `payload:`) and still reads the module ledger shape; fragments name `units:` and still read `modules:`; a changelog started under another heading becomes `# Changelog`. `release.modules` and `release.registry` are refused naming `release.units`: a module is now an entry listing `ecosystem: telo` with its `registry:`, an image module one listing `[telo, docker]`, and a module's npm and Cargo packages are found from its controller locators and `sources:` crates rather than fixed `nodejs/` and `rust/` subpaths.
### Fixed
* A crate's layer reads a `license-file` or `readme` its manifest names outside the crate from where it is, as `cargo package` does, instead of refusing it as missing.
* An npm layer digests the packed `package.json` with each dependency map in name order: pnpm writes the workspace ranges it resolves in the order its resolution finishes, so the same package packed twice could digest differently and be planned again.
* `apply` now moves a dependent crate's `version` requirement on a path dependency it bumps, keeping its operator, so a candidate of a crate others name with a requirement still resolves; and an apply that fails after it began stamping — a version file, a host hook, or the reading the ledger is recorded from — restores every file it wrote and records no ledger. A host's `check` gate now receives the plan the gate formed.
* On Windows, packing an npm package for its evidence starts the package manager through `cmd.exe`, every argument quoted: `npm`, `pnpm`, `yarn` and `bun` are `.cmd` shims there, which no spawn finds without a shell, so `telo-release status` and every command reading npm evidence failed to start the manager on Windows.
