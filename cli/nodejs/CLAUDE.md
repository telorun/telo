# CLI (Node) — package guide

Loaded when working under `cli/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. The release model this CLI drives (planner, ledger, workspace marker) is in `analyzer/nodejs/src/release/CLAUDE.md`; the artifact format it publishes in `kernel/nodejs/CLAUDE.md` § Layered module artifacts; the `requires:` mechanism in `analyzer/nodejs/CLAUDE.md`. The `telorun/node` kernel image is built from `cli/nodejs/Dockerfile`.

## Output seam

**Every CLI-owned write goes through the `Output` seam** (`src/output.ts`), never `console.*` and never a bare `process.stdout.write`. A global `-o, --output text|json` (default `text`) selects the encoding. **The stream split is the contract, and it is what the format rests on**: *stdout is the machine surface* — under `-o json` it carries the payload and nothing else, so `line()` (prose) goes silent there; *stderr is the human surface in **both** formats*, so `errLine()` always writes. Suppressing stderr under `json` was error swallowing: only the commands that separately collected their messages into a payload kept them, and every other failure reason vanished, leaving `{"ok":false}` with no cause. Keeping prose on stderr is also what npm, cargo and kubectl do, and it is one rule rather than a re-collection obligation on each new command.

**Two payload shapes, one serializer.** `emit()` writes a result **envelope** and is silent under `text`; `document()` writes a **bare document** and writes in *either* format, because the per-command `--json` flags (`cel`, `search`, `module versions|manifest|digest|resources|kinds`) predate `-o` and must keep working under the default. A document command's stdout is therefore *the document or empty* — it never mixes an error envelope in, because a CEL expression evaluating to `{"ok":false,…}` would be indistinguishable from a failure report; its errors are prose on stderr plus a non-zero exit.

**`telo run` is exempt from `-o json` entirely**, and the exemption is structural, not an oversight: the kernel runs in-process and `teeStdio` *copies* rather than redirects, so the app writes to these same two descriptors and **neither is the CLI's to claim**. An envelope appended after arbitrary app output is unparseable on either stream. The machine surface for a run is `--debug`, whose wire protocol is framed per event precisely because it shares a stream.

**Colour is decided per stream** (`Output.stdout` / `Output.stderr` palettes over `decideColor`), because diagnostics go to stderr while summaries go to stdout and one process-wide decision is wrong for whichever stream is redirected; stdout is never coloured under `json`, while stderr keeps its colour since it stays human-facing. **A payload write is followed by `process.exitCode`, never `process.exit()`** — on a pipe `write` is asynchronous and `exit` does not flush, so a large diagnostic set truncates into invalid JSON. `Output` takes its streams and env as constructor arguments so tests construct one over recorders (`installOutput` swaps the ambient instance) rather than spying on process globals. `yaml` is deliberately unimplemented; `-o` is an enum so it can gain the value without a second flag, and `parseOutputFormat` **throws** on an unrecognized one rather than degrading to text.

## Exit status

**0 the work was done, 1 it failed, 2 the invocation was refused before any work** (`src/exit-status.ts`, `cli/README.md` § Exit status) — what `cli/rust` already did. Every refusal by the argument parser is a 2: yargs' failure hook (`src/usage-refusal.ts`) prints the usage and the reason on stderr, sets the status and stops the parse. The hook sees a command handler's rejection too, with no message: that is the command's own failure, left to reject the parse with its status of 1. The output middleware runs after validation, so a value outside `--output`'s choices is a usage error rather than a throw from `parseOutputFormat`. A command refusing one of its own options before it starts (`telo runner`'s bind and port) uses the same constant.

## Runtime reach

**Runtime reach is derived, never declared.** Which kernels can host a kind follows from its `controllers:` PURL candidates: `pkg:cargo` → **both** kernels (Node's `napi-loader` builds the crate as a `.node` addon, the Rust kernel's `cargo_loader` as a cdylib), `pkg:npm` and `pkg:telo/local/js` / `napi` → Node only, `pkg:telo/local/dylib` → Rust only, `wasm` → no kernel today. **A kernel candidate** — `{ runtime: kernel, entry }`, the one a definition the runtime synthesizes carries (a need type's) — is hosted by exactly the kernels registering a controller under `entry`: Node's set is `BUILTIN_CONTROLLER_ENTRIES` (`@telorun/kernel`, the keys of the table its boot registers from, read rather than copied), Rust's a mirror kept in `classifyCandidate` beside the PURL one (empty today — that kernel instantiates no built-in kind and refuses need types). So a need type reports `{ runtimes: [nodejs], languages: [], portable: false }`: not portable, because its controller is the kernel's, and not blank, because the fact is derivable. Which documents declare a kind, and the declaration each yields, is the analyzer's `kindDeclarationOf`, never a test of `kind:`. A module declaring `native:` also reports the platforms and ABIs those entries cover (`runtime.native`), per module rather than per kind because no kind declares which native name it uses. **`telo module manifest --json` reports it** (`cli/nodejs/src/controller-runtime.ts`) and the hub stores what it is told — the PURL→kernel mapping is loader knowledge, and a second copy in a consumer would drift silently the day a loader lands. Three invariants: it is **per kind**, not per module (`console` has Rust controllers on two of four kinds, so a module boolean would lie — the roll-up is full/partial); a controller-less kind is **`portable`**, a flag rather than an enumeration of today's kernels, which would go stale when a third kernel ships; and **language is a separate axis from runtime**, left blank for `napi`/`dylib`/`wasm` whose source language the PURL cannot determine.

## `requires:` — CLI half

**CLI half** (Node by nature): `release/verify-requires.ts` (per module, `publish` preflight — a refuted range is fatal, an unpublished upper bound is fatal, an uninstallable edge warns) and `release/check-requires.ts` (workspace-wide, batched by shared edge so a stdlib declaring one or two lower bounds costs one or two runs, wired into `telo release check`). **A FORWARD-DECLARED lower bound is a third state** (`pending`, `unreleasedEdge`): adopting new syntax means declaring the release that will carry it, so on that commit the edge names a version npm does not have — one possible outcome, arriving as an `ETARGET` wrapped in install noise indistinguishable from being offline. So the registry is asked BEFORE any edge runs (`publishedTeloVersions`, memoized) and such an edge is never spawned. The latest published version is reported beside the bound, because that is the only signal against a TYPO above the latest (`>=0.790.0` beside `0.78.0` reads wrong; "could not run" does not). Informational at `telo release check`, **fatal at publish** — npm publishes before modules, so by then the floor exists, and a module landing at the registry with a floor no runtime satisfies is a version every consumer's `upgrade` refuses. An edge BELOW the latest that is nevertheless absent (yanked) stays "could not run": guessing why it is missing would be a rule with nothing behind it. An unreachable registry classifies nothing. `telo upgrade` selects the highest version whose range accepts this runtime, walking newest-first and stopping at the first satisfied one — and **reports what it held back**, or the pin is a silent ceiling and *"up to date"* becomes the new confusing report. It short-circuits when the newest published version is already the pin: there is no candidate to choose, so the question has no bearing and asking it would cost a fetch per import on the path that changes nothing (a pin the runtime cannot read is the LOAD gate's to report — `upgrade` moves pins forward, it does not walk anyone backwards).

## Publishing

Modules get their **own Version PR** (`module-release/main`, `chore(release): version modules`), opened on every push to main independently of whether npm changesets are pending — they used to ride the changesets PR whenever one existed, which made one review cover two ledgers, and a release routinely republishes sixty modules because a shared library reached their bundles. Its body is GENERATED from `telo release status -o json` captured **before** `apply` consumes the fragments (`scripts/module-release-pr-body.mjs`): declared changes first, unattributed republishes as a table, degrading in stated stages under GitHub's 65536-character body limit — an over-long body is rejected outright rather than truncated, so the PR would open with no body at all.

**Publish is where two of the invariants are enforced.** Pins are **authored and verified, never discovered**: `telo install` / `telo upgrade` write them, and the payload builder REFUSES a remote import carrying none (it used to be fetched best-effort, so one commit produced different bytes depending on network reachability, and an unresolvable import shipped silently unpinned — error swallowing this repo forbids). Existing pins are verified against the registry; a mismatch is fatal. An in-repo sibling's pin is derived from the sibling's **own locally-built published bytes**, in topological order, so a batch is plannable offline against post-bump versions the registry has never seen. Manifest re-serialization is **unconditional** — it used to depend on whether a pin happened to be written, so one commit serialized two ways.

**The payload is built by the kernel, not staged by a package manager.** `cli/nodejs/src/bundle/module-payload.ts` is the single builder both `telo publish` and `telo release` consume; it builds every bundled controller through the kernel's own `buildControllerBundle` (`source-bundle-builder.ts`, the analogue of the Rust `napi-loader`) rather than reading the gitignored `path=` artifact. Shipped bytes and digested bytes are the same bytes by construction, the edge graph gets its metafile from the same run, and the esbuild half of 47 per-module `build` scripts plus `build:bundles` are retired (the `tsc -p tsconfig.lib.json` type-check half stays). On the publish/release path the optional-esbuild fallthrough becomes a **hard failure** — digesting a stale bundle is the one outcome the design exists to prevent.

**A browser entry is built there too** (`bundle/browser-entries.ts`, over the kernel's `buildBrowserEntries`): every `exports.browser:` entry, one build per distinct `external` set, before the partition — because the files a build puts beside an entry (shared chunks, a stylesheet, the `<path>.siblings.json` sidecar) are part of its `browser` layer and only the build knows them, so `partitionLayers` takes them as `builtBeside`. An entry naming no `source` is refused. `telo package` builds a local module's entries through the same helper and writes them at their paths, sources left behind. The sidecar is `{ "files": [ { "path": "<module-relative POSIX path>" } ] }`, sorted by `path` and serialized one way, since it is inside the layer's integrity; its name is reserved, so both commands refuse a module whose manifest puts a file of its own at `<entry path>.siblings.json` (`assertSidecarNamesFree`, asked before anything is built).

**The index is written by the PAYLOAD BUILDER, before anything is pushed** (`ModulePayloadBuilder.buildPayload` → `Transport.layerIndex`), so `publishedManifest()` returns the bytes that ship. It used to be injected by the transport at push time, and that made the builder's manifest a document no registry holds — while a dependent's sibling pin is a hash of exactly that text, so **every module shipping a payload published a pin naming bytes nobody serves**, and 18 standard-library modules could not resolve their own dependencies at load. Nothing caught it: `payload-drift` compares layer digests, which injection does not move, and the ledger's `manifest` digest was pre-injection on both sides. What the fix requires is that a `blob` be knowable before its blob is pushed, so **layer framing is a pure function of the files** (`makeTarGz` pins every header field that is not the entry's name, contents, kind — regular, executable at mode `0o755`, or symbolic link — or link target, which is also reproducibility) and `publish` **verifies** each pushed blob against the index rather than rewriting it: the manifest may already be pinned, so a disagreement is fatal, not correctable. Framing stays the transport's (`layerIndex` is on `Transport`), since a `blob` digest covers framed bytes.

**Publish gates on the pin, not on a ledger.** A consumer's import pin is a hash of `telo.yaml` alone, so `telo publish` refuses whenever the pin of the `telo.yaml` it is about to push differs from the pin of the one already published at that `metadata.version` (`checkPublishedPin`, `cli/nodejs/src/bundle/payload-drift.ts`), under `--dry-run` too. Identical bytes pass, which is what makes a re-push (to change annotations, or to heal a failed push) legal. The published `telo.yaml` is read from the registry itself, never a cache; "not found" is the only registry answer that passes, and any other failure fails the publish. It used to compare payload layers only, which let a manifest-only change — a description, an import, a re-serialization — republish a version under a new pin, and never compared a manifest-only module (every application with no controllers of its own) at all: every consumer pinned to that version then failed verification. The per-layer comparison stays, but only to EXPLAIN a refusal — a bundle inlines its dependencies, so a shared-library fix or a lockfile bump moves a layer's `integrity` while touching nothing under the module's own directory, and naming that layer points the author at the cause; when no layer moved the refusal says the manifest itself changed. The remedy it names is a new `metadata.version` (`telo release status` / `apply` in a release workspace), never a re-push. **The drift question is answered on the module track only** — `telo release status`, whose plan moves `metadata.version` in the module Version PR, so a module whose bytes moved with no bump is a pending bump there. It used to be re-asked as a `--dry-run` pass in the npm publish script, which is the one place it could only misfire: see the publication split below.

**Staged files are digested from their pins, and only publish reads them.** The builder has two modes (`stagedFiles`): `pins`, the default every release command takes, turns a file a `sources:` entry stages into a pinned entry whose integrity line is the one its bytes would produce, and gives its layer a stand-in `blob` (the hex of the integrity digest) — so a fork's cold tree and the release job compute the same layer digests, and only the never-reconciled `manifest` digest sees the stand-in; `disk`, which `telo publish` takes, reads and verifies the staged bytes and frames them. The mode is the builder's, never inferred from what happens to be on disk: deciding per tree would make one commit's `manifest` digest depend on whether `telo release stage` had run. Publish never fetches — the publish job stages first, and only what it reads: the modules it pushes and their in-repo import closure (`telo release order -o json` carries each module's `imports`), since a dependent's pin is derived from its sibling's published bytes — and `sources:` is dropped in `transformManifest` beside `include:`, before any sibling pin hashes the text. The named-file rules publish applies (which files a source may stage — a `native:` path, a platform-qualified controller `path=`, an entry an `assets:` pattern selects, a notice — a native path also named as code, a staged entry nothing names) are the analyzer's (`module-named-files.ts`), shared with `telo check`; `bundle/staged-files.ts` is only their filesystem half. Every staged path joins the partition's input the way a notice does, so a staged asset lands in the `assets` layer with no `files:` entry. Under `pins` a `!module-path` claim counts a staged module file (the analyzer's `stagedModuleFiles`, the rule `telo check` applies) as present, and a directory claim expands to the staged files beneath it plus what is on disk; under `disk` only the disk answers, so `MODULE_PATH_NOT_FOUND` / `MODULE_PATH_EMPTY` still refuse at publish.

**A module root's `LICENSE` ships because it is there, not because `files:` names it** — the payload builder adds it to the partition's input the way it adds a source's notices, so it lands in `common`, and `telo package` copies it beside a local module's manifest. `metadata.license` names a license; without the text and the copyright line in the artifact, whoever redistributes a pulled module cannot satisfy a notice condition. Only the file at the module root counts: one in a parent directory is outside the module.

For the standard library, which releases through `telo release`, the gate is a backstop that should not fire. It does fire for an author publishing by hand outside a release workspace, which is who it now exists for. Registry publish is still gated on `metadata.version` movement (`scripts/publish-modules.mjs`), whose ordering now comes from `telo release order` rather than a regex over `imports:`.

**The npm release publishes the telo version line together.** `@telorun/cli` is one member of the changesets `fixed` group of the runtime packages (sdk, templating, analyzer, kernel, cli, ide-support, language-server), so a Version PR moves all of them to one version and `changeset publish` ships them at it — `@telorun/language-server@X`, the editor engine of telo `X`, beside `@telorun/cli@X`. The CLI carries no engine export of its own; editors fetch the engine package. The same Version PR's `version-packages` writes the line version into the Rust twins' `Cargo.toml` and `Cargo.lock` (`scripts/version-line.mjs`). `requires:` verification and the upper-bound existence check keep asking the registry about `@telorun/cli` — the same number as every other member by construction.

**Author annotations are a flag, not metadata.** `telo publish --annotation <key>=<value>` (repeatable; split at the first `=`; a reverse-domain key; a key given twice refused — `src/publish-annotations.ts`) writes the pair onto every OCI manifest the invocation pushes, beside the `org.opencontainers.image.*` keys the transport derives from `metadata`. A derived key is refused naming the `metadata` field to set, whether or not the manifest declares it, and the refused set is the transport's own projection table — the transport answers both `checkAuthoredAnnotations` (before anything is built or fetched) and `publishedAnnotations` (the complete set, which `--dry-run` prints and `-o json` reports per manifest). **The pushed set REPLACES the published one**: a republish writes derived keys plus exactly this invocation's pairs, never a merge, so an annotation dropped from the command line is dropped from the artifact. Annotations cross the transport seam as a neutral map (`PublishOptions.annotations`), and a transport that cannot write them refuses a publish carrying them rather than dropping them. `telo release` and `scripts/publish-modules.mjs` take no annotations — a release publishes what its manifests say.

**`telo publish -o json` names each module's outcome.** Beside the envelope's `published` / `failed` lists, `modules` carries one entry per manifest: on success the `version`, the `integrity` pin of the published `telo.yaml`, the pushed artifact's `digest` (the transport's `PublishResult.digest`, absent under `--dry-run`) and whether the version was already published `identical`; on failure a `code` from the closed set in `src/publish-failure.ts` with its `details`. **A code is decided where its cause is known** — the payload builder throws `PublishFailure("import_unpinned")`, pin verification `import_pin_mismatch` / `import_unreachable` — never inferred from a message further up, and anything no code names is `publish_failed`. Telo Cloud's publisher is the consumer: it runs `publish --skip-controllers -o json` over a tenant's checkout, which is why **that path must execute nothing the module supplies**. Bundling a controller parses its source and runs none of it, staged files are read and never built, and the `requires.telo` edge check starts `npx` in a neutral directory with an absolute manifest path, because `npx` reads the `.npmrc` of the directory it starts in and one beside the manifest would otherwise choose the registry `@telorun/cli` is installed from.

**A `Telo.Builtins` root publishes as the release rendered it** (`bundle/builtin-vocabulary-payload.ts`): no module analysis, payload builder, staging or `requires:` check runs; the archive is read by the analyzer's `readBuiltinVocabulary` and refused (`manifest_invalid`) for any problem, an existing `layers:` index, an `X+unreleased` version or no `LICENSE` beside it; its one layer is `common` holding that `LICENSE`, and the published `telo.yaml` is the file's bytes with the `layers:` block appended at the end of the root document — never re-serialized, so removing the block gives the archive back. The pin gate and the annotation projection run as for any module (`pushManifest`, the tail both share). The `publish-builtins` job of `.github/workflows/publish.yml` (`scripts/publish-builtins.mjs`) reconciles `<TELO_OCI_REGISTRY>/telo` on every push: each `@telorun/analyzer` version at or above its floor constant, published no earlier than the floor, whose tag is missing is published from that version's tarball (`src/builtin-vocabulary/`) with the checkout's CLI. `telo module manifest --json` reports such a root with `runtime: null` and `application: null`.

**Polyglot debt, publishing:** `telo publish` is part of the one `telo` surface and `cli/rust` has none, so it owes the command — including `--annotation` and the pin gate above.

**Publication is split by artifact, because the dependency runs npm → modules → images.** A module artifact is built by the workspace CLI, so the CLI ships first and modules follow. `pnpm run release` is **`changeset publish` and nothing else**; module manifests are pushed by `scripts/publish-modules.mjs` in its own workflow job, on every push to main (both its gates — version moved in this commit, version absent at the registry — are idempotent, so nothing is republished and a failed push heals on the next push). They were one script, which had the npm release decide module questions: it ran the payload-drift gate over already-published modules, and that gate demands module versions be moved BEFORE npm publishes — the inverse of the real order — so every release following a byte-changing change failed *after* `changeset publish` had shipped the packages and pushed the tags, where nothing could retry it. A second implementation of the release planner (`git diff` regexes, registry queries) also drifts silently from `telo release`, which owns those answers.

**A kernel image's existence is a function of what is on npm, not of a job's exit code.** `telorun/node:latest*` moved only when the changesets action reported `@telorun/cli` in `publishedPackages`, so *any* later failure in that run left every deployment pulling a kernel image releases behind, with nothing reporting it — and `publish-docker.yml` had no `workflow_dispatch`, so the only recovery was another release. The `context` job now also builds the release tag set when the workspace CLI version is **live on npm and has no `telorun/node:<v>-slim`** (probed with an anonymous registry token; a probe that cannot answer reports *present*, since a missed build heals next push while a false *missing* would re-tag `latest` from an arbitrary commit). `@telorun/sdk` is checked alongside the CLI because the Dockerfile's `--prod deploy` resolves it from npm and the two publish with no ordering guarantee. `workflow_dispatch` takes a `cli-version` for the by-hand case.

## `telo upgrade --pin-local` — a relative import back to its pin

A repository holding both modules and their consumers (examples, starters, apps, blueprints) imports a module by relative path while a change to it is unreleased; `--pin-local` rewrites such an import to `<destination>@<version>#<pin>` once the change has shipped (`src/release/local-import-pins.ts`). **The verdict is the release plan's, never a digest of its own**: a module the plan would bump is one whose published artifact is not the working copy, so its import stays relative with the plan's own reasons (`imports modules/sql` names the sibling that holds a dependent back), and comparing source files instead would be comparing bytes publish rewrites. The plan is the one `telo release status` builds (`src/release/workspace-plan.ts`, extracted so both callers share it), built at most once per workspace and only when an import actually names one of its modules. **The registry has the last word** — the ledger is committed before the artifact is pushed, so a version the plan calls settled may not exist yet, and the pin is read from the registry; a registry that cannot answer is an error, never a guess. Three things are left exactly as without the flag: a target that is no module of a release workspace, an image module, and a manifest inside the module it imports (that module's own test). **Only the manifests NAMED on the command line are repinned**: one reached through `--recursive` is some module's own manifest, whose relative imports are the edges its release is planned along. **The plan is only meaningful under the Node build** — measured on a tree where `telo release status` reports nothing to release, the same command run by bun from the TypeScript entry reports every module's payload as changed — so `scripts/upgrade-imports.mjs` takes the built CLI whenever it is given the flag. That script never applies the flag to a manifest under `tests/` or `__fixtures__/`, which import what they exercise by relative path on purpose. The `Sync imports` workflow runs it after every `Publish` and daily, and opens one rolling pull request (`imports/main`) with `TELO_BOT_TOKEN`, because a pull request opened with the default token starts no workflow and the PR's own checks are what judge the result.

## `telo install` — the tree an image boots from

**An install whose manifest does not load is a failed install.** Its last pass is the runtime's own `kernel.load` in `analyzeOnly` mode (baking the analysis stamp and the validator cache), and a refusal there exits 1 with the kernel's diagnostics. It used to be a warning — on the grounds that the runtime re-validates — and that is how an image whose embedded prompt was missing from the build context built green and failed on every container start: a build log's warning is one nobody reads, and the installed tree is what the image boots from.

## The standalone binary

`scripts/build-standalone.mjs` builds the single-file `telo` executable: the CLI bundled to one script by esbuild and injected into an official Node runtime as a Node single-executable application, with esbuild's own executable riding along as an embedded asset. `pnpm --filter @telorun/cli build:standalone` builds for the host; `--target <os>-<arch>[-musl]` downloads that target's runtime instead. Released by `.github/workflows/cli-standalone-release.yml` on the same gate the kernel image uses — `cli/nodejs/package.json`'s version moving on main — with `.github/scripts/package-standalone.mjs` wrapping each binary in the formats a platform installs from, and `install.sh` / `install.ps1` at the repo root installing the archive. **The advertised command is `curl -fsSL https://telo.sh/install.sh | sh`** (`irm https://telo.sh/install.ps1 | iex`): the product's most permanent line names the product, never a git host, an org, a repo name and a branch. `telo.sh` redirects those two paths to the scripts **at a release tag** — a redirect nobody sees, to bytes that cannot move under a user, since the installer and the asset names it builds are one contract and `main` moves without the release. The workflow's last job moves both Cloudflare redirect rules to the new tag once the release is published, finding each by its current target (no rule id is stored) and failing unless exactly one rule per script matches; it needs the `CLOUDFLARE_API_TOKEN` (zone-scoped, redirect rules edit) and `CLOUDFLARE_ZONE_ID` secrets. The site keeps copying both into `pages/static/` at build, so `telo.run/install.sh` stays a working mirror.

**The binaries are ASSETS OF THE PRODUCT'S RELEASE, not a release of their own.** `scripts/github-releases.mjs` creates `v<cli version>` on the same signal and owns its name and body; this workflow attaches files to that tag and sets neither.

**A `v<version>` release is never PUBLISHED without its installers.** It is created as a **draft**, and the standalone workflow promotes it only after every target has built and the packages have installed in containers with no Node.js. Two releases shipped assetless before this gate existed — the npm job created them, the binary build failed afterwards, and nothing connected the two. `releases/latest`, which the install scripts read, skips drafts, so a failed build now leaves the previous release standing rather than pointing users at an empty one, and the failure is visible as a stuck draft. Because both fire on one commit, either may arrive first, so the release script fills a body it finds empty rather than treating an existing release as "nothing to do" — otherwise which job won the race decided whether the release ever got a changelog. Assets are named in **Telo's own platform vocabulary** (`telo-<version>-linux-amd64-gnu.tar.gz`, `…-windows-arm64.zip`), the tokens `native:` entries and `telo install --platform` already use; native installers keep their own format's spelling (`telo_<v>_amd64.deb`), since that is the package manager's namespace.

**One command, whichever kernel is behind it.** `cli/rust` builds a binary called `telo` too, at the same version, and is not published while it hosts fewer controller formats than this one — 185 standard-library kinds ship as `pkg:telo/local/js` bundles, which only the Node kernel opens. When a build cannot host everything this one hosts, it is named for that restriction, never for the language it was written in: which kernel can host a kind is derived from its `controllers:` PURLs, so it is not a question to hand a user at download time.

**Seven targets, because those are the ones nodejs.org publishes a runtime for**: linux x64 glibc and musl, linux arm64 glibc, darwin x64 and arm64, win32 x64 and arm64. There is no linux arm64 musl runtime to inject into, so that binary cannot exist — a module may still ship a native file for the tuple, which the npm-installed CLI uses. **The musl binary is not self-contained**: the official musl runtime is dynamically linked against `libstdc++`, which a bare Alpine carries no more than it carries `libgcc_s`, so it fails to relocate until `apk add libstdc++` — which is why every check that runs it does that first, and why `install.sh` says so when the installed binary will not start.

**Three things the build decides that the bundle cannot ask at runtime.** Versions are baked (`__TELO_BAKED_VERSIONS__`, read by `distribution-versions.ts` here and `runtime-versions.ts` in the kernel) because a binary has no `package.json` — the CLI's own version read `unknown` before, and the cache keys were worse. `telo --version` prints neither: it prints the telo identity (`TELO_RUNTIME_VERSION` — `X`, or `X+unreleased` for a build made while `X` is pending), the string `Kernel.Starting` and the built-in vocabulary carry, and `cli/rust` prints the same, read from its embedded archive. `import.meta.url` is rewritten to the executable's own path, since the output is CommonJS. And esbuild's JavaScript API is inlined while its executable is an asset, unpacked to `<cache-root>/tools/` on first use by `src/standalone/standalone-runtime.ts` — a run that loads only published modules never unpacks it.

**There is no second code path.** `src/standalone/entry.ts` registers what the binary supplies and then imports the ordinary CLI — or, for a binary carrying an application started without `TELO_APP_CLI=1`, calls `telo run`'s own implementation on itself — so a command cannot work in one distribution and not the other. What the binary genuinely lacks is a package manager, so an npm-delivered controller fails there with the kernel's actionable message; `telo check` warns about it ahead of time (`src/controller-tool-probe.ts`, the probing half of the kernel's shared tool table).

## `telo package` — an application as one executable

`telo package <manifest> --out <file> [--platform os/arch[/libc]]` writes the released `telo` binary for that platform with the application's payload inside it: the manifest, every local file its graph reaches, and the warmed import closure. **The carrier is this CLI's own version** — this executable when it IS that binary, carries no application of its own and the platform is the host's, the release asset otherwise (verified against the release's `checksums.txt`, cached under the user cache). **The asset's SHAPE is per platform and is part of the target table**, not derived at the download: Windows publishes a `.zip` holding `telo.exe` at its root (what `Compress-Archive` writes and `Expand-Archive` opens on a bare machine), every other platform a `.tar.gz` whose binary sits inside `telo-<version>-<target>/`. Assuming one shape asked the release for an asset that does not exist and reported a 404 about a Windows build that is published. The zip half is `package/zip.ts` — central directory, stored or deflated, no zip64 — because shelling out to `unzip` is not available where this runs: a single-file executable on a machine that carries no such tool. There is no `--telo-version` and no flag naming a carrier file: a carrier and the CLI inside it are one version by construction, and a flag would be the seam where they stop being — so packaging from a source checkout goes through that checkout's own standalone build, the way `telo runner` supervises the running executable. `cli/rust` owes this command, as it owes `telo runner`.

**Only a RELEASED telo may download a carrier** (`planCarrier` → `assertMayDownloadCarrier`, decided before the payload is built since it depends on nothing the build produces). A version number is not an identity for an unreleased tree — a working copy and the release of the same number are different code — so a downloaded carrier would put the app inside the RELEASE while the command claims it carries the telo that built it, and every local change under test would be silently absent. What a distribution IS is answered rather than inferred: a binary carries `build: "release" | "local"` baked by the release workflow (`TELO_RELEASE_BUILD`), and an npm package still naming `workspace:` dependencies in its own manifest is a checkout, since publishing rewrites those. A working copy may therefore package only what it can BE the carrier for — itself, built — and the refusal's remedy differs by where the reader stands, since telling a binary to build the binary it already is would be advice it has taken. This is the guard; `carrierReadsPayloads` (scanning a carrier for the reader's own magic) is the backstop under it, for the residue where a released CLI's own published binary predates the reader — which is how the feature's first cross-repo packaging produced a file that ran the CLI.

**The platform is spelled `os/arch[/libc]`, as `telo install` spells it.** `linux-amd64-gnu` is the release ASSET's name, a filename in the download namespace; two spellings of one concept on one CLI makes a user translate between them to answer one question. The **abi is never asked for and never guessed**: it is the carrier's, stated once in `src/carrier-runtime.ts` (`CARRIER_NODE_VERSION` / `CARRIER_NODE_ABI`) and read by both halves — the build injects that runtime and asserts the pair wherever it can see it, and the command warms native layers for that abi. Reading `process.versions.modules` instead was wrong precisely on the path that legitimately downloads a carrier: an npm-installed CLI has no baked values, so an operator running Node 20 packaged an app whose layers no carrier could open.

**Placement is per executable format, because one of the three refuses trailing bytes.** ELF and PE take the payload appended, followed by a 52-byte trailer (`version`, `length`, sha256, the magic `TELOAPP1`) — no absolute offset, so one reader serves both placements. Mach-O takes it in a `TELO_APP` segment, injected with the same `postject` the standalone build drives (hence a runtime dependency now) with the ad-hoc signature stripped and restored around it: data after `__LINKEDIT` is what "main executable failed strict validation" means, and an unsigned arm64 binary does not launch. **Packaging a darwin platform therefore requires a macOS host**, refused elsewhere rather than writing a file that cannot run. The reader tries the tail first (one 52-byte read every `telo` startup pays) and walks Mach-O load commands second; the payload is always checked against the trailer's digest, because a magic can occur inside a 140 MB binary's own data.

**Every file the manifest NAMES must be there**, or packaging refuses naming the module, the path and the syntax that claimed it. Skipping a missing one silently is the failure class the layer rule closes, reopened on the local half: an unbuilt controller, an unstaged `native:` entry or a missing `!include-text` would leave a payload that is quietly incomplete and fails on first boot, on someone else's machine. **The payload's layout is anchored at the ENTRY's directory**, with every module placed at its path relative to it and the whole layout pushed down by as many anonymous `_` levels as the deepest `..` needs. Taking the deepest common directory preserved the offsets too, but the segments above the topmost module are the builder's own directory names — so the payload disclosed where it was built and the same application packaged from two checkouts produced different bytes, losing the digest-keyed unpack reuse. **A downloaded carrier is verified or refused**: continuing past a missing `checksums.txt` would bake an unverified network-fetched executable into someone's product, and `sha256sum`'s binary-mode `*name` spelling counts as listed.

**Three rules turn a best-effort cache into a complete one**, all of them because a packaged app has no lazy path and does not run where it was built:

- **A layer that did not land is a refusal for a NAMED target** (`warmModuleLayers` returns `gaps`, `describeGaps` renders them, the remedy is the caller's since `telo package` accepts no `--abi`). The two skip classes — a failed fetch, and a layer constraining an axis the target leaves undetermined — were warnings on the grounds that `run` fetches lazily; that is false for a baked image and for a payload, where the warmed tree is the only cache. **For the host it stays a warning**, and `parsePlatformTarget` keeps the host's abi when no `--platform` is given: an install for this machine is an optimization over a run that can still fetch, and discarding an abi already in hand made a bare install unable to warm the layer its own runtime opens.
- **A local module is carried BUILT.** Nothing warms a module reached by a relative `source:` — including the application's own `Telo.Definition`s — so its controller and every `exports.code:` entry point are built through the same builder publish and release share, written at the `path=` the manifest names, and its `sources:` entries are staged for the platform. The TypeScript sources are left behind, and that absence is what makes the property self-enforcing: the loader's dev branch fires only when a `local_path` source is on disk, so the prebuilt file is what loads and the embedded esbuild is never unpacked. Not by minting artifacts for local modules — a layered artifact is addressed by a pinned ref and verified against it, and a module no registry holds has neither.
- **Portability is derived from the carrier, not listed** (`package/portability.ts`): the carrier's kernel must open the candidate's format, and the candidate must need no external program on the target (the kernel's own tool table). A kind passes on one satisfying candidate; a closure with an npm-delivered or crate-built kind and nothing else is refused naming the kind, the candidate and which predicate failed. The day `cli/rust` is a carrier the same closure gets the opposite verdict with no edit here. **Judged over the kinds something INSTANTIATES**, since the kernel resolves a controller per instantiated kind and skips the rest — otherwise importing a module that happens to declare one crate-built kind refuses a packaging of an app that never uses it. The used set is collected from every `kind` string at any depth and matched on the suffix alone: over-inclusive on purpose, because judging an unused kind costs a refusal the author can act on while missing a used one ships an app that cannot boot.

**The analysis verdict is keyed by the payload.** The stamp is filed under a hash of the ENTRY URL and signed over each file's SOURCE URL — both absolute paths on the building machine — so a payload unpacked at a digest-keyed path misses on every start, silently, since a miss is the designed quiet recovery. `kernel.load({ analysisKey })` takes the payload's own digest over its file set instead (`cache/analysis`, `cache/validators` and `cache/yaml-parses` excluded from it: the stamp cannot name itself, and a validator or a parse is a pure function of a schema or text the key covers). Verified by execution — with the payload's stamp a run writes nothing; with the signature corrupted it re-validates and says so.

**The contract is written down** — `kernel/specs/packaged-application.md`: the trailer and the Mach-O segment, the payload index and the analysis key, `TELO_APP_CLI`, `TELO_APP_DIR`, the retired `TELO_APP_INFO`, and the `./orders <args>` identity.

**A packaged executable is a manifest source.** Every command that takes a manifest resolves its argument through ONE resolver (`src/manifest-input.ts`): a regular file whose trailer or segment says it carries a payload is unpacked (`src/package/app-unpack.ts`) into `<cache root>/apps/<name>-<digest>` — the directory a run of it uses, written beside it and renamed into place with `.telo-app-ready` last, held by `live/<pid>` — and the command loads that tree's entry against the payload's `cache/`, the analysis keyed by the index's `analysisKey`. `run` reaches it through `resolveRunInput`, `check` / `cel functions` and `describe` / `needs report` / `env template` (`src/analyzed-graph.ts`) through `cacheTargetFor(input)`. Nothing the payload carries is executed by reading it, so `telo describe ./orders` and `telo describe <unpacked entry>` print the same bytes. **Only a run reclaims the app's other digests**, keeping any tree a live process holds; deletion is safe because a reclaimed tree comes back out of the binary that owns it, and a command that only reads a binary says nothing about which build is deployed. **The payload's `cache/` is a SEALED root** (`ManifestInput.cacheSealed`, carried onto `CacheTarget.sealed`): `check` / `cel functions` / `describe` / `needs report` / `env template` load it through a session of its own (`openSession` routes a sealed target to one and refuses it beside any other target), whose loader serves every scheme the cache maps from that root alone, revalidates no tag and so drops nothing, and `check` writes no cache into it; a module it lacks falls through to the transports. The freshness pass exists because a working directory's cache can go stale under a moved tag — a payload cannot, and revalidating it deleted cached manifests out of the tree every start of the binary shares and sent an offline binary to the network. `check ./other ./orders` therefore judges `./orders` against its payload's copy even where `./other`'s cache holds the same tag. A run reads the same root (`resolveRunInput`) and is the one command that may add to it. `TELO_CACHE_DIR` is overridden rather than honoured — the payload IS the cache — and `TELO_APP_DIR` relocates the unpack root, which is what a read-only container needs; with nowhere writable the command refuses naming it. **Env files are read from the WORKING DIRECTORY** (`PackagedInput.envAnchor` → `RunArgv.envAnchor`), because the entry manifest sits at a digest-keyed path no operator should have to find; `.env*` never travels in a payload. The same anchor places `--debug`'s `.telo.debug.jsonl`, `env template --write`'s files and the answers a run asks for at the terminal and offers to save. `run --watch` on a binary re-resolves each cycle and watches the binary itself — its unpacked tree never changes.

**`TELO_APP_CLI=1` turns a packaged binary into the plain CLI for one start; the application start IS a run of itself.** `src/app-cli-switch.ts` is a side-effecting module imported first by both entry points (`cli.ts` after the colour bridge, `standalone/entry.ts` before anything): it reads the variable, **deletes it from `process.env` whatever it holds** — so no kernel, controller or child sees it, in every distribution, payload or not — and keeps the verdict. `1` is the CLI, unset or empty the application, anything else refused before anything runs, naming the variable and `1` — a refusal of the invocation, read before any manifest, so it exits 2 in every distribution, `cli/rust` included (`EXIT_REFUSED`). On a telo with no payload it does nothing else. `standalone/entry.ts` asks `carriesPayload(process.execPath)` (the trailer alone, not the payload) and, for the application, calls `run({ path: process.execPath, applicationArgs: hideBin(argv) })` — so `./orders <args>` is `TELO_APP_CLI=1 ./orders run ./orders <args>` by construction, with the same unpack directory, cache, analysis key, env anchor and exit code. **`TELO_APP_INFO` is retired**: the application start refuses while it is set (exit 2, as above) and names `TELO_APP_CLI=1 <binary> package inspect <binary>`, because a script that set it expects the index and must not start the service instead; with `TELO_APP_CLI=1` the binary is the plain CLI and ignores it. **The self-spawn seam re-adds the switch**: `selfInvocation()` returns `env: { TELO_APP_CLI: "1" }` when the running executable carries a payload, and `spawnApp` sets it over the session's env — a release binary `telo-supply.ts` downloads carries none. **An executable carrying a payload is never `telo package`'s own carrier** (`planCarrier`): a release falls back to the release asset, a local build refuses saying it is the carrier for no platform. There is no `TELO_OPTIONS` and no per-option variable.

## `telo run` — where the CLI's arguments end

**Every token after the manifest path is the application's**: `telo run [options] <path> [arguments]`, the rule every interpreter follows (`node [options] app.js [args]`) and what a packaged application already does. The kernel reads them against the root Application's `arg:` bindings (`kernel/specs/application-arguments.md`). **Position decides, never a list of the CLI's flags**: stripping known telo flags from anywhere after the path meant an application could not declare `--verbose` or `--watch` for itself, and every flag the CLI gained later would silently start taking one away from an existing application. The split runs before yargs (`src/run-invocation.ts`), because yargs cannot stop at a positional once commands are registered (`halt-at-non-option` stops at the command name); a first positional naming no top-level command is the default command's manifest, which is why the commands are registered through one name-keyed table in `cli.ts`. **Which options consume the next token is read off the same tables yargs registers** (`GLOBAL_OPTIONS`, `RUN_OPTIONS`): a string or number option with `requiresArg` or `choices` always does, and one without either has an OPTIONAL value that must declare the shape of that value (`RUN_OPTIONAL_VALUE_SHAPES`) or the split throws — a second list kept beside yargs would take the manifest as the value of the next valued option someone adds. `--inspect` is the one optional-valued option: before the path it reads the next token only when it has the shape of a port, so a bare host is `--inspect=<host>`. `telo run <path> --help` prints the APPLICATION's usage (`Kernel.applicationHelp`), since `--help` after the path is the application's; `telo run --help` stays the CLI's. Every spawn in the repo that runs telo (the runners, the hub image) puts its telo flags before the path — which an older CLI parses identically, so a runner and a kernel image can move in either order.

## `telo runner`

**The CLI hosts a runner, and the substrate it owns is this binary.** `telo runner` serves the backend-neutral `/v1` session contract (`@telorun/runner-core`) over a local-process backend: each application in a session is a `telo run --watch --inspect` of **the currently-running executable**, never a `telo` resolved from `PATH`. A single-file executable IS the command; an npm install re-enters through `process.argv[1]`. A packaged binary run as `TELO_APP_CLI=1 ./orders runner` hands its children `TELO_APP_CLI=1` (`SelfInvocation.env`), since every telo strips the variable at start and the child would otherwise be the application.

**An application that names another telo version runs on that release's own binary** (`src/runner/telo-supply.ts`). The runner's own identity — `X`, or `X+unreleased` for a build made while `X` is pending, the same string the kernel reports on `Kernel.Starting` — runs as this executable; any other version is the release asset for this platform, fetched, verified against the release's `checksums.txt` and cached by the fetch `telo package` uses for a carrier (`src/release-binary.ts`). **What is known without the network is refused before a session exists; the download happens inside the session's start.** Another build's unreleased identity, which no release can stand in for, and a platform no binary is published for, are `400 telo_version_unavailable`. A release this machine does not hold yet is fetched by `start`, reported as a progress event on the session's stream, and a fetch that fails is that session's failed start with the reason for the user to read: no release or no binary for the platform (HTTP 404), the host unreachable or failing (its status), a missing or non-matching checksum, no writable cache directory. Nothing is left behind a start that could not get its telo, and two applications started together on a version not yet held share one download. **A cached binary is rehashed against the digest recorded when it was written, which catches a truncated or damaged file and nothing more**: the digest sits beside the binary in the same user-writable directory, so it is corruption detection, not protection from someone who can write there. Supervising another version is what the container runners already do with a kernel image and rests on the same rule: every flag the runner passes sits before the manifest path, which every release reads the same way. Unlike a carrier, a downloaded telo here is asked for by exactly its version, so a working copy may fetch one.

Three differences from the container runners, each **advertised rather than hidden**, because a capability a client cannot read is a surprise at run time:

- **`io: ["streams"]` only.** Nothing in the repo carries a pty library and a native one cannot ride inside the single-file executable. An explicit `io: "tty"` is refused (`400 io_unsupported`) rather than downgraded — `isatty()` is observable to the application.
- **No isolation.** The workload inherits this process's environment (a local run's whole point is the machine it runs on) and its privileges. Hence loopback by default (`--host` anything else is refused without `--allow-remote`) and **no browser origin by default**: `*` is right for a runner an operator deployed, and wrong here, because every page the user visits reaches `127.0.0.1` from their browser and a cross-origin `POST /v1/sessions` that `*` waves through runs arbitrary code as this user. `--allow-origin` names one; the editor passes its own webview's. `RUNNER_CORS_ORIGINS` still wins, and core refuses an unnamed origin server-side rather than trusting the browser to (the byte channel already did, with `4403`).
- **No session config**, and that is enforced, not only advertised: a request carrying one is `400 invalid_config`. A closed schema on `/v1/capabilities` with nothing behind it is the half-kept invariant the contract change exists to remove. The telo version an application runs on is not config: it is the contract's own field, advertised as `features.teloVersions`.
- **Ports are bound, not published.** A port that appears on reload is reachable as soon as something binds it, which is the case a host-publishing docker session has to refuse. A port two apps in one session both declare is still reported as rejected.

**Session workspaces are private and reclaimable.** They hold the user's source, so the state root and every directory under it are `0700` (chmod'ed, since `mkdir`'s mode is masked by the umask), and each runner owns a subdirectory named by its PID. A runner that is SIGKILLed cannot clean up, so the next one sweeps the PID directories whose process is gone — a question with an answer, unlike a timestamp heuristic that eventually deletes a live session's files.

**Child-process discipline replaces container labels.** Each app runs in its own process group (`detached` on POSIX, `taskkill /T` on Windows), a stop kills the group, and the command's SIGTERM handler stops every live session before the process exits. A leaked `telo run --watch` holding a port after the editor quits is the failure that discipline exists to prevent.

**The web server is loaded when the command runs, not when the CLI starts.** `commands/runner.ts` registers with yargs statically (so `--help` lists it) and `await import()`s `@telorun/runner-core` inside the handler: fastify, pino and ws are ~70ms of a ~270ms startup, and no other command needs them. This is the one place the repo's static-import convention is deliberately not followed, and the reason is the hot path every `telo check` takes.

**`telo runner` is NOT exempt from the `Output` seam** the way `telo run` is: workload bytes travel the `/v1` byte channel, so the runner's own stdout and stderr are genuinely the CLI's. It emits its address as the command's result (`-o json`) and passes stderr to runner-core as the server's `logStream`, because pino's default destination is stdout.

**Studio ships this binary** and supervises `telo runner` on loopback (`apps/studio/scripts/stage-cli-sidecar.mjs` builds it per Rust target triple), so the standalone build now has a second consumer: a break in `telo runner` is a desktop editor that cannot run anything.

**Polyglot debt, application arguments:** `kernel/specs/application-arguments.md` is not implemented by the Rust half — `kernel/rust` refuses a manifest declaring Application `variables:` / `ports:` at all, and `cli/rust` accepts no token after the manifest path. Both are consistent refusals rather than silent divergence, and both are owed — §4.1, asking at the terminal for a missing input and `--no-input`, included.

**Polyglot debt:** `telo runner` is part of the one `telo` surface — running an application on a named release included — so `cli/rust` owes it and `packages/runner-core` owes a Rust twin under the one-for-one layout rule. Unlike the retired editor-side runner, this is a second implementation of a WRITTEN contract — the case the mirroring rule exists to cover — rather than a second implementation of an unspecified concept.

## `telo builtins` — the built-in vocabulary of this telo

`telo builtins [<name>...]` prints the `Telo.Builtins` archive this CLI was built with (`kernel/specs/builtin-vocabulary.md`): the bytes `@telorun/analyzer` exports as `BUILTIN_VOCABULARY_ARCHIVE`, written with `raw()`, or under `-o json` as one JSON string through `document()`. Names select entries through the analyzer's `selectBuiltins` — a kind with or without `Telo.`, a fragment, a value type, a zone attribute or a format — joined by `---` in argument order; a name selecting nothing writes the names there are to stderr and exits 1. Nothing is rendered at runtime, and `cli/rust` embeds the same file (`include_str!`, its `build.rs` refusing a build without it and naming the commands that render it) and prints through `cli/rust/src/output.rs`, the twin of this seam's document/error split alone. Another release's vocabulary is `telo module manifest oci://ghcr.io/telorun/telo@<version>`.

## `telo needs report` — what an application reads from the environment

`telo needs report <manifest>` prints, with nothing booted, the need table's `environment` list — the same list the kernel reads the environment against, so the report and the load cannot name different variables. It loads the graph through the check session (`src/load-need-table.ts`, shared with `telo env template`), analyzes it into a fresh `AnalysisRegistry` and resolves the table over the WHOLE graph (`needGraphFromLoadedGraph` + `needGraphScopeOf`), so every refusal the kernel would raise refuses the report too: an application the kernel would refuse has no report — its refusals go to stderr, stdout stays empty, exit 1. Under `-o json` the document is written with `document()` (`reportVersion: 1`; `src/needs-report.ts` builds it, each entry carrying the need's `version` range or `null` and its `features`); in text, one block per need. A module location (`declaredBy`, `type.module`) is the requested location with no `@<version>` / `#<pin>`, or a filesystem module's path relative to the root's directory, prefixed `./`, a `telo.yaml` named by its directory. `report` is the only `telo needs` verb.

## `telo describe` — what a module does

`telo describe <manifest>` renders the analysis's outline (`ManifestAnalysis.outline`, `analyzer/nodejs/CLAUDE.md`) and nothing else: it loads and analyzes the graph exactly as `telo check` does (`src/analyzed-graph.ts`, shared with `telo needs report` / `telo env template`), finds the entry's module doc in the flattened set by its source — the root Studio's module graph is built from — and asks the analysis for the outline over the registry's `moduleGraphDeps` with `{ root, entryModule }`. A Library is described as an Application is. A manifest with an error diagnostic has no outline — the `telo needs report` posture: the errors on stderr, stdout empty, exit 1. Under `-o json` the bare `outlineVersion: 1` document goes through `document()`; in text `src/outline-text.ts` renders it from the document alone — the inputs with the fields reading each, then the boot targets (the roots no boot target names under `Started`, a Library's under `Exports`), each resource expanded where it is first reached and named `(see above)` everywhere after, an entry point's `catches` ladder beneath its edge, and `Unreached`. The text labels an entry by its matcher values as `key=value` — never by a kind or a field it knows — and prints every value through the analyzer's `readWrittenValue`, a literal mapping as `{k: v}`, and every string inside a list or a mapping quoted, so a literal string can never read as an expression or a mapping.

**Polyglot debt:** `cli/rust` has no `telo describe`, and `analyzer/rust` builds no outline (it owes a runner of `analyzer/outline-conformance/`). `cli/rust` reads `TELO_APP_CLI` (`src/app_cli_switch.rs`: stripped first in `main`, a value other than `1`, empty or unset refused) but takes no packaged executable as a manifest source, and when it becomes a carrier it owes the application dispatch — `<binary> <args>` as `run <binary> <args>` — and the `TELO_APP_INFO` refusal (`kernel/specs/packaged-application.md` §4–§6).

## `telo env template` — the environment files of an application

`telo env template <manifest> [--write]` writes every environment variable the application reads — its `env:`-bound `variables:` / `secrets:` / `ports:` entries (`readApplicationContract`) and every field of the needs report — as env-file lines (`src/env-template.ts`, `src/commands/env.ts`), one per variable, grouped (`variables`, `ports`, `secrets`, `needs`), with a trailing comment carrying only what the line does not show — `required`, the entry's description, a need field's path — which the reader drops once the line is uncommented. **The split is by whether a value may be committed**: every sensitive input (the analyzer's `sensitiveEnvironmentInputs` — a secret, a need field the table marks sensitive) goes to the LAST sensitive entry of the workspace's `env.files`, the rest to the last entry that is not (`envFileDestination`; `.env.local` and `.env` by default, the defaults too for a manifest that is a URL); a kind the template has values for and the workspace has no file for refuses, printing as well as `--write`, naming what to declare. **Every line is written commented out**, and that is the design rather than caution: the kernel reads `NAME=` as the empty string, which satisfies a required string, and an uncommented default would freeze today's default against a later edit of the manifest, since a set variable beats `default:`. So the template changes nothing about a run until a line is uncommented; a secret's default is never written. A value is spelled by the analyzer's `spellEnvFileValue`, so the reader every run uses gives it back unchanged (bare, then single-, backtick- or double-quoted; a value no spelling reproduces — a line break, all three quotes — is noted and left empty). `--write` appends to the files beside the manifest only the variables a file does not already mention, set or commented (that rule is the CLI's), through the analyzer's `appendEnvFileLines`, and never rewrites a line; it warns when a sensitive file it wrote is not git-ignored inside a repository. Printing writes both files labelled (`raw()`), or `{ files: [{ name, text }] }` under `-o json`; `--write` emits `{ ok, files: [{ path, created, added }] }`.

## `telo run` — the env files

**The walk, the marker's `env:` block, the precedence, the env-file format and the sensitive mark are the analyzer's** (`resolveWorkspaceEnv`, `src/workspace-env/` there), the one answer Studio also uses; `src/env-files.ts` is the Node half — the start directory (realpathed, a manifest's directory or the one named), the one read every file goes through, and native ↔ `/`-separated paths. The CLI no longer depends on `dotenv`. `run.ts` applies the values to `process.env` where the real environment has none and keeps the resolution and the applied keys from process start; after every successful `kernel.load` (once per watch reload, never on a failed load) it prints `[env] <secret|sensitive need field> X is set in ./<file>, which env.files does not mark sensitive — move it to a sensitive file` for every sensitive input whose applied value came from a file without the mark (`sensitiveValueFindings`; the sentence is the analyzer's, the path rendered relative to the working directory). The run proceeds. Under bun the runtime itself loads the working directory's `.env*` files before the CLI starts, so a value there is not one the walk applies. **Polyglot debt:** `cli/rust` reads no env files, and `analyzer/rust` reads no `env:` block.

## `telo run` — asking for a missing input

`run.ts` installs a kernel `inputResolver` only when stdin and stderr are both TTYs and `--no-input` is absent; every runner backend passes `--no-input`. `application-input-prompt.ts` asks one entry at a time on stderr, reads exactly one line and unshifts the rest so the app's own stdin is intact, enters raw mode only for a hidden (sensitive) entry, and re-raises Ctrl-C as SIGINT. `application-input-session.ts` keeps answers for the session keyed by entry identity (a watch reload asks only for what is new or refused), offers once to save them through the analyzer's `envFileDestination` / `appendEnvFileValue`, and builds the hint a missing-values refusal ends with when nothing could ask. The file reads and git-ignore check it shares with `env template --write` live in `env-file-writes.ts`.

## `telo changed` — selecting what a change reaches

`telo changed <globs..> --base <ref>` expands Telo-glob patterns (resolved against the working directory, `!` excludes) over the repository's files — `git ls-files` tracked plus untracked, minus `.gitignore` — and lists the matched files a change since the ref reaches: one per line, or `{ base, diffed, affected, unaffected }` under `-o json`. It answers per FILE, because its consumers select work — the module test manifests a pull request can break, or an expensive job (the live-model suites in `.github/workflows/e2e.yml`) gated on its entry point by an empty `affected` list.

**What a file depends on follows from what it is.** A `telo.yaml` owns its directory; any other Telo manifest owns only itself and the `__fixtures__/` beside it, because anchoring the directory of a manifest that owns nothing made `examples/test-suite-live.yaml` claim every example; any other file owns itself. Both kinds of manifest add everything they NAME: their `include:` partials, the files their `!include-*` / `!module-path` tags claim, every other Telo manifest a relative path in them names (an `Assert.Manifest` / `App.Instance` `source:` runs one without importing it — the one generic signal for that edge is a relative path that resolves to a module doc), and their **relative** `imports:` closure — the edges `telo release` propagates a bump along, read through the same `importSourceRefs` / `resolveSiblingManifest` pair the payload builder uses, stopping at the manifest text so nothing is built. A pinned `oci://` import is not followed: its source cannot reach this diff until it is published and re-pinned. **The closure also follows the `workspace:` `dependencies` of the `package.json` nearest each controller / `exports.code` `local_path` and each `exports.browser` entry's `source`**, transitively: a bundle — a controller's, a library's or a browser entry's — inlines those packages and no manifest edge names them, so a change to a shared TypeScript package would otherwise reach nothing. A `workspace:` dependency naming no package in the repository is an error, not a skipped edge. **Not followed: a `pkg:cargo` controller's Cargo path dependencies** — the crates they reach live under `sdk/` and `kernel/`, whose changes already run everything in CI, so the gap is stated rather than closed. Each file is parsed once per invocation however many manifests name it, which keeps the whole repository's test set near 6s.

**Everything is spelled relative to the REPOSITORY ROOT and anchored there** — `git diff --name-only` reports root-relative paths wherever it runs, and a slash-free glob floats, so an unanchored `package.json` would match every package's. **The exit code carries only failure**: 0 is an answer, empty or not, so a gate never confuses "nothing affected" with a crash; it skips only on an explicit empty `affected`. **When the diff cannot be taken** (no merge base, base ref not fetched) every matched file is reported affected, with a warning on stderr — an answer that skips work must be one the diff gave. Outside a git repository the command fails.
