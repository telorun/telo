# Changelog

## 0.4.0 - 2026-10-10
### Added
* Breaking: FindNodes, FindRelationships and Traverse page by opaque cursor. They take 'limit' (1 to 1000, default 100) and 'cursor' and return 'next' only when more exist; 'offset' is removed from their inputs with no migration, and a call naming no limit now returns at most 100 items. A cursor is bound to the operation kind, the store's declared name, the type's declared name (a traversal's path and start key), the endpoint filters and the filter, so GRAPH_CURSOR_INVALID is thrown for a malformed cursor or one issued for another operation, store, type or filter; a caller that receives it restarts the listing. The store interface changes with it: the page argument is { limit, after }, list results are found with { items, next }, and a tail the backend cannot read as one it wrote is the outcome cursorInvalid, returned before any statement is issued. A tail it can read is a position with the standing of a key input: it reaches a statement only as a bound value, and a value the engine refuses for the key's type fails the call as that value in 'key' would. In graph-sql a find seeks to its cursor through the key index and resumes after a key of any type an operation returns - text, numbers, booleans, bytes, lists and maps alike - a traversal page costs at most one walk of its reach, a node type's properties exclude its table's internal columns, and the docs name the indexes a relationship table should declare and the limit on key types: a key or endpoint column must be a type the engine returns as its table projects it, which on PostgreSQL excludes date, timestamp, timestamptz, interval, bigint and numeric today. A DeleteNode through a layered store cascades nothing, and the operations page now says so. graph now requires telo 0.108.0 or newer: a tail is written in the typed-frame encoding whose generation exports @telorun/sdk first publishes in that release, and an older runtime fails when the controllers load. graph-sql keeps its own floor and takes this one through its import of graph.
* Node and relationship values may carry origin, the name of the layer a value was resolved from: an optional string on the output of all twelve operations and on the values of the @telorun/graph store interface. A layered store sets it on every value; a plain backend never does, and the member is then absent.
* The code library @telorun/graph exports what a module adding a listing operation over a Graph.Store needs, so it pages through the graph's own cursor instead of building one - GraphListing (binds a cursor to the listing's subject, yields the page for the store, and raises GRAPH_CURSOR_INVALID), boundName and declaredName, quoteKey, and assertNodeListed and assertRelationshipListed, the creation twins of GRAPH_TYPE_NOT_IN_STORE - and what a backend reads its inputs and writes its tail with: filterOperands, every comparison a where holds as operator, property and value with an unknown operator refused, and encodeKeyTail and decodeKeyTail, the key values of a listing's last item as tail text. A tail carries each key in the value domain's own one-to-one encoding, so a listing resumes after any key an operation returns; text that is not such a tail, of another arity or of an encoding generation the runtime does not read yields no value, and a key outside the value domain is refused with ERR_TYPED_FRAME_UNENCODABLE. The envelope's encoding, version and digest stay private. No operation, kind or cursor changes.

### Added
