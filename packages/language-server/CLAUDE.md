# Language server — package guide

Loaded when working under `packages/language-server/`. Repo-wide rules live in the root `CLAUDE.md`; the protocol this package implements is specified in `packages/editor-protocol/README.md`; every answer it gives is ide-support's and the analyzer's (`packages/ide-support/CLAUDE.md`, `analyzer/nodejs/CLAUDE.md`).

## What it is

`@telorun/language-server` is telo's **engine**: every Telo diagnostic and editor feature of ONE telo version, served over LSP from `serve(port)`. Telo `X` publishes `@telorun/language-server@X` — the package is on the telo version line, so its version is the surface generation it implements. `initialize` reports the engine's **identity** as `serverInfo: { name: "telo", version }`: `X` for a release build, `X+unreleased` for a build made while a changeset of the line is still pending (a development checkout, a main-branch studio deployment) — it implements `X` but is not the published `X`, and editors tell engines apart by the whole identity. The identity is generated into the untracked `src/engine-version.ts` by `scripts/generate-telo-version.mjs` (run by the root `prepare` and this package's own `prepare`). **The publish guard** (`prepack`, `scripts/check-engine-identity.mjs`) regenerates it and asks the built `dist/language-server.mjs` for its handshake, refusing the tarball unless the engine reports exactly the package version — so a pending line changeset, or a `dist` built from another tree, cannot be published. An editor host chooses a telo version, loads that version's engine into a worker and speaks LSP to it; the engine is the only source of Telo semantics in an editor host.

**It ships in one artifact form, and every editor ships the same one**: `dist/language-server.mjs`, a single ES module with no imports. VS Code, studio (desktop and browser) and any other host load exactly this file — the one bundled into the editor and the ones fetched from npm for other versions are the same build.

## The engine does no I/O

No `fetch`, no filesystem, no Node built-in. Every file, directory listing, import (`oci://` and `https://` included), candidate manifest and hub answer is a `telo/*` request the host serves (`src/host-manifest-source.ts`, `src/host-ide-adapter.ts`, `src/workspace-marker.ts`). **`include:` globs are the engine's own**: it walks `telo/listDirectory` from the including file's directory, collecting `file` entries and descending into `directory` ones — never through a `symlink` — pruning `GLOB_PRUNE_DIRS`, and selects with `@telorun/glob`'s `selectByPatterns(…, { applyDefaultIgnore: false })` — the kernel's local source's exact rule — so a host serves directories, never patterns, and no host can match a glob differently. **Every `file:` URI it emits is canonical** (`src/document-uri.ts`, `@telorun/editor-protocol` § URIs), whatever spelling the host opened a document under; a file on a UNC share is the source `//host/share/…` and keeps its lowercased host both ways. `tests/canonical-form.test.ts` runs one table through this canonicaliser and the host's. Transports, credentials, caches and integrity checks are the host's; that is what lets one build run in every host. Two things enforce it: `tsconfig.json` has no Node types and the `WebWorker` lib (a Node built-in import fails type-check), and the build guard below. A host-side failure is a JSON-RPC error the engine reports — a load failure becomes a diagnostic, a hub failure is logged — never swallowed.

## Analysis

`src/workspace-session.ts` holds the open documents (full text sync; an open buffer stands in for the host's copy), resolves each document's **owner module** the way `telo check` does, and analyses each owner over its whole import closure exactly as `telo check` does (same loader options, `moduleDocuments`, `assembleGraphDiagnostics`, located by `findPositions`; no host versions, since an editor is not the machine that runs the manifest). A change re-analyses every owner whose closure read the changed file, and diagnostics are republished for every file whose set moved — open or not. After each owner analysis it sends `telo/requirements` (`src/requirements.ts`). Work is serialized and coalesced per document.

## Build

`pnpm --filter @telorun/language-server build` runs `tsc` and then `scripts/build.mjs`. The type-check reads its dependencies' BUILT declarations, not their sources (the sdk's source surface uses Node types this tsconfig deliberately lacks), so the dependencies are built first: the workspace build orders that, and building this package alone takes `pnpm --filter "@telorun/language-server..." build`. It does not rebuild them itself, because under `pnpm -r build` a nested build would rewrite the analyzer's `dist` while its dependents compile. `scripts/build.mjs` bundles `src/index.ts` with esbuild, every dependency inlined from workspace SOURCES (the `source` condition), then refuses the result — deleting it — on any of three failures:

- **The bundle guard** (`scripts/bundle-guard.mjs`) parses the output as a program and fails on any static or dynamic `import`, any reference to `require`, or any `node:` specifier — Node built-ins are left external precisely so the guard names each one with its position. It reads the program, not the text: the bundle legitimately carries strings such as AJV's code-generation templates that merely look like `require(...)`.
- **`teloInlines`**: `package.json` lists every workspace package the bundle inlines, the full closure (today the analyzer, editor-protocol, glob, ide-support, sdk and templating). `verifyInlines` — exported by `scripts/check-changeset-status.mjs`, which owns the field's meaning — attributes each input of esbuild's metafile to the workspace package containing it and fails, naming each one, when a package is inlined but unlisted or listed but absent. The changeset gate reads the same list to require a release of this package whenever one of those packages changes.
- **The protocol generation**: `package.json`'s `teloEditorProtocol` must equal `@telorun/editor-protocol`'s `TELO_EDITOR_PROTOCOL`. Hosts select engines by that field.

Every runtime dependency is a `devDependency`, because everything is inlined.

## Tests

`tests/` drives the BUILT bundle (built fresh by `tests/global-setup.ts`) through an in-memory host (`tests/harness.ts`) that serves `telo/*` from the fixture directories, checks every protocol message against a CLOSED projection of `editor-protocol-schema.json` (`tests/closed-schema.ts` — the published schema is open, so a later addition validates for hosts, but this engine may send nothing beyond its generation), and refuses any non-canonical `file:` URI the engine sends. Published diagnostics are compared with `telo check -o json` over repo fixtures, and each feature with ide-support's in-process answer (`tests/in-process.ts`).
