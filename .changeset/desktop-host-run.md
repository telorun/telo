`telo run` is the desktop host of an application whose root declares a `Telo.DesktopHost` need while the environment sets neither of its fields: before anything initializes it takes the application's single-instance lock (a second start shows the first one's windows, prints `<productName> is already running (process <pid>, <source>); its windows are shown` and exits 0), binds the window origin on `127.0.0.1` at its remembered port, starts the `telo-desktop-host` helper, and serves `desktop_host-1` on a private control channel with a fresh token — supplying the port and the need to the kernel by name, so the port's variable needs no value. Every connection to the app's origin is admitted first: a window's first load exchanges a single-use code for the `telo-window` cookie on a second loopback origin of the host's own (`/admit`, a port assigned at every launch), which also serves every page the host shows in a window — the startup view, the inputs form and the sign-in replay — so a connection handed to the application is never read by the host again; a request without the cookie is refused with `403`. The application stops gracefully on `Desktop.Quit`, on an OS quit, and when the user closes the last window with no tray icon open; a same-origin `window.open` opens another window and other http(s) origins open in the system browser. Without a tray, hidden windows are shown. `telo run --watch` refuses to be the desktop host. The host opens its own startup window at once, which shows a startup view, asks the root's missing inputs in a form (a masked field for a secret, a select for an enum; `--no-input` refuses as before) and, when the application fails to boot, shows the diagnostics and exits 1 when the window is closed; the application's first visible window replaces it. The helper tells the host when the user hides a window declared `onClose: hide`, so hiding the last visible one stops the application as closing one does. The kernel takes `redactedValues`, secrets a host holds that every log record of the application redacts. A sign-in that leaves for an external identity provider returns through the window's origin: each navigation a window sends to the system browser arms one return, and the first request from the browser without the window's cookie to one of the need's `callbackPaths` (a GET, or a form POST of at most 64 KiB, from the provider's own origin) is answered with a "Return to <productName> to finish signing in." page, focuses the window and is replayed there — a POST as a single-use page of the host origin that submits the form to the app's origin, with the host origin as `Origin` — so the session lands in the window's cookies; any other such request is `403`.
