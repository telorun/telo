The built-in vocabulary is data, and the capability roster is closed. Every `Telo.*` kind — the module, definition, import and need-type documents, the sinks, `Telo.JsonSchema`, `Telo.Function`, the capability abstracts, `Telo.PublicUrl` / `Telo.PublicHostPattern` — and every `telo://manifest#/$defs` fragment is one JSON file under `sdk/builtins/`, read by both analyzers, both kernels and the editor support; the format entries move from `analyzer/formats/` to `sdk/formats/`. Shapes two built-ins share are fragments a module may point at too (`LogLevel`, `LoggingScope`, `ModuleMetadata`, `ModuleImports`, `NativeEntries`, `PlatformAxes`, `NeedRequest`, `ThrowCodes`, `CallableParams`, `CallableReturns`, `CallableType`, `DispatchTarget`, `KindMetadata`, …).

`Telo.Definition` and `Telo.Abstract` documents are validated against one built-in schema by `telo check` and the kernel alike, so a key neither declares (`controllrs:`) is `SCHEMA_VIOLATION` and `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED` rather than passing the check and failing at boot. A capability names a lifecycle a kernel implements, so no module adds one: `capability:` takes exactly `Telo.Callable`, `Telo.Invocable`, `Telo.Mount`, `Telo.Provider`, `Telo.Runnable`, `Telo.Service`, `Telo.Sink` or `Telo.Type`. Anything else is `CAPABILITY_UNKNOWN` — with the nearest role suggested for a misspelling, and `extends:` named for a built-in kind that is no role — and `Telo.Executable` / `Telo.Template` are `CAPABILITY_NOT_DECLARABLE`; both are reported for a dependency's definition at the entry's `imports:` entry through which the dependency is first reached, however deep, and both kernels refuse with the `ERR_`-prefixed twins before the document's schema is checked. This is a breaking change: a capability a third party invented, which the Node kernel used to accept, is refused. It is breaking a second way: an abstract's `schema:` and `status:` are now held to JSON Schema like a definition's, so an abstract's malformed `schema:` / `status:` — a keyword JSON Schema refuses — is `SCHEMA_VIOLATION` at `telo check` and `ERR_RESOURCE_SCHEMA_VALIDATION_FAILED` at boot, where the kernel used to accept it. A `Telo.Definition` / `Telo.Abstract` declared as a `with:` scope member is judged by `telo check` too — its `capability:` against the roster and the document against its built-in schema, at the member's own line, or for a dependency's at that same `imports:` entry — so a load refuses it before the scope that would create it ever opens.

The legacy `capability: <Alias>.<Kind>`, naming a module's kind, is rewritten to `extends:` at load by the `capability-as-extends` migration and reported as `CAPABILITY_SHADOWS_EXTENDS`; `telo migrate` writes it to the file. A migrated kind is checked as the child it claimed to be — its parent's schema, invocation contract and `throws` ceiling now apply, so a published dependency that violated its abstract's contract fails where it was skipped. Migration entries gain `valuePattern` / `valueNotPattern`, written in the RE2 subset; an entry using lookaround or a backreference is refused. Capability completion and hover offer exactly the declarable roles, each with its roster description. `@telorun/analyzer` exports the roster readers (`capabilityRoster`, `declarableCapabilities`, `throwsAllowedCapabilities`, `capabilityProblem`, `capabilityDescription`, `isCapabilityRole`, `builtinKindNames`) and `builtinDocumentSchema`, and no longer exports `THROWS_SCHEMA`, `ABSTRACT_THROWS_SCHEMA`, `THROWS_CAPABLE_CAPABILITIES` or `OBSERVED_STATE_SCHEMA`.
