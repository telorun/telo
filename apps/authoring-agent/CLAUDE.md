# Authoring agent — package guide

Loaded when working under `apps/authoring-agent/`. Repo-wide rules live in the root `CLAUDE.md` — including the MANDATORY rule that every architectural change updates this agent's system prompt (`chat/primer.md`, which the chat library's `system:` reads with `!include-text`) in the same change. The primer's SHA-256 is the agent's prompt identity (`GET /capabilities` → `prompt.id`), so an edit to it is visible to every client.

## Asking the user

- "how does the agent ask the user a question?" → the analysis phase in the authoring agent's system prompt (`apps/authoring-agent/chat/primer.md`) and its e2e pair (`chat/tests/{authors-manifest,asks-before-building}.yaml`), `apps/studio/src/agent/questions.ts` (the block's single reader), `components/agent/QuestionCard.tsx`. **A question is a fenced `telo-questions` JSON block in the reply TEXT, never a tool call** — a tool result feeds the model loop straight into another step, so a tool cannot end a turn, and ending the turn is what asking is for. The editor renders it as clickable options and sends the picks back as an ordinary message, so the agent is never told whether a client parsed the block; a client that does not, and the user's own opt-out, both degrade to the same questions as text. **A question with NO options is an open one** — a fact only the user has (a sheet's columns, a tracker's field names, a join key), which the agent must never invent: the hub answers what a MODULE's fields are, nothing answers what the USER's are, and a made-up column name is not a syntax error but a manifest that checks clean, runs, and is wrong. The phase is CONDITIONAL on the request leaving something material unsaid — which is why the two e2e cases only assert anything as a pair, since either alone is satisfied by an agent that always asks or never does. **A placeholder is never an implementation** — a fetched-then-ignored source, a join returning a constant, a `value:` step of example rows where a computation belongs. Such a manifest checks clean and renders invented numbers, which is worse than not building: it reads as real and nothing downstream flags it. A computation the agent cannot work out is reported at the top of its reply; a gap in the CENTRAL capability is asked about before building around it, never footnoted after (the rule that permitted this said "build everything that does not depend on it", which is right for a peripheral unknown and licenses a hollow app for the load-bearing one). **A `default:` for a fact only the user has is an invented answer** wearing a nicer word, so such a variable is declared required. **A PROBE beats a question**: where a system is addressable and the agent has its identifier and a credential, it writes a throwaway read-only manifest under `.probes/`, runs it through `run_manifest`, reads what it printed off stdout and deletes it — so a spreadsheet's tabs and headers are discovered rather than transcribed by the user, leaving only the identifier and the credential's env var to ask about. The read-only rule is prompt-level and therefore NOT enforcement (the agent authors the probe); the enforceable control is the credential's own scope. **Having no credential is not a refusal** — the agent obtains one through `oauth-client`'s DEVICE flow (print the verification URL + user code, the user approves, poll), never the redirect flow, whose callback needs a listener the user's browser can reach and the container is not. It spans two runs, since a poll cannot outlast `runTimeoutMs` while a human signs in, and the second run does the READING too — an in-memory grant dies with the process that obtained it, so keeping the grant and the work together is what removes the need to persist one. Gated by `ALLOW_MANIFEST_RUNS`, off by default — the switch grants running ANY manifest, so it reaches the user's live systems with whatever the container holds, which is why it is named for what it does rather than for tests. **Questions come in ROUNDS that narrow** (shape first, then only what the previous answers made relevant, three-round ceiling): asking everything at once is what produced compound questions cramming four asks into one, and a tab's column headers cannot be asked for before the tab is known. **What the workspace CONTAINS is injected into every turn** as a `WORKSPACE STATE:` message rather than left to `list_dir` — the agent asked whether to create a new app or extend an existing one against an empty workspace, and a tool the model must remember to call is one it sometimes will not.

## Conversations

- "who owns a conversation, and what counts as a change to it?" → the chat library (`chat/telo.yaml`): `conversations` holds only what nothing else determines (title, archived, timestamps, `revision`, the `removed_at` tombstone, the internal `assembling` mark); `model`, `messageCount` and `totalTokens` are DERIVED at read time from live turns through the `conversation_view` view over `turn_projections`, whose `tokens` / `model` / `context_tokens` / `summary` / `summary_through` are folded from the journal like `messages`, so the projection stays disposable. **`revision` + `updated_at` move in the transaction of every change** — admission, continue, a turn's ending (`endTurn`, in a `finally` so a failed projection still counts), a generated title applied, PATCH, truncation marking, the tombstone — and retention idleness is `updated_at`. **Admission order is the invariant everything else leans on: claim the journal key, THEN write the `turns` row** conditionally on a live, unarchived conversation, bumping `revision` in the same transaction (`admitTurn`'s `recordTurn`). A turn row is therefore never visible before its key, and **a continue likewise takes its turn's key over before its revision-bumping transaction** (`continueTurn`'s `takeOver`, then `touch`, which also refuses a turn marked removed); a refusal after the takeover gives the key back failed with the error it held just before the takeover, the error the takeover itself reports (`releaseAttempt`: a sink adopts the claim and re-raises the error) and refunds the reservation, so a removed key is never started; a takeover reporting no error created the key (removed and its marker forgotten since the continue's state-only snapshot), so it is given back failed `ERR_JOURNAL_KEY_REMOVED` and refused 410; the note's records are read after the takeover; `tombstoneConversation` is a compare-and-set on the `revision` it read beside its running check (DELETE retries on a mismatch, the sweep reports `busy` and moves on), and truncation compares its `revision` inside its marking transaction. **Deletion, truncation and the sweep share one removal**: mark (`turns.removed_at`, projection rows dropped, in the tombstone/marking transaction), then `cascadeTurns` removes each marked turn's key before its rows, so a crash leaves marked turns the next sweep finishes; a branch writes its conversation row FIRST, hidden (`assembling = 1`: excluded by `conversation_view`, so every route answers 404, and refused by every liveness-checked write), copies turns under it only while it is still hidden and live, and clears the mark last — so no turn row ever lacks its conversation row; a refusal mid-copy runs `discardBranch` (tombstone + cascade) and re-raises, and a branch a crash cut short is an idle conversation the sweep removes like any other (`tombstoneConversation`'s `includeHidden`). **Title and compaction are sources of the turn's own stream** (`nameConversation`, `compactHistory`, between the lead record and `agentTurn` in `turnRunner`), so their records are journaled before the agent reads the projection, and their usage is in the turn's settled amount (`turnEnd`) and `tokens`. **A call that returned is always journaled with its usage**: an unusable summary (a reply not ending `stop` → `ERR_SUMMARY_INCOMPLETE`, checked first; empty → `ERR_SUMMARY_EMPTY`) is a `context-summary` with `error` and no `summary`, yielded before `compactHistory` raises `ERR_CONTEXT_COMPACTION_FAILED` from a later `Stream.Concat` source, and only a record carrying `summary` is a summary (projection, provider-state reset, branch remap keep the two apart); a title the conditional update did not apply is `conversation-title { model, usage }`, so a `title` in a record is always one the conversation took. A `try:` step catches a cancellation, so both rethrow `ERR_INVOKE_CANCELLED` themselves. The naming and summary calls run on `bufferedModel` (`Ai.Buffered` over `lowEffortModel`: the agent's `model` and request at `reasoning.effort: low` with no reasoning summary, because `max_output_tokens` bounds reasoning and reply together), capped at 1024 and `maxContextTokens / 8` output tokens (`maxContextTokens` is at least 8, so the summary cap is at least 1); the stub tells them apart by their instructions. A branch's title stays within PATCH's 200 code points (`branchTitle`). Title handling counts code points: `titleOf` strips and cuts with regexes and the naming prompt is the first message's first 4000 code points, never `substring` (UTF-16 units). Tests: `chat/tests/{conversations,conversation-title,context-compaction,context-floor,conversation-removal,conversation-truncation,conversation-branch,conversation-migration,turn-spend,tool-result-bound}.yaml`.

## The boundary

- "who may call the agent, and what may a tool touch?" → the `api` mount's `guard` in `telo.yaml` (origin allowlist, then an HMAC-compared bearer token when `AGENT_TOKEN` is set; `probes` — `/health`, `/ready` — is a separate unguarded router), `Chat.outsideWorkspace` (the one lexical path rule every path-taking tool sequence and both `/workspace` routes apply first), and the write/edit sequences' `credentialFindings` scan (`ERR_SECRET_IN_MANIFEST`, before anything is written, no override). **A tool error reaches the model as its message alone** — the `ai` tool-result record carries no code — so a refusal the primer tells the agent to recognise leads its message with its code. **Tool results are text** (`result:` renderings; the check part is `Chat.renderCheck`, a command's output `Chat.renderRun`), while the structured value rides the record's `output` for Studio. Tests: `chat/tests/{boundary-auth,workspace-tools,turn-tracing}.yaml`, offline against the provider stub, whose `STUB_CALLS:<base64 JSON>` directive scripts tool calls.
