# Studio — package guide

Loaded when working under `apps/studio/`. Repo-wide rules live in the root `CLAUDE.md` (Radix primitives, `lucide-react` icons). The runner contract the editor talks to is in `packages/runner-core/CLAUDE.md`; the agent's question protocol in `apps/authoring-agent/CLAUDE.md`; the module-graph projection the topology view draws in `analyzer/nodejs/CLAUDE.md` § Module graph.

## Run

**The desktop build runs through the `telo` it SHIPS.** Studio bundles the CLI as a Tauri sidecar, built from the same commit (`scripts/stage-cli-sidecar.mjs`, staged into `src-tauri/binaries/telo-<rust target triple>`), and the Rust shell supervises `telo runner` on loopback; the editor then talks to it through the ordinary http-runner adapter, so `local-cli` is the same thin "where does `baseUrl` come from" wrapper `local-docker` is. **The executable is configuration, never a lookup**: the adapter's one field defaults to the sidecar, a user may name their own build, and nothing searches `PATH` — an app whose behaviour depends on machine state is the failure this rules out. That executable is the RUNNER; the telo an application runs on is the version its module is edited against (Language tooling, below), which the runner supplies as itself or as that release's verified binary. A development build has no sidecar and names this checkout's CLI explicitly instead. It is seeded and made active only on a FIRST launch; docker stays selectable (it is the runner that runs an application the way production does) and is the only local option in the browser build, which has no process to supervise. Unlike docker there is no consent gate: that gate exists because the docker runner mounts the daemon socket, not because a run is local. **The shell names the origins its own webview sends** (`--allow-origin`), because the runner refuses browser origins it was not given — a local API that runs code is reachable from every page the user visits, so the client that needs an origin allowed is the one that declares it.

**The settings row asks the ADAPTER whether a local runner is up and how to stop it** (`isRunning` / `teardown`), never a table keyed by adapter id: the registry exists so the UI does not know adapters by name, and a fourth runner should not mean editing a UI file.

**A run's files sit in the session where the editor holds them, relative to the workspace root** (`run/bundle.ts`): an Application at `<root>/apps/todo/telo.yaml` is `apps/todo/telo.yaml` in the session workspace, never `telo.yaml`. The session workspace has more than one writer — the agent's sync writes the editor's whole tree into the same volume, relative to that same root — and rooting the bundle at the application's own directory made the two layouts disagree: the first agent turn deleted the app's files from under the running kernel (`ENOENT … /workspace/telo.yaml`) and wrote them again one level down. Only a closure that reaches a file outside the workspace root falls back to the common ancestor of what it ships. **What a run ships is what `telo publish` would**: each reached module's manifest and partials, its `files:` patterns, and every file a tag claims (`!module-path`, `!include-*`, read through the analyzer's `collectModuleFileClaims`; a directory is expanded only where `!module-path` names it); a claim naming nothing ships nothing, so the kernel's own refusal names it. Files are read as bytes (`WorkspaceAdapter.readBytes`) and a non-UTF-8 one travels as base64, in the bundle and in a watch session's change sets alike.

**A run's environment is the workspace's env files, read fresh when Run is pressed** (`run/application-env.ts`, over the analyzer's `resolveWorkspaceEnv` and the workspace adapter's read in `loader/workspace-file-read.ts`): the walk `telo run` takes from the manifest's directory up to `telo-workspace.yaml`, collecting its `env.files`, except that the marker search never climbs above the opened folder — with no marker inside it, only the manifest's own directory is read. The merged values are the session `env` whole (on the local runner they override what Studio's own process inherited, where `telo run` lets the shell win), and the missing-value check and the port mappings read them before a port's `default:`. A marker whose `env:` is refused or cannot be read, and an env file that exists and cannot be read, refuse the run as the dock's `env-files` blocker, each naming its workspace-relative file and the reason: Studio has no shell to fall back on, so a value it cannot read is a value the run lacks. A watch session keeps the values it started with. No environment is stored per application; the `telo-studio:deployments:v1` key an earlier Studio wrote is deleted on start, its values dropped.

**The Variables tab is a view over those files** (`components/views/run/`), never their owner: one row per declared variable, secret and port, showing its value and the file it comes from, or that it is unset and whether that refuses a run. An edit rewrites that one line in that file and an empty value removes the key's lines there (the analyzer's set / clear edits, every other byte kept); an unset value is appended in the manifest's own directory, to the last `env.files` entry of the kind it needs — a secret to the last sensitive one, and when the workspace declares none the row says so, naming `env.files`, and writes nothing. A secret read from a file not marked sensitive carries the warning `telo run` prints. The tab re-reads on open, when a write touches a file named by an `env.files` entry in force or the marker, and on every workspace reload: the workspace adapter is wrapped once when a workspace opens (`loader/observed-workspace-adapter.ts`), so every writer — a save, a form edit, a file operation, the agent's sync — is heard without knowing the tab exists. Variables nothing declares live in the same files, opened in the code editor (`.env` / `.env.local` highlighted as `ini`).

**The desktop file scope adds `$HOME/**/.env` and `$HOME/**/.env.*` to `$HOME/**`**: the shell matches a leading dot only literally, so without them a `.env` showed in the explorer and could not be opened, and with them `~/.ssh`, `~/.aws` and `.envrc` (which direnv executes, so it gets no write access) still cannot. `src-tauri/tests/fs_scope.rs` matches the capability's patterns under the shell's own match options. A dot-file the scope refuses is reported as outside Studio's desktop file scope (the Tauri adapter rewords the shell's `forbidden path`), so an `env.files` entry the scope does not reach is an unreadable file naming the scope.

**The editor offers ONE Run**, and the mode is not a user choice: it asks for a watch session when the runner advertises one and degrades to a plain run when it does not, read from a capabilities fetch on the run path rather than from asynchronously-filled state — where a Run clicked early would silently start the other kind. `mode` stays on the wire, so a one-shot run is still expressible by any client.

**The top bar's workspace menu is the one place a workspace is switched or closed** (`components/WorkspaceSwitcher.tsx`). It lists what this device can open without asking — the browser-stored workspace and the Telo Cloud working copies in the local index, so both open offline and signed out — beside "Open folder…" (where a picker exists), "Open from Telo Cloud…" (signed in) and "Close workspace". The browser-stored workspace is opened by its BACKEND, never by its root: where a directory picker exists, a picked folder named `workspace` has the same root, `/workspace`. Closing leaves the files alone and records the close (`forgetWorkspaceRoot`), so a reload opens nothing — not even a browser-stored workspace found by its files — until the user opens one.

**Phone width is one boundary, Tailwind's `md`, and CSS decides everything it can.** Spacing, touch targets and what is hidden are `max-md:` / `md:hidden` classes; `useIsMobile` (`hooks/useIsMobile.ts`, the same boundary) exists only for what CSS cannot do — the sidebar becoming a drawer (`ui/sheet`), opened from the top bar's menu button, closed by opening a file or module, and starting open in a workspace with nothing open. Below the boundary the top bar keeps the workspace menu as an icon, folds Undo / Redo / theme into one menu and puts the module name and telo version on a row of its own; the agent panel and the topology's detail panel cover the editor; and every action a sidebar row offers on right-click or hover is on a visible button, because a touch screen has neither.

**The app's font is Geist, shipped in the build, and Radix Themes is told so.** The `<Theme>` wrapper around the whole app sets its own system font stack, which wins over the theme's `--font-sans` for everything inside it; the stylesheet therefore points `--default-font-family` / `--code-font-family` on `.radix-themes` at the Geist tokens. The font files come from `@fontsource-variable/geist` and `-geist-mono`, imported in `main.tsx` — not from the stylesheet, where the bundler leaves their `url()`s unresolved and emits no font file — so the desktop build has them offline and no page load reaches a font CDN. `--brand` (`text-brand`) is the Telo brand hue, the one colour beside the neutral palette; the top bar's wordmark uses it for "Studio".

**A render failure stays in the region it happened in** (`components/RegionErrorBoundary.tsx`): the sidebar, the open tab, each view, the graph, the detail panel, the run dock and the agent panel each show their own failure — the error and "Try again" — while the rest keeps working, and one more boundary at the root covers what no region contained. A boundary given a `resetKey` clears when what it shows changes (another view, tab or selection). A new top-level region gets a boundary of its own. Schema walks read during render answer "unresolved" instead of throwing: `resolveRef` (`schema-utils.ts`) is `undefined` for a reference it cannot follow, a shape another module declares (`telo://Ui/Node`) included.

## Language tooling

**Every diagnostic studio shows, and everything its structured views read about a module, comes from the engine of the telo version the module is edited against.** A workspace runs one `@telorun/language-host` router (`src/language/language-session.ts`), which picks each module's telo version (Auto, or the workspace's pin), runs that version's `@telorun/language-server` engine in a module Web Worker made from a `blob:` URL of the verified bytes, and serves the engine's reads from studio: `file:` reads through the workspace adapter (`WorkspaceFileSystem`, confined to the root for the browser's virtual workspaces), `oci://` / `https://` through the loader's own manifest-cache and HTTP sources, the hub through language-host's `HubClient`. The engine studio ships is `@telorun/language-server`'s built file, copied unchanged into the build as `engine/language-server-<content hash>.mjs`, its name given to the app by `virtual:telo-bundled-engine` (`vite-bundled-engine.ts`); nothing stamps its version — the router reads it from the engine's handshake, so a build of an unreleased tree is named **X (local)** in the version menu and in the status tooltip. The label beside the menu is deliberately shorter — the version in effect, and `(auto)` when Auto chose it — because the menu next to it already names the choice. Downloaded engines live in Cache Storage `telo-engines`. The per-workspace setting and Auto resolutions are `localStorage` (`LOCAL_PREFIXES.teloVersion`, `LOCAL_PREFIXES.engineResolutions`), the engine catalog `LOCAL_KEYS.engineCatalog`, shared by every workspace because it describes the registry.

- **Documents are Monaco models.** `WorkspaceModels` keeps one model per workspace manifest document at its `file:` URI (`language/file-uri.ts`: a browser workspace's virtual path maps the same way, `file:///workspace/app/telo.yaml`), whether or not a source view shows it — so every module is analysed from the moment the workspace opens, and a form edit reaches the engine as the text it produced. The source view edits these same models (`path` + `keepCurrentModel`); a model the user has typed into keeps their text until they commit it.
- **The Monaco↔LSP bridge (`language/monaco-lsp-bridge.ts`) is Telo-agnostic**: full-text sync of the models, published diagnostics as markers, and a Monaco provider for exactly the capabilities the server advertised — completion, hover, definition, rename with prepare, signature help, semantic tokens (legend from the capabilities), code actions, code lenses with their commands, `workspace/applyEdit` — each registered, re-registered and withdrawn as the router's dynamic registrations say, since the router offers the union of its running engines' features. Any other notification reaches whoever listens for it by method (`onNotification`), and the session sends requests of its own through it (`sendRequest`); the Telo vocabulary of both lives in the session, never in the bridge. It replaced the source view's in-process registrations; no `monaco-languageclient`, no `@codingame/*`. The resource YAML slice pane is a projection of its document's model served by the same engine (`components/detail-yaml-projection.ts` over the bridge's generic `ModelProjections` seam: requests asked of the source document at mapped positions, answers mapped back, nothing outside the slice kept; a keystroke is spliced into the document model at once and the pane re-derives whenever that model changes). Non-Telo files get no Telo features because they are not Telo documents — a file becomes one by being a module owner or an `include:` partial, which open in the source view.
- **The engine also serves each module's view model** (`@telorun/editor-protocol` § The view model), read through `LanguageSession` (`viewModel`, `celCompletion`, `onViewModelChanged`, `supportsViewModel`), a module named by its workspace path and as an owner by the canonical URI of that path (`ownerOf`). `language/view-model-store.ts` holds the last model per module for the workspace (`useLanguageSession`'s `viewModels`, read with `hooks/useViewModel.ts`): fetched when its first reader subscribes and again when its engine announces a higher revision, one fetch per module at a time, an answer at or below the held revision dropped; its status is `loading` (asked, or no engine serving it yet), `ready`, `unsupported` (the serving engine predates structured editing, naming its version), `absent` (the engine answered `null`) or `failed` with the reason — the read's failure, or, when no engine serves the module because the one it is edited against cannot run (failed, refused, offline and not cached, an unoffered pin), the session's status in language-host's `describeTeloStatus` words. A model is **current** (`ViewModelStore.isCurrent`) while every document its `documents` names is still at that version in its Monaco model — the number the bridge sends in `didChange`. The views read the model through adapters that give them the shapes they already take: `language/module-graph-from-data.ts` (the analyzer's `ModuleGraph` with its lookups), `language/structured-model.ts` (`StructuredModel`: the picker's `RefResolver` plus contracts and the module document's schema, built over the module's `viewData` kinds because an output verdict is found by its slot's place — `<canonical kind>#<pointer>` — in the schema studio holds, never by comparing `outputType`s; `forTemplate(kindId)` is the same model judging a template body's own entries, which the template canvas hands its views), `templateGraphFromViewModel` (`module-graph-view/template-graph.ts`), `findViewModelReferences` (`resource-references.ts`, reference slots from the model and CEL reads from the manifest) and `language/cel-field-completion.ts` (a form field's CEL completion).
- **The diagnostics store has one producer**: what the engines publish, routed by `Diagnostic.data.resource` (form fields paint by `data.path`) — `language/engine-diagnostics.ts`, fed from `hooks/useLanguageSession.ts`.
- **Structured views read the engine's view model of the active module** (`useViewModel` in `components/Editor.tsx`): topology and the module graph, the module bar's boot and logging shapes (`moduleRootSchema`), the template canvas, the ref pickers and step contracts, and the reference check behind delete and inline (`findViewModelReferences`). Until the model is `ready` the canvas says why in its place (`components/views/topology/StructuredModelNotice.tsx`): `loading` and `absent` read "Analyzing module…", `absent` adding that the engine is not analysing the module; `unsupported` names the version that predates structured editing and offers the source view; `failed` shows the reason with Retry (`ViewModelStore.retry`, which starts the module's engine again first when the engine is what failed), and a language session that never started is that failure. Meanwhile the forms and pickers offer existing resources with no kind resolution, inlining is refused as unchecked (with the reason for `unsupported` / `failed`), and a delete prunes no reference slot — the engine then reports what it left dangling. **A ready model that is not current is treated as not ready by inlining**: its sites miss a reference written since, so the inline is refused as unchecked and the module is read again, and retrying once the engine has caught up proceeds. **A delete clears a reference site only where the module's live value still names the deleted resource** (`referenceSlotsToClear`): the sites may predate an edit, and clearing splices an array item without reading it, so a second delete before the engine catches up would otherwise clear a sibling. A form field's CEL editor asks the engine too: `language/cel-field-provider.ts` binds each CEL model to its field and the session, which the editor finds through `CelFieldContext` (the active module and the session, provided by `Editor.tsx`). Studio still builds two things itself: each module's `viewData` — its kinds and their schemas, from the workspace's own documents (`view-data.ts` over `loader/queries.ts`) — and the eval-mode answers of the schema forms, the analyzer's free functions over those schemas. A form field's eval mode is the analyzer's answer, not the form's reading of the annotation: `getCelEvalMode` (`components/resource-schema-form/cel-utils.ts`) asks `declaredEvalMode` / `declaresCelRegion` of the field's schema node and only propagates the result to descendants, so an `x-telo-eval: accessor` field offers `!cel` alone and nothing beneath it takes a tag, as in VS Code. A `Selection` carries the same three modes, and `celEvalModeAtPointer` answers `accessor` for a pointer at or inside an accessor field: a form rooted there renders that field's members, which are part of its value, so none of them takes a tag.
- **The version a module is edited against is the version it runs on.** Run asks a runner advertising `features.teloVersions` for exactly the version the language session reports for that module's manifest (`run/run-version.ts` over `LanguageSession.statusOf`: the pin, or Auto's answer for that module) and leaves out exactly the config properties the runner says a version supersedes (`config.supersededByTelo` — its `image` and `pullPolicy`). A module nothing serves has no version to ask for, so its run is refused with the status that already explains why — never run on some other version. A runner's refusal before the session exists (`TeloVersionRefusedError`: `telo_version_unavailable` / `telo_version_unsupported`) is the dock's blocker with the runner's own reason; a version the runner only finds it cannot fetch while starting (an image pull, a release download) is that session's failed start, with the same reason on its status. **A live run whose module has since moved to another version says so** (`staleRunVersion`): a run's telo is fixed when it starts, so after a pin change the editor checks against one version while the session runs another, each agreeing with itself — the dock warns and the next Run moves it. **A runtime that reports another version is a warning, never a stop** (`run/telo-alignment.ts`, drawn in the dock beside each app's generation): the runner passes on what the runtime says it is, Studio compares it with what it asked for, and by then the manifest has loaded on that runtime. One that reports nothing shows the requested version as not confirmed. A runner without `teloVersions` is sent no version and keeps its `image`.
- **A settings form leaves out what its schema deprecates** (`deprecatedProperties` / `withoutDeprecated` in `run/ui/capability-form.ts`): the standard keyword, so the form knows no field by name. An aligned runner marks `image` and `pullPolicy` (how a version's image is pulled is its operator's), so its settings show only what addresses it; an older one marks neither and keeps both; Studio's own copy of the docker schema carries the mark so the field does not show and then vanish.

## Telo Cloud

Signing in is optional, and everything else in Studio works without it. A signed-in user creates or opens a Telo Cloud project, edits it in a local working copy, commits to its git repository, publishes a module, deploys an application to a stage and watches it run; members, repository connections, stages, hosting, and stopping or deleting anything are the console's.

**Everything a developer does daily is done in Studio; what Studio never does is stop or delete** (`plans/cloud-developer-loop.md`). "New Telo Cloud project…" creates a project — Cloud gives it one stage, Production, on the place the form names, which starts on the organization's default (`cloud/new-project.ts`: `initialPlacement` is the choice Cloud makes for a request that names none, shown before it is sent). "Publish and deploy" sends the stage with the publication and **Cloud starts the deployment**, so closing Studio loses nothing; Studio only watches (`publish` in `cloud/context.tsx` polls until the publication's `deploy` is settled). The Cloud view (`components/views/cloud/`, `ViewId` `"cloud"`, offered for an Application while a Cloud project is open) shows the app per stage and takes the actions Cloud has for a deployer: deploy a published version, revert to the previous version, promote, restart, apply changed variables, cancel. A deployment is followed over its event stream through the one transport, reopened after the last event seen (`cloud/deployment-progress.ts`). Suspend, resume, delete, scale and stages are linked to in the console, whose address is the session's `consoleUrl` and nothing else (`cloud/console-links.ts`). What the session may do is its `permissions` (`hasPermission` in `cloud/session.ts`), never a guess from a refusal.

**Studio's JavaScript never holds a Cloud token, in memory or in storage, and neither build depends on CORS.** Studio runs downloaded language engines and renders agent and module content, and a Cloud token can deploy to customer clusters. Every Cloud call goes through one transport with two implementations chosen by build target (`cloud/backend.ts`), and nothing else knows which is active. The web build asks `/api` on its own origin — which is why the web build is served by Telo Cloud (`ghcr.io/telorun/studio-web`, `apps/studio/Dockerfile`, deployed with `apps/studio/chart`, whose version is this package's and whose route takes everything on the host but `/api`) — with the HttpOnly `__Host-sid` cookie the browser keeps to itself and an `X-CSRF-Token` on unsafe methods. The desktop build hands a method, a path under the API base, headers and a body to the shell, which holds the access and refresh tokens (the refresh token in the OS credential store, service `com.telo.studio`), attaches the Bearer and streams the answer back. **The API base and the identity provider are the shell's build settings** (`VITE_TELO_CLOUD_API_URL`, `VITE_TELO_ACCOUNTS_URL`, read from the build's environment), never something the webview supplies: a webview-chosen base would let page content send the token anywhere. No content-security policy stands in for this on the desktop — runners are user-configured hosts, so the webview's network access cannot be an allowlist.

**"Is Cloud here" is decided on the session's shape, not the status.** The web build reads `GET /api/session`: JSON of the session's shape is signed in, `401 session_required` is anonymous, and anything else — the dev server answers every path with 200 and the page — hides every Cloud control. A 401 at any later time puts Studio back to anonymous without touching the working copy.

**The top bar's products menu is accounts' list, read by the browser once per page load** (`products/`, `components/ProductSwitcher.tsx`): `<accounts>/v1/products` (anonymous, CORS `*`, 3 s), every entry validated before it reaches an `<img src>` or CSS — id, name, https `url`, an https `icon` on accounts' own origin, both `oklch(…)` colours — an invalid entry dropped and logged, any other failure no menu at all. The colours are `--product-<id>` custom properties in a `<style>` for `:root` and `.dark`, and a name is coloured with `var(--product-<id>)`; `studio` is the current product. **Where accounts is differs by build**: the web build reads `/config.json` (`{"accountsUrl"}`), which the image's nginx renders at start from `ACCOUNTS_URL` (the chart's `accountsUrl`; `NGINX_ENVSUBST_FILTER` keeps nginx's own variables intact, and `/etc/nginx/conf.d` is a writable volume because the root filesystem is read-only); where that file is absent or not an https origin — `vite dev` — and always on the desktop, it is `VITE_TELO_ACCOUNTS_URL`, then `https://accounts.telo.run`.

**A working copy is one more workspace storage backend, rooted at `/cloud/<project id>` on both builds** (`cloud/working-copy-adapter.ts`), over a byte store with two implementations: the browser's Origin Private File System, and a folder under the app's data directory. The backend is chosen by that root, not by the environment. The explorer, autosave, undo, runs and the agent read and write it unchanged, and nothing they do reaches Cloud. Three things follow from the stores, not from choice:

- **What changed is decided on bytes, below the storage interface** (`cloud/working-copy.ts`), because that interface reads every file as text and says nothing about a binary one.
- **Modes and symbolic links live in the base record** (`base.json` beside the tree: commit, branch, and each path's mode, link target and SHA-256), since neither store can hold them on every platform. A changed file is committed with the mode its base records; a link is never materialized in the tree.
- **The desktop store escapes a leading dot in every stored name** (`%2E`), because the shell's file scope does not let a wildcard match one and a repository is full of them.

**A sensitive env file never reaches Telo Cloud.** A file is sensitive when its name is a `sensitive` entry of the NEAREST `telo-workspace.yaml` at or above it in the tree (`.env.local` where no marker governs) — the analyzer's `classifySensitiveEnvFiles`, since a nested marker governs the runs in its subtree and so the files they read. The working copy leaves such files out of the base, the working tree and the head when it lists changes and commits: a secret committed before its file was marked stays in git as it is and never shows as changed or deleted, and Copy to Telo Cloud project neither reads nor copies one. Which files are sensitive is the working tree's markers' answer. **Seeding, discarding and updating judge by both sides**: a tree file is left untouched when the tree's markers or the incoming ones (the snapshot's for a seed or branch switch, the base's for a discard, the head's for an update) mark it, an incoming file is written unless its path is left alone or the incoming markers mark it, and an update's merge leaves every such path out — so a file left alone only by the markers being replaced is an ordinary file afterwards and may show as a change. A marker of the working tree whose `env:` is refused, or that cannot be read, refuses listing changes, committing, copying in, seeding, discarding and updating with its message and changes nothing; a broken marker in the snapshot, base or head marks nothing, so the operation proceeds on the tree's markers alone and the broken marker, once written, refuses the next listing until it is fixed. Anything else wrong in a marker never refuses.

**Committing is explicit, and the server never merges.** A commit sends the difference from the base with the base's commit, under an `Idempotency-Key` kept in the working-copy index until the commit is seen to land — so a retry after a dropped connection, a reload included, yields one commit. The branch head is read on focus, every 30 seconds and before every commit: a clean working copy follows it once no run sync or agent turn is in progress (the editor's `idle()`), a changed one is offered Update. Update and a commit answered `409 branch_moved` run the same per-path merge (`cloud/three-way-merge.ts`): a path one side changed takes that side, a path both changed differently is the user's choice of "Keep mine" or "Take theirs", there is no merge inside a file, and afterwards the head is the base with nothing committed. Editing is paused while an update is in progress or waiting on that choice, and a `viewer` cannot edit at all — both through the one `editingPaused` reason every write path in `Editor.tsx` reads.

**A module is published for the telo version it is edited against — the same answer a run asks its runner for** (`run/run-version.ts`: the pin, or Auto's answer for that module), sent as the publication's required `teloVersion`. Cloud publishes with that release's CLI and runs every deployment of the published version on that release's kernel image, so what checked the manifest is what publishes and runs it. A module nothing serves has no version, so Publish is disabled with the status that explains why — never published for some other version. The version is the one the dialog opened with: a publication under way is not started again when the editor resolves another. Cloud's refusals are the dialog's failure in words: `telo_version_unavailable` (not a released `X.Y.Z` from `minimumTeloVersion` on — a development build's `X+unreleased` included — or a release with no kernel image or standalone CLI), `telo_version_mismatch` (the module version is already published for another telo version, or for none; the dialog offers the manifest, as for `version_content_mismatch`, since the way out is a new `metadata.version`) and `telo_release_unavailable`.

**A browser-stored workspace reaches git by being copied into a working copy, never by a commit path of its own** ("Copy to Telo Cloud project…" in the workspace menu, offered while that workspace is open and holds files, to a signed-in user, for projects whose role is not `viewer`). The files are written into the working tree at the repository root and become ordinary uncommitted changes, so the existing Commit is what persists them and Cloud gains no route. The target must be clean and is first brought to its branch head — so Discard undoes exactly the copy, and what the copy would replace is what git holds now; those paths are listed and replaced only on confirmation. Everything is refused before the first write (`prepareImport`): a file where the project holds a directory or the reverse, and whatever the repository's `limits` would refuse of the commit that follows. The directories the agent sync excludes are not copied, because a working copy commits everything outside `.git`; an explicit telo version pin is carried to the project's root, a conversation is not. **It is a copy, and the browser workspace is offered for removal only after the commit lands**: until then the files exist only in a working copy sign-out deletes. The index entry holds the digest of what was copied (`browserImport`), cleared by the commit and by Discard, and the offer is made only when the browser workspace still has that digest — one edited since is kept without asking. **Removal keeps what the copy left out**: the sensitive env files, whose secrets exist nowhere else, and every `telo-workspace.yaml` at or above one of them; everything else goes, a marker with no kept file below it included. The prompt names the kept files, and Remove classifies the workspace again over the same files the copy reads — a marker whose `env:` is refused then deletes nothing and its message is the toast. The workspace stays in the menu while it holds a kept file.

**The console links to a project as `/?org=<org id>&project=<project id>[&module=<module path>]`, and only the web build reads it** (`cloud/project-link.ts`; the desktop build reads no query parameters, and the three are ignored beside `open`). `module` is the directory of the module's `telo.yaml` in the repository, left out for the module at its root. Studio waits for the session, then: signed out, or signed in to another organization, it navigates to `/api/session/login` with `returnTo` holding the same address and `orgId` naming the organization, so the parameters survive the round trip; signed in to that organization, it finds the project in `GET /api/v1/projects`, opens its working copy and activates the named module. **A link gets one sign-in** — a `sessionStorage` mark set before the navigation, cleared on any load that carries no link — so a visitor who returns still outside the organization is told so and not sent round again. The parameters are stripped once the link is acted on, and every failure is the editor's error line: a project not in the list (unknown, or not the visitor's), a module the project does not hold, a refused open. **A link decides what opens**: the silent restore of the last workspace is held back while one is pending and stays off after a refusal, so the message never stands over another workspace; on an origin with no Cloud behind `/api` the link is ignored, its parameters left alone, and the restore proceeds.

**Sign-out removes the working copies**, after a confirmation naming the projects with uncommitted changes; a session that turns out to belong to a different user than the stored copies asks before removing them and otherwise signs out again. The index of working copies is `LOCAL_KEYS.cloudWorkingCopies` (user, org, project, branch, base commit — nothing secret). **An entry stored while Cloud called a project a workspace is not a working copy**: its id names nothing Cloud still has, so it is never listed or opened, and Studio offers once per load to remove it with its files.

## Agent

**The editor prefers a co-resident agent over launching one of its own**, and the two differ in where the shared workspace is: a standalone agent owns a directory and serves its own `/workspace` routes, a co-resident one writes the session volume, which the editor reads and writes through `/v1/sessions/:id/workspace` — the same path its saves take. The runner-seeded `telo-workspace.yaml` is excluded from that sync in BOTH directions: filtering one side only would either re-push it every turn (a reload each time) or delete it on the first (scattering one module cache into one per app). **A sensitive env file is excluded by the same one rule** (`included` in `agent/sync.ts`), for every agent: on each pass the editor's markers classify every path either side holds, the nearest marker governing, so no secret is copied into a session and none an agent writes is pulled back; a marker whose `env:` is refused, or that cannot be read, refuses the pass with its message. The transcript's links follow what the last pass left out.

**Every agent request carries the agent's bearer token when one is known**, resolved together with the URL in the same precedence: the override's token field, the runner-minted `RunnerEndpoint.token` of a co-resident or launched agent. **Neither is written to browser storage**: the override's token lives in memory only, and the run index strips `token` from every endpoint of the statuses it persists — a re-attached session gets its live token again from the runner's status stream. That is why the turn's events are read by a fetch-based SSE reader (`agent/event-stream.ts`) rather than `EventSource`, which cannot send a header: it does what `EventSource` did — reopens a dropped connection from the last record id (`Last-Event-ID` and `?lastEventId=`), drops a replayed record at or below it — and ends at once on a 401. A 401 `ERR_UNAUTHENTICATED` reads "This agent requires a token." wherever it surfaces. **The tool card's verdict comes from the tool result's structured `output`** (`checkExitCode`, `checkReport.diagnostics`), and so does the mid-turn pull (`output.path`); `content` is the text the model was given and is shown only as that. `GET /capabilities` is asked once per agent instance (URL + token): a "No auth" badge on the panel when it reports `auth: "none"`, and name, version and prompt id read-only beside the URL override (unavailable on a 404).

**Every conversation surface is gated on the capability document's `features`, never on the agent's version.** `conversations` turns on agent-minted conversations — the title becomes a switcher (search → `q`, archived, load more, rename, archive, export, delete), "New conversation" opens a draft that the first send creates with `POST /conversations` before `POST /chat`, and the per-workspace `telo-studio:agent:conv:<workspaceKey>` becomes a last-opened pointer (a 404/410 falls back to the most recent non-archived conversation, else a draft; any other failure keeps the pointed conversation open, shows the error and retries on the next tick or focus; a send never replaces an unconfirmed conversation with a new one; **a workspace opened while no agent is reachable shows a draft and opens or mints no id** — the agent a send then launches is a fresh instance that holds nothing, so asking it for an id chosen before it existed is a 404 on every first send — and the pointer is resolved by whichever agent appears, or settled by that send: created there, or on an agent without `conversations` the stored id, minted when there is none); `conversation-truncation` adds Retry, Edit & resend and Delete from here (a `DELETE …/turns?from=&revision=`, then a fresh `POST /chat` for the first two); `conversation-branching` adds Branch. A missing feature hides only its own actions; without `conversations` — no `features`, a 404, a failed ask — the panel is exactly the older one: a client-minted id, "New conversation" mints, no switcher, Copy only on hover, and the settings block lists what the agent lacks. A conversation belongs to the agent it was read from: a different agent re-resolves the pointer, and a send decides mint-or-create only once it knows what the agent it just selected serves. `manifestRuns: false` badges "No test runs"; absent says nothing.

**A tool card is chosen by the fields its structured `output` holds, never by the tool's name** — the tools an agent reaches through MCP are the hub's vocabulary, not Studio's, and a renamed or added tool must not need an editor release. `checkExitCode` (with `checkReport.diagnostics`) is a check verdict: a failed one lists its diagnostics, each opening its file at its line, a clean one is the line "check: clean". `changes` / `hunks` beside it are a write's or an edit's own diff — the hunks as the agent computed them (Studio diffs nothing), ± counts from `changes[0]`, the path opening the file at the first hunk's `newStart`. `exitCode` + `output` is a command: an exit badge when it is not 0, the last 20 lines of stdout, and all of stdout and stderr (`messages`) in the dialog. Any other `output` is the generic card: the tool's name and scalar arguments as the headline, text parts as text and everything else as a folding tree. A call still running, one that failed outright and an agent that reports no `output` keep the text card. **Every card is one row** — chevron, name, the scalar arguments (a lone one without its key) truncated with the full text as a tooltip, the verdict icon last — and its details are a preview held to a few lines (`ToolOutputPreview`; a command's keeps its last lines in view) under a failed check's diagnostics, which are shown whole, with "View full output" opening everything in a dialog with Copy, offered when the preview overflows or already left something out. Two or more consecutive tool or thinking parts between pieces of the reply fold into one "N steps" group that counts its failed calls (a tool error, a non-zero exit, a failed check) — open while the turn streams, folded once it ends, the reader's toggle overriding either. On a write or an edit whose check failed the card opens by itself and the diagnostics come before the diff. **Which editor file an agent's path names is answered in one place: the workspace bridge the editor registers** (`editorFile`, beside the snapshot and the writes it already owns, so a link opens the very path a pull wrote). The agent context composes the sync's own exclusion rule in front of it and hands the transcript that one mapping; nothing in the agent context or its components joins a path or holds a root. A path the mapping resolves is a link calling the diagnostics context's `navigate`; one it does not is plain text — a path under a directory the sync excludes (`.telo`, `.probes`, `.telo-agent`, `node_modules`, `.git`, `dist`), the session's `telo-workspace.yaml`, a sensitive env file, an absolute path, a URL, one that leaves the workspace through `..`, and every path while no workspace is registered.

**A turn's `summary` and `revert` are state on the turn, read from the records route — not records of its stream.** So a turn of this client's is read again once its stream ends, from an agent that keeps summaries. The summary card after each ended turn lists the files it changed on balance (status, ± lines, each opening at its `firstLine`; a deleted one is listed, not opened), the check, the runs and the tokens. A turn that changed no file, ran nothing and was not reverted gets no card — a turn that only answered a question has nothing to summarise. `files: null` is a turn from before the agent kept checkpoints — unknown, not empty — and shows no file list, no View changes and no Revert. **View changes** asks `GET /chat/{turnId}/changes` each time it opens and shows each file's turn-level hunks; `changedSince` is live state with three values — `true` marks the file "changed since", `false` leaves it unmarked, and null (the agent did not compare the workspace file) marks it "not compared". **Revert** confirms naming the file count, posts `POST /chat/{turnId}/revert`, and shows the recorded outcome — also another client's, which arrives on the revision poll — with its skipped paths and the paths the editor kept (below); it stays offered afterwards, since repeating it evaluates skipped paths again, and is not offered while a turn runs or on an archived conversation (the agent answers 409). A refusal of either route is the card's error, by its code; a 503 `ERR_WORKSPACE_BUSY` (also from `POST /workspace`) is resent with the client's backoff like every other 503. **The editor's files follow a recorded revert, whoever issued it — the rule runs on every records read** (first load, revision poll, the re-read after a turn or a 409) and on this client's own revert response, which is the same path and nothing special. What licenses changing an editor file is three facts about its path together — the agent's recorded revert marks it `restored`, the agent's tree now holds `before` there, and the editor's copy is byte-identical to `after` (`before`, `after`: the digests the turn's `summary.files` records; null is no file) — with no remembered or persisted record of what Studio last synced:

| Recorded outcome | Agent's workspace now | Editor's copy | Studio does |
| --- | --- | --- | --- |
| `skipped`, or path absent from `summary.files` | — | — | nothing |
| `restored` | does not hold `before` | anything | nothing, not reported |
| `restored` | holds `before` | holds `before` | nothing — already in line |
| `restored` | holds `before` | holds `after` | replaces it with the workspace's content; deletes it when `before` is null |
| `restored` | holds `before` | anything else | leaves it, reports the path as kept |

"Holds `before`" with `before` null means the path is absent from the workspace's tree, whether the tree holds other files or none — reverting the turn that created every file of a fresh workspace deletes them in the editor. A tree read that fails — a refused request, or an answer carrying no file list — is a failed apply, never read as an empty tree. Digest equality is the only evidence that the editor's copy is the turn's, so a file put back byte-identical to what a reverted turn left, before any send, is taken for the turn's copy when a later session first reads the revert. A turn's revert is applied once per `revertedAt` in a session (a memory-only marker, set only once the rule completed), never under this client's own turn (its end-of-turn reconcile converges everything), one convergence at a time — serialized with the seed and the reconcile — and at the cost of one editor snapshot and one workspace tree per read however many reverted turns it carries. A failure is shown (`The editor's files could not be brought in line with the revert: …`) and stays pending: it is retried at the next records read and before the next seed, and a send whose retry fails does not seed. The kept paths are state of the turn in the agent context, not of the card — they survive the panel closing — replaced by whatever a later run finds, and listed under the agent's own "N restored, M skipped" with: "Restored in the agent's workspace, but not in the editor — the editor's copy is not what this turn left. It will replace the restored file when you next send a message."

**Continue is not Resume.** A turn that spent its step budget on an agent serving `turn-conclusion` is a COMPLETED turn whose `finish` carries `limit: "max-steps"`: the conversation's last such turn offers Continue, which sends an ordinary new turn (`POST /chat`) saying `Continue.`, shown as the user's bubble. Resume stays what it was — `POST /chat/{turnId}/continue`, another attempt at an INTERRUPTED turn. An older agent's spent budget is a failed turn, so it shows Resume.

**Each turn surface is gated on its own `features` string, and a missing one hides only that surface**: `turn-changes` — the diff on write/edit cards and View changes (without it those cards show path and verdict); `turn-revert` — Revert; `turn-summary` — the summary card; `turn-conclusion` — Continue. The diagnostics list, the command card, the step groups and the generic card are not gated: they draw what any agent filling `output` already sends.

**The composer is state of the agent context, not of the panel**: its unsent text and its one queued message, kept in `localStorage` under `telo-studio:agent:composer:v1:conversation:<id>` — `…:workspace:<root>` while no conversation exists, re-homed when the first send creates one — so it survives the panel closing, a reload and a conversation switch, and an empty one stores nothing. Sending clears the text. The composer is disabled only where nothing can be written (no workspace, an archived conversation), never by a running turn: **a submit while a turn runs queues**, a further submit is appended to the queued message after a blank line, and the queued item offers Edit (back into the composer) and Remove. **A queued message is sent only after a turn whose `finish` record this client saw**, as an ordinary new turn, and only once the end-of-turn reconcile succeeded — the next turn seeds the agent from the editor. Every other ending returns it to the composer, ahead of what was typed since: a failed or stopped turn, a send that never became a turn, a failed reconcile, and a stored queue whose turn is found ended (or unreadable) after a reload or a switch; one whose turn is still running is re-attached with it and follows its finish. Enter and Cmd/Ctrl+Enter submit, Shift+Enter adds a line, Esc in the composer stops a running turn, and **Cmd/Ctrl+J** opens the panel and focuses the composer from anywhere — not Cmd/Ctrl+K, which is the prefix of Monaco's chords in the source view.

**A message may carry files, offered only by an agent whose `features` has `attachments`** — without it the composer and the transcript are the older ones, and an older agent's records never carry the field. The composer's state is `{ text, attachments, queued: { text, attachments } | null }`. A file reaches the composer through the picker button, a drop on the panel, or a paste, and **is uploaded when it is added, not at send** (`POST /conversations/{id}/attachments`, one part named `file`): a draft's conversation is created first, through the same serialized path a first send takes, so the send that follows reuses it. Each file is a chip — name, size, an image's thumbnail, uploading, or failed with the reason — and Remove only drops it from the message, since the agent has no route to delete an upload. **What the capability document's `attachments` rules out is refused before anything is sent**, on the chip, naming the limit: over `maxBytes`, a type outside `mediaTypes` (`type/*` is every subtype), more than `maxPerMessage`. The part's declared type is the browser's when the agent takes it, else the extension's (`.yaml`/`.yml` → `application/yaml`, `.json` → `application/json`, `.md` → `text/markdown`, `.csv` → `text/csv`, `.sql`/`.log`/`.txt` → `text/plain`). An agent's refusal is read by its `code` into words with the limit it carries, the server's own `{ error: { code, message, data } }` envelope included. Submit is held while a file uploads and until a failed one is removed or retried; files alone are a message. The uploaded ids go on `POST /chat` in chip order, the queue carries them with its text (Edit returns both, a further submit appends both, and one that would pass `maxPerMessage` is refused under the composer), and **storage keeps descriptors (`id`, `name`, `mediaType`, `size`), never bytes** — a file still uploading, or failed, at a reload or a conversation switch is dropped. A user bubble's files come from its `user-message` record (and from the send itself while the bubble is still local): an image is a thumbnail read through the client with the bearer token — the route answers `application/octet-stream`, so the record's `mediaType` types the Blob — as an object URL revoked when the bubble leaves, fetched once it is in view, opening larger in a dialog, and falling back to a named chip when the read fails; any other file is a chip that downloads it under its name. Retry and Edit & resend send the original message's ids again; Copy and the Markdown export list the names.

**An entry point into the agent writes the composer and never sends.** All of them call the context's `compose`: it appends the prepared text after what is already there, opens the panel and focuses the composer. They are "Fix with AI" on a diagnostic (the popover behind every diagnostic badge, the notes under a form field, and a quick fix on a marker in the source view), "Ask AI" on a module-canvas node's menu and in the detail panel's header, and "Explain this failure" in the run dock (the failure the dock shows, plus the last 40 lines / 4000 characters of output it holds). The text names files by their workspace-relative path — the bridge's `workspaceFile`, the inverse of `editorFile`. Entry points read a narrow context of their own (`useAgentCompose`), null wherever the shell does not offer the panel (`setPanelAvailable`, the same condition as the top bar's toggle), so they are hidden exactly where the toggle is and a canvas node is not re-rendered by a streaming turn.

**A selection in an editor goes with the next message, shown before it is sent.** The source view's editors and the detail panel's YAML pane report their selection to the agent context (`setEditorSelection`, keyed by the editor so one editor's empty selection does not drop another's; the pane's is mapped back to its document's lines), and the composer shows it as a chip — `<file>:<start>-<end>`, opening the file there, with Remove. Submitting sends or queues it with the message and drops it; it comes back only with a new selection, so one selection is never sent twice, and a selection alone is no message. The live selection is never stored, and it is held outside React state (`agent/editor-selection-store.ts`, read with `useEditorSelection`): an editor reports every step of a drag, and a state change in the agent provider re-renders every agent consumer, the editor included. **A queued message keeps its selections beside its text** (`selections`, written into the text as blocks only when it is sent), so it is stored with the queue, and Edit — or a turn that ends without sending it — returns them to the composer as chips, never as block text. **It travels in the message TEXT as a fenced `telo-selection <file>:<lines>` block** (`agent/editor-selection.ts`, the block's one writer and reader), like `telo-questions` in a reply: every agent reads it as a quoted excerpt with no route or feature behind it, and every other client shows a code block. The user's bubble and the queued preview draw a parsed block as the same chip, and Edit & resend edits what was typed and sends the selections again.

**With no workspace open, the closed-workspace screen takes the request itself** — wherever the panel's toggle is offered, and nowhere else. The usual ways to open a workspace come first and say nothing of the agent — "Open a workspace", with "Start from a starter" as the one primary action — and under an "or" divider follow "What do you want to build?", one composer card and the starter prompts as a grid (one fills the input). Submitting opens the browser-stored workspace — on the desktop build too, with whatever files it already holds — opens the panel, and sends the text to that workspace's conversation. This one sends, because the user wrote it; the text is held in memory only, and stays in the input when the workspace could not be opened. **An open workspace with no module shows the same request input**, sending in that workspace, under "This workspace has no modules yet" and its primary "Start from a starter" (hidden while editing is paused; shown without the agent too). **The send waits until the workspace's conversation is settled** (`sendOnOpen`): the conversation resolved and no transcript read in flight, since the transcript that replaces the draft would wipe a bubble sent before it. A conversation found with a turn running takes the request as its queued message, an archived one leaves it in the composer, and a workspace closed first drops it.

**An empty conversation claims only what the capability document says**: `manifestRuns` true or false and `auth: "none"` become one line, and an agent whose document is unknown or carries neither shows none. Its starter prompts are four fixed requests (`agent/starter-prompts.ts`), each written the way a request the agent can act on is — routes, storage, refusals and tests named; picking one replaces the composer's text — the one writer that does not append, since a starter is a whole request.

**Other clients are seen by revision, not by push.** While the panel is open and the document visible, the open conversation's `revision` is read every 5 s and on focus; a change replaces the transcript from the records route (re-attaching a running last turn), and a revert another client recorded is applied to the editor's files on that read, as on every records read — except under a turn of this client's, where only the title and archive state move and the transcript is re-read once its stream ends. 410/404 leave for the most recent remaining conversation with the reason shown. A truncation carries the revision its turn count was shown at, so a 409 `ERR_CONVERSATION_CHANGED` re-reads and applies the confirmation rule again to the re-read transcript: Delete from here asks with the new count, Retry and Edit & resend ask only when later turns would go (or their turn is gone) and otherwise run at once. A turn's `conversation-title` record names the header live (a failure is a muted notice on the turn), and a `context-summary` is drawn after the last turn it covers, expandable to the summary; an export (JSON: the records route's turns verbatim; Markdown: what the model received) is composed here from `GET /conversations/{id}` and the records route.
