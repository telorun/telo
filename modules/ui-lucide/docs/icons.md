# Lucide glyphs

## `UiLucide.Icon`

```yaml
kind: UiLucide.Icon
metadata:
  name: settingsIcon
name: settings
```

| Field | | |
| --- | --- | --- |
| `name` | required | the glyph's name in the Lucide set, as [lucide.dev/icons](https://lucide.dev/icons) lists it — `house`, `settings`, `chart-line` |

The kind extends [`Ui.Icon`](../../ui/docs/icons.md), so it goes wherever an
icon does: a navigation entry's `icon` declares one inline or names one by
reference. It provides the glyph's SVG file, which `ui-react` serves under its
content digest and draws as a mask in the colour of the entry's text.

A name outside the set is a `SCHEMA_VIOLATION` at `telo check`, on the line
writing it, and the application does not start. The message names the nearest
glyphs rather than the whole set (`/name must be one of 1943 allowed values;
did you mean 'house'?`).

An icon used once is declared inline, where the entry names it — `name` is the
kind's own field, so this is a declaration, not a reference:

```yaml
navigation:
  items:
    - type: page
      page: !ref home
      icon: { kind: UiLucide.Icon, name: house }
```

An icon several entries share is declared once as a named resource and each
entry references it with `!ref`. An application writing an icon inline declares
`requires: { telo: ">=0.121.0" }`: an earlier runtime reads `{ kind, name }`
there as the removed form of a reference and refuses it.

## The glyph set

The module ships every glyph of one Lucide release, staged from the
`lucide-static` package of that release through the module's `sources:` block,
each file pinned by its digest, with Lucide's ISC license (and the MIT license
of the glyphs derived from Feather) as `notices/lucide.LICENSE`. They ship in
the module's `assets` layer; an application reads only the files its icons
name, so its check and start time do not depend on the size of the set.

In a checkout, a glyph is fetched and verified against its pin the first time
an application reads it; `telo release stage --module modules/ui-lucide`
stages them all.

## Updating the set

`telo.yaml` is generated by `scripts/generate-ui-lucide-module.mjs`: it reads
the Lucide version the workspace's `lucide-react` resolves to in
`pnpm-lock.yaml`, lists the glyphs of that `lucide-static` release, writes one
`sources:` entry per glyph and the same list as the enum of `name` — so the
names a manifest may write and the files the module ships are one list — and
pins every entry with `telo release stage --pin`. Never edit `telo.yaml` by
hand; after `lucide-react` moves, run the script again.
