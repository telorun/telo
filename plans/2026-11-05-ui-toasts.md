# Toasts for declarative UI

## Problem

A page has no way to say "it happened". A call draws its answer in place (`result:` / `failure:` trees), which is right for a state but wrong for an event: after a row call archives a record, the refresh drops the row and its drawn answer with it — the user sees the row vanish and nothing else. There is no Undo, no "Saved" after a dialog closes, no word when the renderer's event stream is lost. Component authors have no host call to report an event either.

## Constraints

None.

## Surface

**Added**

- `Ui.Notify` — an effect kind (extends `Ui.Effect`) `{ text, tone?, link?, call? }`: `text` a `Ui.BoundText`, `tone` one of `info | success | warning | danger`, `link` `{ text, to }`, `call` a `Ui.MutationCall`.
- `Ui.MutationCall.onFailure` — a list of effects run when the call does not succeed, over `error` and `input`.
- `Ui.Form.onSuccess` / `onFailure` — lists of effects run after the form's default write to its `record`.
- `UiReact.App.notifications` — `{ position }`, `top | bottom` × `start | center | end`, default `bottom-end`.
- `ui_react_controls-5` — the controls contract with the layer control `Notifications`: 26 controls, eleven of them layer controls.
- Styling parts `notifications`, `notification`, `notification-text`, `notification-actions`.
- Host field `postNotification({ text, tone, link?, action? })`, returning `dismiss()`.
- Wire: the effect spec `{ type: notify, text, tone, link?, call? }`; `onFailure` on every call (`[]` when none); `onSuccess` / `onFailure` on the `form` node; `notifications: { position }` in the application document.
- Keyed texts `notificationsRegion`, `dismissNotification`, `connectionLost`, `connectionRestored`, in `Ui.Translations` and its fourteen translations.
- `modules/ui/conformance/notifications.json` — the timing, limit and deduplication rows.

**Changed**

- `Ui.Listing.delete` — takes `true` or `{ onSuccess?, onFailure? }`, each a list of effects.
- `UI_CONTROLS_LAYERS_PARTIAL` — counts eleven layer controls; a set written against `ui_react_controls-4` is `BROWSER_ENTRY_ABI_UNSUPPORTED`.

**Removed**

- `ui_react_controls-4` — no longer hosted by the renderer.

## Solution

**One principle:** a notification reports an *event*; a *state* (a read failed, a field is invalid, a copy succeeded) stays drawn where it holds. A notification never holds the only record of an outcome, so it can be dropped safely.

**A notification is an effect.** `Ui.Notify` is one more `Ui.Effect`, written in any `onSuccess` or `onFailure` list beside the destinations, and run in the list's order:

- `text` — a `Ui.BoundText` (one sentence, translated and announced as one).
- `tone` — `info | success | warning | danger`; `ui` fills `success` in an `onSuccess` list and `danger` in an `onFailure` list.
- `link` — `{ text, to }`, `to` a `Ui.Destination` as on a `link` node ("View"): a `Ui.Navigate` moves to an address, a `Ui.OpenPage` opens the page in its surface. A notification has no element on the page to anchor to, so the surface is drawn as its `compact`, else a dialog; a `Ui.Close` there is `SCHEMA_VIOLATION`.
- `call` — a `Ui.MutationCall` (Undo), `label` required: run exactly as from a row — busy while pending, its `result` replaces the button, its own `onSuccess` and `onFailure` run.

**Where effects are written.** Wherever an operation's outcome is known, nowhere else: a call's `onSuccess` (over `result`, `input`) and its new `onFailure` (over `error`, `input`) — every row action, `move`, annotation, `button` node, form `onSubmit` and Undo is a call; a form's `onSuccess` / `onFailure` for its default write to its `record` (over `input`, the record sent, plus `error`), so a form says "Saved" the same way opened from a listing and on a page of its own; and `Ui.Listing.delete` as `{ onSuccess?, onFailure? }` (over `row`, plus `error`). Bound values are resolved when posted, so a notification outlives its row and a page move: `[{ kind: Ui.Navigate, … }, { kind: Ui.Notify, … }]` shows the notification on the page moved to. A failure notification **adds to** the `failure` tree, never replaces it.

**Timing, one fixed rule (no author key):** `info` / `success` with no `link` or `call` last 6 s, paused while hovered, focused or the document is hidden; everything else stays until dismissed (WCAG 2.2.1). Every notification has a dismiss button; Escape and a swipe dismiss too. At most three are shown — a fourth drops the oldest timed one, else the oldest. An equal notification (tone, formatted text, link destination, call and inputs) is not added again; the shown one restarts its timer. Reduced motion: no movement. Pinned as rows in `modules/ui/conformance/notifications.json`.

**Placement:** one region per application, `UiReact.App.notifications: { position }` (`top|bottom` × `start|center|end`, default `bottom-end`). Below the breakpoint it spans the width at its edge, above a tab bar. It sits above every layer: a modal never makes it inert, it shields nothing.

**Accessibility:** `danger` is assertive, the rest polite; each is announced once with its button labels. Posting never moves focus; F8 reaches the region (through a modal's trap), Tab walks its buttons, Escape dismisses, focus returns.

**Renderer.** A new layer control `Notifications` (group `status`) makes the controls contract `ui_react_controls-5`, as each earlier layer control made a generation (`Navigation` the second, `Combobox` the fourth): 26 controls, eleven of them layer controls, still replaced as one unit (`UI_CONTROLS_LAYERS_PARTIAL` counts eleven), so a set implementing the ten of `ui_react_controls-4` is refused. The renderer hosts `ui_react_controls-5` alone, as it hosts `-4` alone today. The control is fully controlled — the renderer owns timers, the limit and deduplication and draws each item's parts (`notification-text`, `notification-actions`); the control owns `notifications` (at the end of `<body>`, `data-telo-layer`), `notification` (`data-state`, `data-tone`), announcements, F8, Escape and swipe. `ui-react-radix` implements it with Radix Toast, its set and theme moving to `ui_react_controls-5`. The renderer posts two notices of its own: `connectionLost` (warning, when the event stream fails to reopen; withdrawn at the next `hello`) and `connectionRestored`. Components post through a new host field `postNotification({ text, tone, link?, action? })`, returning `dismiss()`.

**Wire.** An effect spec `{ type: notify, text, tone, link?, call? }`, `tone` always present, `link` `{ text, to }` with `to` a `Ui.DestinationSpec`, `call` a call spec; every call carries `onFailure` beside `onSuccess`; a `form` node and a listing's delete carry `onSuccess` and `onFailure`; the application document carries `notifications: { position }`. New keyed texts, in `Ui.Translations` and all fourteen translations: `notificationsRegion`, `dismissNotification`, `connectionLost`, `connectionRestored`.

## Example

```yaml
- type: button
  label: Archive
  mutation:
    kind: Ui.Mutation
    inputModel: !ref ProjectRef
    outputModel: !ref ProjectSummary
    url: { path: "/api/projects/{id}/archive", pathParams: { id: !cel "input.id" } }
    refreshes: [/api/projects]
  inputs: { id: !cel "params.id" }
  onSuccess:
    - kind: Ui.Notify
      text: { text: "{$name} archived.", values: { name: !cel "result.name" } }
      call:
        label: Undo
        inputs: { id: !cel "result.id" }
        mutation:
          kind: Ui.Mutation
          inputModel: !ref ProjectRef
          url: { path: "/api/projects/{id}/restore", pathParams: { id: !cel "input.id" } }
          refreshes: [/api/projects]
        onSuccess: [{ kind: Ui.Notify, text: Restored. }]
  onFailure:
    - kind: Ui.Notify
      text: { text: "Could not archive the project: {$message}", values: { message: !cel "error.message" } }
```

## Decisions

- **A notification is an effect, not a key.** It sits in the same ordered list as the destinations, so "go there, then say so" is two entries and a later effect kind joins with no new key.
- **Notifications are declared, not returned by the API** — a server-supplied text would be unchecked and untranslated; a page binds `result.<field>` when it wants the server's words.
- **Content is a text, not a node tree** — a live region cannot announce a layout, and a tree would open a second layout surface.
- **Undo is a call, never a link** — a destination never runs an operation. The call is the `Ui.MutationCall` every other trigger holds, refused the same way (`CONTRACT_INPUTS_MISMATCH`, twin `ERR_UI_MUTATION_CALL_INPUTS_INVALID`).
- **Tone is a plain enum, not kinds and not `style`** — it changes behaviour (politeness, timing), not keys.
- **No author `duration`** — it would let a timer sit on an actionable notification; the rule derived from tone and buttons meets WCAG 2.2.1 for every manifest.
- **One app-level region, not a page node** — notifications must survive navigation and share one announcer and stack.
- **A layer control in the one-unit set** — a region outside the stack that draws modals would be made inert by them.
- **A form's notifications are the form's, not its opener's** — the write is the form's wherever it is placed, so one declaration serves a form opened from a listing and one on a page.
- **Reads, chat and copy do not post** — a query node keeps its `failure` tree, the chat draws outcomes in the transcript, the copy button keeps its local check glyph and announcement.
- **No new `UI_*` rule** — every refusal is the generic machinery: `SCHEMA_VIOLATION`, `REFERENCE_KIND_MISMATCH` for anything but an effect in an effect list or a destination at `link.to`, the path-template codes, `CEL_UNKNOWN_IDENTIFIER` (e.g. `result` in an `onFailure` list), `CONTRACT_INPUTS_MISMATCH`, `MESSAGE_PLACEHOLDER_UNBOUND`, the cycle refusal for a call leading back to its own mutation; the body-read rule counts an effect reading `result`.
- **No `requires:` floor** — only keys on `ui`'s own kinds, delivered in its artifact.

## Verify

- A row archived and refreshed off the list still shows its notification and a working Undo; Undo's own `onSuccess` posts "Restored.".
- `[{ kind: Ui.Navigate, … }, { kind: Ui.Notify, … }]` shows the notification on the page moved to.
- Five posts show three; a repeated failure shows once; an `onFailure` notification is drawn beside the call's `failure` tree, which stays.
- A form's default write with `onSuccess: [{ kind: Ui.Notify, text: Saved. }]` posts it from a listing's opened page and from the same page reached by its address.
- Omitting `notifications` gives the same application document as `{ position: bottom-end }`.
- A notification above an open modal dialog is read and pressed with both control sets; F8 reaches it with a modal open.
- A ten-of-eleven layer set is refused; a copy press leaves the region empty.
- `result.name` in an `onFailure` list is `CEL_UNKNOWN_IDENTIFIER`; an Undo `call` without `label` is `SCHEMA_VIOLATION`; `{ kind: Ui.Dialog }` in an effect list is `REFERENCE_KIND_MISMATCH`.
