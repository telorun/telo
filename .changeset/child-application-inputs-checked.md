`telo check` follows a child application's source and holds what a resource hands it to the child's declarations. A new annotation, `x-telo-application-source: { variables?, secrets?, ports?, needs? }`, marks the top-level string field naming the application a resource runs, each key a JSON Pointer to the map feeding that block of the child. The loader resolves the source as it resolves an import and loads the child's graph (`LoadedGraph.applicationSources`); the analysis then reports, at the field, `IMPORT_UNRESOLVED` / `INVALID_IMPORT_SOURCE` / `INVALID_IMPORT_TARGET` for a source that cannot be obtained or is not a `Telo.Application`, `APPLICATION_INPUT_UNDECLARED` for a map key the child does not declare, `SCHEMA_VIOLATION` for a literal its declaration refuses (an expression is typed against it — for a resource declared at the top level only: an expression handed to a child declared in a `with:` scope or inline in a step is not type-checked against the child's declarations, while its literals are), and for a need `REFERENCE_KIND_MISMATCH` (a `!ref` to anything but a need or fulfilment of the child's type), `NEED_FORWARD_INCOMPATIBLE` (a need stating less than the child's) and the field-map refusals. A resource is judged wherever it is declared — at the top level, in a `with:` scope, or inline in a step. A durable directory forwarded whole to two child applications, or to a child application and a library import, is `NEED_DIRECTORY_FORWARDED_TWICE`. The child declarations reach the analysis beside the flattened set, as `AnalysisOptions.applicationSources` (`collectApplicationSources(graph)`), and the loader recognises an annotated kind by resolving each resource's kind through the declaring file's imports. A malformed annotation is `APPLICATION_SOURCE_ANNOTATION_INVALID`. The kernel's load runs the same analysis, so such a run is refused before anything starts, and its analysis cache covers every child file.
