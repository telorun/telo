**A rule reads an accessor field as its binding.** In `x-telo-resource-rules` and `x-telo-referrer-rules` alike, every declaration a rule binds — `self`, `this`, a declaration reached through `resolve:`, `referrer`, `peers`, `entry`, and an inline declaration beneath any of them — is read with each `x-telo-eval: accessor` field as what its controller receives: `{ root, path }` for a `!cel` chain, `{ value }` for a literal. Before, such a field read as an expression not known until creation, so every rule reading one, and every `resolve:` or `peers:` over a collection whose entries hold one, reported `RESOURCE_RULE_SKIPPED` / `REFERRER_RULE_SKIPPED` and never ran. A skip remains for a value that really is computed: an expression in a compile- or runtime-evaluated field the rule reads, one in an entry's own data beside a reference, and an accessor field holding anything but a plain chain or a literal. BREAKING for a rule that read a LITERAL at an accessor field: it now reads `{ value: <literal> }` rather than the literal itself. The binding is written by one function, exported from the analyzer as `withAccessorBindings`, which the kernel now delivers a controller's accessor fields with (what a controller receives is unchanged). In a template body's entry, an accessor field holding an expression that reads only `self` is read by a rule as a literal of unknown value — `{ value }`, never `{ root: "self", … }` — so a rule reading that inner value is skipped.
