A kind that `extends` another without `base:` is now judged by its ancestors' `x-telo-resource-rules` and `x-telo-referrer-rules` as well as its own; before, declaring any rule of its own silently dropped every inherited one. A child adds rules and never removes one: a resource rule whose `code` it inherits, or a referrer rule with an inherited `code` under the same `referrer:` filter, is refused at the child as `RESOURCE_RULE_INVALID` / `REFERRER_RULE_INVALID`. Each rule is judged as its declaring kind's — its module calls resolve there, and a rule that fails to evaluate is reported at that kind's declaration. A `base:` child still inherits no rule. A bare `!ref` a rule reads past now resolves in the module that wrote it, so a rule over a declaration from another module no longer reports `RESOURCE_RULE_SKIPPED` / `REFERRER_RULE_SKIPPED` when the application declares the same name. A rule's `resolve:` pointer crossing into a declaration another module wrote now continues through that declaration's own references in that module — its imports, and the declarations it does not export — so a rule relating a resource to an exported resource whose model the library keeps to itself (a `DataModel.Collection` relation into another module's collection) is judged by `telo check` instead of reporting `RESOURCE_RULE_SKIPPED`. A binding typed from the resource's referrers (`x-telo-context-from-referrer`) is typed by one referrer at a time, so a defect only one referrer's type makes is reported once, naming that referrer, instead of once per mixed combination.
