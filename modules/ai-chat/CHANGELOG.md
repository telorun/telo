# Changelog

## 0.3.0 - 2026-11-09
### Added
* Chat.Conversation takes an optional titles: { model }, an Ai.Model that names untitled conversations: as a turn ends on a conversation with no title, the model writes a three-to-six-word title from the user's message and the reply, before the turn's final event, so a client reading the conversation at the turn's end sees it. A title already set, a rename included, is kept, and a failed title call is logged without failing the turn.
### Fixed
* The telo requirement that static checking cannot see is now a `restrictions:` entry carrying its reason, and `requires.telo` holds the measured floor.

## 0.2.0 - 2026-11-06
### Added
* An uploaded file belongs to the conversation that first sends it. POST /attachments answers { id, mediaType, size } with no address; the first admitted turn naming the upload binds it to its conversation in the admission's own write, a turn naming one that is unknown, expired, deleted or held by another conversation is refused at /body/attachments/<i>, and one naming an id twice is refused at /body/attachments. A file is read only at GET /conversations/{conversationId}/attachments/{attachmentId}, and an attachment's url in entries and journaled events is the relative reference conversations/<id>/attachments/<attachment id>; reading it under another conversation, pending, deleted or by an unknown id is one 404 ERR_CONVERSATION_ATTACHMENT_NOT_FOUND, and the flat GET /attachments/{id} is gone. Deleting a conversation makes its files unreadable at once and touches no other conversation's. Uploads no message sent within Chat.Conversation attachments.pendingRetention (24h when omitted; zero or less refused as AI_CHAT_PENDING_RETENTION_NOT_POSITIVE) and deleted conversations' files are removed by AiChat.AttachmentExpiry, which the application schedules. A file's name is kept in its record, not as a second blob.
* Chat.Api's events and upload routes are built from public kinds (Stream.Map, Stream.Recover, Sse.Encoder, Multipart.ReadPart), so its whole body names only kinds an importer can name and can be copied into an application's own library. Frames are byte for byte as before, except that a failure carrying no code ends the stream with code INTERNAL_ERROR, and an upload with no file part is a 400 ERR_MULTIPART_PART_MISSING with its issue still at /body/file. A part sent as application/octet-stream reaches the detector as sent. StartTurn, ListConversations, ReadConversation, ConversationEntries, UpdateConversation, DeleteConversation, PutAttachment and GetAttachment declare the store codes they pass through.
* Media a model or tool produces is registered bound to its turn's conversation before its bytes are stored, so the conversations/<id>/attachments/<attachment id> address a content event carries reads while the turn is still running, whether or not a later message is stored, and no expiry pass removes it however long the turn runs; a superseded turn's media is refused at registration.
* New module: a chat server over a streaming AI agent. AiChat.Conversation publishes what the endpoint offers (the media the model accepts with the tighter size bound, and the operations branch and cancel); transport-neutral invocables start a turn, stream its journaled events from any position on any replica, cancel it from anywhere, list, read, rename, archive and delete conversations, and store and read attachments; AiChat.Api mounts them on an HTTP server as the conversation contract, with Server-Sent Events that resume from Last-Event-ID, streamed multipart uploads checked against the accepted media, and problem documents. GET /conversations speaks the collection contract against Conversation.conversations: title.contains, archived, sort by updatedAt or -updatedAt, limit 1 to 100 and cursor, anything else refused as ERR_INPUT_INVALID with its issue under /query; reading, renaming, archiving and deleting a conversation are served whatever the spec lists. A turn whose writer died or was shut down closes with an error and a failed ending, a retried send under one idempotency key starts one turn, and a client may send again as soon as it has read a turn's end. The journal's retention applies only while the application runs RecordStream.JournalExpiry on a schedule.
