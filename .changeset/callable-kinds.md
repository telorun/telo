Functions become declarable. `Telo.Callable` is a new capability — a synchronous `call(args)`, deliberately outside `Telo.Executable`, so a step's `invoke:` naming one is refused by `telo check` (`REFERENCE_KIND_MISMATCH`) and by the kernel (`ERR_RESOURCE_NOT_INVOKABLE`). `Telo.Function` is a new built-in kind for a function written in CEL: `params`, `returns` and a required `body: !cel "…"`, with a closed schema, so `deterministic:` on one is a `SCHEMA_VIOLATION`. A body is typed against its parameters, so `value.amont` is `CEL_UNKNOWN_FIELD`; the new `x-telo-context-parameters-from` annotation is what brings an ordered parameter list into a field's CEL scope, and it REPLACES the kernel globals there — a body reading `variables`, `secrets`, `resources`, `ports`, `module`, `steps` or `request` is `CEL_UNKNOWN_IDENTIFIER`, while catalog functions and module calls stay reachable.

A callable `Telo.Definition` or `Telo.Abstract` declares a signature — `params` (an ordered list of `{ name, schema, description?, nullable?, optional? }`) and `returns` (`{ schema, description?, nullable? }`) — layered like an invocation contract: the instance, then the nearest declaration along `extends`, replacing rather than merging. `schema` is JSON Schema in which `!ref <Shape>` resolves at the root and at any depth, on a kind document as on an instance; the rest of a kind document keeps its references unresolved. A native kind may claim `deterministic: true` when it declares its own `controllers:`, and a callable abstract may require it.

New diagnostics: `CALLABLE_DEFINITION_INVALID` (a callable kind holding a non-callable, non-type slot; declaring `x-telo-eval: runtime`, `status:`, a zone annotation, `x-telo-scope`, a step body or a template body; extending `Telo.Function`; `deterministic` non-boolean, declared without its own `controllers:`, or claimed over a slot whose abstract does not require it; a controller-inheriting child redeclaring a signature; a signature or `deterministic` on a kind that is not callable), `X_TELO_REF_CALLABLE_UNTYPED` (a slot constrained to bare `Telo.Callable`), `FUNCTION_OPTIONAL_NOT_TRAILING` and `FUNCTION_TYPE_NAME_FORM` (a bare shape name, repaired with `!ref`). The kernel refuses the same kinds at registration with `ERR_CALLABLE_DEFINITION_INVALID`, reading the analyzer's rules. `CONTRACT_NOT_SUBSTITUTABLE` extends to signatures replacing a callable abstract's: parameters contravariant and positional, the result covariant, arity, and determinism the abstract requires. `x-telo-sensitive` inside a signature stays `SENSITIVE_ANNOTATION_MISPLACED`. A slot constrained to a function kind that declares no signature of its own — `Telo.Function` among them — is `X_TELO_REF_CALLABLE_UNTYPED` like bare `Telo.Callable`. A `!ref` in a signature that names nothing, at the root or nested, is `CONTRACT_TYPE_NOT_FOUND`, refused by the kernel at registration too. An instance takes `params` / `returns` as its signature only where its kind's schema declares them, and `deterministic` on an instance of a function kind is `CALLABLE_DEFINITION_INVALID`. Parameter names go through the naming rules (`INVALID_NAME`, `NAME_CASE_CONVENTION`). The kernel's `ERR_CALLABLE_DEFINITION_INVALID` message names each clause by its analyzer code and path.

A kind's `inputType` / `outputType` naming a shape with `!ref` now resolves in the module that declared the kind — it was left unresolved, so the kernel refused the contract at dispatch with `ERR_CONTRACT_UNRESOLVABLE` while `telo check` said nothing — and one naming nothing is `CONTRACT_TYPE_NOT_FOUND`. A consumer's analysis now carries a library's own shapes that the library's contracts and signatures name, so `CONTRACT_NOT_SUBSTITUTABLE` compares a child against an imported abstract's named shapes rather than passing by comparing nothing. `throws:` on a callable is refused by `THROWS_ON_NON_DISPATCH_CAPABILITY` and the kernel's capability branch.

The kernel binds a contract's `!ref <Shape>` to the shape in the module that wrote the reference, on a kind and on an instance. It looked the shape up by its bare name, which every module declaring a shape of that name registers, so a library declaring `Money` and importing a library that exports another `Money` had its results checked against the import's — `ERR_OUTPUT_INVALID` on a value `telo check` accepted. A shape's CEL `rules:` apply through the same resolution.

A `Telo.Abstract` with `extends` now defers registration until its ancestor is loaded, as a `Telo.Definition` already did, so one whose `extends` names no kind fails at boot; `telo check` reports it at the abstract as `EXTENDS_MALFORMED` / `EXTENDS_UNKNOWN_TARGET`, which it previously checked on definitions only.
