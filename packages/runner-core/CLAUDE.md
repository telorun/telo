# Runners — package guide

Loaded when working under `packages/runner-core/`. Also the guide for `apps/docker-runner/`; k8s-specific rules (routing seam, infrastructure error summaries, the Helm chart) are in `apps/k8s-runner/CLAUDE.md`. Repo-wide rules live in the root `CLAUDE.md`.

**Runners** — `packages/runner-core` (the backend-neutral `/v1` session contract, routes, registry, ring buffers) plus `apps/docker-runner`, `apps/k8s-runner` and the CLI's own local-process backend behind the `RunnerBackend` seam.

**A backend is hosted by the artifact that owns its substrate.** The docker backend lives in the image that fronts a docker socket, the k8s one in the deployment that holds the API credentials, and the local-process one in `telo` itself — a local run IS `telo run --watch --inspect`, so any other host would put a supervisor beside the thing it supervises and make them agree on an unwritten protocol. What is shared is the contract, not the substrate: core's routes, lifecycle and registry know nothing about an executable, a process group or a container — the session supervisor this package also builds is reached only through its protocol (`specs/supervisor-protocol.md`), by the container backends.

## The session config is the runner's, not the contract's

`SessionConfig` and `ProbeConfig` are opaque bags (`Record<string, unknown>`). They used to declare `image` and `pullPolicy` — container vocabulary in the backend-neutral contract, which only stayed invisible while every backend ran containers, and which the third one exposed. The runner is the authority on its own config surface and already said so twice: `config.schema` on `/v1/capabilities` is what the editor renders the form from, and `ServerDeps.validateConfig` is what enforces the same against a client that skipped the editor. **The forbidden repairs are a fake image on the local runner and a `kind: "process"` branch in core.** `container-config.ts` holds both halves of the container backends' answer — the schema they advertise and the parser they read it back with — so a field cannot be advertised in a shape the backend will not accept.

**An origin allowlist is enforced by the runner, not by the browser.** With `corsOrigins` narrowed, core refuses a request whose `Origin` is not on the list (`403 origin_not_allowed`) instead of only withholding the CORS header — a client that ignores response headers is otherwise unaffected by CORS, and a local runner starts workloads for whoever reaches it. A request with NO origin is left alone (every CLI and health check sends none; the transport is what bounds those), while the byte channel makes the opposite call for the opposite reason — a browser always sends one on an upgrade, so a missing origin there is a rejection, closed with `4403` rather than an HTTP status a WebSocket client cannot read. The hook skips upgrades so that answer stays the io route's.

## Capabilities are enforced, not just published

`features.io` reaches the Run route from the same capabilities document the client reads (`server.ts` passes `capabilities.features.io` into the session routes). `io` is chosen per Run, and one the runner does not serve is refused with `400 io_unsupported`. **Never silently downgrade a `tty` request**: `isatty()` drives colour, buffering and prompts, so a run that claims a terminal it does not have is a lie the application can detect. The same rule governs terms (`428 terms_required`).

**`identity` is built by core from the configuration that verifies it** (`RUNNER_IDENTITY_AUDIENCE` + `RUNNER_IDENTITY_ISSUERS`, `identity/`): `buildServer` adds the RFC 9728 metadata to whatever capabilities the backend describes, serves the same object at `/.well-known/oauth-protected-resource` (and its path-inserted form), and hands the same configuration to the credential seam — so no backend can advertise an audience the runner does not verify, or verify one it does not advertise. A client checks `identity.resource` against the URL it connects to and never takes it; that check is what stops a runner from advertising another runner's audience to collect a token valid there.

**A gate that only one backend installs is a gate.** `validateConfig` is the runner's half of the config contract, and it has to be UNCONDITIONAL: k8s used to install one only when a base-image catalog was configured, so a catalog-less deployment accepted `{"image": 42, "pullPolicy": "sometimes"}` and started a pod on its default image under `missing`. The readers in `container-config.ts` throw rather than coerce for the same reason — only the gate decides what is acceptable, and a reader that substitutes a default makes the gate optional in practice.

`buildServer` takes an optional `logStream`. Pino's default destination is stdout, which is right for a container whose stdout IS its log and wrong inside a CLI, where stdout is the machine surface — `telo runner` passes stderr.

## The telo version is the contract's; how it is obtained is the backend's

**An application may name the telo version it runs on** (`telo` on a `SessionAppSpec`): the version its module is edited against, so what checks a manifest is what runs it. It sits in the contract and not in `config` because every backend runs *a* telo — what differs is how each gets one, which stays behind the seam. **Never a substitute**, on any backend. `features.teloVersions` is advertised by a runner that honours the field and enforced like `io` — a version sent to a runner without it is `400 telo_version_unsupported`.

**Refused before the app set is accepted only when the answer is cheap and certain; fetched inside the workload creation otherwise.** Versions are judged when an app set is created (`POST /v1/sessions`) or replaced (`PUT …/apps`), because that is when an app's image is chosen. `RunnerBackend.supplyTelo(version, config)` is asked before the set is accepted and returns why a version can NEVER be run here (`400 telo_version_unavailable`, with `{ app, version, reason }`): an unreleased build identity nothing can supply, a platform no binary is published for. Core itself adds one refusal on every backend (`400 telo_version_unavailable`): a release older than `MIN_SUPERVISABLE_TELO`, because what a runner asks of a telo — `--watch --no-input --inspect --no-open` before the path, a finished generation reported on the debug stream, the workspace marker — is the contract's. That floor is the oldest release VERIFIED BY EXECUTION, not the point where it breaks; lower it only by running the candidate. It is `0.123.0`, the release whose `telo run --watch` takes no hold of its own, so a one-shot app's generation runs to teardown and emits `Kernel.Stopped` with its exit code — on an older release that generation never ends and its run is never `completed` — forward-declared until that release is published, and verified by execution then. It also carries `--no-input` (0.121.0; without it a runner's `tty` session would block on an input prompt). **The k8s base-image catalog gates `config.image` and nothing else**: it is a bounded display menu read from its own repository setting, and using it as the version allowlist refused an older pin and every version on a mirror. It must not pull or download. The slow half — a docker image pull, the local runner's release download — belongs to `create`, because that is where a progress event and the session ceilings already exist: holding `POST /v1/sessions` open for a pull shows the user nothing and gives them no session to stop, and puts the global ceiling after a fetch it would then refuse. A fetch that fails there is a `failed` session on the stream, carrying the same reason.

**The runner's own containers stay on the operator's kernel.** A session's `workspace` container runs the runner's manifest, verified against the kernel the runner ships with, so on both container backends it runs on the operator's image (`RUNNER_IMAGE`) and only the applications follow `telo` (docker: an `app-<name>` container on that version's image; k8s: the one `apps` container runs that release's binary, fetched from `RUNNER_TELO_RELEASES_URL` into the session claim). Running it on the user's version would fail a session for a reason unrelated to the user's manifest.

**On docker, an unreleased build has no image unless the operator names one (k8s always refuses it).** `X+unreleased` is a working copy, so no registry holds it under a version tag. `RUNNER_TELO_UNRELEASED_IMAGE` names the kernel image built from that same tree — a development stack, where the editor's bundled engine is itself unreleased — and without it the refusal says so and names the variable. The reported version still exposes a wrong mapping.

**One answer per session to "who chooses what runs".** Either every app names its version or none does (`400 invalid_telo_version`), and a container backend refuses `config.image` beside a version (`400 invalid_config`) — which is why `validateConfig` is told whether the request names one (`ConfigGate`). **What a version supersedes is advertised, not inferred** (`config.supersededByTelo` on the capability document): a client leaves out exactly those properties, rather than everything marked `deprecated`, which says a field is on its way out and nothing about why. And **the feature and the seam are one statement**: `buildServer` refuses a runner that advertises `teloVersions` over a backend with no `supplyTelo`, which would otherwise accept every version and run what it pleased. `image` is deprecated, not removed: a client naming no version still sends it and gets exactly the old behaviour, and the advertised schema marks it `deprecated: true` so a form can leave it out. **`pullPolicy` went with it, to the operator** (`RUNNER_PULL_POLICY`): a version tag does not move, so `always` buys a run nothing, and `never` describes a deployment whose images are preloaded rather than a choice someone makes per run. It is refused beside a version rather than ignored — a field a runner accepts and does nothing with tells its sender something false — and applies to every image the runner chooses itself, its own workspace container's included.

**The runner reports the version; it judges nothing.** `Kernel.Starting` carries the runtime's own version, the projection passes it on as `telo` on that generation's `run` `started` event, and nothing compares it: by the time the frame arrives the manifest has loaded on that runtime, so stopping it would undo nothing. The editor compares and warns. A runtime from before the field reports none, and the event carries none.

## Sessions

**A session is a workspace, and it is the only shape.** Its workload is one pod (on the local runner, one directory and its processes): a `workspace` container, an optional co-resident **`agent`** configured by the operator (`AGENT_*` variables; the k8s runner's agent file), and one idle slot per Application (k8s: one `apps` container with a supervisor per slot, started by `supervisor --slots N`, at most `RunnerBackend.maxApps` apps, else `400 too_many_apps`). **Nothing runs until Run**: `POST …/apps/:app/run` is a process start inside a slot that already exists, under `telo run --watch`, so an edit costs a kernel reload rather than a pod. What recreates the workload (the session id never changes) is a change to the agent, and on docker also to the app set; on k8s the app set changes slots only. **No runner builds an image**, and a module cache lives as long as the session's storage. **The session seeds `telo-workspace.yaml` at the workspace root**, so the kernel anchors ONE `.telo` there for every app in it; app runs therefore carry no `TELO_CACHE_DIR`, which outranks the marker, and core drops a client-supplied one from a Run's env. `RUNNER_MAX_SESSIONS` bounds RUNNING sessions, because concurrency is bounded by simultaneous EDITORS rather than simultaneous runs, and the session settings are `RUNNER_SESSION_*`. A runner started with a retired variable (`RUNNER_WATCH_*`, `RUNNER_WORKSPACE_CHECKPOINT_SECONDS`, `RUNNER_EXIT_TTL_MS`, `RUNNER_MAX_TTL_SECONDS`, `RUNNER_APP_MAX_TTL_SECONDS`, `RUNNER_APPS`) refuses to boot, naming its replacement or saying it is gone.

**Core owns what a run means; the backend spawns, signals and reports.** Core mints the run id, builds the argv (`telo run --watch --no-input --inspect <listen> --no-open <entry>`, the `listen` address the backend's `addresses(app)` gives), merges the env, and arms ONE debug relay per process when the app reports `running`, ending it on the next `ready` — so a relay's last-event-id is fresh per process and a new kernel's `Kernel.Starting` is never skipped as already seen. Reachability is watched by core, from the host the backend names, only while the app runs. A backend's `onAppState` is the one source of the `app` events, adopted runs included.

**Ownership is one check.** A create with no identity mints a resume secret, answered once, stored as its SHA-256 (`session-credentials.ts`); every session route resolves the caller through ONE `CallerResolver` and compares owners with `ownsSession`. A missing credential is `401 session_auth_required`; another owner's session answers the same `404` as an unknown id, so an id reveals nothing. **An identity is a branch of that resolver, never a second check**: `Authorization: DPoP <token>` plus a `DPoP` proof resolves to the owner `(iss, sub)` once the RFC 9068 token and the RFC 9449 proof hold (`identity/access-token-verification.ts`, `identity/dpop-proof.ts`, keys through discovery in `identity/issuer-keys.ts`); a proof's `jti` goes through the STORE (`recordJti`), not memory, so a replay is refused across a restart, and the lifecycle tick purges expired ones. An issuer the runner cannot reach is `503 identity_provider_unavailable` for identity callers only — resume secrets never touch the issuer. Scope and `client_id` are deliberately not judged: the audience is the delegation and ownership is the authorization. Routes only an identity may use (`GET /v1/sessions`, adoption at `POST …/owner`) answer a resume secret `403 identity_required`, since a secret names one session rather than an owner; adoption carries the secret in the BODY, because `Authorization` carries the identity, and goes through the lifecycle's queue so the store changes owner before the live record does. The byte channel takes only a single-use, 30-second ticket bound to the session and the app (`io-tickets.ts`), because a browser cannot set a header on an upgrade and a credential must never appear in a URL.

## Status, run events and output

**Status, app state and run outcome are three nouns on one stream**: `status` is the session's (`starting`/`running`/`suspended`/`failed`/`stopped`), the `app` event is one app's slot (`ready`, or `running` with its `runId`), and a `run` event is one generation of one process, so a one-shot Runnable finishing leaves its app `running` until the process ends and the next edit starts generation N+1. Those `run` events are **projected from the kernel debug stream, never parsed out of the terminal** (`debug/run-projection.ts`): every run is started with `--inspect`, `Kernel.Starting` / `Kernel.Stopped` bracket each generation on the run's one debug connection that survives reloads, and a process that ends without `Kernel.Stopped` closes its open generation from the run's ending. **A debug frame over `DEBUG_FRAME_MAX_BYTES` (1 MiB) is relayed as a stand-in** carrying the event's name, timestamp and size (`payload.omitted`, `payload.bytes`), never parsed or buffered: an invocation event carrying a whole result set runs to tens of megabytes, and three of them in a row took a runner from 77 MiB to 442 MiB and its pod to `OOMKilled`. The lifecycle events the projection reads are small, so no outcome depends on a frame the bound replaces. The one thing that stream did not carry is a manifest that fails to LOAD, so the CLI emits **`Kernel.RunFailed`** (`{ phase: "load" | "start", code?, message }`) — a dotted event name inside an existing frame kind, which obliges no other runtime where a new frame kind would oblige all of them. **`Kernel.PortsResolved`** rides the same stream and carries the Application's `ports:` block re-resolved per load, so a host patches its Service/Ingress without re-parsing a manifest on the save path; it is the DECLARED set, because routing what happened to BIND would expose an undeclared port and would rest on a per-module listening convention — whether anything bound it is the reachability watcher's answer, per port. **Workload output never travels the event channel** — it goes over the byte channel, keyed `(session, app)` because each app has its own terminal, with every frame `[seq:4 BE][stream:1][payload]`; the `stdout`/`stderr` `RunEvent` variants that used to be declared were emitted by nothing and are deleted rather than qualified.

**`io` is `tty` or `streams`, chosen per Run**, and the difference is observable to the APPLICATION: `isatty()` drives colour, buffering and prompts, so an always-PTY loop hides production behaviour. Under `streams` the run's stdout and stderr stay separate, under `tty` it gets a fresh pty, and `CLICOLOR_FORCE` is injected only under `tty`. Changing it changes nothing about the workload.

## Workspace, env and ports

**The workspace surface is runner infrastructure, not agent functionality**: it is part of the `/v1` contract, so the manifest lives in `runner-core/workspace-app/telo.yaml` (`Http.Api` over `Fs.TreeSnapshot` / `TreeSync` / `File` — no new module, no `JS.Script`) and runs on the plain kernel image, delivered as a content-addressed ConfigMap on k8s and a per-session directory on docker. Hanging it off the agent's catalog image would invert the dependency and need a second implementation for the agentless case.

**The env split IS the credential boundary** — operator env on `agent` alone, session env only in the process a Run starts, neither on `workspace` and none in any workload definition: `WorkloadSpec`, `setApps` and `setAgent` carry no env at all, so session env never appears in a pod spec, and the store never holds it. Ports are unique across the WHOLE session (`400 port_conflict`), because session hosts are `<port>-<sessionId>.<domain>`, a single label carrying no app name. A port the workload binds for its own machinery (each app's supervisor and inspect ports, by position — on k8s they share the pod's network namespace with every app, and docker reserves the same positions so a port means the same on both) is the backend's to name — `RunnerBackend.reservedPorts(apps)`, asked on create and `PUT …/apps` — and refused the same way, naming what binds it; core cannot know it, since only the backend chose it.

**The workspace is `/workspace` on BOTH backends**: docker mounts each session's own `workspace` subdirectory of the shared bundle volume there (`Subpath`, Engine API 1.45 / Docker 26), so a manifest is `/workspace/telo.yaml` either way, no session id reaches a workload's paths, one session cannot read another's files on disk, and nothing is laid over a directory an operator's catalog image may already use — mounting the volume whole at `/srv` covered up the authoring agent's own installation, which is why the co-resident agent could never start there. Only the runner's own `workspace` container keeps the whole-volume bind, because its manifest and cache sit BESIDE the workspace it serves; the same siblinghood is what keeps them out of the user's file tree. An older daemon silently ignores `Subpath` and would mount everything at `/workspace`, which is why the docker runner refuses to boot on one, naming the Docker 26 requirement — with one session shape there is nothing left to degrade into.

**A runner is a HOST of the application's public addresses**, under the contract `README.md` § Public addresses states once (report mode: supply every address need from `telo needs report`; template mode: set `TELO_HOST_PUBLIC_URL_TEMPLATE` / `_SECONDARY_TEMPLATE` and route what the kernel announces). Core reads the announcement off `Kernel.PortsResolved` — each port's `publicUrls` becomes `PortMapping.publicHosts` (`debug/ports-resolved.ts`) — and names no template; which mode a backend is, and how it routes, is the backend's. Only k8s is a template-mode host; docker and the local runner set no template, so an address need comes from the session's env.

## Co-resident agent

**A co-resident agent is REACHED like an app port and REPORTED beside them**: `AGENT_PORT` (the agent file's `port` on k8s) declares the port it listens on (required at boot — the runner knows nothing about any specific app, and guessing 8080 would be exactly that knowledge), so an agent is never offered unreachable, and the `running` status carries an `agent` endpoint SEPARATE from `endpoints`, which are the ports the user's applications declared. **The advertised name IS the acceptance condition** — `features.agents` names the one agent the runner offers, and a session naming anything else is `400 unknown_agent`. **Where an app declares the agent's port the MANIFEST wins** on a create: the session starts without the agent and says so on its stream, rather than refusing to open a workspace over a container the user cannot decline; asked for on its own (`PUT …/agent`) the clash is refused (`agent_port_conflict`), and an app set declaring the session's agent port is refused (`port_conflict`). **An agent's `AGENT_TOKEN_ENV` gets a token per workload creation** (create, resume, agent change), minted by core, injected through the agent's own env and reported by core as `RunnerEndpoint.token` on `status.agent` — core rather than each backend, so no backend can publish an endpoint without the token its workload holds; the store never holds it, and an adopted workload's token is read back by the backend. Nothing verifies the agent LISTENS on the declared port — what the image binds is configured separately — so a mismatch routes to nothing. k8s needs no routing of its own — the pod's containers share a network namespace, so the port just joins the session Service and routing objects — while docker gives the agent its OWN alias (`telo-run-<sessionId>-agent`, resolved by the proxy's existing trailing-capture rule), because a shared alias is round-robined and putting the agent on the session's would make every app port a coin flip. **One validation, two readers**: `loadAgentFromEnv` (the `AGENT_*` variables) and `loadAgentFromObject` (a file a runner parsed — the k8s agent file) resolve through the same checks, each refusal naming the variable or the file key; a file is closed and names its secrets only, each read from `AGENT_SECRET_<NAME>`, so no secret sits in a ConfigMap. **The session user is the same shape**: `loadSessionUserFromEnv` (`RUNNER_SESSION_USER`, `<uid>:<gid>`) and `loadSessionUserFromObject` (the k8s session file's closed `user: { uid, gid }`) in `container-config.ts` share one validation and the default `1000:1000` — numeric ids only, uid `0` refused, gid `0` allowed — and the local runner refuses `RUNNER_SESSION_USER`, since its sessions run as whoever started it.

## Session containers

**A session's workload may start containers, and core serves it the engine to do it with** (`RUNNER_SESSION_CONTAINERS`, off by default; the k8s runner's session file `containers.enabled`): every Run of a session gets `TELO_HOST_CONTAINER_ENGINE_URL` = `<RUNNER_INTERNAL_URL>/v1/sessions/<id>/engine` and `TELO_HOST_CONTAINER_ENGINE_TOKEN`, a per-session token core mints and holds in memory (a client-supplied value of either is written over; a runner restart mints a new one for new runs, while an adopted session's live runs keep theirs — the store holds every token a live run may hold as its SHA-256, never the token, beside the session's containers), and the route answers the Docker Engine API 1.41 subset `Docker.Engine` sends — ping, image inspect and pull, container create / start / inspect / logs / list-by-label / delete — and refuses everything else. `RUNNER_INTERNAL_URL` is the runner as a WORKLOAD reaches it, which no runner can infer, so boot refuses without it; a runner enabling the setting over a backend with no `containers` seam is refused at boot too, the rule `teloVersions` / `supplyTelo` already follow. **Core owns everything common** (`session-containers/`, `routes/engine.ts`): the bearer check (401 missing, 403 forged), the create whitelist (`create-request.ts` — `Image`, `Cmd`, `Entrypoint`, `Env`, `User`, `ExposedPorts`, `Labels`, and `HostConfig.PortBindings` only as one `127.0.0.1` binding with an empty `HostPort` per exposed port; anything else is a 400 naming the full field path), the forced `run.telo.session=<id>` label, the per-session ceiling (`RUNNER_SESSION_CONTAINERS_MAX`, 429 beyond it), and scoping — a container id another session created is a 404, and a list shows the session's own. **A backend only runs what it is handed** (`SessionContainerEngine` on `RunnerBackend.containers`): a refusal only its substrate makes (a k8s non-numeric user) is `SessionContainerFieldRefused`, answered as a 400 naming the field, and a vanished container is `SessionContainerNotFound`. Its optional `endSession` is called once a session is gone for good (deleted — never a suspend, a failure or the runner shutting down), after its containers are removed, for what the backend holds per session beside them (the k8s per-session NetworkPolicies).

**The facade publishes nothing and answers the binding.** A client asks for a loopback binding with an engine-chosen port because that is how a local daemon reports an address it can reach; the facade binds no host or node port and answers inspect's `NetworkSettings.Ports["<p>/tcp"]` with the address the SESSION reaches the container at — container IP on the child network (docker), pod IP (k8s) — and the container port. One client behaviour on every engine, no mode.

**Removal follows the runs, not the client.** The workload removes its containers when it ends normally; core removes the rest on every status meaning the runs are gone — `stopped` (deleted; the engine ends), `suspended` and `failed` (the token survives for the resume) — by subscribing to the session's own event stream, and before `PUT …/apps` or `PUT …/agent` recreates the workload. **A runner shutting down removes nothing** (`preClose` only ends in-flight engine requests and finishes the store writes), because the workload that started the containers may outlive it: each session's containers and accepted token hashes are written to its record (`containerEngine`), so a session the next runner adopts keeps both, and one it does not is suspended, which removes them. A token of an earlier process stops being accepted once its runs are gone (any release). Each backend's boot sweep removes what no live session holds (docker by the session labels, k8s by the managed-by label plus the pods' owner references to the session pod).

## The session supervisor

**An app container's main process is the session supervisor, and the protocol is the only thing it shares with a runner** (`specs/supervisor-protocol.md`, generation 1; the crate is `supervisor/`, a Rust crate with no Node twin because it runs inside an arbitrary app image with no runtime in it). It knows nothing about telo: it runs the argv core builds, one process group per run, and answers idempotently by `runId`, so `SupervisorClient` settles every request across a reconnect by asking again — a `run` re-sent until answered, an ending missed while disconnected asked for with `stop`, which stops nothing that already ended. A change to a message, a field, a close code or a behaviour the vectors pin is a new generation, made in the spec, both halves and `supervisor/vectors/` together; both the crate's tests and runner-core's run every vector. The client reports what ends a connection for good as a distinct `SupervisorTermination` (`generation_mismatch` — the backend recreates the pod; `unauthorized`; `superseded`; `restarted` — a new `instance`, so the container restarted and its run is gone; `protocol_error`) and reconnects through everything else.

**One adapter, one fake, both here.** `SupervisedApp` (`src/supervisor/supervised-app.ts`) is an app slot driven through its supervisor in `/v1` terms, used by both container backends: `started` is `running`, `exited` / `failed` is `ready` with the run's ending, frames the ring lost are told on the app's output, nothing is reported before `report()` (so a workload says `running` before any app says `ready`), and `isGenerationMismatch` recognises the termination a backend answers by recreating the workload. It names no container — the backend passes the `label` its messages use (`container 'app-web'` on k8s, the full container name on docker). `FakeSupervisor` (`src/supervisor/fake-supervisor.ts`, exported ONLY as `@telorun/runner-core/test-support`, which no runner code imports) is the protocol-speaking supervisor both runners' fakes stand up; it runs no program — a run is live from `run` until `stop` (ending `SIGTERM` at once) or `end()` — and runner-core runs every exchange vector that starts no program and every runner message vector against it, so a fake that drifts from the protocol fails here rather than passing a runner's test the real supervisor would fail.

## The docker backend

**A session is sibling containers over its own directory of the bundle volume** (`apps/docker-runner/src/docker/`): `workspace`, one `app-<name>` per application and an optional `agent`, named `telo-run-<sessionId>-<role>` and found by their `telo.run/session-id` label, never by name; the runner reaches each at its address on the child network. `<sessionId>/workspace` and `<sessionId>/agent` are mounted through `Subpath` (the agent's at `/var/lib/telo-agent-state`, with `TELO_HOST_STATE_DIR` pointing at it), and suspend removes the containers and keeps the directory. **The supervisor is delivered on the same volume**: the runner's image carries it at `/opt/telo-runner/supervisor`, and at boot the runner writes it to `.supervisor/<digest>/` (`supervisor-delivery.ts`), which every app container mounts read-only at `/opt/telo-runner` with `Entrypoint` replaced by it — keyed by content so another build never overwrites what an adopted container runs, and labelled on the container (`telo.run/supervisor-build`) so the sweep keeps every build still mounted. Supervisor and inspect ports are `9330` / `9230` + position, as on k8s, so `reservedPorts` names the same set on both. **The container definition is the token's durable home**: adoption reads each `TELO_SUPERVISOR_TOKEN` (and the agent's `tokenEnv`) back with container inspect. Containers are created without `AutoRemove`, so one that ended is still there to name — at adoption it makes `adopt` throw naming it; live, `wait()` reports it as the session's failure. A `generation_mismatch` at adoption removes the containers and resolves `undefined`, as on k8s. **Every container of the workload runs as the session user, `RUNNER_SESSION_USER`, default `1000:1000`** (the kernel image's `node` user; the k8s pod's `runAsUser` / `runAsGroup` / `fsGroup`), with a writable `HOME` at `/home/telo` on its role's directory under `<sessionId>/home/` (Docker gives a uid the image's passwd lacks `HOME=/`), and every create and resume first gives the session's directory to it, re-owning only what someone else owns — the upgrade path for a session a root-run runner left — before any container exists, an entry it cannot give away failing the start; an adopted container not running as the configured user is stale, so the resume re-owns before anything writes. Containers a session starts through its engine run as their request or image says, since they run arbitrary images and mount nothing of the session. Unlike a pod's, the containers are replaced per role: an app-set change replaces the app containers and keeps `workspace` and `agent`; an agent change replaces the agent and ends every live run.

## Suspension and durability

**A session is not a pod, and not a process's memory either**: its record is in the store and its files are on its own storage, so suspending deletes the workload and keeps both, and `resume` rebuilds the workload under the same id with every app `ready`. A session suspends with no subscriber for the idle window, past its running limit (counted from when this runner process saw it running), or on `POST …/suspend`; a suspended or `failed` one is deleted with its storage after retention (`RunnerBackend.destroy`). **Every record change is written to the store before the live entry or the stream shows it** (`session/session-lifecycle.ts` queues the events behind a pending write, so a status the store has not taken is never overtaken). A write that fails is retried with a bounded backoff (100 ms, 500 ms, 2 s); one that still fails FAILS the session — its runs end, its workload is removed, its storage kept — with the store's error as the `failed` status message, the request that caused it answered `500 session_store_failed`, and the failed status written behind it; until that write lands the store keeps the earlier status, which a restart reads as a workload to adopt or suspend. At boot every record is loaded; a `running` one is adopted (`RunnerBackend.adopt`) when its workload is still there and `suspended` when it is not or the backend cannot adopt; the backend's sweep then runs with the known and live ids, sparing every known session's storage. Closing the runner detaches workloads and stops nothing that outlives it. There is no checkpoint: the workspace survives on the session's storage.

## The session store

**A session's record is durable and holds no secret** (`session-store/`): `SessionStore` is the seam, `SqliteSessionStore` (Node's built-in `node:sqlite`, `sessions.sqlite` in the runner's state directory) and `PostgresSessionStore` (`pg`, tables prefixed `runner_`) the two implementations, `openSessionStore` the selection by `RUNNER_SESSION_STORE`. A record never carries session env, workload tokens (an engine token only as its SHA-256) or an agent's operator env — each is supplied again per run or pod — and a resume secret is held only as its SHA-256. One session per owner and `workspace` is a unique constraint, reported as a typed `exists` result rather than an exception. **`node:sqlite` is reached through `process.getBuiltinModule`**, never an `import`: Vite (and so vitest) resolves `node:sqlite` as a package named `sqlite`, since it is a prefix-only builtin. The schema is versioned per backend, a migration carries every row forward, and a database at a newer version is refused. **`RUNNER_STATE_DIR` names a runner's WHOLE state directory, on every runner, never the store's alone**: the container runners keep `sessions.sqlite` there and require it with SQLite (`requireStateDirectory`); a host with a state root of its own (`telo runner`: `--state-dir`, then `RUNNER_STATE_DIR`, then the platform's per-user state directory) resolves it in its own precedence and passes the answer to `loadCoreConfig` as `stateDir`, which then wins — so the store and the session directories cannot land in two places.
