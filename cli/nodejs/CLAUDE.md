# CLI (Node) — package guide

Loaded when working under `cli/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. The release model this CLI drives (planner, ledger, workspace marker) is in `analyzer/nodejs/src/release/CLAUDE.md`; the artifact format it publishes in `kernel/nodejs/CLAUDE.md` § Layered module artifacts; the `requires:` mechanism in `analyzer/nodejs/CLAUDE.md`. The `telorun/node` kernel image is built from `cli/nodejs/Dockerfile`.

## Output seam

**Every CLI-owned write goes through the `Output` seam** (`src/output.ts`), never `console.*` and never a bare `process.stdout.write`. A global `-o, --output text|json` (default `text`) selects the encoding. **The stream split is the contract, and it is what the format rests on**: *stdout is the machine surface* — under `-o json` it carries the payload and nothing else, so `line()` (prose) goes silent there; *stderr is the human surface in **both** formats*, so `errLine()` always writes. Suppressing stderr under `json` was error swallowing: only the commands that separately collected their messages into a payload kept them, and every other failure reason vanished, leaving `{"ok":false}` with no cause. Keeping prose on stderr is also what npm, cargo and kubectl do, and it is one rule rather than a re-collection obligation on each new command.

**Two payload shapes, one serializer.** `emit()` writes a result **envelope** and is silent under `text`; `document()` writes a **bare document** and writes in *either* format, because the per-command `--json` flags (`cel`, `search`, `module versions|manifest|digest|resources|kinds`) predate `-o` and must keep working under the default. A document command's stdout is therefore *the document or empty* — it never mixes an error envelope in, because a CEL expression evaluating to `{"ok":false,…}` would be indistinguishable from a failure report; its errors are prose on stderr plus a non-zero exit.

**`telo run` is exempt from `-o json` entirely**, and the exemption is structural, not an oversight: the kernel runs in-process and `teeStdio` *copies* rather than redirects, so the app writes to these same two descriptors and **neither is the CLI's to claim**. An envelope appended after arbitrary app output is unparseable on either stream. The machine surface for a run is `--debug`, whose wire protocol is framed per event precisely because it shares a stream.

**Colour is decided per stream** (`Output.stdout` / `Output.stderr` palettes over `decideColor`), because diagnostics go to stderr while summaries go to stdout and one process-wide decision is wrong for whichever stream is redirected; stdout is never coloured under `json`, while stderr keeps its colour since it stays human-facing. **A payload write is followed by `process.exitCode`, never `process.exit()`** — on a pipe `write` is asynchronous and `exit` does not flush, so a large diagnostic set truncates into invalid JSON. `Output` takes its streams and env as constructor arguments so tests construct one over recorders (`installOutput` swaps the ambient instance) rather than spying on process globals. `yaml` is deliberately unimplemented; `-o` is an enum so it can gain the value without a second flag, and `parseOutputFormat` **throws** on an unrecognized one rather than degrading to text.

## Runtime reach

**Runtime reach is derived, never declared.** Which kernels can host a kind follows from its `controllers:` PURL candidates: `pkg:cargo` → **both** kernels (Node's `napi-loader` builds the crate as a `.node` addon, the Rust kernel's `cargo_loader` as a cdylib), `pkg:npm` and `pkg:telo/local/js` / `napi` → Node only, `pkg:telo/local/dylib` → Rust only, `wasm` → no kernel today. A module declaring `native:` also reports the platforms and ABIs those entries cover (`runtime.native`), per module rather than per kind because no kind declares which native name it uses. **`telo module manifest --json` reports it** (`cli/nodejs/src/controller-runtime.ts`) and the hub stores what it is told — the PURL→kernel mapping is loader knowledge, and a second copy in a consumer would drift silently the day a loader lands. Three invariants: it is **per kind**, not per module (`console` has Rust controllers on two of four kinds, so a module boolean would lie — the roll-up is full/partial); a controller-less kind is **`portable`**, a flag rather than an enumeration of today's kernels, which would go stale when a third kernel ships; and **language is a separate axis from runtime**, left blank for `napi`/`dylib`/`wasm` whose source language the PURL cannot determine.

## `requires:` — CLI half

**CLI half** (Node by nature): `release/verify-requires.ts` (per module, `publish` preflight — a refuted range is fatal, an unpublished upper bound is fatal, an uninstallable edge warns) and `release/check-requires.ts` (workspace-wide, batched by shared edge so a stdlib declaring one or two lower bounds costs one or two runs, wired into `telo release check`). **A FORWARD-DECLARED lower bound is a third state** (`pending`, `unreleasedEdge`): adopting new syntax means declaring the release that will carry it, so on that commit the edge names a version npm does not have — one possible outcome, arriving as an `ETARGET` wrapped in install noise indistinguishable from being offline. So the registry is asked BEFORE any edge runs (`publishedTeloVersions`, memoized) and such an edge is never spawned. The latest published version is reported beside the bound, because that is the only signal against a TYPO above the latest (`>=0.790.0` beside `0.78.0` reads wrong; "could not run" does not). Informational at `telo release check`, **fatal at publish** — npm publishes before modules, so by then the floor exists, and a module landing at the registry with a floor no runtime satisfies is a version every consumer's `upgrade` refuses. An edge BELOW the latest that is nevertheless absent (yanked) stays "could not run": guessing why it is missing would be a rule with nothing behind it. An unreachable registry classifies nothing. `telo upgrade` selects the highest version whose range accepts this runtime, walking newest-first and stopping at the first satisfied one — and **reports what it held back**, or the pin is a silent ceiling and *"up to date"* becomes the new confusing report. It short-circuits when the newest published version is already the pin: there is no candidate to choose, so the question has no bearing and asking it would cost a fetch per import on the path that changes nothing (a pin the runtime cannot read is the LOAD gate's to report — `upgrade` moves pins forward, it does not walk anyone backwards).

## Publishing

Modules get their **own Version PR** (`module-release/main`, `chore(release): version modules`), opened on every push to main independently of whether npm changesets are pending — they used to ride the changesets PR whenever one existed, which made one review cover two ledgers, and a release routinely republishes sixty modules because a shared library reached their bundles. Its body is GENERATED from `telo release status -o json` captured **before** `apply` consumes the fragments (`scripts/module-release-pr-body.mjs`): declared changes first, unattributed republishes as a table, degrading in stated stages under GitHub's 65536-character body limit — an over-long body is rejected outright rather than truncated, so the PR would open with no body at all.

**Publish is where two of the invariants are enforced.** Pins are **authored and verified, never discovered**: `telo install` / `telo upgrade` write them, and the payload builder REFUSES a remote import carrying none (it used to be fetched best-effort, so one commit produced different bytes depending on network reachability, and an unresolvable import shipped silently unpinned — error swallowing this repo forbids). Existing pins are verified against the registry; a mismatch is fatal. An in-repo sibling's pin is derived from the sibling's **own locally-built published bytes**, in topological order, so a batch is plannable offline against post-bump versions the registry has never seen. Manifest re-serialization is **unconditional** — it used to depend on whether a pin happened to be written, so one commit serialized two ways.

**The payload is built by the kernel, not staged by a package manager.** `cli/nodejs/src/bundle/module-payload.ts` is the single builder both `telo publish` and `telo release` consume; it builds every bundled controller through the kernel's own `buildControllerBundle` (`source-bundle-builder.ts`, the analogue of the Rust `napi-loader`) rather than reading the gitignored `path=` artifact. Shipped bytes and digested bytes are the same bytes by construction, the edge graph gets its metafile from the same run, and the esbuild half of 47 per-module `build` scripts plus `build:bundles` are retired (the `tsc -p tsconfig.lib.json` type-check half stays). On the publish/release path the optional-esbuild fallthrough becomes a **hard failure** — digesting a stale bundle is the one outcome the design exists to prevent.

**The index is written by the PAYLOAD BUILDER, before anything is pushed** (`ModulePayloadBuilder.buildPayload` → `Transport.layerIndex`), so `publishedManifest()` returns the bytes that ship. It used to be injected by the transport at push time, and that made the builder's manifest a document no registry holds — while a dependent's sibling pin is a hash of exactly that text, so **every module shipping a payload published a pin naming bytes nobody serves**, and 18 standard-library modules could not resolve their own dependencies at load. Nothing caught it: `payload-drift` compares layer digests, which injection does not move, and the ledger's `manifest` digest was pre-injection on both sides. What the fix requires is that a `blob` be knowable before its blob is pushed, so **layer framing is a pure function of the files** (`makeTarGz` pins every header field that is not the entry's name, contents, kind — regular, executable at mode `0o755`, or symbolic link — or link target, which is also reproducibility) and `publish` **verifies** each pushed blob against the index rather than rewriting it: the manifest may already be pinned, so a disagreement is fatal, not correctable. Framing stays the transport's (`layerIndex` is on `Transport`), since a `blob` digest covers framed bytes.

**Publish gates on bytes, not on a ledger.** A bundle inlines its dependencies, so a fix in a shared TS library — or a transitive bump the lockfile alone moved — changes a dozen modules' shipped bytes while touching no file under any of their directories and moving no package version. `telo publish` therefore builds the payload and compares each layer's `integrity` against the artifact already published at that `metadata.version` (`cli/nodejs/src/bundle/payload-drift.ts`), refusing to publish changed bytes at an unchanged version and naming the digest that moved. Exact rather than inferred: it cannot miss what no version records, and cannot fire spuriously, because identical bytes hash identically. This replaced the auto-fragment step in `version-packages.mjs`, which answered the same question by proxy. **The drift question is answered on the module track only** — `telo release status`, whose plan moves `metadata.version` in the module Version PR, so a module whose bytes moved with no bump is a pending bump there. It used to be re-asked as a `--dry-run` pass in the npm publish script, which is the one place it could only misfire: see the publication split below.

**Staged files are digested from their pins, and only publish reads them.** The builder has two modes (`stagedFiles`): `pins`, the default every release command takes, turns a file a `sources:` entry stages into a pinned entry whose integrity line is the one its bytes would produce, and gives its layer a stand-in `blob` (the hex of the integrity digest) — so a fork's cold tree and the release job compute the same layer digests, and only the never-reconciled `manifest` digest sees the stand-in; `disk`, which `telo publish` takes, reads and verifies the staged bytes and frames them. The mode is the builder's, never inferred from what happens to be on disk: deciding per tree would make one commit's `manifest` digest depend on whether `telo release stage` had run. Publish never fetches — the publish job stages first, and only what it reads: the modules it pushes and their in-repo import closure (`telo release order -o json` carries each module's `imports`), since a dependent's pin is derived from its sibling's published bytes — and `sources:` is dropped in `transformManifest` beside `include:`, before any sibling pin hashes the text. The named-file rules publish applies (which files a source may stage — a `native:` path, a platform-qualified controller `path=`, an entry an `assets:` pattern selects, a notice — a native path also named as code, a staged entry nothing names) are the analyzer's (`module-named-files.ts`), shared with `telo check`; `bundle/staged-files.ts` is only their filesystem half. Every staged path joins the partition's input the way a notice does, so a staged asset lands in the `assets` layer with no `files:` entry.

`cli/nodejs/src/bundle/payload-drift.ts` stays as the publish-time backstop and should now never fire. Registry publish is still gated on `metadata.version` movement (`scripts/publish-modules.mjs`), whose ordering now comes from `telo release order` rather than a regex over `imports:`.

**Publication is split by artifact, because the dependency runs npm → modules → images.** A module artifact is built by the workspace CLI, so the CLI ships first and modules follow. `pnpm run release` is **`changeset publish` and nothing else**; module manifests are pushed by `scripts/publish-modules.mjs` in its own workflow job, on every push to main (both its gates — version moved in this commit, version absent at the registry — are idempotent, so nothing is republished and a failed push heals on the next push). They were one script, which had the npm release decide module questions: it ran the payload-drift gate over already-published modules, and that gate demands module versions be moved BEFORE npm publishes — the inverse of the real order — so every release following a byte-changing change failed *after* `changeset publish` had shipped the packages and pushed the tags, where nothing could retry it. A second implementation of the release planner (`git diff` regexes, registry queries) also drifts silently from `telo release`, which owns those answers.

**A kernel image's existence is a function of what is on npm, not of a job's exit code.** `telorun/node:latest*` moved only when the changesets action reported `@telorun/cli` in `publishedPackages`, so *any* later failure in that run left every deployment pulling a kernel image releases behind, with nothing reporting it — and `publish-docker.yml` had no `workflow_dispatch`, so the only recovery was another release. The `context` job now also builds the release tag set when the workspace CLI version is **live on npm and has no `telorun/node:<v>-slim`** (probed with an anonymous registry token; a probe that cannot answer reports *present*, since a missed build heals next push while a false *missing* would re-tag `latest` from an arbitrary commit). `@telorun/sdk` is checked alongside the CLI because the Dockerfile's `--prod deploy` resolves it from npm and the two publish with no ordering guarantee. `workflow_dispatch` takes a `cli-version` for the by-hand case.

## The standalone binary

`scripts/build-standalone.mjs` builds the single-file `telo` executable: the CLI bundled to one script by esbuild and injected into an official Node runtime as a Node single-executable application, with esbuild's own executable riding along as an embedded asset. `pnpm --filter @telorun/cli build:standalone` builds for the host; `--target <os>-<arch>[-musl]` downloads that target's runtime instead. Released by `.github/workflows/cli-standalone-release.yml` on the same gate the kernel image uses — `cli/nodejs/package.json`'s version moving on main — with `.github/scripts/package-standalone.mjs` wrapping each binary in the formats a platform installs from, and `install.sh` / `install.ps1` at the repo root installing the archive. **The advertised command is `curl -fsSL https://telo.sh/install.sh | sh`** (`irm https://telo.sh/install.ps1 | iex`): the product's most permanent line names the product, never a git host, an org, a repo name and a branch. `telo.sh` redirects those two paths to the scripts **at a release tag** — a redirect nobody sees, to bytes that cannot move under a user, since the installer and the asset names it builds are one contract and `main` moves without the release. The site keeps copying both into `pages/static/` at build, so `telo.run/install.sh` stays a working mirror.

**The binaries are ASSETS OF THE PRODUCT'S RELEASE, not a release of their own.** `scripts/github-releases.mjs` creates `v<cli version>` on the same signal and owns its name and body; this workflow attaches files to that tag and sets neither.

**A `v<version>` release is never PUBLISHED without its installers.** It is created as a **draft**, and the standalone workflow promotes it only after every target has built and the packages have installed in containers with no Node.js. Two releases shipped assetless before this gate existed — the npm job created them, the binary build failed afterwards, and nothing connected the two. `releases/latest`, which the install scripts read, skips drafts, so a failed build now leaves the previous release standing rather than pointing users at an empty one, and the failure is visible as a stuck draft. Because both fire on one commit, either may arrive first, so the release script fills a body it finds empty rather than treating an existing release as "nothing to do" — otherwise which job won the race decided whether the release ever got a changelog. Assets are named in **Telo's own platform vocabulary** (`telo-<version>-linux-amd64-gnu.tar.gz`, `…-windows-arm64.zip`), the tokens `native:` entries and `telo install --platform` already use; native installers keep their own format's spelling (`telo_<v>_amd64.deb`), since that is the package manager's namespace.

**One command, whichever kernel is behind it.** `cli/rust` builds a binary called `telo` too, at the same version, and is not published while it hosts fewer controller formats than this one — 185 standard-library kinds ship as `pkg:telo/local/js` bundles, which only the Node kernel opens. When a build cannot host everything this one hosts, it is named for that restriction, never for the language it was written in: which kernel can host a kind is derived from its `controllers:` PURLs, so it is not a question to hand a user at download time.

**Seven targets, because those are the ones nodejs.org publishes a runtime for**: linux x64 glibc and musl, linux arm64 glibc, darwin x64 and arm64, win32 x64 and arm64. There is no linux arm64 musl runtime to inject into, so that binary cannot exist — a module may still ship a native file for the tuple, which the npm-installed CLI uses. **The musl binary is not self-contained**: the official musl runtime is dynamically linked against `libstdc++`, which a bare Alpine carries no more than it carries `libgcc_s`, so it fails to relocate until `apk add libstdc++` — which is why every check that runs it does that first, and why `install.sh` says so when the installed binary will not start.

**Three things the build decides that the bundle cannot ask at runtime.** Versions are baked (`__TELO_BAKED_VERSIONS__`, read by `distribution-versions.ts` here and `runtime-versions.ts` in the kernel) because a binary has no `package.json` — `telo --version` printed `unknown` before, and the cache keys were worse. `import.meta.url` is rewritten to the executable's own path, since the output is CommonJS. And esbuild's JavaScript API is inlined while its executable is an asset, unpacked to `<cache-root>/tools/` on first use by `src/standalone/standalone-runtime.ts` — a run that loads only published modules never unpacks it.

**There is no second code path.** `src/standalone/entry.ts` registers what the binary supplies and then imports the ordinary CLI, so a command cannot work in one distribution and not the other. What the binary genuinely lacks is a package manager, so an npm-delivered controller fails there with the kernel's actionable message; `telo check` warns about it ahead of time (`src/controller-tool-probe.ts`, the probing half of the kernel's shared tool table).

## `telo package` — an application as one executable

`telo package <manifest> --out <file> [--platform os/arch[/libc]]` writes the released `telo` binary for that platform with the application's payload inside it: the manifest, every local file its graph reaches, and the warmed import closure. **The carrier is this CLI's own version** — this executable when it IS that binary and the platform is the host's, the release asset otherwise (verified against the release's `checksums.txt`, cached under the user cache). **The asset's SHAPE is per platform and is part of the target table**, not derived at the download: Windows publishes a `.zip` holding `telo.exe` at its root (what `Compress-Archive` writes and `Expand-Archive` opens on a bare machine), every other platform a `.tar.gz` whose binary sits inside `telo-<version>-<target>/`. Assuming one shape asked the release for an asset that does not exist and reported a 404 about a Windows build that is published. The zip half is `package/zip.ts` — central directory, stored or deflated, no zip64 — because shelling out to `unzip` is not available where this runs: a single-file executable on a machine that carries no such tool. There is no `--telo-version` and no flag naming a carrier file: a carrier and the CLI inside it are one version by construction, and a flag would be the seam where they stop being — so packaging from a source checkout goes through that checkout's own standalone build, the way `telo runner` supervises the running executable. `cli/rust` owes this command, as it owes `telo runner`.

**Only a RELEASED telo may download a carrier** (`planCarrier` → `assertMayDownloadCarrier`, decided before the payload is built since it depends on nothing the build produces). A version number is not an identity for an unreleased tree — a working copy and the release of the same number are different code — so a downloaded carrier would put the app inside the RELEASE while the command claims it carries the telo that built it, and every local change under test would be silently absent. What a distribution IS is answered rather than inferred: a binary carries `build: "release" | "local"` baked by the release workflow (`TELO_RELEASE_BUILD`), and an npm package still naming `workspace:` dependencies in its own manifest is a checkout, since publishing rewrites those. A working copy may therefore package only what it can BE the carrier for — itself, built — and the refusal's remedy differs by where the reader stands, since telling a binary to build the binary it already is would be advice it has taken. This is the guard; `carrierReadsPayloads` (scanning a carrier for the reader's own magic) is the backstop under it, for the residue where a released CLI's own published binary predates the reader — which is how the feature's first cross-repo packaging produced a file that ran the CLI.

**The platform is spelled `os/arch[/libc]`, as `telo install` spells it.** `linux-amd64-gnu` is the release ASSET's name, a filename in the download namespace; two spellings of one concept on one CLI makes a user translate between them to answer one question. The **abi is never asked for and never guessed**: it is the carrier's, stated once in `src/carrier-runtime.ts` (`CARRIER_NODE_VERSION` / `CARRIER_NODE_ABI`) and read by both halves — the build injects that runtime and asserts the pair wherever it can see it, and the command warms native layers for that abi. Reading `process.versions.modules` instead was wrong precisely on the path that legitimately downloads a carrier: an npm-installed CLI has no baked values, so an operator running Node 20 packaged an app whose layers no carrier could open.

**Placement is per executable format, because one of the three refuses trailing bytes.** ELF and PE take the payload appended, followed by a 52-byte trailer (`version`, `length`, sha256, the magic `TELOAPP1`) — no absolute offset, so one reader serves both placements. Mach-O takes it in a `TELO_APP` segment, injected with the same `postject` the standalone build drives (hence a runtime dependency now) with the ad-hoc signature stripped and restored around it: data after `__LINKEDIT` is what "main executable failed strict validation" means, and an unsigned arm64 binary does not launch. **Packaging a darwin platform therefore requires a macOS host**, refused elsewhere rather than writing a file that cannot run. The reader tries the tail first (one 52-byte read every `telo` startup pays) and walks Mach-O load commands second; the payload is always checked against the trailer's digest, because a magic can occur inside a 140 MB binary's own data.

**Every file the manifest NAMES must be there**, or packaging refuses naming the module, the path and the syntax that claimed it. Skipping a missing one silently is the failure class the layer rule closes, reopened on the local half: an unbuilt controller, an unstaged `native:` entry or a missing `!include-text` would leave a payload that is quietly incomplete and fails on first boot, on someone else's machine. **The payload's layout is anchored at the ENTRY's directory**, with every module placed at its path relative to it and the whole layout pushed down by as many anonymous `_` levels as the deepest `..` needs. Taking the deepest common directory preserved the offsets too, but the segments above the topmost module are the builder's own directory names — so the payload disclosed where it was built and the same application packaged from two checkouts produced different bytes, losing the digest-keyed unpack reuse. **A downloaded carrier is verified or refused**: continuing past a missing `checksums.txt` would bake an unverified network-fetched executable into someone's product, and `sha256sum`'s binary-mode `*name` spelling counts as listed.

**Three rules turn a best-effort cache into a complete one**, all of them because a packaged app has no lazy path and does not run where it was built:

- **A layer that did not land is a refusal for a NAMED target** (`warmModuleLayers` returns `gaps`, `describeGaps` renders them, the remedy is the caller's since `telo package` accepts no `--abi`). The two skip classes — a failed fetch, and a layer constraining an axis the target leaves undetermined — were warnings on the grounds that `run` fetches lazily; that is false for a baked image and for a payload, where the warmed tree is the only cache. **For the host it stays a warning**, and `parsePlatformTarget` keeps the host's abi when no `--platform` is given: an install for this machine is an optimization over a run that can still fetch, and discarding an abi already in hand made a bare install unable to warm the layer its own runtime opens.
- **A local module is carried BUILT.** Nothing warms a module reached by a relative `source:` — including the application's own `Telo.Definition`s — so its controller and every `exports.code:` entry point are built through the same builder publish and release share, written at the `path=` the manifest names, and its `sources:` entries are staged for the platform. The TypeScript sources are left behind, and that absence is what makes the property self-enforcing: the loader's dev branch fires only when a `local_path` source is on disk, so the prebuilt file is what loads and the embedded esbuild is never unpacked. Not by minting artifacts for local modules — a layered artifact is addressed by a pinned ref and verified against it, and a module no registry holds has neither.
- **Portability is derived from the carrier, not listed** (`package/portability.ts`): the carrier's kernel must open the candidate's format, and the candidate must need no external program on the target (the kernel's own tool table). A kind passes on one satisfying candidate; a closure with an npm-delivered or crate-built kind and nothing else is refused naming the kind, the candidate and which predicate failed. The day `cli/rust` is a carrier the same closure gets the opposite verdict with no edit here. **Judged over the kinds something INSTANTIATES**, since the kernel resolves a controller per instantiated kind and skips the rest — otherwise importing a module that happens to declare one crate-built kind refuses a packaging of an app that never uses it. The used set is collected from every `kind` string at any depth and matched on the suffix alone: over-inclusive on purpose, because judging an unused kind costs a refusal the author can act on while missing a used one ships an app that cannot boot.

**The analysis verdict is keyed by the payload.** The stamp is filed under a hash of the ENTRY URL and signed over each file's SOURCE URL — both absolute paths on the building machine — so a payload unpacked at a digest-keyed path misses on every start, silently, since a miss is the designed quiet recovery. `kernel.load({ analysisKey })` takes the payload's own digest over its file set instead (`cache/analysis` and `cache/validators` excluded from it: the stamp cannot name itself, and a validator is a pure function of a schema the key covers). Verified by execution — with the payload's stamp a run writes nothing; with the signature corrupted it re-validates and says so.

**At run time there is no second code path.** `standalone/entry.ts` asks whether this binary carries a payload; if it does, it unpacks once into `<cache root>/apps/<name>-<digest>` and calls **`telo run`'s own implementation**, which is what carries the SIGINT/SIGTERM handling and the kernel's exit code into a packaged service. Every argument is the application's (`hideBin`, so argv starts where the CLI would have started it) and the CLI is unreachable — the user of `./orders` is not a telo user, which is why `TELO_APP_INFO=1` (the index, through `outDocument`) and `telo package inspect <file>` exist instead. **Env files are read from the WORKING DIRECTORY** (`RunArgv.envAnchor`), because the entry manifest sits at a digest-keyed path no operator should have to find; `.env*` never travels in a payload. `TELO_CACHE_DIR` is overridden rather than honoured — the payload IS the cache — and `TELO_APP_DIR` relocates the unpack root, which is what a read-only container needs; with nowhere writable the app refuses naming it. **A successful start reclaims the app's other digests**, keeping any tree a live process holds (`live/<pid>`, the runner's sweep); deletion is safe because a reclaimed tree comes back out of the binary that owns it.

## `telo runner`

**The CLI hosts a runner, and the substrate it owns is this binary.** `telo runner` serves the backend-neutral `/v1` session contract (`@telorun/runner-core`) over a local-process backend: each application in a session is a `telo run --watch --inspect` of **the currently-running executable**, never a `telo` resolved from `PATH`. That is what makes supervisor and supervised one version by construction — same debug wire, same workspace marker, same run flags — with no version pair to keep in agreement. A single-file executable IS the command; an npm install re-enters through `process.argv[1]`.

Three differences from the container runners, each **advertised rather than hidden**, because a capability a client cannot read is a surprise at run time:

- **`io: ["streams"]` only.** Nothing in the repo carries a pty library and a native one cannot ride inside the single-file executable. An explicit `io: "tty"` is refused (`400 io_unsupported`) rather than downgraded — `isatty()` is observable to the application.
- **No isolation.** The workload inherits this process's environment (a local run's whole point is the machine it runs on) and its privileges. Hence loopback by default (`--host` anything else is refused without `--allow-remote`) and **no browser origin by default**: `*` is right for a runner an operator deployed, and wrong here, because every page the user visits reaches `127.0.0.1` from their browser and a cross-origin `POST /v1/sessions` that `*` waves through runs arbitrary code as this user. `--allow-origin` names one; the editor passes its own webview's. `RUNNER_CORS_ORIGINS` still wins, and core refuses an unnamed origin server-side rather than trusting the browser to (the byte channel already did, with `4403`).
- **No session config**, and that is enforced, not only advertised: a request carrying one is `400 invalid_config`. A closed schema on `/v1/capabilities` with nothing behind it is the half-kept invariant the contract change exists to remove.
- **Ports are bound, not published.** A port that appears on reload is reachable as soon as something binds it, which is the case a host-publishing docker session has to refuse. A port two apps in one session both declare is still reported as rejected.

**Session workspaces are private and reclaimable.** They hold the user's source, so the state root and every directory under it are `0700` (chmod'ed, since `mkdir`'s mode is masked by the umask), and each runner owns a subdirectory named by its PID. A runner that is SIGKILLed cannot clean up, so the next one sweeps the PID directories whose process is gone — a question with an answer, unlike a timestamp heuristic that eventually deletes a live session's files.

**Child-process discipline replaces container labels.** Each app runs in its own process group (`detached` on POSIX, `taskkill /T` on Windows), a stop kills the group, and the command's SIGTERM handler stops every live session before the process exits. A leaked `telo run --watch` holding a port after the editor quits is the failure that discipline exists to prevent.

**The web server is loaded when the command runs, not when the CLI starts.** `commands/runner.ts` registers with yargs statically (so `--help` lists it) and `await import()`s `@telorun/runner-core` inside the handler: fastify, pino and ws are ~70ms of a ~270ms startup, and no other command needs them. This is the one place the repo's static-import convention is deliberately not followed, and the reason is the hot path every `telo check` takes.

**`telo runner` is NOT exempt from the `Output` seam** the way `telo run` is: workload bytes travel the `/v1` byte channel, so the runner's own stdout and stderr are genuinely the CLI's. It emits its address as the command's result (`-o json`) and passes stderr to runner-core as the server's `logStream`, because pino's default destination is stdout.

**Studio ships this binary** and supervises `telo runner` on loopback (`apps/studio/scripts/stage-cli-sidecar.mjs` builds it per Rust target triple), so the standalone build now has a second consumer: a break in `telo runner` is a desktop editor that cannot run anything.

**Polyglot debt:** `telo runner` is part of the one `telo` surface, so `cli/rust` owes it and `packages/runner-core` owes a Rust twin under the one-for-one layout rule. Unlike the retired editor-side runner, this is a second implementation of a WRITTEN contract — the case the mirroring rule exists to cover — rather than a second implementation of an unspecified concept.

## `telo changed` — gating a job on a dependency graph

`telo changed <paths..> --base <ref>` answers whether anything an entry point depends on moved since a git ref, so an expensive CI job (the live-model suites in `.github/workflows/e2e.yml`) is gated on its own graph instead of paying on every push. It walks the same **relative** `imports:` edges `telo release` propagates a bump along — the same `importSourceRefs` / `resolveSiblingManifest` pair the payload builder reads them through — but stops at the manifest text: no payload is built, so a graph costs a few YAML parses. A pinned `oci://` import is deliberately not followed; its source cannot reach this diff until it is published and re-pinned.

**A module entry point is spelled `telo.yaml`**, as it is everywhere else in the repo. A manifest under another name is matched literally, because anchoring a module's whole DIRECTORY is only right for a directory the module owns: `examples/test-suite-live.yaml` parses as an application and owns nothing, so taking it as an entry point anchored `examples/**` and made a gate watching two examples fire on every example in the tree. **Patterns and the diff are both spelled relative to the REPOSITORY ROOT** (`git rev-parse --show-toplevel`), which is what `git diff --name-only` reports against wherever it runs — a cwd-relative pattern turned `./hub` into `hub/**` against a diff naming `apps/hub/…`, a wrong answer in the skip direction.

**The exit code cannot carry a failure, so a consumer reads the ANSWER.** 0 is "changed" and 1 is "unchanged" — and 1 is also what a crash, a bad flag or a missing toolchain exits, so a gate shaped `if telo changed …` turns a broken gate into a silently disabled test. Both e2e gates take `-o json` and skip only on an explicit `false`; `--fail-open` (default) covers the narrower case where the command runs and the diff will not take (no merge base, base ref not fetched, not a repository).
