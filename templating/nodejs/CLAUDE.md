# Templating (Node) — package guide

Loaded when working under `templating/nodejs/`. Repo-wide rules live in the root `CLAUDE.md`. What an expression is typed AGAINST (the CEL scope rule) is the analyzer's — see `analyzer/nodejs/CLAUDE.md`.

## CEL analysis

**One expression, one verdict — the templating engine's.** `TemplatingEngine.analyze` returns `{ diagnostics, type?, calls }` (`templating/nodejs/src/engine.ts`), and the engine owns the `env.check()` call: the analyzer hands it the environment **typed for that path** and reads the resolved type back rather than checking again. Splitting the two is what let cel-js's opaque `found no matching overload` survive beside the diagnostic that explained it, and left interpolation holes chain-validated but never type-checked at all. Everything derivable from the expression alone is derived there once; everything needing manifest context — the field's declared type, its `x-telo-eval` mode, which verdict outranks which — stays with the analyzer, which is the only side that has it. That split is also what a second (Rust) CEL engine implements: a classifier, not a rulebook.

Call classification (`cel/diagnose.ts`) reads `Environment.getDefinitions()` — every registered signature, cel-js built-ins and Telo's catalog alike, with its call form and parameters — so `CEL_UNKNOWN_FUNCTION` and `CEL_WRONG_CALL_FORM` are decided by lookup and **nothing parses cel-js's message text**. A read of an undeclared field is explained the same way, from the schema the host supplies as `AnalyzeEnv.explainSchema` (the site's names, kernel globals included): `CEL_UNKNOWN_FIELD` naming what IS declared, in place of the checker's `No such key`. It only ever explains a rejection: the audit is reported solely when `check()` already failed, so a construct cel-js accepts but the registry cannot account for (a macro the parser expands, which a cel-js upgrade can add) degrades to no explanation rather than to a hard error on valid CEL.

## Module calls — the engine's second input

**An expression is compiled against a NAME SET as well as an environment.** `CompileEnv.moduleNames` / `AnalyzeEnv.moduleNames` carry the declaring module's own names — its `imports:` keys, `Self`, its `metadata.name` and `Telo` — and a call whose receiver is one of them (`Billing.format(x)`) is a call on a resource of the module that name reaches, not a method on a value. Everything else is the core catalog, so `format(…)` and `Billing.format(…)` never collide and one catalog environment still compiles both. The caller supplies the set because it is known from the module's own file before any import resolves; a partial is compiled with the names of the module including it, and the analyzer's parse cache is keyed on them. Absent means "no module names here", which is the reading every caller had before module functions existed.

**Resolution happens on the PARSED TREE** (`cel/module-call.ts`, the single reader — `resolveModuleCalls` writes, `moduleCallOf` reads, and no other surface pattern-matches the shape). The author's text, spans and the expression a trace shows stay as written, which rewriting the source would move. It rests on cel-js internals the package's typings do not expose, so the dependency is pinned to an exact version and `tests/module-call.test.ts` pins each one: `setMeta('macro', …)` redirects check and evaluation, a comprehension macro's `alternate` wins over `macro` unless it is cleared, and an rcall's asyncness is derived from state the replaced checker filled in. A receiver that is a field access (`a.b.c(x)`) is not a module call.

**Every reader takes the resolved tree, never a re-parse.** `extractAccessChains`, the nullable walk and `auditCalls` all skip a resolved call's receiver — it names a module, so reading it as a root would invent a dependency, an undeclared identifier and a `resources` read the expression never states — and the type check goes through `parsed.check()`, since `Environment.check(source)` re-parses and loses the rewrite. A `CompiledValue` carries its qualified calls in `calls`, beside `refs`, because re-deriving them needs the name set a consumer holding one expression does not have. `CEL_UNKNOWN_FUNCTION` / `CEL_WRONG_CALL_FORM` skip a module call, and no catalog flag is attached to one: what a module function's determinism and host-backedness are follows from the callable it resolves to, so a module call's `CallSite.deterministic` / `CallSite.hostBacked` carry what the host's `AnalyzeEnv.moduleCallFlags` (or `auditCalls`' `moduleCallFlags` argument) derives, and stay absent where it gives nothing — which every consumer reads as "no signal". A catalog call carries both from the catalog entry.

**The dispatch is private.** `evaluate` reads a per-scope table from the activation under `MODULE_CALL_DISPATCH_KEY` (`@telo:module-functions`) — `@` and `:` are outside CEL's identifier grammar and the activation is reachable no other way, so no author can call past the export gate or the dependency edge. Binding the table is the kernel's, per owning scope; with none, evaluating throws `unbound function '<qualified>'`.

**Whether a call reaches a function is the ANALYZER's verdict, not this engine's** — it is manifest context, and the engine reports every module call in `AnalyzeResult.calls` for the caller to judge (`FUNCTION_UNRESOLVED` / `_NOT_EXPORTED` / `_NOT_CALLABLE` / `_ARITY_MISMATCH` / `_ARGUMENT_MISMATCH`), each with its arguments' CEL types and, for an argument that is a plain chain, the chain — the caller compares those against the signature. What the engine does take from the host is the callee's RESULT: `AnalyzeEnv.moduleCallType` types the call node (so an operator over it checks), and `moduleCallResult` supplies the schema a member read off it is checked against (`CEL_UNKNOWN_FIELD`, labelled `<qualified>(…)`); absent, a call types as `dyn`. The one place manifest vocabulary would otherwise leak in is the unknown-identifier hint: the engine knows which bare identifiers are unresolved call *receivers*, and asks the host through `AnalyzeEnv.couldNameModule` whether such a name could denote a module at all, so `dbb.query(1)` is not told to add an `imports:` alias. Naming rules are the host's; absent, the hint stays off.

**Null-safety:** dereferencing a value whose schema admits `null` (e.g. `error` inside a `finally` block, typed `["object","null"]`) without a null-guard is a static error (`CEL_NULLABLE_ACCESS`). The analyzer recognises guards through `?:` ternaries and `&&` / `||` short-circuits — `error != null && error.code`, `error == null ? … : error.code`. General: applies to any nullable value in any CEL context (`templating/nodejs/src/cel/analyze.ts` `findNullableAccessIssues`, wired in `engines/cel.ts`).

## Interpolation (`!interpolate`) and the hole grammar

**`!interpolate` is text with `${{ expr }}` holes, always a string, and its meaning is fixed as exactly the CEL expression joining the text with `string(<hole>)` for each hole** (`engines/interpolate.ts`). Conversion is the environment's own `string()` overloads — RFC 3339 for a timestamp, the `Telo.Duration` plain encoding for a duration (`5400s`, the catalog's `string(duration)`), UTF-8 for bytes — never the host's `String()`, which is what makes a Go or Rust engine render the same text. Statically each hole is analyzed by the shared `analyzeCelExpression` (diagnostics and fixes re-anchored onto the whole scalar, as `!sql` does), a clean hole is checked by type-checking `string((<hole>))` in the same environment — a type no overload accepts is `INTERPOLATION_HOLE_NOT_CONVERTIBLE` — and a hole that is a plain chain whose schema admits null is `CEL_NULLABLE_ACCESS`. A `dyn` hole passes; one that is null, a list or a map at runtime throws `ERR_INTERPOLATION_HOLE_NOT_CONVERTIBLE` naming the hole, its offset and the type found — null never renders as `""`, which would contradict the static verdict. `producedType()` declares `{type: string}`, so the slot check, the placeholder substitution and the studio picker handle it without naming it.

**One hole grammar, normative** (`cel/interpolation-holes.ts`, read by `!sql`, `!interpolate` and the `untagged-interpolation` migration's `match.scalar`): a hole opens at `${{` and closes at the first `}}` outside a CEL string literal and outside any `{` the expression itself opened. String literals are CEL's — `'`, `"`, their triple-quoted forms, the `r`/`b` prefixes, a raw string taking no escapes, a single-quoted one ending at a newline. Outside a hole only `${{` is special, and a literal one is written `${{ '${{' }}`. A hole that never closes is a reading failure at its `${{`, never a guess. The expression is the hole's body trimmed. A scalar's SHAPE is `none` / `lone-hole` (one hole, only whitespace around it) / `interpolated` / `malformed`. The `[^}]+?` regex it replaced could not read a map literal and left such a string as literal text.

**Where a tag's CEL sits is the ENGINE's to say** — `expressionRegions(source)`: the whole scalar for `!cel`, each hole's expression for a tag with holes, nothing for a tag holding no CEL. `celExpressionsOf(engine, source)` is the single reader, and every analyzer pass that asks "what CEL is written here" (non-eval fields, observed-state reads, durable regions, throws, scope reach, unused declarations, module calls, the module graph's data edges) goes through it, as the editor's segment builder does — so no consumer outside the registry branches on `interpolate`. A question about the value's OWN expression (is it a plain chain, a computed reference) stays `!cel`'s: a tag with holes produces something other than the value of one expression.

**A plain string is never an expression.** The untagged `"…${{ }}…"` spelling is rewritten at load by the core migration `untagged-interpolation` (a lone hole to `!cel "<expr>"`, anything else to `!interpolate` with the text unchanged), and `precompileDoc` refuses one that survives (`ERR_UNTAGGED_INTERPOLATION`) in whichever module holds it, so its static twin `UNTAGGED_INTERPOLATION` is reported for every module too — a dependency's at the consumer's import of it, read off the library's full documents (`moduleDocuments`). The load-time rewrite changes one thing a published artifact did: a hole null, a list or a map at runtime now fails where the untagged spelling printed empty text or a comma list, and the entry's `reason` says so. The Rust tag reader refuses `!cel` / `!interpolate` / `!sql` by name and a plain string holding `${{`, having no expression engine.

## Embedded files (`!include-text` / `!include-bytes`)

Two tags embed a file that ships beside the manifest as a manifest value — `!include-text` → string, `!include-bytes` → `Uint8Array` (what a `Telo.Bytes` slot accepts). Engines in `templating/nodejs/src/engines/include.ts`, registered in the closed `builtinEngines` set, mirrored by `templating/rust/src/engines/include.rs`.

**Paths are MODULE-ROOT-relative, never relative to the declaring file** — the rule a controller's `path=` and `files:`/`assets:` already follow. It is load-bearing rather than cosmetic: `telo publish` deletes `include:` and inlines every partial as an extra document into one published `telo.yaml` (`expandAndInlineIncludes`), so the declaring file does not exist in the artifact and a per-file-relative path would silently move — passing `telo check` locally and failing only for consumers. **Confinement is a PURE STRING check** (`normalizeIncludePath`), which is what lets the browser-safe analyzer decide it: root-relative means `..` below depth zero is an escape regardless of where the module sits on disk. Literal paths only — a URL, glob or absolute path is `INCLUDE_PATH_INVALID` / `INCLUDE_PATH_ESCAPES_MODULE`. A **computed path is deliberately unrepresentable**: a file that must ship inside the artifact has a name known at publish time, so the dynamic case is `Fs.File`'s, not this one.

**A module's `source` is what EVERY module-relative reference is measured from** — `ctx.resolveModuleFile` for a controller, an embed for a manifest value — so an import's child `ModuleContext` carries the **library's own manifest URL** (`moduleManifest.metadata.source`, stamped by the loader), never the importer's and never `resolvedUrl` (which is the import source as written, a directory whose last segment `new URL` would drop). Carrying the parent's made a library read the CONSUMER's directory, silently returning the consumer's file when one sat at the same relative path — and it contradicted packaging, which is per-module.

**An embed's type is a constant of the TAG, not of the slot.** `substituteCelFields` gives every other tagged sentinel a slot-shaped placeholder (right for `!cel`, whose type is only derivable from the expression); these two substitute a real `""` / `Uint8Array`, so AJV and the `x-telo-type` keyword reject a byte embed at a string slot — and the reverse — statically, with no new diagnostic code. **The ENGINE is what says so**: `TemplatingEngine.producedType()` declares the fragment (`fileClaims`' precedent applied to the one fact it left behind), and `substituteCelFields` reads it through `producedTypeOf` instead of branching on two tag names — the only place a tag's produced type was written down, and it was written in the consumer.

**`compile` is identity on the marker** — the sentinel survives precompile the way `!ref` does, but needs no special case in `precompileDoc`. **The read happens at RESOURCE CREATION** (`kernel/nodejs/src/resolve-include-sentinels.ts`, called from `_createInstance` before schema validation so bytes reach a `Telo.Bytes` slot as a `Uint8Array`), never at manifest load: the artifact spec gives `telo.yaml` its own layer so reading a manifest cannot pull the payload, and an app loads every imported library's manifest. The walk **stops at nested `{ kind }` declarations** (a `with:`-scoped resource resolves when its scope runs — Phase-5 injection draws the same line) and **only recurses into plain containers**, because a template kind expands `${{ self.connection }}` to a live `ResourceInstance` whose graph is cyclic. The same rule governs `compileWalker` (rebuilding any object from `Object.entries` would turn a byte buffer into `{"0":137,…}` silently), `walkCelExpressions` and the kernel's dependency-edge walk (`collectResourceRefs`): every walk over a declaration meets that live instance on every creation attempt of a template child, and one that descends into it overflows the stack or traverses the whole kernel. An embed on a doc that is never instantiated is `INCLUDE_OUTSIDE_RESOURCE` — nothing would read it, and nothing else would report that.

**Payload membership is ONE generic mechanism, and no consumer recognises a syntax.** `TemplatingEngine.fileClaims(source)` lets an engine declare what its tag embeds (the `ref-slot.ts` precedent); `collectModuleFileClaims` (`analyzer/nodejs/src/module-file-claims.ts`, browser-safe) is the single reader, aggregating engine claims **and** the controller `path=`/`siblings=` claims into `{ path, role, selector?, siblings?, origin }`; `partitionLayers` consumes that and knows about neither PURLs nor tag names. It is **deliberately not part of `analyze()`** — that pass is flattened and import-inclusive, so its claims would mix in imported libraries' files (whose paths are relative to *their* module) and would make packaging depend on resolving the whole import graph, which today it does not. Publish refuses a named file that does not exist. Cap: 32 MB per file. The Rust kernel resolves `!include-text` only — its manifest is `serde_json::Value`, which has no bytes variant, so `!include-bytes` fails there explicitly rather than producing a number array.

## Module paths (`!module-path`)

`!module-path ./public` names a file or DIRECTORY that ships with the module by its LOCATION: at resource creation the kernel resolves it — beside the embeds, through the same `resolveModuleFileUri`, so a published module's assets layer is materialized first — to the absolute path on disk, and refuses one naming nothing (`ERR_MODULE_PATH_NOT_FOUND`). Engine in `templating/nodejs/src/engines/module-path.ts`, mirrored by `templating/rust/src/engines/module_path.rs`; its path grammar is the include grammar under its own codes (`normalizeModulePath`, `MODULE_PATH_INVALID` / `MODULE_PATH_ESCAPES_MODULE`, the module root itself refused). It produces a `Telo.HostPath`, which is how a slot on the host (`Http.Static.root`) holds a directory of the module without the controller anchoring a relative string itself — a relative literal there is `HOST_PATH_RELATIVE`, whose repair is this tag.

**Its claim may be a directory** (`EngineFileClaim.directory`), so the analyzer's claim stays a pure string and the Node side that holds the directory expands it (`cli/nodejs/src/bundle/module-path-claims.ts`) into one assets claim per file, for publish and `telo package` alike — refusing `MODULE_PATH_NOT_FOUND` / `MODULE_PATH_EMPTY`, since an empty directory is not something a layer can carry. **Existence is asked at LOAD, of the source**, because the analyzer never touches a filesystem: the loader puts each entry-module `!module-path` to the entry's `ManifestSource.exists(base, relative)` and records `MODULE_PATH_NOT_FOUND` in `LoadedGraph.modulePathDiagnostics` (`analyzer/nodejs/src/module-path-existence.ts`), which the shared assembler and the runtime seam report — so `telo check`, VS Code, Studio and `Assert.Manifest` all see it. A path at or above a module file the module's own `sources:` block stages (an entry an `assets:` pattern selects, or a notice) counts as present, since the kernel stages it on first use; the classification is the kernel's (`stagedModuleFiles` in `module-named-files.ts`, native entries first), nothing is exempted while the block does not read, and release planning from pins expands a directory claim over the same staged entries. A source that cannot answer (an in-browser store) reports nothing and the kernel's refusal remains. Emptiness is NOT asked there: it depends on the packaging ignore rules, so it stays a publish/package refusal alone rather than a second rule that could disagree with it. A tag on a doc that is never instantiated is `MODULE_PATH_OUTSIDE_RESOURCE`.

## Where to look

- Embedding or locating a file that ships with a module → `templating/nodejs/src/engines/include.ts` (the path grammar), `engines/module-path.ts`, `analyzer/nodejs/src/module-file-claims.ts` (who claims which file), `kernel/nodejs/src/resolve-include-sentinels.ts` (the read and the location)
- Holes and `!interpolate` → `templating/nodejs/src/cel/interpolation-holes.ts` (the grammar), `engines/interpolate.ts`, `engines/hole-analysis.ts` (shared with `!sql`), `celExpressionsOf` in `builtins.ts`
- CEL type checking → `templating/nodejs/src/engines/cel.ts` (`analyzeCelExpression`, which owns the verdict), `cel/diagnose.ts` (the call classifier); the analyzer supplies the typed environment (`cel-environment.ts`) and the context schema (`validate-cel-context.ts`)
- "is this call the catalog's or another module's?" → `templating/nodejs/src/cel/module-call.ts` (the rewrite, the reader and the private dispatch key), `analyzer/nodejs/src/module-call-names.ts` (where a module's names come from, at load and at analysis)
