Every `telo release` command digests a file a `sources:` entry stages from its pin, so a tree with nothing staged computes the same layer `integrity` as publish computes from the staged bytes; a layer holding such a file takes a stand-in `blob` (`sha256:` plus the hex of its integrity digest) that only the `manifest` ledger digest sees. `telo publish` reads staged files off disk, verifies each against its pin and frames the real bytes, and never fetches. The published `telo.yaml` no longer carries `sources:` — it is removed before any dependent's pin is derived, so editing only a source's `url` moves no digest — and each source's notice files ship in the `common` layer with no `files:` entry. Publish refuses a staged file that is missing, unpinned or does not match its pin, a `native:` path or platform-qualified candidate `path=` that no source stages and git does not track, an unreadable `sources:` block, and a source entry nothing in the manifest names. The module publish job runs `telo release stage` before pushing, over the modules it pushes and their in-repo import closure, which `telo release order -o json` now reports as each entry's `imports`. The kernel's layer integrity accepts a pinned entry (`PayloadPinnedFile`, `LayerEntry`, `isPinnedFile`), and the kernel exports its layer entry rules (`findLayerViolations`, `describeLayerViolations`).
