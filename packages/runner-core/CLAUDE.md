# Runners — package guide

Loaded when working under `packages/runner-core/`. Also the guide for `apps/docker-runner/`; k8s-specific rules (routing seam, infrastructure error summaries, the Helm chart) are in `apps/k8s-runner/CLAUDE.md`. Repo-wide rules live in the root `CLAUDE.md`.

**Runners** — `packages/runner-core` (the backend-neutral `/v1` session contract, routes, registry, ring buffers) plus `apps/docker-runner`, `apps/k8s-runner` and the CLI's own local-process backend behind the `RunnerBackend` seam.

**A backend is hosted by the artifact that owns its substrate.** The docker backend lives in the image that fronts a docker socket, the k8s one in the deployment that holds the API credentials, and the local-process one in `telo` itself — a local run IS `telo run --watch --inspect`, so any other host would put a supervisor beside the thing it supervises and make them agree on an unwritten protocol. What is shared is the contract, not the substrate: core knows nothing about an executable, a process group or a container.

## The session config is the runner's, not the contract's

`SessionConfig` and `ProbeConfig` are opaque bags (`Record<string, unknown>`). They used to declare `image` and `pullPolicy` — container vocabulary in the backend-neutral contract, which only stayed invisible while every backend ran containers, and which the third one exposed. The runner is the authority on its own config surface and already said so twice: `config.schema` on `/v1/capabilities` is what the editor renders the form from, and `ServerDeps.validateConfig` is what enforces the same against a client that skipped the editor. **The forbidden repairs are a fake image on the local runner and a `kind: "process"` branch in core.** `container-config.ts` holds both halves of the container backends' answer — the schema they advertise and the parser they read it back with — so a field cannot be advertised in a shape the backend will not accept.

**An origin allowlist is enforced by the runner, not by the browser.** With `corsOrigins` narrowed, core refuses a request whose `Origin` is not on the list (`403 origin_not_allowed`) instead of only withholding the CORS header — a client that ignores response headers is otherwise unaffected by CORS, and a local runner starts workloads for whoever reaches it. A request with NO origin is left alone (every CLI and health check sends none; the transport is what bounds those), while the byte channel makes the opposite call for the opposite reason — a browser always sends one on an upgrade, so a missing origin there is a rejection, closed with `4403` rather than an HTTP status a WebSocket client cannot read. The hook skips upgrades so that answer stays the io route's.

## Capabilities are enforced, not just published

`features.io` reaches the session routes from the same capabilities document the client reads (`server.ts` passes `capabilities.features.io` into both session-creating routes). An app that declares no `io` takes the runner's first advertised mode; one that declares a mode the runner does not serve is refused with `400 io_unsupported`. **Never silently downgrade a `tty` request**: `isatty()` drives colour, buffering and prompts, so a session that claims a terminal it does not have is a lie the application can detect. The same rule already governed `watch` (`400 watch_disabled`) and terms (`428 terms_required`).

**A gate that only one backend installs is a gate.** `validateConfig` is the runner's half of the config contract, and it has to be UNCONDITIONAL: k8s used to install one only when a base-image catalog was configured, so a catalog-less deployment accepted `{"image": 42, "pullPolicy": "sometimes"}` and started a pod on its default image under `missing`. The readers in `container-config.ts` throw rather than coerce for the same reason — only the gate decides what is acceptable, and a reader that substitutes a default makes the gate optional in practice.

`buildServer` takes an optional `logStream`. Pino's default destination is stdout, which is right for a container whose stdout IS its log and wrong inside a CLI, where stdout is the machine surface — `telo runner` passes stderr.

## The telo version is the contract's; how it is obtained is the backend's

**An application may name the telo version it runs on** (`telo` on a `SessionAppSpec`, or on the request for a single-app session): the version its module is edited against, so what checks a manifest is what runs it. It sits in the contract and not in `config` because every backend runs *a* telo — what differs is how each gets one, which stays behind the seam. **Never a substitute**, on any backend. `features.teloVersions` is advertised by a runner that honours the field and enforced like `io` and `watch` — a version sent to a runner without it is `400 telo_version_unsupported`.

**Refused before the session only when the answer is cheap and certain; fetched inside the start otherwise.** `RunnerBackend.supplyTelo(version, config)` is asked before the session exists and returns why a version can NEVER be run here (`400 telo_version_unavailable`, with `{ app, version, reason }`): an unreleased build identity nothing can supply, a platform no binary is published for. Core itself adds one refusal on every backend: a release older than `MIN_SUPERVISABLE_TELO`, because what a runner asks of a telo — `--watch --inspect --no-open` before the path, the debug stream, the workspace marker — is the contract's. That floor is the oldest release VERIFIED BY EXECUTION, not the point where it breaks; lower it only by running the candidate. **The k8s base-image catalog gates `config.image` and nothing else**: it is a bounded display menu read from its own repository setting, and using it as the version allowlist refused an older pin and every version on a mirror. It must not pull or download. The slow half — a docker image pull, the local runner's release download — belongs to `start`, because that is where a progress event, a cancellation and the session ceilings already exist: holding `POST /v1/sessions` open for a pull shows the user nothing and gives them no session to stop, and puts the global ceiling after a fetch it would then refuse. A fetch that fails there is a failed start on the stream, carrying the same reason.

**The runner's own containers stay on the operator's kernel.** A watch session's `workspace` container runs the runner's manifest, verified against the kernel the runner ships with, so on both container backends it runs on the operator's image (`RUNNER_IMAGE`) and only `app-<name>` containers follow `telo`. Running it on the user's version would fail a session for a reason unrelated to the user's manifest.

**An unreleased build has no image unless the operator names one.** `X+unreleased` is a working copy, so no registry holds it under a version tag. `RUNNER_TELO_UNRELEASED_IMAGE` names the kernel image built from that same tree — a development stack, where the editor's bundled engine is itself unreleased — and without it the refusal says so and names the variable. The reported version still exposes a wrong mapping.

**One answer per session to "who chooses what runs".** Either every app names its version or none does (`400 invalid_telo_version`), and a container backend refuses `config.image` beside a version (`400 invalid_config`) — which is why `validateConfig` is told whether the request names one (`ConfigGate`). **What a version supersedes is advertised, not inferred** (`config.supersededByTelo` on the capability document): a client leaves out exactly those properties, rather than everything marked `deprecated`, which says a field is on its way out and nothing about why. And **the feature and the seam are one statement**: `buildServer` refuses a runner that advertises `teloVersions` over a backend with no `supplyTelo`, which would otherwise accept every version and run what it pleased. `image` is deprecated, not removed: a client naming no version still sends it and gets exactly the old behaviour, and the advertised schema marks it `deprecated: true` so a form can leave it out. **`pullPolicy` went with it, to the operator** (`RUNNER_PULL_POLICY`): a version tag does not move, so `always` buys a run nothing, and `never` describes a deployment whose images are preloaded rather than a choice someone makes per run. It is refused beside a version rather than ignored — a field a runner accepts and does nothing with tells its sender something false — and applies to every image the runner chooses itself, its own workspace container's included.

**The runner reports the version; it judges nothing.** `Kernel.Starting` carries the runtime's own version, the projection passes it on as `telo` on that generation's `run` `started` event, and nothing compares it: by the time the frame arrives the manifest has loaded on that runtime, so stopping it would undo nothing. The editor compares and warns. A runtime from before the field reports none, and the event carries none.

## Session shapes

**A session is one of two shapes.** A `run` session is one run: one container/pod, terminal when the workload exits, resolving its module closure in-pod on both backends — the k8s one used to prebuild a per-app image with an on-cluster Kaniko Job, which is gone along with the `telo-builds` namespace and every `RUNNER_BUILD_*` / `RUNNER_REGISTRY_*` knob, so **no runner builds an image** and start latency is the price (a run session's cache dies with its pod; a watch session's lives as long as it). A **`watch` session is a workspace that runs continuously** — one pod, a shared `/workspace` volume, one container per application under `telo run --watch`, and optionally a co-resident **`agent`** from the operator's `RUNNER_APPS` catalog — so an edit costs a kernel reload rather than a pod. **The session seeds `telo-workspace.yaml` at the workspace root**, so the kernel anchors ONE `.telo` there for every app in it; the app containers therefore carry no `TELO_CACHE_DIR`, which outranks the marker and is exactly what would give each app a cache of its own. Off unless `RUNNER_WATCH_SESSIONS` is set, with its own ceilings (`RUNNER_WATCH_*`) because its concurrency is bounded by simultaneous EDITORS rather than simultaneous runs.

## Status, run events and output

**Status and run outcome are two nouns on one stream**: `status` is the session's (`starting`/`running`/`suspended`/`stopped`/`failed` — `exited` belongs to a run session, where the session IS the run), while a `run` event is one app's generation, so a one-shot Runnable finishing leaves the session up and the next edit starts generation N+1. Those `run` events are **projected from the kernel debug stream, never parsed out of the terminal** (`debug/run-projection.ts`): a watch session always runs with `--inspect`, and `Kernel.Starting` / `Kernel.Stopped` bracket each generation on one debug connection that survives reloads. The one thing that stream did not carry is a manifest that fails to LOAD, so the CLI emits **`Kernel.RunFailed`** (`{ phase: "load" | "start", code?, message }`) — a dotted event name inside an existing frame kind, which obliges no other runtime where a new frame kind would oblige all of them. **`Kernel.PortsResolved`** rides the same stream and carries the Application's `ports:` block re-resolved per load, so a host patches its Service/Ingress without re-parsing a manifest on the save path; it is the DECLARED set, because routing what happened to BIND would expose an undeclared port and would rest on a per-module listening convention — whether anything bound it is the reachability watcher's answer, per port. **Workload output never travels the event channel** — it goes over the byte channel, keyed `(session, app)` because each app has its own terminal, with every frame `[seq:4 BE][stream:1][payload]`; the `stdout`/`stderr` `RunEvent` variants that used to be declared were emitted by nothing and are deleted rather than qualified.

**`io` is `tty` (default) or `streams`**, and the difference is observable to the APPLICATION: `isatty()` drives colour, buffering and prompts, so an always-PTY loop hides production behaviour. Neither backend invents a transport — docker's non-TTY attach and the k8s attach subresource already separate the streams, and the TTY is what collapses them — and `CLICOLOR_FORCE` is injected only under `tty`.

## Workspace, env and ports

**The workspace surface is runner infrastructure, not agent functionality**: it is part of the `/v1` contract, so the manifest lives in `runner-core/workspace-app/telo.yaml` (`Http.Api` over `Fs.TreeSnapshot` / `TreeSync` / `File` — no new module, no `JS.Script`) and runs on the plain kernel image, delivered as a content-addressed ConfigMap on k8s and a per-session directory on docker. Hanging it off the agent's catalog image would invert the dependency and need a second implementation for the agentless case.

**The env split IS the credential boundary** — operator env on `agent` alone, session env on every `app-<name>`, neither on `workspace` — structural before (two pods), a code invariant now, so it is asserted by a test. Ports are unique across the WHOLE session (`400 port_conflict`), because session hosts are `<port>-<sessionId>.<domain>`, a single label carrying no app name.

**The workspace is `/workspace` on BOTH backends**: docker mounts each session's own `workspace` subdirectory of the shared bundle volume there (`Subpath`, Engine API 1.45 / Docker 26), so a manifest is `/workspace/telo.yaml` either way, no session id reaches a workload's paths, one session cannot read another's files on disk, and nothing is laid over a directory an operator's catalog image may already use — mounting the volume whole at `/srv` covered up the authoring agent's own installation, which is why the co-resident agent could never start there. Only the runner's own `workspace` container keeps the whole-volume bind, because its manifest and cache sit BESIDE the workspace it serves; the same siblinghood is what keeps them out of the user's file tree. An older daemon silently ignores `Subpath` and would mount everything at `/workspace`, so the runner probes at boot and advertises `features.watch: false` rather than degrading into that.

## Co-resident agent

**A co-resident agent is REACHED like an app port and REPORTED beside them**: its catalog entry declares the `port` its image listens on (no default — the runner knows nothing about any specific app, and guessing 8080 would be exactly that knowledge), a session requesting an agent without one is refused (`400 agent_port_undeclared`) rather than started unreachable, and the `running` status carries an `agent` endpoint SEPARATE from `endpoints`, which are the ports the user's applications declared. **The advertised set IS the acceptance condition** — `coResidentAgentNames` derives `features.agents` from the same `port` the route requires, in runner-core rather than per runner, because the two were one list by construction (`Object.keys`) and adding a condition to only one is how an upgraded operator's port-less catalog gets advertised, attached to every run by the editor, and then refused. **Where an app declares the agent's port the MANIFEST wins**: the session starts without the agent and says so on its stream, rather than refusing to run a user's application over a container a client asked for on their behalf and they cannot decline. **A catalog entry's `tokenEnv` gets a per-session workload token**, minted by core, injected through the operator-env channel (the agent's own env, or the app session's) and reported by core as `RunnerEndpoint.token` on that workload's endpoints — core rather than each backend, so no backend can publish an endpoint without the token its workload holds; it rides the retained launch, so resume keeps it. Nothing verifies the agent LISTENS on the declared port — what the image binds is configured separately — so a mismatch routes to nothing. k8s needs no routing of its own — the pod's containers share a network namespace, so the port just joins the session Service and routing objects — while docker gives the agent its OWN alias (`telo-run-<sessionId>-agent`, resolved by the proxy's existing trailing-capture rule), because a shared alias is round-robined and putting the agent on the session's would make every app port a coin flip.

## Suspension

**A session is no longer a pod**: idleness suspends it (pod deleted, workspace checkpoint held, `suspended` deliberately non-terminal) and `resume` rebuilds one under the same id. The checkpoint is a **cache, never the only copy** — the runner is a single replica with an in-memory registry, so a restart answers `404` and the editor, which holds the authoritative workspace, re-seeds from its own copy in one change set. Changing WHICH apps run reuses that same path, because a pod's container list is fixed at creation.

- "how does a session run, and for how long?" → `packages/runner-core/src/contract.ts` (the `/v1` shapes), `backend.ts` (the `RunnerBackend` seam + `WorkspaceAccess`), `session/registry.ts` (per-app channels, generations, the non-terminal `suspended`), `session/watch-supervisor.ts` (the checkpoint timer + the idle reaper), `debug/run-projection.ts` (run outcomes from kernel lifecycle events), `routes/sessions.ts` (validation + the workspace/reload/apps/resume surface), `apps/{k8s,docker}-runner/src/*/watch-session.ts`
