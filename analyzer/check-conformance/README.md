# Check conformance vectors

What `telo check` reports for a manifest, and what a run of it is refused with, frozen as data: every analyzer and every kernel reads these rows and answers each identically, word for word and position for position. Editing one expected message breaks every runner until each implementation says it.

## Format

`vectors/<id>/` is one row:

- a manifest tree — `telo.yaml`, the entry `Telo.Application`, and every module it imports, beside it under the row's own directory and imported by relative path; nothing is fetched;
- `expected.json` — `{ "diagnostics": [ … ], "runFails": … }`, and no other key.

`diagnostics` is every diagnostic `telo check` reports for the entry, every severity: the entry's parse, import-resolution and analysis diagnostics, assembled as every host assembles them (a file that failed to parse, or whose import failed, has its analysis held back), then every imported library's own verdict — what `telo check <library>` reports — at the library's own lines, since every row imports by relative path; an import-anchored refusal of the entry that a library's verdict reports as the same defect (its `data.writtenAt`) is that library's finding, so it appears once, where the library writes it. `runFails` stays the import-anchored refusal: the kernel's load does not compute the verdict. Each is the analyzer's whole `AnalysisDiagnostic` — `severity`, `code`, `source`, `message`, `tags`, all of `data` — with `range` the UTF-16 LSP range the diagnostic is shown at: its own range when it carries one, else the range its position fallback resolves (the resource's position, then its document, then the file's start); a diagnostic nothing locates has no `range`. They are compared as a multiset: a runner sorts both lists by each diagnostic's JSON text with keys sorted at every depth, compared by code point, and compares the sorted lists whole. A row stores them in that order.

`runFails` is what loading the entry and running its targets is refused with — decided, in both kernels, by one load refusal rule over the loaded graph and the analysis (the analyzer's `loadRefusal`, twinned by `load_refusal`) — as one text — `[<CODE>] <message>` of the refusal, then each diagnostic it carries on a line of its own as `  [<CODE>] <message>` (`  <message>` for one with no code) — or `null` when the run succeeds. The carried diagnostics are in the canonical finding order, which every kernel takes from its analysis unchanged, while `diagnostics` stays a multiset.

Every file a row's values name is relative to the row directory: a runner removes the row directory's own prefix (its `file://` URL or its path, followed by a separator) from every string it compares. Then it writes its own build's running surface — `TELO_RUNNING_SURFACE`, the version a `requires:` gate compares, `X` or `X+unreleased` — as `<running-surface>` in every string it compares, so a row stays true across releases; no row writes the current version itself: one too new for any runtime is `>=999.0.0`, one too old `<0.1.0`.

The values are Node's answers, recorded by running the Node analyzer and the Node kernel over each row. No generator is committed: a row's values are written once, read by every runner, and change only when the answer does. A row lands only when all four runners pass it, so a construct only one kernel refuses (one the Rust kernel cannot read yet, `ERR_UNSUPPORTED_MANIFEST_FEATURE`) never appears in a row.

## Rows

- `clean-application`, `clean-library-kinds` — nothing is reported and the run succeeds.
- `parse-*` — `MANIFEST_PARSE_FAILED`, one row per kind of YAML failure both loaders classify alike (`duplicate-key`, `unresolved-alias`, `alias-limit`, `tab-indentation`, `unclosed-quote`, `unclosed-flow-collection`, `bad-indentation`, `invalid-escape`, `reserved-character`, `plain-value-colon`), one in an imported library (`parse-in-dependency`), and one whose file's analysis is held back (`parse-holds-back-analysis`).
- `branch-position-metadata`, `repeat-outside-template-include` — an expansion tag where the loader reads before anything is expanded: `BRANCH_POSITION_INVALID`, `REPEAT_OUTSIDE_TEMPLATE`.
- `branch-shape-sequence`, `branch-shape-marker-key`, `repeat-shape-sequence` — an expansion tag of the wrong shape: `BRANCH_SHAPE_INVALID`, `REPEAT_SHAPE_INVALID`.
- `reserved-prefix-alias`, `reserved-prefix-library-name`, `reserved-prefix-entry-name` — `KIND_PREFIX_RESERVED` for an import's alias, an imported library's name and the entry's own name; `import-failure-holds-back-analysis` — the importing file's analysis held back.
- `import-unresolved-not-found`, `import-unresolved-not-a-module` — `IMPORT_UNRESOLVED` for a local source that names nothing and for a directory holding no `telo.yaml`, worded by Telo with `data.sourceFailure`; `import-authored-document` — the same failure of an authored module-level `Telo.Import` document; `import-invalid-source` — `INVALID_IMPORT_SOURCE` for the removed bare ref form; `import-malformed-http-source`, `import-malformed-oci-source` — `INVALID_IMPORT_SOURCE` for an http(s) URL the URL parser refuses and an `oci://` ref with no repository, refused before any source is asked (so before the Rust hosts' http(s) refusal); `import-target-no-library`, `import-target-duplicate-module` — `INVALID_IMPORT_TARGET` for a target declaring no library (its file `MODULE_DECLARATION_MISSING`) and one declaring two module documents (its file `MODULE_DECLARATION_DUPLICATE`).
- `module-declaration-missing-empty`, `module-declaration-missing-definitions`, `module-declaration-duplicate` — the module-declaration rule over the entry: an empty file, documents with no module document, a second module document.
- `partial-kind-forbidden`, `partial-not-found`, `partial-not-found-directory` — `PARTIAL_KIND_FORBIDDEN` on a partial declaring a `Telo.Definition`, `PARTIAL_NOT_FOUND` for a missing partial and for a directory entry; `partial-not-found-beside-glob` — a missing path entry refused beside a glob, the glob's partial still analysed; `include-glob-and-path` — partials named by a glob and by a path, each analysed in its own file.
- `capability-unknown`, `capability-not-declarable` — `CAPABILITY_UNKNOWN` / `CAPABILITY_NOT_DECLARABLE` on the entry's own definitions; `capability-in-dependency`, `capability-in-transitive-dependency` — on a dependency's: `telo check` reports it at the library's own line, and the run is refused with it at the entry's `imports:` entry reaching it, with `data.writtenAt` naming where the library writes it.
- `builtins-entry` — the built-in vocabulary archive as the entry: one `UNDEFINED_KIND` at its `kind:`, the file's analysis held back; `library-empty-first-document` — an imported library whose first document is empty, its definitions still judged, at the library's own lines.
- `reference-form-target`, `reference-form-slot` — `INVALID_REFERENCE_FORM`, with its `quotedPlace`, at a boot target and at a kind's reference slot.
- `migration-capability-as-extends`, `migration-ref-slot-scalar-type`, `migration-normalize-value-types`, `migration-element-from-item`, `migration-caught-member-marks`, `migration-untagged-interpolation` — the deprecation each core migration entry reports for the entry's own file (`CAPABILITY_SHADOWS_EXTENDS`, `X_TELO_REF_SCALAR_TYPE`, `X_TELO_TYPE_DEPRECATED`, `DEPRECATED_ELEMENT_FROM_ITEM_FIELD`, `DEPRECATED_IMPLICIT_CAUGHT_MEMBER`, `DEPRECATED_UNTAGGED_INTERPOLATION` for a lone hole and for text with a hole), at the author's own path. A row whose migrated manifest declares what only one kernel runs (an `extends:`, a resource of a kind with no controller, an expression) also declares a misspelled capability, so both kernels refuse it at load on that alone.
- `migration-capability-in-dependency` — a dependency's `capability: <Alias>.<Kind>` is rewritten: the entry's own check reports no migration of it, and the library's own verdict reports its deprecation at the library's line.
- `untagged-interpolation-entry` — `UNTAGGED_INTERPOLATION` for a plain string in the entry left holding a `${{` no hole can be read out of; `untagged-interpolation-in-dependency` — a library's, at the entry's `Telo.Import` reaching it and, by the library's verdict, at its own line; `untagged-interpolation-in-transitive-dependency` — a library no import of the entry names directly: at the library's own file, at the intermediate library's `Telo.Import` (its verdict) and at the library's own line (its verdict).
- `metadata-stamp-entry` — `METADATA_RESERVED_FIELD` for a loader stamp the entry's own document writes in `metadata`, at `metadata.<field>`; `metadata-stamp-in-dependency`, `metadata-stamp-in-transitive-dependency` — a dependency's: `telo check` reports it at the library's own line, and the run is refused with it at the entry's `imports:` entry first reaching it, with `data.writtenAt` naming where the library writes it.
- `mixed-entry-and-dependency` — several of the above in one manifest.
- `library-entry` — a `Telo.Library` as the entry: `telo check` reports nothing, and the run is refused by the load refusal rule's root-module group.
- `requires-newer` — `MODULE_REQUIRES_NEWER_RUNTIME` for `requires: { telo: ">=999.0.0" }`, its cover holding back the entry's other finding (a `CAPABILITY_UNKNOWN`); `requires-older` — `MODULE_REQUIRES_OLDER_RUNTIME` for a `restrictions:` ceiling `<0.1.0`, quoting the entry's reason; both refused by the load refusal rule's last group as `ERR_MANIFEST_VALIDATION_FAILED`.
- `requires-invalid` — `REQUIRES_INVALID` for an upper bound on the entry's own `requires.telo`, a malformed `host.node` range, an unknown host axis and an unknown axis; `restrictions-invalid` — `RESTRICTIONS_INVALID` for a `versions` range past the declaring version, a missing reason, an entry stating no bound, an entry leaving the version usable by no telo and a key no entry holds.
- `requires-in-dependency` — a gated library: the gate at the library's own line, its cover holding back the library's `CAPABILITY_UNKNOWN` in its own verdict while the entry's refusal at the `imports:` entry stands; `requires-invalid-in-dependency` — a library's malformed declaration: an error by its own verdict, a warning by the entry's analysis, and a ceiling on its `requires.telo` honoured rather than refused, so the run succeeds.

## Runners

No runner has a skip path or a tolerance list.

- `analyzer/nodejs/tests/check-conformance.test.ts` — the Node analyzer: `diagnostics`, as `telo check` reports them (`analyzeLoadedGraph`: the entry assembly plus the dependency stage).
- `kernel/nodejs/tests/check-conformance.test.ts` — the Node kernel: `runFails`.
- `analyzer/rust/tests/check_conformance.rs` — the Rust analyzer's API: `diagnostics`, through its twin of that assembly (`analyze_loaded_graph`).
- `kernel/rust/tests/check_conformance.rs` — the Rust kernel: `runFails`.

## What the Rust analyzer covers

The Rust analyzer reports YAML parse failures (`MANIFEST_PARSE_FAILED`) — every error the `yaml` package raises, in every document, read by a twin of its lexer, parser and composer — the loader's expansion refusals (`BRANCH_POSITION_INVALID`, `REPEAT_OUTSIDE_TEMPLATE`, `BRANCH_SHAPE_INVALID`, `REPEAT_SHAPE_INVALID`), the loader's file refusals (`MODULE_DECLARATION_MISSING`, `MODULE_DECLARATION_DUPLICATE`, `PARTIAL_KIND_FORBIDDEN`, `PARTIAL_GLOB_UNSUPPORTED`, `PARTIAL_NOT_FOUND`), every import failure of the module graph it walks — inline imports desugared, authored module-level `Telo.Import` documents, `include:` partials — (`INVALID_IMPORT_SOURCE`, `IMPORT_UNRESOLVED` with `data.sourceFailure`, `INVALID_IMPORT_TARGET`, `KIND_PREFIX_RESERVED`), version reconciliation (`MODULE_VERSION_CONFLICT`, `MODULE_VERSION_HOISTED`), the declared runtime requirements of the entry's module documents and of every library its imports reach (`MODULE_REQUIRES_NEWER_RUNTIME`, `MODULE_REQUIRES_OLDER_RUNTIME`, `REQUIRES_INVALID`, `RESTRICTIONS_INVALID`) against the running surface its embedded built-in vocabulary archive names, the gate covering every other analysis finding in a gated module's files, the capability roster (`CAPABILITY_UNKNOWN`, `CAPABILITY_NOT_DECLARABLE`), `INVALID_REFERENCE_FORM`, `UNTAGGED_INTERPOLATION` — the entry's own and a dependency's at the entry's `Telo.Import` reaching it — and `METADATA_RESERVED_FIELD` for a stamp written on a top-level document — the entry's own where it is written, a dependency's at the entry's `imports:` entry first reaching it — and the Rust kernel raises each from them (the stamp as `ERR_METADATA_RESERVED_FIELD`); it applies every core migration to every file at load, reporting the entry's own. Its `telo check` adds the dependency verdict: each imported library judged by those same passes as its own entry, a path-imported library's findings at its own lines (every severity), an artifact's errors as warnings at the entry's `imports:` entry reaching it. Node's other passes have no twin there yet, so a manifest any of them would report has no row. It may under-report and never over-report; where it does, no row can hold the manifest until a runner can pass it, and these are owed:

- `MODULE_VERSION_CONFLICT` and `MODULE_VERSION_HOISTED` key on an `oci://` ref, which no runner fetches, so no row holds them; each half's unit tests pin them.
- `PARTIAL_GLOB_UNSUPPORTED` needs a source that cannot list files, and every runner reads the filesystem, so no row holds it; each half's unit tests pin it.
- An import or a partial through a transport the Rust sources lack (http(s), a path inside an `oci://` artifact) is a host refusal of the Rust hosts (`ERR_UNSUPPORTED_MANIFEST_FEATURE`), the file naming it held back.
- `METADATA_RESERVED_FIELD` for a stamp written on a nested declaration (inline at a slot, a scope member, a template body entry) or on a `Telo.Import` declared as a scope member: Node judges every option of each as written and reports it where it is written (a dependency's at the import), while the Rust analysis has no nested judge and the Rust loader walks no scoped import; a scoped import's failure is unreported for the same reason.
- A `host:` axis is read and a malformed bound refused, but never judged: the Rust hosts supply no host version, so a `host.node` bound the running Node does not meet is refused by Node alone, and no row carries one the Node runners' host could fail.
- `UNTAGGED_INTERPOLATION` inside a nested declaration (`{ kind, … }`) or behind an expansion tag in the entry: Node reports it under the resource and path its normalization and expansion give it, which the Rust tree does not hold.

The vectors are not built-in vocabulary: nothing under `sdk/builtins/` reads them, and no runtime ships them.
