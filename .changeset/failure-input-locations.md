A failure can now say which of its inputs it is about, and a caller can say where it wrote those inputs. An `InvokeError` takes an optional `inputPointer` — a JSON Pointer into the inputs of the dispatch that raised it (`/expected/rows`) — and carries a `location` (`{ kind, name, module?, pointer? }`, the resource whose declaration holds the offending value and a pointer into it) that is only ever attached once: the first location given is kept. An invocation context may carry `inputsAt`, a JSON Pointer to where the calling resource's declaration writes this call's inputs (`/steps/1/inputs`); it belongs to the one dispatch carrying it, so a context derived from it for another call drops it unless restated. Neither member reaches a `catch:` branch's `error`, nor an error's JSON. A step body run with the place its list is written (`/steps`) sends every invoke step's `inputsAt` — branches, loop bodies, switch cases (keys escaped), and `try:` / `catch:` / `finally:` included — and a body run without one sends none — never the `inputsAt` its own invocation arrived with. A step whose target is an instance no dispatch identifies is sent no `inputsAt`, and marks a pointer raised there as one no dispatch exit may anchor, rethrowing the failure unchanged. The controller protocol gains these as additive members within generation `telo-7`: `inputsAt` on the `Dispatch.Invoke` / `Dispatch.InvokeResolved` context, and `inputPointer` and `location` on a failure.

`telo run` and a child run (`Test.Suite`, `Assert.Manifest`) now report a failure that left a step's dispatch at the place it was caused: `<file>:<line>:<col>  error  <message>  <code>`, the node inside the failing step's `inputs:` — the first difference of an `Assert.Equals`, the field an `inputType` refuses — in the innermost sequence that ran it, whether the target is declared inline or by `!ref`, and an inline boot target's `targets[<i>].inputs`. The kernel attaches the `location` where an unlocated failure leaves a dispatch, naming the resource whose controller issued it (an `ERR_EXECUTION_FAILED` wrap's diagnostic carries it too, as `RuntimeDiagnostic.location`), and `Kernel.failureDiagnostics(err)` answers the diagnostics a failure is reported with, each located one carrying the `origin` the analyzer's `locateDiagnostic` resolves. A position is given only where the running declaration provably is the written one — a step a template body declares, the parent an inherited kind builds, or a step list an `!if` / `!for-each` reshaped names the resource and gives no position. A refused child's stderr (controller protocol §9.2) writes that position before the located failure's line. The analyzer exports `writtenFailureSite`, the resolution behind it.
