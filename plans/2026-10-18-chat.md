# Chat

A fully featured AI chat a manifest declares as one node, whose upload button,
conversation sidebar and other input surfaces appear only when the agent behind it
offers them.

## Shape of the solution

- **`ui` owns the viewer's side.** A `Ui.Chat` composite (wire node `chat`) draws a
  conversation; a `Ui.Conversation` abstract provides what that conversation offers
  (`Ui.ConversationSpec`). `ui` defines the conversation contract — a sibling of the
  collection and action contracts — in its own vocabulary, and never imports `ai`.
- **The model owns what it accepts.** `Ai.Model` and `Ai.ModelStream` declare
  `accepts:`. The same declaration makes the provider refuse an unaccepted part and
  makes the upload button appear; nothing else restates it.
- **Storage is separate from presentation.** `ai-conversation` persists branching
  transcripts for any agent consumer; `ai-chat` serves `ui`'s conversation contract
  over an `Ai.AgentStream`, storing through `ai-conversation`.
- **Declared vs drawn.** Only what the user acts on before a reply is declared —
  attachments and conversation operations. Reasoning, tool calls, approvals,
  citations and usage are drawn from the events that arrive.

Dependency direction: `ai-chat` → `ui`, `ai`, `ai-conversation`, `record-stream`,
`blob`, `media-type`, `http-server`, `sse-codec`; `ai-conversation-sql` →
`ai-conversation` → `ai`, `sql`; `ui` and `ui-react` import no `ai`;
`apps/studio` and `apps/authoring-agent` → MIT packages only. Every new module is
MIT, with `license: MIT` and its own `LICENSE`.

No phase widens the manifest grammar (no new annotation, built-in key or fragment),
so no module takes a new `requires:` floor.

## Phase 1 — The conversation contract and `Ui.Chat`

**Before.** `ui` has no streaming node. A chat is hand-built as a custom component
through the component ABI, reading `host.fetch` by hand.

**After.**

Shapes in `ui`, each a named `Telo.JsonSchema`:

- `Ui.ConversationSpec` — what an endpoint offers before any event arrives:
  - `attachments` (absent when none): `{ accepts: [{ type, mediaTypes, maxBytes }], maxPerMessage }`,
    `type` one of `image`, `audio`, `video`, `file`.
  - `operations`: the subset of `list`, `rename`, `delete`, `branch`, `cancel` the
    endpoint supports.
- `Ui.ConversationEvent` — a closed union on `type`: `text-delta`,
  `reasoning-delta`, `content` (a completed part: media by attachment URL, a
  citation, a refusal), `tool-call-delta`, `tool-call`, `tool-result`,
  `approval-request`, `approval-decision`, `step-usage`, `turn-end` (usage and a
  `reason`: `stop`, `limit`, `approval`, `cancelled`, `failed`), `error` (`code`,
  `message`). The contract grows only by adding event types; a client ignores a
  type it does not know.
- `Ui.ConversationEntry` — one transcript entry as a viewer reads it: id, parent
  id, role, content parts (media by URL), tool calls and results, usage.

Kinds in `ui`:

- `Ui.Conversation` — a `Telo.Abstract` (Provider) providing a
  `Ui.ConversationSpec`.
- `Ui.Chat` — extends `Ui.Composite`. Fields: `conversation` (a ref to a
  `Ui.Conversation`), `source: { basePath }`, `title`, `placeholder`, `starters`
  (prompts offered on an empty conversation), and `show: { reasoning, toolDetail,
  usage, sidebar }`. Its controller reads the provided spec and emits a `chat`
  node carrying the spec and every presentation member, defaults filled by `ui`
  (every `show` switch on). A switch can only hide a surface; none can turn on what
  the spec does not offer.

The conversation contract (`modules/ui/docs/conversation-contract.md`), every path
under `source.basePath`:

| Route | Meaning |
| --- | --- |
| `GET /capabilities` | the same `Ui.ConversationSpec` the node carries, for non-`ui` clients |
| `POST /turns` | `{ conversation?, parent?, message, attachments, approvals? }` → `{ conversation, turn }`; `approvals` resumes a turn that ended with `reason: approval` |
| `GET /turns/<id>/events` | SSE of `Ui.ConversationEvent`, each frame's `id` its resume position; resumed with `Last-Event-ID` |
| `POST /turns/<id>/cancel` | stops a running turn (offered when `operations` holds `cancel`) |
| `GET /conversations` | cursor-paged list `{ rows, next }` (`list`) |
| `GET /conversations/<id>/entries` | cursor-paged transcript of one branch, `?leaf=` choosing the branch |
| `PATCH /conversations/<id>` | rename (`rename`) |
| `DELETE /conversations/<id>` | delete (`delete`) |
| `POST /attachments` | streamed upload → `{ id, url, mediaType, size }` |
| `GET /attachments/<id>` | the stored bytes |

Refusals use `ui`'s 400 validation envelope; 401 / 403 / other failures surface as
`ERR_UI_UNAUTHORIZED` / `ERR_UI_FORBIDDEN` / `ERR_UI_REQUEST_FAILED`, as for
tables and actions.

The `chat` node in `ui-react`:

- Transcript with markdown (CommonMark + GFM tables and task lists; no raw HTML;
  links obey the app-relative address rule) and highlighted code blocks with copy.
- Streaming text, a collapsible reasoning panel, tool-call cards with arguments and
  result, approval cards (approve / reject with reason) that resume the turn,
  citations, refusals, per-turn usage.
- Composer: multiline input, Enter to send / Shift+Enter for a newline, stop while
  a turn runs; attachments by button, drag-and-drop and paste, checked against
  `accepts` and `maxPerMessage` before upload, with per-file progress and removal.
- Edit-and-resend and regenerate (as branches when `branch` is offered, with a
  branch switcher on the entry), copy message, export transcript as Markdown.
- Conversation sidebar (when `list` is offered and `show.sidebar` holds): new,
  search, rename, delete, cursor-paged loading.
- Reconnects a dropped event stream with `Last-Event-ID`; an `error` event or a
  failed request is shown in place with its code.
- Keyboard-reachable throughout, with live-region announcements for streamed text.
- The chat's markdown and highlighting load as a separate chunk of the renderer
  entry, so a page without a chat does not fetch them.
- Every drawn element carries `data-telo-part` (added to the part list in the
  styling contract) and reads the existing theme tokens.

**Verify.**

- `ui`'s import graph holds no `ai`.
- A page document (`<mount>/_telo/ui/page?path=…`) with a `Ui.Chat` over a test
  `Ui.Conversation` returns a `chat` node with every presentation member present,
  written or defaulted (`Assert.Equals`).
- With `attachments` absent from the spec the node renders no upload control under
  any `show` setting; with `list` absent, no sidebar (ui-react unit tests).
- A `chat` node fed a recorded event sequence renders text, reasoning, a tool card
  and an approval card; dropping the stream mid-turn resumes from the last id.
- A page without a chat does not load the chat chunk.
- `modules/ui/docs/chat.md`, `conversation-contract.md`, the `ui-react` styling
  docs and the part-list test agree.

## Phase 2 — `accepts:` on models

**Before.** No model declares what content it carries. A provider refuses an
unsupported part at call time (`ERR_MODEL_CONTENT_UNSUPPORTED`); what each provider
carries is written only in prose tables in its docs.

**After.**

- `ai` declares the shape `Ai.AcceptedContent`: a list of
  `{ type: image|audio|video|file, mediaTypes, maxBytes? }`. `Ai.Model` and
  `Ai.ModelStream` both declare `accepts:` of that shape. Absent means text only.
  There are no defaults keyed on model ids.
- Every provider kind narrows `accepts` in its own schema to what its dialect can
  carry at all — the content of today's prose tables becomes that ceiling: `openai`'s
  chat-completions and responses pairs, `anthropic`'s messages pair.
- Every provider refuses a part outside the resource's own `accepts` with
  `ERR_MODEL_CONTENT_UNSUPPORTED`, before anything is sent — the same code and
  payload as today.
- `Ai.Agent`, `Ai.AgentStream` and `Ai.Buffered` publish their model's `accepts`
  in their reading (`resources.<name>.accepts`).
- The prose capability tables are replaced by `accepts` examples in the provider
  docs; `ai-model.md` documents the field.
- This is breaking for an application that sends media without declaring
  `accepts`; each module's fragment is `Added` and says so. Every in-repo manifest
  that sends media (tests, examples, starters, the authoring agent) declares it.

**Verify.**

- An `accepts` entry outside a provider's ceiling is `SCHEMA_VIOLATION` under
  `telo check`, at the line that wrote it.
- A model with no `accepts` refuses an image part with
  `ERR_MODEL_CONTENT_UNSUPPORTED` and makes no request; the same model declaring
  `image/png` sends it.
- `resources.<agent>.accepts` equals its model's `accepts` (`Assert.Equals`),
  through `Ai.Buffered` as well.

## Phase 3 — `ai-conversation` and `ai-conversation-sql`

**Before.** Each agent consumer stores history its own way; `agent-app` keeps user
and assistant text only, in one SQLite table, with no list and no branches.

**After.**

- `ai-conversation` (depends on `ai`): the `AiConversation.Store` abstract and its
  operations, each an invocable over a store ref:
  `AiConversation.Create`, `AiConversation.List`, `AiConversation.Entries`,
  `AiConversation.Append`, `AiConversation.Rename`, `AiConversation.Delete`,
  `AiConversation.StartTurn`, `AiConversation.EndTurn`.
- A conversation is a header (id, title, version, created / updated) and a
  branching transcript of `Ai.Message` entries, each naming its parent; editing or
  regenerating appends a sibling and keeps the old branch.
- `List` and `Entries` page by opaque cursor.
- `StartTurn` is a conditional write on the version: one running turn per
  conversation, a second refused with `ERR_CONVERSATION_TURN_RUNNING`. A stale
  version on any write is `ERR_CONVERSATION_CONFLICT`; an unknown id
  `ERR_CONVERSATION_NOT_FOUND`.
- Public ids carry a prefix: `cnv_…` for conversations, `ent_…` for entries.
- `ai-conversation-sql`: `AiConversationSql.Store` over a `Sql.Connection`, owning
  its tables.

**Verify.**

- Append on a branch, then regenerate: `Entries` with each leaf returns each branch
  intact (`Assert.Equals`).
- Two `StartTurn` calls on one version: exactly one succeeds, the other is
  `ERR_CONVERSATION_TURN_RUNNING`.
- Paging a 1 000-entry transcript and a 1 000-conversation list returns every row
  once.
- `modules/ai-conversation/docs/` and `modules/ai-conversation-sql/docs/` exist and
  match.

## Phase 4 — `ai-chat`

**Before.** Nothing serves the conversation contract.

**After.**

- `AiChat.Conversation` (Provider, extends `Ui.Conversation`): `agent` (an
  `Ai.AgentStream`), `store` (an `AiConversation.Store`), `journal` (a
  `RecordStream.Journal`), `blobs` (a `Blob.Store`), `detector` (a
  `MediaType.Detector`) and `attachments: { maxBytes?, maxPerMessage? }`. It
  provides the spec: `attachments.accepts` is the agent's published `accepts`, each
  entry's `maxBytes` the tighter of the model's and its own; `attachments` is
  absent when the agent accepts nothing; `operations` is all five.
- The turn, history and attachment operations are invocables that know no
  transport; `AiChat.Api` is a templated HTTP binding over them that speaks the
  conversation contract, mounted where `Ui.Chat`'s `source.basePath` points.
- A turn (`trn_…`) runs the agent and writes each translated
  `Ui.ConversationEvent` to the journal keyed by the turn, so
  `GET /turns/<id>/events` resumes with `Last-Event-ID` on any replica. Each
  `message` part is appended to the store as it commits; `message` and
  `provider-state` never cross the wire.
- Cancelling writes a stored fact the running replica observes; the turn ends with
  `reason: cancelled`. A replica dying mid-turn ends it as `failed` once its claim
  lapses, keeping every committed entry.
- An attachment (`att_…`) streams into the blob store under `maxBytes`; its
  detected media type must fall within the spec's `accepts`, else a 400 naming it.
  Its bytes are loaded into a `data` part only when a turn calls the model.
- A unit test reads both manifests and fails when an `Ai.AgentStreamPart` type is
  neither mapped to an event nor listed as dropped.

**Verify.**

- An application of `AiChat.Conversation` + `AiChat.Api` + `Ui.Chat` over the
  echo model fixture: a turn's events, its entries after the turn, and
  `GET /capabilities` match expected values (`Assert.Equals`).
- Over a text-only model, `/capabilities` has no `attachments` and the page's
  `chat` node draws no upload control; declaring `accepts: [{ type: image,
  mediaTypes: [image/png] }]` adds both.
- Two application instances sharing one SQLite file (store and journal through
  `record-stream-sql`): two turns started on one conversation — exactly one runs;
  events opened on the other instance resume from a given id.
- An upload over `maxBytes`, or of a type outside `accepts`, is a 400 and stores
  nothing; a large upload keeps memory bounded.
- No wire frame holds base64 media.
- A new `Ai.AgentStreamPart` type fails the mapping test.

## Phase 5 — `agent-app` on `ai-chat`

**Before.** `blueprints/agent-app` serves `POST /conversations/{id}/messages` →
`{ reply }` over a buffered agent.

**After.** `AgentApp.App` serves the conversation contract through `AiChat.Api`
and a `Ui.Chat` page, over an `Ai.AgentStream`, storing through
`ai-conversation-sql`. Its old routes are removed; the fragment is `Added` and
says so. The starter importing it moves with it.

**Verify.** The blueprint's tests run a turn through the contract and read the
page's `chat` node; the starter's tests pass.

## Phase 6 — Studio and authoring-agent on the contract

**Before.** `apps/authoring-agent` serves its own protocol (`GET /capabilities`
with `features[]`, `POST /chat`, `GET /chat/<turnId>/events`, …) and studio's panel
gates every surface on `features`.

**After.**

- authoring-agent serves its conversations through `ai-chat`; its `/chat` and
  capability routes are removed.
- Studio's panel becomes a client of the conversation contract, keeping its own
  React components; its feature gating reads `Ui.ConversationSpec`.
- Authoring-only operations (workspace changes and revert, editor-selection
  context, manifest runs) stay a separate contract of authoring-agent's own, never
  an extension of `Ui.ConversationSpec`.
- `plans/production-ready.md` is updated to the new protocol.

**Verify.** Studio's panel connects to a plain `ai-chat` endpoint (not
authoring-agent) and every conversation surface works; authoring-only surfaces
appear only against authoring-agent.
