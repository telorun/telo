A `Telo.Library` or `Telo.Application` doc may declare a `sources:` block beside `native:`: a map of named sources, each `{ version, url, archive, notices, entries }` with an optional `build`, whose entries are keyed by the module-relative path they produce and are either a file (`upstream`, `member`, and the pins `sha256` / `executable`) or a link (`target`). `url` is an `https://` template — plain `http://` only for a loopback host — and `archive` is `tar.gz`. `telo check` reports `SOURCE_URL_PLACEHOLDER_UNKNOWN`, `SOURCE_URL_INSECURE`, `SOURCE_ENTRY_UNCLAIMED` (a path no `native:` entry, platform-qualified controller `path=` or notice names), `SOURCE_ENTRY_UNPINNED` (a file entry with no pin), `SOURCE_LINK_TARGET_UNRESOLVED`, `SOURCE_LINK_CYCLE` (a link that never reaches a file), `SOURCE_ENTRY_INVALID`, `SOURCE_ENTRY_DUPLICATE`, `SOURCE_ENTRY_NESTED` (a path running through another) and `SOURCE_INVALID` for the entry module's own block; the analyzer exports the block's reader as `readModuleSources`, `resolveSourceUrl` and `sourceUrlProblem`. New `telo release stage [--pin] [--module <path>]` fetches each source's archive once per module, following at most ten redirects each vetted by the `url` rule before it is requested and bounded at five minutes, 512 MiB downloaded and 2 GiB decompressed; it extracts and verifies every file against its pin, writes it with its executable bit, creates link entries, and skips the fetch for a file already staged and matching its pin. `--pin` first writes `sha256` and `executable` into `telo.yaml` as a byte splice in block and flow mappings alike, keeping the file's line endings and leaving the rest of the file unchanged, and writes only when the edited text reads back with exactly the pins computed, replacing the file in one step. The kernel's `readTarGz` takes a `maxBytes` bound on the decompressed size.
