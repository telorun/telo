# `multipart`

Multipart bodies: combine several parts into one payload with the boundary framing servers expect, and split a received payload back into its parts.

Four kinds:

| Kind | What it does |
| --- | --- |
| `Multipart.Encoder` | An ordered list of parts → one framed byte stream, plus the media type to send it under. |
| `Multipart.Decoder` | A received payload + its media type → the parts it contains, collected whole. |
| `Multipart.Reader` | The same, read incrementally — a stream of parts, each a stream of bytes — for uploads too large to hold. |
| `Multipart.ReadPart` | One named part, streamed — the parts before it discarded, the rest of the payload never read. A single-file upload. |

`Multipart.Part` is the shape of a streamed part (`{ content, headers, contentType?, name?, filename? }`), exported for a contract that passes one on.

## Why use this

A file API that takes metadata and content in one request — Google Drive's `uploadType=multipart`, an S3-style form upload, any HTML form with a file field — needs a body that CEL cannot build. String concatenation is text-only, so a binary part cannot survive it, and it is whole-payload, so a large part must be held in memory to be joined.

## The content type is an output

The boundary is generated by the encoder and has to appear in **both** the framing and the `Content-Type` header. So the encoder returns them together:

```yaml
- name: Encode
  inputs:
    subtype: related
    parts:
      - contentType: application/json
        content: '{"name":"report.png","parents":["folder-1"]}'
      - contentType: image/png
        filename: report.png
        content: !cel "steps.Render.result.bytes"
  invoke:
    kind: Multipart.Encoder

- name: Upload
  inputs:
    url: https://www.googleapis.com/upload/drive/v3/files
    method: POST
    query: { uploadType: multipart }
    headers:
      content-type: !cel "steps.Encode.result.contentType"
    body: !cel "steps.Encode.result.output"
  invoke: !ref DriveUpload
```

Writing `content-type: multipart/related` by hand there would omit the boundary, and the server would find no parts — a request that succeeds while uploading nothing. Returning the header beside the bytes is what makes that unrepresentable.

`boundary` is also returned, for a caller that must reproduce the header itself (a signature over the request, say).

## Parts

Each part takes `content` plus optional `contentType`, `name`, `filename` and `headers`.

- **`content`** is a string (encoded UTF-8), raw bytes, or a **byte stream**. A streamed part is written through as it is consumed, so a part larger than memory costs one chunk — which is the reason this is a module and not CEL.
- **`name`** becomes `Content-Disposition: form-data; name=...`, which is what a form server keys on. A `related` part is positional and needs none; a part with neither `name` nor `filename` gets no disposition at all rather than an empty one.
- **`filename`** is what makes a server treat the part as an uploaded file. It is independent of `name`: a part
  declaring only `filename` decodes back with no `name`, rather than with the file name standing in for it.
- **`headers`** are merged **over** the derived ones, so an explicit header always wins.

`subtype` selects `form-data` (default), `related` or `mixed`. Same framing throughout — only the media type differs.

## Decoding

`Multipart.Decoder` takes the payload and the media type the sender used, because **the boundary lives in the header, not in the bytes**. A content type with no `boundary=` parameter is an error rather than a payload with zero parts; the two are otherwise indistinguishable to a caller.

Parts come back as a list, each with `content` (bytes), `headers` (lowercase keys), and `contentType` / `name` / `filename` where the part carried them.

## Limits

The three inbound kinds take three limits, each an integer of at least 1:

| Limit | Counts | `Decoder` default | `Reader` / `ReadPart` default |
| --- | --- | --- | --- |
| `maxPartBytes` | One part's content — not its headers or framing. | 8 MiB | none |
| `maxParts` | The parts in the payload. | 1000 | 1000 |
| `maxTotalBytes` | Every byte read: framing, headers and content. | 16 MiB | none |

The decoder holds each part whole to return it, so all three have defaults; the reader and `ReadPart` hold nothing, so their byte limits apply only when set. A part `ReadPart` skips counts toward them. A limit stops the read as soon as the bytes read show it is crossed, never after collecting the payload.

## Failures

The inbound kinds declare two codes a route can map:

- `ERR_MULTIPART_MALFORMED` — `error.data.reason` is `boundary-missing`, `truncated`, `header-malformed` or `header-too-large`.
- `ERR_MULTIPART_LIMIT_EXCEEDED` — `error.data` is `{ limit, max, part?, name? }`, `limit` naming the input that was exceeded.

`ReadPart` adds a third, `ERR_MULTIPART_PART_MISSING` with `error.data` `{ name }`, for a payload that reaches its closing boundary with no part of that name.

A route whose handler is one of them must cover its codes (or declare a catch-all), or `telo check` reports `UNCOVERED_THROW_CODE`. The decoder raises them from the call; the reader raises all but a missing boundary as its streams are drained; `ReadPart` raises one met before the part from the call and one met inside it from the read of its `content`. Details: [`docs/decoder.md`](docs/decoder.md), [`docs/reader.md`](docs/reader.md), [`docs/read-part.md`](docs/read-part.md).

## Not a `Codec`

No kind here extends `Codec.Encoder` / `Codec.Decoder`. That contract's input is a single `input` stream; multipart takes an ordered list of parts with per-part headers, and decoding additionally needs the boundary from outside the bytes. Extending it would claim substitutability at every `Codec` slot and be false — a consumer holding this as a `Codec.Encoder` would pass `input` and get nothing back.

## Reader vs Decoder

`Decoder` buffers and is bounded by its limits (8 MiB a part, 16 MiB in all); `Reader` streams and is bounded by one chunk. Use `Decoder` for form fields and anything you want as a plain value; use `ReadPart` for an upload carrying one file, and `Reader` for one carrying several. Skipping a part in `Reader` is safe — advancing discards the remainder rather than leaving the cursor mid-part.

## Receiving an upload

`Http.Server` accepts a multipart body out of the box, as **raw bytes**, so a route receiving one declares a stream request body and passes it straight to a decoder. Declaring your own `contentTypeParsers` entry for a `multipart/` type still works and takes precedence. See `tests/over-http.yaml`.

The server holds every request body to its own `maxBodyBytes` (1 MiB by default), multipart included, so an upload route over that raises the route's `maxBodyBytes` together with the decoder's limits — see `tests/over-http-limits.yaml`.
