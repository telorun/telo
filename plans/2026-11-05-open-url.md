# Opening the app in a browser

## Problem

A Telo web app cannot open itself. `telo run` logs `Listening  server.address=0.0.0.0  server.port=8080  url.scheme=http` and leaves the person to put a URL together. `--open` opens only the inspector, and only together with `--inspect`. A terminal sign-in has the same gap: `OAuthClient.Authorization` returns a consent `url`, and the manifest can only print it.

Locally an app also has no public URL to name: a `Telo.PublicUrl` must be set by hand (`TELO_NEED_SITE__URL=http://localhost:8080`), because `telo run` supplies no template the way the runners do.

The app decides when a page should open. The person running it approves or rejects. No flag decides it.

## `Telo.OpenUrl`

A new built-in `Telo.Invocable` in `sdk/builtins/`, implemented by the kernel. It needs no import.

- **Input:** `url`, a `Telo.Url` with scheme `http` or `https`. A URL carrying a user or password is refused with `ERR_INPUT_INVALID`, and is never shown or opened.
- **Output:** `outcome` is one of:
  - `opened`: the person approved and the opener started;
  - `declined`: the person said no;
  - `repeated`: this host session already answered for this exact URL, so nothing was asked or done;
  - `unavailable`: no one could be asked;
  - `failed`: the opener could not start, with a `reason`.
  
  No outcome is an error, so a missing browser never stops an app.
- **Always logged:** every call logs one `info` record (`telo.url.open`) with `url.full` and the outcome. The URL is in the log whatever happened.
- **Event:** every call emits `Kernel.UrlOpenRequested` (`{ url, outcome }`), so a consumer of the debug stream sees the request.

The app asks by placing a call in `targets:` after the server. Targets run in order and each is awaited. `Http.Server`'s `run()` returns only after it is listening, so the page loads when the browser opens. A sign-in calls it as a step with the consent `url`.

## Who answers

The kernel takes an optional open-url hook from its host, beside the existing hook that asks for missing inputs. A kernel with no hook answers `unavailable`.

- **`telo run` at a terminal** (stdin and stderr are TTYs, no `--no-input`) installs the hook. It writes `<app name> wants to open <url> in your browser. Open? [Y/n]` on stderr and reads one line, exactly as the missing-input prompt does: it puts back the bytes typed past the line break, and Ctrl-C raises SIGINT. An empty answer or `y` opens, `n` declines.
  - **Opening:** `$BROWSER` first, otherwise the OS opener. Inside VS Code remote, `$BROWSER` is VS Code's helper, which opens the page in the local browser and forwards the port.
  - **A failed launch** returns `failed` with the reason, and the CLI prints the URL beside it. Today's opener ignores a failed spawn; that is fixed for both its callers, the inspector included.
  - **Answers last for the session** and are keyed by exact URL. A `--watch` reload asking for the same start page gets `repeated`. A new consent URL is a new question.
- **Every other host** answers `unavailable`, and the logged record carries the URL. That covers `--no-input`, runner sessions, CI, pipes, the test suite and the Rust CLI.

## A public URL in local runs

At a terminal, under the same check as the prompt, `telo run` supplies `TELO_HOST_PUBLIC_URL_TEMPLATE=http://localhost:{port}` and `TELO_HOST_PUBLIC_URL_SECONDARY_TEMPLATE=http://{label}.localhost:{port}` when the environment (env files included) sets neither. A need's own variable still wins, as it does today.

Without a terminal nothing is supplied. A container missing its variable is still refused with `ERR_NEED_UNMET`, rather than given a localhost redirect URI. `localhost` and not `127.0.0.1`, because `{label}.localhost` resolves to loopback in browsers and an IP literal has no such form.

## `Http.Server`'s `Listening` record

The record gains `url.full`, the socket's own URL: `http`, or `https` under `tls`. `0.0.0.0` and `::` are written as `localhost`, an IPv6 literal in brackets. It is the socket, not a public address, and `modules/http-server/docs/log-events.md` says so.

## The chat example

`examples/chat` declares `site: { kind: Telo.PublicUrl, parameters: { port: http, primary: true } }` and lists an inline `Telo.OpenUrl` call on `resources.site.url` after `!ref server` in `targets:`. Its description stops telling the reader to open the address. Its tests supply `site` through `App.Instance` `needs:`, and its `requires: telo:` floor moves to the release that carries `Telo.OpenUrl`, verified by execution as the root guide requires.

## Rust half

`kernel/rust` refuses a `Telo.OpenUrl` resource with `ERR_UNSUPPORTED_MANIFEST_FEATURE`, naming the kind. It owes the kind and the hook. `cli/rust` installs no hook.

## Verify

1. In a VS Code Remote-SSH terminal, `pnpm run telo --watch ./examples/chat`, with no address set: the prompt appears after `Listening`, `Y` opens the chat in the local browser, and the record shows `url.full=http://localhost:8080`. Editing a file reloads without asking again. The same run answered `n` prints the URL and runs on.
2. `pnpm run telo --no-input ./examples/chat` refuses with `ERR_NEED_UNMET` naming `TELO_NEED_SITE__URL`. Set that variable and it starts, asks nothing, and logs `telo.url.open` with outcome `unavailable` and the URL.
3. `tests/open-url.yaml` (`Assert.Equals`): with no hook the outcome is `unavailable`, and a URL with a password is refused with `ERR_INPUT_INVALID`.
4. CLI unit tests over recorded streams: an empty answer, `y`, `n`, the same URL twice in one session (`repeated`), a different URL (asked), no TTY (not asked), and an opener that fails to spawn (`failed` with the reason).
5. `npx @telorun/cli@<previous> check examples/chat` with the `requires:` block removed reports the unknown kind. With the block back it reports `MODULE_REQUIRES_NEWER_RUNTIME`.

The editor half (studio and the VS Code extension offering an Open button for `Kernel.UrlOpenRequested`) is a separate change.
