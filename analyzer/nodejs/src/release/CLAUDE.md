# Release model, Telo half — guide

Loaded when working under `analyzer/nodejs/src/release/`. **The release model itself — units, anchors, fragments, ledger, edge graph, groups, version planning, candidates, changelogs — is `@telorun/release`** (`release/nodejs/CLAUDE.md`, MIT, off the telo line). The RULES every change follows (a fragment for every change to a released unit, pre-1.0 minors) are in the root `CLAUDE.md`; the evidence half of the `telo` ecosystem, publishing and the Telo-only subcommands are in `cli/nodejs/CLAUDE.md`. Guide: `docs/extend/releasing-modules.md`.

This directory is the **pure, browser-safe half of what only Telo has**: the `telo` ecosystem adapter, the Telo `telo-workspace.yaml` reader, and the module-shaped pieces. Nothing here plans a version.

**The `telo` adapter** (`telo-adapter.ts`, registered beside the shipped `npm` / `cargo` / `docker` / `helm` adapters). An anchor holding a `telo.yaml` whose module doc carries a `metadata.version` is one Telo module. **A module lists no anchors for its own packages**: each controller locator's `local_path` names a source inside the module, and the nearest `Cargo.toml` (for `pkg:cargo`) or `package.json` (any other) at or above it — never above the module — is a package the module ships, as is each `sources:` `build.cargo` crate; their version files carry the module's version. So moving a controller to another directory needs no marker change. A module with a `Dockerfile` is an image only when its entry lists `[telo, docker]` (or a `docker` anchor); no code here reads a Dockerfile.

**The payload digest** (`payload-digest.ts`) is the per-layer digest of a module's artifact, taken with the framing-independent content digest the published `layers:` index carries, nested under the module's `telo` anchor in the ledger (`telo: { ".": { manifest, … } }`). Taking it from the bytes is what makes it fire for an inlined sibling, a shared-library fix or a lockfile-only bump, none of which touch a file under the module's directory; the controller build's metafile supplies the inline edges. An image's base image is deliberately outside its digest. `LOCALLY_DERIVED_LAYERS` are keys the registry cannot answer for, which `verify` preserves.

**Destinations** (`destinations.ts`): a module's destination is its resolved `registry` plus its own directory name, ASSIGNED, never derived from an importer's path — an import of one workspace module by another is written as the target's destination, `<destination>@<version>#<pin>`, so modules at different depths and bases import each other relatively. Path resolution against the importer's destination is left only to a library nested inside the importer's directory. `DESTINATION_COLLISION` (two modules on one ref, over every `order` row) and `NO_DESTINATION_KNOWN` (a `telo`, `docker` or `helm` anchor whose cascade ends with no `registry`) are checked at plan time, before any payload is built. The `telo` cascade is anchor → `release.ecosystems.telo` → `--registry` → `TELO_OCI_REGISTRY` → the base the module's own ledger entry recorded, the ledger last: a workspace that authors its destination has said where it publishes. Plan-time `IMPORT_TARGET_NOT_RELEASED` and `WORKSPACE_MODULE_NESTED` are the module import graph's.

**The version stamp** (`version-stamp.ts`) writes a module's version into `telo.yaml` — the module doc's `metadata.version` and the `pkg:npm` pins naming the module's own package — by splicing over the scalar's span (`yaml-source-edit.ts`), so a bump is a one-line diff. A version in a shape it cannot address is a hard error. The module's npm and Cargo packages are written by their own ecosystems' handlers.

**The marker, as a Telo host reads it** (`workspace-config.ts`, `workspace-schema.ts`): `telo-workspace.yaml` at the repo root; **its location is the anchor** for every unit key, ledger entry, fragment path and the `.telo` cache, and **every FIELD lives in a block scoped to what it governs**. The `release:` block (`units`, `groups`, `ignore`, `maxBump`, `ecosystems`) is `@telorun/release`'s to read, against the ecosystems the host serves — this reader passes it the Telo adapter set and adds the repo-shaped `WORKSPACE_ENTRY_MATCHES_NOTHING` / `_SHADOWED` / `WORKSPACE_MARKER_SHADOWED` the editor shows. The `env:` block (`roots:`, `files:`, each file a filename or `{ name, sensitive }`) is Telo's alone. **What `env:` MEANS is not this directory's**: the walk, the env-file format and the sensitive mark live in `analyzer/nodejs/src/workspace-env/`, one answer the CLI, a packaged application and Studio all run through a read their host injects. **Sensitive** means a file holds values that must not be committed or synced; it decides where `telo env template` writes a secret, the warning `telo run` prints for a secret read from a file without it, and which files whole-tree copies leave out. It is unrelated to log redaction. The file and every block are optional, so a marker of comments only is valid — which is what the runner seeds.

**The reader is lenient and the strict half is diagnostics; which are FATAL is the caller's policy.** `telo release` refuses on any error; **`telo run` consumes `env:` alone** — an error under `release:` is printed and the run proceeds, while one INSIDE `env:` fails the run, because degrading to the marker-wide bound would WIDEN the walk. An unknown top-level BLOCK is a warning; a near-miss of a known one is an error. `release.modules` and `release.registry` are recognized and refused, naming `release.units` and `release.ecosystems` (`WORKSPACE_MODULES_MOVED`), and a top-level `modules:` is the same code. Gitignore matching is injected (`PatternMatch`) because the grammar is `@telorun/glob`'s and the analyzer is browser-safe.

## Where to look

- "will this change bump anything, and why?" → `release/nodejs/src/release-plan.ts`; for a module, the payload digest here and `cli/nodejs/src/bundle/module-payload.ts` (the one payload builder publish and release share).
- "what may the marker say, and who reads which half?" → `release/nodejs/src/marker-schema.ts` and `release-settings.ts` (`release:`), `workspace-schema.ts` / `workspace-config.ts` here, `analyzer/nodejs/src/workspace-env/`, `packages/ide-support/src/workspace/` (diagnostics, completion), `docs/guides/workspaces.md`.
- the Telo ecosystem's evidence half → `cli/nodejs/src/release/` (`workspace.ts` discovery, `evidence.ts`, `telo-host.ts`, `targets.ts` the cascade + import graph).
