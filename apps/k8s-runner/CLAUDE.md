# k8s runner — package guide

Loaded when working under `apps/k8s-runner/`. The backend-neutral session model (the session, status/run events, workspace, env split, co-resident agent, suspension) is in `packages/runner-core/CLAUDE.md` — read it too. Repo-wide rules live in the root `CLAUDE.md`.

## Routing layer

**THE ROUTING LAYER IS A SEAM, because Ingress and Gateway API are both current** (`apps/k8s-runner/src/k8s/routing/`, `SessionRouter`): neither is a migration target for the other, clusters ship one, the other or both, and a runner hardcoding either is unroutable on the rest — silently, since routing objects nothing reconciles are created with no error, leaving a healthy pod and a 404 on every URL. It stays inside the k8s backend: docker publishes host ports through its own proxy, and `runner-core` owns the backend-neutral `/v1` contract, where "Ingress or HTTPRoute" is not a distinction that exists. `SESSION_ROUTING_MODE` is `auto` (default) / `ingress` / `gateway` / `none`, and **`auto` resolves on what is CONFIGURED before what is INSTALLED** — a named Gateway, then an IngressClass, then the cluster's own APIs — because Gateway API CRDs are frequently present without being the intended path, so their presence is not evidence of intent; two usable layers with nothing configured is genuinely ambiguous and **refuses at boot**, once, rather than 404-ing every session afterwards. Resolution is also where a certificate configured for a layer that will never present it is refused (`SESSION_INGRESS_TLS_SECRET` under gateway mode, where the cert belongs to the Gateway listener).

**Gateway mode publishes ONE HTTPRoute PER PORT**, forced by the API rather than chosen: `hostnames` is a property of the whole route while a rule matches on path and never on host, so one route carrying every session hostname would send them all to whichever rule matched `/` first — an Ingress rule owns its host, which is why that layer needs one object; the consequence is that a reload dropping a port must DELETE that port's route, where an Ingress merely loses a rule on replace.

**Route health is its own axis** (`RouteState` — `pending` / `programmed` / `unprogrammed` — on the `/v1` stream), never folded into `ReachabilityState`: reachability dials the workload's own address and proves only that the app is LISTENING, so the two fail independently and one is the user's manifest while the other is the operator's cluster. Gateway API answers it precisely, from the `Accepted` / `ResolvedRefs` conditions its controller writes (`NotAllowedByListeners` is the listener that does not admit the session namespace); Ingress has no rejection signal at all, so there an unclaimed route is caught by the timeout rather than by a reason the cluster gave. Reported, never fatal — a slow controller and an absent one look alike for the first few seconds. The session NetworkPolicy peer is `sessionRouting.dataPlaneNamespace`, named for the DATA PLANE rather than an ingress controller because the two layers put it in different places; without it the route programs correctly and the workload is still unreachable, which is the confusing half of the same failure.

**A routed session is a template-mode host of `Telo.PublicUrl`** (`routing/session-endpoints.ts`): `publicUrlTemplateEnv` sets `TELO_HOST_PUBLIC_URL_TEMPLATE=https://{port}-<session>.<base>` and `_SECONDARY_TEMPLATE=https://{label}--{port}-<session>.<base>` on every app container, which each run inherits from its supervisor (a Run's env may override them: whoever sets a host value there is acting as the host). `hostsForPort` is what both routers publish for a port: its own host, then each announced `publicHosts` entry that is one label ending in `-<session>.<base>` (so the wildcard certificate covers it); a host outside that suffix came from the session's env and is not routed. A session republishes its routes when a port's hosts change, with the pod unchanged. Patterns and `customDomains` are never routed here — the session env's author is their host.

## Sessions: the pod, the claim, the supervisor

**A session's files are a PersistentVolumeClaim, its pod is disposable** (`k8s/session-volume.ts`, `k8s/session-workload.ts`). Each session gets one claim, `telo-session-<id>`, labelled with the session id and `RUNNER_MANAGED_BY` and owned by NOTHING — an owner reference to the pod would make suspend delete the workspace. It holds `workspace/` (mounted at `/workspace` by every container, so the `.telo` cache the workspace marker anchors persists and a resume starts warm), `telo/` (the telo releases apps asked for, below) and `agent/` (mounted for the agent alone at `/var/lib/telo-agent-state`, outside the workspace, with `TELO_HOST_STATE_DIR` pointing at it). The pod's `supervisor` init container creates the directories as the pod's user, because a `subPath` the kubelet creates is root's. Suspend deletes the pod and keeps the claim; `destroy` deletes both; the Service, routing objects and session-container policies are owned by the pod and go with it. **A replacement pod is created only once the old one is gone** (`deletePodAndWait`): the claim is ReadWriteOnce and the agent's SQLite state must never have two writers.

**One `apps` container runs every app, and the pod never changes with the app set** (`k8s/pod-spec.ts`): Kubernetes cannot change a pod's container list, so a container per app made every app added or removed recreate the pod — and the workspace and agent in it. The container's process is the session supervisor in launcher mode (`supervisor --slots 9`: nine independent generation-1 supervisors on consecutive ports, eight app slots plus a tooling slot; the protocol is unchanged and a supervisor still runs one thing). The init container copies `/opt/telo-runner/supervisor` out of the runner's own image (`RUNNER_SUPERVISOR_IMAGE`; the Dockerfile's `supervisor` stage cross-builds it static per `TARGETARCH`) into an `emptyDir` the container mounts read-only. It has no TTY, no stdin, no session env and no shell; it carries `TELO_SUPERVISOR_LISTEN=0.0.0.0:9330` (the launcher adds the slot to the port) and ONE `TELO_SUPERVISOR_TOKEN` minted at pod creation. **The pod spec and the `telo.run/app-slots` annotation are the durable home** — the store holds no secret and the slot of an app is not derivable, so an adopting runner reads the token, the agent's `tokenEnv` value and the slot of each app back from the pod. `setApps` takes and frees slots (`assignSlots`: kept apps keep theirs, a new one takes the lowest free), rewrites the annotation and republishes the routes; only an agent change still recreates the pod. More than `APP_SLOTS` (8) apps is `400 too_many_apps` (`RunnerBackend.maxApps`). Supervisor ports (`9330+slot`) and inspect ports (`9230+slot`) are reserved statically, since one network namespace, so `reservedPorts` names them to core (`400 port_conflict`) and a reload declaring one is `rejected`. The chart's session NetworkPolicy admits the runner's namespace on every port, so no rule names them.

**An app's telo version is a release binary, not an image** (`k8s/telo-release.ts`): the container runs the session's picked image (or `RUNNER_IMAGE`) and an app naming a version is run as `/var/lib/telo-releases/<version>/telo`, which the tooling slot downloads from `RUNNER_TELO_RELEASES_URL` (default the GitHub releases), checks against the release's `checksums.txt` and moves into place whole. The directory is the claim's `telo/` subPath, so a resume finds it. An app naming none runs the image's own `telo`. An unreleased build (`X+unreleased`) has no binary and is refused. The apps container needs `node` and `tar`, which the kernel image has, and egress to the release URL; the container's limits are shared by every app in it.

**A container that ends is the session's failure, never a run's**: a terminated container status, a pod that fails or is deleted, or a supervisor connection ending for good (`restarted`, `unauthorized`, `superseded`, `protocol_error`) reports `failed` naming the container; core removes the pod and `resume` rebuilds it over the same claim.

**Adoption** (`backend.ts` `adopt`): the session's pod by label; one not Running, or whose slots are not the stored app set or whose agent is not the stored one, is removed and the session suspends. **`generation_mismatch` is realised as suspend-then-resume, not an inline recreate**: the stale pod is removed and `adopt` resolves `undefined`, so the session is `suspended` and the editor's `resume` builds a current pod. Core adopts before the runner listens, and recreating pods there would hold the boot for minutes past the liveness probe; supervisors are dialled with a 10 s bound for the same reason. A mismatch on a LIVE workload fails the session (resumable) through `onStatus`, never a hang. A pod with an ended container makes `adopt` throw, naming it; the session fails and the orphan sweep removes the pod, since it is not live — as does the next `create`, which first removes every pod carrying the session's label.

**The orphan sweep** (`reapOrphans`, called by core after adoption) deletes managed pods of sessions not live, session-container pods of them, claims of sessions the store does not know, then unreferenced workspace ConfigMaps; it throws, naming every object it could not remove.

## Infrastructure errors

**The k8s backend summarizes its own infrastructure errors before they reach a client** (the docker one has no equivalent yet): a k8s `ApiException`'s message is the whole HTTP dump (raw `Status` body, headers) and a start failure's message is published verbatim as the session's terminal status, so a missing RBAC grant printed the runner's ServiceAccount, the audit id and the flowschema UIDs in the editor. The client now gets the operation, the status and the API's one-word `reason`; the exception rides along as `cause` for the log, so EVERY wrap on a failure path must forward it. Two things are read and never echoed — a `403`'s admission message, only to tell an RBAC denial from a `ResourceQuota` rejection, which are the same code and the same `reason` and want opposite actions — and a `code` is a status only when it is a NUMBER in the HTTP range, since `ECONNREFUSED` and a `DOMException`'s `ABORT_ERR` land in the same field and mean the apiserver was never reached.

## Session containers

**A session's container is a pod beside the session's, never inside it, and never with credentials in the session.** The engine core serves (`packages/runner-core/CLAUDE.md` § Session containers) is answered here by pods in the session namespace (`k8s/session-container-{engine,pod}.ts`): the namespace enforces PodSecurity `restricted`, so a pod runs as a numeric non-root user (a named or root `User` is a 400 naming it, refused before the API is asked, and a pod admission still refuses is reported as the Pod Security standard's refusal — classified from the 403's admission message, which is never echoed). Relaxing the posture to admit an image is not the repair: it would loosen the session pods' namespace too. **Pods carry `run.telo.session`, not `telo.run/session-id`**, because the session Service selects on the latter; they carry the managed-by label so the boot reaper takes them, and an owner reference to the session's live pod (looked up per create, skipping one being deleted) so the cluster collects them with it. **Reachability is two NetworkPolicies per session**, both owned by the session's pod and deleted by `endSession` when the session ends: the namespace policy denies pod-to-pod and private-range egress, and policies only add, so an ingress policy on the containers and an egress policy on the session's pods open exactly that path. A session's pod is replaced on resume and on an app-set change, so a create re-owns a policy whose owner is not the current pod rather than leaving it to be collected. The node pulls an image at pod start, so image inspect answers "held" and pull is already done; the start is where an unpullable image fails, with the kubelet's waiting reason.

## Chart and image

**A HELM CHART's version is the version of the package it deploys**, in both `version` and `appVersion` — `scripts/stamp-chart-version.mjs` writes them from `package.json` inside `version-packages` (right after `changeset version`, so the bump is reviewed in the Version PR) and `pnpm run check:charts` fails a PR where the two disagree. A chart here has no independent lifecycle: it deploys one image built from one workspace package, that package's version is already what the image's immutable tag is cut from, and a chart-only edit ALREADY forces a package bump because the changeset gate attributes a changed file to its nearest package directory — so a second number could only ever be a way for the chart and the image to disagree about which build is installed. The chart is pushed as an OCI artifact (`oci://ghcr.io/telorun/charts/<chart>`) from `publish-docker.yml`, gated on the same version-moved test as the image's `:<version>` tag and ordered after it, so a chart never names an image the run did not just build. **A chart is named after its component, never prefixed with the vendor** (`k8s-runner`, matching `telorun/k8s-runner` and the unprefixed module refs), and its NAME is not what its objects are named after: the name helper returns a literal, so renaming a chart moves no object — which matters because that literal is also the runner's default `RUNNER_MANAGED_BY`, the label its orphan reaper selects on.

**Structured settings are two mounted files, not env** (`config.ts`, `config-file.ts`): the session file (`SESSION_CONFIG_FILE` — `resources`, `containers`, `baseImages`) and the agent file (`AGENT_CONFIG_FILE` — the agent's settings, read by runner-core's `loadAgentFromObject`, and its `resources`, split off here), each rendered by the chart with `toYaml` into a ConfigMap whose checksum rolls the runner. Both are CLOSED — a key the runner does not read refuses to boot — because Helm drops an unknown values key silently and an env var nobody reads does the same, so a typo used to become a default. Secrets stay env (`AGENT_SECRET_<NAME>`), so no secret sits in a ConfigMap; the variables the files replaced refuse to boot, naming the key. **A container has a CPU limit only when one is configured** (`limits.cpu` absent is plain Kubernetes "none"), and requests are configured apart from limits and held at or below them; that is why the session quota names no `limits.cpu`, which would refuse every pod without one.

**A runner bakes the kernel it was built against.** `apps/k8s-runner`'s `TELO_SESSION_IMAGE` build arg fixes `RUNNER_IMAGE` at image build time, and the chart's `session.image` defaults to empty so the baked value wins. A mutable `latest-slim` there made a session's kernel whatever was last released, independently of the runner that was tested with it — which is how a kernel two CLI releases old ran a module published against a newer one and failed on syntax it had never heard of (the case `requires:` exists to name).
