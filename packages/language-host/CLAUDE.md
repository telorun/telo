# Language host — package guide

Loaded when working under `packages/language-host/`. Repo-wide rules live in the root `CLAUDE.md`; the protocol spoken to engines is `packages/editor-protocol/README.md`; the engine itself is `packages/language-server/CLAUDE.md`.

## What it is

`@telorun/language-host` is the editor-side half of telo's language tooling, shared by every editor host (VS Code, studio). It decides **which telo version** each module is edited against, obtains that version's engine (`@telorun/language-server@X`), and presents one LSP endpoint in front of however many engines are running. It is **version-agnostic**: it knows nothing about Telo manifests, depends only on `@telorun/editor-protocol` and `vscode-languageserver-protocol`, and never on the analyzer, ide-support or an engine — a host must be able to run engines older and newer than itself. It is published and deliberately **not** on the telo version line, since one host drives many generations.

**Browser-safe**: `tsconfig.json` has no Node types, and the code uses only globals browsers and Node ≥20 share — `fetch`, WebCrypto `crypto.subtle`, `DecompressionStream`, `TextDecoder`, `ReadableStream`. The test suite runs twice (`vitest.workspace.ts`), under Node and under a jsdom environment.

## The pieces

- **Catalog** (`version-catalog.ts`): the npm package document of `@telorun/language-server` (the full document — the abbreviated install form drops `teloEditorProtocol`). Offered = plain versions whose `teloEditorProtocol` is a generation this host speaks, not deprecated, with a `sha512` integrity; every other published version is recorded with its reason, so a pin on it can say why it is refused. The bundled engine is always offered, under the identity its handshake reports. The registry read is bounded (15 s); failing that, the last cached catalog, else the bundled engine alone. A fresh catalog the cache cannot store is still used, and the cache's failure reported on its own.
- **Engine identity** (`plain-version.ts`): an engine is known by its `serverInfo.version` — `X` for a release, `X+unreleased` for a build made while `X` is still pending. Identities are ordered, and tested against intervals, by semver precedence (build metadata ignored), and told apart by the whole string. The bundled engine's identity is read from its handshake, never stamped by the host, so a label can never disagree with the code it names.
- **Selection** (`select-version.ts`): ONE function for every host. Rule 1: the owner declares `requires: telo:` → the lowest known version its interval and every closure interval accept. Rule 2: it declares none → the bundled version if the closure accepts it, else the lowest version all accept. Rule 3: nothing accepts → the bundled version, reported as unsatisfiable. On a precedence tie (a published `X` and a bundled `X+unreleased`) the published engine is the lower candidate; only rule 2's "the bundled version" picks the bundled one. A pin names an identity exactly; it is always honoured when offered and refused with its reason otherwise. Intervals come normalized from the engine (`telo/requirements`); range TEXT is never parsed here, and versions are compared by a strict plain-version comparator (`plain-version.ts`) — an edge it cannot read admits nothing.
- **Hub** (`hub-client.ts`, `HubClient` over a `HubEndpoint { url(), fetch? }`): `GET <hub>/module/versions?ref=` (404 → `[]`, lenient, a non-canonical `integrity` dropped) and `GET <hub>/refs?q=`; failures reject naming the hub. The one reader of the hub's answers for every host.
- **Engine supply** (`engine-supply.ts`, `engine-archive.ts`): the bundled engine as shipped; else the host's cached copy, its digest rechecked on every load (a changed file is refused, reported and fetched again); else a download verified against `dist.integrity`, gunzipped, read by a minimal ustar/pax reader, and refused unless the tarball's own `package.json` declares a spoken `teloEditorProtocol`.
- **Router** (`language-router.ts`): one connection to the editor, one per running engine. **Every URI is compared in its canonical form** (`canonical-uri.ts`, `@telorun/editor-protocol` § URIs) — text sync, requests, the active document, published diagnostics, `telo/requirements` and stored resolutions — so an editor and an engine spelling one location differently still agree (a UNC share keeps its lowercased host, and `file:////host/…` folds to `file://host/…`); messages pass on unrewritten. A file an owner stops claiming leaves its membership and falls under the rule for unclaimed files. A restarted bundled engine is the engine of the identity the bundled one last reported until its own handshake says otherwise — never looked up or downloaded as that identity — and an engine dying while `initialized` is being sent counts as failed, not running. A document goes to the engine of the owner that lists it in `telo/requirements.documents`; an unclaimed one to the bundled engine. **`initialize` never waits for the network**: it is answered once the bundled engine's handshake settles, routing starts on the cached catalog (or the bundled engine alone), the registry is read in the background, and when its catalog arrives every owner is chosen for again; only an engine download waits for it. **Auto resolutions persist per workspace** through the host's `ResolutionStore` (`{ owners: { <owner>: { version, documents } } }`): read once with the catalog before the first document is routed, so a module reopens straight on the engine it last resolved to. A stored entry is honoured only when its version is known and runnable without a download (bundled, or in the `EngineCache`); otherwise it is dropped. An honoured entry whose engine then fails to load sends the owner back to the bundled engine for its first analysis, logged through `window/logMessage` and with no status error — the stored choice was a starting point, not a requirement. Written when an owner's Auto-chosen engine or its documents change, serialized, a failed write logged; nothing is written, and the store is ignored, under a pin; the move-once guard is not persisted. An owner moves when its engine's requirements resolve elsewhere — once per requirement set and set of known versions, so two engines reading a closure differently cannot bounce it. **Diagnostics**: a file open in the editor, or claimed as an owner's member, shows only its serving engine's publication; any other file (an imported library) shows the deduplicated union of what the running engines publish for it, so a library's diagnostics appear whichever engine analysed the app, and shrink as engines withdraw them or stop. **The router owns every editor registration** (`editor-capabilities.ts`): per feature, one registration of the union of the running engines' options (trigger characters, commands and code-action kinds unioned; the semantic-token legend unioned by name, each engine's tokens remapped into it), re-registered when that union changes and withdrawn when no engine advertises it; an editor that cannot register a feature dynamically gets the bundled engine's options statically. A request goes only to an engine that advertised it — otherwise the router answers the empty result — and a resolve goes back to the engine that produced the item. File watchers an engine registers become one editor registration per distinct watcher, and each change reaches each engine whose own watchers match it (`watcher-glob.ts`). A registration of a method the router does not own is passed on and withdrawn when its engine goes. `telo/*` are answered by the router itself (`host-answers.ts`) over the host's raw seams, with the rules written once: a directory reads as its `telo.yaml` (`TELO_MODULE_FILENAME`) and answers with that URI, a path naming nothing is `null`, anything else a host could not do is an error, `relative` resolves against the directory of `base` by URI arithmetic, and listing a file or nothing is `null`. `include:` globs are not a host question — the engine expands them over `telo/listDirectory`. **Every handshake is verified** — named `telo`, a spoken protocol generation, and for a downloaded engine exactly the version it was downloaded as — else `engine-refused`. **An engine that fails** (its module throws while loading, an uncaught error, an unreadable message, an exit nobody asked for — `SpawnedEngine.onFailure` — or no answer to `initialize` within 30 s) is `engine-failed`: its pending requests are rejected naming the version and the reason, its documents are left with no engine, its registrations and diagnostics withdrawn, the failure logged; `retry()` starts it again, the bundled one included. Nothing after the handshake is timed. A version that cannot run (not cached and unreachable, refused, failed, an unoffered pin) leaves its documents with NO engine and an error in the status — **never a substitute**. Status events are host-neutral (`TeloStatus`, including `starting`); `markVersions()` feeds a picker; `describeTeloStatus(status, host)`, `describeVersionMark(mark)` and `describeAutoMark(marks)` (`describe-status.ts`) are the words every host shows, so a host adds only icons and actions.

## Host seams

A host supplies:

- `HostFileSystem` — raw workspace access by `file:` URI: `stat` (`"file" | "directory" | undefined`, links followed), `readText`, `readDirectory` (each entry's `kind` — `file`, `directory`, `symlink`, `other` — read without following links).
- `RemoteReader` — every non-`file:` `telo/read` (the host owns `oci://`, `https://`, any cache, and their integrity checks).
- `HubClient` — built by the host from a `HubEndpoint`.
- `EngineCache` — engine bytes + recorded digest by version.
- `CatalogCache` — the last catalog read.
- `ResolutionStore` — this workspace's Auto resolutions.
- `EngineSpawner` — engine bytes → a structural port plus `onFailure` (fired once, with the reason, when the engine's module throws while evaluating, raises an uncaught error, sends an unreadable message or exits unasked) and `terminate`; run the verified BYTES, never a path that could change after the check.
- `BundledEngine` — `{ load() }`: the engine the host ships. It carries no version; the engine names itself.

plus the editor-facing transports (`createInProcessTransports()` for an in-process LSP client). The JSON-RPC runtime layer is installed from web globals only when the host's LSP client has not installed one.
