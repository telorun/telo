A `!cel` argument at a call site is held to the target's declared `inputType` by `telo check`, as a resource's own fields already were. A step's `inputs:`, an Application boot target's inline step and every reference slot's `inputs:` map (an `Http.Api` route, `Stream.Tap`, `Schedule.Interval`, `RecordStream.EndHandler`) now report `CEL_TYPE_ERROR` at the argument when its expression's type does not fit the slot — a string into an `integer`, a map into a `string`, `duration(...)` into a `string`, a chain declared a string into an `integer` — where the manifest checked clean and failed at dispatch with `ERR_INPUT_INVALID`. A plain chain reading a value its producer declares nullable into a field or argument whose declared type takes no null is `CEL_TYPE_ERROR` too, naming the source and the guard to write (`x != null ? x : <fallback>`); a guarded, computed or `dyn(...)` expression, and a result its producer does not declare, are left to the runtime. One rule decides the code when a plain chain's declared shape conflicts with its slot, at a resource's own field and at a call site alike: `CEL_TYPE_ARGUMENT_MISMATCH` exactly when every conflict lies beneath a type argument of a value type both sides name (a stream of bytes into a stream of strings, at any depth), `CEL_TYPE_ERROR` for everything else — two different value types, `Telo.Bytes` against `type: object`, two JSON types, a missing required member. An own-field conflict outside a type argument therefore moves from `CEL_TYPE_ARGUMENT_MISMATCH` to `CEL_TYPE_ERROR`.
