# Studio — package guide

Loaded when working under `apps/studio/`. Repo-wide rules live in the root `CLAUDE.md` (Radix primitives, `lucide-react` icons). The runner contract the editor talks to is in `packages/runner-core/CLAUDE.md`; the agent's question protocol in `apps/authoring-agent/CLAUDE.md`; the module-graph projection the topology view draws in `analyzer/nodejs/CLAUDE.md` § Module graph.

## Run

**The desktop build runs through the `telo` it SHIPS.** Studio bundles the CLI as a Tauri sidecar, built from the same commit (`scripts/stage-cli-sidecar.mjs`, staged into `src-tauri/binaries/telo-<rust target triple>`), and the Rust shell supervises `telo runner` on loopback; the editor then talks to it through the ordinary http-runner adapter, so `local-cli` is the same thin "where does `baseUrl` come from" wrapper `local-docker` is. **The executable is configuration, never a lookup**: the adapter's one field defaults to the sidecar, a user may name their own build, and nothing searches `PATH` — an app whose behaviour depends on machine state is the failure this rules out. That executable is the RUNNER; the telo an application runs on is the version its module is edited against (Language tooling, below), which the runner supplies as itself or as that release's verified binary. A development build has no sidecar and names this checkout's CLI explicitly instead. It is seeded and made active only on a FIRST launch; docker stays selectable (it is the runner that runs an application the way production does) and is the only local option in the browser build, which has no process to supervise. Unlike docker there is no consent gate: that gate exists because the docker runner mounts the daemon socket, not because a run is local. **The shell names the origins its own webview sends** (`--allow-origin`), because the runner refuses browser origins it was not given — a local API that runs code is reachable from every page the user visits, so the client that needs an origin allowed is the one that declares it.

**The settings row asks the ADAPTER whether a local runner is up and how to stop it** (`isRunning` / `teardown`), never a table keyed by adapter id: the registry exists so the UI does not know adapters by name, and a fourth runner should not mean editing a UI file.

**A run's files sit in the session where the editor holds them, relative to the workspace root** (`run/bundle.ts`): an Application at `<root>/apps/todo/telo.yaml` is `apps/todo/telo.yaml` in the session workspace, never `telo.yaml`. The session workspace has more than one writer — the agent's sync writes the editor's whole tree into the same volume, relative to that same root — and rooting the bundle at the application's own directory made the two layouts disagree: the first agent turn deleted the app's files from under the running kernel (`ENOENT … /workspace/telo.yaml`) and wrote them again one level down. Only a closure that reaches a file outside the workspace root falls back to the common ancestor of what it ships.

**The editor offers ONE Run**, and the mode is not a user choice: it asks for a watch session when the runner advertises one and degrades to a plain run when it does not, read from a capabilities fetch on the run path rather than from asynchronously-filled state — where a Run clicked early would silently start the other kind. `mode` stays on the wire, so a one-shot run is still expressible by any client.

**The top bar's workspace menu is the one place a workspace is switched or closed** (`components/WorkspaceSwitcher.tsx`). It lists what this device can open without asking — the browser-stored workspace and the Telo Cloud working copies in the local index, so both open offline and signed out — beside "Open folder…" (where a picker exists), "Open from Telo Cloud…" (signed in) and "Close workspace". The browser-stored workspace is opened by its BACKEND, never by its root: where a directory picker exists, a picked folder named `workspace` has the same root, `/workspace`. Closing leaves the files alone and records the close (`forgetWorkspaceRoot`), so a reload opens nothing — not even a browser-stored workspace found by its files — until the user opens one.

**Phone width is one boundary, Tailwind's `md`, and CSS decides everything it can.** Spacing, touch targets and what is hidden are `max-md:` / `md:hidden` classes; `useIsMobile` (`hooks/useIsMobile.ts`, the same boundary) exists only for what CSS cannot do — the sidebar becoming a drawer (`ui/sheet`), opened from the top bar's menu button, closed by opening a file or module, and starting open in a workspace with nothing open. Below the boundary the top bar keeps the workspace menu as an icon, folds Undo / Redo / theme into one menu and puts the module name and telo version on a row of its own; the agent panel and the topology's detail panel cover the editor; and every action a sidebar row offers on right-click or hover is on a visible button, because a touch screen has neither.

**A render failure stays in the region it happened in** (`components/RegionErrorBoundary.tsx`): the sidebar, the open tab, each view, the graph, the detail panel, the run dock and the agent panel each show their own failure — the error and "Try again" — while the rest keeps working, and one more boundary at the root covers what no region contained. A boundary given a `resetKey` clears when what it shows changes (another view, tab or selection). A new top-level region gets a boundary of its own. Schema walks read during render answer "unresolved" instead of throwing: `resolveRef` (`schema-utils.ts`) is `undefined` for a reference it cannot follow, a shape another module declares (`telo://Ui/Node`) included.

## Language tooling

**Every diagnostic studio shows comes from the engine of the telo version the module is edited against; the structured views do not.** A workspace runs one `@telorun/language-host` router (`src/language/language-session.ts`), which picks each module's telo version (Auto, or the workspace's pin), runs that version's `@telorun/language-server` engine in a module Web Worker made from a `blob:` URL of the verified bytes, and serves the engine's reads from studio: `file:` reads through the workspace adapter (`WorkspaceFileSystem`, confined to the root for the browser's virtual workspaces), `oci://` / `https://` through the loader's own manifest-cache and HTTP sources, the hub through language-host's `HubClient`. The engine studio ships is `@telorun/language-server`'s built file, copied unchanged into the build as `engine/language-server-<content hash>.mjs`, its name given to the app by `virtual:telo-bundled-engine` (`vite-bundled-engine.ts`); nothing stamps its version — the router reads it from the engine's handshake, so a build of an unreleased tree is named **X (local)** in the version menu and in the status tooltip. The label beside the menu is deliberately shorter — the version in effect, and `(auto)` when Auto chose it — because the menu next to it already names the choice. Downloaded engines live in Cache Storage `telo-engines`. The per-workspace setting and Auto resolutions are `localStorage` (`LOCAL_PREFIXES.teloVersion`, `LOCAL_PREFIXES.engineResolutions`), the engine catalog `LOCAL_KEYS.engineCatalog`, shared by every workspace because it describes the registry.

- **Documents are Monaco models.** `WorkspaceModels` keeps one model per workspace manifest document at its `file:` URI (`language/file-uri.ts`: a browser workspace's virtual path maps the same way, `file:///workspace/app/telo.yaml`), whether or not a source view shows it — so every module is analysed from the moment the workspace opens, and a form edit reaches the engine as the text it produced. The source view edits these same models (`path` + `keepCurrentModel`); a model the user has typed into keeps their text until they commit it.
- **The Monaco↔LSP bridge (`language/monaco-lsp-bridge.ts`) is Telo-agnostic**: full-text sync of the models, published diagnostics as markers, and a Monaco provider for exactly the capabilities the server advertised — completion, hover, definition, rename with prepare, signature help, semantic tokens (legend from the capabilities), code actions, code lenses with their commands, `workspace/applyEdit` — each registered, re-registered and withdrawn as the router's dynamic registrations say, since the router offers the union of its running engines' features. It replaced the source view's in-process registrations; no `monaco-languageclient`, no `@codingame/*`. The resource YAML slice pane is a projection of its document's model served by the same engine (`components/detail-yaml-projection.ts` over the bridge's generic `ModelProjections` seam: requests asked of the source document at mapped positions, answers mapped back, nothing outside the slice kept; a keystroke is spliced into the document model at once and the pane re-derives whenever that model changes). Non-Telo files get no Telo features because they are not Telo documents — a file becomes one by being a module owner or an `include:` partial, which open in the source view.
- **The diagnostics store has one producer**: what the engines publish, routed by `Diagnostic.data.resource` (form fields paint by `data.path`) — `language/engine-diagnostics.ts`, fed from `hooks/useLanguageSession.ts`.
- **Structured views stay on the bundled model**: topology and the module graph, schema forms with their CEL editor and value-tag offers, the template canvas and resource create/edit read `state.analysis`, built in process by studio's own analyzer (`analysis.ts`), which produces no diagnostics. A form field's eval mode is the analyzer's answer, not the form's reading of the annotation: `getCelEvalMode` (`components/resource-schema-form/cel-utils.ts`) asks `declaredEvalMode` / `declaresCelRegion` of the field's schema node and only propagates the result to descendants, so an `x-telo-eval: accessor` field offers `!cel` alone and nothing beneath it takes a tag, as in VS Code. A `Selection` carries the same three modes, and `celEvalModeAtPointer` answers `accessor` for a pointer at or inside an accessor field: a form rooted there renders that field's members, which are part of its value, so none of them takes a tag.
- **The version a module is edited against is the version it runs on.** Run asks a runner advertising `features.teloVersions` for exactly the version the language session reports for that module's manifest (`run/run-version.ts` over `LanguageSession.statusOf`: the pin, or Auto's answer for that module) and leaves out exactly the config properties the runner says a version supersedes (`config.supersededByTelo` — its `image` and `pullPolicy`). A module nothing serves has no version to ask for, so its run is refused with the status that already explains why — never run on some other version. A runner's refusal before the session exists (`TeloVersionRefusedError`: `telo_version_unavailable` / `telo_version_unsupported`) is the dock's blocker with the runner's own reason; a version the runner only finds it cannot fetch while starting (an image pull, a release download) is that session's failed start, with the same reason on its status. **A live run whose module has since moved to another version says so** (`staleRunVersion`): a run's telo is fixed when it starts, so after a pin change the editor checks against one version while the session runs another, each agreeing with itself — the dock warns and the next Run moves it. **A runtime that reports another version is a warning, never a stop** (`run/telo-alignment.ts`, drawn in the dock beside each app's generation): the runner passes on what the runtime says it is, Studio compares it with what it asked for, and by then the manifest has loaded on that runtime. One that reports nothing shows the requested version as not confirmed. A runner without `teloVersions` is sent no version and keeps its `image`.
- **A settings form leaves out what its schema deprecates** (`deprecatedProperties` / `withoutDeprecated` in `run/ui/capability-form.ts`): the standard keyword, so the form knows no field by name. An aligned runner marks `image` and `pullPolicy` (how a version's image is pulled is its operator's), so its settings show only what addresses it; an older one marks neither and keeps both; Studio's own copy of the docker schema carries the mark so the field does not show and then vanish.

## Telo Cloud

Signing in is optional, and everything else in Studio works without it. A signed-in user opens a Telo Cloud project, edits it in a local working copy, commits to its git repository and publishes a module; projects, members and repository connections are the console's.

**Studio's JavaScript never holds a Cloud token, in memory or in storage, and neither build depends on CORS.** Studio runs downloaded language engines and renders agent and module content, and a Cloud token can deploy to customer clusters. Every Cloud call goes through one transport with two implementations chosen by build target (`cloud/backend.ts`), and nothing else knows which is active. The web build asks `/api` on its own origin — which is why the web build is served by Telo Cloud (`ghcr.io/telorun/studio-web`, `apps/studio/Dockerfile`, deployed with `apps/studio/chart`, whose version is this package's and whose route takes everything on the host but `/api`) — with the HttpOnly `__Host-sid` cookie the browser keeps to itself and an `X-CSRF-Token` on unsafe methods. The desktop build hands a method, a path under the API base, headers and a body to the shell, which holds the access and refresh tokens (the refresh token in the OS credential store, service `com.telo.studio`), attaches the Bearer and streams the answer back. **The API base and the identity provider are the shell's build settings** (`VITE_TELO_CLOUD_API_URL`, `VITE_TELO_ACCOUNTS_URL`, read from the build's environment), never something the webview supplies: a webview-chosen base would let page content send the token anywhere. No content-security policy stands in for this on the desktop — runners are user-configured hosts, so the webview's network access cannot be an allowlist.

**"Is Cloud here" is decided on the session's shape, not the status.** The web build reads `GET /api/session`: JSON of the session's shape is signed in, `401 session_required` is anonymous, and anything else — the dev server answers every path with 200 and the page — hides every Cloud control. A 401 at any later time puts Studio back to anonymous without touching the working copy.

**A working copy is one more workspace storage backend, rooted at `/cloud/<project id>` on both builds** (`cloud/working-copy-adapter.ts`), over a byte store with two implementations: the browser's Origin Private File System, and a folder under the app's data directory. The backend is chosen by that root, not by the environment. The explorer, autosave, undo, runs and the agent read and write it unchanged, and nothing they do reaches Cloud. Three things follow from the stores, not from choice:

- **What changed is decided on bytes, below the storage interface** (`cloud/working-copy.ts`), because that interface reads every file as text and says nothing about a binary one.
- **Modes and symbolic links live in the base record** (`base.json` beside the tree: commit, branch, and each path's mode, link target and SHA-256), since neither store can hold them on every platform. A changed file is committed with the mode its base records; a link is never materialized in the tree.
- **The desktop store escapes a leading dot in every stored name** (`%2E`), because the shell's file scope does not let a wildcard match one and a repository is full of them.

**Committing is explicit, and the server never merges.** A commit sends the difference from the base with the base's commit, under an `Idempotency-Key` kept in the working-copy index until the commit is seen to land — so a retry after a dropped connection, a reload included, yields one commit. The branch head is read on focus, every 30 seconds and before every commit: a clean working copy follows it once no run sync or agent turn is in progress (the editor's `idle()`), a changed one is offered Update. Update and a commit answered `409 branch_moved` run the same per-path merge (`cloud/three-way-merge.ts`): a path one side changed takes that side, a path both changed differently is the user's choice of "Keep mine" or "Take theirs", there is no merge inside a file, and afterwards the head is the base with nothing committed. Editing is paused while an update is in progress or waiting on that choice, and a `viewer` cannot edit at all — both through the one `editingPaused` reason every write path in `Editor.tsx` reads.

**Sign-out removes the working copies**, after a confirmation naming the projects with uncommitted changes; a session that turns out to belong to a different user than the stored copies asks before removing them and otherwise signs out again. The index of working copies is `LOCAL_KEYS.cloudWorkingCopies` (user, org, project, branch, base commit — nothing secret). **An entry stored while Cloud called a project a workspace is not a working copy**: its id names nothing Cloud still has, so it is never listed or opened, and Studio offers once per load to remove it with its files.

## Agent

**The editor prefers a co-resident agent over launching one of its own**, and the two differ in where the shared workspace is: a standalone agent owns a directory and serves its own `/workspace` routes, a co-resident one writes the session volume, which the editor reads and writes through `/v1/sessions/:id/workspace` — the same path its saves take. The runner-seeded `telo-workspace.yaml` is excluded from that sync in BOTH directions: filtering one side only would either re-push it every turn (a reload each time) or delete it on the first (scattering one module cache into one per app).

**Every agent request carries the agent's bearer token when one is known**, resolved together with the URL in the same precedence: the override's token field, the runner-minted `RunnerEndpoint.token` of a co-resident or launched agent. **Neither is written to browser storage**: the override's token lives in memory only, and the run index strips `token` from every endpoint of the statuses it persists — a re-attached session gets its live token again from the runner's status stream. That is why the turn's events are read by a fetch-based SSE reader (`agent/event-stream.ts`) rather than `EventSource`, which cannot send a header: it does what `EventSource` did — reopens a dropped connection from the last record id (`Last-Event-ID` and `?lastEventId=`), drops a replayed record at or below it — and ends at once on a 401. A 401 `ERR_UNAUTHENTICATED` reads "This agent requires a token." wherever it surfaces. **The tool card's verdict comes from the tool result's structured `output`** (`checkExitCode`, `checkReport.diagnostics`), and so does the mid-turn pull (`output.path`); `content` is the text the model was given and is shown only as that. `GET /capabilities` is asked once per agent instance (URL + token): a "No auth" badge on the panel when it reports `auth: "none"`, and name, version and prompt id read-only beside the URL override (unavailable on a 404).

**Every conversation surface is gated on the capability document's `features`, never on the agent's version.** `conversations` turns on agent-minted conversations — the title becomes a switcher (search → `q`, archived, load more, rename, archive, export, delete), "New conversation" opens a draft that the first send creates with `POST /conversations` before `POST /chat`, and the per-workspace `telo-studio:agent:conv:<workspaceKey>` becomes a last-opened pointer (a 404/410 falls back to the most recent non-archived conversation, else a draft; any other failure keeps the pointed conversation open, shows the error and retries on the next tick or focus; a send never replaces an unconfirmed conversation with a new one; **a workspace opened while no agent is reachable shows a draft and opens or mints no id** — the agent a send then launches is a fresh instance that holds nothing, so asking it for an id chosen before it existed is a 404 on every first send — and the pointer is resolved by whichever agent appears, or settled by that send: created there, or on an agent without `conversations` the stored id, minted when there is none); `conversation-truncation` adds Retry, Edit & resend and Delete from here (a `DELETE …/turns?from=&revision=`, then a fresh `POST /chat` for the first two); `conversation-branching` adds Branch. A missing feature hides only its own actions; without `conversations` — no `features`, a 404, a failed ask — the panel is exactly the older one: a client-minted id, "New conversation" mints, no switcher, Copy only on hover, and the settings block lists what the agent lacks. A conversation belongs to the agent it was read from: a different agent re-resolves the pointer, and a send decides mint-or-create only once it knows what the agent it just selected serves. `manifestRuns: false` badges "No test runs"; absent says nothing.

**A tool card is chosen by the fields its structured `output` holds, never by the tool's name** — the tools an agent reaches through MCP are the hub's vocabulary, not Studio's, and a renamed or added tool must not need an editor release. `checkExitCode` (with `checkReport.diagnostics`) is a check verdict: a failed one lists its diagnostics, each opening its file at its line, a clean one is the line "check: clean". `changes` / `hunks` beside it are a write's or an edit's own diff — the hunks as the agent computed them (Studio diffs nothing), ± counts from `changes[0]`, the path opening the file at the first hunk's `newStart`. `exitCode` + `output` is a command: an exit badge, the last 20 lines of stdout, and all of stdout and stderr (`messages`) behind a toggle. Any other `output` is the generic card: the tool's name and scalar arguments as the headline, text parts as text and everything else as a folding tree. A call still running, one that failed outright and an agent that reports no `output` keep the text card. Two or more consecutive tool or thinking parts between pieces of the reply fold into one "N steps" group that counts its failed calls (a tool error, a non-zero exit, a failed check) — open while the turn streams, folded once it ends, the reader's toggle overriding either. On a write or an edit whose check failed the card opens by itself and the diagnostics come before the diff. **Which editor file an agent's path names is answered in one place: the workspace bridge the editor registers** (`editorFile`, beside the snapshot and the writes it already owns, so a link opens the very path a pull wrote). The agent context composes the sync's own exclusion rule in front of it and hands the transcript that one mapping; nothing in the agent context or its components joins a path or holds a root. A path the mapping resolves is a link calling the diagnostics context's `navigate`; one it does not is plain text — a path under a directory the sync excludes (`.telo`, `.probes`, `.telo-agent`, `node_modules`, `.git`, `dist`), the session's `telo-workspace.yaml`, an absolute path, a URL, one that leaves the workspace through `..`, and every path while no workspace is registered.

**A turn's `summary` and `revert` are state on the turn, read from the records route — not records of its stream.** So a turn of this client's is read again once its stream ends, from an agent that keeps summaries. The summary card after each ended turn lists the files it changed on balance (status, ± lines, each opening at its `firstLine`; a deleted one is listed, not opened), the check, the runs and the tokens. A turn that changed no file, ran nothing and was not reverted gets no card — a turn that only answered a question has nothing to summarise. `files: null` is a turn from before the agent kept checkpoints — unknown, not empty — and shows no file list, no View changes and no Revert. **View changes** asks `GET /chat/{turnId}/changes` each time it opens and shows each file's turn-level hunks; `changedSince` is live state with three values — `true` marks the file "changed since", `false` leaves it unmarked, and null (the agent did not compare the workspace file) marks it "not compared". **Revert** confirms naming the file count, posts `POST /chat/{turnId}/revert`, and shows the recorded outcome — also another client's, which arrives on the revision poll — with its skipped paths and the paths the editor kept (below); it stays offered afterwards, since repeating it evaluates skipped paths again, and is not offered while a turn runs or on an archived conversation (the agent answers 409). A refusal of either route is the card's error, by its code; a 503 `ERR_WORKSPACE_BUSY` (also from `POST /workspace`) is resent with the client's backoff like every other 503. **The editor's files follow a recorded revert, whoever issued it — the rule runs on every records read** (first load, revision poll, the re-read after a turn or a 409) and on this client's own revert response, which is the same path and nothing special. What licenses changing an editor file is three facts about its path together — the agent's recorded revert marks it `restored`, the agent's tree now holds `before` there, and the editor's copy is byte-identical to `after` (`before`, `after`: the digests the turn's `summary.files` records; null is no file) — with no remembered or persisted record of what Studio last synced:

| Recorded outcome | Agent's workspace now | Editor's copy | Studio does |
| --- | --- | --- | --- |
| `skipped`, or path absent from `summary.files` | — | — | nothing |
| `restored` | does not hold `before` | anything | nothing, not reported |
| `restored` | holds `before` | holds `before` | nothing — already in line |
| `restored` | holds `before` | holds `after` | replaces it with the workspace's content; deletes it when `before` is null |
| `restored` | holds `before` | anything else | leaves it, reports the path as kept |

"Holds `before`" with `before` null means the path is absent from the workspace's tree, whether the tree holds other files or none — reverting the turn that created every file of a fresh workspace deletes them in the editor. A tree read that fails — a refused request, or an answer carrying no file list — is a failed apply, never read as an empty tree. Digest equality is the only evidence that the editor's copy is the turn's, so a file put back byte-identical to what a reverted turn left, before any send, is taken for the turn's copy when a later session first reads the revert. A turn's revert is applied once per `revertedAt` in a session (a memory-only marker, set only once the rule completed), never under this client's own turn (its end-of-turn reconcile converges everything), one convergence at a time — serialized with the seed and the reconcile — and at the cost of one editor snapshot and one workspace tree per read however many reverted turns it carries. A failure is shown (`The editor's files could not be brought in line with the revert: …`) and stays pending: it is retried at the next records read and before the next seed, and a send whose retry fails does not seed. The kept paths are state of the turn in the agent context, not of the card — they survive the panel closing — replaced by whatever a later run finds, and listed under the agent's own "N restored, M skipped" with: "Restored in the agent's workspace, but not in the editor — the editor's copy is not what this turn left. It will replace the restored file when you next send a message."

**Continue is not Resume.** A turn that spent its step budget on an agent serving `turn-conclusion` is a COMPLETED turn whose `finish` carries `limit: "max-steps"`: the conversation's last such turn offers Continue, which sends an ordinary new turn (`POST /chat`) saying `Continue.`, shown as the user's bubble. Resume stays what it was — `POST /chat/{turnId}/continue`, another attempt at an INTERRUPTED turn. An older agent's spent budget is a failed turn, so it shows Resume.

**Each turn surface is gated on its own `features` string, and a missing one hides only that surface**: `turn-changes` — the diff on write/edit cards and View changes (without it those cards show path and verdict); `turn-revert` — Revert; `turn-summary` — the summary card; `turn-conclusion` — Continue. The diagnostics list, the command card, the step groups and the generic card are not gated: they draw what any agent filling `output` already sends.

**Other clients are seen by revision, not by push.** While the panel is open and the document visible, the open conversation's `revision` is read every 5 s and on focus; a change replaces the transcript from the records route (re-attaching a running last turn), and a revert another client recorded is applied to the editor's files on that read, as on every records read — except under a turn of this client's, where only the title and archive state move and the transcript is re-read once its stream ends. 410/404 leave for the most recent remaining conversation with the reason shown. A truncation carries the revision its turn count was shown at, so a 409 `ERR_CONVERSATION_CHANGED` re-reads and applies the confirmation rule again to the re-read transcript: Delete from here asks with the new count, Retry and Edit & resend ask only when later turns would go (or their turn is gone) and otherwise run at once. A turn's `conversation-title` record names the header live (a failure is a muted notice on the turn), and a `context-summary` is drawn after the last turn it covers, expandable to the summary; an export (JSON: the records route's turns verbatim; Markdown: what the model received) is composed here from `GET /conversations/{id}` and the records route.

## Where to look

- "how does Studio reach Telo Cloud, and where are the tokens?" → `apps/studio/src/cloud/backend.ts` (the build-target choice), `web-backend.ts` (same-origin, cookie, CSRF, the session-shape rule), `desktop-backend.ts` (the shell bridge and the streamed body), `src-tauri/src/cloud_auth.rs` (settings, refresh, session), `cloud_authorization.rs` (the loopback authorization), `cloud_token_store.rs` (credential store, memory fallback, the cross-process refresh lock), `cloud_transport.rs` (path and header rules)
- "what is a working copy, and what does a commit send?" → `apps/studio/src/cloud/working-copy.ts` (tree, base record, changes, commit preparation, update), `three-way-merge.ts`, `snapshot-tar.ts`, `byte-store.ts` with `opfs-byte-store.ts` / `tauri-byte-store.ts`, `working-copy-index.ts`; the flows over them — open, commit, update, head polling, publish, leaving — are `cloud/context.tsx`, the routes `cloud/api.ts`, the UI `components/cloud/`

- "which telo version checks this module, and where does a diagnostic come from?" → `apps/studio/src/language/` (session, bridge, models, the host seams), `hooks/useLanguageSession.ts` (one session per workspace, the store feed), `components/TeloVersionControl.tsx` (status, setting, error actions; its words are language-host's `describeTeloStatus` / `describeVersionMark` / `describeAutoMark`)

- "which telo version does a run use, and what if the runner cannot supply it?" → `apps/studio/src/run/run-version.ts` (what is asked for), the version block of `handleRunModule` in `components/Editor.tsx` (the request, and both refusals as dock blockers), `run/telo-alignment.ts` and `RunTeloVersions` in `run/ui/RunDock.tsx` (the reported version and the mismatch warning), `run/ui/capability-form.ts` (deprecated fields)
- "how does a local run reach a telo?" → `apps/studio/src/run/adapters/local-cli/` (adapter, config, the supervisor bridge), `src-tauri/src/cli_runner.rs` (process lifecycle, the executable resolution order, and why the stop is SIGTERM rather than a kill), `scripts/stage-cli-sidecar.mjs` (the one place Telo's platform tokens meet Rust target triples)
- "where does the editor's agent live, and whose workspace does it write?" → `apps/studio/src/agent/agent-workspace.ts` (the two surfaces behind one interface, and the runner-seeded path excluded from both directions), `agent/sync.ts` (the convergence), the `ensureAgent` precedence in `agent/context.tsx` (override > co-resident > launch), `coResidentAgent` in `apps/studio/src/run/context.tsx` (which session, resolved from its own `running` status)
- "a turn failed — what can be picked back up?" → `interruptedTurn` in `apps/studio/src/agent/records.ts` (the pure half), the `retry` / `continueTurn` / `dispatchTurn` split in `agent/context.tsx`. **A turn the agent holds is continued there, never re-sent**: `retry()` posts `POST /chat/{turnId}/continue` and re-attaches the stream from the last record it folded, so the agent's `turn-continued` record and the new attempt land on the same reply and the model resumes from its full recorded history — a turn still running (its stream was lost, not its work) is simply attached to. Only a message the agent never admitted is sent again as it was. What makes a turn continuable is `ChatMessage.completed`, set ONLY by the `finish` record: `pending` is cleared by every ending including a failure, so half a streamed reply is indistinguishable from a whole one without it — and reading half a reply as an answer is what would offer a Resume button with nothing behind it. A stopped turn (the user's abort) is an ending, not an interruption, and offers no Resume.

- A template's body as a canvas → `module-graph-view/TemplateCanvas.tsx` (the module canvas over the analyzer's `templateModule`), `template-body.ts` (every canvas write re-addressed into the definition's `resources[i]` / `targets:`; a lone `run:` becomes `targets:` once written). Extraction, relocation and deletion are not offered there: each writes a document of its own, which an entry does not have. A module resource the body references is drawn read-only and selecting it opens the resource itself; a forwarded field (`self.<path>`) is a box titled by the kind's schema, with nothing to open. A write to a name the body declares twice, or no longer has, is refused with a toast rather than sent to a guess.
