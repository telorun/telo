A browser entry a resource names is held to what its kind accepts, and a controller can serve an entry a library it imports ships. `x-telo-browser-export` gains two optional keys: `abi`, the generations the kind accepts (each `<family>-<version>`), and `external`, the bare specifiers the kind supplies. An entry whose own `abi` is not listed (or which declares none) is `BROWSER_ENTRY_ABI_UNSUPPORTED`, and one leaving to its host a specifier the kind does not supply is `BROWSER_ENTRY_IMPORT_UNSUPPLIED`, both at the field naming the entry, refused at creation as `ERR_BROWSER_ENTRY_ABI_UNSUPPORTED` / `ERR_BROWSER_ENTRY_IMPORT_UNSUPPLIED`. A resource an imported library declares is now judged by `telo check` too — against that library's own `exports.browser`, for the version the application loads — and all four browser-export codes (`BROWSER_ENTRY_UNKNOWN` and `BROWSER_EXPORT_UNKNOWN` included) are reported once, at the `imports:` entry through which the library is first reached; before, a dependency's mistake passed `telo check` and failed the run. The annotation's own shape is checked: anything but `{ entry: <JSON Pointer>, abi?: [<family>-<version>…], external?: [<specifier>…] }` is `BROWSER_EXPORT_ANNOTATION_INVALID` at the kind (at the `imports:` entry for a dependency's) and `ERR_BROWSER_EXPORT_ANNOTATION_INVALID` when the kernel registers it. `ctx.resolveControllerBrowserEntry(specifier)` resolves against the kind's own module first and, when it declares no such entry, against the one module it imports directly that does; two such imports are `ERR_BROWSER_ENTRY_AMBIGUOUS`, naming both. The analyzer exports `browserExportAnnotationProblems`.
