`telo package` packages a root that declares a `Telo.DesktopHost` need as a desktop app, with no flag: the identity is read from the need table, an `icon` that is not a square PNG of at least 1024 px is refused with `ERR_DESKTOP_ICON_INVALID` before anything is written, the `telo-desktop-host` helper for the packaged platform rides in the payload (a failure to obtain it is `ERR_DESKTOP_HOST_UNAVAILABLE`), and the payload index gains `desktopHost: { identifier }`, which `telo package inspect` prints. A packaged desktop app reads its `.env` from the per-user application directory of its `identifier`, and once it hosts itself works there with `TELO_HOST_STATE_DIR` set to `<that directory>/state`, so its durable directories and child applications land beneath it. Linux is written as the plain executable with the helper in its payload. macOS is written as the application bundle `<out>.app`: an `Info.plist` from the need's `identifier`, `productName` and `showInDock` (`LSUIElement`) and the root's `metadata.version`, with `LSMinimumSystemVersion` 14.0, an `AppIcon.icns` built from the icon, the carrier at `Contents/MacOS/<productName>` and the helper beside it, both signed ad hoc so the operator's `codesign` and notarization apply to the bundle. Windows is written as a GUI-subsystem `<out>.exe` that opens no console, with the icon and a version resource (`ProductName`, `FileDescription`, `ProductVersion`, `FileVersion`) and the payload carried as the PE resource `RT_RCDATA` / `TELO_APP_PAYLOAD` rather than appended, so a `signtool`-signed executable still finds it; `telo package inspect` reports that placement as `pe-resource`, and takes a `.app` bundle's path.
