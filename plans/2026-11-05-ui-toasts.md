# Toasts for declarative UI

## Problem

A page has no way to say "it happened". A call draws its answer in place (`result:` / `failure:` trees), which is right for a state but wrong for an event: after a row call archives a record, the refresh drops the row and its drawn answer with it — the user sees the row vanish and nothing else. There is no Undo, and no "Saved" after a dialog closes. Component authors have no host call to report an event either.

## Constraints

None.

## Surface

**Added**

- `Ui.Toast` — an effect kind (extends `Ui.Effect`) `{ text, tone?, link?, call? }`: `text` a `Ui.BoundText`, `tone` one of `info | success | warning | danger`, `link` a `Ui.Press` `{ to, label }`, `call` a `Ui.MutationPress` with `label` required.
- `Ui.Close` — an effect kind (extends `Ui.Effect`, not `Ui.Destination`): closes the opened surface the call ran in; `REFERENCE_KIND_MISMATCH` at every `to`.
- `Ui.MutationPress` — named shape `{ mutation, inputs, label?, onSuccess?, onFailure? }`: a mutation run by a press, and the effects run after its answer.
- `onFailure` beside every `onSuccess` — `Ui.MutationPress.onFailure` (so on every `Ui.MutationCall`) and `Ui.Move.onFailure` over `error` and `input`; `Ui.Form.onFailure` over `error` and `values`: effects run when the write does not succeed.
- `UiReact.App.toaster` — `{ side?, align? }`: `side` `top | bottom` (default `bottom`), `align` `start | center | end` (default `end`).
- `ui_react_controls-5` — the controls contract with the layer control `Toaster` (group `overlay`; props `items`, `side`, `align`, `label`, `dismissLabel`; intents `onDismiss(key, reason)`, `onPauseChange(paused)`): 26 controls, eleven of them layer controls.
- Styling parts `toaster`, `toast` (`data-state`, `data-tone`), `toast-text`, `toast-actions`.
- Host field `toast({ text, tone?, link? })`, `link` `{ to, label }`, returning `{ dismiss }`.
- Wire: the effect specs `{ type: toast, text, tone, link?, call? }` (`link` a `PressSpec`) and `{ type: close }`; `onFailure` beside every `onSuccess` (`[]` when none) — on every call spec and on the `form` node; a listing's `delete` as `false` or `{ onSuccess, onFailure }`; `toaster: { side, align }` in the application document.
- Keyed text `toaster` ("Notifications"), in `Ui.Translations` and its fourteen translations.
- `modules/ui/conformance/toasts.json` — the timing, limit, deduplication, press and in-flight rows.

**Changed**

- `Ui.MutationCall` — extends `Ui.MutationPress`, `label` required, adding `confirm?`, `prompt?`, `enabled?`, `result?` and `failure?`.
- `Ui.Listing.delete` — takes `false`, `true` or `{ onSuccess?, onFailure? }`, each a list of effects.
- `UI_CONTROLS_LAYERS_PARTIAL` — counts eleven layer controls; a set written against `ui_react_controls-4` is `BROWSER_ENTRY_ABI_UNSUPPORTED`.

**Removed**

- `ui_react_controls-4` — no longer hosted by the renderer.

## Solution

**One principle:** a toast reports an *event*; a *state* (a read failed, a field is invalid, a copy succeeded) stays drawn where it holds. A toast is never the only record of an outcome, nor the only way to act on one — its `link` and `call` are shortcuts to what the page offers elsewhere — so it can be dropped safely.

**A toast is an effect.** `Ui.Toast` is one more `Ui.Effect`, written in any `onSuccess` or `onFailure` list beside the destinations and `Ui.Close`, and run in the list's order — the flat handler list Retool, Power Apps and Appsmith put "show notification" in:

- `text` — a `Ui.BoundText` (one sentence, translated and announced as one).
- `tone` — `info | success | warning | danger`, the words `ui`'s styles and the `color.danger` token already use; `ui` fills `success` in an `onSuccess` list and `danger` in an `onFailure` list.
- `link` — a `Ui.Press` `{ to, label }` ("View"), drawn as an `<a>`. A toast sits in no surface and anchors nothing, so a `Ui.OpenPage` from one opens a `Ui.ViewportOverlay` as declared, any other surface as its `compact`, else as `Ui.Dialog` with its defaults — and an omitted `surface` as `Ui.Dialog` with its defaults.
- `call` — a `Ui.MutationPress` (Undo, Retry), `label` required. It draws no tree and asks nothing: busy while pending; on success the toast is withdrawn and the press's `onSuccess` runs; on failure the toast stays, its button pressable again, and the press's `onFailure` runs — omitted, `ui` fills it with one `danger` toast reading `{$message}` over `error.message`, so a failed Undo is never silent. A dismiss or a drop never aborts a press already sent, and its lists still run.

**`Ui.Close` is an effect, not a destination.** It has no address, so it cannot be drawn as a link or opened in a new tab. It extends `Ui.Effect` directly; every `to` slot names `Ui.Destination`, so `Ui.Close` at a toast's `link.to` or a `link` node is `REFERENCE_KIND_MISMATCH`. In an effect list it closes the opened surface the call ran in — for a toast's `call`, the surface the posting call ran in — if that surface is still open.

**Where effects are written.** `onFailure` stands beside every `onSuccess`, and nowhere else:

- `Ui.MutationCall` (a `button` node, `rowActions`, `annotations.action`), `Ui.Move` and a toast's `call` (`Ui.MutationPress`) — `onSuccess` over `result` and `input`, `onFailure` over `error` and `input`;
- `Ui.Form`, for its one submit write — the default write to `record`, or `onSubmit`'s — `onSuccess` over `values` and `result` (from `onSubmit`'s mutation, or the stored record after the default write), `onFailure` over `values` and `error`. On success the `result` tree is drawn, then `afterSubmit` applies, then `onSuccess` runs; on failure the `failure` tree is drawn, then `onFailure` runs. `onFailure` runs only when a submit write was sent and did not succeed. `onSubmit`, `autosave` and `record` hold no lists, so neither list follows an `autosave` write;
- `Ui.Listing.delete` as `{ onSuccess?, onFailure? }` (over `row`, plus `error`). A failed delete keeps its confirmation open with the failure drawn in it, as a row action's confirmation does, and the toast adds to it.

The roots where the form or listing is placed (`params`, `query`) stay in scope. A toast's `text` values, `link.to` and `call.inputs` read the roots of the list holding it, resolved when it is posted, so a toast outlives its row; a toast call's own lists bind its own `result` / `error` / `input`, shadowing the outer ones. A toast after `Ui.Navigate` to a declared page shows on the page moved to; a navigation to any other address is an ordinary browser load, which drops every toast. A failure toast **adds to** the `failure` tree, never replaces it. A press whose toast runs the same mutation again (Retry, "Archive again") is legal: every edge waits for a person. Effects are written inline, so a Retry that should say what the first success says repeats that list.

**Timing, one fixed rule (no author key):** `info` / `success` with no `link` or `call` last 6 s, paused while the toaster reports a pause or the document is hidden; everything else stays until dismissed, so no control a person must operate is timed. Every toast has a dismiss button; Escape and a swipe dismiss too. At most three are shown — a fourth drops the oldest timed one, else the oldest, which the principle makes safe. An equal toast (tone, formatted text, link destination, call and inputs) is not added again; the shown one restarts its timer. Reduced motion: no movement. Pinned as rows in `modules/ui/conformance/toasts.json`.

**Placement:** one region per application, `UiReact.App.toaster: { side, align }` — `side` and `align` as `Ui.Drawer` and `Ui.Popover` name them. Below the breakpoint it spans the width at its edge, above a tab bar.

**Accessibility:** `danger` is assertive, the rest polite; each is announced once with its button labels. Posting never moves focus; F8 reaches the region, Tab walks its buttons, focus returns where F8 took it from.

**The `Toaster` control.** A new layer control (group `overlay`, beside `Tooltip` and `Popover`) makes the controls contract `ui_react_controls-5`, as each earlier layer control made a generation (`Navigation` the second, `Combobox` the fourth): 26 controls, eleven of them layer controls, still replaced as one unit (`UI_CONTROLS_LAYERS_PARTIAL` counts eleven), so a set implementing the ten of `ui_react_controls-4` is refused. It must come from the same implementation as the stack it stays out of, which is why it is in the unit. The renderer hosts `ui_react_controls-5` alone, as it hosts `-4` alone today; `ui-react-conformance`'s vectors and scenes move with it.

- **Props:** `items`, each `{ key, tone, children }` (`children` the renderer's `toast-text` and `toast-actions`); `side`; `align`; `label` (keyed text `toaster`); `dismissLabel` (the existing keyed text `close`).
- **Intents:** `onDismiss(key, reason)`, `reason` a `CloseReason` — `escape`, or `close` for its dismiss button and a swipe, never `outside`; `onPauseChange(paused)`, `true` while the pointer is over the toaster or focus is inside it.
- **Owned by the renderer:** timers (and the document being hidden), the limit and deduplication. **Owned by the control:** the `toaster` part at the end of `<body>` with `data-telo-layer`, the `toast` part (`data-state`, `data-tone`), announcements, F8 and swipe.
- **Outside the stack** — the toaster is drawn as a layer but is never a member of the stack, as a Radix `DismissableLayer.Branch` is not:
  1. Escape outside the toaster goes to the stack as usual: with a dialog open, Escape in the dialog closes the dialog and the toast stays.
  2. Escape inside the toaster dismisses the focused toast and never reaches the stack; focus moves to the next toast, else back where F8 took it from — inside a dialog included.
  3. A press or focus inside the toaster closes no layer: Undo pressed with a non-modal drawer, a popover or an open Select list leaves them open.
  4. A modal opened while a toast is up never sets `inert` or `aria-hidden` on the toaster, a toast or any of their ancestors; every `toast` and what it holds keeps a computed `pointer-events` other than `none`; its trap admits focus into the toaster only through F8.

`ui-react-radix` draws the toaster on the DOM itself — Radix Toast would join Radix's layer stack — and keeps it out of its stack through its layers' own dismissal vetoes, its set and theme moving to `ui_react_controls-5`. The renderer posts nothing of its own: the event stream carries only `hello`, and every read and write reports its own failure where it was made.

**Components.** A component posts into the same toaster through a host field `toast({ text, tone?, link? })` added to `ui_react-1` (additive, no new ABI): `text` a string in the component's words, `tone` default `info`, `link` `{ to, label }` with `to` an app-relative reference resolved as the host's `navigate` resolves it. It returns `{ dismiss }`, a handle that can take more members later. Timing, limit and keys are the renderer's; two posts are equal when tone, text and link match. A component offering Undo draws it in its own output.

**Wire.** The effect specs `{ type: toast, text, tone, link?, call? }` (`tone` always present, `link` a `PressSpec`, `call` a press spec `{ mutation, inputs, label, onSuccess, onFailure }`, `onFailure` holding the filled default when the manifest omits it) and `{ type: close }`, each tag one-to-one with its kind; `onFailure` beside every `onSuccess` — every call spec and the `form` node — `[]` when none; a listing's `delete` is `false` or `{ onSuccess, onFailure }` (`true` is `{ onSuccess: [], onFailure: [] }`); the application document carries `toaster: { side, align }`. New keyed text, in `Ui.Translations` and all fourteen translations: `toaster`.

## Decisions

- **A toast is an effect, not a key.** It sits in the same ordered list as the destinations, so "go there, then say so" is two entries and a later effect kind joins with no new key.
- **Toasts are declared, not returned by the API** — a server-supplied text would be unchecked and untranslated; a page binds `result.<field>` when it wants the server's words.
- **Content is a text, not a node tree** — a live region cannot announce a layout, and a tree would open a second layout surface.
- **A toast's buttons are presses, named by `label`** — `link` is a `Ui.Press`, `call` a `Ui.MutationPress`: a destination never runs an operation, and the call's trees, `prompt`, `confirm` and `enabled` mean nothing in a toast, so the shape a toast holds lacks them instead of a rule refusing them. Its inputs are refused as every call's are (`CONTRACT_INPUTS_MISMATCH`, twin `ERR_UI_MUTATION_CALL_INPUTS_INVALID`).
- **`Ui.Close` is an effect, not a destination** — every destination has an address and is drawn as a link; listing the allowed kinds at a toast's `link.to` instead would refuse another module's destination kind there.
- **Tone is a plain enum, not kinds and not `style`** — it changes behaviour (politeness, timing), not keys.
- **No author `duration`, and actionable toasts are never timed** — a timer on a control a person must operate fails anyone who cannot reach it in time.
- **A bounded display, made safe by the principle** — any bound can drop a toast, and an unbounded or "+N" stack only moves the bound; safety comes from a toast never being the only way to act, which `toasts.md`, the primer and the hub guide teach.
- **One app-level region, not a page node** — toasts must survive navigation and share one announcer and stack.
- **A layer control in the one-unit set, outside the stack** — a region outside the unit would be made inert by the set's modals; a region inside the stack would let Escape in a dialog dismiss a toast, or a press on Undo close the drawer beside it.
- **`onFailure` beside every `onSuccess`, a form's pair on the form** — a form makes one submit write, so its lists sit on the form, as the action-form plan puts `onSuccess`, and `onSubmit` holds none.
- **Reads, chat and copy do not post** — a query node keeps its `failure` tree, the chat draws outcomes in the transcript, the copy button keeps its local check glyph and announcement.
- **The renderer posts nothing when the event stream drops** — the stream carries only `hello`, reconnects routinely (idle proxies, sleep, deploys), and its loss impairs nothing the person does.
- **Components post into the one toaster, text and link only** — a component drawing its own toast layer would bring a second announcer and stack; a press would need a second press machine beside `Ui.MutationPress`.
- **No new `UI_*` rule** — every refusal is the generic machinery: `SCHEMA_VIOLATION`, `REFERENCE_KIND_MISMATCH` for anything but an effect in an effect list or a destination at `link.to`, the path-template codes, `CEL_UNKNOWN_IDENTIFIER` (e.g. `result` in an `onFailure` list), `CONTRACT_INPUTS_MISMATCH`, `MESSAGE_PLACEHOLDER_UNBOUND`; the body-read rule counts an effect reading `result`. A press leading back to its own mutation is not a cycle.
- **No `requires:` floor** — only keys and shapes on `ui`'s and `ui-react`'s own kinds, delivered in their artifacts, using no annotation the analyzer does not already read.

## Verify

- A row archived and refreshed off the list still shows its toast with working View and Undo; Undo's own `onSuccess` posts "Restored."; a failing Undo leaves the toast pressable and posts one `danger` toast with the error's message.
- Dismissing, or dropping by the limit, a toast whose Undo is pending still posts "Restored." on success, or the `danger` toast on failure.
- A failed archive keeps the row's `failure` tree and posts a toast whose Retry sends the archive request again and posts "Apollo archived." on success; `telo check` passes it.
- Delete posts "Apollo deleted."; a 500 on delete keeps the confirmation open with the failure in it and posts the failure toast.
- The rename sends `PATCH /api/projects/1` and posts "Saved." once the drawer has closed, and on `/projects/1` reached by its address, where the form stays.
- Archive inside the drawer closes it, then posts "Apollo archived.".
- Create moves to `/projects/3` and shows "Artemis created." there; a 500 on create draws the form's `failure` tree and posts the failure toast; an `autosave` failure runs no `onFailure`; a `Ui.Navigate` to an address no page declares drops every toast.
- A failed board drop draws its `failure` on the record and runs `Ui.Move.onFailure`.
- View from the archive toast opens the project page in a default dialog; an `Ui.OpenPage` there into a `Ui.Popover` with a drawer `compact` opens the drawer.
- Five posts show three; four Undo toasts drop the first, whose project the Archived page still restores; a repeated failure shows once.
- Omitting `toaster` gives the same application document as `{ side: bottom, align: end }`.
- With both control sets: Escape in an open dialog closes the dialog and leaves the toast; F8 from inside the dialog's trap focuses the toast, Escape there dismisses only it and focus returns into the dialog; Undo pressed with a popover, a non-modal drawer and an open Select list closes none of them; a modal opened after a toast leaves the toaster free of `inert` and `aria-hidden` and its toasts pressable; hovering the toaster reports `onPauseChange(true)`, leaving it `false`.
- A ten-of-eleven layer set is refused; a copy press leaves the toaster empty; killing and reopening the event stream posts nothing.
- A test component's `toast({ text: "Saved", link: { label: "Open", to: "/drafts/7" } })` shows one sticky toast in the same stack as a declared one; calling `dismiss` removes it.
