# IDE support — package guide

Loaded when working under `packages/ide-support/`. Repo-wide rules live in the root `CLAUDE.md`. Every answer this package gives is the analyzer's, never a re-implementation: CEL scope (`CelScopeQuery`), `ManifestAnalysis`, `DiagnosticFix` and the upgrade-compatibility verdict are described in `analyzer/nodejs/CLAUDE.md`.

## CEL colouring

**CEL is COLOURED through the semantic layer, never a grammar** (`packages/ide-support/src/cel/tokens.ts`, consumed by `buildSemanticTokens`): both hosts already share that function, so a Monarch tokenizer beside the VS Code TextMate one would be a second CEL lexer to hold in agreement — and a grammar can only know the roots someone hardcoded into it, which is why `request` and `steps` went uncoloured while the stock YAML grammar painted the whole `!cel` scalar as the string it is not. Scope-aware: a name the resolved scope confirms is coloured, one it cannot is left alone (the unresolved-`kind:` signal), and with no query names colour syntactically so a body never reads as a plain string. **Colour encodes what a symbol IS, never the shape of the value behind it** — the chain ROOT is a `namespace` (a scope the runtime injects, not data the author declared) and its members are uniformly `property`, so a chain reads as scope · path; object-vs-scalar colouring is type-directed highlighting, which turns the palette into a type legend, moves a name's colour as analysis resolves, and says nothing exactly where the scope declares no shape. New token types are APPENDED to `SEMANTIC_TOKEN_LEGEND` — a host registers it once at activation, so an insert repaints every existing token. **Where the CEL is in a scalar is the ENGINE's answer** (`expressionRegions`, read through the analyzer's `celSegments()`): the whole body of `!cel`, each hole of `!interpolate` / `!sql`, nothing in a plain string — so colouring, completion, hover, go-to-definition and rename work inside the holes of any tag without naming it, and a still-unclosed hole yields an `open` segment for completion mid-typing.

## Rename

- "rename this and everything that references it" → `packages/ide-support/src/rename/` (`build-rename.ts` the entry points + every refusal, `find-sites.ts` the site discovery), `packages/ide-support/src/cel-chain.ts` (the shared CEL-chain walk), `ide/vscode/src/rename.ts`. **A rename is a refactor, not a `DiagnosticFix`** — a fix replaces one node, a rename is correct only when every reference moves with it — so it is never offered as a quick fix. Edits are precise sub-spans: a `!ref` scalar's AST range is its value (tag excluded) and a CEL identifier's is `CelNode.propertyRange`, so renaming a step inside one hole of an `!interpolate` scalar touches nothing else. Three surfaces are renameable because their reference set is enumerable from the workspace (resource instance, `Run` step, `variables`/`secrets`/`ports` key); everything else refuses **with its reason**, never an empty result, since a refusal here means the name has too MANY references. The load-bearing refusals: an `exports.resources` entry or a `Telo.Library`'s declared config key (public surface — a breaking change to version, not an edit to apply), and a name declared twice in reach (a `with:`-scoped resource shadowing a module-level one — references resolve to different declarations). A step's edit set is document-scoped, because `steps.<name>.result` is readable only inside the declaring resource and a resource is one document. The new name goes through `checkName`, so a rename cannot introduce a name `telo check` would reject. The live buffer always stands in for the current file — the graph is a snapshot, and its offsets go stale.

## Elsewhere in this package

- Upgrade selection and per-version marking → `src/import-upgrades/version-compatibility.ts` (over the analyzer's `manifestCompatibility`; see the analyzer guide § `requires:`)
- Rendering a `DiagnosticFix` back into YAML → `src/diagnostics/fix-edit.ts`
- Which cascade of a broken import is held back → `src/diagnostics/graph-diagnostics.ts`
- CEL symbols, completion, hover, go-to-declaration → `src/cel/symbols.ts`, `src/completions/cel-completions.ts`, the CEL branch of `src/hover/build-hover.ts`, `src/definition/locate-step.ts`, `src/definition/locate-context-binding.ts`
- Which schema vocabulary completion offers where → `src/completions/prop-keys.ts`
- Which YAML tags a field takes → `src/value-tags/offered-value-tags.ts`, the one rule VS Code, studio's source view and studio's schema form share: a tag's produced type must fit the field's DECLARED schema (read with combinators kept — the merged leaf key completion uses would erase a union's branches), and an expression tag needs a field `AnalysisRegistry.celEvalModeAt` says is evaluated. Completion on a tag and on a module-relative path → `src/completions/value-tag-completions.ts`, `src/completions/module-file-completions.ts`; the host lists entries against the MODULE ROOT (`listModuleEntries`), since a partial's own directory is not where its paths are measured from
- Module calls → `src/cel/module-calls.ts` (completion after `<Module>.`, hover with signature and determinism, `buildSignatureHelp`, go-to-declaration, renaming a function with its call sites); every answer comes from `CelScope.moduleFunction` / `moduleFunctionsOf`
